一个 CPU，三个进程，全都处于就绪态。

谁先跑？

这个问题每毫秒都要回答一次。

先看一组数字。

三个进程同时到达，运行时间分别是 10、1、1。

按 A → B → C 的顺序跑：

```text
时间   0          10 11 12
A      ██████████
B                  ██
C                     █
```

周转时间：A = 10，B = 11，C = 12，平均 11。

带权周转时间：A = 10/10 = 1，B = 11/1 = 11，C = 12/1 = 12，平均 8。

改成 B → C → A：

```text
时间   0  1  2          12
B      ██
C         █
A            ██████████
```

周转时间：B = 1，C = 2，A = 12，平均 5。

带权周转时间：B = 1，C = 2，A = 12/10 = 1.2，平均 1.4。

平均周转从 11 降到 5，平均带权从 8 降到 1.4。

一行代码没改，只是换了个顺序。

调度算法研究的就是这一件事：换哪个顺序。

## 1. 这个问题解决什么：三个问题与一条时间轴

CPU 只有一个，就绪进程有几百个。

调度器要在这条时间轴上，给每个进程切出一段一段的 CPU 时间。

它每次只回答三个问题：

```text
选谁：从就绪队列里挑一个
跑多久：给多少时间片，或者让它跑到阻塞为止
什么时候换：什么事件发生时重新做上面两个决定
```

第一个问题叫策略，第二个问题叫粒度，第三个问题叫时机。

408 的选择题几乎都在这三个词的边界上出。

比如"时间片过大"会退化成先来先服务，"时间片过小"会让切换开销吃掉 CPU。

再比如"进程主动阻塞"和"时间片用完"都会让出 CPU，但前者是非抢占的必然结果，后者是抢占的触发条件。

调度的目标不是让某个进程跑得快。

是让一批指标在整体上好看。

这句话听着正常，但它埋了整篇最反直觉的伏笔，第 5 节再说。

再说频率。

一次调度决策本身要花时间：读队列、比优先级、更新数据结构、写日志。

如果时钟每 1 ms 打一次中断，每次决策花 5 μs，光决策就吃掉 0.5% 的 CPU。

看着不多。

但这是"每秒一千次的固定税"，而且它发生在最不该慢的地方——中断上下文里。

所以内核的调度器写得极其克制：CFS 选下一个进程就是取红黑树最左节点，O(1) 取，O(log n) 插入。

408 不考这个复杂度，但你要知道"为什么不能在这里做全表扫描"。

因为它是热路径，热到每毫秒一次。

## 2. 三级调度：作业、内存、进程

调度不是一个函数，是三个层次的决策。

```text
          外存                          内存
 ┌───────────────────┐          ┌──────────────────┐
 │     后备队列       │──①高级──▶│     就绪队列      │──③低级──▶ 运行
 │  （作业 / 进程）    │          │                  │
 │                   │◀─②中级──▶│     阻塞队列      │
 │     挂起队列       │ 挂起/激活 │                  │
 └───────────────────┘          └──────────────────┘
```

**高级调度（high-level scheduling）**，也叫作业调度。

它决定把外存后备队列里的哪个作业调入内存，为它建 PCB、分配资源、放进就绪队列。

高级调度的频率最低，因为一次调入意味着一大堆准备工作。

批处理系统离不开它，分时系统里往往根本没有"作业"这个概念，所以也就没有高级调度。

高级调度还控制一个关键数字：多道程序度（degree of multiprogramming）。

内存里同时放几个进程，就是这个度。

**中级调度（medium-level scheduling）**，也叫内存调度。

它管的是"挂起"和"激活"。

内存紧张时，把某个进程整个换出到外存，状态变成就绪挂起或阻塞挂起。

内存宽松时，再把它换回来，状态变回就绪或阻塞。

这里有一个极易混的点：**中级调度换出的是整个进程，不是一页。**

换页是内存管理里请求分页干的事，颗粒度是 4 KB。

中级调度的颗粒度是"一个进程的全部地址空间"。

被挂起的进程不参与低级调度，因为它人都不在内存里。

为什么需要它？

算一笔账。

内存 4 GB，每个进程实际占用 500 MB，同时只能放 8 个。

第 9 个进程来了，要么拒绝，要么腾地方。

腾地方有两个办法：换出一整页（内存管理干的），或者换出一整个进程（中级调度干的）。

如果那个进程已经阻塞了很久，比如在等一个几秒后才到的网络包，把它的 500 MB 全换出去最划算。

内存腾出来了，多道程序度上升，CPU 的等待时间变短。

这就是中级调度存在的理由：它用磁盘换内存，用内存换 CPU 利用率。

**低级调度（low-level scheduling）**，就是进程调度。

从内存的就绪队列里选一个，把 CPU 给它。

它的频率最高，一次时间片用完就要做一次。

所以它必须快，不能在里面做搜索整张表这种重活。

把三者放进七态模型里，位置就清楚了。

先把五态画出来：

```text
              创建
               │
               ▼
         ┌──────────┐   ③ 调度    ┌──────────┐
         │   就绪   │ ──────────▶ │   运行   │ ──▶ 终止
         └──────────┘ ◀────────── └──────────┘
              ▲      时间片到或被抢占   │
              │                        │ 等待事件
              │       事件发生          ▼
              └──────────────────┌──────────┐
                                 │   阻塞   │
                                 └──────────┘
```

再把"挂起"这一层加上，五态就变成七态：

```text
活动就绪 ──挂起──▶ 静止就绪      活动阻塞 ──挂起──▶ 静止阻塞
活动就绪 ◀──激活── 静止就绪      活动阻塞 ◀──激活── 静止阻塞
活动阻塞 ──事件──▶ 活动就绪      静止阻塞 ──事件──▶ 静止就绪
```

前两行是中级调度的动作。

第三行是外部事件发生，注意方向：事件只让"阻塞"变成"就绪"，不会直接变成运行。

合起来，合法的转换只有这些：

```text
活动就绪 --挂起--> 静止就绪
活动阻塞 --挂起--> 静止阻塞
静止就绪 --激活--> 活动就绪
静止阻塞 --激活--> 活动阻塞
活动阻塞 --事件发生--> 活动就绪
静止阻塞 --事件发生--> 静止就绪
运行 --等待事件--> 活动阻塞
运行 --时间片到--> 活动就绪
活动就绪 --③低级调度--> 运行
运行 --终止--> 终止
```

408 常考的是"下列转换哪个不可能"。

比如 静止阻塞 → 运行，不可能，它既没在内存也没被调度。

比如 静止就绪 → 活动阻塞，不可能，就绪态的进程还没开始跑，谈不上等事件。

## 3. 五个常用指标，加一个派生量

评价调度好不好，靠的是几个能从甘特图上直接量出来的数。

常说的是五个：CPU 利用率、吞吐量、周转时间、等待时间、响应时间。

带权周转时间是从周转派生出来的第六个，考得一样多，一起算。

```text
CPU 利用率   = CPU 有效工作时间 / (有效工作时间 + 空闲时间) × 100%
吞吐量       = 完成的作业数 / 总时间
周转时间     = 完成时间 − 到达时间
带权周转时间 = 周转时间 / 实际运行时间
等待时间     = 周转时间 − 实际运行时间
响应时间     = 首次开始运行的时间 − 到达时间
```

逐个说清定义里的坑。

**CPU 利用率**的分母是总时间，不是"CPU 忙碌时间"。

所以空闲的每一纳秒都在拉低它。

**吞吐量**的单位是"个/单位时间"，不是"个"。

单位时间没写清，答案就错一半。

**周转时间**从到达那一刻开始算，不是从开始运行那一刻。

一个进程 0 时刻到达，等了 5 个单位才开始跑，跑 3 个单位完成，周转是 8，不是 3。

**带权周转时间**是周转除以实际运行时间，它没有量纲。

它的作用是把"运行时间长短"这个因素除掉，让长短作业可以放在一起比。

对任何进程，带权周转时间都 ≥ 1，因为周转 = 等待 + 运行 ≥ 运行。

**等待时间**只算在就绪队列里排队的时间，不算 I/O 等待。

那被抢占之后重新排队的时间算不算？

算，那也算等待。

所以等待时间等于周转减去运行，这个等式在"只考虑 CPU 时间"的前提下永远成立。

**响应时间**只看第一次被响应。

一个进程被反复抢占，响应时间可以很小，等待时间却很大。

这是 408 最爱设的陷阱之一，第 4 节算一遍就明白。

不同系统关心不同指标。

```text
批处理系统：吞吐量、CPU 利用率、周转时间
分时系统：  响应时间、公平性
实时系统：  截止时间的满足率
```

公式还能反过来用。

四个进程同时到达，非抢占，按到达顺序跑，已知其中三个的运行时间是 1、2、3。

平均周转时间是 6，求第四个进程的运行时间。

同时到达意味着到达时间都是 0，所以周转就是完成时间。

```text
完成时刻：1、3、6、6+x      （x 是第四个的运行时间）
平均周转 = (1 + 3 + 6 + 6 + x) / 4 = (16 + x) / 4 = 6
16 + x = 24
x = 8
```

这种逆问题在 408 里出现得不多，但一旦出现，很多人的第一反应是"条件不够"。

条件够，因为同时到达把"等待"这一项消掉了。

## 4. 一次完整走查：从甘特图把指标全算一遍

三个进程：

```text
进程   到达   运行
P1      0     5
P2      1     2
P3      2     1
```

采用抢占式调度，P2 到达时抢了 P1 的 CPU，P3 到达时 P2 已经快跑完，没抢成。

时间轴：

```text
时间   0   1   2   3   4   5   6   7   8
P1     █   ·   ·   █   █   █   █   ·
P2     ·   █   █   ·   ·   ·   ·   ·
P3     ·   ·   ·   ·   ·   ·   ·   █
```

一格一个单位时间，`·` 表示不在运行。

逐项算。

```text
P1：到达 0，首次运行 0，完成 7
   周转 = 7 − 0 = 7      带权 = 7 / 5 = 1.40
   等待 = 7 − 5 = 2      响应 = 0 − 0 = 0

P2：到达 1，首次运行 1，完成 3
   周转 = 3 − 1 = 2      带权 = 2 / 2 = 1.00
   等待 = 2 − 2 = 0      响应 = 1 − 1 = 0

P3：到达 2，首次运行 7，完成 8
   周转 = 8 − 2 = 6      带权 = 6 / 1 = 6.00
   等待 = 6 − 1 = 5      响应 = 7 − 2 = 5
```

汇总：

```text
平均周转     = (7 + 2 + 6) / 3 = 15 / 3 = 5.00
平均带权周转 = (1.40 + 1.00 + 6.00) / 3 = 8.40 / 3 = 2.80
平均等待     = (2 + 0 + 5) / 3 = 7 / 3 = 2.33
平均响应     = (0 + 0 + 5) / 3 = 5 / 3 = 1.67
吞吐量       = 3 / 8 = 0.375 个/单位时间
CPU 利用率   = 8 / 8 = 100%
```

P1 的响应是 0，等待是 2。

这两个数不一样，因为 P1 在 0 时刻就被响应了，但中途被抢了一次，又在就绪队列里待了 2 个单位。

这就是响应时间和等待时间的区别：一个看"第一次"，一个看"总共"。

P3 的数字最难看：等 5 个单位，只跑 1 个。

因为它是最后到达的短作业，前面两个都在它前面。

短作业在后，是抢占式调度最不擅长处理的场景之一。

## 5. 目标之间的矛盾，和那个反直觉的点

调度要同时满足四个愿望，它们互相打架。

**吞吐量 vs 响应时间。**

想让响应快，就多切换，多给小时间片。

但每次切换都要保存现场、换页表、刷 TLB，这些时间不产生任何吞吐。

极端情况下，时间片 0.1 ms、切换开销 0.05 ms，三分之一的 CPU 时间花在换人上。

**吞吐量 vs 公平性。**

最公平的做法是每个进程轮流跑一小段。

但一个长作业被切成一百段之后，每次重新上 CPU，它的 cache 和 TLB 都是冷的。

跑得越碎，实际完成得越慢。

**周转时间 vs 带权周转时间。**

这两个指标的最优解可以指向完全相反的顺序。

再看本系列反复出现的那个算例，只是把规模放大一点。

一个长作业，运行 10 个单位。

一百个短作业，每个运行 1 个单位，和长作业同时到达。

按短作业优先，一百个短作业先跑完，长作业最后跑。

```text
长作业：等待 100，周转 110，带权 = 110 / 10 = 11
短作业：等待 0～99，周转 1～100，带权 ≈ 1
平均周转 = (1+2+...+100 + 110) / 101 = 5160 / 101 ≈ 51.1
```

按到达顺序，长作业先跑。

```text
长作业：周转 10，带权 = 1
短作业：等待 10～109，带权 = 11～110
平均周转 = 6060 / 101 ≈ 60.0，平均带权 ≈ 60
```

短作业优先把平均周转压到了 51.1，代价是长作业的带权周转从 1 涨到了 11。

反过来先来先服务，长作业的带权周转是 1，短作业的带权周转却涨到了 110。

**所以那个反直觉的点是：**

> **平均周转时间最小的调度，往往让短作业先跑，结果长作业的带权和等待时间一起爆炸。**
> **"公平"和"最优"在调度里是敌人，你选哪个指标，就决定哪一批进程被牺牲。**

这句话不是修辞。

上例里，短作业优先让长作业多等了 100 个单位，而它的运行时间只有 10。

换成先来先服务，被牺牲的就变成了一百个短作业，它们的带权周转最高到 110。

任何一个调度算法都要在"平均最优"和"个体最惨"之间选一个立场。

时间片轮转选后者，短作业优先选前者。

实时调度干脆不看平均值，只看有没有人错过截止时间。

还有第四组矛盾：平均 vs 最坏。

实时系统关心的是最坏情况，不是平均情况。

一个调度器让 999 次请求都在 1 ms 内响应，第 1000 次用了 500 ms，平均是 1.5 ms，很好看。

但错过截止时间的那一次，可能让刹车晚半秒。

所以实时调度不用"平均周转"当指标，用"可调度性"——能不能证明每一个任务都在截止时间前完成。

这也是第 06 篇要单讲 EDF 和 RMS 的原因。

最后一种更极端的失效叫饥饿（starvation）。

优先级调度里，如果高优先级进程源源不断地来，低优先级进程可能永远排不上队。

这时候它的周转时间是无穷大，平均值根本不存在。

"算不出来"比"算出来很难看"严重得多。

## 6. 408 怎么考

这一节的题型很固定，三类。

```text
① 给到达时间与运行时间，算平均周转 / 平均带权周转
② 判断某个时刻"该不该调度"，或者"会发生什么转换"
③ 概念辨析：三级调度的分工、抢占与非抢占的触发条件
```

第一类是送分题，前提是时间轴画对。

第二类是丢分题，前提是分清"抢占式"和"非抢占式"。

下面是一道自拟题，覆盖前两类。

四个进程：

```text
进程   到达   运行
P1      0     7
P2      2     4
P3      4     1
P4      5     4
```

第一问：先来先服务的平均周转与平均带权周转。

非抢占，按到达顺序跑，到达相同按编号。

```text
P1  0 → 7    周转 7     带权 7/7  = 1.00
P2  7 → 11   周转 9     带权 9/4  = 2.25
P3  11 → 12  周转 8     带权 8/1  = 8.00
P4  12 → 16  周转 11    带权 11/4 = 2.75

平均周转     = (7 + 9 + 8 + 11) / 4 = 35 / 4 = 8.75
平均带权周转 = (1 + 2.25 + 8 + 2.75) / 4 = 14 / 4 = 3.50
```

注意 P3：它到达是 4，完成是 12，周转 8，运行只有 1，所以带权是 8。

一个 1 单位的短作业被前面两个长作业压了 8 倍，这就是护航效应。

第二问：非抢占式短作业优先的平均周转。

P1 在 0 时刻独占 CPU，谁也抢不了，只能先跑完。

```text
P1  0 → 7    周转 7
P3  7 → 8    周转 4      （剩下三个里最短）
P2  8 → 12   周转 10
P4  12 → 16  周转 11

平均周转 = (7 + 4 + 10 + 11) / 4 = 32 / 4 = 8.00
平均带权 = (1 + 4 + 2.5 + 2.75) / 4 = 10.25 / 4 = 2.5625
```

只从 8.75 降到 8.00。

为什么降这么少？

因为 P1 是非抢占的，它一个人占着 CPU 跑了 7 个单位，短作业优先根本没机会生效。

第三问：改成抢占式短作业优先（SRTN），平均周转是多少。

```text
t=0  P1 跑，剩余 7
t=2  P2 到，需 4 < P1 剩余 5，切换
t=4  P3 到，需 1 < P2 剩余 2，切换
     P3 跑 4 → 5，完成，周转 1
t=5  P4 到，需 4；P2 剩 2；P1 剩 5 → 选 P2
     P2 跑 5 → 7，完成，周转 5
t=7  P4 需 4 < P1 剩 5 → 选 P4
     P4 跑 7 → 11，完成，周转 6
t=11 P1 跑 11 → 16，完成，周转 16

平均周转     = (16 + 5 + 1 + 6) / 4 = 28 / 4 = 7.00
平均带权周转 = (16/7 + 5/4 + 1/1 + 6/4) / 4
             = (2.2857 + 1.25 + 1 + 1.5) / 4
             = 6.0357 / 4 = 1.51
```

三个结果排在一起：

```text
FCFS   平均周转 8.75   平均带权 3.50
SJF    平均周转 8.00   平均带权 2.56
SRTN   平均周转 7.00   平均带权 1.51
```

代价写在最后一行：P1 的周转从 7 涨到了 16。

它的带权从 1.00 涨到 2.29，翻了一倍多。

第四问，判断型：

"t = 2 时 P2 到达，系统是否立即切换？"

答案取决于题干给的调度方式，不取决于"P2 更短"。

```text
若题干说"非抢占式"：不切换，P1 继续跑完 7 个单位。
若题干说"抢占式"或"SRTN"：切换，因为 P2 剩余 4 < P1 剩余 5。
```

考场上的套路只有四条：

```text
1. 先画一条时间轴，标出每个到达时刻
2. 每个时刻只比较"已到达"的进程，没到的不能算
3. 周转从到达算起，不从开始运行算起
4. 带权一定要除运行时间，别忘了
```

## 7. 真实系统里长什么样

Linux 的调度器不是"一个算法"，是五个调度类按优先级排队。

```text
stop       最高，只有迁移线程和热插拔用
deadline   截止时间调度，给实时性要求最硬的场景
rt         实时，SCHED_FIFO / SCHED_RR
fair       普通进程，nice 值决定权重
idle       最低，只在没事干时跑
```

调度入口是 `schedule()`，真正干活的是 `__schedule()`（简化示意）。

它做四件事：关抢占、挑下一个任务、切换、重新开抢占。

"该不该抢占"靠一个标志位 `need_resched`。

时钟中断、唤醒更高优先级进程、系统调用返回，都会把它置上。

内核在几个固定位置检查它，最常见的是从系统调用或中断返回用户态之前。

所以"抢占"不是随时随地把人拽下来，而是在允许的时间点检查。

这也是"不能让调度发生在内核临界区"的落地方式，第 8 节细说。

普通进程的调度类叫 fair。

它长期用 CFS（完全公平调度器），核心是一个叫 `vruntime` 的虚拟运行时间。

每跑一段时间，`vruntime` 就涨一点，涨得慢的进程被优先选中。

就绪队列是一棵按 `vruntime` 排序的红黑树，选下一个就是取最左节点。

Linux 6.6 起，fair 类换成了 EEVDF，但 `vruntime` 加红黑树这套骨架没变。

优先级不叫优先级，叫 nice 值，范围 −20 到 19。

nice 每降 1，CPU 权重涨大约 1.25 倍，这个比例是设计出来的，不是实测的。

xV6 的调度器简单到可以直接读完。

`scheduler()` 在一个死循环里遍历进程表，找到第一个 `RUNNABLE` 的进程，调用 `swtch()` 换过去（简化示意）。

没有优先级，没有时间片计数，没有红黑树。

抢占靠时钟中断：中断进来后调用 `yield()`，把当前进程从 `RUNNING` 改回 `RUNNABLE`，再进调度器。

如果找不到可跑的进程，xV6 执行 `wfi` 让 CPU 睡到下一个中断。

这就是"闲逛"在这套代码里的形态。

## 8. 抢占式、非抢占式，与四个调度时机

**非抢占式（non-preemptive）**：进程一旦拿到 CPU，就一直跑到它自己放弃。

放弃只有两种：正常结束，或者主动阻塞。

**抢占式（preemptive）**：操作系统可以在进程不配合的情况下把 CPU 收回来。

收回的理由通常有两个：时间片用完，或者来了个更该跑的。

抢占的物理基础是时钟中断。

没有周期性中断，内核根本不知道一个进程跑了多久。

所以"分时"这件事，本质上是"用中断把 CPU 抢回来"。

调度可以发生的时机，408 归纳成四种：

```text
① 进程创建：新进程进入就绪队列，可能触发抢占
② 进程终止：CPU 空出来了，必须重新选一个
③ 进程阻塞：主动让出 CPU，必须重新选一个
④ 就绪队列变化：时间片到、更高优先级进程被唤醒、中断返回
```

前三种非抢占式也会发生。

第四种是非抢占式不会发生的，因为它要求"在别人正跑着的时候做决定"。

再补一条容易漏的：中断处理结束、返回用户态之前，也是一个检查点。

因为中断可能唤醒了某个高优先级进程。

Linux 把这件事做成了编译期选项，三档（简化示意）：

```text
CONFIG_PREEMPT_NONE      内核态不抢占，只有返回用户态时才可能换人
CONFIG_PREEMPT_VOLUNTARY 内核代码里显式插入检查点，主动让
CONFIG_PREEMPT           内核态也能被抢占，实时性最好，吞吐最差
```

三档的取舍，正好是第 5 节那几组矛盾的工业版。

服务器选第一档，图吞吐。

桌面选第二或第三档，图响应。

实时系统必须第三档，因为"最坏延迟"比"平均吞吐"重要得多。

有一句话要记住：

**调度不能发生在内核临界区里。**

内核正在改就绪队列、正持有一把自旋锁、正关着中断的时候，不能切走。

切走了，另一个进程进来看到的是改了一半的数据结构。

Linux 用 `preempt_count` 计数来解决：这个数不为 0，就不许抢占。

## 9. 一次切换做了什么，闲逛进程为什么存在

调度是"决定"，切换是"执行"。

一次完整的进程切换分四步。

```text
① 保存现场
   把当前进程的 PC、通用寄存器、PSW、栈指针
   存进它的 PCB 或者内核栈

② 选进程
   调用调度器，从就绪队列挑一个

③ 切换
   换内核栈、换页表基址寄存器（x86 上是 CR3）
   必要时刷 TLB

④ 恢复现场
   从新进程的 PCB 里恢复寄存器，跳到它上次停下的地方
```

开销分两类。

直接开销是执行这几步指令的时间，微秒量级。

间接开销更贵：新进程的代码和数据不在 cache 里，页表换了 TLB 要重新填。

一个刚被切回来的进程，前几万条指令可能都在等内存。

这就是"时间片不能太短"的物理原因，下一篇会给具体数字。

区分两种"切换"，能省掉一道选择题。

```text
模式切换：用户态 → 内核态 → 用户态
         同一个进程，栈换到内核栈，不换页表
         发生在系统调用、中断、异常时，成本低

进程切换：进程 A → 进程 B
         换内核栈、换页表、刷 TLB、改 PCB
         成本高，因为它破坏了 cache 和 TLB 的局部性
```

线程切换介于两者之间。

同一个进程内的两个线程切换，页表不变，地址空间不变，只需要换寄存器和栈。

所以线程切换比进程切换便宜，这是多线程被大量使用的直接原因之一。

还有一个常被忽略的角色：闲逛进程（idle process）。

如果就绪队列空了，CPU 该跑什么？

答案是不能什么都不跑。

调度器的代码形态是"保存 A，切到 B"，B 必须存在。

所以每个 CPU 都有一个永远就绪、优先级最低的进程，Linux 里叫 `swapper/N`，pid 是 0。

它有三个特点：

```text
永远不会被阻塞（否则 CPU 就真的没东西可跑了）
永远可以被抢占（任何进程都比它优先）
运行时执行 hlt / wfi 之类的指令，让 CPU 进入低功耗状态
```

它还兼职一个功能：它的累计运行时间，就是 CPU 的空闲时间。

`top` 里那个 `idle` 百分比，来源就是它。

所以空闲不是"CPU 停着"，是"CPU 在跑一个特别的进程"。

## 10. 容易混淆的点

第一组：周转、等待、响应。

```text
周转 = 完成 − 到达          （全过程有多长）
等待 = 周转 − 运行          （其中排队占了多久）
响应 = 首次运行 − 到达      （多久看到第一眼反应）
```

非抢占时，等待和响应往往相等。

抢占时，一个进程可以响应很快、等待很久。

第二组：带权周转和周转。

带权不是"加权平均"，是"除以运行时间"。

它把长短作业拉到同一把尺子上，所以短作业被拖会显得特别难看。

第三组：中级调度和页面置换。

中级调度换出整个进程，页面置换换出一页。

前者改变进程状态（进七态模型），后者不改变进程状态。

第四组：调度和切换。

调度是选谁，切换是换过去。

选完了可以不换（比如选中的还是当前进程）。

第五组：抢占和时间片。

时间片是抢占的一种触发条件，不是抢占本身。

优先级抢占也是抢占，跟时间片没关系。

第六组：CPU 利用率高就是好？

不一定。

一个进程在自旋等锁，CPU 利用率 100%，但没干一点有用的活。

所以利用率要配合"有效工作"看。

第七组：作业和进程。

作业是"用户提交的一次任务"，可以是程序加数据。

进程是"程序的一次执行"，是资源分配单位。

批处理系统里，一个作业对应一个进程，从外存调入内存才成为进程。

分时系统里根本没作业这个概念，用户直接开进程。

所以高级调度又叫作业调度，这个别名就说明了它属于哪类系统。

第八组：调度时机和进程状态转换。

"进程阻塞"既是状态转换，也是调度时机。

"时间片到"既是状态转换（运行 → 就绪），也是调度时机。

两件事同时发生，但回答的问题不一样：一个问"它变成什么状态"，一个问"要不要换人"。
