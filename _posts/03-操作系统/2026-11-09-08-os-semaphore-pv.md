先看一段"看起来没问题"的代码。

```c
semaphore mutex = 1;   // 缓冲区互斥
semaphore empty = 8;   // 空位数
semaphore full  = 0;   // 产品数

// 生产者
while (true) {
    produce(item);
    P(mutex);      // ← 换了个位置
    P(empty);
    put(item);
    V(mutex);
    V(full);
}
```

两个 `P` 的位置调换了一下。

程序能跑，能生产，看起来一切正常。

直到缓冲区第一次被填满。

那一刻，生产者执行 `P(mutex)` 拿到了锁，然后执行 `P(empty)` 发现没有空位，阻塞。

它阻塞的时候，手里还握着 `mutex`。

消费者要取东西，得先 `P(full)`，这一步没问题，缓冲区是满的。

然后它执行 `P(mutex)`，锁在生产者手里。

消费者也阻塞。

```text
生产者：等空位，但持着 mutex
消费者：等 mutex，但空位的产生要靠消费者
```

两个人互相等，谁也不会动。

这就是死锁。

一行顺序，整个系统停摆。

## 1. 信号量：一个整数加一个队列

信号量（semaphore）是 Dijkstra 在 1965 年提出来的。

名字来自铁路信号灯，P 和 V 来自荷兰语 proberen（测试）和 verhogen（增加）。

所以别去英文里找 P 和 V 的全称，没有。

不同教材还有别的叫法：

```text
P = wait = down = 申请
V = signal = up = 释放
```

408 题干里这三种写法都可能出现，看到 `wait(S)` 就当 `P(S)`，看到 `signal(S)` 就当 `V(S)`。

它的全部内容就两样东西：

```text
一个整数 value
一个等待队列 L
```

最开始的版本叫整型信号量，只有一个整数。

```c
int S = 1;

void P(int *S) {          // P 来自荷兰语 proberen，测试
    while (*S <= 0) {
        // 空转
    }
    (*S)--;
}

void V(int *S) {          // V 来自 verhogen，增加
    (*S)++;
}
```

这个版本有个明显的毛病：`while` 空转。

它满足互斥，但不满足让权等待，和第 07 篇的 TSL 一个毛病。

于是有了记录型信号量，加了等待队列。

```c
typedef struct {
    int value;              // 剩余资源数，可以为负
    struct process *L;      // 等待队列
} semaphore;

void P(semaphore *S) {
    S->value--;
    if (S->value < 0) {
        block(S->L);        // 自己阻塞，进等待队列
    }
}

void V(semaphore *S) {
    S->value++;
    if (S->value <= 0) {
        wakeup(S->L);       // 唤醒队首的一个
    }
}
```

`block()` 和 `wakeup()` 是原语，由内核提供。

它们做的事是：把进程状态改成阻塞、挂到队列上、触发一次调度。

所以记录型信号量的 P 操作是能"让权"的。

为什么这个结构比锁强？

一把普通的锁只有两个状态：锁着、开着。

它能表达"现在有人占用"，但表达不了"已经有 3 个人在排队，还欠 2 个资源"。

信号量多出来的那个负数，就是"排队人数"。

这就是它能同时做互斥和同步的根本原因：它记住了"欠了多少"。

一个锁记不住欠账，所以锁做不了同步。

`value` 的含义，要分正负看：

```text
value > 0：还有 value 个资源可用
value = 0：刚好用完，没有进程在等
value < 0：|value| 个进程正在等这个资源
```

三个状态都要能读出来。

举个具体数：`value = −3`，意思是"资源已经欠了 3 个，有 3 个进程在队列里睡着"。

这个负数是 408 的高频考点，因为很多人只记"value 表示资源数"，看到负数就慌。

## 2. P 和 V：一个可能阻塞，一个绝不阻塞

把两个操作的动作拆开看。

```text
P(S)：
  ① value 减 1
  ② 如果减完小于 0，阻塞自己，进等待队列
  ③ 否则继续走

V(S)：
  ① value 加 1
  ② 如果加完小于等于 0，唤醒队列里的一个
  ③ 继续走
```

注意减法和判断的顺序：**先减后判断**。

为什么？

因为减完为负，说明"这次申请把资源透支了"，那自己就是那个欠账的人，得去排队。

如果先判断再减，判断和减之间就有窗口。

两个进程可能同时判断出"还有资源"，然后都去减，结果一起进场。

所以"减"和"判断"必须在同一个原子操作里完成。

V 是**先加后判断**。

加完是 `0` 或负数，说明队列里还有人等着，得叫醒一个。

加完是正数，说明没人等，资源就放在那儿。

最关键的一句话：

```text
P 可能阻塞，V 一定不阻塞。
```

P 阻塞是因为资源不够。

V 不阻塞是因为"释放"这个动作永远能完成，它只是把值加回去，顺手叫醒一个。

这条性质决定了后面所有的顺序规则。

因为只有会阻塞的操作，才有"阻塞时手里拿着什么"的问题。

`V` 不阻塞，所以它放在哪儿都不会造成死锁。

两个判断里的不等号，很容易记反，验一遍就知道为什么必须是这两个。

`P` 里为什么是 `value < 0`？

```text
value = 1（有一个资源）
  value-- → 0，0 < 0 为假 → 不阻塞，拿到资源 ✓

value = 0（没有资源）
  value-- → −1，−1 < 0 为真 → 阻塞 ✓

若写成 value <= 0：
value = 1 → 0，0 <= 0 为真 → 明明有资源却阻塞 ✗
```

`V` 里为什么是 `value <= 0`？

```text
value = −2（两个人在等）
  value++ → −1，−1 <= 0 → 唤醒一个，还剩一个 ✓

若写成 value < 0：
value = −1 → 0，0 < 0 为假 → 不唤醒，
但队列里还有一个人在睡，他永远等不到 ✗
```

一个 `<=` 写错，就有一个进程永远醒不过来。

这也是 408 改错题愿意考的地方。

## 3. 三种用法：互斥、同步、计数

同一个数据结构，三种完全不同的用法。

区别只在初值和配对方式。

```text
互斥：初值 1。P 和 V 包住临界区。
同步：初值 0。先做的 V，后做的 P。
计数：初值 n。P 拿走一个，V 还回一个。
```

**互斥**，初值 1，保护临界资源。

```c
semaphore mutex = 1;

P(mutex);
// 临界区
V(mutex);
```

初值 1 的意思是"一开始允许一个人进"。

第一个 `P` 把 1 减成 0，进了。

第二个 `P` 把 0 减成 −1，阻塞。

这正是我们要的。

**同步**，初值 0，保证顺序。

```c
semaphore s = 0;

// 进程 A（先做）
A1();
V(s);

// 进程 B（后做）
P(s);
B1();
```

初值 0 的意思是"一开始没有东西可等"。

B 如果先跑到 `P(s)`，会把 0 减成 −1，阻塞。

等 A 执行完 `V(s)`，值变回 0，唤醒 B。

如果 A 先跑完，`V(s)` 把值变成 1，B 再来 `P(s)` 时直接减成 0 通过。

所以"谁先跑"都不影响正确性，A 一定在 B 之前。

**计数**，初值 n，管 n 份相同的资源。

```c
semaphore seats = 4;    // 四个座位

P(seats);               // 占一个
// 使用
V(seats);               // 还一个
```

初值 4，第 5 个人来就会阻塞。

计数用法在实际系统里最常见的形式是连接池。

```text
数据库连接池最多 10 条连接，semaphore db = 10
取连接 → P(db)
还连接 → V(db)
```

这样第 11 个请求会乖乖排队，而不是把数据库打崩。

限流器、停车场、缓冲区空位，本质都是同一个东西。

这三种用法，就是信号量的全部。

> **反直觉的点在这里：**
> **信号量的 P/V 不是"加锁解锁"，而是"计数 + 排队"。**
> **它同时管互斥和同步，这也是它容易写错的原因：同一个数据结构，两套语义，全靠初值和位置区分。**

把 P/V 当 `lock/unlock` 用，就会写出本篇开头那种代码。

因为加锁解锁只关心"有没有人持有"，而信号量还关心"欠了几个、谁在等"。

## 4. 固定模式：互斥包住临界区，同步连成前趋图

两种模式的写法是固定的，背下来能省很多时间。

**互斥模式：**

```c
P(mutex);
临界区
V(mutex);
```

一对 P/V，包住临界区，中间不能有别的 P（会阻塞的那种）。

**同步模式：**

```c
// 先做的那个
V(s);

// 后做的那个
P(s);
```

一个 V 对应一个 P，写在不同进程里，方向不能反。

## 5. 生产者-消费者：三个信号量一起用

把两种模式合起来，就是生产者-消费者。

```c
semaphore mutex = 1;    // 缓冲区互斥
semaphore empty = n;    // 空位数
semaphore full  = 0;    // 产品数

// ---- 生产者 ----
while (true) {
    item = produce();
    P(empty);           // ① 先确认有空位
    P(mutex);           // ② 再进缓冲区
    put(item);
    V(mutex);           // ③ 离开缓冲区
    V(full);            // ④ 通知有新产品
}

// ---- 消费者 ----
while (true) {
    P(full);            // ⑤ 先确认有产品
    P(mutex);
    take(item);
    V(mutex);
    V(empty);           // ⑥ 通知有空位
    consume(item);
}
```

三件互斥、两件同步，全在一个例子里。

```text
mutex：互斥，初值 1，缓冲区同时只能一个人动
empty：同步 + 计数，初值 n，管"还有没有空位"
full ：同步 + 计数，初值 0，管"有没有产品"
```

为什么说 `empty` 和 `full` 既是同步又是计数？

它们同时在做两件事：记录数量（计数语义），和拦住不该走的进程（同步语义）。

走一遍，取 `n = 2`，两个生产者 P1、P2，一个消费者 C1。

```text
初始：mutex=1  empty=2  full=0  缓冲区 []

P1  P(empty) → empty=1
    P(mutex) → mutex=0
    put      → 缓冲区 [a]
    V(mutex) → mutex=1
    V(full)  → full=1

P2  P(empty) → empty=0
    P(mutex) → 0
    put      → [a, b]
    V(mutex) → 1
    V(full)  → full=2

P3  P(empty) → empty=−1 → 阻塞（进 empty 队列）

C1  P(full)  → full=1
    P(mutex) → 0
    take     → [b]
    V(mutex) → 1
    V(empty) → empty=0，且 0 ≤ 0 → 唤醒 P3

P3  （被唤醒，从 P(empty) 之后继续）
    P(mutex) → 0
    put      → [b, c]
    V(mutex) → 1
    V(full)  → full=2
```

注意 P3 被唤醒之后，不是重新执行 `P(empty)`，而是从它阻塞的地方继续。

它的 `empty` 已经减过了（减到 −1），`V(empty)` 把值加回 0 表示"这次的账平了"。

这就是记录型信号量把"欠账"记在 value 里的方式。

三个信号量的分工，再理一遍。

```text
mutex：纯互斥，初值 1，不表示任何数量
empty：既计数又同步，初值 n，表示"还能量几个"
full ：既计数又同步，初值 0，表示"能取几个"
```

为什么 `empty` 和 `full` 不用一个变量表示？

因为它们是两个方向。

`empty` 从 n 减到 0，`full` 从 0 加到 n，两者之和恒等于 n。

如果只用一个变量记录"缓冲区里有几个"，生产者和消费者就得共用同一套语义，谁是"加"谁是"减"就说不清了。

两个变量，各自只管一个方向，代码才读得懂。

如果缓冲区是循环队列，还要两个指针 `in` 和 `out`。

这两个指针不需要额外的信号量，但要放在 `mutex` 里面动。

```text
in  ：生产者放的位置，只被生产者改
out ：消费者取的位置，只被消费者改
```

严格说，写它们本身不冲突：in 只被生产者写，out 只被消费者写。

但判断"满没满"需要同时看两个指针，所以整个缓冲区结构仍然要用 `mutex` 包住。

这也说明"互斥"的边界不是"哪个变量被写"，而是"哪一段判断逻辑必须看到一致的状态"。

如果 `n = 1`，这个模型就退化成"单缓冲区"。

此时 `empty` 和 `full` 的值只可能是 0 或 1，语义上等价于两个开关。

很多教材的例子就是 `n = 1`，因为画图方便。

但考试时如果题目给了 `n`，初值就必须写 `n`，不能写 1。

## 6. 408 怎么考

PV 是 408 进程管理最稳的一道大题，题型三类：

```text
① 给前趋图，写 PV 操作，问需要几个信号量
② 给一段代码，问会不会死锁、错在哪、怎么改
③ 给一个场景（生产者消费者、读者写者、哲学家），写完整代码
```

第一类几乎每年换汤不换药。

下面用一张四个节点的前趋图做例题。

```text
        ┌──▶ S2 ──┐
 S1 ────┤         ├──▶ S4
        └──▶ S3 ──┘
```

第一问：至少需要几个信号量？

数边。

```text
S1 → S2
S1 → S3
S2 → S4
S3 → S4
```

四条边，四个信号量，初值全是 0。

第二问：写出 PV 代码。

```c
semaphore a = 0;   // S1 → S2
semaphore b = 0;   // S1 → S3
semaphore c = 0;   // S2 → S4
semaphore d = 0;   // S3 → S4

// S1
S1();
V(a);
V(b);

// S2
P(a);
S2();
V(c);

// S3
P(b);
S3();
V(d);

// S4
P(c);
P(d);
S4();
```

规则很简单：**边的起点 V，边的终点 P，一条边一个信号量。**

为什么初值必须是 0？

因为 0 表示"这件事还没发生"。

如果写成 1，S2 的 `P(a)` 一上来就能减成 0 通过，S2 会在 S1 之前跑，同步失效。

初值是"一开始允许通过的人数"，同步场景里一开始谁也不该通过，所以是 0。

互斥场景里一开始允许一个人进，所以是 1。

资源计数场景里一开始有 n 个，所以是 n。

三种初值，一个解释：初值就是"开局时手里的票数"。

S1 有两条出边，所以 V 两次。

S4 有两条入边，所以 P 两次。

第三问，判断题：如果把 S4 的两个 P 写成 `P(c); P(d);`，能换成 `P(d); P(c);` 吗？

能。

两个 P 都是在拿"已经发生"的信号，顺序不影响正确性。

但会引起一个细节差异：如果 c 和 d 不同时就绪，先 P 哪个决定了先等哪个。

只要两个都等到才执行 S4，结果一样。

不过这条"顺序任意"只对"都是同步信号量"成立。

如果两个信号量里有一个是互斥量，顺序就不能随便换了。

更一般地说，一个进程要申请多个资源时，要按全局统一的顺序申请。

所有进程都先要 A 再要 B，就不会出现"我持 A 等你放 B，你持 B 等我放 A"。

这是死锁预防里的"资源有序分配法"，第 11 篇会正式讲。

前趋图里的多个 P 之所以安全，是因为它们等的都是"已经发生的事实"，不存在互相持有。

第四问，计算题：缓冲区大小 `n = 8`，当前已放满 8 个产品，之后又来了 3 个生产者，都卡在 `P(empty)` 上。

求 `empty`、`full`、`mutex` 的 value。

```text
empty：初值 8，生产者取了 8 个空位 → 0
       再来 3 个，各减 1 → −3
       所以 empty.value = −3，表示 3 个生产者在等

full ：初值 0，放了 8 个产品 → 8
       没有消费者取 → 8

mutex：没有任何人持有 → 1
```

答案：`empty = −3`，`full = 8`，`mutex = 1`。

这道小题能同时考三个点：负数的含义、初值与计数的关系、互斥量在不被持有时是几。

第五问，改错题，就是本篇开头那段。

```c
P(mutex);
P(empty);
```

问：什么时候死锁？

答：缓冲区满的时候。

生产者拿到 `mutex`，卡在 `empty`；消费者要 `mutex`，卡在生产者手里。

改法只有一句：把两个 P 换个位置，`P(empty)` 在前。

第六问，一个小计算：如果 S1 到 S4 每段都要 1 个单位时间，有两个 CPU，整个前趋图最短多久跑完？

```text
S1 必须最先，占 1 个单位
S2 和 S3 没有先后关系，可以并行，再占 1 个单位
S4 必须等 S2 和 S3 都完成，再占 1 个单位

总时间 = 1 + 1 + 1 = 3
```

如果只有一个 CPU，就是 4。

前趋图给出的信息只有"偏序"，能并行多少，取决于边的结构，不取决于信号量。

信号量只负责"该等的等住"，不负责"能并行的并起来"。

这也是 408 综合题里常见的一个坑：问"最短时间"，要按图算，不能按信号量个数算。

第七问，判断题：把 S4 前面的一个 `P(c)` 写成 `V(c)` 会怎样？

`V(c)` 会把 `c` 从 0 加到 1，S4 不再等 S2。

如果 S2 还没执行完，S4 就读到了不完整的数据。

这是"同步被破坏"，不是死锁。

改错题里，"V 写成 P"会导致死锁，"P 写成 V"会导致顺序错乱，两种都要能认出来。

## 7. 真实系统里长什么样

Linux 内核里有一个 `struct semaphore`，字段是 `count` 加一个等待链表。

对应操作叫 `down()` 和 `up()`，语义和 P/V 一一对应（简化示意）。

```text
down()：count 减 1，小于 0 就睡在 wait_list 上
up()  ：count 加 1，小于等于 0 就唤醒一个
```

`down()` 还有几个变体：`down_interruptible()` 可以被信号打断，返回错误码；`down_trylock()` 不睡，抢不到就返回。

内核里还有 `struct mutex`，它和 `semaphore` 长得像，但多了两个东西：owner 字段和更严格的约束。

只有持有者能解锁，不允许递归加锁，支持优先级继承（需要实时补丁）。

这些约束让 `mutex` 比 `semaphore` 更安全，所以内核代码里更推荐用它。

用户态的信号量是 POSIX 那套：

```c
sem_t s;
sem_init(&s, 0, 1);    // 第二个参数 0 表示线程间共享，非 0 表示进程间共享
sem_wait(&s);          // 就是 P
sem_post(&s);          // 就是 V
```

`sem_wait` 在 Linux 上也是 futex 实现的（简化示意）。

快路径是一条用户态原子减法，减成功就走人。

只有减成负数，才进内核挂起。

所以"信号量的开销"不是一个固定值，取决于有没有竞争。

没有竞争时，它和一条原子指令差不多贵。

有竞争时，它才付出两次上下文切换的代价。

这一点，第 07 篇的忙等 vs 阻塞那一节可以对照看。

还有一个使用边界必须记住：`down()` 会睡眠，所以不能在中断上下文里调用。

中断处理程序没有进程上下文，切走之后没人把它切回来。

中断里只能用自旋锁，或者用 `down_trylock()` 这种不睡的版本（拿到就拿，拿不到返回错误）。

这条限制和"信号量能阻塞"是同一件事的两面。

xV6 里没有信号量。

它用的是更底层的一对原语：`sleep(chan, lock)` 和 `wakeup(chan)`。

```c
// xv6 风格的等待（简化示意）
while (count == 0) {
    sleep(&count, &lock);    // 睡在 count 这个地址上，同时释放 lock
}
```

`sleep` 的第二个参数是关键：它要传一把锁，因为"判断条件"和"进入睡眠"之间不能有窗口。

如果先判断 `count == 0`，再睡觉，中间来了个 `wakeup`，这个唤醒就丢了。

这叫丢失唤醒（lost wakeup），是手写条件等待最经典的 bug。

`wakeup(chan)` 会把所有睡在这个通道上的进程全部唤醒。

注意是"全部"，不是"一个"。

所以 xV6 的模型更粗糙，代价是惊群（thundering herd）：一堆进程被叫醒，抢同一把锁，最后只有一个能干活。

信号量的等待队列叫醒一个，就没有这个问题。

## 8. P 的顺序：为什么不能反

现在把那个死锁彻底拆开。

生产者有两个 P：`P(empty)` 和 `P(mutex)`。

只有两种顺序，逐个看。

**顺序一：先 `P(empty)` 再 `P(mutex)`（正确）**

```text
缓冲区满 → empty = 0 → P(empty) 阻塞
阻塞时手里没有任何锁
消费者可以自由地 P(mutex)、取走产品、V(empty)
V(empty) 唤醒生产者
```

**顺序二：先 `P(mutex)` 再 `P(empty)`（死锁）**

```text
缓冲区满 → 生产者 P(mutex) 成功，持有锁
        → P(empty) 阻塞，抱着锁睡
消费者  → P(full) 成功
        → P(mutex) 失败，锁在生产者手里
        → 消费者也睡
谁也叫不醒谁
```

区别只有一句话：

```text
P(empty) 在前，阻塞时手里是空的
P(mutex) 在前，阻塞时手里握着锁
```

所以规则是：

**会阻塞的 P，要放在互斥锁的外面，也就是先申请资源信号量，再申请互斥信号量。**

消费者同理，`P(full)` 必须在 `P(mutex)` 之前。

如果消费者也反了，死锁条件是"缓冲区空"，比满更容易触发。

因为程序一启动缓冲区就是空的。

**V 的顺序呢？**

无所谓。

`V(mutex); V(full);` 和 `V(full); V(mutex);` 都对。

因为 V 不阻塞，它只是加值和唤醒，不存在"抱着什么睡"的问题。

但有个性能差别：先 `V(mutex)` 再 `V(full)`，被唤醒的消费者能立刻拿到锁。

反过来，消费者被唤醒后可能还要等 `mutex`，多一次上下文切换。

所以习惯上先放锁，再通知。

这也解释了一个常见疑问："V 的顺序真的随便吗？"

正确性上随便，性能上有讲究，考场上答"顺序任意"就行。

还有一个更隐蔽的坑：**一个信号量不能同时当互斥和同步用。**

比如有人把 `mutex` 拿来当"缓冲区里有几个产品"。

它初值是 1，生产者放一个就 `V`，消费者取一个就 `P`。

看起来能跑，实际上是两套语义挤在一个变量里，一旦需要互斥保护整个缓冲区，就彻底乱了。

## 9. 前趋图：把偏序写成 PV

前趋图（precedence graph）是 408 里 PV 题的标准输入。

它是一种有向无环图，节点是程序段，边是"必须先做"。

```text
A ──▶ B    表示 A 必须在 B 之前完成
```

把一个前趋图翻译成 PV 代码，三步：

```text
① 数边：几条边就几个信号量，初值全 0
② 每条边：起点末尾 V 一次，终点开头 P 一次
③ 检查：每个节点的 P 次数 = 入度，V 次数 = 出度
```

第三条是自检用的。

如果某个节点的 P 次数和入度对不上，或者 V 次数和出度对不上，代码一定错了。

再看一个带"多前驱"和"多后继"的例子。

```text
A ──▶ B ──▶ D
 │           ▲
 └──▶ C ─────┘
     │
     └──▶ E
```

```text
边：A→B, A→C, B→D, C→D, C→E
五个信号量，全部初值 0
```

```c
semaphore ab = 0, ac = 0, bd = 0, cd = 0, ce = 0;

void PA() { A(); V(ab); V(ac); }

void PB() { P(ab); B(); V(bd); }

void PC() { P(ac); C(); V(cd); V(ce); }

void PD() { P(bd); P(cd); D(); }

void PE() { P(ce); E(); }
```

检查：

```text
A 出度 2 → V 两次 ✓
B 入度 1、出度 1 ✓
C 入度 1、出度 2 ✓
D 入度 2 → P 两次 ✓
E 入度 1 ✓
```

如果题目问"这个程序至少需要几个信号量"，答案是 5。

如果问"能不能用 4 个"，答案是不能，因为每条边都要一个独立的同步信号量。

有没有例外？同一个起点有两条出边，能不能只用一个信号量？不能，因为一次 `V` 只让一个 `P` 通过，另一条边就卡住了。

所以"边数 = 信号量数"这条在标准题型里是硬结论。

## 10. 写 PV 时常犯的七种错

```text
① 两个 P 的顺序反了 → 死锁（本篇开头）
② mutex 初值写 0   → 所有进程都进不去
③ mutex 初值写 n   → 互斥失效，n 个进程同时进
④ 漏了一个 V       → 一次漏，永久少一个资源，其他进程永远等
⑤ 多了一个 V       → 计数虚高，互斥被破坏，可能出现两个进程同时进
⑥ 一个信号量两用   → 互斥和同步挤在一个变量上，语义混乱
⑦ 前趋图漏边或多边 → 顺序错，或者过度串行
```

④和⑤在 408 里常以"改错"的形式出现。

判断方法：数一数每对 P/V 是不是配平。

```text
V 的总次数要够：V 次数 + 初值 ≥ P 次数
```

更实用的检查：对着每条可能的执行路径走一遍，看有没有进程永远等不到 V。

还有一个概念级的错：把 `P` 和 `V` 当成"申请锁"和"释放锁"。

那样就会觉得"先 P 哪个都行，反正最后都要拿到"。

真实的语义是"减计数，减成负的就排队"，一旦接受这个语义，顺序的重要性就自然浮现了。

检查一段 PV 代码，按下面三句问一遍，比死记规则有用。

```text
① 每个 P 阻塞时，它手里还握着别的什么？
   握着互斥量，就可能死锁
② 每个 V 唤醒的人，能不能立刻往前走？
   不能，就只是慢，还能接受
③ 每个等待中的进程，等的那次 V 由谁发出？
   找不到，就是永久阻塞
```

这三问覆盖了 408 里绝大多数 PV 改错题。

第①问对应生产者消费者的顺序坑。

第②问对应 V 的顺序，只影响性能。

第③问对应漏 V 和配对错乱。

## 11. 容易混淆的点

第一组：整型信号量和记录型信号量。

```text
整型：只有一个 value，没有队列，P 用 while 空转 → 不满足让权等待
记录型：value 可以为负，配等待队列，P 会 block → 满足让权等待
```

408 说"信号量"时，默认是记录型。

第二组：value 的正负。

```text
正数 = 可用资源数
负数 = 等待进程数（绝对值）
零   = 刚好用完
```

别把 `value < 0` 理解成"资源是负的"。

第三组：互斥信号量和同步信号量。

```text
互斥：初值 1，P 和 V 在同一个进程里，成对包住临界区
同步：初值 0，V 在前的进程里，P 在后的进程里
```

看初值就能分辨，看 P/V 在不在同一个函数里也能分辨。

第四组：P 阻塞和 V 唤醒。

```text
P 可能阻塞，阻塞时进等待队列
V 绝不阻塞，它只负责加值和唤醒一个
```

所以"V 会不会死锁"这个问题，答案是"不会"。

第五组：信号量和管程。

信号量是"用户自己保证 P/V 配对"，写错就死锁。

管程把互斥和条件变量封装起来，编译器保证一次只进一个，写错的空间更小。

第 10 篇会讲管程。

第六组：唤醒谁。

标准信号量唤醒队首的一个，具体是 FIFO 还是优先级，看实现。

xV6 的 `wakeup` 唤醒全部，这是惊群的来源。

第七组：P/V 和加锁解锁。

这是本篇的核心误解。

加锁解锁只有"有人持有/没人持有"两态，信号量有"欠了几个"这个第三态。

生产者消费者的死锁，正是因为"欠账"和"持有"能同时发生。

第八组：信号量和条件变量。

条件变量本身不记状态：没有人在等的时候 `signal` 一次，这次唤醒就丢了。

信号量记状态：没有人在等的时候 `V` 一次，值会存着，下一个 `P` 直接通过。

所以"V 不会白 V，signal 会白 signal"。

这条差异是管程和信号量最本质的区别，第 10 篇会展开。

第九组：互斥信号量和"二值信号量"。

二值信号量的初值是 1，取值只能是 0 或 1，看起来和锁一样。

但它仍然能靠 `P` 阻塞和 `V` 唤醒配对，所以可以当同步用。

锁不行，锁没有计数和排队语义。

第十组：信号量能不能当条件变量用？

可以，反过来不行。

这也是为什么 408 的题几乎都能用 PV 解，而管程题需要额外的条件变量。

## 12. 小结 + 下一篇

这一篇的骨架：

```text
信号量 = 一个整数 + 一个等待队列
P：先减后判断，减成负的就阻塞自己
V：先加后判断，加完不正是唤醒别人
三种初值：互斥 1，同步 0，资源计数 n
```

四条必须记住的结论：

```text
P 可能阻塞，V 一定不阻塞
会阻塞的 P 要放在互斥锁外面
前趋图：一条边一个信号量，起点 V 终点 P
value 为负时，绝对值就是等待的进程数
```

再补一句本篇最重要的心态：

写 PV 代码不是写"锁"，是写"账本"。

每申请一次资源，账上就少一个；每释放一次，账上就多一个并叫醒一个欠账的人。

把账算平了，代码就对了。
