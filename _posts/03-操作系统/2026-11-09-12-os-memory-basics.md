反汇编一个再普通不过的程序。

```text
0000000000401136 <main>:
  401136:  push   %rbp
  401137:  mov    %rsp,%rbp
  40113a:  call   401040 <foo>
```

`main` 在 `0x401136`，`foo` 在 `0x401040`。

这个地址是编译的时候定下来的。

那么问题来了。

```text
如果操作系统把这段代码装到物理内存的 0x800000 处，
那条 call 401040 还对不对？
```

地址里的数字没变，可 `foo` 已经不在 `0x401040` 了。

程序照样能跑。

因为 `0x401040` 根本不是物理地址。

```text
它是「相对于这个程序自己的地址」。
真正落到哪，由操作系统在装入时决定。
```

**这一篇讲的就是「这个偏移量怎么变成物理地址」，以及当内存按整块分配时，会产生什么样的浪费。**

## 1. 内存管理要做的四件事

先把范围框住。

```text
① 分配与回收：哪块内存归哪个进程，用完怎么还。
② 地址转换：程序里的地址，怎么变成内存条上的地址。
③ 保护：进程 A 不能读写进程 B 的内存。
④ 扩充：内存不够时，怎么让程序以为自己有很多。
```

画成一张图。

```text
            ┌──────────── 内存管理 ────────────┐
            │  分配回收：谁用哪块，用完还给谁     │
            │  地址转换：逻辑地址 → 物理地址      │
            │  保护    ：这块只有你能读写         │
            │  扩充    ：用外存假装内存更大       │
            └──────────────────────────────────┘
```

四条里，这一篇讲前三条。

```text
第 ④ 条（扩充）就是虚拟内存，留给 14 篇。
```

这四条不是并列的。

```text
先有「分配」，才有「这块归谁」。
有了「归谁」，才谈得上「转换」和「保护」。
有了「转换」，才可能「移动」，才谈得上「紧凑」。
```

## 2. 逻辑地址与物理地址

两个词必须先分清。

```text
逻辑地址（logical address）：程序里看到的地址，也叫虚拟地址（virtual address）。
物理地址（physical address）：内存条上真实的单元编号。
```

编译之后，程序里的地址都是逻辑地址。

```text
目标文件里，main 在 0x1136，foo 在 0x1040。
链接之后，整个程序被放到一个从 0x400000 开始的「假想空间」里。
```

这个假想空间，就是地址空间的雏形。

```text
每个程序都以为自己从某个地址开始，独占一整片内存。
实际上它们共用同一根内存条。
```

把「逻辑地址 → 物理地址」这个动作叫地址重定位（relocation）。

```text
重定位 = 把逻辑地址加上一个偏移，得到物理地址。
那个偏移，通常就记在 CPU 的一个寄存器里。
```

什么时候加，决定了三种装入方式。

## 3. 一次完整走查：同一个程序，三种装入

程序很简单。

```text
逻辑地址 0x1000：main 的第一条指令
逻辑地址 0x2000：变量 x
main 里有条指令：call 0x2000
```

假设要装到物理地址 `0x10000` 处。

### 3.1 绝对装入

编译的时候就定死：这个程序一定装在 `0x10000`。

```text
编译器直接把地址改成物理地址：
  main       → 0x11000
  变量 x     → 0x12000
  call 0x2000 → call 0x12000
```

生成的可执行文件里，写的就是 `0x12000`。

走一遍。

```text
装到 0x10000：call 0x12000 → 跳到 0x12000，正是 x 的地址。对。
装到 0x80000：call 0x12000 → 跳到 0x12000，那里现在是别人。错。
```

结论。

```text
绝对装入只能用在「单道、位置固定」的场合。
早期的手写汇编、或者嵌入式里固定地址的固件，还能看到它的影子。
```

### 3.2 可重定位装入（静态重定位）

编译时地址还是相对的，装入时一次性修改。

```text
目标文件里：main=0x1000，x=0x2000，call 0x2000

装入到 0x10000，基址 = 0x10000，把每个地址都加上去：
  main       = 0x1000 + 0x10000 = 0x11000
  x          = 0x2000 + 0x10000 = 0x12000
  call 0x2000 → call 0x12000
```

注意关键的一点。

```text
修改发生在「装入时」，只做一次。
装好之后，代码里就是物理地址了。
```

后果。

```text
程序一旦装入，就不能移动。
移走以后，代码里那些已经改过的地址全错——没人会去改第二遍。
```

这也是为什么「紧凑」必须配动态重定位，光靠静态重定位做不了。

### 3.3 动态运行时装入（动态重定位）

地址到了 CPU 里才转换。

```text
目标文件里：call 0x2000，永远是 0x2000。
装入到 0x10000，重定位寄存器 = 0x10000。

CPU 执行 call 0x2000：
  MMU 做加法：0x2000 + 0x10000 = 0x12000
  真正去访问 0x12000
```

现在把程序挪到 `0x80000`。

```text
只需要把重定位寄存器改成 0x80000。
代码一个字节都不用动。
下一次访问 0x2000 → 0x82000。对的。
```

这就是动态重定位的全部优势。

```text
地址转换从「装入时一次」变成「每次访问一次」。
代价是多了一个加法器和一次查寄存器，换来的是「程序可以移动」。
```

三种方式放在一起比。

| 装入方式 | 地址何时确定 | 装入后能否移动 | 需要的硬件 |
|---|---|---|---|
| 绝对装入 | 编译时 | 不能 | 无 |
| 可重定位装入（静态） | 装入时一次性修改 | 不能 | 无（但要改代码） |
| 动态运行时装入（动态） | 每次访问时 | 能 | 重定位寄存器 + MMU |

第三行那个「能移动」，是后面所有内存管理技术的前提。

```text
不能移动 → 只能一次性给一块连续内存 → 外部碎片无解。
能移动   → 可以紧凑、可以换出、可以分页。
```

## 4. 拆开看：链接、重定位与保护

### 4.1 三种链接时机

装入之前还有一步：链接（linking）。

```text
把若干目标模块 + 库函数，拼成一个完整的程序。
```

三种时机。

```text
静态链接：链接时全部拼好，生成一个完整的可执行文件。
装入时动态链接：装入内存时，边装入边链接。
运行时动态链接：运行到真正调用时，才去链接。
```

三者的取舍。

```text
静态链接：跑得最快，但库一更新就要重新链接，多个程序各存一份库，浪费空间。
装入时动态链接：便于模块更新和共享，但装入时间变长。
运行时动态链接：装入最快，用到才链接，最省空间；缺点是第一次调用有延迟。
```

「运行时动态链接」在真实系统里就是这些。

```text
Linux 的共享库 .so + dlopen / dlsym
Windows 的 DLL
```

### 4.2 MMU 与重定位寄存器

MMU（memory management unit）是 CPU 里做地址转换的部件。

```text
CPU 发出逻辑地址
        │
        ▼
   ┌─────────┐
   │   MMU   │ ◀── 重定位寄存器（基址）
   └────┬────┘
        │ 物理地址 = 基址 + 逻辑地址
        ▼
      内存
```

一句话。

```text
程序永远发逻辑地址，内存永远收物理地址，中间那层是 MMU。
```

所以「同一个地址在两个进程里读到不同值」这件事，根本不是魔法。

```text
两个进程的重定位寄存器不一样。
同一个逻辑地址，加出来的物理地址不一样。
```

### 4.3 上下限寄存器与越界判断

有了重定位，还得防着程序乱来。

```text
程序 A 的基址是 0x10000，长度是 0x2000。
它如果发一个逻辑地址 0x5000，加出来是 0x15000。
那个地址属于程序 B。
```

所以要有界地址寄存器（bound register），也叫限长寄存器。

```text
基址寄存器（base）：这一段的起始物理地址。
限长寄存器（limit）：这一段的长度。

合法条件：0 ≤ 逻辑地址 < 限长
物理地址 = 基址 + 逻辑地址
```

越界就走异常。

```text
逻辑地址 ≥ 限长 → 硬件产生越界中断（地址异常）→ 交给操作系统处理
```

写成代码，只有两行。

```c
phys_addr translate(logical_addr la, reg base, reg limit) {
    if (la >= limit) {
        raise(ADDRESS_ERROR);      // 越界：不产生物理地址，直接陷入
    }
    return base + la;              // 合法：加一次
}
```

注意顺序。

```text
先判越界，再做加法。
如果先加再判，一个恶意地址可能加出一个「看起来合法」的物理地址，
正好落在别的进程或者内核里。
```

注意这个「≥」，不是「>」。

```text
限长 0x1000 表示合法偏移是 0x000 到 0xFFF。
0x1000 已经越界了。
```

走一遍。

```text
基址 = 0x3000，限长 = 0x1000

访问 0x0EFF：0x0EFF < 0x1000 ✓
             物理 = 0x3000 + 0x0EFF = 0x3EFF
访问 0x0FFF：0x0FFF < 0x1000 ✓
             物理 = 0x3000 + 0x0FFF = 0x3FFF
访问 0x1000：0x1000 ≥ 0x1000 ✗  越界，异常
访问 0x2000：0x2000 ≥ 0x1000 ✗  越界，异常
```

还有一种变体：用「下限 + 上限」两个寄存器。

```text
下限寄存器 = 基址，上限寄存器 = 基址 + 长度。
判断：下限 ≤ 物理地址 < 上限。
```

两种写法等价，408 都出现过。

```text
国内教材多用「基址 + 限长」，因为判断在加之前做，硬件实现更简单。
```

## 5. 连续分配：三种分区方式

「连续分配」的意思是：一个进程占一整块连续的内存。

```text
进程 A 占 [100K, 300K)，进程 B 占 [300K, 400K)，中间不许有空。
```

三代做法，一代比一代灵活。

### 5.1 单一连续分配

```text
内存分成两块：
  低地址：操作系统（常驻）
  高地址：用户区，一次只放一个程序
```

特点。

```text
没有外部碎片（用户区就是一整块）。
有内部碎片——如果程序比用户区小，剩下的就浪费了。
不支持多道程序。
```

### 5.2 固定分区分配

把用户区预先切成若干块，每块大小固定，可大可小。

```text
分区 1： 8K
分区 2：16K
分区 3：32K
分区 4：64K
```

作业来了，找一个装得下的分区放进去。

```text
作业 5K  → 放进 8K 分区，剩下的 3K 谁也拿不到。
```

这 3K 就是内部碎片（internal fragmentation）。

```text
内部碎片 = 已经分给进程、但进程用不上的那部分。
它在这块分区里面，别的进程进不来。
```

固定分区的两个毛病。

```text
① 内部碎片：分区越大，浪费越多。
② 分区数固定：并发度被写死了，大作业可能一个都装不下。
```

### 5.3 动态分区分配

不预切，按需切。

```text
作业要 120K，就找一块 ≥120K 的空闲区，切 120K 给它，剩下的还回去。
作业结束，它那块变成空闲区，和相邻的空闲区合并。
```

这次碎片跑到外面去了。

```text
外部碎片（external fragmentation）：
空闲总量够，但没有一块连续的够大。
```

举个例子。

```text
空闲区：100K、50K、200K，加起来 350K。
新作业要 150K → 装不下。
```

三个空闲区都不够 150K。

```text
总空闲 350K > 150K，但装不下。
这就是外部碎片——它不在任何分区内部，它散在分区之间。
```

两种碎片一句话分开。

```text
内部碎片：给了你，你用不完。
外部碎片：有得给，但拼不起来。
```

### 5.4 四种分配算法：空闲区怎么排

动态分区要回答一个问题：来了一个请求，从空闲区里挑哪一块？

四种算法，差别只在两点。

```text
空闲区链表怎么排序？
从哪个位置开始找？
```

**首次适应（first fit, FF）**

```text
空闲区按「地址递增」排列。
从头开始找，找到第一个装得下的就分。
```

特点。

```text
优点：尽量用低地址，把高地址的大块留给大作业；算法简单，通常最快。
缺点：低地址区被反复切割，碎片越来越多；每次都从头扫。
```

```c
/* 空闲区按地址递增串成一条链表 */
Block* first_fit(int size) {
    for (Block* p = free_list; p != NULL; p = p->next) {
        if (p->size >= size) {
            if (p->size > size) {          // 有多余，切一刀
                Block* rest = new Block(p->start + size,
                                        p->size - size);
                insert_after(p, rest);     // 剩余部分仍留在原位置之后
            }
            p->size = size;
            remove_from_list(p);
            return p;                      // 分配成功
        }
    }
    return NULL;                           // 走完整条链表，分配失败
}
```

这里那行 `insert_after` 值得看一眼。

```text
切开以后，「剩余空闲区」的始址是 p->start + size，不是 p->start。
写错这一行，空闲链表就和真实内存对不上了。
```

**最佳适应（best fit, BF）**

```text
空闲区按「容量递增」排列。
从头开始找，第一个装得下的，就是「装得下的里面最小的」。
```

特点。

```text
优点：每次浪费最小（这次分配看起来最省）。
缺点：切下来的剩余部分往往极小，完全用不上；外部碎片最多。
```

**最坏适应（worst fit, WF）**

```text
空闲区按「容量递减」排列。
每次都取最大的那块，切走需要的，剩下的还够大。
```

特点。

```text
优点：剩下的块还比较大，不容易产生极小碎片。
缺点：大块被迅速耗尽，后面来个大作业就没地方放了。
```

**邻近适应（next fit，也叫循环首次适应）**

```text
空闲区按「地址递增」排列。
从「上次分配结束的位置」开始往后找，找到表尾就绕回表头。
```

特点。

```text
优点：不用每次从头扫，分配更均匀，低地址不会一直被切。
缺点：高地址的大块被反复切碎，系统整体缺少大分区。
```

四种算法的排序和扫描起点，一张表记住。

| 算法 | 空闲区怎么排 | 从哪开始找 | 主要问题 |
|---|---|---|---|
| 首次适应 | 地址递增 | 表头 | 低地址碎片多 |
| 最佳适应 | 容量递增 | 表头 | 留下大量无用小碎片 |
| 最坏适应 | 容量递减 | 表头 | 大块迅速耗尽 |
| 邻近适应 | 地址递增 | 上次结束处 | 高地址大块被切碎 |

### 5.5 一次完整分配走查

同一张空闲分区表，四种算法各走一遍。

初始状态（按地址递增）。

```text
编号   始址     大小
 1      20K      40K
 2     100K     200K
 3     400K     100K
 4     600K     300K
 5    1000K     150K
```

作业依次到达。

```text
J1 要 120K
J2 要  90K
J3 要 250K
J4 要  60K
```

**首次适应。**

```text
J1(120K)：1 号 40K 不够；2 号 200K 够 → 分配在 100K，剩 80K 始址 220K
J2( 90K)：1 号 40K 不够；剩块 80K 不够；3 号 100K 够 → 分配在 400K，剩 10K 始址 490K
J3(250K)：4 号 300K 够 → 分配在 600K，剩 50K 始址 850K
J4( 60K)：1 号 40K 不够；220K 处剩 80K 够 → 分配在 220K，剩 20K 始址 280K
```

四个全部分配成功。

剩余空闲区：

```text
40K@20K、20K@280K、10K@490K、50K@850K、150K@1000K
```

**最佳适应。**

初始按容量递增排：`40、100、150、200、300`。

```text
J1(120K)：装得下的有 150、200、300 → 取最小的 150（5 号）
          分配在 1000K，剩 30K 始址 1120K
J2( 90K)：装得下的有 100、200、300 → 取 100（3 号）
          分配在 400K，剩 10K 始址 490K
J3(250K)：装得下的只有 300（4 号）
          分配在 600K，剩 50K 始址 850K
J4( 60K)：装得下的有 200 → 取 200（2 号）
          分配在 100K，剩 140K 始址 160K
```

四个也都成功，但结果很不一样。

剩余空闲区：

```text
40K@20K、140K@160K、10K@490K、50K@850K、30K@1120K
```

注意那个 `10K`、`30K`。

```text
它们谁也装不下，只会一直躺在空闲链表里。
这就是最佳适应留下的「用不上的小洞」。
```

**最坏适应。**

初始按容量递减排：`300、200、150、100、40`。

```text
J1(120K)：取最大的 300（4 号）→ 分配在 600K，剩 180K 始址 720K
J2( 90K)：取最大的 200（2 号）→ 分配在 100K，剩 110K 始址 190K
J3(250K)：现在最大的只剩 180K（720K 处），不够
          次大的 150K、110K、100K、40K 也都不够 → 分配失败
J4( 60K)：取最大的 180K（720K 处）→ 分配在 720K，剩 120K 始址 780K
```

J3 卡住了。

```text
系统里空闲总量：40+110+100+150 = 400K，够 250K。
但没有一块连续的 ≥250K。
典型的「最坏适应把大块提前花光」。
```

剩余空闲区：

```text
40K@20K、110K@190K、100K@400K、120K@780K、150K@1000K
```

**邻近适应。**

从地址 0 开始，每次记住「这次分配到哪儿」。

```text
J1(120K)：从 0 开始：40K 不够，200K@100 够 → 分配在 100K，剩 80K@220K
          指针 → 220K
J2( 90K)：从 220K 开始：80K 不够，100K@400 够 → 分配在 400K，剩 10K@490K
          指针 → 490K
J3(250K)：从 490K 开始：10K 不够，300K@600 够 → 分配在 600K，剩 50K@850K
          指针 → 850K
J4( 60K)：从 850K 开始：50K@850 不够，150K@1000 够 → 分配在 1000K，剩 90K@1060K
          指针 → 1060K
```

四个都成功，但 J4 的位置和首次适应完全不同。

```text
首次适应：J4 放在 220K
邻近适应：J4 放在 1000K
```

同样一张表，同样一串作业，只有一个分配位置不同。

```text
差别来自「从哪儿开始找」。
首次适应永远从表头，所以低地址的 80K 空洞会被反复利用。
邻近适应从指针处开始，于是低地址的空洞被跳过，高地址的 150K 被切掉。
```

剩余空闲区：

```text
40K@20K、80K@220K、10K@490K、50K@850K、90K@1060K
```

四种算法，同一个初始状态，结果汇总：

```text
               J1        J2        J3        J4
首次适应     100K      400K      600K      220K
最佳适应    1000K      400K      600K      100K
最坏适应     600K      100K      失败      720K
邻近适应     100K      400K      600K     1000K
```

看这一串数字，就能看出四种算法的性格。

```text
首次适应：喜欢低地址。
最佳适应：喜欢「刚好够」的那块。
最坏适应：喜欢最大的那块。
邻近适应：喜欢「上次干完活的地方」附近。
```

### 5.6 碎片、紧凑与伙伴系统

外部碎片攒多了，有两个办法。

```text
① 紧凑（compaction）：把所有进程往一端挪，把碎片挤成一大块。
② 换出（swap）：把某些进程整个换到外存，腾出连续空间。
```

紧凑的代价要说清楚。

```text
① 要移动数据：几百 MB 的内存搬一遍，是真实的拷贝开销。
② 要能改地址：进程挪了位置，地址必须跟着变。
   → 必须用动态重定位，静态重定位做不了。
③ 移动期间进程不能跑：要么暂停，要么整个系统停一下。
```

所以紧凑「能解决问题，但很贵」。

```text
贵到现代操作系统基本不做它——改成分页，从根上避免「必须连续」。
```

第三条路是伙伴系统（buddy system）。

```text
它的思路是：把内存按 2 的幂切成块，分配时不断对半分裂，回收时找「伙伴」合并。
```

规则只有两条。

```text
分裂：需要 2^k 大小的块，就从 2^(k+1) 的块里劈一半。
合并：释放时，如果「伙伴」也空闲，就合并成上一阶的块，继续往上合并。
```

伙伴怎么算。

```text
地址异或：伙伴地址 = 我的地址 XOR 我的块大小。
```

```c
int buddy_of(int addr, int size) {
    return addr ^ size;          // 按块大小对齐的地址，异或就是「翻一位」
}
```

为什么是异或。

```text
8 块的例子：块大小 2 时，[0-1] 和 [2-3] 是伙伴。
0 XOR 2 = 2，2 XOR 2 = 0。翻的正是「块大小」那一位。
块大小 1 时，[2] 和 [3] 是伙伴：2 XOR 1 = 3，3 XOR 1 = 2。
```

走一个 8 块的例子。

```text
总空间 8 块，编号 0..7，最小单位 1 块。
初始：一整块 [0-7]，大小 8。
```

**请求 2 块。**

```text
8 块不够精确 → 分裂成 4+4：取 [0-3]（4 块），[4-7]（4 块）空闲
4 块还大 → 再分裂：取 [0-1]（2 块），[2-3]（2 块）空闲
分配 [0-1]

空闲：[2-3] 2 块、[4-7] 4 块
```

**请求 1 块。**

```text
有 2 块的 [2-3] → 分裂成 [2] 和 [3]
分配 [2]

空闲：[3] 1 块、[4-7] 4 块
```

**再请求 1 块。**

```text
空闲里正好有 1 块的 [3] → 直接分配

空闲：[4-7] 4 块
```

**释放 [2]。**

```text
[2] 的伙伴是 [3]。但 [3] 还被占着 → 不能合并。

空闲：[2] 1 块、[4-7] 4 块
```

**释放 [0-1]。**

```text
[0-1] 的伙伴是 [2-3]。但 [2-3] 里的 [3] 还被占着 → 不能合并。

空闲：[0-1] 2 块、[2] 1 块、[4-7] 4 块
```

**释放 [3]。**

这里开始连锁。

```text
第 1 次合并：[3] 和 [2] → [2-3]，2 块
第 2 次合并：[2-3] 和 [0-1] → [0-3]，4 块
第 3 次合并：[0-3] 和 [4-7] → [0-7]，8 块
```

回到一整块。

```text
一次释放触发了三次合并，把整个内存还原了。
这就是伙伴系统的「级联合并」。
```

写成循环，就是三层合并压成一层。

```c
void release(int addr, int size) {
    while (size < TOTAL_SIZE) {            // 合到整块就停
        int b = buddy_of(addr, size);
        if (!is_free(b, size)) break;      // 伙伴不空闲，合并到此为止
        addr = (addr < b) ? addr : b;      // 合并后取较小的始址
        size = size * 2;                   // 升一阶，继续试
        remove_free(b, size / 2);          // 伙伴从空闲链表摘掉
    }
    insert_free(addr, size);
}
```

关键在 `size = size * 2` 那一行。

```text
合并成功后，块变大了，它的「伙伴」也换了一个。
所以必须重新算一次伙伴地址，而不是继续用旧的那个。
```

它的代价。

```text
只能分配 2 的幂大小 → 内部碎片最多浪费将近一半。
请求 33 块 → 给 64 块 → 浪费 31 块。
```

所以真实系统会再套一层小对象缓存，把这个浪费补回来。

## 6. 408 怎么考

五类题。

```text
① 判：给基址和限长，判断几个逻辑地址是否越界，算出物理地址。
② 判：三种装入方式，哪个能移动、地址在哪一刻确定。
③ 算：给空闲分区表，用指定算法分配，写始址和剩余大小。
④ 算：内部碎片 / 外部碎片的总量。
⑤ 算：伙伴系统的分配与回收，写出每步的空闲块。
```

### 6.1 例题一：越界判断

基址寄存器 = `0x3000`，限长寄存器 = `0x1000`。

判断下面三个逻辑地址，哪些合法？合法的算出物理地址。

```text
(a) 0x0EFF
(b) 0x0FFF
(c) 0x1000
```

逐条算。

```text
(a) 0x0EFF < 0x1000，合法
    物理 = 0x3000 + 0x0EFF = 0x3EFF

(b) 0x0FFF < 0x1000，合法
    物理 = 0x3000 + 0x0FFF = 0x3FFF

(c) 0x1000 ≥ 0x1000，越界
    不产生物理地址，走越界异常
```

答案：

```text
合法的只有 (a) 和 (b)。
物理地址分别是 0x3EFF 和 0x3FFF。
```

要点只有一个。

```text
限长 0x1000 是「长度」，不是「最大地址」。
合法偏移的上界是 0x0FFF。
```

### 6.2 例题二：固定分区的内部碎片

分区表（按地址递增）。

```text
分区 1： 8K
分区 2：16K
分区 3：32K
```

作业依次到达：`5K、20K、12K`。

按「找第一个装得下的分区」放置。

```text
5K  ：分区 1 装得下（8K）  → 内部碎片 8 - 5 = 3K
20K ：分区 1 不够，分区 2 不够（16K < 20K），分区 3 装得下（32K）
      → 内部碎片 32 - 20 = 12K
12K ：分区 1 已占，分区 2 装得下（16K）
      → 内部碎片 16 - 12 = 4K
```

答案：

```text
三个作业都装下了，内部碎片总量 = 3 + 12 + 4 = 19K。
```

再补一问：如果作业 20K 先到呢？

```text
20K 还是只能进 32K 分区，内碎 12K。
5K 进 8K，内碎 3K。
12K 进 16K，内碎 4K。
一样是 19K。
```

### 6.3 例题三：首次适应还是最佳适应

空闲分区表（按地址递增）。

```text
A： 0K 起，100K
B：200K 起，300K
C：600K 起，200K
```

两个请求依次到达：`R1 = 180K，R2 = 250K`。

问：用首次适应和最佳适应，分别能不能都分配成功？

首次适应。

```text
R1(180K)：A 100K 不够；B 300K 够 → 分配在 200K，剩 120K 始址 380K
R2(250K)：A 不够；380K 处剩 120K 不够；C 200K 不够 → 失败
```

最佳适应。

```text
R1(180K)：装得下的有 B(300K)、C(200K) → 取最小的 C(200K)
          分配在 600K，剩 20K 始址 800K
R2(250K)：A 不够；B 300K 够 → 分配在 200K，剩 50K 始址 450K
```

答案：

```text
首次适应：R1 成功，R2 失败。
最佳适应：R1 成功，R2 成功。
```

这一题正好说明一件事。

```text
最佳适应不是「每次都最省」，而是「每次都挑最小的够用块」。
挑小的会把中等块提前花掉，后面的中等请求就没地方了。
```

## 7. 真实系统里长什么样

> 以下是简化示意，函数名与文件取自 Linux 内核，行为细节有删减。

现代操作系统基本不用连续分配。

```text
不是因为它不好想，是因为外部碎片无法根治。
紧凑能解决，但代价太大（要搬数据、要停进程、要动态重定位）。
所以从根上放弃「必须连续」这个约束——这就是分页。
```

不过在「物理页框」这一层，伙伴系统活得好好的。

```text
Linux 的物理内存分配器就是伙伴系统：
  mm/page_alloc.c 里的 __alloc_pages()
  struct free_area free_area[MAX_ORDER]
  每个阶（order）一条空闲链表，order 0 是 1 个页，order k 是 2^k 个页
```

它和教材版几乎一样。

```text
分配：从 order 开始往上找第一个非空的阶，取一块，一路对半分裂下来。
释放：和伙伴合并，合并成功就升一阶继续试。
查看：/proc/buddyinfo 能直接看到每个阶有多少空闲块。
```

数字感。

```text
页大小 4 KB，order 0 = 4 KB，order 10 = 4 MB。
MAX_ORDER 默认 11，也就是阶 0 到 10。
```

这也解释了为什么内核里「大块连续内存」很贵。

```text
order 10 的块要 4 MB 连续物理内存，跑久了基本拼不出来。
所以内核里要连续大内存，宁可启动时预留，也不指望运行时分配。
```

伙伴系统的内部碎片，靠 slab 补。

```text
SLUB（mm/slub.c）先从伙伴系统拿整页，再切成固定大小的小对象。
比如 task_struct、inode、dentry 都有各自的对象缓存。
这样「请求 33 块给 64 块」的浪费就不会发生。
```

用户态看到的是另一套。

```text
malloc 小块用 brk 扩堆，大块用 mmap 直接映射。
程序的装入早就不是「绝对装入」了：
  可执行文件是 ELF，按段映射到地址空间；
  PIE（位置无关可执行文件）配合 ASLR，每次运行的基址都随机。
```

至于保护，界地址寄存器也基本退役了。

```text
现代 CPU 用页表的权限位：U/S（用户/内核）、R/W（读写）、NX（不可执行）。
比「一段连续内存的上下限」细得多，可以按页设置。
```

但那个「越界就异常」的思想一点没变。

```text
mmap_min_addr 就是它的直系后代：
  禁止把低地址映射给用户态，防止空指针解引用变成可利用的漏洞。
```

## 8. 为什么最佳适应最差

回到 5.5 那张表。

假设现在又来一个作业。

```text
J5 要 145K。
```

四种算法当时的剩余空闲区。

```text
首次适应：40@20、20@280、10@490、50@850、150@1000     → 150 ≥ 145，成功
最佳适应：40@20、140@160、10@490、50@850、30@1120     → 最大 140 < 145，失败
最坏适应：40@20、110@190、100@400、120@780、150@1000   → 150 ≥ 145，成功
邻近适应：40@20、80@220、10@490、50@850、90@1060      → 最大 90 < 145，失败
```

最佳适应失败了。

奇怪的地方在于：它前面每一次分配都比别人「省」。

```text
J1 要 120K：
  首次适应给了 200K 的块 → 剩 80K，浪费 80K
  最佳适应给了 150K 的块 → 剩 30K，浪费 30K
```

从单次看，最佳适应赢了 50K。

```text
但它把 150K 的块用掉了，只留下 30K。
而 30K 这个洞，以后几乎装不下任何东西——它不是「省下来的空间」，是「被浪费掉的空间」。
```

反过来看首次适应。

```text
它用 200K 的块装 120K，剩 80K。
80K 还能装下 60K、70K 的作业，是有用的。
```

一句话总结。

```text
最佳适应留下的剩余部分，恰好是「装不下当前请求、也装不下任何比它大的请求」的尺寸。
它把每个空闲区都切成「刚好差一点」的大小。
```

这就是那个反直觉的结论。

> **反直觉的点**：最佳适应听起来最省，实际最差。
> 它每次只浪费一点点，但那一点点积累起来，全是「装不下任何东西的小洞」——既不能合并（大多不相邻），也不能使用。
> 首次适应看起来粗糙，却把小请求压在低地址，把大块留给后面。

数字上还能看得更清楚。

```text
最佳适应分配 4 个作业后，5 个空闲块里有 4 个小于最小作业 60K：
  40K、10K、50K、30K —— 合计 130K，全部无法使用。
首次适应：40K、20K、10K、50K —— 合计 120K 无法使用，但保住了 150K 的大块。
```

这也解释了一个工程事实。

```text
真实分配器里最常用的是「按大小分桶 + 伙伴系统」，
而不是「每次都找最小的够用块」。
因为「最省」这个目标本身是短视的。
```

## 9. 容易混淆的点

**内部碎片和外部碎片。**

```text
内部碎片：已经分给你了，你用不完的那部分。在分区内部。
外部碎片：还没分出去，但太小拼不起来的那部分。在分区之间。
固定分区 + 分页 → 内部碎片。
动态分区 + 分段 → 外部碎片。
```

**静态重定位和动态重定位。**

```text
静态：装入时改一次地址，之后不能移动。
动态：每次访问都转换，程序可以随时移动。
判断口诀：能不能移，看地址是「改在代码里」还是「留在寄存器里」。
```

**紧凑和交换。**

```text
紧凑：在内存里挪进程，把碎片拼起来。不涉及外存。
交换（swap）：把进程整个搬到外存。腾出的是「整块」。
```

**首次适应和邻近适应。**

```text
两者都按地址递增排，都找第一个装得下的。
唯一区别：从表头开始，还是从上次结束处开始。
```

**逻辑地址、物理地址、相对地址。**

```text
逻辑地址 = 程序里写的地址，也叫虚拟地址。
物理地址 = 内存单元的编号。
相对地址 = 相对于模块起始的偏移，链接时才会被合并。
```

**「限长」不是「最大地址」。**

```text
限长 0x1000 → 合法偏移 0x000~0xFFF。
判断用「逻辑地址 < 限长」，不是「≤」。
```

## 10. 小结 + 下一篇

三句话收束。

```text
① 逻辑地址到物理地址的转换，可以发生在编译时、装入时、运行时；只有运行时才能移动。
② 连续分配的死穴是碎片：固定分区有内部碎片，动态分区有外部碎片。
③ 四种算法只差两点：空闲区怎么排、从哪儿开始找。
```

再把最容易考的两组数字记一遍。

```text
物理地址 = 基址 + 逻辑地址      （先判越界，再加）
碎片总量 = 分区大小 - 进程大小   （内部碎片）
```

回到开头那条 `call 401040`。

```text
它一直是 0x401040，从来没变过。
变的只是「谁来加那个基址」。
加在编译期，程序就不能挪；加在装入期，挪了要重改；加在每次访问，随便挪。
```
