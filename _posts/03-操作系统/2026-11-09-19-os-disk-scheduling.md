一次读盘，慢在哪？

拆成三段看：

```text
寻道     8.00 ms     磁头臂移到目标磁道
旋转     4.17 ms     等到目标扇区转到磁头下
传输     0.13 ms     把 4 KB 读出来
──────────────────────────────
合计    12.30 ms
```

传输只占 1%。

剩下 99% 的时间，磁盘在「找位置」。

所以磁盘调度的全部意义只有一件事：

```text
把「找位置」的次数和距离压下来。
```

而调度算法的选择，直接决定这一天磁盘臂要走多远。

**反直觉的点先放这里：**

> **SSTF 每次都选最近的磁道，总移动距离却不一定最小。**
> **贪心在磁盘调度里不是最优解。**

## 1. 这个问题解决什么：99% 的时间在找位置

磁盘是机械装置。

机械的东西有惯性，动起来要时间，停下来也要时间。

```text
7200 转/分的盘，磁头臂从一道移到另一道平均要 1 ms 左右
跨 100 道就是 100 ms 量级
而读 4 KB 只要 0.13 ms
```

于是有个很朴素的优化：

```text
如果一个方向上有 5 个请求，另一个方向上有 1 个，
先服务那 5 个，路上顺手把第 6 个也做了。
```

这就是磁盘调度（disk scheduling）。

它要回答的问题：

```text
当前磁头在 53，
请求队列是 98、183、37、122、14、124、65、67，
下一个服务谁？
```

答案不同，总移动磁道数差 2.7 倍。

```text
FCFS  640 个磁道
SSTF  236 个磁道
```

同一个队列，同一块磁盘，差 404 个磁道。

按 1 ms / 100 道算，差 4 ms。

按每秒 100 个请求算，一天差 4 秒。

**这就是为什么这一章值得单独学。**

## 2. 最小模型：盘面、磁道、柱面、扇区

一块硬盘，打开看是这样：

```text
        ┌──────── 盘片（platter）× N ────────┐
        │   ○ 磁道（track）环形同心圆        │
        │   每个盘面一个磁头（head）          │
        │   所有盘面上半径相同的磁道 = 柱面    │
        └─────────────────────────────────────┘

俯视图（一个盘面）：
        ╭───────────────────╮
        │  ╭─────────────╮  │   ← 最外圈磁道
        │  │ ╭─────────╮ │  │
        │  │ │ ╭─────╮ │ │  │
        │  │ │ │ 主轴 │ │ │  │
        │  │ │ ╰─────╯ │ │  │
        │  │ ╰─────────╯ │  │
        │  ╰─────────────╯  │
        ╰───────────────────╯
```

四个概念：

```text
盘面 surface   一个盘片有两个面，每面一个磁头
磁道 track     一个面上的一圈，编号从外到内 0,1,2,...
柱面 cylinder  所有盘面上半径相同的磁道集合，编号 = 磁道号
扇区 sector    磁道上的一段弧，通常 512 B 或 4 KB
```

关键几何事实：

```text
同一个柱面上的磁道，磁头不用移动就能访问（换个磁头/盘面就行）。
换柱面 = 寻道，最贵。
换扇区 = 旋转，次贵。
换盘面 = 电子切换，几乎免费。
```

所以磁盘地址的顺序是：

```text
(柱面号, 盘面号, 扇区号)
```

**柱面在最前面，不是随便排的。**

这样排，逻辑上连续的块会先填满同一个柱面的所有盘面，再换下一个柱面。

```text
块 0 → 柱面 0, 盘面 0, 扇区 0
块 1 → 柱面 0, 盘面 0, 扇区 1
...
块 k → 柱面 0, 盘面 1, 扇区 0     ← 换盘面，不寻道
...
块 m → 柱面 1, 盘面 0, 扇区 0     ← 换柱面，要寻道
```

这叫「按柱面优先」。

如果反过来按（盘面, 柱面, 扇区）编号，读一个连续文件会疯狂换柱面。

**一个编号顺序，能把顺序读的性能差出几倍。**

### 2.1 磁盘的参数

```text
盘面数     一个盘片 2 面，多个盘片叠起来
磁道数     每个面多少圈，现代盘外圈约 10 万圈以上（用 zone 分区）
扇区数     每道多少个扇区，外圈多内圈少（zone bit recording）
转速       5400 / 7200 / 10000 / 15000 rpm，或 SSD 的「无」
```

408 题里常见的简化设定：

```text
每个磁道扇区数相同（比如 100 个）
每个扇区 512 B
转速 7200 r/min
平均寻道时间 8 ms（或给「每跨一道 0.2 ms + 启动 2 ms」）
```

参数不同，算法不变。

### 2.2 为什么外圈扇区更多

物理上，外圈周长更长。

```text
同样一位数据的长度，外圈能放更多
所以现代磁盘把盘面分成若干 zone，外圈 zone 每道扇区更多
```

这叫 zone bit recording（分区记录）。

```text
结果：外圈顺序读比内圈快 1.5~2 倍
这也解释了为什么「磁盘开头快、结尾慢」
```

但 408 的题几乎都假设「每道扇区数相同」。

因为考的是寻道距离，不是磁记录密度。

**题目给什么参数，就用什么，别自己加戏。**

### 2.3 从块号算出磁盘地址

设：200 个柱面，每个柱面 20 个盘面（磁头），每道 100 个扇区，一个块 = 一个扇区。

求块号 2345 的磁盘地址。

```text
每柱面块数 = 盘面数 × 每道扇区数 = 20 × 100 = 2000

柱面号 = 2345 / 2000 = 1
余数   = 2345 % 2000 = 345
盘面号 = 345 / 100 = 3
扇区号 = 345 % 100 = 45
```

```text
块 2345 → （柱面 1，盘面 3，扇区 45）
```

反过来验算：

```text
1 × 2000 + 3 × 100 + 45 = 2000 + 300 + 45 = 2345  ✔
```

这个换算在 408 里偶尔出现，也是文件系统「逻辑块 → 物理地址」的最后一步。

**注意除数顺序：先除每柱面的块数，再除每道的扇区数。**

除反了，答案全错。

## 3. 访问时间：三个公式

访问时间（access time）= 寻道 + 旋转 + 传输。

```text
T = Ts + Tr + Tt
```

### 3.1 寻道时间 Ts

```text
Ts = m × n + s

m  每跨一个磁道的时间
n  跨越的磁道数
s  启动时间（磁头臂加速、稳定）
```

例：`m = 0.2 ms`，`s = 2 ms`，跨 20 道：

```text
Ts = 0.2 × 20 + 2 = 4 + 2 = 6 ms
```

题目如果直接给「平均寻道时间 8 ms」，就不用算，直接用。

### 3.2 旋转延迟 Tr

先算转一圈要多久：

```text
一圈时间 = 60 / 转速(转每分) 秒
```

```text
5400 rpm → 60/5400 = 11.11 ms
7200 rpm → 60/7200 =  8.33 ms
15000 rpm → 60/15000 = 4.00 ms
```

平均旋转延迟取**半圈**：

```text
Tr = 1/2 × 一圈时间 = 1/(2r)，r 是每秒转数
```

```text
7200 rpm → r = 120 转/秒 → Tr = 1/(2×120) = 1/240 s = 4.17 ms
5400 rpm → r = 90        → Tr = 1/180 s = 5.56 ms
15000 rpm → r = 250      → Tr = 1/500 s = 2.00 ms
```

**为什么是半圈？**

因为目标扇区在圆周上的位置是随机的。

运气最好，转 0 就到；运气最差，要等一整圈。

平均下来是半圈。

### 3.3 传输时间 Tt

```text
Tt = b / (r × N)

b  要读写的字节数
r  每秒转数
N  一条磁道上的字节数
```

例：7200 rpm，每道 512 个扇区 × 512 B = 262,144 B，读 4 KB。

```text
Tt = 4096 / (120 × 262144)
   = 4096 / 31,457,280
   = 0.000130 s
   = 0.13 ms
```

换个算法验算：

```text
一圈 8.33 ms 读完一整道 256 KB
读 4 KB 需要 8.33 × (4/256) = 8.33 × 0.015625 = 0.13 ms  ✔
```

### 3.4 一个完整的数

```text
平均寻道 8 ms + 平均旋转 4.17 ms + 传输 0.13 ms = 12.3 ms
```

三段的比例：

```text
寻道 65%
旋转 34%
传输  1%
```

**磁盘优化，永远先优化寻道。**

这就是为什么调度算法只关心「移动多少磁道」，而不关心「读多少字节」。

### 3.5 一次完整走查：顺序读 1 MB 有多快

设：7200 rpm，每道 256 KB，1 MB 文件连续放在 4 条相邻磁道上（同一柱面的 4 个盘面）。

```text
寻道：磁头臂移到起始柱面        8 ms（一次）
旋转：等到起始扇区             4.17 ms（平均半圈）
传输：4 条磁道 × 每道 256 KB   4 × 8.33 = 33.3 ms
──────────────────────────────────────────────
合计                          45.5 ms
```

折算带宽：

```text
1 MB / 45.5 ms = 1024 KB / 0.0455 s ≈ 22 MB/s
```

同样的 1 MB，如果拆成 256 个随机分布的 4 KB 块：

```text
每块 = 8 + 4.17 + 0.13 = 12.3 ms
256 块 = 3149 ms
```

对比：

```text
顺序读   45.5 ms
随机读   3149 ms
比值     69 倍
```

**这就是「文件碎片」为什么是真问题。**

一个文件被拆成 256 个碎块，读它的时间从 45 ms 变成 3 秒。

磁盘调度能做的是「把随机请求重排成接近顺序」，能救回一部分。

但救不回全部——因为块本来就不在一起。

## 4. 六种调度算法（上）：FCFS、SSTF、SCAN

统一设定（后面全部按这个算）：

```text
磁盘磁道号 0 ~ 199
当前磁头在 53
请求队列（按到达顺序）：98, 183, 37, 122, 14, 124, 65, 67
当前移动方向：磁道号增大
```

先把请求排序，方便看：

```text
14, 37, 65, 67, 98, 122, 124, 183
```

### 4.1 FCFS：先来先服务

按到达顺序服务，谁也不插队。

```text
53 → 98 → 183 → 37 → 122 → 14 → 124 → 65 → 67
```

逐个算：

```text
53 →  98   |98-53|  = 45    累计 45
 98 → 183  |183-98| = 85    累计 130
183 →  37  146             累计 276
 37 → 122  85              累计 361
122 →  14  108             累计 469
 14 → 124  110             累计 579
124 →  65  59              累计 638
 65 →  67  2               累计 640
```

**总移动 640 个磁道。**

优点：公平，不会饿死。

缺点：磁头来回横跳，像电梯每次只按一个人的楼层跑一趟。

### 4.2 SSTF：最短寻道时间优先

每次选离当前磁头最近的请求。

```text
53 出发，各请求距离：
  65 → 12   ← 最近
  67 → 14
  37 → 16
  14 → 39
  98 → 45
```

```text
53 → 65  12   累计 12
 65 → 67   2   累计 14
 67 → 37  30   累计 44
 37 → 14  23   累计 67
 14 → 98  84   累计 151
 98 → 122 24   累计 175
122 → 124  2   累计 177
124 → 183 59   累计 236
```

**总移动 236 个磁道。**

比 FCFS 少 404，少 63%。

优点：平均寻道最短（局部看）。

缺点：**饥饿**。

```text
如果 14 附近一直有源源不断的新请求到达，
磁头就永远在低磁道区转，183 那个请求可能永远等不到。
```

这不是理论担忧。

真实系统里，一个热点目录的元数据请求就能把远处的请求饿死。

### 4.3 SCAN：电梯算法

磁头沿一个方向一直扫，扫到端点再折返。

```text
方向：增大，端点 199

53 → 65 → 67 → 98 → 122 → 124 → 183 → 199 ┐
                                            │ 折返
14 ← 37 ←───────────────────────────────────┘
```

```text
53 →  65  12   累计 12
 65 →  67  2    累计 14
 67 →  98  31   累计 45
 98 → 122 24    累计 69
122 → 124  2    累计 71
124 → 183 59    累计 130
183 → 199 16    累计 146   ← 到端点
199 →  37 162   累计 308
 37 →  14 23    累计 331
```

**总移动 331 个磁道。**

注意第 7 步：即使 199 上没有请求，也要走到端点。

这就是 SCAN 和 LOOK 的唯一差别。

**SCAN 的代价是「空跑」，收益是「不会饿死」。**

因为每个请求最多等一趟完整扫描。

## 5. 六种调度算法（下）：C-SCAN、LOOK、C-LOOK

前三个算法都允许「来回服务」。

后三个开始考虑「单向」和「端点」。

差别只在一句话：

```text
往哪走、走到哪回头、回头的时候服不服务。
```

### 5.1 C-SCAN：单向扫描

SCAN 有个不公平：中间磁道被扫两次（去一次、回一次），两端只扫一次。

C-SCAN 的改法是：

```text
往一个方向扫，扫到端点，
然后快速回到起点（回程不服务任何请求），
再从起点往同一方向扫。
```

```text
53 → 65 → 67 → 98 → 122 → 124 → 183 → 199
                                        │
                                        │ 直接跳回 0，不服务
                                        ▼
                                        0 → 14 → 37
```

```text
53 → 183 = 130（中间照常停靠）
183 → 199 = 16    累计 146
199 →   0 = 199   累计 345   ← 空跑回程
  0 →  14 = 14    累计 359
 14 →  37 = 23    累计 382
```

**总移动 382 个磁道。**

比 SCAN 多 51。

多出来的就是那趟 199 → 0 的空跑（本来只回 14 就行）。

但 C-SCAN 换来一个性质：

```text
每个磁道的等待时间几乎相同。
```

因为磁头只往一个方向扫，任何请求最多等「从当前位置扫到端点 + 从 0 扫回来」的时间。

**均匀性比平均值更重要的时候，用 C-SCAN。**

### 5.2 LOOK 与 C-LOOK

SCAN 和 C-SCAN 有个明显的浪费：跑到端点，可端点往往没有请求。

LOOK 的改法只有一句：

```text
不跑到端点，跑到「这个方向上最后一个请求」就折返。
```

```text
53 → 65 → 67 → 98 → 122 → 124 → 183   （183 是最大请求，不是 199）
183 → 37   146    累计 276
 37 → 14    23    累计 299
```

**总移动 299 个磁道。**

比 SCAN 少 32。

少的正好是 `183 → 199 → 183` 那两趟空跑（16 + 16 = 32）。

C-LOOK 同理：

```text
53 → 183 = 130
183 → 14 = 169   累计 299   ← 跳回最小请求，不服务回程
 14 → 37 = 23    累计 322
```

**总移动 322 个磁道。**

### 5.3 六个结果并排

```text
算法     服务顺序                                       总移动磁道数
─────────────────────────────────────────────────────────────────
FCFS     98,183,37,122,14,124,65,67                        640
SSTF     65,67,37,14,98,122,124,183                        236
SCAN     65,67,98,122,124,183,(199),37,14                  331
C-SCAN   65,67,98,122,124,183,(199),(0),14,37              382
LOOK     65,67,98,122,124,183,37,14                        299
C-LOOK   65,67,98,122,124,183,(14),37                      322
```

六个数的排序：

```text
236 (SSTF) < 299 (LOOK) < 322 (C-LOOK) < 331 (SCAN) < 382 (C-SCAN) < 640 (FCFS)
```

按移动距离看，SSTF 最好。

按「最坏等待时间」看，SSTF 最差（可能无限等待）。

**这就是调度里永恒的矛盾：平均值 vs 公平性。**

| 算法 | 总移动 | 饥饿 | 均匀性 | 一句话 |
|---|---|---|---|---|
| FCFS | 640 | 无 | 差 | 公平但瞎跑 |
| SSTF | 236 | **有** | 差 | 贪心，局部最优 |
| SCAN | 331 | 无 | 中 | 扫到端点，来回服务 |
| C-SCAN | 382 | 无 | **好** | 单向扫，回程空跑 |
| LOOK | 299 | 无 | 中 | SCAN 不跑到端点 |
| C-LOOK | 322 | 无 | 好 | C-SCAN 不跑到端点 |

### 5.4 FSCAN 与 N-Step SCAN：SCAN 还不够的地方

SCAN 有个隐含前提：**请求队列在扫描期间不变。**

现实里请求一直在来。

```text
磁头正从 53 扫向 183，
这时来了一个新请求 60。
它在磁头已经走过的位置 → 必须等下一趟。
```

如果新请求不断出现在「磁头前方」，那还好。

如果新请求总是出现在「刚走过的位置」，就退化成「永远在返程」。

FSCAN 的改法：

```text
把请求队列复制成两份：
  Q1：当前这趟服务的
  Q2：这趟期间新来的
扫完 Q1 再扫 Q2，Q2 期间新来的进 Q1。
```

```text
效果：把「无界的新请求」切成「有界的一批」。
代价：实现复杂，Q2 里的请求要等一整趟 Q1。
```

N-Step SCAN 更狠：一次只服务 N 个请求，剩下的排队等下一轮。

**这些变体 408 不考，但它们解释了「为什么真实调度器比教科书复杂」。**

教科书教的是形状，工程里要处理的是「流」。

## 6. 408 怎么考

三类题。

```text
① 给请求队列和磁头位置，算某个算法的总移动磁道数
② 给算法，写出服务顺序
③ 问 SCAN 和 LOOK、SCAN 和 C-SCAN 的区别
```

套路三步：

```text
第一步：排序，写出所有请求
第二步：画出扫描方向，标出折返点
第三步：逐段相减，累加
```

### 6.1 例题：SSTF、SCAN、LOOK 各算一遍

题目（自拟）：

```text
磁道号 0~199，磁头初始在 100，向磁道号增大方向移动。
请求队列（按到达顺序）：55, 58, 39, 18, 90, 160, 150, 38, 184
求 SSTF、SCAN、LOOK 三种算法的总移动磁道数。
```

先排序：

```text
18, 38, 39, 55, 58, 90, 150, 160, 184
```

**SSTF：**

```text
100 出发，最近的是 90（距离 10）
100 → 90   10    累计 10
 90 → 58   32    累计 42
 58 → 55    3    累计 45
 55 → 39   16    累计 61
 39 → 38    1    累计 62
 38 → 18   20    累计 82
 18 → 150 132    累计 214
150 → 160  10    累计 224
160 → 184  24    累计 248
```

答案：**248**。

验算：把每段距离加起来 —— 10+32+3+16+1+20+132+10+24。

```text
10+32 = 42
42+3  = 45
45+16 = 61
61+1  = 62
62+20 = 82
82+132= 214
214+10= 224
224+24= 248  ✔
```

**SCAN（增大方向，到 199 折返）：**

```text
100 → 150  50    累计 50
150 → 160  10    累计 60
160 → 184  24    累计 84
184 → 199  15    累计 99    ← 到端点
199 →  90 109    累计 208
 90 →  58  32    累计 240
 58 →  55   3    累计 243
 55 →  39  16    累计 259
 39 →  38   1    累计 260
 38 →  18  20    累计 280
```

答案：**280**。

验算（用端点公式）：

```text
上行：(199 - 100) = 99
下行：(199 - 18)  = 181
合计：99 + 181 = 280  ✔
```

这个公式很好用：

```text
SCAN 总移动 = |端点 - 起点| + |端点 - 最远反向请求|
```

**LOOK（到 184 折返）：**

```text
100 → 184  84    累计 84
184 →  18 166    累计 250
```

答案：**250**。

验算：

```text
上行 184 - 100 = 84
下行 184 - 18  = 166
合计 84 + 166  = 250  ✔
```

三个数放一起：

```text
SSTF 248 < LOOK 250 < SCAN 280
```

**注意 SSTF 赢了，但只赢了 2 个磁道。**

而它付出的代价是「18 号请求等到了最后」——正是那个 132 的大跳跃。

### 6.2 例题：SCAN 与 C-SCAN 的服务顺序

题目（自拟）：

```text
沿用上题数据，磁头 100，向增大方向。
写出 C-SCAN 的服务顺序，并算总移动磁道数。
```

服务顺序：

```text
100 → 150 → 160 → 184 → 199 → (跳回 0，不服务) → 18 → 38 → 39 → 55 → 58 → 90
```

```text
上行     199 - 100 = 99
回程     199 - 0   = 199
再次上行  90 - 0   = 90
────────────────────────
合计     99 + 199 + 90 = 388
```

答案：**388**。

对比一下：

```text
SCAN   280（回程服务，一趟扫完）
C-SCAN 388（回程空跑，多花 108）
```

多花的 108 = 199 - 90 - 1... 换个说法：

```text
C-SCAN 多走了「0 到 18 那一段」加上「回程不能服务」的代价。
```

**C-SCAN 更慢，但每个请求的等待时间更均匀。**

### 6.3 常见问法与陷阱

```text
问：SCAN 一定要走到 199 吗？       答：看题目约定，教材默认走到端点；LOOK 则走到最后一个请求
问：磁头初始方向重要吗？           答：非常重要，方向反了答案完全不同
问：SSTF 会不会饿死？              答：会，新请求不断插入近处时
问：FCFS 有什么优点？              答：公平、实现简单、不会饿死
问：C-SCAN 的回程算不算移动？      答：算，回程空跑也消耗时间
```

最容易错的两个点：

```text
① 忘了算折返那一段（只算了上行）
② 把 199 当成 183（题目给的是端点，不是最大请求）
```

## 7. 真实系统里长什么样

Linux 的块层（block layer）里，调度器是可插拔的。

```bash
$ cat /sys/block/sda/queue/scheduler
[none] mq-deadline kyber bfq
```

方括号里是当前生效的。

四个常见选择：

```text
none          不做重排，直接下发（NVMe SSD 常用）
mq-deadline   带截止时间的多队列版本，防饿死
kyber         面向低延迟设备，按队列深度调
bfq           按进程公平分配带宽，桌面常用
```

**SSD 为什么常常用 none？**

因为 SSD 没有磁头，没有「寻道」这个概念。

```text
机械盘：随机访问 12 ms，顺序访问 0.1 ms → 差 100 倍，必须重排
SSD：  随机访问 0.1 ms，顺序访问 0.05 ms → 差 2 倍，重排收益很小
```

重排反而增加延迟和 CPU 开销，不划算。

这就是「算法依赖硬件特性」的典型例子。

**看磁盘是不是机械的。**

```bash
$ cat /sys/block/sda/queue/rotational
1        # 1 = 机械盘，0 = SSD
$ lsblk -d -o NAME,ROTA,SIZE,MODEL
NAME ROTA  SIZE MODEL
sda     1 465.8G ST500DM002
nvme0n1 0 476.9G Samsung SSD 980
```

`ROTA` 就是 rotational，一眼看出该不该用调度。

**看分区和引导。**

```bash
$ sudo fdisk -l /dev/sda
Disk /dev/sda: 465.76 GiB, 500107862016 bytes, 976773168 sectors
Units: sectors of 1 * 512 = 512 bytes
Disklabel type: dos
Device     Boot   Start       End   Sectors  Size Id Type
/dev/sda1  *       2048   1050623   1048576  512M 83 Linux
/dev/sda2       1050624 976773119 966712496  461G 83 Linux
```

`Boot` 列那个 `*`，就是「活动分区」。

BIOS 读完 MBR 之后，跳到这个分区的第一个扇区（分区引导块），再往下走。

**看坏块。**

```bash
$ sudo smartctl -a /dev/sda | head -20
SMART overall-health self-assessment test result: PASSED
  5 Reallocated_Sector_Ct   0x0033   100   100   010    Pre-fail
197 Current_Pending_Sector  0x0012   100   100   000    Old_age
```

`Reallocated_Sector_Ct` 就是「已经用备用扇区顶替掉的坏扇区数」。

现代磁盘出厂时就留了一批备用扇区，坏了就重映射（简化示意）。

**看磁盘的实际速度。**

```bash
$ sudo hdparm -Tt /dev/sda
 Timing cached reads:   18000 MB in  2.00 seconds = 9000 MB/sec
 Timing buffered disk reads: 400 MB in  3.00 seconds = 133 MB/sec
```

机械盘顺序读 100~200 MB/s，SSD 能到几千 MB/s。

这个差别，就是「有没有寻道」的差别。

以上是简化示意，不含 zone、TCQ、NCQ、多队列的具体实现。

## 8. 磁盘管理：分区、格式化、引导块、坏块

### 8.1 分区

一块物理磁盘，逻辑上切成几块，每块叫一个分区。

```text
/dev/sda
├── /dev/sda1   512 MB     /boot
├── /dev/sda2   100 GB     /
├── /dev/sda3    16 GB     swap
└── /dev/sda4   剩余       /home
```

分区表有两种：

```text
MBR   主引导记录，4 个主分区，最大 2 TB，兼容性好
GPT   全局唯一标识分区表，128 个分区，支持超大磁盘，需要 UEFI
```

分区表存在磁盘的第一个扇区（MBR）或前几个扇区（GPT）。

### 8.2 格式化

格式化分两步，很多人混成一步。

**低级格式化（物理格式化）**：出厂时做，或者在磁盘上重新划分扇区。

```text
给每个扇区写：前导码、地址标记、数据区、ECC 校验码
结果是「一堆能读写的扇区」，还没有文件系统
```

现在这一步基本在出厂时完成，用户不做。

**高级格式化（逻辑格式化）**：建文件系统。

```text
写超级块
建 inode 表
建位示图
建根目录
```

```bash
$ mkfs.ext4 /dev/sda2
```

这一步之后，磁盘上才有「文件」这个概念。

**顺序不能反：分区 → 高级格式化 → 挂载。**

### 8.3 引导块

开机时 CPU 执行的第一条指令在 ROM 里。

ROM 里的代码（BIOS/UEFI）只知道一件事：读第一个扇区。

```text
① CPU 复位，跳到 ROM 里的固件
② 固件自检，然后读磁盘的第 0 号扇区（MBR，512 B）
③ MBR 里的引导代码扫描分区表，找到活动分区
④ 跳到活动分区的第 0 个扇区（分区引导块 / 引导扇区）
⑤ 分区引导块加载操作系统内核
```

画成链：

```text
ROM 固件 → MBR（含分区表）→ 活动分区的引导块 → 内核
```

有些文件系统会在自己的开头留一个 boot block，专门放引导代码（简化示意）。

**MBR 只有 512 B，装不下多少代码。**

所以它通常只做一件事：把控制权交给更大的引导程序（GRUB 的 stage1.5 / stage2）。

### 8.4 坏块

磁盘用久了会出现坏块（bad block）。

三种处理方式：

```text
① 扇区备用（spare sectors）
   出厂预留一批备用扇区，坏了就重映射，操作系统看不见
② 扇区转发（sector forwarding）
   坏块的表项指向一个备用块，逻辑块号不变
③ 文件系统标记
   FAT 把坏簇标成 0xFFF7；ext 系列用坏块列表（badblocks）
```

```bash
$ sudo badblocks -sv /dev/sda2
Checking blocks 0 to 52428799
Pass completed, 0 bad blocks found.
```

坏块处理对上层是透明的，代价是「备用扇区用完了就真坏了」。

**这就是 SMART 里 `Reallocated_Sector_Ct` 值得盯着的原因。**

### 8.5 分区对齐：一个 512 B 引发的性能问题

老磁盘的扇区是 512 B，新磁盘（尤其是大容量盘和 SSD）的物理扇区是 4 KB。

```text
文件系统按 512 B 的逻辑扇区编号，实际按 4 KB 的物理扇区读写。
```

如果分区起点没和 4 KB 边界对齐：

```text
一个 4 KB 的文件系统块，横跨两个物理扇区
→ 一次读变成两次读
→ 写更糟：要先读-改-写
```

```bash
$ sudo parted /dev/sda align-check optimal 1
1 aligned
```

现代分区工具默认从 2048 号扇区（1 MB 处）开始，就是为了对齐。

**这个问题在 SSD 上更严重**，因为 SSD 的写放大直接换算成寿命。

## 9. 反直觉：SSTF 为什么不是最优

前面那组数据，SSTF 是 236，比 LOOK 的 299 还小。

看起来贪心赢了。

但换个请求队列，贪心就输。

看这个小例子：

```text
磁道 0~199，磁头在 50，请求：0, 40, 49, 51, 60, 100
```

**SSTF 走法：**

```text
 50 →  49   1    累计 1
 49 →  51   2    累计 3
 51 →  60   9    累计 12
 60 →  40  20    累计 32
 40 →   0  40    累计 72
  0 → 100 100    累计 172
```

总移动 **172**。

**LOOK 走法（先向大）：**

```text
 50 →  60  10
 60 → 100  40
100 →   0 100    （回程顺手服务 49、40、0）
```

总移动 **150**。

```text
SSTF 172 > LOOK 150
```

**贪心输给了一趟扫描。**

为什么？

因为 SSTF 的每一步都只看「眼前最近」，它把 49、51、40、0 这几个近处的点反复来回吃掉，最后被迫从 0 一口气跑到 100。

```text
SSTF 的路径：50→49→51→60→40→0→100
              来回折返 3 次

LOOK 的路径：50→60→100→0
              只折返 1 次
```

这就是「贪心算法」的经典失败模式：

```text
每一步都选局部最优，
整体却可能落在次优解上。
```

磁盘调度是一维的「访问所有点」问题。

一维情况下，最优解的形状是确定的：

```text
先走到一端，再走到另一端。
总距离 = (max - min) + min(|起点 - min|, |起点 - max|)
```

代入：max = 100，min = 0，起点 50。

```text
(100 - 0) + min(|50-0|, |50-100|)
= 100 + min(50, 50)
= 150
```

**150 就是理论下界，LOOK 正好达到。**

SSTF 的 172 比下界多 22。

所以结论不是「SSTF 不好」，而是：

```text
SSTF 平均很好，但没有最优保证，而且会饿死。
SCAN/LOOK 靠「扫一遍」，牺牲一点平均，换来有界的最坏情况和稳定性。
```

这就是为什么真实系统里的调度器（mq-deadline）更像 SCAN 的亲戚，而不是 SSTF。

**在工程里，「可预测的最坏情况」常常比「好看的平均值」值钱。**

### 9.1 为什么下界是那个公式

一维上访问所有点，路径一定由「向前的一段」和「向后的一段」组成。

```text
要么先去最小值、再去最大值；
要么先去最大值、再去最小值。
```

两种走法：

```text
先去 min 再去 max：(起点 - min) + (max - min)
先去 max 再去 min：(max - 起点) + (max - min)
```

公共项是 `(max - min)`，可变项是 `min(起点 - min, max - 起点)`。

所以：

```text
最优 = (max - min) + min(|起点 - min|, |起点 - max|)
```

**这个式子只在一维、且所有点都要访问时成立。**

二维的磁盘（柱面 + 盘面）就不是这样了。

但 408 只考一维。

### 9.2 饥饿真的会发生吗

会，而且很容易构造。

```text
场景：一个数据库服务器，磁头在 1000 附近。
低地址区（0~100）每 5 ms 来一个日志写请求，
高地址区（9000~9100）有一个归档读请求。
```

```text
SSTF：磁头永远在 1000 附近打转，
      每次都被「距离 500 以内」的新日志请求吸走，
      9000 那个请求永远排不上。
```

```text
SCAN：磁头照样扫到 9100，
      归档请求最多等一趟完整扫描（约几十 ms）。
```

现实中这类问题的表现更隐蔽：

```text
某个目录的元数据一直被访问，
它的 inode 恰好在磁盘的低地址区，
于是低地址区的请求永远占优，
高地址区的文件读起来像「卡住」。
```

**调度器的公平性，不是「道德问题」，是「能不能保证上界」的工程问题。**

## 10. 容易混淆的点

**① 寻道时间和旋转延迟。**

```text
寻道   磁头臂横向移动，跨磁道，最贵（几 ms）
旋转   等盘片转到位置，半圈时间（几 ms）
传输   真正读数据（几十 μs）
```

**② 柱面和磁道。**

柱面是「多个盘面上半径相同的磁道集合」。

所以「柱面号 = 磁道号」，只是视角不同。

**③ SCAN 和 LOOK。**

```text
SCAN 走到磁盘端点（199）
LOOK 走到最后一个请求（183）
```

差的就是那两趟空跑。

**④ SCAN 和 C-SCAN。**

```text
SCAN   来回都服务，中间磁道被扫两次
C-SCAN 只在一个方向服务，回程空跑
```

**⑤ FCFS 的「公平」是什么意思。**

不是「每个请求等待时间相同」，而是「按到达顺序，不会被插队」。

**⑥ 磁盘地址的顺序。**

是（柱面, 盘面, 扇区），不是（盘面, 柱面, 扇区）。

顺序换了，连续读的性能差几倍。

**⑦ 低级格式化和高级格式化。**

```text
低级：划分扇区，写 ECC，出厂做
高级：建文件系统（超级块、inode 表、位示图）
```

**⑧ 调度算法和文件系统的关系。**

磁盘调度在「块层」，文件系统在它上面。

文件系统给出「读物理块 8712」，块层决定「什么时候读、和谁一起读」。

**两层各管各的，别混。**

## 11. 一次完整的调度过程：从 read 到磁头

前面算的是「算法内部」的账。

真实系统里，一个请求要走完这条路径。

```text
用户 read(fd, buf, 4096)
   │
   ▼
页缓存命中？ ── 命中 ──▶ 直接返回（0 次磁盘 I/O）
   │ 未命中
   ▼
文件系统：逻辑块号 → 物理块号
   │
   ▼
块层（block layer）：生成 bio 请求
   │
   ▼
I/O 调度器队列：合并 + 排序
   │
   ▼
设备驱动 → 磁盘控制器 → 磁头
```

关键一步是「合并 + 排序」。

**合并（merge）**：两个请求的块号相邻，合成一个大请求。

```text
请求 A：块 100，长度 4 KB
请求 B：块 101，长度 4 KB
合并后：块 100，长度 8 KB   ← 一次寻道，一次旋转
```

**排序（sort）**：按块号排，让磁头单向走。

```text
队列（按到达）：块 900、块 120、块 300、块 130
排序后：      块 120、块 130、块 300、块 900
```

看出来了吗？

```text
合并减少请求数，排序减少寻道距离。
这两个动作，比「选哪个算法」影响更大。
```

一个极端的例子：

```text
100 个相邻块的读请求，如果不合并：
  100 次寻道 × 8 ms = 800 ms
合并成一条 400 KB 的请求后：
  1 次寻道 8 ms + 传输 1.6 ms ≈ 10 ms
```

**80 倍的差距，来自「合并」这一步，不是来自调度算法。**

所以真实的块层代码里，`elevator` 的注释会先讲合并，再讲排序。

调度算法是在「合并完之后还剩多少请求」的基础上做选择的。

**算法只是最后一层，前面的合并和缓存才是大头。**

所以 408 的题和真实系统是「两个视角」：

```text
408 问：给定队列，这个算法走多少磁道？   → 考算法的形状
真实系统问：这一秒的 1000 个请求怎么排？  → 考合并、队列深度、设备类型
```

两者都对，只是观察的尺度不同。

**先把算法的形状记牢，再理解它为什么在工程里要被改写。**

## 12. 小结

这一篇的骨架：

```text
访问时间 = 寻道 + 旋转 + 传输
         = 8 ms + 4.17 ms + 0.13 ms
         = 12.3 ms
```

三个数要背下来：

```text
7200 rpm  → 一圈 8.33 ms，平均旋转 4.17 ms
5400 rpm  → 一圈 11.11 ms，平均旋转 5.56 ms
传输时间 = 数据量 / (每秒转数 × 每道字节数)
```

六个算法的结果（本题数据）：

```text
FCFS 640、SSTF 236、SCAN 331、C-SCAN 382、LOOK 299、C-LOOK 322
```

四句话总结：

```text
FCFS 公平但瞎跑
SSTF 快但会饿死，且没有最优保证
SCAN 扫到端点，来回服务，不饿死
C-SCAN 单向扫，最均匀，代价是空跑回程
LOOK / C-LOOK 只是把「端点」换成「最后一个请求」
```

这四句之外，还要多记一句：

```text
LOOK 和 C-LOOK 不改变「服务方向」，只改变「回头的位置」。
```

那个反直觉的点再说一遍：

```text
SSTF 每一步都选最近的，
总距离却可能大于「先扫到一端再扫回来」。
贪心不是最优，一维的最优形状是「两段单调」。
```

```text
CPU 怎么和键盘、网卡、磁盘这些速度差 6 个数量级的设备打交道？
程序查询、中断、DMA、通道，四种方式差在哪？
```

```text
操作系统系统讲解 20：I/O 硬件与控制方式
```
