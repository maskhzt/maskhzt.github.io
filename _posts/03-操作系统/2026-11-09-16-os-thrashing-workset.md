> **读这篇之前，你只需要知道**：内存被切成一样大的小块，叫页框；一个进程能占的页框数是有限的；程序真正在用的那几页如果装不下，就会一直缺页，而一次缺页要去磁盘取，几毫秒，比读内存慢几万倍。
> **这篇讲什么**：为什么进程一多，系统会陷进"CPU 闲着、磁盘狂转、越努力越慢"的死循环，以及怎么用一个能算出来的量把它摁住。
> **一个类比**：十个人挤一个灶台，谁都做不完一道菜；不如先让三个人做，做完再换人——少几个人同时上，总产出反而更高。


先描述一个很多人见过的场景。

编译一个大项目，`make -j8` 跑了 3 分钟。

有人想快一点，改成 `make -j64`。

结果跑了 15 分钟，还没完。

看一眼 `top`：

```text
%Cpu(s):  3.2 us,  1.1 sy, 95.7 id
```

CPU 95% 空闲。

再看磁盘：

```text
iostat -x 1
```

利用率接近 100%，读写队列排到几十。

内存呢？

```text
free -m
              total   used   free   shared  buff/cache
Mem:          15884  15620    120       80         144
Swap:          8191   6100    2091
```

内存满了，swap 用掉 6 GB。

这就是抖动（thrashing）。

它的表现很反常识：

```text
CPU 几乎不干活
磁盘忙到冒烟
吞吐量接近零
```

更反常识的是它的成因链。

操作系统看到 CPU 空闲，会得出一个结论：

**"多道程度不够，再放几个进程进来。"**

多道程度（degree of multiprogramming）：同一时刻内存里同时跑着几个进程。

多，意味着资源摊得薄；少，意味着每个进程分到的页框多。

于是又调进来几个编译进程。

每个进程分到的页框更少，缺页更多，CPU 更空闲。

操作系统看到 CPU 更空闲，决定再放几个。

越调越糟。

## 1. 抖动：越努力越糟

为什么偏偏要给这个现象单独起个名字？

因为它的表现和"内存不够就慢一点"的直觉正好相反：它不是慢一点，是能让整台机器接近停摆，而且越调度越糟。

抖动的定义，一句话：

```text
进程刚换出的页，马上又要用；
刚换入的页，还没来得及用就被换出。
缺页率高到系统把绝大部分时间花在换页上。
```

拆开看，是三个数字同时恶化。

```text
缺页率：从千分之几涨到百分之几十
CPU 利用率：从 90% 掉到个位数
磁盘 I/O：从偶尔几次变成持续满负荷
```

为什么会形成正反馈？

把操作系统的决策逻辑写出来就清楚了。

```text
① 调度器看 CPU 利用率
② CPU 利用率低 → 判断"进程太少，都在等 I/O"
③ 提高多道程度，调入更多进程
④ 每个进程分到的页框变少
⑤ 工作集装不下 → 缺页率上升
⑥ 缺页要等磁盘 → 进程阻塞 → CPU 更空闲
⑦ 回到 ①，而且情况更糟
```

画成环：

```text
      CPU 利用率低
           │
           ▼
    ┌──────────────┐
    │ 提高多道程度 │
    └──────┬───────┘
           │
           ▼
      每进程页框少
           │
           ▼
        缺页率↑
           │
           ▼
     进程等磁盘阻塞
           │
           └──────▶ CPU 利用率更低
```

这个环一旦转起来，唯一的出口是**减少**多道程度，或者加内存。

而那正是操作系统最不愿意做的两件事。

> **反直觉的点在这里。**
>
> 抖动时系统看起来很"忙"：磁盘灯狂闪，`load average` 很高，`iostat` 满负荷。
>
> 但吞吐量接近零。
>
> 这是唯一一个"越努力越糟"的性能问题：调度器越想提高利用率，利用率越低。

算一笔账，看看缺页率有多可怕。

这一步算的是"平均一次访存要多久"，用它来解释 `top` 里 CPU 为什么那么闲。

算法还是加权平均：绝大多数访存很快，极少数缺页极慢，平均下来会被那极少数拖垮。

内存访问 100 ns，缺页处理 8 ms。

缺页率 0.1%（每 1000 次访存缺一次）：

```text
EAT = 0.999 × 100 + 0.001 × 8,000,000
    = 99.9 + 8000
    = 8099.9 ns
```

有效利用率：

```text
100 / 8099.9 ≈ 1.23%
```

**CPU 有 98.8% 的时间在等磁盘。**

这就是 `top` 里那 95% 的空闲。

不是没活干，是活干不下去。

再算一步，看看"多道程度"在这条链上扮演什么角色。

假设每个进程每秒需要 S 次访存，缺页率 p，缺页处理时间 8 ms。

那么每个进程每秒花在等页上的时间是：

```text
S × p × 8 ms
```

CPU 每秒能提供的有效计算时间是有限的。

进程数越多，缺页率 p 越高（因为每人的页框更少），等页时间按平方级增长。

所以吞吐量曲线一定会掉头向下。

这不是某个算法的 bug，是"资源总量固定 + 需求随并发线性增长"的必然结果。

## 2. 最小模型：驻留集、工作集、缺页率

要判断"是不是要抖了"，需要一个可计算的量。

三个概念先分清。

```text
驻留集（resident set）：当前真正在内存里的页的集合
                        大小 = 分到的页框数
工作集（working set）：最近 Δ 时间内被访问过的页的集合
                        大小 = WSS（working set size）
```

一句话区分：

```text
工作集是"需要多少"，驻留集是"给了多少"。
```

判断标准：

```text
驻留集 ⊇ 工作集 → 不缺页，跑得动
驻留集 ⊂ 工作集 → 一定缺页，缺得厉害就是抖动
```

**如果没有工作集这个概念会怎样？**

操作系统只能拍脑袋给每个进程分页框：分多了浪费，分少了抖动。

更麻烦的是它没有任何依据判断"现在到底够不够"。

因为 CPU 忙不忙，看不出内存紧不紧——抖动的时候 CPU 恰恰是闲的。

等发现变慢，往往已经掉进正反馈里了。

工作集的价值，就是把"够不够"变成一个能算的数：需求多少、供给多少，一比就知道。

工作集的定义有两种写法。

```text
按时间：W(t, Δ) = 在时间区间 [t−Δ, t] 内被访问过的页
按引用：W(t, Δ) = 在最近 Δ 次访存里被访问过的页
```

408 用第二种，因为它不需要时间轴，只数引用次数。

两种定义的本质一样：

```text
用一个"窗口"圈住最近的活动，窗口里的页就是当前的工作集。
```

窗口（window）：一段固定的观察范围，可以是最近 Δ 毫秒，也可以是最近 Δ 次访存。

窗口大小 Δ 是个关键参数。

```text
Δ 太小：窗口只圈住最近几页，漏掉真正在用的页 → 低估工作集
Δ 太大：窗口圈进早就用完的页 → 高估工作集
```

工程上 Δ 通常取几十毫秒到几秒，或者几千次访存。

工作集有三个性质，判断题常用来排除错误选项：

```text
① WSS ≤ Δ：窗口里最多 Δ 次访问，不同页不会更多
② WSS ≤ 进程的总页数
③ WSS 随 Δ 单调不减：窗口变大，圈进来的页只多不少
```

第三条解释了为什么 Δ 要动态调：

```text
程序刚启动，窗口小一点更准
程序进入稳定循环，窗口大一点更稳
```

还有第三个量：缺页率。

```text
缺页率 = 缺页次数 / 访存次数
```

它和工作集的关系是：

```text
工作集装得下 → 缺页率低（只剩冷启动和偶尔的冲突）
工作集装不下 → 缺页率随"缺多少"迅速上升
```

## 3. 一次完整走查：算工作集

为什么非要亲手算一遍？

因为工作集的题，坑不在公式，在"数不同页"这个动作上。

算两三个时刻，手就熟了；只看别人算，考场上一定把窗口长度当答案。

引用串（16 次）：

```text
3, 1, 4, 1, 5, 9, 2, 6, 5, 3, 5, 8, 9, 7, 9, 3
```

取 Δ = 5，按"最近 5 次访存"算工作集。

逐个时刻算：

```text
t=1   访问 3        窗口 {3}                       WSS=1
t=2   访问 1        窗口 {3,1}                     WSS=2
t=3   访问 4        窗口 {3,1,4}                   WSS=3
t=4   访问 1        窗口 {3,1,4,1} → {1,3,4}       WSS=3
t=5   访问 5        窗口 {3,1,4,1,5} → {1,3,4,5}   WSS=4
t=6   访问 9        窗口 {1,4,1,5,9} → {1,4,5,9}   WSS=4
t=7   访问 2        窗口 {4,1,5,9,2} → 5 个不同页  WSS=5
t=8   访问 6        窗口 {1,5,9,2,6} → 5 个不同页  WSS=5
t=9   访问 5        窗口 {5,9,2,6,5} → {2,5,6,9}   WSS=4
t=10  访问 3        窗口 {9,2,6,5,3} → 5 个不同页  WSS=5
t=11  访问 5        窗口 {2,6,5,3,5} → {2,3,5,6}   WSS=4
t=12  访问 8        窗口 {6,5,3,5,8} → {3,5,6,8}   WSS=4
t=13  访问 9        窗口 {5,3,5,8,9} → {3,5,8,9}   WSS=4
t=14  访问 7        窗口 {3,5,8,9,7} → 5 个不同页  WSS=5
t=15  访问 9        窗口 {5,8,9,7,9} → {5,7,8,9}   WSS=4
t=16  访问 3        窗口 {8,9,7,9,3} → {3,7,8,9}   WSS=4
```

两个细节值得停一下。

**t=4 时窗口有 4 次访问，但只有 3 个不同页。**

因为 1 出现了两次。

工作集是集合，重复访问不增加大小。

这是最容易写错的地方：把"窗口长度"当成"工作集大小"。

**t=7 和 t=8 时 WSS=5，正好等于 Δ。**

不是巧合：窗口里 5 次访问落在 5 个不同页上，说明这段时间没有任何复用。

这种"零复用"的窗口，是抖动的前兆。

WSS 序列：

```text
1, 2, 3, 3, 4, 4, 5, 5, 4, 5, 4, 4, 4, 5, 4, 4
```

三个统计量：

```text
最大 WSS = 5
最小 WSS = 1
平均 WSS = (1+2+3+3+4+4+5+5+4+5+4+4+4+5+4+4) / 16
        = 61 / 16
        = 3.8125
```

验算求和：

```text
1+2 = 3
3+3 = 6     → 9
4+4 = 8     → 17
5+5 = 10    → 27
4           → 31
5           → 36
4+4+4 = 12  → 48
5           → 53
4+4 = 8     → 61
```

61 / 16：

```text
61 ÷ 16 = 3.8125 ✓
```

现在做容量规划。

假设有 4 个这样的进程并发。

按平均 WSS 算：

```text
4 × 3.8125 = 15.25 → 至少 16 个页框
```

按峰值算：

```text
4 × 5 = 20 个页框
```

如果系统只有 12 个页框：

```text
供给 12 个，需求 16 个，缺 4 个
```

四个进程的工作集总需求已经超过供给，缺页率必然升高。

缺 4 个页框，就意味着至少有一个进程的工作集装不全。

它就是那个"一直缺页"的进程。

它一直缺页，就一直占着 CPU 时间片却干不出活，调度器看到 CPU 空闲，又会调入新进程。

正反馈开始。

再看一个对照：Δ 取 10。

t=16 时窗口是 t=7 到 t=16：

```text
2, 6, 5, 3, 5, 8, 9, 7, 9, 3
```

集合：

```text
{2,3,5,6,7,8,9} → WSS=7
```

Δ 从 5 加到 10，WSS 从 4 涨到 7。

多出来的 2、6 早就不再用了，但因为还在窗口里，被算进了工作集。

这就是"Δ 太大导致高估"的具体样子。

高估的后果是：系统给进程多分了页框，别的进程就少了。

所以 Δ 不是越大越好。

再看另一个极端：Δ 取 2。

t=16 时窗口只有 `9, 3`，WSS=2。

t=14 时窗口是 `7, 9`，WSS=2。

但这两个时刻程序真正在用的页明显不止 2 个。

低估的后果是：系统只给 2 个页框，进程每次跨页都缺页。

```text
Δ=2  → 低估 → 帧给少了 → 缺页
Δ=10 → 高估 → 帧给多了 → 别的进程缺页
Δ=5  → 接近真实工作集
```

这就是为什么工作集模型在工程上难用：Δ 得跟着程序的行为变。

没有一个 Δ 能同时适合所有程序。

## 4. 拆开看：原因、策略、曲线、映射

知道抖动长什么样之后，要追问：它为什么会发生？

四个原因里，有两个是操作系统自己造成的——进程放太多、置换选错范围。

也就是说，抖动不全是程序的错，调度策略也会亲手把它推下去。

### 4.1 抖动的四个原因

```text
① 进程太多（多道程度过高）
② 每个进程分到的页框太少
③ 置换算法不当
④ 程序本身局部性差
```

第①和第②是同一件事的两面。

页框总数固定，进程越多，每人分到的越少。

举个数：

```text
16 GB 内存，4 KB 页 → 4,194,304 个页框
内核和页缓存占掉 40% → 剩约 250 万个
2000 个进程 → 平均每个 1250 个页框（约 5 MB）
```

看起来还行。

但如果每个进程的工作集是 8 MB（2048 页），需求就是 400 万页框。

供给 250 万，需求 400 万。

差的这 150 万页框，就是抖动的燃料。

第③条比较隐蔽。

全局置换会让一个进程的缺页，去抢别的进程的页。

```text
A 缺页 → 抢了 B 的热点页
B 立刻缺页 → 抢了 C 的
C 缺页 → 抢了 A 的
```

三个本来都还过得去的进程，被串成一条缺页链。

局部置换至少保证"每个进程自己抖，不传染"。

第④条是程序的问题，操作系统管不了。

"局部性差"有两种，后果不一样。

```text
完全没有复用：每页只碰一次，碰完就走
              → 每次都是冷缺页，慢在 I/O，但不叫抖动
复用多、间隔长：数据集比内存大，访问又接近随机
              → 刚换出就要用，这才是抖动的典型来源
```

真正要命的是第二种。

举个具体例子。

一个程序要处理 100 GB 的日志，方式是"逐行读、逐行算、结果写走"。

每一行只读一次，读完就再也不碰。

```text
工作集 = 当前正在处理的那几页 + 输出缓冲的那几页
       ≈ 几十 KB
```

这个程序的工作集很小，不管文件多大，它都不会抖。

反过来，一个程序要把 100 GB 的数据建成哈希表，然后反复随机查询。

```text
工作集 = 整个哈希表 ≈ 100 GB
```

内存只有 16 GB，它每次查询都可能缺页。

这不是操作系统的问题，是程序选错了数据结构。

同一台机器上，第一种程序跑得很好，第二种必然抖动。

### 4.2 页面分配策略

三种可用策略，一种自相矛盾。

| 策略 | 帧数 | 置换范围 | 特点 |
|---|---|---|---|
| 固定分配 + 局部置换 | 固定 | 自己的帧 | 简单；帧数定少了就抖，定多了浪费 |
| 可变分配 + 全局置换 | 可变 | 全局 | 灵活；会传染缺页，容易连锁 |
| 可变分配 + 局部置换 | 可变 | 自己的帧 | 最稳；实现复杂，需要动态调帧 |
| 固定分配 + 全局置换 | 号称固定 | 全局 | 自相矛盾，基本不用 |

重点看第三种。

它的做法是：

```text
每个进程先分一批帧
运行中观察缺页率
  缺页率 > 上限 → 从空闲链表或其他进程拿几帧给它
  缺页率 < 下限 → 收回几帧
缺页时只在自己帧里选 victim
```

这套机制的好处：

```text
抖动的进程能自己缓过来（拿到更多帧）
不会把别人拖下水（只换自己的帧）
```

坏处：

```text
"从其他进程拿帧"这一步，还是可能引发连锁
调帧的阈值和步长难定
```

但它是工程上最常用的折中。

Linux 的 cgroup 内存控制，本质上就是"可变分配 + 组内全局回收"：

```text
组内的页框总数有上限（memory.max）
组内谁缺页，就从组内的 LRU 链表里抢
组间互不影响
```

### 4.3 缺页率与多道程度

把"多道程度"作为横轴，把"CPU 利用率"作为纵轴，会得到一条很典型的曲线。

```text
CPU
利用率
  │                    ╭──────╮
  │                 ╭──╯      ╰──╮
  │              ╭──╯            ╰──╮
  │          ╭───╯                 ╰───╮
  │      ╭───╯                         ╰────
  │  ╭───╯
  └──┴────┴────┴────┴────┴────┴────┴────┴──▶ 多道程度
     上升区      饱和区      抖动区
```

三段：

```text
上升区：进程少，CPU 没喂饱，加进程就涨
饱和区：CPU 基本跑满，再加进程收益很小
抖动区：进程太多，每个都装不下工作集，利用率断崖下跌
```

判断"是不是进了抖动区"，有两种模型。

```text
工作集模型：Σ WSS(所有进程) > 可用页框数 → 抖动
缺页率模型（PFF）：某进程缺页率 > 上限 → 给它加帧；加不了 → 挂起它
```

工作集模型的问题是要实时算 WSS，代价高。

PFF（page fault frequency）只看缺页率，便宜得多。

它的逻辑：

```text
缺页率太高 → 页框不够 → 加帧
缺页率太低 → 页框多了 → 减帧
加不出来 → 挂起这个进程
```

**"挂起进程"是抖动的标准解法。**

中级调度把一些进程换出到磁盘，多道程度降下来，剩下的进程就能装下工作集。

代价是那些进程暂时不干活。

但总比所有进程都干不了活强。

这就是抖动的残酷之处：

```text
想提高吞吐量，先得降低并发度。
```

还有一点：抖动区有滞后性。

一旦进入，即便立刻挂起几个进程，也要等一段时间才能恢复。

因为被换出的页要重新读回来，而磁盘队列已经排满了。

所以运维上宁可提前限流，也不要在抖动发生之后再补救。

### 4.4 内存映射文件：mmap

为什么讲抖动的文章要花一节讲 mmap？

因为它是"少占内存、少做拷贝"的一条正路：同一份文件数据，不必在内存里存两份。

省下来的页框，正好是给工作集用的。

mmap 是另一条路：把文件直接映射进地址空间，读写内存就是读写文件。

```c
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>

int fd = open("data.bin", O_RDWR);
off_t len = 4096 * 1024;                 /* 4 MB */

char *p = mmap(NULL, len,                /* 让内核选地址 */
               PROT_READ | PROT_WRITE,   /* 可读可写 */
               MAP_SHARED,               /* 共享映射 */
               fd, 0);                   /* 从文件偏移 0 开始 */

if (p == MAP_FAILED) { /* 处理错误 */ }

p[0] = 'A';                              /* 写内存 */
memcpy(p + 4096, buf, 1024);             /* 还是写内存 */

msync(p, len, MS_SYNC);                  /* 确保落盘 */
munmap(p, len);                          /* 解除映射 */
close(fd);
```

它和 `read/write` 的区别，画出来最清楚：

```text
read/write：
  磁盘 → 页缓存 → 用户缓冲区 → 程序
                  ↑ 一次内核到用户的拷贝

mmap：
  磁盘 → 页缓存
           ↑
        程序的页表直接指向它
        没有拷贝
```

mmap 之后，第一次访问某一页会触发缺页。

内核把文件对应的页从 page cache 填进页表，然后返回。

之后再访问，就是普通的内存访问。

两种映射要分清：

```text
MAP_SHARED：修改写回文件，其他映射了同一文件的进程能看到
MAP_PRIVATE：写时复制，修改只对自己可见，不写回文件
```

共享映射的图：

```text
        ┌────────────────┐
        │   page cache   │  物理内存里的一份文件页
        │  ┌────┬────┬──┐│
        │  │页 0│页 1│… ││
        │  └─┬──┴─┬──┴──┘│
        └────┼────┼──────┘
             │    │
     ┌───────┘    └────────┐
     ▼                     ▼
  进程 A 的页表          进程 B 的页表
  都指向同一份物理页
```

两个进程读同一页，物理内存里只有一份。

这就是共享内存最省内存的实现方式。

私有映射的图不一样：

```text
  进程 A 写之前 → 指向 page cache 的同一页
  进程 A 写之后 → 复制一份新页，页表改指新页，page cache 不变
```

这叫写时复制（copy-on-write）。

`fork` 之后父子进程的地址空间，也是这么处理的。

匿名映射是第三种用法：

```c
void *p = mmap(NULL, size, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
```

没有文件后备，等价于"要一块会自动清零的内存"。

大块 `malloc` 在内核里常常就是走这条路。

mmap 的四个好处：

```text
① 省一次拷贝：数据不用从页缓存复制到用户缓冲区
② 懒加载：只映射，不读；真访问才缺页
③ 共享方便：多个进程映射同一个文件，共享同一份 page cache
④ 随机访问：像数组一样跳着读写，不用 seek
```

三个坑：

```text
① 缺页开销：第一次访问每一页都要陷入内核
② 文件被截断：访问超出文件末尾的页会收到 SIGBUS
③ 小文件不合适：映射的系统调用开销比直接 read 还大
```

## 5. 容易混淆的六个点

为什么这几组词特别容易混？

因为它们描述的是同一件事的不同侧面：需求、供给、机制、现象，四个维度混在一起，词就容易串。

下面每条都点明"它站在哪一边"。

```text
① 抖动 ≠ 缺页
   缺页是正常事件；抖动是缺页率持续高到系统干不了活

② 工作集 ≠ 驻留集
   工作集是"需要的页"，驻留集是"已经给的页框里的页"

③ 工作集大小 ≠ Δ
   Δ 是窗口长度，WSS 是窗口里不同页的个数，WSS ≤ Δ

④ 全局置换 ≠ 更好的利用
   它能救活一个进程，也能拖死一群进程

⑤ mmap ≠ 一次性读入
   它只是建立映射，真正读数据发生在缺页时

⑥ 交换（swapping）≠ 换页（paging）
   交换以进程为单位，换页以页为单位
```

再补一个：

```text
页面大小也会影响抖动。
```

页越大，同样数据量占的页框越少，工作集也越小。

但每页浪费的内部碎片也越大：只用到几十字节的小对象，也要占一整页。

极端情况下，一个装满小对象的进程，一半以上的内存是页内空白。

所以 408 只考"页大小对缺页率的一般影响"，不要求算最优点。

## 6. 408 怎么考

为什么这一篇的题以"数"和"判"为主，而不是"算 EAT"？

因为 408 想考的不是"会不会套公式"，而是"能不能把需求和供给摆在一起比"。

工作集、可用页框、进程数，三个数凑一块，答案就出来了。

题型三类：

```text
① 给引用串和 Δ，算某时刻的工作集、平均工作集
② 给内存大小、进程数、工作集大小，判断会不会抖动
③ 给场景，选分配策略（固定/可变，局部/全局）
```

### 例题一：工作集与帧需求（自拟）

引用串：

```text
3, 1, 4, 1, 5, 9, 2, 6, 5, 3, 5, 8, 9, 7, 9, 3
```

Δ = 5。

求 t=16 时的工作集、平均工作集大小；若有 4 个这样的进程并发，至少需要多少页框？

解：

t=16 的窗口是最近 5 次访问：

```text
8, 9, 7, 9, 3
```

集合：

```text
{3, 7, 8, 9} → 大小 4
```

WSS 序列：

```text
1, 2, 3, 3, 4, 4, 5, 5, 4, 5, 4, 4, 4, 5, 4, 4
```

平均值：

```text
61 / 16 = 3.8125
```

4 个进程：

```text
按平均：4 × 3.8125 = 15.25 → 16 个页框
按峰值：4 × 5 = 20 个页框
```

答案：t=16 时工作集 {3,7,8,9}；平均 3.8125；至少 16 个页框，保险起见按峰值 20 个。

验算：

```text
1+2+3+3 = 9
4+4 = 8      → 17
5+5 = 10     → 27
4            → 31
5            → 36
4+4+4 = 12   → 48
5            → 53
4+4 = 8      → 61
61 / 16 = 3.8125 ✓
```

### 例题二：会不会抖动（自拟）

一台机器 4 GB 内存，页大小 4 KB。

内核和页缓存占 10%，其余给进程。

系统里有 2000 个进程，每个进程的工作集是 600 页。

问会不会抖动；最多能同时跑多少个。

解：

页框总数：

```text
4 GB / 4 KB = 2^32 / 2^12 = 2^20 = 1,048,576
```

可用页框：

```text
1,048,576 × 90% = 943,718.4 → 943,718
```

需求：

```text
2000 × 600 = 1,200,000
```

比较：

```text
1,200,000 > 943,718 → 会抖动
缺口 = 1,200,000 − 943,718 = 256,282 个页框
```

最多进程数：

```text
943,718 / 600 ≈ 1572.86 → 1572 个
```

验算：

```text
1572 × 600 = 943,200 ≤ 943,718 ✓
1573 × 600 = 943,800 > 943,718 ✗
```

结论：会抖动；最多约 1572 个进程，超出的要挂起。

**这道题的关键不是除法，是"需求按工作集算，供给按可用页框算"。**

### 例题三：策略选择（自拟，选择题风格）

某系统频繁出现"一个进程缺页导致其他进程接连缺页"，最可能的原因是：

```text
A. 采用了固定分配局部置换
B. 采用了可变分配全局置换
C. 页大小太小
D. 缺页率统计错误
```

答案：B。

理由：

```text
全局置换允许从一个进程的页框里抢页给另一个进程。
一个进程缺页，就可能抢走别人的热点页，引发连锁。
```

如果改成"可变分配局部置换"，连锁就断了：

```text
缺页只在自己帧里换 → 影响范围限于本进程
```

代价是：帧数真的不够时，该进程只能自己抖。

这时候要靠"加帧"或"挂起"来解决。

### 三个高频陷阱

```text
陷阱一：把窗口长度当工作集大小
        Δ=5 时窗口有 5 次访问，但不同页可能只有 3 个

陷阱二：忘记工作集是集合
        同一个页在窗口里出现多次，只算一次

陷阱三：算供给时用物理内存总量
        要减掉内核、页缓存、保留区
```

## 7. 真实系统里长什么样

前面讲的都是模型，这里看真实内核怎么落地。

真实内核里没有"多道程度"这个旋钮，也没有"工作集"这个计数器。

它靠的是一套更简单的信号：内存还剩多少，回收来不来得及。

Linux 判断"内存紧不紧"，靠的是水位线（watermark）。

水位线（watermark）：给空闲内存画几条警戒线，剩多少以下就触发对应的动作。

每个内存区有三个水位：

```text
min    最低水位：低于它，直接回收（进程自己动手）
low    低水位：低于它，唤醒 kswapd
high   高水位：高于它，kswapd 睡觉
```

`kswapd` 是后台回收线程。

它醒来后按 LRU 链表扫描（[15 篇](/posts/os-page-replacement/)讲的活跃/不活跃四条链），把干净的页直接丢掉，脏页写回。

进程自己动手回收叫 direct reclaim。

它的代价是**同步等待**：进程必须停下来，等回收完成才能继续。

所以 direct reclaim 一多，应用就会卡。

可观察的指标：

```bash
grep -E 'pgfault|pgmajfault|pswp|workingset|allocstall' /proc/vmstat
```

```text
pgfault            缺页总数
pgmajfault         主缺页数（要读磁盘）
pswpin/pswpout     换入/换出的页数
workingset_refault 工作集里的页被换出后又重新读回
workingset_activate 被重新读回的页直接升为活跃
allocstall         进程被迫直接回收的次数
```

`workingset_refault` 是最接近"抖动"的指标。

它统计的是：

```text
一页刚被换出去，很快又被访问，只能再读回来。
```

这个数一涨，说明系统的内存已经装不下工作集了。

`vmstat 1` 里的 `si` / `so` 两列就是换入/换出的速率：

```text
si：每秒从 swap 读入多少 KB
so：每秒写入 swap 多少 KB
```

抖动时 `si` 和 `so` 会持续很高，同时 `r`（可运行队列）不长、`b`（阻塞）很多。

这正是"CPU 空闲但系统很慢"的来源。

顺带说一句 `free` 的读法。

```text
不要看 free 那一列。
Linux 会把空闲内存拿去做 page cache，free 很小是正常的。
看 available 那一列：它估算的是"还能再给应用多少"。
```

`available` 接近 0 才是真的紧。

`free` 接近 0 只说明缓存用得多，是好事。

容器场景看 cgroup：

```bash
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.stat
cat /sys/fs/cgroup/memory.events
```

```text
memory.max     这个组最多能用多少内存
memory.current 当前用了多少
memory.events  里 high / max / oom 的计数
```

`memory.events` 里的 `max` 计数一涨，说明这个组撞到了上限。

再涨下去就是 OOM killer。

还有一个旋钮值得提：`vm.swappiness`。

```text
它控制"匿名页和文件页，回收时优先动谁"。
值高 → 更愿意把匿名页换出到 swap
值低 → 更愿意丢文件页（page cache）
```

服务器上把它调低，可以让热点匿名页不被换出去。

但调得太低，内存压力大时会转而频繁丢 page cache，文件读写变慢。

没有万能值，只有权衡。

OOM killer 挑进程的依据是 `oom_score`，大致和进程占用的内存成正比。

```text
/proc/<pid>/oom_score
```

**以上是简化示意，水位线计算、cgroup 文件位置随内核版本和部署方式变化。**

回到 mmap。

Linux 里每个映射对应一个 VMA（`vm_area_struct`），挂在 `mm_struct` 上。

第一次访问映射区时，缺页处理函数按 VMA 的 `vm_ops` 找到文件，从 page cache 取页。

```text
文件的页在 page cache 里 → 直接把页表指向它，零拷贝
不在 → 先从磁盘读到 page cache，再指过去
```

所以：

```text
读写 mmap 的内存，实际上是在读写 page cache。
msync 只是把脏页标记成"该写回了"，不一定立刻落盘。
```

## 8. 一张图 + 一张清单

为什么这一节要把图和清单放在一起？

因为"帧够不够"是一条连续的量变，而"要不要动手处理"是一个二选一的决定。

图管看趋势，清单管当场拍板。

先看"帧数够不够"的图。

```text
缺页率
  │╲
  │ ╲
  │  ╲
  │   ╲
  │    ╲
  │     ╲
  │      ╲
  │       ╲
  │        ╲
  │         ╲________________
  └──────────────────────────▶ 分到的页框数
      抖动区     转折点    平稳区
                （≈ 工作集大小）
```

两种状态的分界，就是工作集大小。

```text
帧数 < WSS：缺页率随帧数变化极陡，差几帧就差几倍
帧数 ≥ WSS：缺页率接近平地，再多的帧收益很小
```

这条曲线解释了一个工程事实：

```text
给进程加帧，在"刚好够"之前收益巨大，之后几乎为零。
```

所以容量规划的正确做法不是"按平均值给"，是"按峰值工作集给"。

再看一张判断清单。

```text
系统很慢，先问三个问题：

① CPU 利用率高不高？
   高 → 不是抖动，看别处（可能是计算密集或锁竞争）
   低 → 继续

② 磁盘 I/O 高不高？swap 有没有在用？
   都不高 → 不是抖动（可能是网络或锁）
   都在涨 → 继续

③ 进程数是不是很多？每个进程的 RSS 是不是很小？
   是 → 大概率是抖动
```

RSS（resident set size，驻留集大小）：这个进程此刻真正占着多少内存（多少页框）。

抖动时每个进程都在抢页框、又都装不全，所以进程数多、单个 RSS 小，这个组合很典型。

三步都指向抖动，处理顺序：

```text
① 降并发：减少同时跑的进程数（编译 -j 调小、限制 worker 数）
② 加内存：扩物理内存或调大容器限制
③ 调参数：给热点进程加帧、降低 swappiness、调大 min_free_kbytes
```

注意第①条。

它和直觉相反：系统慢了，第一反应是"多给点资源"。

抖动的正确解法是"少给点并发"。

最后提醒一个会骗人的指标：`load average`。

它统计的是"可运行 + 不可中断睡眠"的进程数。

抖动的进程大部分时间卡在磁盘 I/O 上，处于 D 状态（不可中断睡眠），照样计入 load。

所以抖动时 load 很高，CPU 却不忙。

```text
load 高 + CPU 忙   → 算力不够
load 高 + CPU 闲   → 内存在拖后腿
```

## 9. 再练两题

再练两题，是因为工作集这一块，眼睛看会了手不一定会。

考场上要的是三分钟内数完 16 个窗口。

### 9.1 工作集序列

引用串：

```text
7, 0, 1, 2, 0, 3, 0, 4
```

Δ = 4。

求每一时刻的 WSS、平均值、最大值。

解：

```text
t=1  7   窗口 {7}                  WSS=1
t=2  0   窗口 {7,0}                WSS=2
t=3  1   窗口 {7,0,1}              WSS=3
t=4  2   窗口 {7,0,1,2}            WSS=4
t=5  0   窗口 {0,1,2,0} → {0,1,2}  WSS=3
t=6  3   窗口 {1,2,0,3} → 4 个不同页 WSS=4
t=7  0   窗口 {2,0,3,0} → {0,2,3}  WSS=3
t=8  4   窗口 {0,3,0,4} → {0,3,4}  WSS=3
```

验算 t=5 的窗口：

```text
最近 4 次 = t=2..5 = 0, 1, 2, 0
不同页 = {0,1,2}，大小 3
```

验算 t=8 的窗口：

```text
最近 4 次 = t=5..8 = 0, 3, 0, 4
不同页 = {0,3,4}，大小 3
```

这两个时刻都有一次重复访问。

窗口里有 4 次访问，但只有 3 个不同页。

WSS 序列：

```text
1, 2, 3, 4, 3, 4, 3, 3
```

平均：

```text
(1+2+3+4+3+4+3+3) / 8 = 23 / 8 = 2.875
```

最大值 4，最小值 1。

**这道题的坑在这里：数的是"窗口里不同页的个数"，不是"窗口里有几次访问"。**

如果把窗口长度 4 当成 WSS，t=5、t=7、t=8 都会算错。

### 9.2 最多几个进程

一台机器 8 GB 内存，页大小 4 KB。

可用比例 80%，每个进程的工作集 1000 页。

问最多同时跑几个进程。

解：

```text
页框总数 = 8 GB / 4 KB = 2^33 / 2^12 = 2^21 = 2,097,152
可用页框 = 2,097,152 × 80% = 1,677,721.6 → 1,677,721
最多进程 = 1,677,721 / 1000 = 1677.721 → 1677
```

验算：

```text
1677 × 1000 = 1,677,000 ≤ 1,677,721 ✓
1678 × 1000 = 1,678,000 > 1,677,721 ✗
```

结论：1677 个。

超过这个数，就至少有一个进程的工作集装不全，缺页率开始爬。

### 自检三问

1. 如果把内存加了一倍，但进程数不变，抖动一定消失吗？

   答不上来说明只记住了"加内存"，没记住"按需求算"：抖动看的是需求之和与供给的比较。若每个进程的工作集也随数据量涨上去，加内存可能只是把抖动推后一点。

2. 为什么"CPU 空闲"在抖动时反而是个坏消息，而在正常情况下是"该加进程"的信号？

   答不上来说明没学透正反馈：正常时 CPU 空是活不够，加进程能提吞吐；抖动时 CPU 空是在等磁盘，加进程只会让每个进程的页框更少，缺页更凶。

3. 引用串 `3,1,4,1,5,9,2,6,5,3,5,8,9,7,9,3`，Δ = 5，t=16 的工作集是几页？4 个这样的进程平均需要多少页框？

   答不上来说明"不同页"这一步没走熟：t=16 窗口是 `8,9,7,9,3`，集合 `{3,7,8,9}` 共 4 页；平均 WSS 3.8125，4 个进程约 16 个页框，按峰值要 20 个。

## 10. 小结

这一篇的三条主线：

```text
抖动 = 需求（工作集之和）超过供给（可用页框）
工作集 = 最近 Δ 次访问里的不同页
mmap = 把文件页直接挂进页表，省一次拷贝
```

再压成一句：

```text
虚拟内存的所有性能问题，最后都归结为"工作集装不装得下"。
```

装得下，缺页率低，EAT 接近内存访问。

装不下，缺页率高，EAT 接近磁盘时间。

抖动是后者的极端形态：装不下的部分太多，系统把时间全花在换页上。

而它最阴险的地方，是那个正反馈：

```text
CPU 越闲 → 系统越要加进程 → 每进程帧越少 → CPU 越闲
```

唯一的解法是反过来：

```text
降低并发，让每个进程的工作集重新装得下。
```

这也是为什么容量规划要按"峰值工作集"算，不能按平均值。
