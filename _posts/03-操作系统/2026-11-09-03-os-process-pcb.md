先看两个进程。

```text
进程 A 的页表：虚拟地址 0x400000 → 物理页 0x1A2
进程 B 的页表：虚拟地址 0x400000 → 物理页 0x7C5
```

同一个地址，两块内存。

CPU 每执行一条指令，都在用其中一张表。

它怎么知道现在该用哪张？

答案在一个寄存器里：

```text
cr3
```

`cr3` 指向当前进程的页表基址。

换进程，就换 `cr3`。

**所以"进程"这个东西，在硬件眼里就是"一个 cr3 值 + 一组寄存器"。**

这句话是这一篇的底。

## 1. 这个问题解决什么

01 篇说 CPU 要虚拟化。

虚拟化 CPU 的意思是：

```text
一个物理 CPU，让每个程序都以为自己独占一个。
```

要做到这一点，需要回答四个问题。

```text
① 程序跑到一半被换下去，怎么记得自己跑到哪了？
② 换回来的时候，怎么接着往下跑？
③ 系统里同时有几十个程序，怎么记住它们各自的状态？
④ 怎么保证它们不互相踩内存？
```

四个问题，一个答案：

```text
给每个"正在运行的程序"配一个数据结构，
把所有"它需要记住的东西"都塞进去。
```

这个数据结构叫进程控制块（PCB，process control block）。

这个"正在运行的程序"，叫进程（process）。

**进程不是程序。**

程序是磁盘上的一个文件，静态的、只读的、可以复制一万份。

进程是它在内存里的一次执行，动态的、有状态的、用完就没了。

```text
程序：a.out，躺在磁盘上，一年不动也不会变
进程：./a.out 跑起来之后的那一坨，几毫秒就变一次状态
```

## 2. 最小模型：进程 = 程序 + 数据 + PCB

一个进程在内存里长这样：

```text
┌─────────────────────────────┐
│  内核空间                    │
│  ┌───────────────────────┐  │
│  │ PCB（task_struct）     │  │  ← 进程存在的唯一标志
│  │   pid = 1234          │  │
│  │   state = RUNNING     │  │
│  │   cr3 = 0x1A2000      │  │
│  │   rip = 0x401136      │  │
│  └───────────────────────┘  │
├─────────────────────────────┤
│  用户空间                    │
│  ┌───────────────────────┐  │
│  │ 栈（stack）↓           │  │  局部变量、返回地址
│  ├───────────────────────┤  │
│  │ 空闲                   │  │
│  ├───────────────────────┤  │
│  │ 堆（heap）↑            │  │  malloc 出来的
│  ├───────────────────────┤  │
│  │ .bss / .data          │  │  全局变量、静态变量
│  ├───────────────────────┤  │
│  │ .text                 │  │  代码
│  └───────────────────────┘  │
└─────────────────────────────┘
```

左边是"这个进程有什么"。

右边（PCB）是"内核怎么记住它"。

### 2.1 进程的四个特征

```text
① 动态性：它是程序的一次执行，有生命周期
② 并发性：多个进程可以同时存在于内存中，交替推进
③ 独立性：它是资源分配的基本单位，有独立的地址空间
④ 异步性：各自按不可预知的速度推进
```

四条里，动态性是根本。

```text
程序没有"状态"，进程有。
程序的代码不会变，进程的 PCB 每秒变几千次。
```

### 2.2 PCB 是唯一标志

这句话要背下来：

```text
PCB 是进程存在的唯一标志。
```

为什么是"唯一"？

因为：

```text
进程的代码可以和其他进程共享（共享库、fork 后的只读段）
进程的数据可以为空（一个空进程）
进程的栈可以很小
只有 PCB，一个进程一份，绝不共享
```

内核管理进程，实际就是管理一堆 PCB。

```text
就绪队列   = 一堆 PCB 排成队
阻塞队列   = 一堆 PCB 挂在某个事件上
进程表     = 所有 PCB 的集合
```

**调度器选的不是进程，是 PCB。**

## 3. 一次完整走查：fork 到 wait

看一段最普通的代码。

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();

    if (pid == 0) {
        printf("child\n");
        return 0;
    }

    wait(NULL);
    printf("parent\n");
    return 0;
}
```

从 `fork()` 开始，走一遍 PCB 的变化。

```text
① 父进程调用 fork → 陷入内核 → sys_fork
② 内核分配一个新的 PCB（新 pid、新地址空间描述符）
③ 复制父进程的页表，但把页标记为只读、写时复制
④ 复制父进程的寄存器现场到子进程 PCB
⑤ 子进程状态设为"就绪"，挂进就绪队列
⑥ fork 返回：父进程拿到子 pid，子进程拿到 0
⑦ 调度器选中子进程 → 切换 cr3 → 子进程开始跑
⑧ 子进程 printf → write → 输出 "child"
⑨ 子进程 return → exit → 内核回收内存、文件
   但 PCB 不回收，状态改为"僵尸"，等父进程来收
⑩ 父进程 wait 返回 → 内核释放子进程 PCB
```

十步里，最值得注意的是第③步和第⑨步。

**第③步：fork 不复制内存。**

它只复制页表，把两边的页都标成只读。

谁写，谁触发缺页，内核才真的复制那一页。

```text
这叫写时复制（copy-on-write，COW）。
好处：fork 几乎瞬间完成，哪怕进程有 1 GB 内存。
代价：两边都写的时候，还是要复制。
```

**第⑨步：进程结束了，PCB 还在。**

因为父进程可能还要读子进程的退出码。

```text
进程已终止，但 PCB 未释放 → 僵尸进程（zombie）
```

这两步都指向同一个事实：

```text
PCB 的生命周期，不等于程序的生命周期。
```

## 4. 状态机：三态、五态、七态

### 4.1 三态

最基本的三态：

```text
        调度
就绪 ───────────▶ 运行
  ▲                 │
  │  时间片到        │ 等待事件
  └─────────────────┤
                    ▼
                  阻塞
                    │
                    │ 事件发生
                    └──────▶ 就绪
```

三个状态的定义：

```text
就绪（ready）：万事俱备，只差 CPU
运行（running）：正占着 CPU 在跑
阻塞（blocked）：在等某个事件（I/O 完成、信号量、sleep）
```

注意"就绪"和"阻塞"的区别：

```text
就绪：等的是 CPU
阻塞：等的是事件
```

CPU 只有一个，所以同一时刻：

```text
单处理机：最多一个进程处于运行态
多处理机：最多 N 个（N = CPU 数）
就绪和阻塞的个数都没有上限
```

### 4.2 五态

加上创建和终止：

```text
                创建
                 │ 许可
                 ▼
    ┌───────── 就绪 ◀────────┐
    │            │ 调度        │ 时间片到
    │            ▼            │
    │          运行 ──────────┘
    │            │
    │            │ 等待事件       事件发生
    │            ▼                  │
    │          阻塞 ────────────────┘
    │            │
    └────────────┤
                 │ 退出
                 ▼
                终止
```

两个新状态的意义：

```text
创建：PCB 已分配，但还没完全建好（比如还没装入内存）
      为什么要单独一个状态？
      因为创建工作要读磁盘、要分配资源，不能一口气做完。
      做完之前，它不能进就绪队列。

终止：进程已经结束，但 PCB 还没被回收
      为什么要单独一个状态？
      因为父进程可能还要读退出码。
```

**五态的两个新状态，都是为了"资源还没交割清楚"这种情况留的缓冲。**

### 4.3 七态

再加挂起。

```text
挂起 = 把进程从内存挪到磁盘（换出，swap out）
```

为什么要挂起？

```text
① 内存不够，先把暂时不用的进程换出去
② 用户主动暂停（Ctrl+Z、调试器）
③ 操作系统定期换出（负载均衡）
```

挂起之后，状态要分裂成两组：

```text
活动就绪（就绪）    ↔  静止就绪（就绪挂起）
活动阻塞（阻塞）    ↔  静止阻塞（阻塞挂起）
```

完整的七态：

```text
七个状态：
  创建、活动就绪、运行、活动阻塞、终止
  + 静止就绪（就绪挂起）
  + 静止阻塞（阻塞挂起）
```

不要画成一张乱麻。

把它拆成"两对 + 六条边"就清楚了。

```text
两对配对：

  活动就绪 ⇄ 静止就绪    挂起 / 激活
  活动阻塞 ⇄ 静止阻塞    挂起 / 激活

六条新边：

  运行     → 静止就绪    时间片到，同时被换出
  活动就绪 → 静止就绪    内存紧张，直接被换出
  活动阻塞 → 静止阻塞    换出，但还在等事件
  静止就绪 → 活动就绪    激活，换入内存
  静止阻塞 → 活动阻塞    激活，换入，仍然在等事件
  静止阻塞 → 静止就绪    事件发生了，但进程还在磁盘上
```

原来的三态边全部保留，只是两端可能换成"活动"版本。

**关键：静止阻塞的进程，事件发生了也只到"静止就绪"，不会直接去运行。**

因为它还在磁盘上。

从"静止就绪"到"运行"，中间必须经过"活动就绪"这一格。

这就是 4.4 节里"就绪挂起 → 运行不可能"的理由。

### 4.4 哪些转换不可能

这是 408 最爱考的一格。

逐个说"为什么不可能"。

**① 阻塞 → 运行（不可能）**

```text
阻塞的进程没有 CPU。
没有 CPU 就没法"被调度"。
必须先有人把它变成就绪，调度器才可能选它。
```

这个错误选项几乎年年出现。

**② 就绪 → 阻塞（不可能）**

```text
阻塞是"等事件"。
只有正在运行的进程，才会执行到"我要等 I/O"这条指令。
就绪的进程一条指令都没执行，怎么可能去等事件。
```

**③ 就绪 → 静止阻塞（不可能）**

同理，没运行就不会等事件。

**④ 就绪挂起 → 运行（不可能）**

进程还在磁盘上，先要换入内存变成就绪。

**⑤ 创建 → 运行（不可能）**

必须先变成就绪，再被调度。

严格的教材会写"创建 → 就绪"，有些简化版允许"创建 → 就绪挂起"。

**⑥ 阻塞 → 终止（可以，但少见）**

被 kill 掉是可以的。

除了"创建"之外，任何状态都能进"终止"，因为它是"被外力结束"。

```text
创建 → 终止：不叫终止，叫"创建失败"，直接回收 PCB
```

**⑦ 运行 → 就绪（可以）**

时间片到，或者被更高优先级抢占。

**⑧ 运行 → 阻塞（可以）**

执行了等待操作。

这一格最容易理解，也最容易被忽略。

**⑨ 阻塞 → 就绪（可以）**

事件发生了。

注意方向：是"就绪"，不是"运行"。

### 4.5 一张转换合法性表

```text
        目标 →   就绪  运行  阻塞  就绪挂 阻塞挂  终止
来源 ↓
就绪              -    ✓    ✗     ✓      ✗     ✓
运行              ✓    -    ✓     ✓      ✗     ✓
阻塞              ✓    ✗    -     ✗      ✓     ✓
就绪挂起          ✓    ✗    ✗     -      ✗     ✓
阻塞挂起          ✗    ✗    ✓     ✓      -     ✓
创建              ✓    ✗    ✗     ✓      ✗     ✗
```

看第三列"运行"：

```text
只有"就绪"能进"运行"。
```

这一条能挡住 80% 的错项。

## 5. 容易混淆的点

### 5.1 进程 vs 程序

```text
程序：静态的指令集合，存在磁盘上
进程：动态的执行过程，存在内存里，有 PCB
```

一句话判据：

```text
能不能被"杀死"？
能 → 进程
不能 → 程序（文件只能被删除）
```

一个程序可以对应多个进程（同时开三个终端跑 `ls`）。

一个进程也可以对应多个程序（`exec` 之后代码全换了，PCB 还是那个）。

**`exec` 只换代码和数据，不换 PCB、不换 pid。**

### 5.6 现场分成两份：用户态一份，内核态一份

看 xv6 会有点晕：

```text
trapframe：用户态现场
context：  内核态现场
```

为什么不是一个？

因为切换发生在内核里。

```text
进程 A 调 read → 陷入内核 → 用户态现场存进 trapframe
read 要等磁盘 → A 阻塞 → 内核要切到 B
切之前，只需要存"内核里的现场"（context）
A 的寄存器早就躺在 trapframe 里了，不用再存一遍
```

**省下来的就是这十几个寄存器的读写。**

这也是为什么"系统调用返回"和"进程切换回来"是两条不同的路径。

前者要恢复 trapframe，后者只恢复 context。

### 5.2 阻塞 vs 挂起

```text
阻塞：等事件，进程还在内存里
挂起：被换出到磁盘，进程不在内存里
```

一个进程可以同时"阻塞"且"挂起"（静止阻塞）。

也可以"就绪"且"挂起"（静止就绪）。

两个维度是正交的：

```text
维度一：在不在内存（活动 / 静止）
维度二：能不能跑（就绪 / 阻塞）
```

### 5.3 调度 vs 切换

```text
调度（scheduling）：决定下一个跑谁 —— 一个决策
切换（switching）： 把 CPU 真的交出去 —— 一个动作
```

顺序是：

```text
先调度（选出来），再切换（交出去）。
```

但两者不一定同时发生：

```text
进程自己 exit，调度器选了同一个进程的兄弟线程 → 不用换地址空间
调度器选了"还是当前进程" → 根本不用切换
```

408 有时问"进程切换一定伴随调度吗"。

答案：切换之前一定有一次选择，但"选择"不一定是完整的调度算法（可能是被动让出）。

更准确的说法：

```text
切换必然由调度触发，调度不一定导致切换。
```

### 5.4 PCB 在内存还是在磁盘

```text
活动进程的 PCB：在内存的内核区
挂起进程：      数据在磁盘，PCB 可能也在磁盘（看实现）
```

但不管在哪，**PCB 必须存在**，否则进程就不存在了。

这就是"唯一标志"的含义。

### 5.5 僵尸进程不是"死进程"

```text
僵尸：进程已经终止，PCB 还在，等父进程 wait
```

它不占 CPU，不占内存（除了一个 PCB），但占一个 pid。

父进程一直不 wait，僵尸会累积，最后 pid 耗尽。

```text
孤儿：父进程先死了，子进程被 init/systemd 收养
```

两个名字方向相反，别记反。

## 6. 408 怎么考

这一篇对应进程管理的第一块：概念、状态、控制、切换。

题型：

```text
① 状态转换判断（给一组转换，问哪个不可能）—— 年年有
② 给一段程序 / 一个事件序列，问状态怎么变
③ PCB 里有什么、PCB 的作用
④ 进程切换的过程与开销
⑤ 进程与程序的区别（概念题）
⑥ 原语的特点（不可中断）
```

三条套路。

**套路一：所有"进运行"只能从"就绪"来。**

这条能秒杀一半的错项。

**套路二：所有"进阻塞"只能从"运行"来。**

没跑起来就不会等事件。

**套路三：数字题只考两样。**

```text
切换次数 = 调度次数
切换开销占比 = 切换时间 / (时间片 + 切换时间)
```

### 6.1 例题一：判断转换

自拟，按真题风格。

```text
某系统采用抢占式调度，进程有七种状态。

下列转换中，不可能发生的是：

A. 运行 → 就绪
B. 阻塞 → 就绪
C. 阻塞 → 运行
D. 静止阻塞 → 静止就绪
E. 就绪 → 静止就绪
F. 运行 → 静止就绪
```

逐条。

A 可以，时间片到或被抢占。

B 可以，等待的事件发生了。

C 不可能。阻塞的进程没有 CPU，必须先进就绪队列。

D 可以。挂起的进程等到事件，状态从"静止阻塞"变成"静止就绪"，但仍在磁盘上。

E 可以。内存紧张，把就绪进程换出。

F 可以。运行中的进程被换出，同时失去 CPU。

答案 C。

### 6.2 例题二：算切换开销

自拟。

```text
某系统：
  时间片 10 ms
  一次进程切换的直接开销（保存/恢复寄存器、更新 PCB）1.2 μs
  切换后页表变了，TLB 被清空
  接下来 500 次访存，每次因 TLB 缺失多花 100 ns

求：
(1) 一次切换的总开销
(2) 切换开销占 CPU 时间的比例
(3) 若时间片改为 1 ms，比例变成多少
```

(1)

```text
直接开销   = 1.2 μs
间接开销   = 500 × 100 ns = 50000 ns = 50 μs
总开销     = 1.2 + 50 = 51.2 μs
```

(2)

```text
一个时间片周期 = 10 ms + 51.2 μs = 10051.2 μs
占比 = 51.2 / 10051.2 ≈ 0.00509 ≈ 0.51%
```

(3)

```text
周期 = 1 ms + 51.2 μs = 1051.2 μs
占比 = 51.2 / 1051.2 ≈ 0.0487 ≈ 4.87%
```

三个数字：51.2 μs、0.51%、4.87%。

两个结论。

```text
① 直接开销只占 1.2/51.2 ≈ 2.3%
   间接开销占 97.7%
② 时间片缩小 10 倍，开销占比涨了约 9.6 倍
```

**第一个结论就是这一篇的反直觉点，第 10 节展开。**

第二个结论解释了 01 篇说的"分时系统不敢把时间片设太小"。

### 6.3 例题三：数状态转换

自拟。

```text
一个进程从创建到终止的时间线如下：

  创建用了 2 ms
  就绪等了 3 ms 后被调度
  运行 3 ms 后请求磁盘读，阻塞
  20 ms 后磁盘中断，事件完成
  就绪等了 4 ms 后被调度
  运行 5 ms，时间片用完
  就绪等了 2 ms 后被调度
  运行 4 ms 后正常退出

求：
(1) 进程处于就绪态的总时间
(2) 进程处于阻塞态的总时间
(3) 一共发生了几次状态转换
```

先排时间轴。

```text
t=0     创建开始
t=2     创建完成 → 就绪
t=5     就绪 → 运行
t=8     运行 → 阻塞（等磁盘）
t=28    阻塞 → 就绪（磁盘中断）
t=32    就绪 → 运行
t=37    运行 → 就绪（时间片到）
t=39    就绪 → 运行
t=43    运行 → 终止
```

(1) 就绪时间

```text
2→5    3 ms
28→32  4 ms
37→39  2 ms
合计   9 ms
```

(2) 阻塞时间

```text
8→28 = 20 ms
```

(3) 转换次数

```text
创建→就绪 ①
就绪→运行 ②
运行→阻塞 ③
阻塞→就绪 ④
就绪→运行 ⑤
运行→就绪 ⑥
就绪→运行 ⑦
运行→终止 ⑧
共 8 次
```

核对总时间：

```text
创建 2 + 就绪 9 + 运行 12 + 阻塞 20 = 43 ms ✓
```

这类题不难，但要求你"按事件顺序排时间轴"。

一乱就错。

**排时间轴的顺序永远是：创建 → 就绪 → 运行 → 阻塞 → 就绪 → ……**

## 7. 真实系统里长什么样

### 7.1 Linux 的 PCB 叫 task_struct

```c
/* 简化示意，只保留几类字段 */
struct task_struct {
    pid_t pid;                  /* 进程标识 */
    volatile long state;        /* 状态：TASK_RUNNING 等 */
    struct mm_struct *mm;       /* 地址空间 */
    struct thread_struct thread;/* 切换时保存的寄存器 */
    struct files_struct *files; /* 打开的文件表 */
    struct fs_struct *fs;       /* 当前工作目录、根目录 */
    struct signal_struct *signal;/* 信号处理 */
    struct list_head tasks;     /* 挂进进程链表 */
    /* ... 几百个字段 ... */
};
```

真实的结构有几百个字段，几千字节。

```text
进程数上限的本质，就是 PCB 能占多少内存。
```

### 7.2 切换的关键几行

```c
/* 简化示意 */
if (prev->mm != next->mm) {
    switch_mm(prev->mm, next->mm);   /* 换 cr3 */
}
switch_to(prev, next);               /* 换寄存器、换栈 */
```

第一行是分水岭。

```text
同一个进程的两个线程：mm 相同 → 不换 cr3
不同进程：          mm 不同 → 换 cr3
```

**"换不换地址空间"，就是线程切换和进程切换的分界线。**

### 7.3 现代 CPU 的补丁：PCID

换 `cr3` 要清 TLB。

清完，接下来几千次访存全部缺页式地查页表。

后来 Intel 加了 PCID（process context identifier）：

```text
cr3 里带一个 12 位的 PCID
换进程时不清 TLB，只换 PCID
每个 TLB 项标记它属于哪个 PCID
```

效果：

```text
不同进程的 TLB 项共存，切换不用清空。
```

代价：

```text
TLB 项变少了（要分给多个 PCID）。
```

ARM 上对应的机制叫 ASID。

### 7.4 xv6 的极简版

xv6 的 PCB 叫 `struct proc`：

```c
/* 简化示意 */
struct proc {
    enum { UNUSED, EMBRYO, SLEEPING, RUNNABLE, RUNNING, ZOMBIE } state;
    char name[16];
    void *chan;          /* 在等什么事件 */
    int pid;
    uint64 sz;           /* 内存大小 */
    pagetable_t pagetable;
    struct trapframe *tf;/* 中断现场的保存处 */
    struct context context; /* 切换时保存的寄存器 */
};
```

注意它把"现场"分成了两份：

```text
trapframe：中断/系统调用时保存的用户态现场
context：  进程切换时保存的内核态现场
```

为什么分两份？

```text
系统调用进内核 → 保存用户态现场到 trapframe
内核里切换进程 → 只需要保存内核栈和内核寄存器（context）
```

**用户态的寄存器不用管，因为它已经躺在 trapframe 里了。**

这个设计能省一半的切换开销。

### 7.5 ps 的输出就是 PCB 的投影

```text
$ ps -eo pid,ppid,stat,etime,time,comm
  PID   PPID STAT     ELAPSED     TIME COMMAND
 1234   1000 Ss        01:23:45 00:00:02 bash
 5678   1234 R+           00:03 00:00:00 a.out
 9012      1 Z          10:00:00 00:00:00 defunct
```

每一列都对应 PCB 的一类字段：

```text
PID / PPID   → ① 进程标识
STAT         → ③ 进程调度信息（S 睡眠、R 运行、Z 僵尸）
ELAPSED      → ⑥ 记账信息（墙上时间）
TIME         → ⑥ 记账信息（CPU 时间）
COMMAND      → ① 进程标识（名字）
```

看不见的是②④⑤：

```text
寄存器现场、页表、打开的文件表 —— 内核不导出这些。
```

所以 `ps` 能告诉你"进程在哪"，但不能告诉你"它停在哪条指令"。

后者要用 `gdb` 或 `/proc/<pid>/stat`。

## 8. PCB 里到底放什么

教材列六类。

```text
① 进程标识
   pid、父进程 pid、用户 id
   作用：唯一识别这个进程

② 处理机状态（现场信息）
   通用寄存器、PC、PSW、栈指针
   作用：换回来时能接着跑

③ 进程调度信息
   状态、优先级、等待的事件、调度队列指针
   作用：调度器要靠它做决策

④ 内存管理信息
   页表基址（cr3）、段表、内存区列表
   作用：切换时换地址空间

⑤ I/O 状态信息
   打开的文件表、设备表、I/O 缓冲区
   作用：记住它正在用哪些外设

⑥ 记账信息
   CPU 使用时间、实际用时、账号
   作用：计费、统计、调度（多级反馈队列要用）
```

六类的记法：

```text
我是谁（标识）
我停在哪（现场）
我该不该跑（调度）
我的内存在哪（内存）
我开着什么（I/O）
我用了多少（记账）
```

一句判断：

```text
凡是"换回来之后必须知道"的信息，都在 PCB 里。
```

### 8.1 PCB 怎么组织起来

单个 PCB 没用。

内核要看的是"一堆 PCB 的整体状态"。

两种组织方式。

**链接方式**

```text
就绪队列：   PCB1 → PCB2 → PCB3 → NULL
阻塞队列：   一个事件一条队列
             PCB4 → PCB7 → NULL   （等磁盘）
             PCB5 → NULL          （等键盘）
```

PCB 里有一个"队列指针"字段。

优点：

```text
插入删除 O(1)
队列数量可以动态增加
```

缺点：

```text
按 pid 查找要遍历，O(n)
```

**索引方式**

```text
就绪索引表： [ PCB1, PCB2, PCB3 ]
阻塞索引表： [ PCB4, PCB5 ]
每个 PCB 里存"我在索引表的第几项"
```

优点：

```text
按类别定位快
```

缺点：

```text
索引表大小固定，进程数受限于表长
```

**真实系统两种都用。**

Linux 的 `task_struct` 同时挂在多个链表上：

```text
tasks 链表：所有进程
children 链表：所有子进程
运行队列：每个 CPU 一条
等待队列：每个等待事件一条
```

一个 PCB，多个链，靠多个 `list_head` 字段实现。

所以 PCB 里"链接字段"不是一个，是一组。

## 9. 五个控制原语

进程控制有五个动作。

```text
① 创建（create）
   分配 PCB → 分配内存 → 初始化现场 → 状态设为就绪 → 入就绪队列

② 终止（terminate）
   回收内存 → 回收文件 → 状态设为终止 → 通知父进程

③ 阻塞（block）
   状态改为阻塞 → 挂到等待队列 → 让出 CPU → 触发调度

④ 唤醒（wakeup）
   从等待队列摘下 → 状态改为就绪 → 入就绪队列

⑤ 切换（switch）
   保存旧现场 → 更新旧 PCB → 选新进程 → 恢复新现场
```

### 9.1 原语为什么不可中断

```text
原语（primitive）：一组不可分割的操作。
```

"不可分割"的意思是：

```text
中间不能被别的执行流插进来。
```

为什么？

看"阻塞"原语。

```text
① 把状态从"运行"改成"阻塞"
② 挂到等待队列
③ 让出 CPU
```

如果第①步做完被中断了，另一段代码看到的是：

```text
一个状态为"阻塞"、却还占着 CPU、也没在等待队列里的进程。
```

它永远不会被唤醒。

状态机坏了。

**所以原语必须"要么都做，要么都不做"。**

实现方式：

```text
关中断
  ① 改状态
  ② 挂队列
  ③ 调度
开中断
```

关中断期间，时钟中断进不来，没人能打断。

注意边界：

```text
关中断只挡得住单处理机上的并发。
多处理机要加锁（自旋锁）。
```

这一点 07 篇会展开。

### 9.2 创建与终止的实际过程

```c
/* 简化示意：xv6 的 fork 骨架 */
int fork(void) {
    struct proc *p = allocproc();        /* 分配 PCB */
    if (p == 0) return -1;

    if (copyuvm(p->pagetable, ...) < 0) { /* 复制页表 */
        freeproc(p);
        return -1;
    }

    p->state = RUNNABLE;                 /* 就绪 */
    return p->pid;
}
```

三步：

```text
分配 PCB → 复制地址空间 → 设为就绪
```

任何一步失败，都要把前面的步骤回滚。

这就是为什么它必须是一段临界区。

### 9.3 阻塞一定引起切换，唤醒不一定

```text
阻塞：当前进程主动让出 CPU → 一定触发调度 → 一定切换
唤醒：把别人变成就绪     → 当前进程还在跑 → 不一定切换
```

这个不对称很关键。

唤醒是"给别人一个机会"，不是"把 CPU 交出去"。

只有两种情况会让被唤醒的进程马上跑：

```text
① 它的优先级比当前进程高，且系统是抢占式的
② 当前进程正好用完时间片
```

所以 408 里"唤醒是否引起进程切换"的正确答案是：

```text
不一定，取决于优先级和调度方式。
```

## 10. 切换的代价：真正贵的是地址空间

先给结论。

> **反直觉的点：一次进程切换，90% 以上的开销不是"保存寄存器"。**
> **寄存器只有十几个，存一下几百纳秒。**
> **真正贵的是换掉整个地址空间：换页表、刷 TLB、污染缓存。**

算一下就清楚。

```text
保存/恢复 16 个通用寄存器：约 100 ns 量级
换 cr3 + 刷新 TLB：        几微秒量级（因为后续访存全要重查页表）
缓存污染：                 几十微秒量级（后面慢慢体现）
```

### 10.1 切换做了什么

```text
① 保存当前进程的内核现场（寄存器、栈指针）
② 更新它的 PCB（状态、时间片剩余）
③ 把它的 PCB 挂到合适的队列
④ 调度器选下一个
⑤ 更新新进程的 PCB
⑥ 切换地址空间（换 cr3、换页表）
⑦ 切换内核栈
⑧ 恢复新进程的内核现场
⑨ 返回到新进程的用户态（iret）
```

第⑥步是分界线。

前面几步加起来是"百纳秒级"。

第⑥步之后，CPU 的 TLB、cache、分支预测器全部要重新热身。

### 10.2 直接开销与间接开销

```text
直接开销（direct cost）：
  保存/恢复寄存器、读写 PCB、换 cr3
  可以在指令级别算出来

间接开销（indirect cost）：
  TLB 失效导致的额外页表遍历
  cache 失效导致的额外内存访问
  分支预测器失效
```

间接开销没法精确算，但可以估。

一个粗略的数字感：

```text
时间片 10 ms 时，切换开销 0.5% 左右 → 感觉不到
时间片 1 ms 时，切换开销 5% 左右   → 开始影响吞吐
时间片 100 μs 时，切换开销 30% 以上 → 系统基本在空转
```

**所以调度器的第一原则是：能不切就不切。**

### 10.3 减小开销的三种办法

```text
① 让切换少一点
   时间片给大一点；能批处理就批处理

② 让切换便宜一点
   用 PCID/ASID，不刷 TLB

③ 换一种更轻的执行流
   用线程代替进程，共享地址空间，不用换 cr3
```

第③条就是 04 篇的主题。

**线程存在的第一理由，不是"并发更方便"，是"切换更便宜"。**

### 10.4 所以调度器会尽量不换 CPU

既然缓存和 TLB 这么贵，调度器就多了一条原则：

```text
缓存亲和性（cache affinity）：
  尽量把进程放回它上次运行的那个 CPU 上。
```

因为那个 CPU 的 cache 里，可能还留着它的一堆热数据。

```text
换到另一个 CPU → cache 全冷 → 前面几十微秒白干
```

Linux 的负载均衡会权衡两件事：

```text
负载不均 → 迁移进程（牺牲缓存）
缓存太冷 → 不迁移（牺牲均衡）
```

这也是"多核调度"比单核调度难的地方。

**单核只要管顺序，多核还要管位置。**

## 11. 僵尸与孤儿：PCB 为什么不马上释放

### 11.1 僵尸

```text
子进程 exit → 内核回收内存、关闭文件
            → PCB 保留，state = ZOMBIE
            → 等父进程 wait 来读退出码
```

如果父进程不 wait：

```text
$ ps -eo pid,ppid,stat,comm | grep Z
1234  1000  Z  a.out
```

`stat` 是 `Z`。

它不占 CPU、不占内存，只占一个 pid。

pid 用完了，新进程就创建不了。

```text
$ ulimit -u
```

这个数就是上限。

### 11.2 孤儿

```text
父进程先退出 → 子进程变成孤儿
            → 被 init（PID 1）或 systemd 收养
            → 由它负责 wait
```

孤儿不是问题，系统会自动收拾。

```text
真正的问题是僵尸：父进程活着，但不 wait。
```

### 11.3 为什么不能"一退出就释放 PCB"

三个原因：

```text
① 父进程要读退出码（exit status）
② 父进程要读资源使用统计（记账信息）
③ 内核要知道"这个 pid 还没被回收"，不能马上复用
```

所以"终止"必须是一个独立的状态。

**这就是五态图里那个终止态的物理理由。**

一句话：

```text
进程的死亡是一个过程，不是一个瞬间。
```


```text
进程是"执行流 + 地址空间 + 一个 PCB"，

```
