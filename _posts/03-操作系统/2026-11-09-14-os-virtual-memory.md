> **读这篇之前，你只需要知道**：内存是"一排带编号的格子"，正在运行的程序就住在里面，CPU 读一格只要几十纳秒；硬盘是"断电还在的仓库"，容量大得多但慢得多，从硬盘搬一页数据进来要几毫秒。
> **这篇讲什么**：内存装不下所有页，那就先只装马上要用的，其余留在硬盘上，碰到不在内存的页再去取——这套"用到才给"的办法就是虚拟内存。
> **一个类比**：书太多，书架放不下，只好把常用的几本放桌上，其余堆进仓库；要看仓库里那本，得跑一趟去取，取回来还得从桌上挪一本走。


先看两个现象。

第一个：

```c
char *p = malloc(1024 * 1024 * 1024);  // 1 GB
```

这一行几乎瞬间返回。

内存没少，程序没崩，1 GB 好像凭空就有了。

第二个：

```c
memset(p, 0, 1024 * 1024 * 1024);      // 真的碰一遍
```

这一行跑得很慢，而且跑完之后，系统的空闲内存才真的少了一大块。

同一块 1 GB，为什么"拿到"不花时间，"碰到"才花时间？

因为 `malloc` 只是答应给你。

真正给，是在你第一次读写那一页的时候。

这就是请求分页（demand paging）。

请求分页：进程启动时只装入少数几页，之后访问到哪一页才把哪一页调进来，没碰过的一页都不装。

它让"分配"和"占用"分开，也让"虚拟"这两个字有了实际含义。

## 1. 为什么需要"用到才给"

先算一笔最简单的账。

一台机器 4 GB 内存。

同时开 10 个进程，每个进程的虚拟地址空间都是 4 GB。

```text
10 × 4 GB = 40 GB
```

40 GB 装进 4 GB。

按"全部装入"的思路，这台机器一台进程都开不起来。

但现实中它开得挺好。

因为那 40 GB 里，绝大部分从来没被碰过。

一个典型的进程，虚拟空间里有什么？

```text
可执行文件映射的代码段、只读数据段
已初始化的数据段、未初始化的 BSS
堆（可能只用了开头几 MB）
栈（可能只用了开头几十 KB）
动态库（libc、libstdc++……）
文件映射区（mmap 打开的文件）
```

真正在跑的时候，用到的只是其中很小一部分。

在 `/proc/self/maps` 里能看到这张清单（简化示意）：

```text
00400000-00452000 r-xp  /usr/bin/app      ← 代码，只读可执行
00651000-00653000 rw-p  [heap]            ← 堆
7f2c00000000-7f2c021000 r-xp  libc.so    ← 动态库
7ffd5a3f2000-7ffd5a413000 rw-p  [stack]   ← 栈
```

每一行是一个 VMA，有自己的权限。

一个进程的虚拟空间可能是几 GB，这四类加起来真正热的只有几 MB。

代码里的错误处理分支，可能一辈子不执行。

一个 100 MB 的数组，可能只用前 1 MB。

**全部装入，就是把"可能用到"当成"马上要用"。**

三个代价跟着来：

```text
① 装入时间长：进程启动要先读几十 MB
② 内存浪费：装了不用的页，占着页框（页框：物理内存里装一页的那一格，一页占一个页框，别人就少一格）
③ 进程数受限：内存除以进程大小，多开一个都不行
```

一个自然的想法是交换（swapping）：内存不够就把整个进程换到磁盘，要用再换回来。

这个办法太粗。

一个进程 500 MB，只因为多用了 1 MB 就被整个换出，磁盘要写 500 MB。

粒度应该更细。

细到一页。

```text
换页（paging）：以页为单位换入换出，一页 4 KB
```

于是有了请求分页：

```text
进程启动时，只装入少数几页
访问到不在内存的页 → 硬件触发缺页 → 操作系统调入那一页
```

先把"缺页"这个词说清楚。

缺页（page fault）：CPU 要访问的某一页不在内存里，硬件当场发现，于是打断正在执行的指令，把控制权交给操作系统，让它去磁盘把那一页搬进来。

注意"缺页"不是"内存坏了"，也不是"程序出错了"，它是一件每天发生几百万次的正常事。

虚拟内存的定义，就落在这三句话上：

```text
① 每个进程有一个独立的虚拟地址空间，可以比物理内存大
② 地址空间的内容按需调入，不是一次装完
③ 不在内存的页放在外存（磁盘/SSD），需要时再换进来
```

虚拟内存的三个特征，408 会直接考：

```text
多次性：一个作业分多次调入内存，不是一次全装
对换性：运行中可以换入换出，允许暂时不在内存
虚拟性：从逻辑上扩充内存，用户看到的空间大于实际
```

三者的关系是有顺序的：

```text
多次性和对换性是手段
虚拟性是结果
```

没有"分多次调入"，就谈不上"换入换出"。

没有"换入换出"，"看起来更大"就站不住。

还有一条隐含的前提：离散分配。

如果进程必须占连续内存，"分多次调入"就做不到，因为每次调入都要找足够大的连续区。

所以：

```text
虚拟内存 = 离散分配 + 多次调入 + 对换
```

很多人把虚拟内存理解成"把硬盘当内存用"。

不对。

硬盘只是后备存储，它的速度还是硬盘的速度。

虚拟内存之所以不慢，靠的是"绝大多数访问都落在已经在内存的那几页上"。

这一点，下一节说清楚。

## 2. 局部性：虚拟内存成立的前提

程序访问内存，不是均匀随机的。

它有两个明显的偏向。

```text
时间局部性（temporal locality）：刚访问过的，很可能马上再访问
空间局部性（spatial locality）：访问了一个地址，附近的地址很可能马上被访问
```

时间局部性的来源：

```text
循环：for 循环体反复执行
计数器、累加变量：每次迭代都读写
反复调用的函数：同一段代码被执行几千次
```

空间局部性的来源：

```text
数组：a[0]、a[1]、a[2] 挨着放
指令：顺序执行，一条接一条
结构体：字段挨着放
```

一个最普通的循环：

```c
long sum = 0;
for (int i = 0; i < 1000000; i++)
    sum += a[i];
```

这段代码的访问模式：

```text
指令：几十条，落在 2 到 3 页里，反复执行 100 万次
数组：a[0..999999]，每 4 KB 一页，共约 4000 页
      但访问是顺序的，一页用完才换下一页
sum：一个变量，一直在一页里
```

按页算，100 万次循环只碰了 4000 多个页，而且每页被连续用了 1024 次。

缺页只可能发生在这 4000 次"跨页"的时刻。

```text
4000 次缺页 / 几百万次访存 ≈ 千分之几
```

如果没有局部性呢？

设想一个程序，每次访问都跳到随机的一页：

```text
第 1 次访存：缺页
第 2 次访存：缺页
第 3 次访存：缺页
```

每次缺页要读磁盘，一次几毫秒。

CPU 每秒能做几十亿次运算，却要等几毫秒才能拿到一个数。

系统会卡在这里，什么也干不了。

**反直觉的点在这里。**

虚拟内存能跑起来，靠的不是"内存大"。

靠的是"程序访问有局部性"。

内存再大，程序如果每次都随机跳页，虚拟内存只会变成抖动。

抖动（thrashing）：缺页率高到系统把绝大部分时间都花在换页上，CPU 反而闲着，吞吐量接近零。

内存再小，只要热点够集中，虚拟内存也能跑得不错。

这就是为什么 [16 篇](/posts/os-thrashing-workset/)要专门讲工作集：

```text
工作集 = 程序当前真正需要的那一小撮页
虚拟内存的性能，取决于工作集能不能全部装进内存
```

顺带说一句：局部性不只解释虚拟内存。

CPU 的缓存、TLB、磁盘的预读，用的都是同一条规律。

TLB（translation lookaside buffer，快表）：CPU 里一张很小的表，缓存"页号 → 页框号"的最近结果，省掉每次访存都查页表。

缓存（cache）：CPU 里比内存更快更小的一块存储，装最近用过的数据。

整个存储层次，就是在把"局部性"这三个字变现：

```text
越近期用到的数据，越放在快而小的介质里。
```

90/10 法则说的就是这件事：

```text
程序 10% 的代码，占了 90% 的执行时间。
```

这是一条经验规律，不是定理。

但它解释了一个事实：

一个几百 MB 的软件，启动后真正热的页可能只有几 MB。

剩下的页，装进来也是躺着。

再看一个反例。

一个 1 GB 的数组，按 4 KB 的步长跳着访问：

```c
volatile char sink;
for (long i = 0; i < 1024L * 1024 * 1024; i += 4096)
    sink = data[i];
```

1 GB / 4 KB = 262,144 页。

每一次访问都落在一个新页上，前一页用完就再也不碰。

如果内存装不下这 262,144 页，每次访存都缺页。

假设一次缺页 5 ms：

```text
262,144 × 5 ms = 1,310,720 ms ≈ 21.8 分钟
```

26 万次访存，要跑二十二分钟。

正常程序 26 万次访存只要二十多毫秒（按每次 100 ns 算，约 26 ms）。

```text
1,310,720 ms / 26 ms ≈ 50,000 倍
```

差四到五个数量级。

**同一台机器、同样的内存，只因为访问模式不同，性能差几万倍。**

这就是"局部性决定虚拟内存成败"的具体含义。

## 3. 请求分页的页表项：多了四个字段

先说为什么页表项必须加字段。

因为"页可以不在内存"这件事，得有个地方记下来。

页表项（page table entry，PTE）：页表里的一行，一个虚拟页对应一行，记着这一页现在在哪个页框。

还要记：这一页被访问过没有（决定该不该换出去）、被改过没有（决定换出去要不要写回）、换出去以后放在磁盘哪里（不然找不回来）。

普通分页的页表项只关心"页在哪"，请求分页的页表项还得关心"页不在时怎么办"。

[13 篇](/posts/os-paging-segmentation/)的页表项，只存页框号和几个权限位。

所以请求分页的页表项，必须比普通页表项多记几件事。

多记的第一件是"在不在内存"，第二件是"不在的话在磁盘哪里"，第三件是"最近用没用过、改没改过"。

```text
┌────────┬────┬────┬────┬──────────┬────────┐
│ 页框号 │ P  │ A  │ M  │  保护位  │ 外存地址│
└────────┴────┴────┴────┴──────────┴────────┘
```

四个新字段，各有各的用处。

```text
P（present，存在位）
  1：这一页在内存，页框号有效
  0：这一页不在内存，页框号无效，外存地址有效

A（accessed，访问位）
  这一页被访问过没有，硬件在访存时置 1
  置换算法靠它判断"最近用没用过"

M（modified / dirty，修改位）
  这一页被写过没有，硬件在写时置 1
  换出时靠它判断"要不要写回磁盘"

外存地址
  这一页在磁盘上的位置（对换区或文件里的偏移）
  不在内存时，靠它把页读回来
```

逐个说清楚。

**存在位**是虚拟内存的开关。

没有它，"页不在内存"这件事就无法表达，缺页也无从谈起。

**访问位**是置换算法的原料。

硬件只负责置 1，什么时候清 0 是操作系统的事。

[15 篇](/posts/os-page-replacement/)的 CLOCK 算法，就是围着这一位转。

**修改位**决定换出的代价。

```text
M = 0：这页和磁盘上的一样，直接丢弃，不用写
M = 1：这页被改过，必须先写回磁盘，才能腾出页框
```

一页 4 KB 的写回，可能比一次缺页读入还贵。

所以置换算法偏爱 M = 0 的页（[15 篇](/posts/os-page-replacement/)的改进 CLOCK）。

**外存地址**最容易被忽略。

它回答一个具体问题：

```text
这一页换出去的时候，放到磁盘的哪里？
```

两种放置方式：

```text
对换区（swap）：连续分配，读写快，但空间有限
文件区      ：按文件块存放，读写慢，但空间大
```

页表项多了这四个字段，一位一位都是钱。

32 位机器上，一个页表项从 4 B 涨到 8 B，页表就大了一倍。

所以真实系统会把标志位塞进页框号空出来的位里。

x86-64 的页表项是 8 B，其中低 12 位全是标志位，高 52 位里放物理页框号。

**这是简化示意，具体位数随架构变化。**

## 4. 一次完整走查：缺页中断处理

这一节把一次缺页从触发到返回，按顺序走一遍。

为什么要一步步走？

因为考卷最爱问的，不是"缺页是什么"，而是"第三步保存的是哪条指令的地址""第五步一定要置换吗""第七步为什么要清 TLB"。

每一步背后都有一个具体的原因，走得慢一点才记得住。

假设进程要读地址 `0x00403ABC` 的一个字节。

页表项说：这一页不在内存。

接下来发生的事，按顺序走一遍。

```text
① CPU 发地址，MMU 查 TLB
       │ 未命中
       ▼
② MMU 查页表，读到 PTE
       │ P = 0
       ▼
③ 触发缺页异常（page fault），CPU 进入内核态
   把当前指令的地址存进 PC/断点寄存器
       │
       ▼
④ 内核检查：地址合法吗？在某个 VMA 里吗？权限够吗？
       │ 不合法 → SIGSEGV，进程被杀
       ▼
⑤ 找空闲页框
   ├─ 有空闲 → 直接用
   └─ 没有   → 置换算法选一个 victim
                ├─ victim 的 M = 1 → 先写回磁盘
                └─ victim 的 M = 0 → 直接释放
       │
       ▼
⑥ 从外存把缺的页读进页框（这段时间进程睡眠）
       │
       ▼
⑦ 修改页表项：P = 1，页框号 = 新页框，M = 0
   如果 TLB 里有这个页号的旧项，清掉
       │
       ▼
⑧ 返回用户态，重新执行刚才那条指令
```

图里有两个词，先解释一下。

置换（page replacement）：空闲页框用光了，只好挑一页赶出去，把它的页框让给新来的页。

victim（牺牲页）：被挑中要赶出去的那一页，英文原意就是"受害者"。

八步里，有三步最容易考。

**第三步：保存的是"当前指令"的地址，不是下一条。**

普通中断（时钟、键盘）发生时，当前指令已经执行完，返回后执行下一条。

缺页不一样：指令执行到一半，访存失败了。

所以返回后必须重新执行同一条指令。

这也是为什么缺页处理函数最后是"返回并重试"，不是"返回并跳过"。

**第五步：先看有没有空闲页框，再谈置换。**

很多题会问"缺页时一定要置换吗"。

不一定。

系统刚启动、或者刚换出过进程时，空闲页框链表可能非空。

只有空闲页框用完，才需要选 victim。

**第七步：一定要清 TLB。**

页表改了，TLB 里可能还留着旧的"页号 → 页框号"。

不清掉，下次访问还是翻译到旧页框，数据就错了。

真实系统里，这一步靠 `invlpg` 一类的指令完成。

把八步压成一句人话：

进程伸手要一个数据 → 发现它不在内存 → 内核核对地址合不合法 → 找一个空页框（没有就赶走一页）→ 去磁盘把数据搬进来 → 改页表 → 回头把刚才那条指令再做一遍。

多核机器上还要通知其他 CPU，叫 TLB shootdown。

用伪代码写出来：

```c
/* 简化示意：缺页异常处理的主干 */
void handle_page_fault(unsigned long addr, unsigned long error_code)
{
    struct vm_area_struct *vma = find_vma(current->mm, addr);
    pte_t *pte;

    if (!vma || !(vma->vm_flags & VM_READ))
        return;                     /* 地址非法，上层杀掉进程 */

    pte = walk_page_table(current->mm->pgd, addr);

    if (!pte_present(*pte)) {
        struct page *page = alloc_page(GFP_HIGHUSER);

        if (!page) {
            page = reclaim_page();  /* 没有空闲页框：选一个 victim */
            if (PageDirty(page))    /* victim 是脏页，先写回 */
                writeback_page(page);
        }

        read_from_disk(pte->swap_entry, page); /* 读入，进程睡眠 */
        set_pte(pte, mk_pte(page, vma->vm_page_prot));
        flush_tlb_page(vma, addr);             /* 清 TLB */
    }
    /* 返回用户态，重新执行缺页的那条指令 */
}
```

（`walk_page_table`、`reclaim_page`、`read_from_disk` 都是示意名，不是逐字的内核代码。）

缺页处理时间不是常数。

它由四段组成：

```text
磁盘寻道 + 旋转延迟 + 传输 4 KB + 内核处理开销
```

机械盘上一次主缺页通常在 5 到 10 ms。

SSD 上降到几十到几百 μs，但还是比内存访问慢三四个数量级。

所以 EAT 题里 t_fault 总是毫秒级，而 t_mem 是纳秒级。

两者放在同一个式子里，缺页项一旦乘上 p，很容易盖过前面所有优化。

### 4.1 一条指令可能缺好几次页

这是请求分页里最反直觉的细节之一。

普通中断一次只处理一个事件。

缺页可能一条指令触发多次。

例子一：跨页访问。

```text
在地址 0x1FFC 处写 8 个字节
覆盖 0x1FFC ~ 0x2003
跨了 0x1000 页和 0x2000 页
```

如果两页都不在内存，这一次写就要缺两次页。

第一次缺页处理完，指令重试，写到第二页，又缺一次。

例子二：字符串复制。

```c
memcpy(dst, src, 1024 * 1024);
```

`rep movsb` 一条指令复制 1 MB，跨 256 个页。

如果源和目的都不在内存，这条指令可能缺几百次页。

例子三：多级页表。

访问一个地址要读页目录、读页表、读数据。

如果页表项所在的那一页也不在内存，读页表本身就是一次缺页。

极端情况下，一次访存要先缺页装入页表页，再缺页装入数据页。

### 4.2 缺页中断和普通中断的区别

| 比较项 | 缺页中断 | 普通中断（时钟、键盘） |
|---|---|---|
| 产生时机 | 指令执行期间，访存失败 | 指令执行完之后 |
| 来源 | CPU 内部，属于异常 | CPU 外部，属于外中断 |
| 返回地址 | 当前指令 | 下一条指令 |
| 一条指令触发次数 | 可能多次 | 至多一次 |
| 处理期间 | 可能要等磁盘 I/O，进程睡眠 | 通常很快，不睡眠 |
| 处理完 | 重新执行同一条指令 | 继续执行下一条 |

记住一句话：

```text
缺页是"这条指令没做完"，普通中断是"这条指令做完了"。
```

## 5. 页框分配与调入策略

一个进程能分到多少页框，直接决定它的缺页率。

分得太少，热点页装不下，刚换出又要换入。

分得太多，别的进程没得用，多道程度下降。

### 5.1 最少要几个页框

下限由指令集决定。

一条指令要能执行完，它碰到的所有页必须同时在内存。

```text
指令本身：x86 指令最长 15 B，4 KB 页下最多跨 2 页
直接操作数：1 页
一级间接寻址：再多 1 页
二级间接寻址：再多 1 页
```

所以下限通常写成：

```text
最少页框数 = 指令跨的页数 + 间接寻址层数
```

常见值是 2 到 6。

低于这个数，指令永远执行不完：刚装入第二页，第一页被换出去了。

举个最小的例子。

一条指令跨两页，进程只分到 1 个页框。

装入第一页，指令执行到一半要用第二页，缺页。

把第一页换出、第二页装进来，指令从头重试，第一页又不在，再缺页。

两个页框来回倒，指令一辈子走不完。

这不是夸张，是计算"最少页框数"这个下限的由来。

**如果没有这条下限，操作系统会把页框分得越省越开心，结果就是所有进程一起卡死。**

408 会问"某机器指令最多跨 6 页，最少需要几个页框"，答案就是 6。

### 5.2 四种组合

为什么要把"分配"和"置换"分成两件事？

因为它们回答的是两个不同的问题：分配决定"你手里有几个页框"，置换决定"缺页时从你手里挑哪一页赶走"。

这两件事可以各自独立地定，于是一组合就有四种做法。

分配方式有两个维度：

```text
分配：固定（每个进程帧数固定） / 可变（帧数可调）
置换：局部（只在自己帧里换） / 全局（可以从别人帧里抢）
```

组合起来四种，但有一种基本不用。

| 组合 | 做法 | 后果 |
|---|---|---|
| 固定分配 + 局部置换 | 每个进程帧数固定，缺页只换自己的页 | 简单；帧数定多了浪费、定少了抖动 |
| 可变分配 + 全局置换 | 缺页时从空闲链表拿帧，没有就全局选一页 | 灵活；但会抢别人的帧，可能连锁缺页 |
| 可变分配 + 局部置换 | 帧数可调，缺页只换自己的页；缺页频繁就加帧 | 折中，最稳；实现最复杂 |
| 固定分配 + 全局置换 | 帧数号称固定，却又允许全局抢 | 自相矛盾，帧数实际上不固定，基本不用 |

重点理解第二种和第三种的区别。

全局置换的毛病在于"连锁反应"：

```text
进程 A 缺页 → 抢了进程 B 的页框
进程 B 下一句就缺页 → 又去抢 C 的
C 缺页 → 再抢 A 的
```

一个进程的缺页，会传染给整个系统。

局部置换把影响关在进程内部：

```text
进程 A 缺页 → 只在 A 自己的页框里挑 victim
```

代价是：如果 A 的帧数本来就不够，它只能一直抖动，谁也帮不了它。

解决办法是动态调帧：

```text
A 缺页率高于上限 → 给 A 加几帧（从空闲链表或其他进程拿）
A 缺页率低于下限 → 收回几帧
```

这就是"可变分配 + 局部置换"，也叫工作集策略的简化版。

### 5.3 调入策略：请求调页与预调页

既然请求调页已经够用了，为什么还要"预调页"？

因为请求调页每次只调一页，而进程刚启动时要连着缺好几十次页，每次都等一次磁盘，启动就慢得难受。

```text
请求调页（demand paging）：缺一页调一页
预调页（prepaging）      ：一次调一批相邻的页
```

请求调页简单，但启动慢。

一个进程刚创建时，要执行第一条指令，就得先缺一次页。

预调页用在两个地方：

```text
进程首次装入：把它预计要用的几页一次读进来
进程换入：把它换出时的整个工作集一次读回来
```

预调页的风险是预测错。

调进来一堆不用的页，白费 I/O，还把别的页挤出去。

所以真实系统是混合的：

```text
对换区（swap）：用预调页，因为换出去的页大概率还会用
文件区        ：用请求调页，因为读文件是随机访问居多
```

### 5.4 页面大小怎么影响缺页率

这一条常被当成"常识"背，其实有账可算。

```text
页大：一页装的数据多，跨页少，缺页次数少；但一页调入的数据多，内部碎片大
页小：按需调入精准，碎片小；但页表大，跨页频繁，缺页次数可能反而多
```

极端情况：

```text
页大小 = 整个进程 → 退化成连续分配，一次全装入
页大小 = 1 字节   → 每次访存都缺页，页表比数据还大
```

中间有个最优点。

它取决于程序的访问模式、磁盘速度和内存大小。

页大小还影响单次缺页的代价：一次缺页搬一整页，页大则传输时间长。

408 只考"页大页小各自的影响"，不考"最优页大小是多少"。

原因很简单：最优点依赖具体参数，没有唯一答案。

## 6. 408 怎么考

为什么这一篇的考点会分成"能算"和"能判"两类？

因为虚拟内存的两半，一半是数字（缺页率、EAT），一半是流程（先找页框还是先置换、返回后执行哪条指令）。

数字题有固定套路，流程题要能说清"为什么是这一步而不是那一步"。

这一篇的考点分两类。

```text
能算的：EAT、缺页率阈值、缺页次数
能判的：缺页处理流程、页框分配策略、调入策略
```

EAT 的公式只有一条主干：

先用一句人话说清它在算什么：一次访存有两种结局，要么页在内存（快），要么缺页（慢得离谱）。

把两种结局各自的耗时，按它们出现的比例加权平均，就是"平均一次访存要多久"。

```text
EAT = 不缺页的概率 × 不缺页的代价 + 缺页的概率 × 缺页的代价
```

逐项解释一遍：

```text
不缺页的概率 = 1 − p，p 是缺页率（每次访存缺页的概率）
不缺页的代价 = 一次正常访存要多久，可能是 t_mem，也可能带 TLB 的几次查表
缺页的概率   = p
缺页的代价   = t_fault，一次缺页处理的总时间，通常给成毫秒级
```

其余全是把"不缺页的代价"换成带 TLB 的版本。

### 例题一：只有缺页，没有 TLB（自拟）

某系统内存访问时间 200 ns，缺页处理时间 8 ms，缺页率 1/10000。

求有效访问时间。

解：

```text
EAT = (1 − p) × 200 + p × 8,000,000
    = 0.9999 × 200 + 0.0001 × 8,000,000
    = 199.98 + 800
    = 999.98 ns
    ≈ 1 μs
```

验算：

```text
0.9999 × 200 = 199.98
0.0001 × 8,000,000 = 800
199.98 + 800 = 999.98 ✓
```

结论：缺页率万分之一，性能掉 5 倍。

追问：缺页率升到千分之一呢？

```text
0.999 × 200 + 0.001 × 8,000,000
= 199.8 + 8000
= 8199.8 ns
```

再追问：缺页率多大时，EAT 翻倍到 2000 ns？

```text
200 + p × (8,000,000 − 200) = 2000
p = 1800 / 7,999,800
  ≈ 2.25 × 10^-4
  = 0.0225%
```

也就是说，缺页率只要到万分之二点二五，平均访存时间就翻倍。

**这道题的结论比答案重要：缺页率到万分之一量级，性能就已经腰斩；到百分之一，系统基本没法用了。**

### 例题二：TLB 加缺页（自拟）

条件：

```text
TLB 访问时间 10 ns
内存访问时间 100 ns
TLB 命中率 98%
缺页率 1/10000（按每次访存计）
缺页处理时间 10 ms
```

求 EAT。

解：

先算不缺页时的平均访存时间：

```text
命中：10 + 100 = 110 ns
未命中：10 + 100 + 100 = 210 ns
平均 = 0.98 × 110 + 0.02 × 210
     = 107.8 + 4.2
     = 112 ns
```

再加上缺页的代价：

```text
1/10000 × 10 ms = 0.0001 × 10,000,000 ns = 1000 ns
```

合计：

```text
EAT = 112 + 1000 = 1112 ns
```

验算：

```text
0.98 × 110 = 107.8
0.02 × 210 = 4.2
107.8 + 4.2 = 112 ✓
0.0001 × 10,000,000 = 1000 ✓
112 + 1000 = 1112 ✓
```

结论：TLB 把查表从 210 ns 压到 112 ns，省了 98 ns。

但缺页一次就赔进去 1000 ns。

**TLB 优化的是"查表"，缺页优化的是"换页"，两者不在一个数量级上。**

追问：若要求 EAT 不超过 120 ns，缺页率上限是多少？

```text
112 + p × 10,000,000 ≤ 120
p ≤ 8 / 10,000,000
p ≤ 8 × 10^-7
```

也就是每 125 万次访存最多缺一次页。

这个数字说明：只要想让系统"接近全在内存"，缺页率必须压到百万分之一量级。

### 例题三：流程判断（自拟，选择题风格）

缺页处理完成后，CPU 应该：

```text
A. 执行下一条指令
B. 重新执行当前指令
C. 重新调度进程
D. 终止进程
```

答案：B。

理由：

```text
缺页发生在指令执行期间，指令没有完成。
页表修好之后，必须重试同一条指令。
```

再加一道：

```text
缺页时一定要进行页面置换吗？
```

答案：不一定。

```text
有空闲页框 → 直接分配，不置换
没有空闲页框 → 才需要选 victim
```

### 408 的四个高频陷阱

```text
陷阱一：p 的定义
  p 是"每次访存缺页的概率"，不是"每个进程缺页的概率"

陷阱二：缺页处理时间包含什么
  一般包含磁盘寻道 + 旋转 + 传输 + 内核开销，题目会给成一个总时间

陷阱三：TLB 未命中 ≠ 缺页
  TLB 没有，页表有，只是多查一次表，不算缺页

陷阱四：初始装入算缺页
  进程刚启动时，第一页也要缺一次页，这叫 compulsory miss
```

## 7. 真实系统里长什么样

前面讲的是一套通用机制，这里看 Linux 用什么数据结构把它落地。

Linux 里，一个进程的地址空间由 `mm_struct` 描述。

```c
/* 简化示意，字段有删减 */
struct mm_struct {
    struct maple_tree mm_mt;      /* 所有 VMA，按地址组织 */
    pgd_t *pgd;                   /* 页表根 */
    unsigned long start_code, end_code;
    unsigned long start_data, end_data;
    unsigned long start_brk, brk;
    unsigned long start_stack;
    atomic_long_t rss_stat[NR_MM_COUNTERS];
};
```

`mm_struct` 是"一个进程的地址空间"。

每个 VMA（`vm_area_struct`）是地址空间里一段连续、同权限的区域：

```text
代码段、数据段、堆、栈、每个 mmap 的文件、每个动态库
```

缺页的入口是 `do_page_fault`。

它先查 `mm`，找到地址落在哪个 VMA 里。

然后用 `handle_mm_fault` 往下走：

```text
handle_pte_fault
  ├─ 页表项为空 + 匿名页  → do_anonymous_page（分配零页）
  ├─ 页表项为空 + 文件页  → do_fault（从 page cache 读）
  ├─ 页表项存在但只读    → do_wp_page（写时复制）
  └─ 页表项存在但换出    → do_swap_page（从 swap 读回）
```

四条分支，对应四种"页不在"的情形。

```text
匿名页：malloc/mmap 出来的内存，没有文件后备
文件页：代码段、动态库、mmap 的文件
写时复制：fork 之后父子共享的页，谁写谁复制
换出页：被置换到 swap 的页
```

计数在 `/proc/vmstat` 里：

```text
pgfault        缺页总数（含次缺页 minor）
pgmajfault     主缺页数（需要读磁盘的那些）
pgalloc_normal 分配的页框数
pswpin/pswpout 换入/换出的页数
```

一个进程自己的计数在 `/proc/<pid>/stat` 里：

```text
minflt：次缺页，不需要磁盘 I/O（比如零页、页表已在）
majflt：主缺页，需要磁盘 I/O
```

**"次缺页"这个词容易误解。**

它不是"次要的缺页"，而是"不需要 I/O 的缺页"。

比如第一次写匿名页，内核直接给一个填零的页，不读磁盘，算 minflt。

想看一个进程的驻留集有多大，读 `/proc/<pid>/status` 里的 `VmRSS`：

```bash
grep -E 'VmRSS|VmSwap' /proc/$$/status
```

`VmRSS` 是驻留集大小，也就是当前真正占着页框的那部分。

它通常远小于 `VmSize`（虚拟空间大小），差额就是"没碰过的页"。

一个进程 `VmSize` 几百 MB、`VmRSS` 几 MB，是完全正常的。

真实系统里还有一个和 408 不完全一致的地方：

```text
Linux 允许 overcommit：malloc 1 GB 时并不检查有没有 1 GB 可用
真正分配发生在第一次写，可能触发 OOM killer
```

`vm.overcommit_memory` 控制这个策略。

**以上是简化示意，函数名和分支随内核版本变化，不要逐字背。**

## 8. 容易混淆的六个点

为什么这些点容易混？

因为虚拟内存里"在不在内存"和"能不能访问"是两码事，而这两件事在页表项里就挨着。

```text
① 虚拟内存 ≠ 交换空间
   交换空间只是后备存储；虚拟内存是"地址空间 + 按需调入"的机制

② 缺页率 p 是每次访存的概率
   不是每个进程的概率，也不是每秒的概率

③ 存在位 ≠ 有效位 ≠ 保护位
   存在位说"在不在内存"，保护位说"能不能读写执行"

④ 缺页是异常，但缺页处理可能被中断
   等磁盘 I/O 时，进程睡眠，CPU 去跑别的进程

⑤ 请求分页 ≠ 请求分段
   前者按页调入，后者按段调入；408 主要考前者

⑥ 页框分配和页面置换是两件事
   分配决定"给你多少帧"，置换决定"缺页时换哪一页"
```

再补一个最隐蔽的：

```text
缺页处理程序本身也可能缺页。
```

它要读页表、访问进程的 VMA、可能还要访问 swap 的元数据。

这些数据结构所在的页，也可能不在内存。

所以内核的缺页路径必须小心，不能自己把自己陷进去。

真实内核里，这部分代码要避免递归缺页。

## 9. 再算两题

### 9.1 TLB 加缺页，换一组参数

条件：

```text
TLB 访问 20 ns
内存访问 80 ns
TLB 命中率 95%
缺页率 0.0002
缺页处理 12 ms
```

解：

```text
命中：20 + 80 = 100 ns
未命中：20 + 80 + 80 = 180 ns
平均不缺页：0.95 × 100 + 0.05 × 180
          = 95 + 9
          = 104 ns
缺页代价：0.0002 × 12,000,000 = 2400 ns
EAT = 104 + 2400 = 2504 ns
```

验算：

```text
0.95 × 100 = 95
0.05 × 180 = 9
95 + 9 = 104 ✓
0.0002 × 12,000,000 = 2400 ✓
104 + 2400 = 2504 ✓
```

结论：缺页率万分之二，平均访存 2.5 μs。

比内存访问慢 31 倍。

### 9.2 反求缺页率上限

条件：

```text
内存访问 100 ns
缺页处理 10 ms
要求 EAT ≤ 2 μs
```

解：

```text
100 + p × (10,000,000 − 100) ≤ 2000
p × 9,999,900 ≤ 1900
p ≤ 1900 / 9,999,900
p ≤ 1.9 × 10^-4
```

验算：

```text
1.9 × 10^-4 × 9,999,900 = 1899.98
100 + 1899.98 = 1999.98 ≤ 2000 ✓
```

结论：缺页率必须低于万分之一点九。

**这类"反求 p"的题，408 出过不止一次，套路就是解一个一元一次不等式。**

## 10. 一页速查

```text
EAT = (1 − p) × t_mem + p × t_fault

带 TLB：
EAT = α(t_TLB + t_mem) + (1 − α)(t_TLB + n × t_mem) + p × t_fault

缺页率上限：
p ≤ (EAT_target − 不缺页代价) / t_fault

最少页框数 = 指令跨的页数 + 间接寻址层数
```

三句话：

```text
虚拟内存不是硬盘当内存，是"用到的才调入"。
缺页是异常，返回后重执行当前指令。
局部性在，虚拟内存就快；局部性没了，就是抖动。
```

### 自检三问

1. 如果页表项里没有"存在位"，虚拟内存还成立吗？

   答不上来说明没抓住 P = 0 是整套机制的开关：没有它，"这一页不在内存"就无法表达，硬件也没法在访存时把控制权交给操作系统，缺页无从谈起。

2. 为什么缺页处理完要"重新执行当前指令"，而不是"执行下一条"？

   答不上来说明没分清异常和中断：缺页发生在指令执行期间，指令没做完；页表修好后必须重试同一条，否则等于把这条指令整个跳过去了。

3. 内存访问 200 ns、缺页处理 8 ms、缺页率万分之一，EAT 是多少？缺页率升到千分之一呢？

   答不上来说明公式还没练熟：前者 999.98 ns ≈ 1 μs，后者 8199.8 ns。缺页率只涨 10 倍，EAT 涨 8 倍多——因为缺页项本来就占了大头。

## 11. 小结

这一篇的主线，可以压成一个因果链：

```text
内存装不下所有页
   → 只装用到的（请求分页）
   → 用不到的页不在内存（存在位 = 0）
   → 访问到就缺页（异常）
   → 缺页要调入，没空位就置换
   → 置换选谁，决定缺页率
   → 缺页率决定 EAT
```

这条链上，每一步都是前一步的补丁。

补到最后，系统能跑了，但跑得好不好，取决于一个前提：

**程序的访问有局部性。**

有局部性，热点页常驻，缺页率低，EAT 接近内存访问时间。

没有局部性，每次访问都换页，EAT 接近磁盘时间。

后者有一个专门的名字：抖动。

它是 [16 篇](/posts/os-thrashing-workset/)的主题。

而这一篇留下的另一个问题是：

```text
没有空闲页框时，置换算法选哪一页？
```

这就是下一篇。

```text
操作系统系统讲解 15：页面置换算法
```

那一篇会把 OPT、FIFO、LRU、CLOCK 放在同一个引用串上算一遍。

还会证明一件事：

页框变多，缺页次数不一定变少。
