先看三条指令。

```asm
cli                 ; 关中断
mov cr3, eax        ; 换页表基址
hlt                 ; 停机
```

三条都很短。

任何一条，如果在你的用户态程序里出现，CPU 会立刻报错。

不是崩，是拒绝执行。

```text
#GP 通用保护故障
```

而同样的三条，在内核里是日常操作。

同一颗 CPU，同一段机器码，为什么待遇不同？

因为 CPU 有一个"模式"开关。

**这个开关，就是整个操作系统能存在的物理基础。**

## 1. 这个问题解决什么

01 篇说操作系统管四类资源。

管理需要权力。

权力在计算机里只有一种形式：

```text
能执行别人不能执行的指令。
能访问别人不能访问的内存。
```

这两件事合起来，叫特权（privilege）。

于是问题变成三个：

```text
① 特权从哪来？         → 硬件提供的模式位
② 谁有权开这个口子？   → 只能由硬件 + 内核
③ 用户程序怎么求内核？ → 系统调用
```

三个问题，一个答案链：

```text
硬件给内核特权
  → 内核用特权隔离用户
  → 用户只能通过"陷入"请求内核
  → 陷入的入口只有中断/异常/系统调用
```

这一篇就是把这条链拆开。

拆完你会发现一个反直觉的事实：

> **操作系统不是一个一直在运行的程序。**
> **它是一堆躺在内存里的代码，被中断叫醒才干活。**

## 2. 最小模型：一条指令的两种身份

### 2.1 特权指令与非特权指令

指令集被分成两半。

```text
特权指令（privileged instruction）：
  只能在核心态执行，执行结果会影响整个系统

非特权指令（unprivileged instruction）：
  用户态也能执行，只影响本进程
```

怎么判断一条指令是不是特权？

一个粗糙但好用的判据：

```text
它会不会改动"全局状态"？
会 → 特权
不会 → 非特权
```

按这个判据过一遍：

```text
特权：
  关中断 / 开中断（cli / sti）
  设置时钟
  清内存
  修改 PSW / 修改模式位
  I/O 指令（in / out）
  修改页表基址寄存器（mov cr3）
  停机（hlt）
  加载微程序
  切换栈指针到内核栈（部分体系结构）

非特权：
  算术运算（add / sub / mul）
  逻辑运算
  访存（load / store，地址受页表约束）
  跳转、调用、返回
  陷入指令（trap / syscall / int）
```

最后一条最容易记反。

**陷入指令必须是非特权的。**

否则用户程序没法主动进内核，系统调用就无从发起。

它是"敲门"，敲门这件事不需要特权。

开门才需要。

### 2.2 内核态与用户态

CPU 怎么知道自己现在是什么身份？

靠一个寄存器位。

教材叫它 PSW（program status word，程序状态字）里的状态位。

x86 上这个位藏在 `CS` 寄存器的最低两位，叫 CPL（current privilege level）。

```text
CPL = 0  → 内核态（核心态、管态）
CPL = 3  → 用户态（目态）
```

取值 0 到 3，四个环。

Linux 只用两个：0 和 3。

```text
ring 0：内核
ring 1、2：几乎没人用
ring 3：所有用户程序
```

为什么有四个环却只用两个？

因为跨环切换有成本，而"两态"已经能表达所有需要。

多出来的两环，历史上留给驱动和虚拟机监控器，实际没用起来。

### 2.3 什么时候切

切换方向只有两个。

用户态进内核态，只有三条路：

```text
① 中断（interrupt）——外部设备敲门
   时钟、键盘、磁盘完成、网卡收包

② 异常（exception）——当前指令出事
   缺页、除零、非法指令、断点

③ 系统调用（system call）——程序自己请求
   本质是异常里的一种（陷入 trap）
```

内核态回用户态，也只有一条路：

```text
中断返回指令（iret）
```

它把之前保存的 PSW 和 PC 恢复回去，CPL 自动变回 3。

画出来：

```text
        用户态 (CPL=3)
           │
           │  ① 中断  ② 异常  ③ 陷入
           ▼
        内核态 (CPL=0)
           │
           │  iret
           ▼
        用户态 (CPL=3)
```

注意一个细节：

```text
中断发生时，CPU 自动把 CPL 从 3 改成 0。
不需要软件干预。
```

这是硬件行为，不是内核代码干的。

因为如果是软件干的，用户程序就能自己改。

**特权级切换的入口必须由硬件把守，否则整套机制立刻失效。**

### 2.4 内核态里也会被中断

内核不是关起门来无敌的。

内核在跑的时候，时钟照样会响。

所以内核代码要区分两种状态：

```text
开中断：允许响应外部中断（大多数时候）
关中断：屏蔽可屏蔽中断（操作关键数据结构时）
```

关中断用的是 `cli`，开是 `sti`。

这两个必须是特权指令，而且必须成对出现。

```text
cli
  修改就绪队列
sti
```

如果中间有人插进来，队列就乱了。

这段"中间"就是 07 篇要讲的临界区。

> **反直觉的点：操作系统不是一直运行的程序，它是"被中断叫醒才干活"的代码集合。**
> **CPU 空闲时，内核连一行代码都不执行。**

证据很直接：

```text
没有中断 → CPU 执行 hlt 睡觉 → 内核代码一行也不跑
```

## 3. 一次完整走查：printf 到屏幕

定义看完了，走一遍。

代码：

```c
#include <unistd.h>
#include <stdio.h>

int main(void) {
    printf("hi\n");
    return 0;
}
```

这一步不是"一句话变成一行字"。

它跨了两次世界。

### 3.1 用户态这一段

```text
① printf 做格式化："hi\n" 三个字节
② 查 stdout 的缓冲区：行缓冲，遇到 \n 就 flush
③ 调 write(1, "hi\n", 3)
④ write 是 glibc 的薄包装：
   - 把系统调用号 1 放进 rax
   - 把 fd=1 放进 rdi
   - 把 buffer 地址放进 rsi
   - 把长度 3 放进 rdx
   - 执行 syscall 指令
```

到这里，程序还在用户态。

### 3.2 硬件那一段

`syscall` 指令一执行，硬件开始动作：

```text
⑤ CPL 从 3 变成 0
⑥ 保存返回地址到 rcx，保存 RFLAGS 到 r11
   （简化示意，具体寄存器依体系结构而定）
⑦ 从 MSR 里取出内核入口地址，装进 rip
⑧ 切换到内核栈（rsp 换成内核栈指针）
⑨ 跳到内核的统一入口
```

六步，全是硬件做的。

**一条指令，完成了"换身份 + 换栈 + 换地址"三件事。**

### 3.3 内核那一段

```text
⑩ 内核入口保存通用寄存器（现场）
⑪ 读 rax 里的系统调用号 = 1
⑫ 查系统调用表 sys_call_table[1] → sys_write
⑬ sys_write 检查 fd=1 是不是合法、buffer 地址是不是用户空间
⑭ 找到终端设备，把三个字节交给它
⑮ 返回值 3 放进 rax
⑯ 恢复现场，执行 iret
⑰ CPL 变回 3，回到用户态下一条指令
```

### 3.4 收拢

整条路上，只有两次"特权级切换"：

```text
user → kernel（syscall 指令，硬件完成）
kernel → user（iret 指令，硬件完成）
```

一次 `printf` 输出三个字节，成本主要在这里。

不是格式化慢，是过边界慢。

## 4. 中断与异常：谁在敲门

### 4.1 外中断（中断）

定义：

```text
来自 CPU 外部的事件，与当前正在执行的指令无关。
```

三类典型：

```text
① 时钟中断
   定时器每隔一个周期发一次，是抢占式调度的物理基础
   没有它，一个死循环程序能永远占着 CPU

② I/O 中断
   磁盘读完一块、网卡收到一帧、键盘按下某个键
   设备干完活了，通知 CPU 来取结果

③ 控制台中断
   操作员干预（老式系统）
```

特征：

```text
异步：什么时候来不确定
与当前指令无关：可能在两条指令之间任意一点发生
可屏蔽：可以用 cli 暂时挡住（NMI 除外）
```

### 4.2 异常（内中断）

定义：

```text
CPU 执行当前指令时产生的意外，与当前指令有关。
```

分三类。

**陷入（trap）**

```text
有意为之，程序主动触发。
例：系统调用、断点指令 int3、调试器单步
返回地址：下一条指令
```

系统调用就是 trap。

这一点很多人记错，以为系统调用是"特殊的中断"。

它是异常，不是外中断。

**故障（fault）**

```text
指令执行出错，但可能被修复。
例：缺页、地址越界、整数除零
返回地址：当前这条指令（修复后重新执行）
```

缺页是最典型的。

```text
指令要访问的页不在内存 → fault
内核把页从磁盘调进来 → 修好了
重新执行这条指令 → 这次成功
```

注意"重新执行"这四个字。

它解释了为什么缺页处理后，程序看起来什么都没发生。

**终止（abort）**

```text
致命错误，无法修复。
例：硬件故障、内存校验错、总线错误、非法指令
返回地址：没有（进程直接被终止）
```

### 4.3 一张对比

| | 中断（外中断） | 异常（内中断） |
|---|---|---|
| 来源 | CPU 外部设备 | CPU 执行指令的过程中 |
| 与当前指令 | 无关 | 有关 |
| 时机 | 异步、随机 | 同步、由指令触发 |
| 典型例子 | 时钟、磁盘完成、键盘 | 缺页、除零、系统调用、断点 |
| 返回地址 | 下一条指令 | trap 下一条 / fault 当前条 / abort 不返回 |

这张表是 408 选择题的高频出处。

尤其第三行和第五行。

### 4.4 中断处理流程

不管哪种，处理流程长一个样。

```text
① 关中断              ┐
② 保存断点（PC、PSW）  ├ 隐指令：硬件自动完成
③ 引出中断服务程序      ┘

④ 保存现场（通用寄存器）  软件
⑤ 执行中断服务程序        软件
⑥ 恢复现场                软件
⑦ 开中断、中断返回（iret） 软件
```

前三条叫"隐指令"（implicit instruction）。

意思是：它们不是程序里的指令，是硬件在响应中断时自动做的一串动作。

408 常问："中断响应过程中，由硬件完成的是哪些？"

答案就是这三条。

```text
关中断
保存断点
引出中断服务程序
```

第③步靠什么"引出"？

靠中断向量（interrupt vector）。

```text
每个中断类型有一个编号
编号 → 中断向量表里的一项 → 服务程序的入口地址
```

现代机器上这张表叫 IDT（interrupt descriptor table）。

x86 上它由 `lidt` 指令装载，地址存在 IDTR 寄存器里。

**为什么要有向量表？**

因为中断来得太频繁，靠软件逐个比较是灾难。

一张表，一次查表，直接跳。

## 5. 容易混淆的点

### 5.1 系统调用是异常，不是中断

```text
外中断：外部设备 → CPU
异常：  CPU 执行指令 → CPU 自己
系统调用：CPU 执行 trap 指令 → CPU 自己
```

所以系统调用归在异常里，具体说是 trap。

408 有时会问"系统调用的过程涉及哪种中断"。

答案：陷入（trap），属于内中断/异常。

### 5.2 缺页是故障，不是陷入

缺页由"访问了不在内存的页"引起。

不是程序主动的，所以不是 trap。

它可能被修复，所以是 fault。

```text
trap：主动、返回下一条
fault：被动、返回当前条（重试）
```

### 5.3 中断处理程序运行在内核态

哪怕触发它的是用户程序。

```text
用户程序执行 int3 → 断点异常 → CPU 切到内核态 → 内核处理
```

处理期间用的是内核栈，不是用户栈。

### 5.4 关中断不等于屏蔽所有中断

```text
cli 关的是"可屏蔽中断"
NMI（不可屏蔽中断）、异常、系统调用 都不受影响
```

教材会说"关中断"能保证原语不被打断。

严格说，保证的是"不被可屏蔽的外中断打断"。

### 5.5 用户态不能关中断

`cli` 是特权指令。

用户态执行会触发 #GP。

不然任何程序都能让时钟停下来，调度器就废了。

## 6. 408 怎么考

这一篇对应概述部分的运行环境：内核态、特权指令、中断与异常、系统调用、内核结构、引导、虚拟机。

题型四类。

```text
① 判断哪些指令是特权指令（选择题，几乎年年有）
② 判断某个事件属于中断还是异常、属于哪一类异常
③ 系统调用的完整过程（顺序、参数传递、返回）
④ 内核态 / 用户态的转换判断（哪些操作会引起切换）
⑤ 内核结构匹配（分层 / 模块化 / 微内核 / 外核 的优缺点）
⑥ 引导顺序、虚拟机类型
```

四条套路。

**套路一：特权指令按"改全局"筛。**

```text
改 CPU 状态、改内存映射、碰设备、碰时钟 → 特权
只算数、只访存、只跳转、只敲门       → 非特权
```

**套路二：中断分类看来源。**

```text
来源是设备/时钟 → 中断
来源是"这条指令" → 异常
程序主动 int/syscall → 陷入
```

**套路三：内核态判断看"有没有碰到硬件或全局资源"。**

```text
缺页处理、中断处理、系统调用、进程切换 → 内核态
用户程序计算、用户态库函数            → 用户态
```

**套路四：库函数不等于系统调用。**

```text
strlen / memcpy：纯用户态
read / write / open：系统调用（可能被库函数包装）
printf：库函数，内部可能调用 write
```

### 6.1 例题一：判断

自拟，按真题风格。

```text
下列操作中，一定在核心态执行的是：

Ⅰ. 关中断
Ⅱ. 读时钟
Ⅲ. 从内存取一条指令
Ⅳ. 修改页表基址寄存器
Ⅴ. 执行 trap 指令
Ⅵ. 响应键盘中断

A. Ⅰ、Ⅱ、Ⅳ、Ⅵ
B. Ⅰ、Ⅳ、Ⅵ
C. Ⅰ、Ⅱ、Ⅳ、Ⅴ、Ⅵ
D. 全部
```

逐条看。

Ⅰ 关中断：写 PSW 的中断允许位，特权。核心态。

Ⅱ 读时钟：读时钟值本身不敏感，但"设置时钟"才是特权指令。

读时钟在用户态能做（读 TSC 或 vDSO）。所以Ⅱ不一定在核心态。

Ⅲ 取指令：任何态都要取指令。非特权。

Ⅳ 改页表基址：改地址映射，绝对特权。

Ⅴ 执行 trap 指令：它必须能在用户态执行，否则进不去内核。

Ⅵ 响应键盘中断：中断响应后必然进内核。

答案 B。

这道题三个坑：Ⅱ 的"读"和"设置"、Ⅴ 的"执行"和"处理"、Ⅲ 的显然性。

**记法：程序主动发起陷入是在用户态，处理陷入是在核心态。**

### 6.2 例题二：算系统调用的开销

自拟。

```text
某系统一次 write 系统调用平均耗时 1.5 μs。
其中：
  模式切换（保存/恢复现场、切栈）0.4 μs
  内核实际处理               1.1 μs

某程序每秒执行 20 万次 write。

求：
(1) 每秒花在 write 上的 CPU 时间
(2) 其中模式切换占 CPU 的比例
(3) 若把多次小 write 合并成一次大 write，
    调用次数降到 4 万次，CPU 时间降到多少？
```

(1) 

```text
20 万 × 1.5 μs = 200000 × 1.5e-6 s = 0.3 s
```

每秒 0.3 秒，占用 30% 的 CPU。

(2)

```text
模式切换总量 = 200000 × 0.4 μs = 0.08 s
占 CPU 比例  = 0.08 / 1.0 = 8%
（占 write 时间的比例 = 0.4 / 1.5 ≈ 26.7%）
```

这里要分清两个分母：

```text
占"总 CPU 时间" = 8%
占"write 时间"   = 26.7%
```

题目问哪个，答案不一样。

(3)

```text
4 万 × 1.5 μs = 40000 × 1.5e-6 = 0.06 s
```

从 0.3 s 降到 0.06 s，省了 80%。

**这就是"缓冲"存在的经济理由。**

不是省磁盘，是省过边界的次数。

## 7. 真实系统里长什么样

### 7.1 四个环，用了两个

x86 定义了 ring 0 到 ring 3。

Linux 只用 ring 0（内核）和 ring 3（用户）。

```text
CPL = CS 寄存器的最低 2 位
```

用户程序想读自己的 CPL，可以执行 `mov %cs, %ax`。

它读出来是 3。

### 7.2 陷入指令换过三代

```text
int 0x80    ：32 位时代的老接口，走中断门，慢
sysenter    ：Intel 的快速系统调用（32 位后期）
syscall     ：x86-64 的标准，AMD 提出，Intel 跟进
```

`syscall` 快在哪？

```text
int 0x80 要查 IDT、要压栈、要做权限检查
syscall  直接从 MSR 取入口，不查表，不压栈
```

代价是它不保存栈指针，得由内核自己切。

所以内核入口前几条指令是手写汇编。

### 7.3 系统调用表是个数组

Linux 内核里：

```c
/* 简化示意，不是真实源码 */
asmlinkage long sys_write(unsigned int fd, const char __user *buf, size_t count);
...
void *sys_call_table[] = {
    [0] = sys_read,
    [1] = sys_write,
    [2] = sys_open,
    ...
};
```

`rax` 里放的是下标。

下标越界，内核直接返回 `-ENOSYS`。

**用户程序能控制的，只是一个数组下标。**

这是系统调用设计里最重要的一条安全约束：

```text
参数可以随便传，但入口只能从表里挑。
```

### 7.4 参数怎么传

x86-64 的约定：

```text
rdi、rsi、rdx、r10、r8、r9   → 六个参数
rax                          → 调用号（进）、返回值（出）
```

超过六个怎么办？

压栈，或者传一个结构体指针。

Linux 的做法是"寄存器为主，指针兜底"。

比如 `clone` 有五个参数，全走寄存器。

`select` 的参数是一个 `fd_set` 指针，走指针。

### 7.5 xv6 的做法

xv6 是教学用内核，能看清全貌。

```text
用户态：usys.S 里每个系统调用是一小段汇编
        mov $SYS_write, %eax
        int $0x40
        ret

内核态：struct trapframe 保存 15 个寄存器的现场
        syscall() 按 %eax 分发
        argint / argstr / argptr 从 trapframe 里取参数
```

注意 xv6 用的是 `int $0x40`，不是 `syscall`。

因为它要简单，不要快。

**教学内核选的是"看得懂"，生产内核选的是"跑得快"。**

### 7.6 中断在真实系统里能看见

```text
$ cat /proc/interrupts
           CPU0       CPU1
  0:         27          0   IO-APIC   2-edge      timer
  1:          9          0   IO-APIC   1-edge      i8042
 16:       1234          0   IO-APIC  16-fasteoi   ehci_hcd
```

每一行一个中断源。

第一列是中断号，中间是每个 CPU 收到的次数。

`timer` 那一行的数字在涨，就是时钟中断在响。

```text
$ cat /proc/stat | head -1
cpu  123456 789 45678 9876543 1234 0 567 0
```

第四个数 idle 的增长，就是 CPU 睡觉的时间。

### 7.7 现代内核在"省中断"

时钟中断不是免费的。

每秒 1000 次（`CONFIG_HZ=1000`），每次都要进内核。

空闲的机器上，这些中断纯属浪费。

所以有了 NO_HZ 机制：

```text
CPU 空闲时，把周期时钟关掉
有事情要做了，再定一个一次性定时器
```

**连"叫醒内核"这件事本身，都在被优化。**

## 8. 系统调用：怎么合法越权

### 8.1 三个要素

```text
① 系统调用号：告诉内核"我要哪个服务"
② 陷入指令：把 CPU 从用户态切到内核态
③ 参数：告诉内核"具体做什么"
```

缺一不可。

只有号没有陷入指令，内核不知道你要干嘛。

只有陷入指令没有号，内核不知道该调哪个函数。

### 8.2 一次调用的完整路径

```text
用户程序
  │ ① 参数入寄存器 / 入栈 / 入内存块
  │ ② 调用号入 rax
  ▼
陷入指令（trap / syscall / int 0x80）
  │ ③ 硬件：切 CPL、切栈、跳入口
  ▼
内核入口（汇编）
  │ ④ 保存现场到 trapframe / pt_regs
  ▼
系统调用分发器
  │ ⑤ 检查号是否合法
  │ ⑥ 查表 → 具体处理函数
  ▼
具体处理函数
  │ ⑦ 校验参数（用户指针能不能读）
  │ ⑧ 干活
  ▼
返回路径
  │ ⑨ 返回值放 rax
  │ ⑩ 恢复现场、iret
  ▼
用户程序继续
```

第⑦步是安全的关键。

用户传进来的指针可能指向内核空间，也可能是野指针。

所以每个系统调用都要 `copy_from_user` 这类检查。

**内核不相信用户传进来的任何东西。**

### 8.3 参数传递的三种方式

```text
① 寄存器传递
   参数直接放通用寄存器
   优点：最快，不用访存
   缺点：寄存器数量有限（x86-64 六个）
   现实：Linux 主要用这个

② 栈传递
   参数压在用户栈上，寄存器传栈指针
   优点：参数数量不受限
   缺点：要多一次访存，还要校验栈指针
   现实：部分体系结构、部分老接口

③ 块传递
   参数打包成一个结构体放内存，寄存器传结构体地址
   优点：参数可以很多、可以嵌套
   缺点：多一次间接访存
   现实：参数特别多的调用（如 clone 的某些变体、select）
```

三种方式可以混用。

408 只考"有哪三种、各自优缺点"，不考具体寄存器名。

### 8.4 返回值和错误

```text
成功：rax = 结果（非负）
失败：rax = -errno（负值）
```

glibc 的包装函数会把负值翻译成：

```text
返回值 -1
同时设置全局变量 errno
```

所以你在 C 里看到的是：

```c
ssize_t n = write(fd, buf, 3);
if (n == -1) {
    perror("write");   // 打印 errno 对应的文字
}
```

`-1` 是库函数给的，不是内核给的。

内核给的是 `-EPIPE` 这样的负数。

### 8.5 为什么不能直接调内核函数

用户程序知道 `sys_write` 的地址，能不能直接 `call`？

不能。

```text
① 地址空间隔离：内核映射在用户态不可访问的页里
② 特权级：就算能跳过去，内核代码里有特权指令，CPL=3 执行会 #GP
③ 栈：内核用自己的栈，用户栈不可信
```

三条，任意一条就够拦住。

**系统调用是唯一合法的门。**

## 9. 库函数不是系统调用

这是最容易被"用久了就忘了"的一组区别。

```text
库函数（library function）：运行在用户态，是普通函数调用
系统调用（system call）：  进内核，是特权级切换
```

三类库函数。

```text
① 纯用户态：strlen、memcpy、strcmp、qsort
   完全不碰内核

② 系统调用的薄包装：open、read、write、close
   里面就一条 syscall 指令 + 错误处理

③ 带缓冲的复合体：printf、fwrite、malloc
   平时在用户态攒着，攒够了才进内核
```

`printf` 是最好的例子。

```c
printf("hi");     // 没有换行
sleep(10);        // 睡 10 秒
```

猜猜这 10 秒里，屏幕上有没有 `hi`？

没有。

因为 stdout 连终端时是**行缓冲**：

```text
遇到 \n 才 flush
缓冲区满（通常 4 KB 或 8 KB）才 flush
```

`"hi"` 两个字节，既没换行也没满，就躺在用户态的缓冲区里。

进程退出时才 flush 出来。

再看重定向：

```text
$ ./a.out > out.txt
```

这时 stdout 不是终端，是文件。

缓冲策略从行缓冲变成**全缓冲**。

行为和刚才又不一样。

**同一个 `printf`，行为取决于它连到哪里。**

`strace` 能看清这一层：

```text
$ strace -e trace=write ./a.out
write(1, "hi\n", 3) = 3
```

你数一下，`printf("hi\n")` 只产生了一次 `write`。

如果你写：

```c
printf("a");
printf("b");
printf("c\n");
```

`strace` 里依然只有一次 `write(1, "abc\n", 4)`。

三次库函数调用，一次系统调用。

**这就是缓冲的价值：把 N 次过边界，压成 1 次。**

## 10. 内核结构：四种装法

内核不是只有一种形状。

四种典型结构，各有取舍。

### 10.1 分层

```text
┌──────────────────────┐
│ 用户程序              │
├──────────────────────┤
│ 第 n 层：文件系统      │
├──────────────────────┤
│ ...                  │
├──────────────────────┤
│ 第 2 层：内存管理      │
├──────────────────────┤
│ 第 1 层：硬件抽象      │
└──────────────────────┘
```

规则：第 k 层只能用第 k-1 层的接口。

优点：

```text
结构清晰，好调试，好验证
某一层改实现，不影响上层
```

缺点：

```text
每层调用都要穿一层，开销累积
层次怎么划分很难定（文件系统要不要依赖内存管理？）
```

### 10.2 模块化

内核是一个大程序，但按功能拆成模块。

```text
核心模块 + 可加载模块（.ko）
模块之间通过明确的接口调用
```

优点：

```text
灵活：要什么加载什么
可扩展：加驱动不用重编内核
```

缺点：

```text
模块之间没有强隔离，一个模块崩了整个内核崩
接口约定靠人守，容易腐化
```

Linux 属于这一类：单内核 + 模块。

### 10.3 微内核

思路相反：能挪出去的全挪出去。

```text
内核里只留：
  进程调度
  基本内存管理
  进程间通信（IPC）

挪到用户态：
  文件系统
  设备驱动
  网络协议栈
```

优点：

```text
可靠：一个服务崩了，重启它就行，内核不动
安全：攻击面小
可扩展：加服务等于加进程
```

缺点：

```text
性能：一次文件读，变成好几次 IPC
每个 IPC 都是模式切换 + 消息拷贝
```

代表：Mach、QNX、L4。

**微内核的性能问题，是它几十年没赢的主要原因。**

### 10.4 外核

更激进：内核只负责"分配物理资源"，连抽象都不做。

```text
内核给：物理页、磁盘块、CPU 时间片
用户态库 OS 负责：把这些拼成虚拟内存、文件系统
```

优点：

```text
抽象可以按应用定制（数据库要的抽象和浏览器不一样）
少一层映射，减少开销
```

缺点：

```text
库 OS 太复杂
应用之间难共享，兼容性差
```

代表：MIT 的 exokernel（研究项目）。

### 10.5 怎么记

```text
分层    → 用"层次"换"性能"
模块化  → 用"隔离"换"灵活"（其实隔离也不多）
微内核  → 用"性能"换"可靠"
外核    → 用"兼容"换"灵活"
```

408 的考法是给一段描述，问是哪种结构。

抓住关键词：

```text
"只能调用相邻层"      → 分层
"可动态加载"          → 模块化
"服务运行在用户态"    → 微内核
"只分配物理资源"      → 外核
```

## 11. 内核怎么被装起来：从通电到 main

内核是躺在磁盘上的一个文件。

谁把它读进内存？

答案是引导程序（bootloader）。

它自己也是一段代码，谁把它读进来？

答案是固件（BIOS / UEFI）。

层层往下，最后落到"CPU 一上电从哪个地址取指"。

### 11.1 完整链路

```text
① 加电
   CPU 复位，从固定地址取第一条指令
   x86 上是 0xFFFFFFF0（实模式下映射到 ROM）

② 固件自检
   BIOS/UEFI 做 POST（上电自检）：测内存、枚举设备

③ 找引导设备
   按启动顺序找：硬盘、U 盘、网络
   读该设备的第一个扇区（512 字节）

④ 检查引导标志
   最后两个字节是 0x55AA → 认为这是一个引导扇区

⑤ 执行引导程序
   MBR 里的代码（446 字节）或者 UEFI 的 .efi 文件
   它知道怎么读文件系统，于是能读 /boot 里的内核

⑥ 加载内核
   把内核镜像读进内存，可能还有 initrd/initramfs
   跳到内核入口

⑦ 内核初始化
   建立页表、初始化中断、初始化驱动、挂载根文件系统
   起第一个进程（init 或 systemd，PID 1）
```

### 11.2 MBR 里为什么只有 446 字节

```text
512 字节的扇区：
  446 字节  引导代码
   64 字节  分区表（4 项 × 16 字节）
    2 字节  0x55AA
```

446 字节装不下文件系统驱动。

所以 MBR 代码只干一件事：把后续的引导程序（GRUB 的 stage1.5/2）读进来。

这叫多阶段引导。

**UEFI 时代不需要这套了。**

UEFI 自带 FAT 驱动，能直接读 ESP 分区里的 `.efi` 文件。

```text
/boot/efi/EFI/ubuntu/grubx64.efi
```

一个文件，一步到位。

### 11.3 408 怎么考引导

```text
① 顺序：BIOS → 引导块 → 引导程序 → 内核
② 引导块在哪：磁盘第一个扇区
③ 引导程序的作用：把内核读进内存并跳过去
④ 分区引导记录 vs 主引导记录
```

一句话记：

```text
固件认扇区，引导程序认文件系统，内核认设备。
```

三级跳，每一级都比上一级"懂得多"。

## 12. 再套一层：虚拟机

### 12.1 两类虚拟机

```text
第一类（bare-metal / Type-1）：
  hypervisor 直接跑在硬件上，是"最底层的操作系统"
  例：Xen、VMware ESXi、Hyper-V

第二类（hosted / Type-2）：
  hypervisor 跑在宿主操作系统上，是一个应用
  例：VirtualBox、VMware Workstation、QEMU
```

差别在"谁管硬件"。

```text
Type-1：硬件 → hypervisor → guest OS
Type-2：硬件 → host OS → hypervisor → guest OS
```

Type-2 多一层，所以慢一点，但装起来方便。

### 12.2 难点在哪

虚拟机要模拟"完整的机器"，包括特权级。

问题来了：

```text
guest OS 以为自己在 ring 0，要执行特权指令
但它其实是宿主上的一个用户态进程（ring 3）
```

怎么办？

两种思路。

**思路一：特权级压缩（ring deprivileging）**

```text
guest 的 ring 0 被"降级"到宿主 ring 1 或 ring 3
guest 执行特权指令 → 触发异常 → hypervisor 捕获 → 模拟执行
```

这叫"陷入-模拟"（trap and emulate）。

**思路二：二进制翻译**

```text
hypervisor 扫描 guest 的代码
把特权指令替换成"调用 hypervisor"的指令
```

不靠硬件异常，靠改写代码。

### 12.3 敏感指令问题

有一类指令叫敏感指令（sensitive instruction）：

```text
读或写特权状态，但在用户态执行时"不报错，只是行为不同"
```

比如读时钟、读 IDT 基址。

这类指令没法靠"陷入"捕获，因为它不陷入。

早年的 x86 就有这个毛病（叫"关键指令不敏感"问题）。

解决办法是硬件辅助：

```text
Intel VT-x / AMD-V
  新增 VMX root / non-root 两种模式
  guest 跑在 non-root，敏感操作自动 VM exit
```

**硬件一出手，软件模拟的补丁就不需要了。**

### 12.4 408 怎么考

```text
① 第一类/第二类的区别（谁直接管硬件）
② 虚拟机与模拟器的区别（同架构/跨架构）
③ 特权指令在虚拟机里怎么处理（陷入模拟）
④ 虚拟化的两个条件（等价、性能、安全 —— 常说的三个充分条件）
```

一句话记：

```text
虚拟机监控器做的事，
就是把"内核态"这件事，在软件层再实现一遍。
```

## 13. 小结

这一篇的骨架：

```text
一条分界线：特权指令 / 非特权指令
一个开关：PSW 或 CPL
三条入口：中断、异常、系统调用
五个步骤：关中断、存断点、引服务、存现场、恢复
三种参数：寄存器、栈、块
四种内核：分层、模块化、微内核、外核
一条引导链：固件 → 引导块 → 引导程序 → 内核
两类虚拟机：Type-1、Type-2
```

如果只记一句话：

```text
操作系统的权力来自硬件，
它的运行由中断驱动，
它的接口只有系统调用一个门。
```

这三句对应三种题型：

```text
特权指令判断
中断分类
系统调用过程
```

```text

```

```text
CPU 只有一个，多个程序怎么"同时"跑？

```

还有一个反直觉的答案：

```text
进程切换最贵的不是保存寄存器，
```
