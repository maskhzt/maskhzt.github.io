先看一段代码。

生产者-消费者，缓冲区 4 个槽。

```c
P(empty);
P(mutex);
buffer[in] = item;
in = (in + 1) % 4;
V(mutex);
V(full);
```

少了最后那个 `V(full)`。

编译器不报错，测试跑得通，压测两天才停。

停的时候现象是「消费者不再消费」，日志里什么都没有。

这就是 PV 的麻烦之处。

```text
互斥和同步，全靠程序员手动写在正确的行、正确的顺序上。
写对是运气，写错不报错。
```

有没有一种写法，让「漏一个 V」这件事在语法上不可能发生？

有。

思路是把加锁这件事，从程序员的活变成编译器的活。

**这一篇讲的就是这个思路：管程（monitor）。**

## 1. 管程要解决的两个麻烦

PV 代码的麻烦有两个，不是三个。

```text
① 互斥要手写：每个过程开头 P(mutex)，结尾 V(mutex)。
② 顺序要手排：同步 P 和互斥 P 谁先谁后，错了就死锁。
```

第一个麻烦可以自动化。

既然临界区永远是「进过程、干活、出过程」，那就让语言来加锁。

```text
进入管程 → 自动加锁
离开管程 → 自动解锁
```

第二个麻烦没法自动化，但可以换个说法。

不再问「谁先 P 谁后 P」，改成问：

```text
「条件不满足的时候，我先出去等一会儿，等条件变了再回来。」
```

于是有了条件变量。

```text
管程解决「谁在什么时候能进来」。
条件变量解决「进来以后发现条件不满足，怎么出去等」。
```

两件事，两个部件。

## 2. 管程的四个部件

管程（monitor）是一个语言层面的结构，写法像类。

四个部件缺一不可。

```text
① 共享数据：只能通过管程的过程访问，外面看不见。
② 一组过程：进入管程的唯一入口。
③ 初始化代码：管程创建时执行一次。
④ 条件变量：过程内部用来等待的队列。
```

```text
monitor BoundedBuffer {
    /* ① 共享数据 */
    int buffer[N];
    int count = 0, in = 0, out = 0;

    /* ④ 条件变量 */
    condition not_full, not_empty;

    /* ② 过程 */
    void put(int item) { ... }
    int  get()        { ... }

    /* ③ 初始化：count = 0, in = 0, out = 0 */
}
```

结构图。

```text
        ┌──────────────── 管程 BoundedBuffer ─────────────────┐
        │  入口：隐式互斥，一次只放一个进程进来                 │
        │                                                     │
        │   ┌─────────────────────────────────────────────┐   │
        │   │ 共享数据  buffer[]  count  in  out          │   │
        │   │ 过程      put()  get()                       │   │
        │   │ 条件变量  not_full    not_empty              │   │
        │   └─────────────────────────────────────────────┘   │
        │                                                     │
        │  出口：离开时自动释放互斥                             │
        └─────────────────────────────────────────────────────┘
             ▲                                        ▲
             │ 生产者 put()                            │ 消费者 get()
```

三条要读准。

```text
共享数据外面直接看不见 → 这叫封装，也是管程能做保护的前提。
互斥不是过程里写的 → 是「进入管程」这个动作自带的。
条件变量不是计数器 → 它是一个等待队列，本身不保存任何「还剩几个」。
```

最后一条最容易记错。

```text
条件变量没有值。
它只有两个操作：wait 和 signal。
```

## 3. 管程的三条语义

教材上说的管程语义，就三句。

### 3.1 一次只有一个进程在管程内执行

```text
任何时刻，最多一个进程在管程的某个过程里跑。
别的进程来了，在管程入口排队。
```

这是管程和类最本质的区别。

```text
类：多个线程可以同时调用同一个对象的多个方法。
管程：不行，一次只进一个。
```

谁来保证？

```text
编译器（或者运行时）在过程入口插一对加锁/解锁。
程序员不需要写，也写不出来。
```

实现上就是一把隐藏的 mutex。

```text
进入过程：lock(monitor_lock)
离开过程：unlock(monitor_lock)
条件变量 wait：在该锁上「原子地解锁并挂起」
```

关键在于「隐藏」。

```text
信号量版的 mutex 是全局变量，谁都能 P 错、V 错、忘掉。
管程版的 mutex 没有名字，也就没法被写错。
```

### 3.2 进程主动放弃管程

```text
管程的互斥没有「时间片到就被踢出去」这一说。
只有三种情况会放行：
  ① 过程执行完毕，正常返回。
  ② 调用 wait，主动去条件变量上等。
  ③ 过程里抛出异常，退出管程。
```

第二点是关键。

```text
wait 的时候，进程必须先把管程的互斥放掉，否则谁也别想进来改条件。
```

所以 `wait` 做的是两件事，而且必须是原子的。

```text
① 释放管程的互斥。
② 把自己挂到该条件变量的等待队列上。
```

这条语义还有一个直接后果。

```text
管程里不能睡。写 sleep 就等于抱着锁睡觉，整个管程停摆。
要等，只能用 wait。
```

### 3.3 条件变量上等待与唤醒

```text
wait(cv)    ：释放管程，进入 cv 的等待队列。
signal(cv)  ：唤醒 cv 队列里的一个进程（如果有）。
```

状态图画出来是这样。

```text
              进入过程 put() / get()
                     │
                     ▼
           ┌───────────────────┐   wait(cv)    ┌──────────────────┐
           │  管程内执行        │ ────────────▶ │  cv 的等待队列    │
           │  （持有隐式互斥）  │ ◀──────────── │  （已释放互斥）   │
           └─────────┬─────────┘  signal 唤醒   └──────────────────┘
                     │
                     │ 过程返回
                     ▼
              离开管程（释放互斥）
```

注意那个箭头是双向的。

```text
被 signal 唤醒的进程，要重新回到管程里。
但「回到管程」这一步，可能要再排一次队。
```

为什么？

因为唤醒它的时候，管程里可能已经有人了。

这一点在 Hoare 和 Mesa 两种语义下表现不同，第 5 节细说。

## 4. 用管程写生产者-消费者

同样的问题，换成管程的写法。

```c
monitor BoundedBuffer {
    int buffer[N];
    int count = 0, in = 0, out = 0;
    condition not_full, not_empty;

    void put(int item) {
        while (count == N) {
            not_full.wait();          // 满了，先出去等
        }
        buffer[in] = item;
        in = (in + 1) % N;
        count++;
        not_empty.signal();           // 有货了，叫醒一个消费者
    }

    int get() {
        while (count == 0) {
            not_empty.wait();         // 空了，先出去等
        }
        int item = buffer[out];
        out = (out + 1) % N;
        count--;
        not_full.signal();            // 有空位了，叫醒一个生产者
        return item;
    }
}
```

调用方的代码。

```c
void producer() {
    while (1) {
        int item = produce();
        BoundedBuffer.put(item);      // 只管调用，不写 P/V
    }
}

void consumer() {
    while (1) {
        int item = BoundedBuffer.get();
        consume(item);
    }
}
```

对比一下两种写法。

```text
信号量版：3 个信号量在过程外面，P/V 由调用方和实现方共同维护。
管程版：0 个信号量，互斥在入口，同步在两个条件变量上。
```

代码量少了一半，而且没有地方能「漏一个 V」。

```text
V 被换成了 signal。
signal 少的后果是「变慢」，不是「卡死」——这点第 5 节讲。
```

### 4.1 为什么是 while 不是 if

几乎所有人第一次写都会写成 `if`。

```c
if (count == N) {
    not_full.wait();
}
```

这样写，在 Mesa 语义下是错的。

原因是一条时间线。

```text
① 生产者 P1 发现 count == N，wait，出去了。
② 消费者取走一个产品，count 变 N-1，signal，唤醒 P1。
③ 但 P1 还没真正进来，另一个生产者 P2 抢先进入管程，
   把空位填了，count 又回到 N。
④ P1 终于进来，从 wait 的下一句继续。
```

如果当初写的是 `if`：

```text
P1 不会再看一眼 count。
它直接往下执行 buffer[in] = item。
缓冲区已经满了 → 覆盖数据，或者下标错乱。
```

如果写的是 `while`：

```text
P1 回到循环顶部，再判断一次 count == N。
成立 → 再 wait 一次，继续等。
不成立 → 才往下走。
```

```text
while 是「醒来以后重新检查」，if 是「醒来就当条件成立」。
```

后者在单核、无竞争的实验室环境里跑一万次都不出错。

```text
这就是并发 bug 的典型形状：测试通过，线上偶发。
```

### 4.2 一次完整走查

N = 2，初始 `count = 0, in = 0, out = 0`。

先让两个消费者来取。

```text
C1 调 get()：进管程，count == 0 → not_empty.wait()，出管程，挂在 not_empty
C2 调 get()：进管程，count == 0 → not_empty.wait()，出管程，挂在 not_empty
此时：count = 0，not_empty 队列有 2 个，not_full 队列有 0 个
```

生产者放两个产品。

```text
P 调 put(A)：
  进管程，count(0) != 2，不等待
  写入 buffer[0]，in = 1，count = 1
  not_empty.signal() → 唤醒 C1
  返回，出管程

P 调 put(B)：
  进管程，count(1) != 2，不等待
  写入 buffer[1]，in = 0，count = 2
  not_empty.signal() → 唤醒 C2
  返回，出管程
```

现在 `count = 2`，缓冲区满。

被唤醒的 C1、C2 各自取走一个。

```text
C1：count 2 → 1，out = 1，not_full.signal()（队列空，没人可唤醒，这次 signal 消失）
C2：count 1 → 0，out = 0，not_full.signal()（同样消失）
```

最终状态。

```text
count = 0
not_empty 队列：0 个（C1、C2 都已被唤醒，产品也取走了）
not_full  队列：0 个
```

那两次 `not_full.signal()` 都是空放。

```text
队列里没有人，signal 就什么也没发生。
它不是「攒下来以后用」。
```

如果把题目改成「三个消费者先到，生产者只放一个」：

```text
C1、C2、C3 全在 not_empty 上等
P 放一个产品，count = 1，not_empty.signal() 唤醒 C1
C1 取走唯一的产品，count 回到 0，not_full.signal() 空放
最终：count = 0，not_empty 上还有 2 个等待者（C2、C3）
```

注意这一问和上一问的最终 `count` 都是 0。

```text
count = 0 说明不了「没人在等」。
状态变量和等待队列是两回事。
```

这一句就是下一节的主题。

### 4.3 signal 该放在哪一行

看 `put` 的三行结尾。

```c
count++;
not_empty.signal();
```

顺序不能反。

```text
先改状态，再叫醒。
被唤醒的进程一进来就会检查 count，如果 count 还没加，它会立刻又睡回去。
```

也不能挪到管程外。

```text
过程返回之后再 signal，这一次 signal 大概率丢：
中间可能已经有别的生产者把缓冲区又填满了。
```

所以规矩是两条。

```text
① 先改状态变量，后 signal。
② signal 在过程内、临界区内。
```

这两条，就是「条件变量必须配状态变量」的工程版本。

## 5. 条件变量和信号量的区别

这是本篇最容易考、也最容易记混的地方。

三个区别，按重要性排。

### 5.1 区别一：条件变量没有值

```text
信号量：是一个整数。P 减一，V 加一。值可以为负，负数的绝对值是等待者数量。
条件变量：没有整数。只有 wait 和 signal 两个操作，以及一个等待队列。
```

后果很直接。

```text
信号量能「记住」事件：没人等的时候 V 一次，值变成 1，以后来的人直接通过。
条件变量记不住：没人等的时候 signal 一次，这次 signal 就消失了。
```

所以条件变量必须配一个「状态变量」一起用。

```text
not_empty 只是「提醒」，真正记录状态的是 count。
signal 丢了不要紧，因为 wait 的外层 while 会去检查 count。
```

反过来，如果只靠 signal 不看 count：

```text
生产者先放了一个产品，signal，此时没有消费者在等 → signal 消失。
消费者随后才来，看到 count == 1，根本不需要等。
```

这个例子里没出问题，恰恰是因为**判断条件用的是 count，不是 signal**。

```text
条件变量负责「叫醒」，状态变量负责「记住」。
把这两件事混在一起，就会写出「明明 signal 了却还是卡住」的代码。
```

### 5.2 区别二：signal 无人等待就会丢失

信号量的 V 不会丢。

```text
V 的时候没人等 → 值加一，留着。
```

条件变量的 signal 会丢。

```text
signal 的时候没人等 → 什么都不发生。
```

这一条差异，决定了两种结构的写法不同。

```text
用信号量：可以先 V 后 P，顺序无所谓，值兜住了。
用条件变量：必须先判断条件，再 wait；signal 只是顺手叫一声。
```

举个一分钟就能看懂的例子。

```text
场景：消费者先 signal 一次（此时没人等），然后才 wait。

信号量版：
  V(full) → full = 1
  P(full) → full = 0，直接通过，不需要任何人再 V 一次

条件变量版：
  not_empty.signal() → 队列空，什么都没发生
  not_empty.wait()   → 真睡下去了，没有人能叫醒它
```

同一个意图，两种结果。

```text
信号量把「事件」存进了值里。
条件变量什么都没存，事件当场蒸发。
```

所以条件变量版本的代码里，那个 `while (count == 0)` 是保命的。

```text
它保证了：睡下去之前一定再确认一次状态。
signal 丢了没关系，因为 wait 的外层循环本来就要检查真实状态。
```

再看 `wait` 和 `P` 的差别。

```text
P(mutex)：只减一，不释放任何别的东西。
wait(cv) ：必须持有管程的互斥，然后「释放互斥 + 挂起」两步原子完成。
```

`wait` 的这条约束经常被违反。

```text
不持锁就 wait → 未定义行为，或者直接抛异常。
Java 里是 IllegalMonitorStateException。
```

### 5.3 区别三：Hoare 语义和 Mesa 语义

`signal` 唤醒了一个等待者，接下来谁跑？

两种答案。

```text
Hoare 语义：signal 之后立即切换。
            被唤醒者马上进管程，signal 者让出管程（进入 urgent 队列）。
            保证被唤醒者醒来时，条件一定还成立。

Mesa 语义：signal 之后不切换。
           signal 者继续执行，直到它退出管程。
           被唤醒者只是变成「就绪」，之后重新竞争管程。
```

画出来。

```text
Hoare：
  P: ... count-- ; signal(not_full) ──┐
                                      │ 立即切换
  C: 被唤醒 ──▶ 进入管程 ──▶ 继续执行  │
                                      │
  P: 等 C 让出管程 ◀──────────────────┘

Mesa：
  P: ... count-- ; signal(not_full) ; 继续执行 ; 退出管程
  C: 被唤醒 ──▶ 变成就绪 ──▶ 排队 ──▶ 等 P 退出后才进管程
```

这直接决定了要不要 `while`。

```text
Hoare：被唤醒时条件必然成立，用 if 也勉强能对。
Mesa ：被唤醒时条件可能已被别人改掉，必须用 while 复查。
```

真实系统全是 Mesa。

```text
Java 的 wait/notify 是 Mesa。
POSIX 的 pthread_cond_signal 是 Mesa。
所以真实代码里，while 是硬规矩，不是风格问题。
```

Hoare 语义还有一个副作用。

```text
signal 者要让出管程，得有个地方待着 → 需要一个 urgent 队列。
两个队列（条件变量队列 + urgent 队列）在 408 里提过，真实系统里基本没人实现。
```

## 6. 408 怎么考

四种问法。

```text
① 判断：管程和信号量是不是功能等价？
② 判断：条件变量的 signal 在没有进程等待时会怎样？
③ 写代码：用管程写一个生产者-消费者 / 读者-写者。
④ 给一段 Java 或伪代码，问最终谁在等、某个变量的值。
```

前两种靠记，后两种靠推。

### 6.1 例题：算等待者

管程实现的有界缓冲区，N = 2，初始 `count = 0`，两个队列都空。

现在依次发生：

```text
C1 调 get()
C2 调 get()
C3 调 get()
P  调 put(A)
P  调 put(B)
```

问最终 `count` 是多少，`not_empty` 和 `not_full` 上各有几个等待者。

按顺序推。

```text
C1 get：count == 0 → not_empty.wait()       not_empty: [C1]
C2 get：count == 0 → not_empty.wait()       not_empty: [C1, C2]
C3 get：count == 0 → not_empty.wait()       not_empty: [C1, C2, C3]

P put(A)：count 0 != 2，写入，count = 1
          not_empty.signal() → 唤醒 C1      not_empty: [C2, C3]

P put(B)：count 1 != 2，写入，count = 2
          not_empty.signal() → 唤醒 C2      not_empty: [C3]
```

现在 `count = 2`，缓冲区满，`not_empty` 上还有 C3。

C1 和 C2 被唤醒后各取走一个。

```text
C1：count 2 → 1，not_full.signal()（队列空，丢弃）
C2：count 1 → 0，not_full.signal()（队列空，丢弃）
```

答案：

```text
count = 0
not_empty 上 1 个等待者（C3）
not_full  上 0 个等待者
```

再补一问：如果 P 只调了一次 `put` 呢？

```text
C1 被唤醒取走唯一的产品，count 回到 0
C2、C3 仍在 not_empty 上等

答案：count = 0，not_empty 上 2 个等待者，not_full 上 0 个
```

注意这两问里 `count` 都是 0。

```text
所以「count == 0」说明不了「没人在等」。
状态和等待队列是两回事，这正是条件变量和信号量最容易混的地方。
```

### 6.2 例题：判断对错

三句判断，逐句看。

**「管程和信号量功能等价。」**

对。

```text
管程能做的，用「一把 mutex + 一个状态变量 + 一个等待队列」都能做。
反过来，管程的隐式互斥展开成 P/V，也是等价的信号量程序。
```

**「条件变量的 signal 在没有进程等待时会丢失。」**

对。

```text
条件变量没有值，不保存历史。
所以等待的一方必须用 while 复查状态变量，不能指望 signal 补上。
```

**「管程自带互斥，所以不需要条件变量。」**

错。

```text
互斥解决「不能同时进」。
它不解决「进不来的时候去哪儿」。
没有条件变量，等待的进程只能占着管程死等，比死锁还糟。
```

**「signal 之后，被唤醒的进程立刻开始执行。」**

错，至少不一定是。

```text
Hoare 语义下是。
Mesa 语义下不是：被唤醒者只是从条件变量队列挪到入口队列，还要重新竞争管程。
Java 和 pthread 都是 Mesa。
```

这三个判断的共同点：

```text
它们都在问「管程和信号量到底差在哪」。
答案集中在三处——有没有值、signal 会不会丢、唤醒后谁跑。
```

## 7. 真实系统里长什么样

> 以下是简化示意，接口名取自 Java 与 POSIX，内部实现有删减。

### 7.1 Java 的 synchronized 就是一个管程

```java
class BoundedBuffer {
    private final int[] buffer = new int[4];
    private int count = 0, in = 0, out = 0;

    public synchronized void put(int item) throws InterruptedException {
        while (count == buffer.length) {
            wait();                 // 等价于 not_full.wait()
        }
        buffer[in] = item;
        in = (in + 1) % buffer.length;
        count++;
        notifyAll();                // 等价于 signal
    }

    public synchronized int get() throws InterruptedException {
        while (count == 0) {
            wait();                 // 等价于 not_empty.wait()
        }
        int item = buffer[out];
        out = (out + 1) % buffer.length;
        count--;
        notifyAll();
        return item;
    }
}
```

对照关系很清楚。

```text
synchronized 方法  → 管程的过程（进入即持锁）
wait()             → 条件变量的 wait（释放锁 + 挂起）
notify()/notifyAll()→ 条件变量的 signal / broadcast
每个对象一个监视器  → 每个管程一个隐式互斥
```

但 Java 有一个硬限制。

```text
一个对象只有一个等待集。
没有「not_full 队列」和「not_empty 队列」之分。
```

后果就是 `notifyAll()`。

```text
notify() 随机叫一个，可能叫错人：
  生产者叫醒的是另一个生产者，缓冲区还是满的，它只好再 wait。
  被叫醒又睡回去，白跑一趟。

notifyAll() 叫醒全部，让它们自己用 while 复查：
  正确，但每次都有大量无效唤醒（惊群）。
```

工程上的标准解法是不用 `synchronized`，改用显式锁加两个条件。

```java
ReentrantLock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();
Condition notEmpty = lock.newCondition();
```

```text
这就是 java.util.concurrent 里 ArrayBlockingQueue 的做法。
它把「一个对象一个等待集」这个限制绕过去了，
等于手写了一个有两个条件变量的管程。
```

管程在 JVM 里的实现也值得一提。

```text
早期 synchronized 直接对应重量级的操作系统互斥量，很慢。
后来加了偏向锁、轻量级锁（CAS 自旋）等优化。
较新的 JDK 已经废弃了偏向锁——说明这套优化本身的收益在变小。
```

还有一条来自 Java 语言规范的硬规矩，值得单独记。

```text
wait / notify 必须在 synchronized 块里调用。
不在里面，直接抛 IllegalMonitorStateException。
```

这条规矩不是为了好看。

```text
wait 要做的事是「释放锁 + 挂起」，它必须先证明你确实持有那把锁。
不持锁就 wait，等于承诺要释放一个不属于你的东西。
```

而 `while` 那一条，Java 文档写得更直接。

```text
wait 可能在没有 notify、没有中断、没有超时的情况下自己醒来。
这叫虚假唤醒（spurious wakeup）。
```

虚假唤醒不是 bug，是允许的实现行为。

```text
线程库为了效率，可能在信号、调度、内存可见性上留下「多醒一次」的余地。
标准允许它发生，所以程序必须能扛住。
```

能扛住的写法只有一个。

```text
醒来 → 重新检查条件 → 不满足就再 wait。
这就是 while。
```

### 7.2 pthread 的 mutex + cond

POSIX 线程的写法是把管程拆成两个对象。

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  not_full  = PTHREAD_COND_INITIALIZER;
pthread_cond_t  not_empty = PTHREAD_COND_INITIALIZER;

void put(int item) {
    pthread_mutex_lock(&m);
    while (count == N) {
        pthread_cond_wait(&not_full, &m);   // 原子地：释放 m + 等待
    }
    buffer[in] = item;
    in = (in + 1) % N;
    count++;
    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&m);
}
```

`pthread_cond_wait` 的参数就是那条约束的证明。

```text
它必须同时拿到条件变量和互斥量。
因为它要做的事是「释放这把锁 + 睡在这个条件上」，两步必须原子。
```

返回值那边也一样。

```text
pthread_cond_wait 返回时，锁已经重新加上了。
所以返回之后可以直接访问受保护的变量。
```

底层实现是 futex。

```text
没有竞争时，加解锁全在用户态用原子指令完成，不进内核。
需要排队时，才通过 futex(FUTEX_WAIT) 挂起、futex(FUTEX_WAKE) 唤醒。
```

### 7.3 Linux 内核里没有「管程」

内核是 C，没有管程语法。

它用的是同一个思路的手工版本。

```c
wait_queue_head_t wq;      // 等待队列，相当于条件变量
struct mutex lock;         // 相当于管程的隐式互斥
```

内核还把它包成了宏。

```c
wait_event_interruptible(wq, condition);
```

这个宏展开以后，就是那个标准形状。

```text
while (!condition) {
    把当前进程加入 wq;
    设置状态为可中断睡眠;
    调度出去;
}
```

也就是：

```text
先判断条件，不满足才睡，醒来再判断。
——while 复查，一个都不能少。
```

内核里没有「条件变量 signal 丢失」的补救机制。

```text
因为它压根不靠 signal 传递状态，只靠 condition 这个表达式。
wake_up 只是「叫人来看一眼」，看不看得上还得自己判断。
```

这正好印证了 5.1 的那句话。

```text
条件变量负责叫醒，状态变量负责记住。
```

## 8. 用管程写读者-写者

同一个套路，换一个问题。

约束是「读者之间可以并发，写者与所有人互斥」。

用管程写，只有一把隐式互斥，所以要把「并发读」这件事显式表达出来。

```c
monitor RW {
    int reader_count = 0;      // 正在读的人数
    int writer_count = 0;      // 正在写的人数（0 或 1）
    condition ok_to_read;      // 可以开始读了
    condition ok_to_write;     // 可以开始写了

    void begin_read() {
        while (writer_count > 0) {
            ok_to_read.wait();         // 有人在写，等
        }
        reader_count++;
    }

    void end_read() {
        reader_count--;
        if (reader_count == 0) {
            ok_to_write.signal();      // 最后一个读者走了，放写者
        }
    }

    void begin_write() {
        while (writer_count > 0 || reader_count > 0) {
            ok_to_write.wait();
        }
        writer_count = 1;
    }

    void end_write() {
        writer_count = 0;
        ok_to_write.signal();          // 优先放写者（写者优先）
        ok_to_read.signal();           // 再放一个读者
    }
}
```

这里出现了管程独有的一个麻烦。

```text
管程一次只让一个进程进。
所以两个读者「同时读」这件事，在管程里根本表达不出来。
```

怎么办？

```text
管程只保护「进门登记」这一小段。
真正的读操作，放在管程外面做。
```

调用顺序就变成：

```c
reader() {
    while (1) {
        RW.begin_read();      // 进管程登记
        read_data();          // 管程外，真正的读，可以并发
        RW.end_read();        // 进管程注销
    }
}

writer() {
    while (1) {
        RW.begin_write();     // 进管程登记（顺带等条件）
        write_data();         // 管程外，独占
        RW.end_write();
    }
}
```

这一点和信号量版是一样的。

```text
信号量版：P(rw_mutex) 只保护「谁在读」的判定，读本身在临界区外。
管程版：管程只保护 reader_count / writer_count 的判定，读本身在管程外。
```

区别只在「谁加锁」。

```text
信号量版靠 readcount + mutex 两个变量互相配合。
管程版靠两个条件变量 + while 判断，形状更统一。
```

`end_write` 里那两句 signal 的顺序，就是优先级的旋钮。

```text
先 signal ok_to_write：写者优先。
先 signal ok_to_read ：读者优先。
两句都写：谁被唤醒看队列实现，通常不保证，所以别这么写。
```

## 9. 管程里其实有三种队列

教材画管程图时经常只画条件变量队列，会漏两个。

```text
① 入口队列（entry queue）：想进管程但进不去，在这里排。
② 条件变量队列（condition queue）：调了 wait，在这里等。
③ 紧急队列（urgent queue）：Hoare 语义下，signal 之后让出管程的进程在这里等。
```

三者的关系。

```text
到达 ──▶ 入口队列 ──▶ 进入管程（持锁）
                          │
                          ├── 正常返回 ──▶ 离开管程（放锁）
                          │
                          ├── wait ──▶ 条件变量队列（放锁）
                          │               │
                          │               └── 被 signal ──▶ 回入口队列（Mesa）
                          │                                 立即进入（Hoare）
                          │
                          └── signal 之后让出 ──▶ 紧急队列（只有 Hoare 有）
```

Mesa 语义下没有紧急队列。

```text
signal 之后，signal 者继续跑，被唤醒者从条件变量队列挪到入口队列。
它要重新竞争一次管程。
```

这一挪，就是「被唤醒不代表立刻执行」的物理原因。

```text
很多「明明 signal 了怎么还卡住」的疑惑，答案就在这条线上：
被唤醒者只是从条件队列挪到了入口队列，前面还排着人。
```

还有一条推论，很实用。

```text
管程默认不保证公平。
入口队列可以是 FIFO，也可以是「谁先抢到锁谁进」。
所以「先到先得」在管程里不是天然的。
```

要公平，得显式做。

```text
把入口队列做成 FIFO（例如 Java 的 ReentrantLock(true) 公平锁），
或者自己维护一个取号叫号的队列。
```

## 10. 管程和信号量，到底谁更强

结论先说。

```text
表达能力等价，编程难度不等价。
```

等价的一面。

```text
信号量 → 管程：把 P/V 藏进过程入口，把同步信号量换成「状态变量 + 条件变量」。
管程 → 信号量：每个条件变量用「一个信号量 + 一个计数器」模拟。
```

不等价的一面在「谁负责正确」。

```text
信号量：互斥和同步都是程序员的活。写错不报错。
管程：互斥是编译器的活，同步还是程序员的活，但同步只写 while + wait，形状固定。
```

换句话说：

```text
管程把「互斥」这件事的正确性，从人手里拿走了。
它没有把「条件判断」拿走——while 里那个条件还是你自己写。
```

这也解释了为什么管程写出来的 bug 类型变了。

```text
信号量版：漏 V、P 顺序反、mutex 保护错对象。
管程版：用了 if 没用 while、signal 错对象、条件写错。
```

少了一类，还剩一类。

```text
没有银弹。只是把容易犯的错，换成了更少的、更容易看出来的错。
```

补一个数字上的对比。

```text
一个有 4 个并发过程的信号量程序，
  互斥 P/V 要写 8 处，同步 P/V 至少 4 处，任何一处错都可能卡死。
同样功能的管程程序，
  加锁次数是 0（编译器插），需要人写的只有 4 个 while 和 4 个 signal。
```

## 11. 容易混淆的点

**条件变量和信号量的名字。**

```text
信号量的 V（signal）和条件变量的 signal 是两个东西。
前者加一，后者唤醒。同名不同物，这是历史遗留。
```

**wait 必须持锁，signal 不必须。**

```text
wait：必须持有管程互斥，否则抛异常（Java）或未定义（C）。
signal：可以在不持锁时调用，但 Mesa 语义下容易丢，通常还是持锁调用。
```

**notify 和 notifyAll。**

```text
notify：叫一个，可能叫错人，被叫醒的发现条件不满足又睡回去。
notifyAll：叫全部，正确但有惊群。
两个条件变量（两个 Condition）比 notifyAll 更好：叫的人是对的。
```

**管程的互斥和条件等待是两件事。**

```text
互斥：一次只能进一个。
条件等待：进不去的时候去哪儿。
前者是管程自带的，后者必须显式写。
```

**Hoare 的 urgent 队列。**

```text
408 会提，真实系统基本不实现。
看到「signal 后立即切换」就知道在说 Hoare。
```

## 12. 小结 + 下一篇

回到开头那段代码。

```c
P(empty);
P(mutex);
...
V(mutex);
V(full);     // 少了这一行
```

管程版里，这行对应 `not_empty.signal()`。

漏了会怎样？

```text
不会死锁，会变慢：消费者一直睡在 not_empty 上，
直到下一个生产者再放一个产品，顺手 signal 一次。
```

所以管程的 bug 更「温和」，也更容易被忽略。

三句话收尾。

```text
① 管程 = 共享数据 + 过程 + 初始化 + 条件变量，互斥由语言保证。
② 条件变量没有值，signal 无人等待会丢，所以必须配状态变量 + while。
③ 真实系统全是 Mesa 语义，所以 while 是硬规矩。
```

再加一句关于「读代码」的。

```text
看到 wait，先找它外面那层 while 的条件是什么。
那个条件才是真正的同步逻辑，wait 和 signal 只是它的搬运工。
```

> **反直觉的点**：管程自带互斥，反而比信号量更需要条件变量。
> 因为互斥只解决「不能同时进」，解决不了「条件不满足时先出去等」。
> 没有条件变量，进程只能占着管程干等——那不是同步，那是把门锁上等人送钥匙。

下一篇换一块：当「等待」形成了环，就不再是同步问题，而是死锁问题。

```text
操作系统系统讲解 11：死锁：四个条件、银行家与检测
```

那一篇会回答：

```text
四个必要条件，各自怎么破坏、代价是什么？
银行家算法为什么是「避免」不是「预防」？
资源分配图上有个环，就一定死锁吗？
```
