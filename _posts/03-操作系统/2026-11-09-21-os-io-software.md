先看三个数。

设备每传一块数据要 100 微秒。

CPU 把这块数据从缓冲区搬到用户区要 50 微秒。

CPU 处理这块数据要 50 微秒。

只有一个缓冲区时，处理 10 块要 **1550 微秒**。

加一个缓冲区，同样 10 块，**1100 微秒**。

省了 450 微秒。

省掉的不是一半，是 29%。

为什么不是一半？

因为加一块缓冲区，能省掉的只有"设备等 CPU 搬数据"那一段。

其余的时间，谁也没浪费，只是排着队。

这一篇要算清的，就是这类账。

## 1. 这个问题解决什么

20 篇讲的是硬件能做到什么。

这一篇讲的是软件怎么用它。

中间隔着一堆麻烦。

```text
设备千奇百怪：磁盘认块号，键盘认字节，打印机认行
速度差六个数量级：CPU 纳秒，磁盘毫秒
独占设备只有一台：打印机不能同时印两份文档
错误到处都有：校验错、缺纸、超时、掉线
```

软件这一层的任务，是把这些麻烦全部吸收掉，只留一个 `read` 和 `write` 给用户。

要吸收四类麻烦，就有了四层结构。

```text
用户看到的接口统一          → 用户层 I/O 软件
设备之间互相隔离            → 设备独立性软件
每种硬件的细节各自封装       → 设备驱动程序
硬件的中断各自处理          → 中断处理程序
```

## 2. 最小模型：I/O 软件四层

从用户往下画。

```text
┌─────────────────────────────────────────────┐
│  用户层 I/O 软件                              │
│  printf / scanf / 库函数 / SPOOLing 的用户界面 │
├─────────────────────────────────────────────┤
│  设备独立性软件（设备无关软件）                │
│  统一接口、缓冲、缓存、设备分配、命名、保护     │
├─────────────────────────────────────────────┤
│  设备驱动程序                                 │
│  填寄存器、发命令、处理设备特有的状态与错误     │
├─────────────────────────────────────────────┤
│  中断处理程序                                 │
│  保存现场、判断中断源、唤醒进程、返回           │
├─────────────────────────────────────────────┤
│  硬件：控制器 + 设备                          │
└─────────────────────────────────────────────┘
```

四层的分界线，不是按"代码在哪"分的。

是按"知道多少"分的。

**越往下，知道得越多；越往上，管得越宽。**

| 层次 | 知道什么 | 不知道什么 |
|---|---|---|
| 用户层 | 文件、格式、业务语义 | 数据在哪块、用哪个驱动 |
| 设备独立性软件 | 有多少设备、谁在用、缓冲区 | 设备寄存器长什么样 |
| 设备驱动程序 | 寄存器每一位的含义、时序 | 上层是谁在调用 |
| 中断处理程序 | 中断号、状态位 | 这次 I/O 是为哪个进程服务的 |

最上面那层，`printf` 根本不知道有"磁盘"这个东西。

它只知道要把一串字节送到一个叫 `stdout` 的地方。

最下面那层，中断处理程序也不知道自己在为谁干活。

它只知道某个设备的状态寄存器变成了"完成"。

中间两层，就是把这些"不知道"接起来的粘合剂。

## 3. 一次完整走查：read() 从用户态到磁盘

写一句最普通的代码。

```c
char buf[4096];
int n = read(fd, buf, 4096);
```

这一行走完，中间发生了什么。

```text
① 用户层：C 库的 read 把参数放进寄存器，执行陷入指令
        │
        ▼
② 系统调用入口：保存现场，按系统调用号分发到 sys_read
        │
        ▼
③ 设备独立性软件：
   - 用 fd 查进程的文件描述符表 → 打开文件表 → inode
   - 检查这个 fd 是不是可读、有没有越权
   - 看请求的 4096 字节在页缓存里有没有
        │
        ├── 命中：直接从页缓存拷到用户 buf，返回 4096   ← 没有驱动，没有 I/O
        │
        └── 未命中：继续往下
        │
        ▼
④ 设备驱动程序：
   - 把这次读转换成一个块请求（起始扇区、长度）
   - 可能合并相邻请求
   - 把请求描述符挂到设备队列，写控制器寄存器启动 DMA
   - 进程进入阻塞态，让出 CPU
        │
        ▼
⑤ 硬件：DMA 把数据从磁盘搬到内存页缓存，完成后发中断
        │
        ▼
⑥ 中断处理程序：
   - 读状态寄存器确认成功
   - 清除中断标志
   - 唤醒等待这个请求的进程
        │
        ▼
⑦ 回到设备独立性软件：把页缓存里的数据拷到用户 buf，返回 4096
```

七个步骤，标出三个最容易被忽略的地方。

```text
第 ③ 步的"命中就直接返回"，说明 read 不一定碰硬件
第 ④ 步的"阻塞"，说明 I/O 的时间主要花在等，不是算
第 ⑥ 步的"唤醒"，说明中断处理程序的核心工作是叫醒别人
```

408 的层次题，全部围绕这张图。

题干说"负责把逻辑块号转换成物理地址"——那是驱动。

题干说"为用户提供统一的设备命名"——那是设备独立性软件。

题干说"处理设备发出的中断信号"——那是中断处理程序。

题干说"把格式化输入转换成对设备的读写"——那是用户层库函数。

再补一个容易混的：**页缓存的命中判断属于哪一层？**

设备独立性软件。

因为"有没有缓存"是设备无关的策略，和具体磁盘无关。

这也是为什么 `O_DIRECT` 这种"绕过页缓存"的标志，是由通用层处理的，而不是驱动。

驱动只负责"把这块数据搬过去"，它不知道也不关心上面有没有缓存。

## 4. 设备独立性与设备分配

### 4.1 四个数据结构

设备分配不是"查个表就完了"。

一个 I/O 请求可能要同时占用设备、控制器、通道三级资源。

每一级都有自己的控制表。

```text
SDT（系统设备表）：全系统一张，记录所有设备，指向各自的 DCT
DCT（设备控制表）：每台设备一张，状态、等待队列、指向 COCT
COCT（控制器控制表）：每个控制器一张，状态、挂的设备、指向 CHCT
CHCT（通道控制表）：每个通道一张，状态、挂的控制器
```

画成一条链。

```text
SDT
 └─▶ DCT（设备） ──▶ COCT（控制器） ──▶ CHCT（通道）
      状态              状态                状态
      等待队列          等待队列            等待队列
```

任何一级"忙"，请求就得在这一级的等待队列里排队。

还有一个表专门解决"名字"的问题。

```text
LUT（逻辑设备表，Logical Unit Table）
  逻辑设备名 → 物理设备名 + 驱动程序入口
  例：LPT1 → 打印机 0，用 printer 驱动
```

LUT 有两种放法。

```text
全系统一张：所有进程共用，逻辑名冲突，但省空间
每进程一张：各自独立，灵活，但每个进程都要维护
```

408 常问"逻辑设备名到物理设备名的映射在哪一层"。

答案：设备独立性软件。

因为驱动只认"物理设备"，它不关心上层叫它 `LPT1` 还是 `printer2`。

### 4.2 分配的三步与安全性检查

分配一个独占设备，要走三步。

```c
/* 简化示意：分配一台独占设备 */
dct = lookup(logical_name);          /* 查 LUT，拿到 DCT */

if (dct->state != FREE)  goto wait;  /* ① 设备分配 */
dct->state = BUSY;

coct = dct->controller;
if (coct->state != FREE) { dct->state = FREE; goto wait; }  /* ② 控制器分配 */
coct->state = BUSY;

chct = coct->channel;
if (chct->state != FREE) { dct->state = FREE; coct->state = FREE; goto wait; }
chct->state = BUSY;                  /* ③ 通道分配 */

return OK;                           /* 三级全拿到才算成功 */
```

注意那两个 `goto` 之前干了什么。

**回退。**

设备拿到了但控制器拿不到，必须把设备释放回去。

否则就是"占着茅坑不拉屎"，别人也用不了。

这就是设备分配的死锁来源。

三个进程，各占一台设备、各等一个控制器，就转成了一个环。

408 爱考的两条改进措施：

```text
① 静态分配：作业开始前一次性申请全部设备，用完才还
   优点：不会死锁
   缺点：利用率极低（设备闲一天，别人也不能用）

② 按序分配：所有进程按"设备 → 控制器 → 通道"的固定顺序申请
   优点：破坏循环等待条件
   缺点：需要程序员遵守约定
```

为什么按这个顺序？

因为资源的使用关系本身就是这个方向。

设备要用控制器，控制器要用通道。

所以按"从小到大"的顺序申请，就不可能形成环。

这和 11 篇里银行家算法的思路是同一个：**有序，就没有死锁。**

## 5. 缓冲：从单缓冲到缓冲池

### 5.1 为什么要缓冲

三个理由，一个比一个实在。

```text
① 速度匹配：CPU 纳秒级，磁盘毫秒级，中间要有个"仓库"
② 适配大小：设备一次一个字节，文件系统一次一个块
③ 减少中断：攒够一批再叫 CPU，中断次数能降几个数量级
```

缓冲的定义很干脆。

**缓冲（buffer）是内存里的一块临时区域，用来在速度不匹配的两个部件之间存放数据。**

关键是"内存里"。

这一句把它和 SPOOLing 分开了，后面细说。

### 5.2 单缓冲

只有一个缓冲区，设备填它，CPU 从它里面取。

三个时间参数，先定义清楚。

```text
T：设备把一块数据填满缓冲区的时间
M：CPU 把缓冲区里的一块数据搬到用户区的时间
C：CPU 处理这一块数据的时间
```

为什么缓冲区到用户区还要单独搬一次？

因为缓冲区是共享的，用户的 `buf` 是私有的。

不能把共享缓冲区的地址直接交给用户，否则下一个 I/O 就把它覆盖了。

单缓冲的时间轴：

```text
设备 ──[ 填 B1 ]──[ 空闲 ]──[ 填 B2 ]──[ 空闲 ]──[ 填 B3 ]
                    ↑                ↑
CPU  ──────────────[ 搬 M ][ 处理 C ][ 搬 M ][ 处理 C ]
```

看第二个"空闲"。

设备想填 B2，得等 CPU 把 B1 搬走（M 结束）。

设备的空闲，就空在这一段 M 上。

所以每块的时间是：

```text
单缓冲：每块时间 = max(C, T) + M
```

`max(C, T)` 是"设备填"和"CPU 处理"两件事并行后的较长者。

`+ M` 是搬走那一段，谁也不能和它并行——因为只有一块缓冲区，搬的时候设备没地方放。

推导一下 10 块的总时间（T=100, C=50, M=50）。

```text
0   – 100  设备填 B1
100 – 150  CPU 搬 B1 到用户区（M）
150 – 200  CPU 处理 B1（C）；设备同时开始填 B2（150–250）
250 – 300  CPU 搬 B2（设备 250 才填完，CPU 200 就空了）
300 – 350  CPU 处理 B2；设备填 B3（300–400）
...
每块 150，第 1 块在 200 处理完，之后每块再加 150：
150 + 9 × 150 + 50 = 1550 μs
```

严格公式：

```text
单缓冲 n 块总时间 = T + M + (n − 1) × [max(C, T) + M] + C
```

代进去：100 + 50 + 9 × 150 + 50 = 1550。

和画出来的时间轴一致。

### 5.3 双缓冲

两块缓冲区，一块在填，另一块在处理。

时间轴：

```text
设备 ──[ 填 B1 ]──[ 填 B2 ]──[ 填 B3 ]──[ 填 B4 ]
CPU  ─────────────[ 搬B1 ][ 处理B1 ][ 搬B2 ][ 处理B2 ]
```

设备不再等 M 了。

填完 B1 立刻去填 B2，中间没有空档。

此时 CPU 每块要花的连续时间是 `C + M`，设备每块要花的是 `T`。

两者完全重叠，谁慢谁决定节奏。

```text
双缓冲：每块时间 = max(C + M, T)
```

10 块：

```text
100 + 50 + 9 × max(100, 100) + 50
= 100 + 50 + 900 + 50
= 1100 μs
```

1550 到 1100，省了 450，提速 1.41 倍。

**省下来的正好是 9 个 M。**

因为单缓冲里设备被 M 挡住 9 次，双缓冲里一次也没被挡。

### 5.4 循环缓冲与缓冲池

双缓冲还不够，就多来几个。

```text
循环缓冲（circular buffer）
  若干个缓冲区连成环，两个指针：
    in  指向下一个可写的空缓冲
    out 指向下一个可读的满缓冲
  输入进程往后写，输出进程往前读
```

它解决的不是"再多省一点时间"，而是**速度波动**。

网络流量是突发的。

来的时候 1 Gb/s，闲的时候几 KB/s。

固定两块缓冲区，突发时丢包，空闲时浪费。

一圈缓冲区，就能吸收这种波动。

代价是复杂度：环路满了怎么办，空了怎么办，指针怎么同步。

这些在 08 篇的信号量里都见过——本质还是一个生产者消费者。

缓冲区再多，也要有人统一管。

这就是缓冲池。

```text
缓冲池（buffer pool）
  系统统一管理的多个缓冲区，分成三个队列：

  空闲缓冲区队列    ── 谁都能拿
  装满输入数据队列  ── 等进程取
  装满输出数据队列  ── 等设备取

  四个工作缓冲区（408 爱考这四个名字）：
  hin  收容输入：设备 → 空缓冲区 → 输入队列
  sin  提取输入：输入队列 → 进程 → 缓冲区变空
  hout 收容输出：进程 → 空缓冲区 → 输出队列
  sout 提取输出：输出队列 → 设备 → 缓冲区变空
```

画成图就是一个"井"字。

```text
      ┌──────────┐
设备 ─▶│ hin 收容 │──▶ 输入队列 ──▶│ sin 提取 │──▶ 进程
      └──────────┘                  └──────────┘
      ┌──────────┐
进程 ─▶│ hout 收容│──▶ 输出队列 ──▶│ sout 提取│──▶ 设备
      └──────────┘                  └──────────┘
              ↑                        │
              └──── 空闲缓冲区队列 ◀────┘
```

408 喜欢问：一个缓冲区从 `hin` 到 `sin`，中间经过几个队列？

答：一个输入队列。然后它变成空缓冲区，回到空闲队列。

这四个工作缓冲区，其实就是一个生产者消费者问题。

进程要取输入数据，就卡在"输入队列非空"上。

设备要取输出数据，就卡在"输出队列非空"上。

队列满的时候，收容的一方要等。

所以缓冲池的实现里一定有信号量，而且是四组。

```text
empty_in / full_in     配合 hin 和 sin
empty_out / full_out   配合 hout 和 sout
```

09 篇那四道经典同步题，在这里全用上了。

区别只是：经典题里是"盘子"和"座位"，这里换成了缓冲区。

## 6. 408 怎么考

四类题。

```text
① 缓冲计算：单缓冲 / 双缓冲的时间，给 T、C、M
② SPOOLing 判断：哪句话对、哪句话错
③ 设备分配：分配顺序、数据结构、能否分配成功
④ 层次判断：某个功能属于四层里的哪一层
```

**缓冲计算**，先把三个符号写下来，再套公式。

```text
单缓冲：每块 = max(C, T) + M
双缓冲：每块 = max(C + M, T)
```

有个陷阱：题目可能不给 M，只给"从缓冲区到用户区的时间"。

那就是 M，别当成 C。

另一类陷阱：题目问"处理 n 块数据的时间"，有人直接套 `n × 每块`。

严格算是 `T + M + (n−1) × 每块 + C`。

n 大时差别不大，n=10 时差 50 微秒，正好能对上一个选项。

**完整例题。**

> 自拟题：某设备每传一块数据到缓冲区需 100 μs（T），
> CPU 把一块数据从缓冲区送到用户区需 50 μs（M），
> CPU 处理一块数据需 50 μs（C）。共 10 块。
> 求：单缓冲、双缓冲各需多少时间？双缓冲比单缓冲快多少？

解。

```text
单缓冲：每块 = max(50, 100) + 50 = 100 + 50 = 150 μs
        总时间 = 100 + 50 + 9 × 150 + 50 = 1550 μs

双缓冲：每块 = max(50 + 50, 100) = max(100, 100) = 100 μs
        总时间 = 100 + 50 + 9 × 100 + 50 = 1100 μs

差值 = 1550 − 1100 = 450 μs
提速 = 1550 / 1100 ≈ 1.41 倍
```

验算一遍：450 正好等于 9 × M。

这不是巧合。

单缓冲被 M 卡住 9 次，双缓冲一次不卡，省的就是这 9 段。

**SPOOLing 判断**，看三句话。

> "SPOOLing 提高了打印机的输出速度。"

错。

打印机的物理速度一点没变。

变的是"用户等的时间"——用户写完队列就返回了。

> "SPOOLing 需要磁盘支持。"

对。

输入井、输出井都在磁盘上。

> "SPOOLing 把独占设备改造成了共享设备。"

对。

这是它唯一的核心目的。

**设备分配**，看有没有回退。

题目给三张表的状态，问"进程 P 申请设备 A 能否成功"。

按设备 → 控制器 → 通道的顺序查，哪一级忙就失败，并要把之前拿到的释放掉。

**层次判断**，记四个典型。

```text
"把逻辑设备名映射为物理设备名"     → 设备独立性软件
"检查用户是否有权访问这个设备"     → 设备独立性软件
"把块号转换成磁头、柱面、扇区"     → 设备驱动程序
"响应中断、保存和恢复现场"         → 中断处理程序
"把整数格式化成十进制字符串"       → 用户层 I/O 软件
```

最后一条最容易错。

因为格式化是 CPU 干的活，和硬件一点关系都没有，当然在最上层。

缓冲题有四个固定坑。

```text
① 把 M 当成 C，或者把"设备到缓冲区"当成"缓冲区到用户区"
② 双缓冲写成 max(C, T) + M，忘了 M 已经进了括号
③ n 块直接乘每块，丢了首块的 T 和末块的 C
④ 单位：μs 和 ms 混着用，最后差三个数量级
```

第 ② 个最要命。

双缓冲的正确写法是 `max(C + M, T)`，不是 `max(C, T) + M`。

因为双缓冲里，CPU 那段 C 和 M 是连续占用自己的时间的，不能藏进 max 里。

## 7. 真实系统里长什么样

先看四层在 Linux 里的对应物。

```text
用户层          glibc 的 read/write/printf
设备独立性软件   VFS（虚拟文件系统）+ 页缓存 + 通用块层
设备驱动程序     nvme.ko、e1000e.ko、usb-storage.ko
中断处理程序     中断上半部 + softirq/tasklet/workqueue
```

**VFS 就是那个"设备独立性软件"。**

它定义了一组统一的接口：`open`、`read`、`write`、`ioctl`。

ext4、xfs、proc、sysfs、tty、socket，全都实现这组接口。

所以 `cat /proc/cpuinfo` 和 `cat /home/a.txt` 用的是同一套系统调用。

对象不同，接口相同。

**页缓存（page cache）就是那个"缓冲"。**

它的位置在第 ③ 步。

读文件时先查页缓存，命中就不碰磁盘。

这就是为什么第二次 `cat` 一个大文件会明显变快。

```text
$ cat bigfile > /dev/null     # 第一次，走磁盘
$ cat bigfile > /dev/null     # 第二次，全在页缓存里
```

想看真实的 I/O，得把缓存清掉。

```text
$ echo 3 > /proc/sys/vm/drop_caches
```

**通用块层（block layer）就是"缓冲池"的现代版。**

它收下所有块设备的请求，合并、排序、限流，再交给驱动。

调度器可换：

```text
$ cat /sys/block/nvme0n1/queue/scheduler
[none] mq-deadline kyber bfq
```

SSD 上默认是 `none`。

因为没有寻道，排序没意义。

**管道和 tty 用的是环形缓冲。**

```text
$ cat /proc/sys/fs/pipe-max-size
1048576
```

一个管道默认 64 KB，最大能调到 1 MB。

写满就阻塞，读空就阻塞。

这是循环缓冲最朴素的样子。

**SPOOLing 在 Linux 里的现实版是 CUPS。**

```text
应用 → libcups → cupsd 守护进程 → 队列文件（/var/spool/cups） → 打印机
```

`/var/spool/cups` 就是"输出井"。

`cupsd` 就是"输出进程"。

应用调 `lp` 立刻返回，打印任务在队列里排队。

三个进程同时打印，谁也不等谁。

**中断处理程序的上下半部，在代码里长这样。**

```c
/* 上半部：关中断执行，越短越好 */
static irqreturn_t my_irq(int irq, void *dev)
{
    u32 status = readl(dev->regs + STATUS);
    if (!(status & DONE))
        return IRQ_NONE;
    writel(DONE, dev->regs + STATUS);   /* 清中断 */
    tasklet_schedule(&dev->tasklet);    /* 剩下的交给下半部 */
    return IRQ_HANDLED;
}
```

上半部只做三件事：读状态、清中断、推给下半部。

和前面说的完全一致。

## 8. SPOOLing：把独占设备改成共享

SPOOLing 的全名很绕：Simultaneous Peripheral Operations On-Line。

翻译成"假脱机"，也不直观。

它的想法只有一句：

**用户要的不是设备，是"我的东西被打印出来"这个结果。**

那就先把结果存起来，慢慢打。

### 8.1 组成

```text
磁盘上的输入井（input well）  ← 预先读入的输入数据
磁盘上的输出井（output well） ← 等着输出的数据
内存的输入缓冲区 / 输出缓冲区  ← 和磁盘之间的中转
输入进程（预输入进程）         ← 提前把数据从设备读进输入井
输出进程（缓输出进程）         ← 有空就把输出井的数据送到设备
井管理程序                     ← 管这两个井的分配与回收
```

### 8.2 打印机怎么变成共享设备

假设三个进程同时要打印。

**没有 SPOOLing 时：**

```text
P1 申请打印机 → 拿到 → 打印 100 页 → 释放      （P1 阻塞 100 页的时间）
P2 申请打印机 → 排队等 → ...                    （白等）
P3 申请打印机 → 排队等 → ...                    （白等）
```

**有 SPOOLing 时：**

```text
P1 写 100 页到输出井 → 立刻返回，感觉自己打完了
P2 写 100 页到输出井 → 立刻返回
P3 写 100 页到输出井 → 立刻返回

输出进程按队列顺序：
  打印机空闲 → 取 P1 的 100 页 → 打
  打完       → 取 P2 的 100 页 → 打
  打完       → 取 P3 的 100 页 → 打
```

用户的感受变了。

原来是"我用打印机，你要等"。

现在是"我有一个打印机，别人也各有一个"。

**独占设备被虚拟成了多台。**

### 8.3 为什么这叫"虚拟设备"

因为它伪造的不是速度，是"独占"这个属性。

```text
物理事实：只有一台打印机，同一时刻只能打一份
用户视角：我有一台打印机，随时能提交
```

系统用一个"排队 + 后台串行"的机制，把物理上的独占变成了逻辑上的共享。

代价也很实在。

```text
① 需要磁盘空间：输出井可能很大
② 需要一次额外拷贝：用户内存 → 磁盘 → 打印机
③ 输出有延迟：提交了不代表马上打
④ 出错要重试：打印机卡纸，队列得能恢复
```

所以 SPOOLing 换来的是"响应快、利用率高"，付出的是"空间和延迟"。

### 8.4 它和缓冲不是一回事

这两个词经常被混用。

```text
缓冲：在内存里，容量小，存活时间以毫秒计，解决"速度不匹配"
SPOOLing：在磁盘上，容量大，存活时间以分钟计，解决"独占变共享"
```

一句话区分：

**缓冲是"临时放一下"，SPOOLing 是"排队等一等"。**

缓冲不会让一台设备变成两台。

SPOOLing 会。

## 9. SSD：块设备，但不转

408 的大纲里有"磁盘与 SSD 特性（磨损均衡、FTL）"。

SSD 是块设备，接口上和磁盘一样，都是按块读写。

但内部完全是另一套逻辑。

### 9.1 三个层次的单位

```text
页（page）    读写单位，常见 4 KB
块（block）   擦除单位，常见 128 ~ 256 个页，即 512 KB ~ 1 MB
```

关键限制：

```text
可以按页读
可以按页写，但只能写"擦干净"的页
擦除必须按块，而且一次擦一整块
```

这个不对称，是所有 SSD 复杂性的根源。

### 9.2 FTL：闪存翻译层

磁盘给了块号，磁头就能直接去找。

SSD 不行。

一个逻辑块号写下去，实际落到哪个物理页，由 FTL（Flash Translation Layer）决定。

```c
/* 简化示意：一次写在 FTL 里发生了什么 */
write(lba, data):
    ppn = find_free_page()          /* 找一个空的物理页 */
    program(ppn, data)              /* 写进去 */
    map[lba] = ppn                  /* 更新映射表，旧页标记为无效 */

    if (free_pages_are_low()):
        gc()                        /* 垃圾回收：搬有效页，擦整块 */
```

一个块里如果还有有效页，就不能擦。

只能把有效页搬到新块，再擦掉整块。

搬的时候，写放大就来了。

```text
写放大 = 实际写入闪存的数据量 / 主机请求写入的数据量
```

举个具体的账。

```text
块大小 256 页，其中 200 页有效、56 页无效
要回收这个块：
  ① 把 200 页有效数据搬到新块     写入 200 页
  ② 擦除这个块                    1 次擦除
主机在这期间只请求写了 56 页
实际写入闪存 = 56 + 200 = 256 页
写放大 = 256 / 56 ≈ 4.6
```

写放大越高，寿命消耗越快，性能越差。

所以 FTL 会尽量挑"无效页多"的块来回收。

无效页越多，需要搬的有效页越少，放大越小。

垃圾回收的时机也有讲究。

写满了才回收，会突然卡一下。

提前在后台慢慢回收，用户就感觉不到。

这就是 SSD 主控里那块"后台 GC"存在的原因。

### 9.3 磨损均衡

闪存的每个块能擦除的次数有限（P/E 次数，消费级 TLC 大约几百到几千次）。

如果总盯着同一批块写，它们先坏，整盘就废了。

磨损均衡（wear leveling）要做的事：让每个块的擦除次数尽量接近。

```text
动态磨损均衡：新数据优先写到擦除次数少的块
静态磨损均衡：定期把长期不动的"冷数据"搬走，腾出低磨损块
```

静态那条容易被忽略：冷数据占着好块不动，也是一种浪费。

### 9.4 与磁盘对比

| 对比项 | 机械磁盘（HDD） | 固态盘（SSD） |
|---|---|---|
| 寻道时间 | 几 ms，占大头 | 没有寻道 |
| 随机读延迟 | 5 ~ 10 ms | 几十 ~ 一百 μs |
| 顺序 / 随机差异 | 极大 | 小很多 |
| 写前是否需要擦除 | 不需要 | 需要，按块擦 |
| 寿命 | 机械磨损，通常更长 | P/E 次数有限 |
| 抗震 | 差 | 好 |
| 是否需要磁盘调度 | 需要（减少寻道） | 基本不需要 |

对操作系统的影响很直接。

```text
磁盘上，调度算法（SSTF/SCAN）能显著减少寻道 → 值得做
SSD 上，没有寻道，排序意义不大 → 调度器常设成 none
磁盘上，随机写和顺序写差几十倍 → 要尽量顺序
SSD 上，随机写和顺序写差距小 → 但仍受写放大影响
```

408 常问一句："为什么 SSD 不需要磁盘调度算法？"

答：因为它没有磁头移动，随机访问和顺序访问的差距很小。

SSD 对操作系统还有一个新要求：TRIM。

文件删除时，系统要告诉 SSD"这几页数据作废了"。

否则 SSD 不知道那些页已经没用，垃圾回收时还要白搬一遍。

```text
没有 TRIM：删了文件，SSD 以为数据还有效，GC 照搬 → 写放大变高、越用越慢
有 TRIM：  删了文件，SSD 把这些页标成无效 → GC 少搬，性能稳定
```

这是"文件系统"和"块设备"之间多出来的一层约定。

机械盘时代完全不需要——磁盘没有"擦除"这个概念，写就是覆盖。

## 10. 容易混淆的点

**一、缓冲与缓存。**

```text
缓冲（buffer）：为了"速度匹配"，存的是"正在传输的数据"
缓存（cache）：为了"减少重复访问"，存的是"可能会再用的数据"
```

页缓存既是缓存也是缓冲，所以这两个词在真实系统里经常混着用。

但在概念题里，缓冲强调"中转"，缓存强调"复用"。

**二、单缓冲与双缓冲的提速上限。**

不是 2 倍。

上限由 M 决定：省掉的是 `(n−1) × M`。

如果 M 很小，双缓冲几乎没有收益。

**三、SPOOLing 与缓冲。**

前面说过：一个在磁盘排队，一个在内存中转。

再补一句：SPOOLing 一定涉及"进程"，缓冲不一定。

因为有"输入进程 / 输出进程"在后台干活，SPOOLing 才是 SPOOLing。

**四、设备驱动程序与设备独立性软件。**

```text
驱动：知道寄存器每一位，一个设备一份
设备独立性软件：不知道寄存器，一套代码管所有设备
```

所以写新驱动只要实现那组固定接口，上层一行都不用改。

这就是"设备独立性"这个名字的由来。

**五、逻辑设备表 LUT 放在哪一层。**

设备独立性软件。

不在驱动里，因为驱动只认物理设备。

**六、中断处理程序与驱动程序的分工。**

```text
驱动：发命令、填寄存器（主动）
中断处理：收结果、清标志、唤醒（被动）
```

一次 I/O 里，驱动跑在前面，中断处理跑在后面。

## 11. 反直觉：缓冲区不是让设备变快

```text
直觉：加一个缓冲区，速度应该翻倍。
现实：加一个缓冲区，最多省掉 M 那一段。

单缓冲：每块 = max(C, T) + M
双缓冲：每块 = max(C + M, T)

两式相减，差值最大就是 M。

如果 M 只占 10%，双缓冲带来的提升也就 10%。
如果 C 远大于 T 和 M，双缓冲一点用都没有——瓶颈在 CPU。
```

真正被解决的不是"设备慢"。

是"设备在等 CPU 搬数据"这件蠢事。

回看单缓冲的时间轴：

```text
设备 ──[ 填 B1 ]──[ 空闲 ]──[ 填 B2 ]
                    ↑
              设备在这里没活干，
              因为唯一的一块缓冲区正在被搬走
```

设备的物理速度一寸没变。

变的是"它有没有活干"。

所以缓冲区的本质不是加速器，是**解耦器**。

它把"设备的节奏"和"CPU 的节奏"分开，让两边各自按自己的速度跑。

跑得快的那一方，等；跑得慢的那一方，被等。

加缓冲，只是把"等"的位置挪了挪。

这也解释了一个常见误解：

> "内存越大，I/O 越快。"

不对。

内存大只意味着能放更多缓存，命中率更高。

真正的 I/O 速度，还是由设备决定。

## 12. 小结 + 下一篇

这一篇的主线是"软件怎么把硬件的差异吃掉"。

```text
四层结构：用户层 → 设备独立性 → 驱动 → 中断处理
一次 read：查缓存 → 组请求 → 启动 DMA → 阻塞 → 中断唤醒 → 拷贝返回
缓冲：单缓冲 max(C,T)+M，双缓冲 max(C+M,T)
SPOOLing：用磁盘上的队列，把独占设备虚拟成共享
SSD：块设备，但没有磁头，靠 FTL 映射，靠磨损均衡续命
```

三个必须能背下来的公式。

```text
单缓冲每块时间 = max(C, T) + M
双缓冲每块时间 = max(C + M, T)
单缓冲 n 块     = T + M + (n−1)·[max(C,T)+M] + C
```

三个必须能一句话说清的概念。

```text
设备独立性软件：不知道寄存器，管所有设备
设备驱动程序：知道每一位，只管自己那台
SPOOLing：在磁盘上排队，让独占设备看起来是共享的
```
