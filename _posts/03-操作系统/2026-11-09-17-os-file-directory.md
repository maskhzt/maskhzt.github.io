先做一个小实验。

```bash
$ echo hello > a.txt
$ ln a.txt b.txt        # 硬链接
$ ln -s a.txt c.txt     # 软链接
$ rm a.txt
$ cat b.txt
hello
$ cat c.txt
cat: c.txt: No such file or directory
```

同一个原文件 `a.txt`，删掉之后，`b.txt` 还能读出 `hello`。

`c.txt` 直接读不了。

两个链接都在 `ls` 里看得见，都指向同一个名字，行为却完全不同。

原因只有一个：

```text
b.txt 指向 inode，
c.txt 指向路径字符串 "a.txt"。
```

路径字符串还在，但它描述的那个名字没了。

**反直觉的点在这里：**

> **文件名不存在 inode 里，它存在目录项里。**
> **所以一个文件可以有多个名字，而 inode 只有一份。**

这一句能解释硬链接、软链接、`link count`、`df -i` 和 408 的半个文件管理部分。

## 1. 这个问题解决什么：磁盘上只有块

磁盘给人的接口只有一个：

```text
读第 k 号块  /  写第 k 号块
```

4 KB 一块，编号从 0 排到几十亿。

没有名字，没有边界，没有权限。

用户需要的东西完全不一样：

```text
一个名字        /home/notes/todo.md
一段字节流      想读第 100 个字节就能读到
一组边界        这个文件到哪结束，下一个文件从哪开始
一套权限        谁能读、谁能写、谁能执行
一条时间线      什么时候建的、什么时候改的
```

这五样东西，块本身一样都不提供。

文件系统要把「块」包装成「文件」，只需要回答四个问题：

```text
① 这个名字对应哪个文件？      → 目录 + 目录项
② 这个文件有哪些块？          → inode 里的块指针
③ 哪些块还空着？              → 空闲空间管理（18 篇）
④ 谁能对它做什么？            → 保护机制
```

第 17 篇管第 ① 和第 ④，顺手把「文件长什么样」说清楚。

第 ②③ 留给 18 篇。

所以「文件」这个概念，精确一点说是这样：

```text
文件（file）= 一个有名字的、由操作系统管理的、相关信息的集合。
```

关键词是「有名字」和「被管理」。

没有名字的字节集合，只是一个块。

### 1.1 七个属性

考试里问「文件属性包括哪些」，答案就是这一串。

```text
名称     name         用户看的字符串，同一目录内唯一
标识符   identifier   系统内唯一，UNIX 里就是 inode 号
类型     type         普通文件、目录、设备、管道、链接
位置     location     在哪台设备、哪些块
大小     size         当前字节数，以及可能的上限
保护     protection   读/写/执行权限，属主与属组
时间     time         atime 访问、mtime 修改、ctime 状态改变
```

这里埋着一个必须分清的区别：

```text
名称    给人看的，可以重复（不同目录、或同一文件的多个名字）
标识符  给系统用的，全局唯一，不可重复
```

**名称和标识符分离，是后面所有共享机制的地基。**

如果文件名存在 inode 里，那一个文件就只能有一个名字，硬链接就不存在了。

### 1.2 七个基本操作

```text
create    建一个空文件，分配 inode
delete    删掉，释放 inode 和块
open      把文件的信息读进内存，返回一个句柄
close     释放句柄
read      从当前位置读 n 个字节
write     往当前位置写 n 个字节
seek      把当前位置挪到指定偏移
```

前两个操作的是「文件存不存在」。

后五个操作的是「打开着的文件」。

这个划分很重要：408 里问「打开文件表的作用」，答案就在这个划分里。

### 1.3 为什么 open 必须单独存在

问：既然 `read` 可以带路径，为什么还要先 `open`？

答：因为路径解析很贵。

一次 `open("/usr/local/src/readme")`，要逐级读目录、查 inode、查权限，可能十几次磁盘 I/O。

如果每次 `read` 都重来一遍，读 1000 次就是上万次 I/O。

`open` 把这一次昂贵的结果缓存下来，放进内存里的一张表。

之后每次 `read` 只查这张表，代价是几次内存访问。

```text
open  = 昂贵的路径解析，做一次
read  = 便宜的表查找，做很多次
```

这条「一次解析，多次使用」的思路，和页表缓存（TLB）、目录项缓存（dcache）是同一个套路。

**操作系统的性能，一半靠缓存，一半靠批处理。**

## 2. 最小模型：文件、inode、目录项、打开文件表

四层结构，从下往上：

```text
┌───────────────────────────────────────────────┐
│ 数据块  data blocks                            │
│ 4 KB 一块，装文件内容，没有名字                 │
└───────────────────┬───────────────────────────┘
                    │ 由 inode 里的块指针指向
┌───────────────────▼───────────────────────────┐
│ 索引结点 inode                                 │
│ 类型、大小、权限、时间、块指针、链接计数        │
│ 没有文件名                                     │
└───────────────────▲───────────────────────────┘
                    │ 目录项里存 inode 号
┌───────────────────┴───────────────────────────┐
│ 目录项 directory entry                         │
│ (文件名, inode 号)                             │
└───────────────────▲───────────────────────────┘
                    │ 目录本身也是一个文件
┌───────────────────┴───────────────────────────┐
│ 目录文件 + 路径解析 + 打开文件表                │
└───────────────────────────────────────────────┘
```

从上往下读一遍就是一次查找：

```text
/home/notes/todo.md
   │
   ├─ 根目录里找 "home"  → 得到 home 的 inode 号
   ├─ home 目录里找 "notes" → 得到 notes 的 inode 号
   ├─ notes 目录里找 "todo.md" → 得到 todo.md 的 inode 号
   └─ 读 todo.md 的 inode → 知道它的块在哪、多大、谁能读
```

注意最后一步之前拿到的都只是「inode 号」，一个整数。

真正的元数据要读 inode 表。

### 2.1 inode 里到底有什么

```c
/* 简化示意：只保留 408 关心的字段 */
struct inode {
    uint16_t i_mode;      /* 类型 + rwx 权限位 */
    uint16_t i_nlink;     /* 硬链接计数 */
    uint32_t i_size;      /* 文件字节数 */
    uint32_t i_blocks;    /* 占用的磁盘块数 */
    uint32_t i_block[15]; /* 12 个直接 + 1 一级 + 1 二级 + 1 三级 */
    time_t   i_atime;     /* 最后访问时间 */
    time_t   i_mtime;     /* 最后修改时间 */
    time_t   i_ctime;     /* inode 自身改变时间 */
    /* 这里是重点：没有文件名字段 */
};
```

`i_block[15]` 这 15 个槽位，是 18 篇要算的最大文件大小。

`i_nlink` 这个计数，是这一篇要用的硬链接。

`i_mode` 里的 9 个权限位，是这一篇最后讲的 rwx。

**一个 128 或 256 字节的结构，撑起了整个文件系统。**

### 2.2 早期 FCB 和现在的目录项

教材里会先讲 FCB（file control block，文件控制块）。

FCB 是「文件存在的标志」，里面包含文件名和所有元数据。

一个目录，就是一堆 FCB 的线性表。

这套模型没错，但有个性能问题：

```text
目录里 10000 个文件
每个 FCB 128 字节，光名字匹配就要读 10000 次比较
而且 FCB 里 90% 的字段（大小、时间、块指针）在「找文件」时根本用不上
```

UNIX 的改法很干脆：把 FCB 拆成两半。

```text
目录项 dentry：只要 (文件名, inode 号)，16 字节左右
inode          ：其余全部元数据，128~256 字节
```

好处立刻出现：

```text
① 目录变薄，同样一个 4 KB 块能装下更多目录项，查找更快
② 一个 inode 可以被多个目录项指向 → 硬链接
③ inode 可以常驻内存缓存，目录项按需读
```

代价是多了一次跳转：先拿 inode 号，再去读 inode。

这个「用一层间接换灵活性」的手法，和页表、二级页表是一模一样的思路。

### 2.3 打开文件表与文件描述符

文件被 `open` 之后，内核要记住三件事：

```text
① 这个文件是谁（哪个 inode）
② 当前读到哪了（文件偏移量 offset）
③ 谁有权限用它（打开模式）
```

这三件事分成两张表。

```text
进程 A 的 PCB                         系统级打开文件表
┌──────────────┐                    ┌─────────────────────────┐
│ fd 0 → ──────┼───────────────────▶│ 表项 0: inode*, off=0   │
│ fd 1 → ──────┼──────┐             │          读模式, 计数 2 │
│ fd 2 → ──────┼──┐   │             ├─────────────────────────┤
│ fd 3 → ──────┼──┼───┘             │ 表项 1: inode*, off=91  │
└──────────────┘  │                 │          写模式, 计数 1 │
                  │                 └─────────────────────────┘
进程 B 的 PCB     │                            ▲
┌──────────────┐  └────────────────────────────┘
│ fd 3 → ──────┼───────────────────────────────┘
└──────────────┘
```

两层表各有分工：

```text
进程级表（per-process）  每个进程一张，下标就是 fd
系统级表（system-wide）  全系统一张，记录 offset 和打开计数
```

为什么 offset 要放在系统级表，而不是进程级表？

因为 `fork` 之后父子进程共享同一个打开文件，偏移量必须共享。

否则父子各读一半，文件就被读乱了。

```text
fd = 进程级表的索引 = 一个小整数（0、1、2、3……）
```

0、1、2 是惯例：标准输入、标准输出、标准错误。

**fd 是索引，不是指针，更不是 inode 号。** 这是选择题最爱设的坑。

## 3. 一次完整走查：open 一个路径，读了几次盘

这是 408 最爱的计算题之一。

题目（自拟）：

```text
文件系统用树形目录，路径 /usr/local/src/readme 存在。
假设：
  根目录的 inode 已在内存中；
  其余每个目录的 inode 都要读 1 次盘；
  每个目录的数据块都要读 1 次盘（一个块装得下所有目录项）；
  没有目录项缓存。
问：打开该文件（拿到它的 inode）共需几次磁盘 I/O？
```

一步一步列：

```text
步骤                          动作                     累计 I/O
─────────────────────────────────────────────────────────────
1  根目录 inode                已在内存                     0
2  读根目录数据块，找 usr      读 1 个目录块                1
3  得到 usr 的 inode 号        读 usr 的 inode              2
4  读 usr 目录块，找 local     读 1 个目录块                3
5  得到 local 的 inode 号      读 local 的 inode            4
6  读 local 目录块，找 src     读 1 个目录块                5
7  得到 src 的 inode 号        读 src 的 inode              6
8  读 src 目录块，找 readme    读 1 个目录块                7
9  得到 readme 的 inode 号     读 readme 的 inode           8
```

答案：**8 次**。

如果题目再加一句「然后读取 readme 的第 1 个数据块」，就是 9 次。

如果题目说「所有目录项都已在内存（目录项缓存命中）」，那就只有 1 次——读 readme 的 inode。

如果题目说「连 readme 的 inode 也在内存」，答案是 0 次。

**所以这类题的答案完全取决于假设，第一步永远是把假设抄下来。**

再看一个变形：只读一次 `read()` 需要几次 I/O？

```text
open 已经做过（inode 和 offset 都在内存）：
  查进程级表    0 次（内存）
  查系统级表    0 次（内存）
  读数据块      1 次（如果不在页缓存里）
```

这就是为什么要区分「打开」和「读」。

打开贵，读便宜。

### 3.1 打开计数与 close

系统级表项里有一个「打开计数」。

```text
进程 A open 一次：计数 = 1
进程 A fork：子进程共享同一表项，计数 = 2
进程 A close：计数 = 1（表项不释放）
子进程 close：计数 = 0（表项释放）
```

计数归零才真正释放表项，但**不释放 inode**。

inode 什么时候释放，看的是 `i_nlink`，不是打开计数。

这是两个完全不同的计数器，混起来就错：

```text
打开计数（open count）  有多少个 fd 指着这个打开实例，归零释放表项
链接计数（link count）  有多少个目录项指向这个 inode，归零释放 inode 和数据块
```

一个文件可以 `nlink = 0` 但还开着（进程删了文件但没关），数据要等到 close 才真正消失。

Linux 里这很常见：临时文件 `open` 之后立刻 `unlink`，程序照常读写，退出时自动清理。

## 4. 逻辑结构：四种组织，四种访问代价

逻辑结构（logical structure）问的是：**文件内部，记录怎么排。**

从用户视角看，跟磁盘块怎么分配无关。

四种形态，从松到紧。

### 4.1 无结构（流式文件）

```text
文件 = 一串字节，没有记录边界
偏移 0    1000   2000   3000
  │        │      │      │
  ▼        ▼      ▼      ▼
[ bytes ................................ ]
```

读第 k 个字节，直接 `seek(k)` 然后 `read`。

```text
找一条「记录」：0 次额外 I/O，但记录边界要程序自己解析
随机访问：支持，按字节偏移
```

适合什么？编译器输出、日志、图片、可执行文件。

UNIX/Linux 的一切都是这种流。

缺点是「按关键字查一条记录」这件事，文件系统不帮你，得自己扫。

### 4.2 顺序文件

记录一条条排，可以定长也可以变长。

```text
定长记录，每条 100 字节：
记录 0: [0, 100)
记录 1: [100, 200)
记录 3 的起点 = 3 × 100 = 300   ← 一步算出来
```

```text
变长记录：不能算，只能从头扫
```

所以顺序文件分两种命运：

```text
定长 + 无序：算偏移直接定位，1 次 I/O，但按关键字查要扫全部
定长 + 按关键字有序：可以二分，平均 log2(N) 次
变长：只能顺序扫，平均 N/2 次
```

这就是 408 里「顺序文件查找一个记录平均要读多少个记录」的来源。

N 条记录，平均 (N+1)/2，约 N/2。

### 4.3 索引文件

给文件配一张索引表：关键字 → 记录地址。

```text
索引表（本身也是一个文件）
┌────────┬──────────┐
│ 关键字 │ 记录块号 │
├────────┼──────────┤
│  1001  │    7     │
│  1002  │    9     │
│  1003  │    3     │
└────────┴──────────┘
```

查一个记录：

```text
① 读索引表所在的块     1 次 I/O
② 按地址读记录所在的块  1 次 I/O
合计 2 次
```

如果索引表常驻内存，就是 1 次。

代价是索引表本身占空间、要维护。

**记录可以随便放，顺序完全不用管。** 这是索引文件最大的好处：插入一条记录不用挪数据，改索引就行。

### 4.4 索引顺序文件

索引顺序文件（indexed sequential file）是折中：记录**按关键字排序**，再分组建索引。

```text
记录：  [1001][1002][1003] | [1004][1005][1006] | [1007][1008][1009]
         └── 第 1 组 ──┘      └── 第 2 组 ──┘      └── 第 3 组 ──┘
索引：     1001→组1            1004→组2            1007→组3
```

N 条记录，分成 √N 组，每组 √N 条，索引表有 √N 项。

平均查找长度：

```text
查索引表：√N / 2
组内顺序查：√N / 2
合计：约 √N
```

N = 10000 时：

```text
顺序文件        平均 5000 次
索引顺序文件    平均 100 次
索引文件        2 次（但要额外的索引表空间）
```

**√N 这个数，是「排序 + 分组」带来的全部收益。**

它也是 408 里少见的、要求记住数量级的地方。

### 4.5 四种结构横向对比

```text
结构            记录定长  按关键字有序  查一条记录        随机访问  适合场景
─────────────────────────────────────────────────────────────────────────
无结构（流式）   无        无            1 次（定位即读）   支持     日志、编译产物、二进制
顺序文件（无序） 是        否            平均 N/2 次        支持     批处理顺序扫描
顺序文件（有序） 是        是            平均 log2 N 次     支持     静态字典、排序好的数据
索引文件        任意      否            2 次（索引+记录）  支持     随机查、频繁插入
索引顺序文件    任意      是            约 √N 次           部分     既要顺序扫又要按关键字查
```

一句话记：

```text
无结构靠偏移，顺序靠排序，索引靠表，索引顺序靠「排序 + 表」。
```

408 问「哪种结构适合随机访问」——除了变长顺序文件，其余都支持。

问「哪种结构查一条记录最省 I/O」——索引文件（2 次），但代价是空间。

问「哪种结构兼顾顺序扫描和随机查找」——索引顺序文件。

## 5. 目录、共享与保护

前面把文件本身讲完了。

现在讲「名字怎么组织」和「谁能动它」。

### 5.1 四种目录结构

**单级目录**：整个系统一张表。

```text
/ 目录
├── a.txt
├── b.txt
├── report.doc
└── ...（全部文件平铺）
```

问题三条：

```text
重名：两个用户都想叫 report.doc，冲突
查找：文件多时线性扫描，慢
分组：没有层次，无法表达「项目 A 的文件」
```

**两级目录**：一个主目录（MFD），每个用户一个用户目录（UFD）。

```text
主目录 MFD
├── alice → UFD_alice { report.doc, notes.txt }
├── bob   → UFD_bob   { report.doc, data.csv }
└── carol → UFD_carol { ... }
```

解决重名（不同用户可同名），但用户内部还是平铺，不能分组。

**树形目录**：目录里可以放目录，形成树。

```text
/
├── usr
│   ├── local
│   │   └── src
│   └── bin
└── home
    └── notes
        └── todo.md
```

有了绝对路径和相对路径，有了「当前目录」。

问题：**不便于共享**。同一个文件要在两个目录下都出现，只能复制两份。

**无环图目录**（acyclic graph directory）：允许一个文件（甚至目录）被多个父目录指向。

```text
/home/alice/project  ──┐
                       ├──▶ 同一个 inode（共享）
/home/bob/shared   ────┘
```

这就是共享。

代价是两个新问题：

```text
① 删除：删掉一个指针，另一个还指着，不能连数据一起删
② 遍历：图上有两条路径通到同一个文件，统计会重复计数
```

第 ① 个问题的答案就是链接计数。

第 ② 个问题的答案是「遍历时记住访问过的 inode」。

**悬挂指针（dangling pointer）** 出现在这里：如果删共享文件时不看引用计数，直接把 inode 和数据块释放，另一个目录项就指向了空地。

访问它，要么读到垃圾，要么内核报错。

所以正确的删除流程是：

```text
unlink(name):
    d = 目录里找到 name 的目录项
    从目录中删掉 d
    inode.i_nlink -= 1
    if inode.i_nlink == 0:
        释放 inode 的所有数据块
        释放 inode
    # 否则：只少了一个名字，文件还在
```

### 5.2 硬链接与软链接

硬链接（hard link）就是上面那个「多个目录项指向同一个 inode」。

```text
目录项： ("a.txt", 1043)
目录项： ("b.txt", 1043)   ← 同一个 inode 号
inode 1043：nlink = 2
```

创建硬链接，就是把 inode 号再写一份到另一个目录项，然后 `nlink++`。

```text
ln a.txt b.txt
  → 新增目录项 (b.txt, 同 inode)
  → inode.i_nlink = 2
```

软链接（symbolic link，符号链接）完全是另一回事：**它自己是一个文件**。

```text
c.txt 的 inode 里存的不是数据块指针链，
它的数据块里存的是一个字符串："a.txt"
文件类型标记为「符号链接」
```

```text
$ ls -li
1043 -rw-r--r-- 2 alice alice    6 Nov 10 00:10 a.txt
1043 -rw-r--r-- 2 alice alice    6 Nov 10 00:10 b.txt
1051 lrwxrwxrwx 1 alice alice    5 Nov 10 00:10 c.txt -> a.txt
```

注意三件事：

```text
a.txt 和 b.txt 的 inode 号相同（1043），nlink 都是 2
c.txt 的 inode 号是 1051，nlink 是 1，大小是 5（"a.txt" 的长度）
c.txt 的类型位是 l（link）
```

删除对比（这是必考的点）：

```text
操作：rm a.txt

硬链接 b.txt：
  目录项 (a.txt, 1043) 被删
  inode 1043 的 nlink 从 2 变成 1
  inode 和数据块都还在
  cat b.txt → hello          ✅

软链接 c.txt：
  c.txt 的 inode 1051 完好无损（它没被删）
  但它的内容 "a.txt" 已经解析不到了
  cat c.txt → No such file   ❌（悬挂）
```

画出来：

```text
rm a.txt 之前：
    a.txt ──┐
            ├──▶ inode 1043 ──▶ 数据块 "hello"
    b.txt ──┘
    c.txt ──▶ inode 1051 ──▶ 数据块 "a.txt" ──┐
                                                └─▶ 指向名字 a.txt

rm a.txt 之后：
    b.txt ──▶ inode 1043 ──▶ 数据块 "hello"     ✅ 还在
    c.txt ──▶ inode 1051 ──▶ "a.txt" ──▶ 找不到该名字 ❌
```

**硬链接让文件名变成「一个 inode 的多个入口」，软链接只是「一段写着路径的文本」。**

区别列成表（这是本篇第 1 张表）：

| 对比项 | 硬链接 | 软链接 |
|---|---|---|
| 指向什么 | inode | 路径字符串 |
| 有没有独立 inode | 没有，与原文件共用 | 有 |
| `nlink` 变化 | +1 | 不变（新链接自己是 1） |
| 能否跨文件系统 | 不能 | 能 |
| 能否指向目录 | 一般不允许（防环） | 可以 |
| 原文件删除后 | 仍可访问 | 悬挂，访问失败 |
| 删除链接本身 | `nlink--`，不影响原文件 | 删掉那个小文件，无关原文件 |

再补两个细节。

第一，硬链接不能跨文件系统，因为 inode 号只在单个文件系统内唯一。

`/` 和 `/mnt/usb` 是两个文件系统，`ln /mnt/usb/x /tmp/y` 会失败。

第二，软链接可以指向一个不存在的路径（悬空链接是合法的），硬链接不行，因为创建时就必须给出真实存在的 inode。

**所以软链接可以「预先生成」，硬链接必须「后向绑定」。**

### 5.3 文件保护：四层手段

保护回答的是：**谁能对这个文件做什么。**

四种手段，从弱到强。

**口令（password）**：每个文件带一个口令，访问前对一下。

```text
优点：实现极简，不需要用户体系
缺点：口令明文/哈希都存在文件里，超级用户能绕过
      文件多了记不住，通常全系统一个口令，等于没有
```

**加密（encryption）**：文件内容加密存储，没有密钥读出来是乱码。

```text
优点：连拷走磁盘都没用，绕过权限也读不懂
缺点：每次读写都要加解密，CPU 开销；密钥管理更麻烦
```

**访问控制列表（ACL，access control list）**：每个文件一张表，列出「谁 → 能做什么」。

```text
文件 report.doc 的 ACL：
  alice : rwx
  bob   : r--
  sales : rw-
  *     : ---
```

```text
优点：精细，能表达「某几个人可以写」
缺点：表可能很长，每次访问要遍历；用户多了管理成本高
```

**权限位（rwx）**：把 ACL 压缩成三组。

```text
        owner   group   other
        r w x   r w x   r w x
        1 1 1   1 0 1   0 0 1     → 751
```

`rwx` 三位分别表示读、写、执行，对目录含义不同：

```text
对普通文件： r 读内容，w 改内容，x 当程序执行
对目录：     r 列目录项，w 增删改名，x 进入（能访问里面的文件）
```

**目录的 x 位最容易被忽略：**

```text
有 r 无 x：能 ls 看到名字，但打不开里面任何文件
有 x 无 r：不能 ls，但知道名字就能直接访问
```

试一下：

```text
$ chmod 644 dir        # rw-r--r--
$ ls dir               # 可以列（有 r）
$ cat dir/a.txt        # Permission denied（没有 x，进不去）
```

这一条在真实系统里天天出问题，408 也考过「目录权限 r 和 x 的区别」。

## 6. 408 怎么考

这一块的题型很稳定，四类。

```text
① 目录结构判断：给一个场景，问该用哪种目录
② 硬链接/软链接：给操作序列，问 nlink、问还能不能访问
③ 读盘次数：给目录树和缓存假设，问检索一个文件要几次 I/O
④ 逻辑结构：给记录数和结构，问平均查找次数
```

套路只有一句：

```text
先把「哪些东西在内存、哪些在磁盘」列清楚，再数 I/O。
```

### 6.1 例题一：路径检索的 I/O 次数

题目（自拟）：

```text
某文件系统采用树形目录，inode 表存在磁盘上。
当前要打开 /usr/local/src/readme。
已知：
  (1) 根目录的 inode 已在内存；
  (2) 每个目录的 inode 需要读盘 1 次；
  (3) 每个目录的数据块需要读盘 1 次，且一个块能装下全部目录项；
  (4) 无任何目录项缓存。
求：打开该文件共需多少次磁盘 I/O？
```

解：

```text
根目录 inode        内存，0 次
根目录数据块        找 usr        1
usr 的 inode                      1   → 2
usr 目录数据块      找 local      1   → 3
local 的 inode                    1   → 4
local 目录数据块    找 src        1   → 5
src 的 inode                      1   → 6
src 目录数据块      找 readme     1   → 7
readme 的 inode                   1   → 8
```

答案 **8 次**。

验算一遍：三个中间目录 `usr`、`local`、`src`，每个贡献 2 次（inode + 数据块），共 6 次。

加上根目录数据块 1 次，共 7 次。

再加 readme 自己的 inode 1 次，共 8 次。✔

如果题目改一个字：「根目录的**数据块**也已在内存」，答案是 7 次。

如果改两个字：「所有目录项都已在内存」，答案是 1 次。

**改一个字变一次答案，这就是这类题的全部难度。**

### 6.2 例题二：链接计数

题目（自拟）：

```text
文件 F 的 inode 号为 500，初始 nlink = 1。
执行以下操作：
  ln F G          # 硬链接
  ln F H          # 硬链接
  ln -s F S       # 软链接
  rm F
  rm G
问：
  (1) 此时 inode 500 的 nlink 是多少？
  (2) H 还能不能读？S 还能不能读？
  (3) 再执行 rm H 之后，inode 500 会怎样？
```

解：

```text
初始                nlink = 1
ln F G              nlink = 2     （G 是第 2 个目录项）
ln F H              nlink = 3     （H 是第 3 个目录项）
ln -s F S           nlink = 3     （S 是新 inode，与 500 无关）
rm F                nlink = 2
rm G                nlink = 1
```

```text
(1) nlink = 1
(2) H 能读（nlink 还是 1，数据块都在）
    S 不能读（它存的是路径 "F"，而 F 这个目录项已经被删了）
    → 内核顺着路径找，返回 ENOENT，S 成为悬挂链接
(3) rm H 之后 nlink = 0，inode 500 和数据块被释放
    此时 S 彻底悬空，永远读不到
```

**注意第 (2) 问的分裂：同一个"删除"，对硬链接是减计数，对软链接是断路径。**

这就是 408 反复考的那个点。

### 6.3 例题三：逻辑结构的平均查找次数

题目（自拟）：

```text
一个文件有 10000 条定长记录，按关键字排列。
分别用「顺序文件」「索引文件」「索引顺序文件」组织，
问平均查找一条记录各需要多少次磁盘访问（索引表不在内存）？
```

解：

```text
顺序文件，已排序，可二分：log2(10000) ≈ 13.3，取 14 次
索引文件：2 次（读索引块 + 读记录块）
索引顺序文件：分成 100 组，每组 100 条
              查索引 平均 50 次（顺序查）+ 组内 50 次 = 100 次
              ≈ √10000 = 100
```

答案：**14 次、2 次、100 次**。

一句话总结这三个数：

```text
排序把 N/2 变成 log N；
建索引把查找变成 2 次，但要额外空间；
分组索引是中间态，把 N/2 变成 √N。
```

### 6.4 常见问法与陷阱

```text
问：fd 和 inode 号是同一个东西吗？        答：不是，fd 是进程表的索引
问：文件名存在 inode 里吗？               答：不存在，存在目录项里
问：删除文件时先删 inode 还是先删目录项？ 答：先删目录项，再减计数
问：目录的 r 和 x 分别是什么？            答：r 列名字，x 进入
问：一个文件能有几个硬链接？              答：理论上 nlink 上限个（如 65535）
```

## 7. 真实系统里长什么样

Linux ext4 的结构和上面讲的基本一致，只是字段更多。

**inode 表按块组分布。**

```text
块组 0              块组 1              块组 2
┌──────────┐       ┌──────────┐       ┌──────────┐
│ 超级块    │       │ 超级块副本│       │ 超级块副本│
│ 组描述符  │       │ ...      │       │ ...      │
│ 位示图    │       │          │       │          │
│ inode 表  │       │ inode 表 │       │ inode 表 │
│ 数据块    │       │ 数据块    │       │ 数据块    │
└──────────┘       └──────────┘       └──────────┘
```

每个块组都有自己的 inode 表和数据位示图（简化示意）。

inode 结构在磁盘上是 128 或 256 字节，`i_block` 有 15 个 32 位槽位。

ext2/ext3 用「12 直接 + 1 一级 + 1 二级 + 1 三级」的混合索引。

ext4 换成了 extent（区段）树，但 408 讲的仍然是经典的混合索引（18 篇会算）。

**看 inode 号。**

```bash
$ ls -i
1043 a.txt   1043 b.txt   1051 c.txt
$ stat a.txt
  File: a.txt
  Size: 6          Blocks: 8        IO Block: 4096  regular file
Device: 803h/2051d  Inode: 1043     Links: 2
Access: (0644/-rw-r--r--)  Uid: ( 1000/ alice)  Gid: ( 1000/ alice)
Access: 2026-11-10 00:10:00
Modify: 2026-11-10 00:10:00
Change: 2026-11-10 00:10:00
```

三个时间都在，`Links: 2` 就是 `i_nlink`。

**看 inode 的使用率。**

```bash
$ df -i
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/sda1      6553600 412033 6141567    7% /
```

`df -i` 看的是 inode 号用完了没有，不是空间用完了没有。

这解释了一个经典现象：

```text
磁盘还有空间，但创建文件失败，报 "No space left on device"
原因：inode 用完了（大量小文件）
```

**默认情况下 ext4 每 16 KB 分配一个 inode**，所以小文件多的目录很容易先把 inode 耗光。

`df` 看空间，`df -i` 看 inode，两个都要看。

**目录项缓存在内存里叫 dentry。**

```text
路径解析时，内核先查 dentry 缓存；
命中就直接拿到 inode，一次盘都不用读。
```

这就是前面第 6 节那道题「假设有缓存」时的真实情况。

冷启动 8 次，热路径 0 次。

**硬链接的几种真实限制。**

```text
① 不能跨文件系统：inode 号只在单个 fs 内唯一
② 默认不能给目录做硬链接：会形成环，破坏树形结构
③ . 和 .. 是例外，它们是目录自带的硬链接
```

`ls -ld dir` 看到的 `Links: 2+N`，N 是子目录个数——每个子目录的 `..` 都是一个指向父目录的硬链接。

```bash
$ mkdir -p d1/sub
$ ls -ld d1
drwxr-xr-x 3 alice alice 4096 ... d1     # 3 = 自己 + . + sub/..
```

这个细节几乎没考过，但能验证「目录能不能有硬链接」这个结论。

**软链接的表现。**

```bash
$ ln -s /very/long/path/target link
$ ls -l link
lrwxrwxrwx 1 alice alice 21 ... link -> /very/long/path/target
$ readlink link
/very/long/path/target
```

软链接的权限位永远是 `rwxrwxrwx`，因为它的权限由目标文件决定，自己的权限位没有意义（Linux 的实现细节）。

以上是简化示意，不含日志、extent、校验和这些细节。

## 8. 容易混淆的八个点

**① 文件名在 inode 里吗？**

不在。inode 只有 inode 号（由位置隐含），没有名字。

名字在目录项里。

**② 一个文件能有几个名字？**

多个，只要每个名字都是一个指向同一 inode 的目录项。

名字数量就是 `nlink`。

**③ 删除硬链接等于删除文件吗？**

不等于。只是把一个名字去掉。

`nlink` 归零才释放数据。

**④ 删除软链接的目标会怎样？**

软链接本身还在，只是解析失败。

内核不会因为目标消失去删链接。

**⑤ `open` 之后 `unlink` 会怎样？**

文件从目录里消失（新进程打不开），但已打开的描述符还能读写。

`close` 之后才真正释放。

这是「临时文件」的标准写法。

**⑥ fd 是文件编号吗？**

不是。fd 是**进程级打开文件表**的下标。

同一个文件在两个进程里，fd 可以完全不同。

**⑦ 目录是不是文件？**

是。目录也是文件，只是内容被规定为「目录项的数组」，而且只有内核能写。

所以目录也有 inode、有权限位、有大小。

**⑧ 逻辑结构和物理结构是一回事吗？**

不是。

```text
逻辑结构：用户看到的记录组织（流、顺序、索引）
物理结构：块在磁盘上怎么放（连续、链接、索引）
```

前者是「文件内部」，后者是「文件在盘上」。

408 常把这两组词混在一道题里，问「索引文件」和「索引分配」是不是一回事——不是。

## 9. 三个能自己验证的实验

这三个在 Linux 上五分钟能跑完，比背定义有效。

```bash
# 实验一：硬链接共享 inode，软链接不共享
$ echo hi > f1
$ ln f1 f2 ; ln -s f1 f3
$ ls -li f1 f2 f3
# 观察：f1 f2 的 inode 号相同，f3 不同

# 实验二：删除原文件
$ rm f1
$ cat f2      # hi
$ cat f3      # No such file or directory

# 实验三：nlink 归零才释放
$ echo data > g1 ; ln g1 g2
$ stat -c '%h %i' g1 g2      # 2 和同一个号码
$ rm g1 ; stat -c '%h' g2    # 1
$ rm g2                      # 此时数据块才释放
```

再加一个「目录 x 位」的实验：

```bash
$ mkdir d && echo x > d/f
$ chmod 644 d
$ ls d          # 能列出 f
$ cat d/f       # Permission denied
$ chmod 755 d
$ cat d/f       # x
```

`644` 是 `rw-r--r--`，没有 `x`，所以进不去目录。

**这条比任何定义都直观：目录的 r 是「看名字」，x 是「走进去」。**

## 10. 小结

这一篇的四层模型，压缩成一张图：

```text
名字（目录项）
   │  多个名字 → 一个 inode   ← 硬链接
   ▼
inode（元数据，无文件名）
   │  一个 inode → 一组块
   ▼
数据块（内容）
```

三个必须记住的结论：

```text
① 文件名在目录项里，不在 inode 里 → 所以能硬链接
② 硬链接减计数，软链接断路径 → 删除行为不同
③ open 把路径解析的结果缓存起来 → 之后 read 很便宜
```

四种逻辑结构对应四种代价：

```text
无结构 1 次，顺序文件 N/2 次（有序则 log N），索引 2 次，索引顺序 √N 次。
```

四种目录结构对应四种能力：

```text
单级 → 两级（解决重名）→ 树形（解决分组）→ 无环图（解决共享，代价是悬挂指针）
```

下一篇回答这一篇故意留下的问题：

```text
inode 里那 15 个块指针，怎么把「文件的第 5000 个块」映射到「磁盘的某个块」？
一个 4 KB 的块，怎么被文件系统借出去、收回来？
```

`i_block[15]` 里藏着 4 TB 的上限，位示图里藏着 32 MB 的开销。

下一篇全部算清楚：

```text
操作系统系统讲解 18：文件系统实现
```
