先算一笔账。

一个 Web 服务器，要同时处理 1000 个连接。

如果每个连接一个进程：

```text
1000 个进程
每个进程一个地址空间
每次切换：换 cr3、刷 TLB、缓存全冷
```

如果每个连接一个线程：

```text
1 个进程，1000 个线程
共享一个地址空间
每次切换：只换栈和寄存器，cr3 不动
```

第二种做法，切换成本差一个数量级。

**这就是线程存在的第一个理由。**

不是"写代码方便"，是"切换便宜"。

## 1. 这个问题解决什么

03 篇的结尾留了一个问题。

```text
进程切换 90% 的开销在换地址空间。
```

那能不能不换？

能。

```text
如果两个执行流本来就该共享同一份地址空间，
那切换时就不用换 cr3。
```

这就是线程。

但线程只解决了一半问题。

因为它默认"共享"。

如果两个执行流**不该**共享地址空间呢？

那就还需要另一套东西：让两个独立进程交换数据。

```text
进程通信（IPC，inter-process communication）
```

所以这一篇有两半。

```text
上半：一个进程内部，怎么有多条执行流  → 线程
下半：多个进程之间，怎么交换数据      → 通信
```

两半回答的是同一个问题的两面：

```text
隔离要多少，共享要多少。
```

## 2. 最小模型：一个进程里的多条执行流

先看图。

```text
进程（一个地址空间）
┌──────────────────────────────────────────┐
│  .text        代码段        ← 所有线程共享 │
│  .data/.bss   全局变量      ← 所有线程共享 │
│  heap         堆（malloc）  ← 所有线程共享 │
│                                          │
│  ┌────────┐  ┌────────┐  ┌────────┐      │
│  │ 线程 1 │  │ 线程 2 │  │ 线程 3 │      │
│  │ 栈     │  │ 栈     │  │ 栈     │ 私有  │
│  │ 寄存器 │  │ 寄存器 │  │ 寄存器 │ 私有  │
│  │ TID    │  │ TID    │  │ TID    │ 私有  │
│  └────────┘  └────────┘  └────────┘      │
└──────────────────────────────────────────┘
│  内核里：一组 task_struct，共享同一个 mm   │
└──────────────────────────────────────────┘
```

一张图记住两句话。

```text
地址空间是共享的。
栈和寄存器是私有的。
```

> **反直觉的点：线程不是"更轻的进程"。**
> **它是一个进程里的一条执行流，共享同一份地址空间。**
> **轻的是切换，不是隔离。**
> **恰恰相反：线程之间根本没有隔离。**

这句话的分量在后面。

因为它解释了线程的所有麻烦：

```text
共享 → 不用通信就能传数据 → 快
共享 → 一个线程写坏指针 → 全进程崩
共享 → 两个线程同时写一个变量 → 数据竞争
```

**线程把"通信成本"换成了"同步成本"。**

### 2.1 换个角度看 PCB

03 篇说 PCB 是进程存在的唯一标志。

有了线程之后，内核里管的对象变了。

```text
Linux 的做法：
  一个 task_struct 对应一个"可调度实体"
  线程和进程用的是同一个结构
  区别只在"哪些字段是共享的指针"
```

所以 Linux 内核里没有"线程"这个类型。

只有"task"，以及它共享了哪些资源。

```text
fork()   → 新 task，所有资源都复制（或 COW）
pthread_create() → 新 task，大部分资源共享
```

**这是理解 Linux 线程模型的关键：线程是"共享得更多的 task"。**

## 3. 一次完整走查：两个线程，一个算一个读

看一段代码。

```c
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>

int total = 0;

void *worker(void *arg) {
    for (int i = 0; i < 1000; i++) total += i;   /* 写全局变量 */
    return NULL;
}

void *reader(void *arg) {
    char buf[64];
    read(0, buf, sizeof(buf));                    /* 阻塞读 */
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, reader, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("total = %d\n", total);
    return 0;
}
```

走一遍。

```text
① main 调 pthread_create → glibc 调 clone(CLONE_VM | CLONE_FS | ...)
② 内核新建一个 task_struct，但 mm 指针指向同一个地址空间
③ 新线程的栈是新分配的（默认 8 MB 虚拟空间，按需提交）
④ 两个线程都进就绪队列
⑤ 调度器把 t1 放到 CPU0，t2 放到 CPU1（如果有多核）
⑥ t1 执行 total += i，t2 执行 read
⑦ t2 的 read 要等键盘 → 阻塞 → 只阻塞 t2 这个 task
⑧ t1 继续算，不受影响
⑨ 键盘输入 → t2 唤醒 → 继续
⑩ 两个线程 join 回来 → main 继续
```

第⑦步是分水岭。

```text
内核级线程：阻塞一个 task，其他 task 照样跑
```

如果换成用户级线程：

```text
⑦' t2 的 read 阻塞 → 内核看到的是"这个进程在阻塞"
    → 整个进程被挂起
    → t1 也停了
```

**这就是用户级线程的致命缺点。**

一个线程做了阻塞系统调用，整个进程陪着停。

### 3.1 用户级线程的伪代码

用户级线程由库来调度，内核完全不知情。

```c
/* 简化示意：一个极小的用户级线程调度器 */
typedef struct utcb {
    void *sp;            /* 该线程的栈指针 */
    int   state;         /* READY / RUNNING / BLOCKED */
    struct utcb *next;
} utcb_t;

utcb_t *ready_q;

void yield(void) {
    utcb_t *old = current;
    utcb_t *new = pick_next(ready_q);   /* 纯用户态选下一个 */

    if (old == new) return;
    old->state = READY;
    current = new;
    new->state = RUNNING;
    swapcontext(&old->ctx, &new->ctx);  /* 只换寄存器，不进内核 */
}
```

注意 `swapcontext` 这一行。

它只保存/恢复寄存器，不执行任何特权指令，不进内核。

```text
好处：切换成本极低（几十纳秒）
坏处：内核看不见这些线程
```

看不见意味着三件事：

```text
① 内核按"进程"调度，一个进程只占一个 CPU → 用户级线程不能并行
② 一个线程阻塞 → 内核挂起整个进程 → 全停
③ 时钟中断打断的是进程，库拿不到"线程级时间片"
```

## 4. 线程共享什么、私有什么

这是 408 最爱考的一格。

判据只有一条：

```text
这个东西，是"进程的资源"还是"执行流的状态"？
资源 → 共享
状态 → 私有
```

### 4.1 共享清单

```text
① 地址空间
   代码段（.text）
   数据段（.data、.bss）
   堆（heap，malloc 出来的）
   共享库的映射

② 打开的文件
   文件描述符表（fd table）
   当前读写偏移（同一个 fd 共享偏移）

③ 信号处理
   信号处理函数（signal handler）
   注意：信号屏蔽字是私有的

④ 进程级身份
   pid、ppid、用户 id、组 id、当前工作目录、根目录

⑤ 其他
   信号量、共享内存段、定时器
```

### 4.2 私有清单

```text
① 栈（stack）
   每个线程一个，独立的调用链

② 寄存器组
   通用寄存器、PC（程序计数器）、SP（栈指针）、PSW

③ 线程标识
   TID（Linux 上是 tid，等于内核里的 pid 字段）

④ 调度相关
   优先级、调度策略、时间片剩余

⑤ 信号屏蔽字
   每个线程可以屏蔽不同的信号

⑥ 线程局部存储（TLS）
   __thread 修饰的变量

⑦ errno
   每个线程一份，不然多线程会互相覆盖错误码
```

### 4.3 为什么栈必须私有

因为栈上放的是"函数调用的现场"。

```text
void f() {
    int x = 1;      ← x 在栈上
    g();
}
```

两个线程同时调 `f`，各有一份 `x`。

如果共享栈，两个 `x` 会互相覆盖，返回地址也会乱。

**函数调用这件事，本质就是"用一个私有栈"来实现的。**

同理，PC 必须私有。

PC 指向"我下一条要执行的指令"。

两个线程如果共用一个 PC，那就不是两个执行流，是一个。

### 4.4 一个反例：堆是共享的

```c
void *worker(void *arg) {
    char *p = malloc(100);   /* 堆，共享 */
    ...
}
```

`malloc` 内部维护一张空闲链表。

两个线程同时 `malloc`，会同时改这张表。

```text
现象：随机崩溃、内存泄漏、double free
```

所以 `malloc` 内部必须加锁（或者用线程本地缓存）。

**"共享堆"不是免费的，代价是分配器要线程安全。**

### 4.5 一个容易忽略的细节：fd 共享意味着偏移共享

```c
/* 两个线程，同一个 fd */
int fd = open("a.txt", O_RDONLY);

/* 线程 1 */
read(fd, buf1, 10);

/* 线程 2 */
read(fd, buf2, 10);
```

两次读，拿到的是文件的前 10 字节和后 10 字节。

因为文件偏移（file offset）在"打开文件表项"里，不在 fd 里。

```text
fd 表（每进程一张） → 指向打开文件表项（系统级）
                      表项里存：偏移、读写标志、引用计数
```

两个线程共享同一张 fd 表，所以共享同一个偏移。

```text
想各读各的？用 pread（带偏移的读），它不动共享偏移。
```

这个细节解释了为什么多线程读同一个文件会"互相抢位置"。

## 5. 容易混淆的点

### 5.1 线程切换 ≠ 进程切换

```text
线程切换：换栈、换寄存器、不换 cr3
进程切换：换栈、换寄存器、换 cr3、刷 TLB
```

差的就是"换不换地址空间"。

### 5.2 线程多 ≠ 跑得快

```text
4 核机器跑 4 个线程，可能加速 4 倍（如果完全独立）
4 核机器跑 400 个线程，可能更慢（调度和切换开销）
```

而且有个硬上限：Amdahl 定律。

```text
如果 50% 的工作必须串行，无论多少核，加速比不超过 2。
```

计算：

```text
加速比 = 1 / (串行比例 + 并行比例 / N)
N → ∞ 时，加速比 → 1 / 串行比例 = 1 / 0.5 = 2
```

### 5.3 用户级线程不能被多核并行

```text
内核只看到一个进程 → 只分一个 CPU → 里头的线程只能交替
```

这是判定题的核心。

题干出现"用户级线程"+"多处理机"，答案通常是"不能真正并行"。

### 5.4 通信不是"必须的"，是"隔离的代价"

```text
同一进程的两个线程：直接读写全局变量，不用通信机制
两个进程：          必须通过内核（共享内存/管道/socket）
```

所以 408 问"为什么进程通信需要操作系统介入"。

答案：因为它们有独立的地址空间。

### 5.5 共享内存也需要同步

```text
共享内存是"最快的通信方式"
但它只提供了"能互相看见"，没提供"不打架"
```

两个进程同时写同一个位置，照样出错。

信号量、文件锁、原子操作，一个都不能少。

### 5.6 线程安全的三件套

既然共享会打架，工程上有三种应对。

```text
① 互斥锁（mutex）
   进临界区前 lock，出来 unlock
   代价：竞争激烈时阻塞，切换开销

② 原子操作（atomic）
   用 CPU 的一条指令完成"读-改-写"
   代价：只能做简单操作（加、交换、比较并交换）

③ 线程局部存储（TLS）
   干脆不共享，每个线程一份
   代价：数据没法在线程间传递
```

三者的选择顺序：

```text
能不共享就不共享（TLS）
必须共享且操作简单，用原子
必须共享且逻辑复杂，用锁
```

408 不考这三者的 API，但会问"为什么需要同步"。

答案永远同一个：

```text
因为它们共享地址空间，而共享不带秩序。
```

## 6. 408 怎么考

这一篇对应进程管理的第二块：线程与通信。

题型：

```text
① 判断哪些资源线程共享、哪些私有 —— 高频
② 给一个场景，判断是用户级线程还是内核级线程
③ 用户级线程的缺点（阻塞、不能并行）
④ 三种通信方式的对比与选择
⑤ 管道的特点（半双工、字节流、亲缘关系）
⑥ 线程切换与进程切换的成本比较
```

三条套路。

**套路一：资源 → 共享，执行状态 → 私有。**

```text
代码、数据、堆、文件、信号处理 → 共享
栈、寄存器、PC、TID、errno   → 私有
```

**套路二：看"内核知不知道"。**

```text
内核看不见 → 用户级 → 不能并行、一阻塞全阻塞、切换快
内核看得见 → 内核级 → 能并行、各自阻塞、切换慢
```

**套路三：通信方式按"数据量 + 是否跨机"选。**

```text
大数据、同一台机器、要快     → 共享内存 + 信号量
小消息、要同步、结构清晰     → 消息传递
父子进程、单向字节流         → 管道
跨机器                       → socket
```

### 6.1 例题一：判断共享

自拟，按真题风格。

```text
同一进程内的两个线程，下列哪些是共享的？

Ⅰ. 栈
Ⅱ. 程序计数器 PC
Ⅲ. 全局变量
Ⅳ. 打开的文件描述符表
Ⅴ. 线程 ID
Ⅵ. 信号处理函数
Ⅶ. errno

A. Ⅲ、Ⅳ、Ⅵ
B. Ⅲ、Ⅳ、Ⅴ、Ⅵ
C. Ⅱ、Ⅲ、Ⅳ、Ⅵ
D. Ⅲ、Ⅳ、Ⅵ、Ⅶ
```

逐条。

Ⅰ 栈：私有。每个线程独立调用链。

Ⅱ PC：私有。不然就不是两条执行流。

Ⅲ 全局变量：共享。在数据段里。

Ⅳ 文件描述符表：共享。同进程共用一张 fd 表。

Ⅴ 线程 ID：私有。TID 标识执行流。

Ⅵ 信号处理函数：共享。信号是整个进程的事。

Ⅶ errno：私有。glibc 用 TLS 实现的。

答案 A。

三个坑：Ⅳ（很多人以为 fd 是私有的）、Ⅵ（信号处理共享，但屏蔽字私有）、Ⅶ（errno 居然是私有的）。

### 6.2 例题二：算阻塞的代价

自拟。

```text
某程序要处理 4 个任务。
每个任务：CPU 计算 5 ms，然后 I/O 等待 10 ms。

求：
(1) 用用户级线程（多对一）实现，总耗时多少？
(2) 用内核级线程、4 核机器实现，总耗时多少？
(3) 用内核级线程、1 核机器实现，总耗时约多少？
```

(1) 用户级线程

```text
线程 A 算 5 ms → I/O 阻塞 → 内核挂起整个进程
  → 线程 B、C、D 全都跑不了
A 的 I/O 完成（10 ms）→ 进程恢复 → B 算 5 ms → 阻塞
每个任务占 5 + 10 = 15 ms
总耗时 = 4 × 15 = 60 ms
```

60 ms。

(2) 内核级 + 4 核

```text
4 个任务完全并行，各占一个核
每个任务 5 ms 计算 + 10 ms I/O
最长的那个决定总时间 = 15 ms
```

15 ms。

(3) 内核级 + 1 核

CPU 只有一块，4 个任务的计算必须排队。

但 I/O 可以和别人的计算重叠。

排时间轴（每个任务只算一次，算完就等 I/O）：

```text
t=0    A 算（0-5），然后等 I/O 到 15
t=5    B 算（5-10），然后等 I/O 到 20
t=10   C 算（10-15），然后等 I/O 到 25
t=15   D 算（15-20），然后等 I/O 到 30
t=15   A 的 I/O 完成 → A 结束
t=20   B 的 I/O 完成 → B 结束
t=25   C 的 I/O 完成 → C 结束
t=30   D 的 I/O 完成 → D 结束
```

逐个结算：

```text
A：0-5 算，5-15 等 → 15 结束
B：5-10 算，10-20 等 → 20 结束
C：10-15 算，15-25 等 → 25 结束
D：15-20 算，20-30 等 → 30 结束
```

总时间 30 ms，由最后一个任务 D 的 I/O 尾巴决定。

CPU 利用率：

```text
20 ms / 30 ms ≈ 66.7%
```

三个数字：60 ms、15 ms、30 ms。

结论：

```text
用户级线程：60 ms（最差，一次阻塞被放大成四次）
内核级 + 4 核：15 ms
内核级 + 1 核：30 ms
```

**用户级线程在多核机器上，比内核级线程在单核上还慢。**

这就是"模型选错"的代价。

顺带一个可以自己验的结论：

```text
如果每个任务的 I/O 时间改成 1 ms，
三个答案会变成 24 ms、6 ms、21 ms。
```

因为 I/O 短了，瓶颈就从 I/O 变成 CPU。

**算这类题，先看瓶颈在哪条资源上。**

## 7. 真实系统里长什么样

### 7.1 clone 的共享标志

Linux 用一个系统调用造出进程和线程。

```c
/* 简化示意 */
int clone(int (*fn)(void *), void *stack,
          int flags, void *arg);

/* 造一个线程 */
clone(fn, stack,
      CLONE_VM | CLONE_FS | CLONE_FILES
    | CLONE_SIGHAND | CLONE_THREAD | CLONE_SYSVSEM,
      arg);
```

每个标志对应"共享哪一块"：

```text
CLONE_VM       共享地址空间（页表）     ← 最关键
CLONE_FS       共享文件系统信息（cwd、根目录）
CLONE_FILES    共享文件描述符表
CLONE_SIGHAND  共享信号处理函数
CLONE_THREAD   放进同一个线程组（同一个 tgid）
CLONE_SYSVSEM  共享 System V 信号量的 undo 信息
```

```text
一个都不加 → 就是 fork，完全独立
加 CLONE_VM → 就是线程
```

**"线程"在 Linux 里不是一个类型，是一组标志。**

### 7.2 /proc 里能看见

```text
$ ls /proc/1234/task/
1234  1235  1236
```

`/proc/<pid>/task/` 下每个目录是一个线程。

主线程的 tid 等于 pid。

所以：

```text
$ ps -eLf | head
```

`LWP` 那一列就是 tid。

### 7.3 NPTL 是一对一

glibc 的 NPTL 实现：

```text
pthread_create → clone(CLONE_VM|...) → 一个内核 task
```

一个用户线程，对应一个内核线程。

好处：

```text
能利用多核
一个阻塞不影响别人
内核调度公平
```

坏处：

```text
线程数上限受内核限制（几千到几万）
每次创建都要进内核
```

历史上还有另一种做法：

```text
LinuxThreads（老实现）：管理线程 + 信号模拟 → 问题多
NGPT（多对多，已废弃）：太复杂，没进主线
```

**Linux 最后选了最简单的一对一。**

### 7.4 线程切换在硬件上是什么样

```text
① 时钟中断 / 系统调用 → 进内核
② 内核把当前 task 的寄存器存进它的内核栈
③ 选下一个 task
④ 如果 mm 相同（同进程的另一个线程）：
     不换 cr3
   否则：
     换 cr3（或用 PCID 只换标记）
⑤ 换内核栈指针
⑥ 恢复新 task 的寄存器
⑦ iret 回用户态
```

第④步是成本差的分水岭。

### 7.5 xv6 没有线程

xv6 一个进程只有一个执行流。

```text
struct proc 里没有"线程"这个概念
调度单位就是进程
```

要加线程，得改 `fork`、改 `struct proc`、加共享计数。

**教学内核故意不做这件事，因为它会掩盖进程的本质。**

### 7.6 线程池为什么存在

```c
for (int i = 0; i < 100000; i++) {
    pthread_create(&t, NULL, handle, arg);   /* 每个请求一个线程 */
    pthread_join(t, NULL);
}
```

这段代码能跑，但很慢。

因为 `pthread_create` 要进内核：

```text
分配 task_struct、分配内核栈、分配用户栈、进调度队列
```

一次创建 + 销毁，量级是微秒。

如果一个请求只要 100 微秒，创建线程的开销就占了 10%。

所以有了线程池：

```text
启动时创建 N 个线程，让它们阻塞在一个任务队列上
来了请求 → 塞进队列 → 某个线程被唤醒 → 处理
```

```c
/* 简化示意 */
while (1) {
    task = queue_pop(&q);     /* 队列空就阻塞 */
    task->run(task);
}
```

代价：

```text
任务队列变成共享资源 → 要加锁
线程数和队列长度要调（太大了切换多，太小了堆积）
```

**线程池是"用一次同步换 N 次创建"的交易。**

## 8. 三种实现：用户级、内核级、组合

### 8.1 用户级线程

```text
线程库在用户态实现
内核只看到进程
切换：swapcontext，不进内核
```

优点：

```text
切换极快（几十纳秒）
可以在任何 OS 上跑（不需要内核支持）
应用可以自定义调度策略
```

缺点：

```text
一个线程阻塞 → 整个进程阻塞
不能利用多核
内核按进程分时间片，线程之间"分蛋糕"
```

### 8.2 内核级线程

```text
每个线程是一个内核可调度实体
切换要进内核
```

优点：

```text
能利用多核
一个阻塞不影响别人
内核可以按线程调度
```

缺点：

```text
切换要过边界（微秒级）
线程数受内核资源限制
```

### 8.3 组合（多对多）

```text
n 个用户线程 映射到 m 个内核线程
n > m
```

```text
线程库负责：n 个用户线程 → m 个内核线程的复用
内核负责：  m 个内核线程 → CPU 的调度
```

优点：

```text
既能大量创建，又能利用多核
一个用户线程阻塞，库可以把另一个挂到别的内核线程上
```

缺点：

```text
两级调度，实现复杂
一次阻塞要让库"感知"到，得用非阻塞 I/O 或调度器激活（scheduler activation）
```

这一套太复杂，主流系统最后都放弃了。

```text
Solaris 试过，Linux 试过（NGPT），都回到一对一。
```

### 8.4 三种模型对照

```text
多对一（用户级）：
  快，但不能并行，一阻塞全阻塞

一对一（内核级）：
  能并行，但创建/切换贵，数量受限

多对多（组合）：
  理论上最好，工程上最难
```

408 的判断法：

```text
题目说"线程库管理" → 用户级
题目说"内核感知每个线程" → 内核级
题目说"n 个用户线程映射到 m 个内核线程" → 组合
```

## 9. 线程切换 vs 进程切换：便宜在哪

### 9.1 成本对比

```text
操作                     量级
线程切换（同进程）        0.5 - 1 μs
进程切换（换地址空间）    3 - 5 μs
```

差 4 到 5 倍。

差在哪？

```text
线程切换：保存/恢复寄存器 + 换栈
进程切换：上面全部 + 换 cr3 + 刷 TLB + 缓存变冷
```

### 9.2 算一笔账

假设每秒要切换 5000 次。

```text
进程切换：5000 × 3.8 μs = 19000 μs = 19 ms
线程切换：5000 × 0.9 μs = 4500 μs  = 4.5 ms
差值：    14.5 ms/s ≈ 1.45% 的 CPU
```

单看比例不大。

但如果切换频率是每秒 10 万次（高并发服务器常见）：

```text
进程切换：100000 × 3.8 μs = 380000 μs = 380 ms
线程切换：100000 × 0.9 μs = 90000 μs  = 90 ms
差值：    290 ms/s = 29% 的 CPU
```

**29% 的 CPU，白烧在换地址空间上。**

这就是为什么高并发服务器用线程，不用进程。

### 9.3 但线程不是免费的

```text
① 同步成本：共享就有竞争，要加锁
② 调试成本：一个线程崩，全进程崩
③ 栈空间：每个线程 8 MB 虚拟空间（默认），1000 个线程就是 8 GB 虚拟地址
④ 隔离成本：一个线程的野指针，能踩坏别的线程的数据
```

第③条值得算一下。

```text
1000 个线程 × 8 MB = 8000 MB = 7.8 GB 虚拟地址空间
```

64 位系统不在乎（地址空间有 128 TB）。

32 位系统直接爆（用户空间才 3 GB）。

所以 32 位时代的服务器，线程数上限常常是几百。

### 9.4 什么时候反而该用多进程

线程不是万能答案。

有些场景，隔离比切换便宜更重要。

```text
① 一个执行流可能被不可信代码污染（浏览器）
   一个标签页崩了，不能带着整个浏览器一起崩

② 需要不同的权限（Web 服务器以不同用户跑不同站点）

③ 需要不同的地址空间布局（32 位程序、特定映射）

④ 语言运行时限制（Python 的 GIL 让多线程算不了并行）
```

所以 Chrome 是"一个标签页一个进程"。

nginx 是"一个 worker 一个进程，进程内单线程 + 事件循环"。

```text
Apache prefork：多进程
Apache worker： 多线程
Nginx：        多进程 + 每进程非阻塞
```

三种路线的取舍，和这一篇的结论完全一致：

```text
要隔离 → 多进程，切换贵
要便宜 → 多线程，没隔离
要两者兼顾 → 多进程 + 每进程少线程
```

## 10. 通信之一：共享内存

### 10.1 怎么做

```c
/* 简化示意：POSIX 共享内存 */
int fd = shm_open("/mybuf", O_CREAT | O_RDWR, 0600);
ftruncate(fd, 4096);

char *p = mmap(NULL, 4096, PROT_READ | PROT_WRITE,
               MAP_SHARED, fd, 0);

/* 现在 p 指向一块两个进程都能看见的内存 */
strcpy(p, "hello");
```

关键在 `MAP_SHARED`。

```text
MAP_PRIVATE：写时复制，各写各的
MAP_SHARED： 写到同一块物理页，互相可见
```

### 10.2 为什么最快

```text
两个进程的页表，都有一项指向同一个物理页框。
进程 A 写 → 直接写进物理内存
进程 B 读 → 直接从物理内存读
中间没有内核参与。
```

对比管道：

```text
进程 A write → 内核缓冲区（一次拷贝）
进程 B read  → 从内核缓冲区拷出来（又一次拷贝）
```

**共享内存省掉两次拷贝，所以最快。**

### 10.3 但它只解决"看得见"

```text
共享内存 = 一块公共黑板
它不保证"你写的时候我不写"
```

所以必须配同步：

```text
① 信号量（sem_wait / sem_post）
② 互斥锁（pthread_mutex，需要放在共享内存里且属性为 PTHREAD_PROCESS_SHARED）
③ 文件锁（flock / fcntl）
④ 原子操作 + 自旋
```

408 的经典问法：

```text
"共享内存为什么需要同步？"
答：它只提供地址映射，不提供互斥。
```

### 10.4 什么时候选它

```text
数据量大（MB 级）    → 共享内存
访问频繁（每秒几万次）→ 共享内存
只是偶尔传个小消息    → 管道/消息队列更省事
```

一句话：

```text
共享内存快，但你要自己管秩序。
```

### 10.5 和内存映射文件的关系

```text
mmap 一个文件，MAP_SHARED
```

效果和共享内存几乎一样：

```text
两个进程映射同一个文件 → 共享同一批物理页
写内存 = 写文件（由内核在背后刷回去）
```

区别只在"后备存储"：

```text
共享内存：后备是内存（或 /dev/shm 里的 tmpfs）
映射文件：后备是磁盘文件，断电还在
```

所以 14 篇讲内存映射文件时，会再遇到这套机制。

**同一个机制，两个用途：一个用来通信，一个用来读写文件。**

## 11. 通信之二：消息传递与管道

### 11.1 消息传递

两种寻址方式。

```text
直接通信：
  send(P, msg)     发给进程 P
  receive(Q, msg)  收来自 Q 的消息
  缺点：要写死对方 pid

间接通信：
  send(mailbox, msg)     发到信箱
  receive(mailbox, msg)  从信箱收
  优点：解耦，多个进程可以共享一个信箱
```

缓冲队列三种。

```text
零容量：发送方必须等到接收方就绪（会合，rendezvous）
有界：  缓冲区满了，发送方阻塞
无界：  发送方从不阻塞（内存无限的前提下）
```

消息传递的好处：

```text
不用同步（消息本身就是同步点）
天然支持跨机器（socket 就是消息传递）
内核可以做权限检查
```

坏处：

```text
每次都要进内核，拷贝两次
数据量大时慢
```

### 11.2 管道

管道是"半双工的字节流"。

```c
int fd[2];
pipe(fd);

if (fork() == 0) {
    close(fd[0]);            /* 子进程只写，关掉读端 */
    write(fd[1], "hello", 5);
    close(fd[1]);
} else {
    close(fd[1]);            /* 父进程只读，关掉写端 */
    char buf[16];
    int n = read(fd[0], buf, sizeof(buf));
}
```

两个 `close` 不是为了省资源，是必需的。

```text
写端全关掉之后，读端的 read 才会返回 0（EOF）。
不关写端，读端会永远等下去。
```

三个特点。

```text
① 半双工：数据只能单向流
   想双向？开两个管道

② 字节流：没有消息边界
   写两次 "ab" "cd"，读端可能一次读到 "abcd"
   要边界就得自己加长度前缀或分隔符

③ 内核缓冲区：Linux 默认 64 KB
   写满了，write 阻塞
```

还有一条 408 常考的：

```text
匿名管道只能用于有亲缘关系的进程（fork 继承 fd）
```

要跨任意进程，用命名管道：

```text
$ mkfifo /tmp/myfifo
$ echo hi > /tmp/myfifo     # 一个终端
$ cat /tmp/myfifo           # 另一个终端
```

命名管道在文件系统里有个名字。

但它不存数据，数据还在内核缓冲区里。

```text
$ ls -l /tmp/myfifo
prw-r--r-- 1 user user 0 ... /tmp/myfifo
```

开头的 `p` 就是 pipe。

### 11.3 管道的原子性

```text
PIPE_BUF = 4096（Linux）
写入不超过 PIPE_BUF 且管道有空位 → 这次写是原子的
超过 PIPE_BUF → 可能和别人的写交错
```

这条细节 408 不考，但写代码时踩过就知道疼。

### 11.4 一个经典用法：把管道当同步点

```c
int fd[2];
pipe(fd);
if (fork() == 0) {
    /* 子进程 */
    char c;
    read(fd[0], &c, 1);      /* 等父进程发信号 */
    /* 干活 */
} else {
    /* 父进程 */
    write(fd[1], "x", 1);    /* 发信号 */
}
```

`read` 会一直阻塞到有数据。

所以管道既能传数据，也能当"事件通知"用。

### 11.5 socket 一句话

```text
管道只能在一台机器上，
要把这套"字节流 + 缓冲区"搬到网络上，就是 socket。
```

TCP socket = 跨机器的双向字节流管道。

### 11.6 三种方式怎么选

```text
共享内存
  拷贝：0 次（映射之后直接读写）
  同步：自己加
  适用：大数据、本机、高频

消息传递
  拷贝：2 次（进内核、出内核）
  同步：机制自带
  适用：小消息、需要解耦、需要权限检查

管道
  拷贝：2 次（写进内核缓冲区、读出）
  同步：写满阻塞、读空阻塞
  适用：父子进程、单向流、命令行组合
```

判据一句话：

```text
要快 → 共享内存（自己管同步）
要省心 → 消息传递
要串命令 → 管道
要跨机器 → socket
```

## 12. 小结

这一篇的骨架：

```text
一个动机：进程切换贵在换地址空间
一个定义：线程 = 共享地址空间的一条执行流
两张清单：共享（地址空间/文件/信号处理）
          私有（栈/寄存器/TID/errno）
三种实现：用户级、内核级、组合
三个模型：多对一、一对一、多对多
两条腿：线程切换便宜（不换 cr3）、线程没有隔离（共享一切）
三种通信：共享内存（最快，要同步）
          消息传递（直接/间接，三种缓冲）
          管道（半双工、字节流、亲缘/命名）
```

如果只记一句话：

```text
线程把"通信成本"换成了"同步成本"。
```

回到那个反直觉的点：

```text
线程轻的是切换，不是隔离。
切换便宜，是因为它不换地址空间；
没有隔离，也是因为它不换地址空间。
```

同一件事，既是优点，也是全部麻烦的来源。

这也是整个第二块（进程管理）的走向：

```text

07-10 篇：共享之后怎么不打架
11 篇：打得太狠会死锁
```
