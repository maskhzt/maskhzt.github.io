> **读这篇之前，你只需要知道**：进程是什么（一个正在跑的程序，可以想成一个正在干活的人）、缓冲区是什么（一块临时存放数据的区域，像蒸笼的格子）、信号量是什么（一个只能加一减一的整数，用来记「还剩几个」）。
> **这篇讲什么**：几个人共用一块地方干活时，怎么排队，才能既不出错、又不互相卡死。
> **一个类比**：包子铺的蒸笼有 4 格，厨师往里放包子，顾客从里面拿。厨师不能往满的蒸笼里塞，顾客不能从空的蒸笼里拿，两个人也不能同时把手伸进同一个格子。

先把三个词说清，后面全篇都在用它们。

**缓冲区（buffer）**：一块临时存放数据的区域。

在包子铺里，它就是那个蒸笼。

**互斥（mutual exclusion）**：同一时刻只允许一个进程动某样东西。

对应「两个人不能同时把手伸进同一个格子」。

**同步（synchronization）**：两个进程之间要讲好先后，一个做完了，另一个才能做。

对应「厨师先放进去，顾客才能拿」。

这两个词经常一起出现，但管的是两件不同的事。

```text
互斥：不能同时。
同步：要有先后。
```

后面四个经典问题，都是这两件事的不同组合。

先看两段代码。

它们只差两行的位置。

```c
/* A */
P(empty);
P(mutex);
```

```c
/* B */
P(mutex);
P(empty);
```

缓冲区 4 个槽，一个生产者，一个消费者。

A 能跑一整天。

B 在缓冲区第一次被填满之后，就永久停住了。

不是变慢，是停住。

两个进程都在等对方松手。

**这一篇讲的四个经典问题，错误几乎都长这样：位置差一点，程序从「排队等」变成「互相等」。**

## 1. 三个信号量各自在管什么

先问一句：如果这三个信号量一个都不设，会怎样？

厨师和顾客各干各的，谁也不知道蒸笼里还剩几个格子。

顾客伸手一摸是空的，白跑一趟。

厨师一看还有空位就往里塞，结果把顾客刚拿起来的包子又压了回去。

程序不会崩，只是数据会错，而且错得随机。

同一份代码，压测一千次可能一次都不出错，上线第二天才出问题。

所以要把「还剩几个」这件事记成数字，让两个人都能看见。

生产者-消费者的约束只有三条。

```text
① 缓冲区满时，生产者不能写。
② 缓冲区空时，消费者不能读。
③ 任何时刻，只有一个进程能改动缓冲区。
```

前两条是同步，第三条是互斥。

于是三个信号量。

```text
mutex = 1     互斥：现在谁能动缓冲区
empty = n     同步：还剩几个空槽
full  = 0     同步：已经放了几个产品
```

初值不是背出来的，是数出来的。

```text
mutex 保护一份资源（缓冲区），初值 1。
empty 的初值是「一开始有几个空槽」，就是 n。
full  的初值是「一开始有几个产品」，就是 0。
```

画出来是这样。

```text
             ┌────── 缓冲区（n 个槽）──────┐
             │ [0] [1] [2] ... [n-1]        │
             └──────────────────────────────┘
生产者                                  消费者
  │ P(empty)  拿一个空槽                   │ P(full)  拿一个产品
  │ P(mutex)  独占缓冲区                   │ P(mutex)
  │ 写 buffer[in]                         │ 读 buffer[out]
  │ V(mutex)                              │ V(mutex)
  │ V(full)   多了一个产品                 │ V(empty) 多了一个空槽
  ▼                                       ▼
```

完整代码。

```c
semaphore mutex = 1;
semaphore empty = n;
semaphore full  = 0;
int in = 0, out = 0;

void producer() {
    while (1) {
        item = produce();
        P(empty);              // 先确认有空槽
        P(mutex);              // 再抢缓冲区的门
        buffer[in] = item;
        in = (in + 1) % n;
        V(mutex);
        V(full);               // 产品数 +1
    }
}

void consumer() {
    while (1) {
        P(full);               // 先确认有产品
        P(mutex);
        item = buffer[out];
        out = (out + 1) % n;
        V(mutex);
        V(empty);              // 空槽数 +1
        consume(item);
    }
}
```

两句要读准。

```text
P(empty) 问的是「有没有位置放」，不是「能不能进」。
P(mutex) 问的才是「能不能进」。
```

所以 P(empty) 必须写在 P(mutex) 前面。

原因下一节算给你看。

**反例：如果彻底去掉 mutex 会怎样**

留一个反例在这儿，后面读代码时会清楚它到底在挡什么。

蒸笼 4 格，现在 `empty = 2`，两个厨师同时来放包子。

```text
厨师 A：P(empty) → empty = 1，看一眼，第 2 格是空的
厨师 B：P(empty) → empty = 0，看一眼，第 2 格也是空的
厨师 A：把包子放进第 2 格
厨师 B：把包子放进第 2 格      ← 同一个格子
```

A 的包子被 B 的包子盖住了。

```text
蒸笼里实际只多了 1 个包子，empty 却减了 2。
计数和实物对不上，而且没有任何报错。
```

顾客按 `full` 去取，会取到一个已经被覆盖的位置。

更糟的情况是 `in` 被两个厨师各加一次。

指针跳过一格，那一格永远空着，永远没人填。

这就是互斥信号量真正防的事。

```text
它防的不是「同时写坏内存」这种低级错误。
它防的是「两个人都以为自己独占了这个格子」。
```

## 2. 一次完整走查：缓冲区怎么被填满的

为什么非要跟着数字走一遍？

因为 PV 代码的形状太像了。

一行 P、一行写、一行 V，光看很难分辨哪一行管「计数」、哪一行管「排队」。

而信号量一旦变成负数，含义会突然变复杂——负几，就代表有几个人在等。

这件事只能在数字里看明白。

取 n = 4。

初始 `empty = 4, full = 0, mutex = 1`。

生产者连续放四个产品。

```text
放第 1 个：P(empty) → empty=3
           P(mutex) → mutex=0
           写入；V(mutex) → mutex=1；V(full) → full=1

放第 2 个：empty=2, full=2
放第 3 个：empty=1, full=3
放第 4 个：empty=0, full=4
```

现在缓冲区满了。

生产者下一轮再来：

```text
P(empty)：empty 从 0 减到 -1，自己没有进门就阻塞了。
```

记录型信号量（就是「一个整数 + 一个等待队列」的那种信号量）的负值是有含义的。

```text
value > 0：还有 value 个资源可用。
value = 0：刚好用完，没人在等。
value < 0：有 |value| 个进程在等这个资源。
```

所以 `empty = -1` 读作：一个空槽都没有，并且有一个生产者在等空槽。

消费者这时候取走一个。

```text
P(full)：full 从 4 减到 3，不阻塞。
P(mutex)：mutex=1 → 0，进临界区。
取出 buffer[out]，out 后移一位。
V(mutex)：mutex=0 → 1。
V(empty)：empty 从 -1 变 0，并唤醒那个阻塞的生产者。
```

被唤醒的生产者，从 `P(empty)` 的下一句继续。

它**不会**再减一次 empty。

```text
P 的减，发生在阻塞之前。
被唤醒的意思是「那次减现在算数了」，不是「重新减一次」。
```

这一点第一次读 PV 代码的人多半会绕一下。

还有一处容易漏。

`in` 和 `out` 也是共享变量。

它们必须和 `buffer[]` 一起，待在 mutex 的临界区（critical section，一段「同一时刻只能一个人进来」的代码）里。

少保护一个指针，两个生产者就可能算出同一个下标，互相覆盖。

顺带记住这个环形下标的性质。

```text
in 是「下一个要写的位置」，out 是「下一个要读的位置」。
两者都只增不减，靠 % n 绕回来。
缓冲区空和满时，in == out 都可能成立，
所以判断空满不能看指针，只能看 empty / full 两个计数。
```

这也是为什么生产者-消费者问题里必须有两个同步信号量，而不能只用一个。

一个只能区分「空」和「非空」，区分不了「满」。

## 3. 把两个 P 换个位置

为什么要专门为一处「写法顺序」开一节？

因为这是整篇唯一一个「代码看起来几乎一样、行为完全相反」的地方。

两行换一下，程序从「排队等」变成「互相等」。

而且改错题里出现它的概率最高。

回到开头那段 B。

```c
void producer() {
    while (1) {
        item = produce();
        P(mutex);              // ① 先抢门
        P(empty);              // ② 再等空槽
        buffer[in] = item;
        in = (in + 1) % n;
        V(mutex);
        V(full);
    }
}
```

缓冲区满时，走一遍。

```text
已知：empty = 0, full = 4, mutex = 1

生产者：P(mutex) → mutex = 0，进了临界区
        P(empty) → empty = -1，阻塞
        ★ 它是在临界区里阻塞的，门还握在手里

消费者：P(full) → full = 3，通过
        P(mutex) → mutex = -1，阻塞
        ★ 它要进门，但门被生产者握着
```

现在两边都在等。

```text
生产者等 empty 变正 —— 只有消费者取走产品，empty 才会变正
消费者等 mutex 变正 —— 只有生产者退出临界区，mutex 才会变正
```

而生产者要退出临界区，必须先拿到 empty。

消费者要取走产品，必须先拿到 mutex。

一个闭环。

这就是死锁（deadlock）：几个进程各自握着对方要的东西，谁都不肯先放，于是谁也无法前进。

```text
   生产者 ──持有──▶ mutex
      │                ▲
      │等待            │等待
      ▼                │
   empty ──持有──▶ 消费者
```

> **反直觉的点**：这段代码的死锁，不在「信号量个数不够」，而在两个 P 的先后顺序。
> 把 `P(empty)` 和 `P(mutex)` 换个位置，代码读起来几乎一样，含义却从「排队等」变成「占着门等」。
> 死锁不是资源不足造成的，是**持有并等待**造成的——这正是 [11 篇](/posts/os-deadlock/) 要拆的四个必要条件之一。

### 3.1 为什么 V 的顺序无所谓

生产者最后两句是：

```c
V(mutex);
V(full);
```

换成：

```c
V(full);
V(mutex);
```

也对。

原因很短。

```text
V 不阻塞。V 只做两件事：值加一，唤醒一个等待者。
```

所以两个 V 谁先谁后，不会让任何进程卡住。

习惯上还是先 `V(mutex)`：

```text
先把门让出来，别人能早点进。
临界区越短，并发度越高。
```

P 就完全不是这样。

```text
P 会阻塞。
先 P 谁，决定了「卡住的时候手里握着什么」。
握着门等资源 = 死锁。
等到了资源再拿门 = 安全。
```

这条不对称，是整篇最该带走的一句。

### 3.2 缓冲区大小为 1 时会发生什么

n = 1 时，两个同步信号量的取值范围被锁死了。

```text
empty 只能是 0 或 1。
full  只能是 0 或 1。
并且 empty + full = 1 恒成立。
```

于是：

```text
缓冲区空：empty=1, full=0。生产者过得了 P(empty)，消费者卡在 P(full)。
缓冲区满：empty=0, full=1。消费者过得了 P(full)，生产者卡在 P(empty)。
```

任何时刻，最多只有一个进程能穿过自己的第一个 P。

另一个必然在等。

互斥已经被保证了。

```text
n = 1 时，mutex 是多余的，可以删掉。
```

```c
semaphore empty = 1;
semaphore full  = 0;

void producer() {
    while (1) {
        item = produce();
        P(empty);
        buffer[0] = item;
        V(full);
    }
}

void consumer() {
    while (1) {
        P(full);
        item = buffer[0];
        V(empty);
        consume(item);
    }
}
```

两句话要说清楚。

```text
① 这是「因为容量恰好是 1」，不是「mutex 没用」。
   n = 2 时，两个生产者可以同时通过 P(empty)，就必须有 mutex。
② 删掉 mutex 可以，换顺序不行。
   如果留着 mutex 却写成 P(mutex) 在前，缓冲区满时一样死锁。
```

所以 408 那句判断题的答案是：

```text
「缓冲区大小为 1 时还需要互斥信号量吗？」
不需要。同步信号量已经隐含互斥。
```

## 4. 读者-写者：为什么需要两把锁

先说没有它会怎样。

假设只用一把锁保护数据。

那么两个读者也不能同时读了。

一个人读的时候，另一个人被锁在门外。

可读操作根本不改数据，本来完全没必要排队。

图书馆里十个人同时看同一本书，谁也不影响谁。

但只要有一个人在改这本书，其他人都得等。

读者-写者问题要的正是这个效果。

所以约束变了。

```text
多个读者可以同时读，互不影响。
写者写的时候，不许任何人读，也不许别人写。
```

注意第一句。

读者之间不互斥。

所以不能只用一把锁。

用一把锁，读者就排成一队了。

需要两把，各管一件事。

```text
rw_mutex   保护数据：写者与所有人互斥
mutex      保护计数器 readcount：谁能改这个整数
```

再加一个整数，记「现在有几个读者在读」。

```text
readcount = 0  没有任何读者
readcount > 0  有人在读，写者必须等
```

结构是这样。

```text
            读者 1..k                     写者
               │                            │
        ┌──────┴──────┐                     │
        │  readcount  │ ◀── mutex           │
        └──────┬──────┘                     │
               │                            │
    第一个读者 P(rw_mutex)                   │ P(rw_mutex)
    最后一个读者 V(rw_mutex)                 │
               ▼                            ▼
        ┌────────────────────────────────────┐
        │            共享数据                 │
        └────────────────────────────────────┘
```

### 4.1 读者优先

```c
int readcount = 0;
semaphore rw_mutex = 1;      // 数据锁
semaphore mutex    = 1;      // 保护 readcount

void reader() {
    P(mutex);
    if (readcount == 0)      // 我是第一个读者
        P(rw_mutex);         // 把写者挡在门外
    readcount++;
    V(mutex);

    read_data();

    P(mutex);
    readcount--;
    if (readcount == 0)      // 我是最后一个读者
        V(rw_mutex);         // 放写者进来
    V(mutex);
}

void writer() {
    P(rw_mutex);
    write_data();
    V(rw_mutex);
}
```

这里最关键的是一句「双重加锁」。

```c
if (readcount == 0) P(rw_mutex);
```

它必须待在 `P(mutex)` 和 `V(mutex)` 之间。

不能在外面。

```text
在外面：两个读者可能同时读到 readcount == 0，
        两次 P(rw_mutex)，第二次就把自己锁死了。
在里面：readcount 的读、判断、自增是一个原子块（原子：中间不会被打断，别人插不进来），安全。
```

走一遍时间线。

```text
R1 到：P(mutex) 进；readcount 0 → P(rw_mutex) 拿走；readcount=1；V(mutex)；开始读
R2 到：P(mutex) 进；readcount 1 ≠ 0，不碰 rw_mutex；readcount=2；V(mutex)；开始读
W  到：P(rw_mutex) → 阻塞（被 R1 拿走了）
R3 到：P(mutex) 进；readcount 2 ≠ 0；readcount=3；V(mutex)；开始读
R1 读完：readcount 2；不还 rw_mutex
R2 读完：readcount 1
R3 读完：readcount 0 → V(rw_mutex) → W 被唤醒
```

看出问题了。

W 在 R2、R3 全部读完之前，一步都动不了。

只要读者源源不断地来，`readcount` 就永远不回 0。

写者永远等。

```text
这叫写者饿死（writer starvation）。
不是死锁——写者不是被谁握着，只是永远排不上。
```

### 4.2 写者优先

要反过来，就得再加一个信号量当「闸门」。

再配一个写者计数器。

```c
int readcount = 0, writecount = 0;
semaphore rw_mutex     = 1;
semaphore count_mutex  = 1;   // 保护 readcount
semaphore wcount_mutex = 1;   // 保护 writecount
semaphore w_gate       = 1;   // 闸门：写者一到就关

void reader() {
    P(w_gate);                // 先看闸门关没关
    P(count_mutex);
    if (readcount == 0)
        P(rw_mutex);
    readcount++;
    V(count_mutex);
    V(w_gate);

    read_data();

    P(count_mutex);
    readcount--;
    if (readcount == 0)
        V(rw_mutex);
    V(count_mutex);
}

void writer() {
    P(wcount_mutex);
    if (writecount == 0)
        P(w_gate);            // 第一个写者关闸
    writecount++;
    V(wcount_mutex);

    P(rw_mutex);
    write_data();
    V(rw_mutex);

    P(wcount_mutex);
    writecount--;
    if (writecount == 0)
        V(w_gate);            // 最后一个写者开闸
    V(wcount_mutex);
}
```

关键在 `w_gate`。

```text
第一个写者到达 → 关闸。
新来的读者卡在 P(w_gate)，进不去。
已经在读的读者不受影响，读完自然散场。
最后一个写者离开 → 开闸。
```

代价反过来了。

```text
写者源源不断 → 闸一直关着 → 读者饿死。
```

所以「读者优先」和「写者优先」不是好坏之分。

是把饿死风险分配给了不同的一方。

把写者优先也走一遍。

```text
状态：R1 正在读（rw_mutex 被 R1 拿走，readcount = 1）
W1 到：P(wcount_mutex)；writecount 0 → P(w_gate)，闸门关闭
       writecount = 1；V(wcount_mutex)
       P(rw_mutex) → 阻塞（R1 还拿着）
R2 到：P(w_gate) → 阻塞（闸门关了）
R1 读完：readcount 0 → V(rw_mutex)
W1 被唤醒：写入
W1 写完：writecount 0 → V(w_gate)，闸门打开
R2 通过 P(w_gate)，继续排队
```

关键的一步是 `W1` 刚到达就关闸。

```text
它还没开始写，就已经把新读者挡在外面了。
所以「写者优先」不是「写者写得快」，是「写者一到就排队头」。
```

代价也很清楚。

```text
W1 后面又来 W2、W3……闸门一直不开。
R2 在 P(w_gate) 上等到所有写者走完。
```

### 4.3 公平

公平的意思是：按到达顺序排队，谁都别插队。

做法只有一个方向。

```text
让读者和写者共用同一个 FIFO 队列。
先到的先被服务，后来的排在后面，不管它是读还是写。
```

具体一点。

```text
① 每个读者、每个写者到达时，先在这个队列上取一个号。
② 队列是 FIFO 的（信号量的等待队列天然是 FIFO）。
③ 排到的人再做「读者登记」或「写者排队」，然后干活。
④ 干完活，叫下一位。
```

用信号量硬写会很长，因为它需要「取号 + 叫号」两个计数器再加两个信号量。

```text
408 对「公平」只要求到这个结论层面：
公平 = 加排队机制，按到达顺序服务，牺牲并发度换不饿死。
```

三种策略摆在一起。

```text
读者优先：读者可能让写者饿死。
写者优先：写者可能让读者饿死。
公平：都不饿死，但并发度最低（读者也可能被前一个写者挡住）。
```

## 5. 哲学家进餐与吸烟者

这一节换两个场景，专门练一件事：从代码里看出「环」。

前面的生产者-消费者只涉及两个人，环最多两步，很容易看出来。

到了五个人，环藏在对称性里，反而看不见了。

吸烟者那题又是另一种结构：一个生产者，三个各等各的消费者。

### 5.1 死锁是怎么凑出来的

五个哲学家，五把筷子，围一圈。

每人要两把才能吃。

```text
      P0
   ┌──────┐
 P4 │      │ P1        筷子 i 在 Pi 和 P(i+1) 之间
   ┌┴──────┴┐
 P3│        │P2
   └────────┘
```

最朴素的写法：

```c
semaphore chopstick[5] = {1, 1, 1, 1, 1};

void philosopher(int i) {
    while (1) {
        think();
        P(chopstick[i]);              // 左
        P(chopstick[(i + 1) % 5]);    // 右
        eat();
        V(chopstick[(i + 1) % 5]);
        V(chopstick[i]);
    }
}
```

五个人的动作完全对称，这就是问题所在。

```text
第 1 步：五个人同时拿起左边那把。
        结果：五把筷子全部为 0，每人手里一把。
第 2 步：五个人同时去拿右边那把。
        结果：每个人的右边，正好是邻居的左边，被邻居握着。
```

```text
P0 持 0 等 1
P1 持 1 等 2
P2 持 2 等 3
P3 持 3 等 4
P4 持 4 等 0
```

首尾相接。

```text
P0 等的是 P1 手里那把 1 号
P1 等的是 P2 手里那把 2 号
P2 等的是 P3 手里那把 3 号
P3 等的是 P4 手里那把 4 号
P4 等的是 P0 手里那把 0 号
                     │
                     └──▶ 又回到 P0，成环
```

循环等待，死锁。

还有一个不等号要分清。

```text
死锁：五个人全部卡住，谁也不能动。
饥饿：某个人一直抢不到两把筷子，别人轮流吃。
```

朴素写法在运气好的时候不会死锁。

```text
五个人错开时间拿筷子，就没事。
偏偏这种「概率上没事」的代码最难查——压测一万次不出错，上线第二天卡死。
```

所以哲学家这一题的真正考点不是「会不会死锁」。

是「你能不能看出这段代码没有对顺序做任何约束」。

注意死锁的成因不是「筷子只有五把」。

五把筷子够五个人轮流吃。

成因是「每人只拿到一半，就再也不松手」。

### 5.2 解法一：最多四个人同时拿

```c
semaphore chopstick[5] = {1, 1, 1, 1, 1};
semaphore count = 4;          // 最多四个人同时抢

void philosopher(int i) {
    while (1) {
        think();
        P(count);                        // 领号，最多四人
        P(chopstick[i]);
        P(chopstick[(i + 1) % 5]);
        eat();
        V(chopstick[(i + 1) % 5]);
        V(chopstick[i]);
        V(count);                        // 交号
    }
}
```

为什么管用？

抽屉原理。

```text
五个人抢五把筷子，如果同时只有四个人在抢，
必然至少有一个人拿齐了两把。
他吃完放下，链条就断了一环。
```

破坏的是**循环等待**：环需要五个人都参与，而第五个人根本进不来。

### 5.3 解法二：奇偶顺序

破坏对称性，让环接不上。

```c
void philosopher(int i) {
    while (1) {
        think();
        if (i % 2 == 0) {                 // 偶数号：先左后右
            P(chopstick[i]);
            P(chopstick[(i + 1) % 5]);
        } else {                          // 奇数号：先右后左
            P(chopstick[(i + 1) % 5]);
            P(chopstick[i]);
        }
        eat();
        V(chopstick[(i + 1) % 5]);
        V(chopstick[i]);
    }
}
```

推一遍。

```text
P0 拿 0，再拿 1
P1 拿 2，再拿 1     ← 反过来了，先抢右边
P2 拿 2，再拿 3
P3 拿 4，再拿 3
P4 拿 4，再拿 0
```

现在看谁和谁撞。

```text
筷子 0：P0 想要，P4 也想要。
        但 P4 是偶数号，先拿 4；P0 也是先拿 0。
        两个人不可能同时「先拿 0 再等别人」形成闭环。
```

更准确的看法是：

```text
资源被编号以后，所有进程要么按升序申请，要么按降序申请。
升序和降序不可能组成一个环。
```

这也是第 11 篇「有序分配法」的雏形。

### 5.4 解法三：AND 型信号量

要么两把一起拿到，要么一把都不拿。

```c
void philosopher(int i) {
    while (1) {
        think();
        P(chopstick[i], chopstick[(i + 1) % 5]);   // AND 型，原子地拿两把
        eat();
        V(chopstick[i], chopstick[(i + 1) % 5]);
    }
}
```

AND 型信号量的语义是：

```text
所有资源都可用 → 一次性全部分配，继续执行。
只要有一个不可用 → 一个都不分配，进程阻塞。
```

它破坏的是**请求并保持**。

```text
哲学家不再「持有一把、再等一把」。
等待的时候手里是空的，所以不会锁住邻居。
```

三种解法的对照，一句话一个。

```text
最多四人：限制参与人数，让环凑不齐。
奇偶顺序：给申请方向定规矩，让环连不上。
AND 型  ：取消「拿一半」，让环没有起点。
```

### 5.5 吸烟者：一个生产者，三个挑剔的消费者

桌上有一个供应者，三个吸烟者。

每人自己带一种原料，无限供应。

```text
吸烟者 A：自带烟草，缺纸和胶水
吸烟者 B：自带纸，缺烟草和胶水
吸烟者 C：自带胶水，缺烟草和纸
```

供应者每次往桌上放两种原料。

能凑齐的那位拿走材料（桌子空了），然后卷烟、抽。

```c
semaphore offer1  = 0;   // 放了「纸 + 胶水」
semaphore offer2  = 0;   // 放了「烟草 + 胶水」
semaphore offer3  = 0;   // 放了「烟草 + 纸」
semaphore finish  = 0;   // 桌子空了，可以放下一轮

void supplier() {
    int i = 0;
    while (1) {
        i = (i + 1) % 3;
        if (i == 0) {
            put(paper, glue);
            V(offer1);
        } else if (i == 1) {
            put(tobacco, glue);
            V(offer2);
        } else {
            put(tobacco, paper);
            V(offer3);
        }
        P(finish);            // 等这一轮被消费掉
    }
}

void smokerA() {              // 自带烟草
    while (1) {
        P(offer1);
        take(paper, glue);
        V(finish);            // 桌子空了
        smoke();
    }
}

void smokerB() {              // 自带纸
    while (1) {
        P(offer2);
        take(tobacco, glue);
        V(finish);
        smoke();
    }
}

void smokerC() {              // 自带胶水
    while (1) {
        P(offer3);
        take(tobacco, paper);
        V(finish);
        smoke();
    }
}
```

三个信号量各有一个初值 0，就是「三种组合各自就绪了没有」。

`finish` 是第四个信号量，作用是**轮流**。

```text
供应者放完就 P(finish)，它必须等这一轮被取走，才能放下一轮。
所以桌上永远只有一份组合，三个吸烟者不会抢。
```

如果去掉 `finish`：

```text
供应者会连着放三份，桌上堆三种组合。
三个吸烟者同时被唤醒，同时去拿，桌子就需要额外互斥。
```

这个问题的结构值得单独记一下。

```text
一个生产者，多个消费者。
但「唤醒谁」不是由消费者自己决定的，是由生产者选的。
```

这正是信号量比「一个 mutex 加一个条件变量」更细的地方。

条件变量（condition variable）：管程内部的一块「等候区」，进程在里面挂起，等别人来叫醒；它不记账，只负责叫醒，详见 [10 篇](/posts/os-monitor/)。

```text
条件变量只有两种叫法：叫醒某一个（不确定是谁）、叫醒全部。
信号量因为队列是按用途分的，「叫谁」非常明确。
```

所以「三个消费者各等各的」这种结构，用信号量写最直接。

```text
三个信号量 = 三个专用队列。
用条件变量写，就得维护一个状态变量再加广播，然后靠 while 各自过滤。
```

## 6. 408 怎么考

这一节不复习概念，只做一件事：把上面四个问题，翻译成考卷上的三种问法。

为什么要翻译？

因为代码会写不等于题会做。

改错题给你的那段代码，一定是「能跑、但某个时刻会停」的。

你要在三十秒内指出哪一行，靠的是一张检查清单，不是感觉。

这一节的题型就三种。

```text
① 写 PV：给一个场景，写出完整代码。
② 改错：给一段代码，指出错在哪、为什么错。
③ 判断：某时刻信号量的值、会不会死锁、缓冲区为 1 还要不要 mutex。
```

写 PV 的四步，按顺序做。

```text
① 数角色：有几类进程？各类几个？
② 数资源：每类临界资源有几个？→ 互斥信号量，初值 = 资源数
③ 找依赖：谁等谁？「有东西才能取」「有空位才能放」→ 同步信号量，初值 0
④ 排顺序：同步 P 在前，互斥 P 在后；V 紧跟临界区
```

第 ④ 步是唯一需要动脑的地方。

一条判据：

```text
凡是「等一个可能永远不来的东西」，就不能在持锁状态下等。
```

### 6.1 例题一：改错

缓冲区 4 个槽。下面两段代码有 3 处问题。

```c
semaphore mutex = 1, empty = 4, full = 0;
int in = 0, out = 0;

void producer() {
    while (1) {
        item = produce();
        P(mutex);
        P(empty);
        buffer[in] = item;
        in = (in + 1) % 4;
        V(mutex);
        V(full);
    }
}

void consumer() {
    while (1) {
        P(full);
        P(mutex);
        item = buffer[out];
        out = (out + 1) % 4;
        consume(item);
        V(mutex);
    }
}
```

**问题 1：生产者的两个 P 顺序反了。**

缓冲区满（`empty = 0`）时，生产者先拿到 mutex，再阻塞在 `P(empty)`。

消费者被 `P(mutex)` 挡住，拿不到产品。

两边互等，死锁。

改法：交换两行。

```c
P(empty);
P(mutex);
```

**问题 2：消费者少了 `V(empty)`。**

`empty` 只减不增。

缓冲区被取空一次以后，`empty` 就再也回不到正数。

生产者永久阻塞在 `P(empty)`。

这不是死锁，是信号量泄漏导致的永久停滞。

改法：在 `V(mutex)` 之后补一句。

```c
V(mutex);
V(empty);
```

**问题 3：`consume(item)` 写在临界区里。**

正确性没问题，但把「消费」这个耗时动作塞进了临界区。

临界区从三行变成「三行加一次消费」。

并发度白白下降。

改法：把 `consume(item)` 挪到 `V(mutex)` 之后。

改完是这样。

```c
void producer() {
    while (1) {
        item = produce();
        P(empty);
        P(mutex);
        buffer[in] = item;
        in = (in + 1) % 4;
        V(mutex);
        V(full);
    }
}

void consumer() {
    while (1) {
        P(full);
        P(mutex);
        item = buffer[out];
        out = (out + 1) % 4;
        V(mutex);
        V(empty);
        consume(item);
    }
}
```

### 6.2 例题二：算信号量的值

缓冲区 4 个槽，初值 `empty = 4, full = 0, mutex = 1`。

某时刻缓冲区满，另有 2 个生产者阻塞在 `P(empty)` 上，没有进程在临界区内。

问此时三个信号量的值。

按记录型信号量的定义算。

```text
缓冲区满 → 4 个槽全被占 → 空槽计数为 0。
2 个生产者阻塞在 P(empty) → empty 的值再减 2 → empty = -2。
full = 4（4 个产品），没有消费者阻塞 → full = 4。
没有进程在临界区 → mutex = 1。
```

答案：

```text
empty = -2
full  = 4
mutex = 1
```

再往前推一步。

现在来了一个消费者，它取走一个产品。

```text
P(full)：full 4 → 3，不阻塞。
P(mutex)：mutex 1 → 0，进临界区。
取走一个产品，V(mutex)：mutex 回 1。
V(empty)：empty 从 -2 变 -1，唤醒一个阻塞的生产者。
```

此时：

```text
empty = -1   （还剩 1 个生产者在等）
full  = 3
mutex = 1
```

被唤醒的那个生产者继续执行，放进一个产品。

```text
V(full)：full 3 → 4，缓冲区又满了。
empty 仍是 -1，因为还有一个生产者没拿到空槽。
```

最终：

```text
empty = -1, full = 4, mutex = 1
```

每一步都对得上，这就是这类题的解法。

```text
先按「资源还剩多少」写正数部分，
再按「有几个人在等」写负数部分，
最后按「有没有人在临界区」定 mutex。
```

## 7. 真实系统里长什么样

> 以下是简化示意，函数名取自 POSIX 与 Linux 内核，行为细节有删减。

为什么要专门看一节真实代码？

因为教材上的 P/V 像一套独立的小语言，容易让人以为它只活在试卷里。

实际正好相反：它的每一种写法，在真实系统里都有一个对应物，只是换了名字。

看懂这层对应，考场上那些「为什么非得这么写」的规定，就都有理由了。

P/V 这两个字母来自 Dijkstra 1965 年的论文。

```text
P = proberen（荷兰语，尝试/测试）
V = verhogen（荷兰语，增加）
```

在 POSIX 里，名字换成了 `sem_wait` / `sem_post`。

```c
#include <semaphore.h>

sem_t empty, full, mutex;

sem_init(&mutex, 0, 1);
sem_init(&empty, 0, 4);
sem_init(&full,  0, 0);

sem_wait(&empty);     // P(empty)
sem_wait(&mutex);     // P(mutex)
/* ... */
sem_post(&mutex);     // V(mutex)
sem_post(&full);      // V(full)
```

`sem_wait` 的快速路径在用户态完成。

```text
用一条原子指令把计数减一。
减成功 → 直接返回，不进内核。
减失败（或发现有人排队）→ 走 futex 系统调用，把自己挂到内核等待队列。
```

这就是 futex（fast userspace mutex）的思路：没人竞争时完全不进内核。

Linux 内核自己写生产者-消费者，几乎不用「三个计数信号量」这个形状。

```text
内核里更常见的是：
  一个 mutex 保护数据
  两个等待队列（wait queue）：一个等「有空间」，一个等「有数据」
  这两个队列对应下一讲的「条件变量」
```

原因是信号量只能表示「还剩几个」，而队列能携带唤醒语义、优先级和超时。

读者-写者有现成的实现。

```text
POSIX 线程：pthread_rwlock_t，pthread_rwlock_rdlock / wrlock / unlock
Linux 内核：struct rw_semaphore，down_read / up_read / down_write / up_write
```

Linux 的 rwsem 有一个细节值得记。

```text
有写者在排队时，新的读者会被挡在门外。
这样写者不会被源源不断的读者饿死。
```

也就是「写者优先」的工程版本。

至于哲学家进餐，真实内核里几乎不会出现「五个进程抢五把筷子」这种纯形式。

但它的教训是内核的硬规矩：

```text
多把锁必须按固定顺序获取。
顺序一乱，就是哲学家问题。
Linux 用 lockdep（CONFIG_PROVE_LOCKING）静态检查锁的获取顺序。
```

吸烟者的结构在真实系统里到处都是。

```text
「几样东西凑齐了才能继续」：
  链接器等所有目标文件就绪
  DMA 完成且缓冲区空闲才启动下一次传输
  select / poll 等一组文件描述符中任意一个就绪
```

最后补一句工程上的取舍。

```text
线程之间传少量「事件」：用条件变量更自然。
线程之间传「配额」（还剩几个缓冲区、还剩几个连接）：用信号量更自然。
因为信号量的计数本身就是配额，不需要再维护一个整数加一把锁。
```

这也是为什么数据库连接池、内存池这类「有固定配额」的场合，信号量至今还在用。

## 8. 找错题：三个典型错误

考试里的改错题，几乎不会让你从零写一段 PV。

它考的永远是「这三类错，你能不能在三十秒内指出来」。

所以这一节按错误分类，不按问题分类。

错误分三类。

记住这三类，比记住四个问题的代码有用。

### 8.1 第一类：P 的顺序反了

```c
P(mutex);
P(empty);        // 错：持锁等资源
```

判断方法：

```text
看每个进程阻塞的时候，手里握着什么。
如果握着锁在等一个需要别人拿锁才能改变的量，就是死锁。
```

### 8.2 第二类：少一个 V

```c
P(empty);
P(mutex);
buffer[in] = item;
in = (in + 1) % n;
V(mutex);        // 少了 V(full)
```

判断方法：

```text
每对 P/V 都要配对。
数一遍：每个信号量 P 了几次、V 了几次。
互斥信号量有 P 必有 V；同步信号量是「我 V 你 P」，跨进程配对。
```

少 V 的症状不是立刻卡死，是「跑一会儿才停」。

因为资源是慢慢漏光的。

### 8.3 第三类：mutex 保护错对象

```c
P(empty);
buffer[in] = item;      // 错：没进临界区
in = (in + 1) % n;      // 错：指针也没保护
V(mutex);               // 错：V 了一个没 P 过的 mutex
V(full);
```

这一段的错更隐蔽，因为程序很多时候能跑对。

两个问题。

```text
① buffer[in] 和 in 没有被保护，两个生产者可能算出同一个 in，互相覆盖。
② 没有 P 就 V，mutex 从 1 变成 2。
```

第二个问题最致命。

```text
mutex = 1 时，P 一次变 0，别人进不来。
mutex = 2 时，P 一次变 1，还是正数，第二个人照样能进。
互斥彻底失效，而且不报错。
```

所以检查 mutex 时，问三个问题：

```text
① 临界区里保护的是不是同一组变量？
② 这些变量是不是被所有访问它的进程都保护了？
③ P 和 V 是不是成对，而且成对在同一个进程里？
```

## 9. 多个生产者、多个消费者

为什么这一节值得单独写？

因为考场上最常见的改法，就是把「一对一」改成「多对多」，看你会不会慌。

很多人第一反应是「人多了，锁也得加一把」。

结果多加的那把锁毫无用处，还多了一个死锁点。

题目把「一个生产者一个消费者」改成「m 个生产者、k 个消费者」，代码要不要改？

不用改。

```text
mutex 保护的是「谁能动缓冲区」，跟有几个人无关。
empty 记的是空槽总数，谁拿都一样。
full  记的是产品总数，谁取都一样。
```

三个信号量本来就是按「资源」记数的，不是按「进程」记数的。

所以多对多的情况下，同一份代码直接能用。

```c
void producer_i() {          // 第 i 个生产者，代码和单生产者完全一样
    while (1) {
        item = produce_i();
        P(empty);
        P(mutex);
        buffer[in] = item;
        in = (in + 1) % n;
        V(mutex);
        V(full);
    }
}
```

但有一个常见的错法。

有人觉得「多个生产者之间也要互斥」，于是加了一把新锁。

```c
semaphore pmutex = 1;        // 多余
P(pmutex);
P(empty);
P(mutex);
...
```

这把锁不是错，是没用。

```text
mutex 已经让所有生产者、所有消费者排成一队。
再加一把，只是多一次加解锁，还多一个可能的死锁点。
```

真正需要注意的不是加锁，是**共享变量的范围**。

```text
in、out 是共享变量，必须在 mutex 里改。
item 是局部变量，不用保护。
produce() 和 consume() 是耗时的，必须放在临界区外。
```

最后一条最容易被忽略。

```text
把 produce() 放进临界区 → 所有生产者串行生产 → 并发度归零。
```

再看一个数字。

```text
n = 4，m = 10 个生产者，k = 10 个消费者。
某一时刻缓冲区空，full = 0。
10 个消费者全部阻塞在 P(full) 上 → full = -10。
此时一个生产者放入 1 个产品，V(full) → full = -9，只唤醒 1 个消费者。
剩下 9 个继续等。
```

这就是记录型信号量的唤醒语义：**V 一次只唤醒一个**。

```text
不是「条件满足了，大家都来看一眼」。
是「我放了一个，就只够一个人用」。
```

这条差异，正是下一讲条件变量 `signal` 和 `broadcast` 的分界线。

## 10. 容易混淆的点

**同步信号量和互斥信号量。**

```text
互斥信号量：初值 1，同一进程 P 又 V，保护一段代码。
同步信号量：初值 0（或资源数），一个进程 P、另一个进程 V，传递「事件发生了」。
```

**信号量的值不等于缓冲区里的数量。**

缓冲区满、有两个生产者在等，`empty` 是 -2，不是 0。

```text
正数部分 = 还剩多少资源
负数部分 = 有多少人在等
```

**读者优先不是「更好」。**

```text
读者优先：写者可能饿死。
写者优先：读者可能饿死。
公平：都不饿死，但并发度最低。
```

**`if (readcount == 0)` 必须在 mutex 里面。**

在外面判断，判断和自增之间会被打断。

**哲学家三种解法破坏的条件不同。**

```text
最多四人：循环等待（环凑不齐）
奇偶顺序：循环等待（方向构不成环）
AND 型  ：请求并保持（不再持有一半）
```

**缓冲区为 1 时，删 mutex 是对的，换顺序是错的。**

这两件事经常被混成一件。

### 自检三问

1. 如果把生产者的 `P(empty)` 和 `P(mutex)` 换个位置，缓冲区满时会怎样？请说出两个进程各自卡在哪一行、卡住时手里握着什么。
2. 缓冲区大小为 1 时，为什么可以删掉 mutex？如果 mutex 留着、顺序却写反了，还会不会死锁？
3. 缓冲区 4 个槽，某时刻 `empty = -2`、`full = 4`、`mutex = 1`。此时一个消费者取走一个产品，三个信号量各变成多少？被唤醒的生产者会不会再减一次 empty？

## 11. 小结 + 下一篇

四个问题，压成一张表。

```text
生产者-消费者   3 个信号量   mutex + empty + full
读者-写者       3 个信号量   rw_mutex + mutex(+ count)
哲学家进餐      5 个信号量   每把筷子一个（+ 一个配额或方向规则）
吸烟者          4 个信号量   三种组合 + finish
```

但真正要带走的不是数量，是三条判据。

```text
① P 会阻塞，V 不会。所以 P 的顺序敏感，V 的顺序不敏感。
② 永远不要在持锁状态下，等一个需要别人拿锁才能改变的量。
③ 每对 P/V 都要配对，互斥信号量在同一进程内配对，同步信号量跨进程配对。
```

回到开头那两段代码。

```c
P(empty); P(mutex);    // 排队等：先排队，再进门
P(mutex); P(empty);    // 互相等：进了门，站在门口等别人给你让路
```

差别只有两行。

后果是永久停住。

下一篇换一条路：把这些容易写错的 P/V，换成一种「编译器帮你加锁」的结构。

```text
操作系统系统讲解 10：管程与条件变量
```

那一篇会回答：

```text
管程凭什么保证「一次只进一个」？
既然管程自带互斥，为什么还需要条件变量？
条件变量的 signal 为什么会丢？
```
