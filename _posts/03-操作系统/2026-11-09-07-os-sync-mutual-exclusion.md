两个线程，一个全局变量。

```c
int count = 0;

// 线程 A 和线程 B 各执行
for (int i = 0; i < 1000000; i++) {
    count++;
}
```

按算术，最后 `count` 应该是 2000000。

实际跑出来，常常是 130 万到 180 万之间的某个数。

每次都不一样。

少掉的那些，去哪了？

先看 `count++` 在机器层面是什么。

```text
load   r1, [count]     ; 把 count 读进寄存器
add    r1, r1, #1      ; 寄存器加一
store  [count], r1     ; 写回内存
```

三条指令，不是一条。

只要两条指令之间发生切换，就会丢更新。

设 `count = 5`。

```text
时刻   线程 A              线程 B              count
 t1    load r1 ← 5                            5
 t2                       load r2 ← 5         5
 t3    add r1 ← 6                             5
 t4                       add r2 ← 6          5
 t5    store [count] ← 6                      6
 t6                       store [count] ← 6   6
```

两个线程都加了 1，`count` 只涨了 1。

丢了的那一次，就是"两个人都以为自己是唯一在读它的人"。

这个问题调度解决不了。

调度只能决定谁先跑，不能阻止两个人都读到 5。

这类错误有个名字：竞态条件（race condition）。

意思是"结果取决于执行的具体时序"，跑一百次可能出现一百种不同的 `count`。

竞态这个词的重点不在"快"，在"顺序不确定"。

只要两个执行流访问同一份数据，且至少有一个在写，又没有同步，就存在竞态。

三个条件缺一不可。

```text
两个执行流
同一份数据
至少一个在写
```

如果都只读，怎么交错都不会错，这也是后面"读者-写者"问题存在的原因。

## 1. 同步与互斥：协作和争用

两个进程（或线程）之间有关系，只有两种。

**同步（synchronization）**是协作关系，有先后顺序。

```text
A 先把数据写进缓冲区，B 才能从缓冲区读
A 算完第一步，B 才能开始第二步
```

同步的核心是"顺序约束"：某件事必须发生在另一件事之后。

**互斥（mutual exclusion）**是争用关系，不能同时。

```text
两台机器都要用同一台打印机
两个线程都要改同一个全局变量
```

互斥的核心是"同一时刻只允许一个"。

两者的区别，用一句话说：

```text
同步：这件事必须在那件事之后（顺序）
互斥：这件事和那件事不能同时（排他）
```

它们不是同一件事的两个名字。

生产者-消费者问题里，两种关系同时存在。

```text
生产者往缓冲区放数据，消费者从缓冲区取数据
缓冲区满时，生产者必须等消费者（互斥 + 同步）
缓冲区空时，消费者必须等生产者（互斥 + 同步）
```

互斥保护的是"缓冲区这个数据结构不被同时改"。

同步保证的是"不会从空缓冲区里取，也不会往满缓冲区里塞"。

一个管空间，一个管时间。

408 常在这里出概念题：给一个场景，问是同步还是互斥。

判断方法很简单：

```text
如果去掉"先后"约束，会发生逻辑错误 → 同步
如果去掉"排他"约束，会发生数据错误 → 互斥
```

还有一种更准的判断：看"能不能同时做"。

两个进程同时读同一块数据，不冲突，那就不需要互斥。

两个进程同时写，冲突，需要互斥。

一个读一个写，也冲突，也需要互斥。

这个分类直接决定了"读者-写者"问题里为什么要给读者开绿灯。

读者之间共享，读者和写者互斥。

这也解释了为什么"临界区"不是一个固定的代码段：一段代码算不算临界区，取决于它访问的资源会不会被并发修改。

## 2. 临界区：四段代码和一个原则集

临界资源（critical resource）是一次只允许一个进程使用的那份资源。

打印机、共享变量、缓冲区、文件表，都算。

临界区（critical section）是访问临界资源的那段代码。

它不是资源本身，是"代码"。

一个进程访问临界资源的完整结构是四段：

```c
while (true) {
    // 进入区 entry section
    //   检查能不能进，能进就上锁
    // 临界区 critical section
    //   访问临界资源
    // 退出区 exit section
    //   解锁，唤醒等待者
    // 剩余区 remainder section
    //   干别的
}
```

四段的名字，408 爱考"哪一段做哪件事"。

```text
进入区：检查 + 上锁（可能阻塞）
临界区：访问共享资源
退出区：解锁
剩余区：其余代码
```

判断一段同步代码对不对，靠的是四条原则。

```text
① 空闲让进：临界区空着，想进的进程应该能进
② 忙则等待：已有进程在临界区，其他进程必须等
③ 有限等待：想进的进程，等待时间必须有上界
④ 让权等待：进不去的时候，应该放弃 CPU，而不是空转
```

这四条不是并列的，是有层次的。

①②保证"不出错"，③④保证"不卡死、不浪费"。

严格来说，①和②是正确性，③是公平性，④是效率。

软件方法能同时满足的，最多到③。

④基本做不到，原因在第 11 节说。

先看三个失败的软件方案，它们各自破坏一条原则。

## 3. 软件法一：单标志法，违背空闲让进

最朴素的想法：用一个变量表示"轮到谁"。

```c
int turn = 0;   // 0 表示轮到 P0，1 表示轮到 P1

// ---- P0 ----
while (turn != 0) {
    // 空转
}
// 临界区
turn = 1;

// ---- P1 ----
while (turn != 1) {
    // 空转
}
// 临界区
turn = 0;
```

互斥满足。

因为 `turn` 只有一个值，两个进程不可能同时通过 `while`。

问题出在"强制轮换"。

设想这个顺序：

```text
1. P0 进入临界区，用完，turn = 1，然后去剩余区干很长的活
2. P1 进入临界区，用完，turn = 0
3. P1 又想进，但 turn 是 0，只能等
4. P0 还在剩余区，根本没打算再进临界区
```

此时临界区是空的，但 P1 进不去。

**临界区空闲，想进的进程却进不了 —— 违背空闲让进。**

这个方案的另一个名字叫"严格轮换"（strict alternation）。

它要求两个进程严格交替进出，谁也不能连续进两次。

在"两个人交替干活"的场景里这没问题。

在"一个人可能连着干十次"的场景里，这就是灾难。

## 4. 软件法二：双标志先检查，违背忙则等待

改进思路：不要强制轮换，改成"我想进的时候举个牌子"。

```c
bool flag[2] = {false, false};

// ---- Pi，j = 1 - i ----
while (flag[j]) {     // ① 先检查对方
    // 空转
}
flag[i] = true;       // ② 再举自己的牌子
// 临界区
flag[i] = false;      // ③ 放下牌子
```

看起来很合理：对方没举牌，我就举牌进场。

问题是 ① 和 ② 之间有一个窗口。

```text
t1  P0 检查 flag[1] → false，通过
t2  P1 检查 flag[0] → false，通过      ← 两人都通过了检查
t3  P0 置 flag[0] = true
t4  P1 置 flag[1] = true
t5  P0 进临界区
t6  P1 进临界区                        ← 两人同时在内
```

两个人都检查过了，两个人都举了牌，两个人都进了。

**违背忙则等待。**

这个错误的形态很典型：检查和置位是两步，中间可以被切开。

任何"先看后做"的实现，只要"看"和"做"不是原子的，就有这个洞。

408 给这种代码时，通常会把 `while` 和赋值写成相邻两行，看着很紧凑。

紧凑不等于原子。

## 5. 软件法三：双标志后检查，违背空闲让进

那换个顺序：先举牌，再检查。

```c
bool flag[2] = {false, false};

// ---- Pi，j = 1 - i ----
flag[i] = true;       // ① 先举自己的牌子
while (flag[j]) {     // ② 再检查对方
    // 空转
}
// 临界区
flag[i] = false;
```

这次不会同时进了。

因为两个人都举了牌，两个人都看到对方举着，两个人都等。

互斥满足了，但变成了另一种错误：

```text
t1  P0 置 flag[0] = true
t2  P1 置 flag[1] = true
t3  P0 检查 flag[1] → true，等
t4  P1 检查 flag[0] → true，等         ← 两人都在等
```

临界区空着，两个进程都在等，谁也进不去。

**违背空闲让进，也违背有限等待。**

这不是死锁（没有人持有资源），是活锁或者饥饿。

两种说法在 408 里都可能出现，关键看题干怎么定义。

注意这个方案和单标志法的错误"方向相反"。

```text
单标志法：  太谦让，把机会让给对方，自己饿着
双标志后检查：太激进，两个人都抢，谁也让不出去
```

## 6. 408 怎么考

这一节的题型只有两类，但都很容易错。

```text
① 给一段同步代码，判断满足/违背哪几条原则
② 给一个场景，问该用同步还是互斥
```

第二类靠第 1 节那句话就能解决。

第一类要靠逐条对照，下面是一道自拟题。

### 6.1 例题：这段代码错在哪

```c
// 自拟题：一个"上锁"函数
int lock = 0;

void enter(void) {
    while (lock == 1) {   // ① 检查
        // 空转
    }
    lock = 1;             // ② 置位
}

void leave(void) {
    lock = 0;             // ③ 清除
}
```

问：这段代码满足临界区四原则里的哪几条？

逐条看。

```text
空闲让进：满足。lock == 0 时，enter 能通过检查并置位。
忙则等待：不满足。① 和 ② 之间可被切换，
         两个进程可能都通过检查，然后都置位，都进临界区。
有限等待：不满足。一直有人抢的话，某个进程可能永远抢不到。
让权等待：不满足。等的时候在空转，占着 CPU。
```

所以答案是：只满足"空闲让进"，违背其余三条。

### 6.2 追问：换成 TSL 为什么就对了

因为 `TestAndSet` 把 ① 和 ② 合成了一条硬件指令。

检查返回旧值，置位写新值，这两件事在一条指令里完成，中间不可能被切开。

```text
软件：读 → 判断 → 写      （三步，可被打断）
TSL ：读 + 写，原子       （一步，不可打断）
```

这就是硬件指令存在的全部理由。

### 6.3 第二个判断题

"单标志法满足互斥，但可能违背空闲让进。"

对。

"双标志先检查满足空闲让进，但可能违背忙则等待。"

对。

"双标志后检查满足互斥，但可能两个进程都进不去。"

对。

三句话连起来，就是软件方法的三次失败。

考场上还有一个高频陷阱：把"进入区"当成"临界区"。

进入区是检查和上锁的代码，它可以阻塞。

临界区是访问共享资源的代码，它应该在拿到锁之后执行。

如果把上锁也写进临界区，讨论"临界区是否互斥"就没有意义了。

## 7. 真实系统里长什么样

真实系统里没人用 Peterson。

不是因为它是错的，是因为它太慢，而且在多核上不可靠。

先看现代的做法。

x86 提供一条带 `LOCK` 前缀的指令，能把"读改写"变成原子操作。

```text
lock cmpxchg [mem], reg     ; 比较并交换，带锁前缀
lock xchg   [mem], reg      ; 交换，带锁前缀
```

`LOCK` 前缀会让这条指令在执行期间独占缓存行，其他核的访问被挡在门外。

Linux 内核里对应的封装是 `atomic_cmpxchg`、`xchg`、`test_and_set_bit` 这类函数（简化示意）。

自旋锁 `spin_lock` 就建在它们上面。

一次 `spin_lock` 大致是：

```text
preempt_disable()      关抢占，防止在临界区里被换出去
smp_mb()               内存屏障，保证前面的读写不被重排到后面
while (cmpxchg(&lock, 0, 1) != 0) { cpu_relax(); }
```

`cpu_relax()` 在 x86 上是 `pause` 指令，作用是让出流水线和超线程资源，别把总线挤死。

这些细节 408 不考，但它解释了一件事：**自旋锁不是一个 while 循环，它是一整套"原子指令 + 屏障 + 关抢占"的组合。**

再看 pthread 的互斥锁。

`pthread_mutex_lock` 在 Linux 上走的是 futex（fast userspace mutex）。

快路径完全在用户态：一条 `cmpxchg`，抢到就返回，一次系统调用都不做。

慢路径才进内核，把自己挂到等待队列上睡眠。

这个设计把"忙等"和"阻塞"缝在了一起：

```text
没人竞争 → 用户态原子指令，纳秒级
有人竞争 → 进内核，睡眠，微秒级 + 两次切换
```

第 10 节会算这笔账。

还有一个真实系统里的坑：编译器重排。

你写的代码顺序，不一定是 CPU 执行的顺序，甚至不一定是生成代码的顺序。

所以要靠内存屏障（memory barrier）把顺序钉住。

C11 的 `atomic_flag`、C++ 的 `std::atomic`，以及 GCC 的 `__atomic` 内建函数，都是为了在语言层面表达"这条语句不能被重排、不能被拆开"。

## 8. Peterson 算法：三个变量解决两个人的问题

把双标志的两个毛病各修一半，就有了 Peterson 算法。

它用三个变量：

```c
bool flag[2] = {false, false};   // 谁想进
int turn;                         // 优先权给谁
```

每个进程的代码：

```c
// ---- Pi，j = 1 - i ----
flag[i] = true;      // ① 我想进
turn = j;            // ② 但优先权让给你
while (flag[j] && turn == j) {
    // ③ 你也要进，且优先权在你，我就等
}
// 临界区
flag[i] = false;     // ④ 我退出
```

逐行看这三步在干什么。

① 是表态，和双标志后检查一样。

② 是谦让，这一步是关键。

③ 的条件是"两个都想进，且优先权在对方"。

注意 ② 的位置：它写在 ① 之后。

最后写 `turn` 的那个进程，会把优先权交给对方，于是它自己等。

这就是"最后表态的人让路"。

用一张表看一次真实的交错。

| 时刻 | P0 | P1 | flag[0] | flag[1] | turn |
|---|---|---|---|---|---|
| t1 | flag[0] = true | — | true | false | — |
| t2 | — | flag[1] = true | true | true | — |
| t3 | turn = 1 | — | true | true | 1 |
| t4 | — | turn = 0 | true | true | 0 |
| t5 | 检查：flag[1] 真，turn 是 0，条件假 → 进临界区 | — | true | true | 0 |
| t6 | （临界区） | 检查：flag[0] 真，turn 是 0，条件真 → 等 | true | true | 0 |
| t7 | flag[0] = false | — | false | true | 0 |
| t8 | — | 再检查：flag[0] 假 → 进临界区 | false | true | 0 |

P1 写了 `turn = 0`，把优先权让给了 P0，所以 P0 进、P1 等。

如果 t4 换成 P0 写 `turn = 1`，结局就反过来。

关键不在于谁先举牌，在于谁最后写 `turn`。

### 8.1 互斥的证明

假设 P0 和 P1 同时在临界区。

两个人的 `flag` 都是 `true`，都跳出了 `while`。

看 `turn` 的最后一次写。

设它由 P0 执行，所以 `turn = 1`。

P1 要跳出循环，必须满足 `flag[0] == false` 或 `turn == 0`。

`flag[0]` 是 `true`（P0 在临界区且没执行 ④），所以只能是 `turn == 0`。

但 `turn` 的最后一次写是 P0 写的 1，之后没人改过。

矛盾。

所以不可能同时在临界区，互斥成立。

### 8.2 前进与有限等待

如果 P1 根本不想进，`flag[1] == false`，P0 的 `while` 条件直接为假，P0 进。

这叫前进（progress），临界区空着就有人能进。

如果两个都想进，只有一个会等，另一个进。

如果 P0 在临界区，P1 在外面等，P0 退出时把 `flag[0]` 置 `false`，P1 就能进。

如果 P0 退出后立刻又想进，它会写 `turn = 1`，于是 P0 自己等，P1 进。

所以 P1 最多被插队一次，等待有上界。

有限等待也满足。

### 8.3 让它失效的那个前提

到这里 Peterson 看起来完美。

它满足互斥、空闲让进、有限等待，只差让权等待（自旋）。

但它在真实机器上会崩。

原因藏在 8.1 的证明里：那个证明假设了"读到的 `turn` 是最后一次写的值"。

这个假设叫顺序一致性（sequential consistency）。

现代 CPU 和编译器都不保证它。

```text
编译器：可能把 while 里的 flag[j] 提到循环外，只读一次
CPU：  可能把 ① flag[i] = true 和 ③ 的读重排
       在 ARM / POWER 这类弱内存模型上，写和读可以换序
```

一旦 ① 和 ③ 换序，P0 就可能"先看到对方没举牌，再举自己的牌"。

两个人同时进场，互斥失效。

> **反直觉的点在这里：**
> **Peterson 算法在单核上靠"顺序一致性 + 编译器不重排"才成立。**
> **到了多核弱内存模型，它需要加内存屏障才能用；加了屏障之后，它又比原子指令慢。**
> **软件方法看起来完美，却没进任何生产系统。**

在 x86 上，很多人试过它"能跑"，因为 TSO 对写-写、读-读的顺序限制比较强。

但 TSO 允许读越过还留在写缓冲里的写，所以"两人同时进场"在这套模型上仍然可能发生。

要修，得在 `flag[i] = true` 和 `turn = j` 之间插一条 `mfence`，或者干脆改用带 `lock` 前缀的原子指令。

修完之后它已经不叫 Peterson 了，它变成了"用屏障模拟原子指令"。

而 C 语言里用普通变量写 Peterson，本身就踩了数据竞争的定义，属于未定义行为。

编译器有权把你的循环优化成一个死循环。

所以正确写法必须用 `atomic` 加内存序，代码立刻变得和硬件指令一样复杂。

这就是它被淘汰的方式：不是错，是不划算。

## 9. 硬件法：关中断、TestAndSet、Swap

软件方法的根本困难是"检查和修改无法合成一步"。

那就把这一步交给硬件。

### 9.1 关中断

最直接的想法：进临界区之前关掉中断，出来再开。

```c
// 单处理机
关中断();          // 特权指令
// 临界区
开中断();
```

关中断之后，时钟中断进不来，进程不会被切换走。

于是"检查和置位"之间不会被打断，互斥成立。

但它有三个硬限制。

```text
① 只对单处理机有效：多核上其他 CPU 照样并行执行，关本核的中断没有用
② 用户态不能执行：关中断是特权指令，用户程序执行会陷入
③ 关久了影响响应：中断被延迟，时钟、磁盘完成、键盘全部迟到
```

所以关中断只在内核里用，而且只包住极短的代码。

现代内核的做法是"关本地中断 + 加自旋锁"：

关中断防的是本核的中断处理程序，自旋锁防的是其他核。

顺序反过来会出事。

如果先拿自旋锁再关中断，持锁期间中断还是开着的。

中断一来，处理程序在同一个核上跑起来，而它可能也要拿这把锁。

它拿不到，只能自旋；可能放锁的那个执行流正被它打断，永远跑不了。

于是死锁。

所以规矩是先关中断，再拿锁。

### 9.2 TestAndSet

TSL 是一条指令，语义是"读出旧值，写入 true"。

```c
// 硬件保证这条函数整体原子
bool TestAndSet(bool *lock) {
    bool old = *lock;
    *lock = true;
    return old;
}
```

用法：

```c
while (TestAndSet(&lock)) {
    // 空转
}
// 临界区
lock = false;
```

`TestAndSet` 返回 `false` 说明锁本来是开的，我把它置成了 `true`，我拿到了。

返回 `true` 说明锁本来就被别人占着（它还是 `true`），继续自旋。

互斥成立，因为检查和置位在一条指令里。

但 TSL 不满足有限等待。

它没有排队机制，谁抢到算谁的。

一个进程可能运气极差，永远抢不到。

这在 408 里是明确的结论：TSL 满足互斥、空闲让进、忙则等待，不满足有限等待和让权等待。

### 9.3 Swap

SWAP 或 XCHG 是另一条原子指令，交换两个变量的值。

```c
void Swap(bool *a, bool *b) {
    bool t = *a;
    *a = *b;
    *b = t;
}

// 用法：key 是本地的 true，lock 是全局的
bool key = true;
do {
    Swap(&lock, &key);
} while (key);
// 临界区
lock = false;
```

逻辑和 TSL 一样：把 `true` 换进去，看换出来的是什么。

换出来 `false`，说明锁是开的，我拿到了。

换出来 `true`，说明锁被别人占着，继续换。

性质也一样：互斥成立，不满足有限等待。

### 9.4 三种硬件法的共同点

```text
关中断     ：单核有效，需要特权，影响响应
TSL / Swap ：多核有效，用户态可用，但都是自旋
```

后两者都靠"原子指令 + 忙等"。

忙等的代价，下一节算。

## 10. 忙等与阻塞：自旋到底亏不亏

等一把锁，有两种姿态。

```text
忙等（自旋）：不放弃 CPU，反复检查
阻塞：        放弃 CPU，进等待队列，被唤醒后再来
```

代价完全不同。

```text
忙等：占着 CPU，但省了两次上下文切换
阻塞：让出 CPU，但唤醒要两次切换（挂起 + 恢复）
```

设临界区长度 `L`，一次上下文切换开销 `S`。

```text
自旋的成本 ≈ L（转圈等着，最多浪费 L 的 CPU）
阻塞的成本 ≈ 2S（一次睡眠 + 一次唤醒）
```

判断规则：

```text
L < 2S  → 自旋更划算
L > 2S  → 阻塞更划算
```

`S` 是几微秒量级，所以"临界区只有几十条指令"时，自旋明显更优。

这也是内核里大量使用自旋锁的原因：内核的临界区通常很短。

但自旋有个前提：**持锁的那个执行流必须能继续跑。**

单核上自旋是纯浪费。

你占着 CPU 转圈，持锁者根本没机会被调度上来。

所以单核上不该用自旋，该用"关抢占"：进临界区前关掉抢占，出来再打开。

Linux 内核在单核配置下，自旋锁就退化成这一件事——关抢占（简化示意）。

多核上自旋才合理：持锁者在另一个核上跑，你在这核转圈是有意义的。

还有第三种代价：自旋会放大优先级反转。

一个低优先级进程持锁被抢占，高优先级进程在自旋，中优先级进程在跑。

CPU 被中优先级占着，低优先级永远拿不回来。

这就是第 06 篇提到的优先级反转的自旋版。

第四个代价在多核上才显出来：缓存行弹跳（cache line bouncing）。

所有核都对着同一个锁变量做原子操作，这个变量所在的缓存行就在核之间来回搬。

每搬一次，就是一次几十到上百个周期的延迟。

核越多，抢得越凶，越搬越慢。

所以自旋锁的扩展性很差，核数一多，锁就成了瓶颈。

工业界的解法是排队锁：每个等待者在自己的变量上转，锁只负责把队首交给下一个人。

票据锁和 MCS 锁都是这个思路，408 不考，但它解释了"为什么抢锁的算法还要继续演进"。

## 11. 让权等待为什么难

四原则里，前三条软件方法都能碰到，第四条几乎做不到。

想做到"进不去就放弃 CPU"，需要什么？

需要把当前进程从运行态改成阻塞态、放进某个等待队列、然后触发一次调度。

这三件事都要改内核数据结构。

而"改内核数据结构"本身又需要互斥。

于是问题绕回来了：为了不忙等，你需要一个阻塞原语；阻塞原语自己需要互斥；互斥又要靠……什么？

答案只能落在硬件上：关中断或者原子指令。

所以"让权等待"注定只能由内核提供的原语来实现。

```text
软件方法（Peterson、双标志）  → 自旋，用户态，做不到让权等待
硬件指令（TSL、Swap）        → 自旋，也做不到让权等待
整型信号量                    → 自旋，还是做不到
记录型信号量                  → 可以，因为 P 操作里能调用 block
```

最后一行是下一篇的主题。

记录型信号量之所以能"让权"，是因为它的 P 操作在 `value < 0` 时会调用 `block()`。

`block()` 是原语，它会把进程挂到信号量的等待队列上，然后让出 CPU。

这一切发生在内核里，用户程序看不见。

所以 408 里那条结论要记牢：

```text
"让权等待"是区分"用户态同步方法"和"内核同步原语"的分水岭。
```

## 12. 容易混淆的点

第一组：同步和互斥。

同步看顺序，互斥看排他。

一个场景可以同时需要两者（生产者-消费者）。

第二组：临界资源和临界区。

临界资源是那份资源，临界区是访问它的那段代码。

题目问"临界区是否互斥"时，问的是代码段能不能同时执行。

第三组：进入区和临界区。

进入区负责检查和上锁，它可以阻塞，可以自旋。

临界区只负责访问共享资源。

第四组：四条原则谁被谁违背。

```text
单标志法      → 违背空闲让进
双标志先检查  → 违背忙则等待
双标志后检查  → 违背空闲让进、有限等待
Peterson     → 满足前三条，不满足让权等待
TSL / Swap   → 满足忙则等待，不满足有限等待、让权等待
关中断        → 单核满足互斥，多核无效
```

这张表是 408 选择题的高频答案源。

第五组：死锁和饥饿。

双标志后检查里两个进程都进不去，是饥饿或活锁。

死锁要求"互相持有并等待对方持有的资源"，这里没人持有。

第六组：互斥和原子性。

原子性是"不可分割"，互斥是"不同时执行"。

一条原子指令可以实现互斥，但互斥不一定要靠原子指令（关中断也行）。

第七组：关中断和屏蔽中断。

关中断是"CPU 不响应中断"，需要特权。

屏蔽中断是"中断控制器不转发某个中断源"，是另一层机制。

408 一般不深究，但看到"用户程序关中断"一定是错的。

第八组：同步机制和通信机制。

同步是"约束执行顺序"，通信是"传递数据"。

共享内存加信号量可以同时做到两件事，但它解决的是同步。

管道既能传数据又能隐式同步，它的同步性来自"读空管道会阻塞"。

这两件事经常一起出现，但答题时要分清问的是哪一个。

TSL / Swap  用硬件把检查置位合成一步，但没有排队
