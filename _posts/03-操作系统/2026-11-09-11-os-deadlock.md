两台打印机，两个进程。

```c
/* P1 */
lock(printer_A);
lock(printer_B);     // 等

/* P2 */
lock(printer_B);
lock(printer_A);     // 等
```

P1 拿到 A，P2 拿到 B。

P1 在等 B，P2 在等 A。

两边都不肯放手。

系统就这么停住了。

单看每一行都对：先拿一把，再拿另一把，拿不到就等。

组合起来，就是死锁。

把时间线摊开，只有四步。

```text
t1  P1 拿到打印机 A
t2  P2 拿到打印机 B
t3  P1 申请 B → 被 P2 持有 → P1 阻塞（A 不还）
t4  P2 申请 A → 被 P1 持有 → P2 阻塞（B 不还）
```

注意 t3 和 t4 的括号里那句「不还」。

```text
如果拿到新资源之前必须放下旧资源，就不会死锁。
如果允许抢占，也不会死锁。
如果申请顺序统一，也不会死锁。
```

三条「如果」，就是后面三种解法的全部。

**这一篇要回答的是一串连锁问题：为什么会停、怎么提前看出来、能不能不算就避免、真停了怎么办。**

## 1. 死锁的定义：一组进程互相等

死锁（deadlock）的严格说法。

```text
一组进程中的每一个，都在等待一个事件，
而这个事件只能由这组进程中的另一个来触发。
于是谁也无法推进。
```

换成资源的话说。

```text
每个进程都持有部分资源，同时等待另一部分资源，
而那一部分正被组内别的进程持有。
```

两个关键词。

```text
① 「组内」——必须是一个闭环，外面的人插不进来。
② 「互相」——不是等外部事件（等键盘输入不算死锁，那叫阻塞）。
```

区分一下阻塞。

```text
阻塞：我等的资源在某个人手里，那个人会还。等着就行。
死锁：我等的资源在一个人手里，那个人也在等我手里的东西。等不到。
```

## 2. 四个必要条件

死锁发生，必须同时满足四条。

```text
① 互斥（mutual exclusion）
   资源一次只能给一个进程用。

② 请求并保持（hold and wait）
   已经拿着资源，还去申请新资源，并且不放手已有的。

③ 不可剥夺（no preemption）
   资源只能由持有者主动释放，别人抢不走。

④ 循环等待（circular wait）
   存在一个进程的环形等待链：P0 等 P1 的资源，P1 等 P2 的……Pn 等 P0。
```

四条要一起成立。

```text
破坏任何一条，死锁就不可能发生。
——这是后面所有「预防」手段的唯一依据。
```

回到开头那两台打印机，四条全中。

```text
互斥：打印机一台只能给一个进程用。        ✓
请求并保持：P1 拿着 A 去申请 B，A 不还。    ✓
不可剥夺：操作系统不会强行把 A 从 P1 手里抢走。✓
循环等待：P1 等 P2 手里的 B，P2 等 P1 手里的 A。✓
```

补一句容易记错的。

```text
这四条是必要条件，不是充分条件。
四条都满足，不一定死锁（多资源、多实例时可能只是暂时卡一下）。
但只要缺一条，一定不死锁。
```

用这四条去套之前见过的题，会快很多。

```text
哲学家进餐：五个人各拿一把筷子 → 循环等待成立 → 死锁。
读者-写者（读者优先）：写者拿不到 rw_mutex，但没人「等写者手里的东西」→ 是饥饿，不是死锁。
生产者-消费者（P 反序）：生产者持 mutex 等 empty，
  而 empty 要消费者拿 mutex 才能改 → 循环等待成立 → 死锁。
```

最后一条要特别留意。

```text
它看起来像「同步写错了」，本质是「两个进程形成了环」。
所以 09 篇那个经典 bug，用死锁的四条件分析一遍，结论是一样的。
```

## 3. 资源分配图：有环就等于死锁吗

把资源和进程画成图，判断就有了形状。

```text
圆圈 = 进程 Pi
方框 = 资源类 Rj（方框里的小圆点 = 实例数）
Pi → Rj  ：请求边（Pi 申请 Rj 的一个实例，还没拿到）
Rj → Pi  ：分配边（Rj 的一个实例已经给了 Pi）
```

一个死锁的图。

```text
        ┌──────────┐  分配   ┌──────────┐
        │    R1    │────────▶│    P1    │
        │  ●       │         │          │
        └──────────┘         └────┬─────┘
              ▲                   │ 请求
              │ 请求              ▼
        ┌─────┴────┐         ┌──────────┐
        │    P2    │◀────────│    R2    │
        │          │  分配   │       ●  │
        └──────────┘         └──────────┘
```

读图的方法：

```text
顺着箭头走。
R1 → P1 → R2 → P2 → R1
走回起点了，有环。
```

结论分两种，这是 408 最爱设的坑。

```text
每个资源类只有一个实例：有环 ⟺ 死锁。
每个资源类有多个实例：有环 ⟹ 可能死锁，不一定。
```

给一个「有环但没死锁」的反例。

```text
R1 有 2 个实例，R2 有 1 个实例。

P1：持有 R1 的 1 个实例，请求 R2。
P2：持有 R2，请求 R1 的另一个实例。
```

画出来。

```text
R1  ──分配──▶  P1
P1  ──请求──▶  R2
R2  ──分配──▶  P2
P2  ──请求──▶  R1      ← 指向 R1 的「另一个实例」，不是 P1 手里那个
```

环是有的：`R1 → P1 → R2 → P2 → R1`。

但 R1 还剩 1 个空闲实例。

```text
P2 请求 R1 → 还有 1 个空闲，直接满足。
P2 拿到 R1 后，工作做完，释放 R2。
P1 拿到 R2，继续跑。
```

没人卡住。

```text
所以「有环」是警报，「死锁」是结果。
多实例的时候，警报会误报。
```

只有一条是稳的。

```text
死锁一定发生在环上。
所以「化简资源分配图」找的就是「能不能把所有边都消掉」。
```

## 4. 预防：破坏四个条件，各自要付什么代价

预防（prevention）的思路很硬：让四个条件至少缺一个。

四条路，四种代价。

| 破坏哪个条件 | 怎么做 | 代价 |
|---|---|---|
| 互斥 | 把资源改造成可共享的，如用 SPOOLing 把打印机变共享 | 多数资源天生不可共享，CPU、锁、写文件都改不了 |
| 请求并保持 | 一次性申请全部资源（静态分配）；或申请新资源前先释放已持有的 | 资源利用率低、可能饿死；「先释放再申请」实现复杂且可能丢中间结果 |
| 不可剥夺 | 申请不到就释放自己已持有的资源 | 已做的工作作废，只适合能保存恢复的资源（CPU 现场、内存页） |
| 循环等待 | 给资源编号，所有进程必须按序号递增申请 | 编号难定；访问顺序被迫改变；新资源加入要重排 |

第三条最值得展开。

```text
「申请不到就释放」听起来很干脆。
但如果被剥夺的是「已经写了一半的文件」，释放就等于丢弃。
所以能剥夺的只有「状态可以完整保存再恢复」的资源。
```

第四条是工程上唯一被大规模采用的。

```text
有序分配：给每把锁一个编号，所有线程按递增顺序获取。
```

回到开头那两台打印机。

```text
给打印机编号 1 和 2。
P1 申请顺序：1 → 2
P2 申请顺序：1 → 2
```

P1 拿到 1，P2 只能等 1。

P1 再拿 2，跑完，释放。

P2 接着拿 1、2。

```text
「先拿小的，再拿大的」→ 环不可能形成。
因为环需要一个「从大到小」的回边，而被规则禁止了。
```

代价也很实际。

```text
真实系统里锁有几百把，编号维护成本高。
更常见的是「按模块层次约定顺序」：
  文件系统锁 → 内存锁 → 调度器锁，绝不允许反向。
——Linux 内核的 lock ordering 就是这套东西。
```

## 5. 避免：安全状态与银行家算法

避免（avoidance）的思路比预防软。

```text
不破坏任何条件。
每次分配之前，先算一遍「分出去之后还安不安全」。
安全就分，不安全就让人等。
```

### 5.1 什么是安全状态

先定义「安全序列」。

```text
一个进程序列 <P1, P2, ..., Pn> 是安全的，当且仅当：
对每个 Pi，它还需要的那部分资源，
都能由「当前可用 + 前面所有 Pj 已经跑完释放的」凑齐。
```

说人话。

```text
存在一个顺序，按这个顺序让进程一个个跑完。
每个进程开跑之前，剩下的资源够它跑到结束。
```

于是三种状态。

```text
安全状态：存在至少一个安全序列。
不安全状态：一个安全序列都找不到。
死锁状态：已经卡住了。
```

三者的关系是包含，不是并列。

```text
安全 ⊂ 不安全之外
死锁 ⊂ 不安全
```

准确说：

```text
安全状态一定不死锁。
不安全状态可能死锁，也可能不死锁（只是没有「保证」）。
死锁状态一定不安全。
```

### 5.2 数据结构与算例

银行家算法（banker's algorithm）要四张表。

```text
Available[j]   ：资源 j 还有几个空闲
Max[i][j]      ：进程 i 最多会要几个 j
Allocation[i][j]：进程 i 已经拿着几个 j
Need[i][j] = Max[i][j] - Allocation[i][j]
```

最后那个减法是全篇最容易写错的地方。

```text
Need = Max - Allocation        对
Need = Max - Available         错
Need 是「我还要多少」，跟「现在还剩多少」无关。
```

上数据。

```text
系统有 A、B、C 三类资源，总量 (10, 5, 7)。

        Allocation      Max
        A  B  C        A  B  C
P0      0  1  0        7  5  3
P1      2  0  0        3  2  2
P2      3  0  2        9  0  2
P3      2  1  1        2  2  2
P4      0  0  2        4  3  3
```

先验一下数据自洽。

```text
Allocation 合计：
  A: 0+2+3+2+0 = 7
  B: 1+0+0+1+0 = 2
  C: 0+0+2+1+2 = 5

Available = 总量 - Allocation = (10-7, 5-2, 7-5) = (3, 3, 2)
```

算 Need。

```text
Need = Max - Allocation

P0: (7-0, 5-1, 3-0) = (7, 4, 3)
P1: (3-2, 2-0, 2-0) = (1, 2, 2)
P2: (9-3, 0-0, 2-2) = (6, 0, 0)
P3: (2-2, 2-1, 2-1) = (0, 1, 1)
P4: (4-0, 3-0, 3-2) = (4, 3, 1)
```

现在做安全性检查。

```c
bool safe_state() {
    Work = Available;
    for (i = 0; i < n; i++) Finish[i] = false;

    for (k = 0; k < n; k++) {
        for (i = 0; i < n; i++) {
            if (!Finish[i] && Need[i] <= Work) {   // 逐分量比较
                Work = Work + Allocation[i];       // 假装它跑完，资源归还
                Finish[i] = true;
                seq[k] = i;                        // 记下安全序列的一位
                break;
            }
        }
        if (i == n) {                              // 这一轮一个都找不到
            return false;
        }
    }
    return true;
}
```

这段伪代码有两个细节容易写错。

```text
① Need[i] <= Work 是逐分量比较，三个分量全要满足。
② 内层 for 找到第一个就 break，一轮只完成一个进程。
   如果写成不 break，会在一轮里连续「跑完」好几个，序列就乱了。
```

规则只有一条：

```text
Work = Available
反复找「Need[i] ≤ Work 且还没跑完」的进程 i，
找到就假装它跑完：Work = Work + Allocation[i]，标记 Finish[i] = true。
找不到就停。
全部标记完 → 安全；否则 → 不安全。
```

一步步来。

```text
初始 Work = (3, 3, 2)

第 1 轮：
  P0 要 (7,4,3)：A 7 > 3，不行
  P1 要 (1,2,2)：1≤3, 2≤3, 2≤2，可以 ✓
     Work = (3,3,2) + (2,0,0) = (5,3,2)
     Finish: P1

第 2 轮：
  P0 要 (7,4,3)：7 > 5，不行
  P2 要 (6,0,0)：6 > 5，不行
  P3 要 (0,1,1)：0≤5, 1≤3, 1≤2，可以 ✓
     Work = (5,3,2) + (2,1,1) = (7,4,3)
     Finish: P1, P3

第 3 轮：
  P0 要 (7,4,3)：7≤7, 4≤4, 3≤3，可以 ✓
     Work = (7,4,3) + (0,1,0) = (7,5,3)
     Finish: P1, P3, P0

第 4 轮：
  P2 要 (6,0,0)：6≤7，可以 ✓
     Work = (7,5,3) + (3,0,2) = (10,5,5)
     Finish: P1, P3, P0, P2

第 5 轮：
  P4 要 (4,3,1)：4≤10, 3≤5, 1≤5，可以 ✓
     Work = (10,5,5) + (0,0,2) = (10,5,7)
     Finish: 全部
```

安全。

安全序列：

```text
<P1, P3, P0, P2, P4>
```

注意安全序列不唯一。

```text
第 1 轮里除了 P1，P3 也能过（(0,1,1) ≤ (3,3,2)）。
所以 <P3, P1, P0, P2, P4> 也是安全的。
考场上写出一条就行，除非题目要求「所有」。
```

### 5.3 一个请求能不能批

现在 P1 来申请资源 `Request = (1, 0, 2)`。

三步检查，顺序不能乱。

```text
① Request ≤ Need？    
   (1,0,2) ≤ (1,2,2) ✓   没超过它声明过的最大需求

② Request ≤ Available？
   (1,0,2) ≤ (3,3,2) ✓   系统现在拿得出来

③ 试分配，再做一次安全性检查。
```

第三步怎么试。

```text
Available = Available - Request = (3,3,2) - (1,0,2) = (2,3,0)
Allocation[P1] = (2,0,0) + (1,0,2) = (3,0,2)
Need[P1]       = (1,2,2) - (1,0,2) = (0,2,0)
```

对新的状态做安全性检查。

```text
初始 Work = (2,3,0)

P0 要 (7,4,3)：7 > 2，不行
P1 要 (0,2,0)：0≤2, 2≤3, 0≤0 ✓
   Work = (2,3,0) + (3,0,2) = (5,3,2)
P3 要 (0,1,1)：✓
   Work = (5,3,2) + (2,1,1) = (7,4,3)
P4 要 (4,3,1)：✓
   Work = (7,4,3) + (0,0,2) = (7,4,5)
P0 要 (7,4,3)：7≤7, 4≤4, 3≤5 ✓
   Work = (7,4,5) + (0,1,0) = (7,5,5)
P2 要 (6,0,0)：✓
   Work = (7,5,5) + (3,0,2) = (10,5,7)
```

安全。

```text
安全序列 <P1, P3, P4, P0, P2>
→ 批准这次请求，真的分配下去。
```

再看一个会被拒的请求。

P0 申请 `Request = (0, 3, 0)`，此时 `Available = (2, 3, 0)`。

```text
① (0,3,0) ≤ Need[P0] = (7,4,3) ✓
② (0,3,0) ≤ Available = (2,3,0) ✓
③ 试分配：
   Available = (2,3,0) - (0,3,0) = (2,0,0)
   Allocation[P0] = (0,1,0) + (0,3,0) = (0,4,0)
   Need[P0]       = (7,4,3) - (0,3,0) = (7,1,3)
```

安全性检查。

```text
Work = (2,0,0)

P0 要 (7,1,3)：7 > 2 ✗
P1 要 (0,2,0)：B 要 2，剩 0 ✗
P2 要 (6,0,0)：6 > 2 ✗
P3 要 (0,1,1)：B 要 1，剩 0 ✗
P4 要 (4,3,1)：4 > 2 ✗
```

一个都过不去。

```text
没有任何进程能跑完 → 找不到安全序列 → 不安全
→ 拒绝 P0 的请求，让它等。
```

这就是「避免」的全部机制。

```text
不是不允许申请，是「申请了之后系统还安不安全」。
不安全就等，等别人释放了再试。
```

注意第三步里那个「试」。

```text
试分配是要改状态、算一遍、再改回去的。
不能直接改完再判断——判断失败的时候状态已经被污染了。
```

所以考场上写过程时，要写清两个阶段。

```text
阶段一：假装分配（Work = Available - Request，Allocation += Request，Need -= Request）
阶段二：安全性检查
结论：安全 → 真分配；不安全 → 恢复原状态，请求排队
```

写成代码，三步检查的形状是这样。

```c
bool request(int i, int Request[]) {
    /* ① 不能超过自己声明的最大需求 */
    if (Request > Need[i]) {
        return ERROR;                      // 请求非法，不是资源不够
    }

    /* ② 现在拿不出来就等 */
    if (Request > Available) {
        block(i);
        return false;
    }

    /* ③ 试分配 */
    Available    = Available - Request;
    Allocation[i] = Allocation[i] + Request;
    Need[i]       = Need[i] - Request;

    if (safe_state()) {
        return true;                       // 安全，分配生效
    }

    /* 回滚，恢复试分配之前的状态 */
    Available    = Available + Request;
    Allocation[i] = Allocation[i] - Request;
    Need[i]       = Need[i] + Request;
    block(i);
    return false;
}
```

注意第 ① 步那个返回值和第 ② 步不同。

```text
① 返回「错误」：这个请求本身不合法，进程应该被杀掉或报错。
② 返回「阻塞」：请求合法，只是现在资源不够，等一等就能满足。
③ 返回「阻塞」：资源够，但分下去会进入不安全状态，也让它等。
```

三种「没批准」，含义完全不同。

```text
这是 408 选择题愿意考的地方：
「请求被拒绝」和「请求导致不安全」是两件事。
```

### 5.4 银行家算法的四个前提

这套算法能成立，靠四个假设。

```text
① 每个进程事先声明最大需求 Max。
② 进程数固定，不会中途创建新进程。
③ 资源类数固定，资源不会被销毁。
④ 进程最终会释放全部资源（会跑完，不会无限占着）。
```

四条里任何一条不成立，算法就失效。

```text
第 ① 条最致命。
内存要多少，程序运行时才知道——这就直接把它从通用 OS 里排除了。
```

这也是为什么银行家只活在教材和少数专用系统里。

```text
它要求的「先验知识」，比它能提供的「永不死锁」更贵。
```

> **反直觉的点**：银行家算法是「避免」，不是「预防」。
> 它一个条件都不破坏——资源照样互斥、照样请求并保持、照样不可剥夺、照样可能出现环。
> 它只是在每次分配之前算一遍：分出去之后还有没有安全序列。
> 有就分，没有就不分。用「拒绝一次分配」换「永不死锁」。

## 6. 408 怎么考

四类题，按出现频率排。

```text
① 算：给 Available / Max / Allocation，求 Need、判安全、写安全序列。
② 算：给一个 Request，判断能否满足（三个检查全写出来）。
③ 判：给资源分配图，判断是否死锁、能否化简。
④ 算：最少资源数——n 个进程各最多要 k 个，至少几个才保证不死锁。
```

### 6.1 例题一：把上面的数据算完

题目就是 5.2、5.3 那套数据。

```text
Available = (3,3,2)
Need：P0(7,4,3) P1(1,2,2) P2(6,0,0) P3(0,1,1) P4(4,3,1)
```

问：当前状态安全吗？写出一条安全序列。

答案：

```text
安全。安全序列 <P1, P3, P0, P2, P4>。

验证：
Work=(3,3,2) → P1(1,2,2) → Work=(5,3,2)
             → P3(0,1,1) → Work=(7,4,3)
             → P0(7,4,3) → Work=(7,5,3)
             → P2(6,0,0) → Work=(10,5,5)
             → P4(4,3,1) → Work=(10,5,7)
每步的 Need 都不超过当时的 Work。
```

再问：P1 请求 (1,0,2)，能给吗？

```text
能。
(1,0,2) ≤ Need[P1]=(1,2,2) ✓
(1,0,2) ≤ Available=(3,3,2) ✓
试分配后 Available=(2,3,0)，仍存在安全序列 <P1,P3,P4,P0,P2>。
```

再问：接着 P0 请求 (0,3,0)，能给吗？

```text
不能。
前两步检查都过，但试分配后 Available=(2,0,0)，
五个进程的 Need 没有一个能满足，找不到安全序列。
→ 不安全，P0 等待。
```

### 6.2 例题二：最少资源数

5 个进程，每个进程最多需要 3 台打印机。

至少需要多少台打印机，才能保证无论怎么调度都不会死锁？

套公式。

```text
最坏情况：每个进程都拿到了 k-1 台，都还差 1 台。
这时只要再多 1 台，就必定有一个进程能凑齐 3 台、跑完、释放。

m = n × (k - 1) + 1
  = 5 × (3 - 1) + 1
  = 5 × 2 + 1
  = 11
```

答案：11 台。

验一下边界。

```text
10 台：5 个进程各拿 2 台，全都在等第 3 台。死锁。
11 台：最坏情况是 5 个进程里 4 个各拿 2 台（8 台），剩 3 台。
      第 5 个进程最多拿 3 台，直接跑完，释放 3 台。
      链条断掉，不会死锁。
```

这一类题的公式只有一个，但要知道它为什么成立。

```text
n × (k-1) 是「所有人都卡在最后一步」的临界点。
再加 1，就必然有人能走完最后一步。
```

### 6.3 例题三：资源分配图能不能化简

给一个图，三个资源类各 1 个实例。

```text
R1 → P1，P1 → R2
R2 → P2，P2 → R3
R3 → P3，P3 → R1
```

化简。

```text
找「既不阻塞（没有未满足的请求边）又非孤立」的进程。
P1 有请求边 P1 → R2，阻塞。
P2 有请求边 P2 → R3，阻塞。
P3 有请求边 P3 → R1，阻塞。
一个都消不掉。
```

结论。

```text
图不可完全化简 → 存在死锁。
```

## 7. 真实系统里长什么样

> 以下是简化示意，函数名与配置项取自 Linux 与常见数据库，行为细节有删减。

通用操作系统基本不用银行家算法。

不是没想到，是条件不成立。

```text
① Max 不可预知：进程要多少内存、要打开几个文件，运行时才知道。
   「先声明最大需求」这条前提，在通用 OS 里根本立不住。
② 开销太大：每次分配都要跑一遍 O(n²) 的安全性检查，
   而内存分配每秒几万次。
③ 规模太大：进程数上千、资源类上千，n² 直接爆炸。
④ 进程动态生灭：算出来的安全序列，下一毫秒就过期了。
```

真正在用的，是三样东西。

**第一样：约定的锁顺序。**

```text
内核里所有锁的获取顺序必须符合层级约定。
Linux 用 lockdep（CONFIG_PROVE_LOCKING）在运行时记录「谁在持有什么锁的时候申请了什么锁」，
一旦发现反向路径，就报 possible circular locking dependency。
```

这就是「破坏循环等待」的工程实现。

```text
不是给每把锁编号，是给每个子系统定层级。
违反层级的代码在测试阶段就被拦下来。
```

**第二样：可超时的加锁。**

```text
pthread_mutex_timedlock、pthread_rwlock_timedrdlock
trylock 失败就退避重试
```

从「不可剥夺」这个角突破：等不到就不等了，放弃已持有的，重来。

```text
代价是活锁风险：两个线程同时退让、同时重试、再次撞上。
所以要加随机退避。
```

数据库用的是更精细的版本。

```text
wait-die：老事务等，年轻事务直接死掉重来。
wound-wait：老事务把年轻事务「打伤」（回滚），自己继续。
—— 用时间戳定优先级，保证不会互相等。
```

**第三样：检测 + 回滚。**

```text
InnoDB 维护一张等待图（wait-for graph）。
发现环，就挑一个「代价最小」的事务回滚：undo 记录最少、修改行数最少。
配置项是 innodb_deadlock_detect。
```

这就是教材里「检测 + 解除」的完整工业版。

```text
检测：在等待图上找环。
解除：撤销（回滚）一个牺牲者。
```

分布式系统更麻烦。

```text
没有全局时钟，拿不到全局一致的等待图。
所以分布式锁基本靠「租约 + 超时」：
  过期就当持有者死了，锁可以被抢。
——这不是检测死锁，是「假设它会死，提前留后路」。
```

至于「内存不够导致的僵局」，Linux 的选择是 OOM killer。

```text
不是解开死锁，是杀掉一个进程把资源抢回来。
严格说这是「剥夺」，而且剥夺得很粗暴。
```

## 8. 检测：把资源分配图化简

如果既不预防也不避免，那就只能事后发现。

检测（detection）的核心操作是「化简」。

```text
① 在资源分配图里找一个「既不阻塞、又非孤立」的进程。
   ——既不阻塞：它没有未满足的请求边。
   ——非孤立：它至少还持有一些资源（有分配边指向它）。
② 消去它的所有边：它释放资源，于是别人可能被唤醒。
③ 重复，直到消不掉为止。
④ 如果所有边都消掉了 → 无死锁。
   如果还剩边 → 有死锁，且剩下的进程就是死锁进程。
```

死锁定理：

```text
状态 S 是死锁状态 ⟺ S 的资源分配图不可完全简化。
```

举个例子，走一遍化简。

```text
R1（1 个实例）→ P1
P1 → R2（请求）
R2（1 个实例）→ P2
P2 → R1（请求）
```

```text
P1 有请求边，阻塞。
P2 有请求边，阻塞。
化简不动 → 不可完全简化 → 死锁。
```

再看一个能化简的。

```text
R1（2 个实例）：1 个给 P1，1 个空闲
P1 → R2（请求）
R2（1 个实例）→ P2
P2 没有请求边
```

```text
P2 既不阻塞又非孤立（它持有 R2）→ 消去 P2 的所有边
R2 空出来 → P1 的请求可以满足 → P1 变成不阻塞 → 消去 P1
全部消掉 → 无死锁。
```

检测的代价是「什么时候检测」。

```text
① 每次资源请求都检测：最及时，开销最大。
② 定时检测：折中，常用。
③ 利用率低时检测：系统闲下来了才查，因为死锁的典型症状就是 CPU 利用率掉下来。
```

第三种在教材里叫「基于利用率的检测」，408 会提一句。

```text
死锁不会让系统崩，只会让它闲。
所以「突然变闲」是个可用的信号。
```

还有一个简化版本，只在单实例资源时成立。

```text
单实例时，资源分配图可以压成「等待图」（wait-for graph）：
  节点只有进程，边 Pi → Pj 表示「Pi 在等 Pj 释放资源」。
死锁 ⟺ 等待图里有环。
```

这一压，把「资源节点」删掉了。

```text
因为每个资源只有一个实例，它的持有者和等待者都是唯一的。
资源节点夹在中间没有信息量，直接连一条进程到进程的边就够了。
```

代价是复杂度。

```text
化简算法的复杂度是 O(m × n²)：m 是资源类数，n 是进程数。
每次请求都跑一遍，对每秒上万次分配的系统来说不现实。
```

## 9. 解除：撤销、剥夺、回滚，以及鸵鸟

真的检测出死锁了，四条路。

```text
① 撤销所有死锁进程：最彻底，代价最大，已算的结果全丢。
② 逐个撤销，直到死锁解除：每次撤销后重新检测，代价可控。
③ 剥夺资源：从某个进程手里抢走资源给另一个，被抢的要能回滚。
④ 进程回滚：回退到之前的检查点（checkpoint），重新跑。
```

四条路总结成一句。

```text
解除的目标不是「解开这一次」，是「用最小的损失解开」。
所以选牺牲者比找环更难。
```

选谁当牺牲者，是有讲究的。

```text
优先级低的先死。
已运行时间短的先死（沉没成本低）。
还需时间长的先死（放开它，收益大）。
占用资源少的先死。
批处理进程比交互进程先死（用户感知小）。
```

这一串就是 408 选择题的原话范围。

最后是鸵鸟策略（ostrich algorithm）。

```text
假装死锁不存在。
不预防、不避免、不检测。
死锁了就重启。
```

听起来很荒唐，但它的理由很硬。

```text
死锁在通用系统里发生的概率很低。
预防的代价（资源利用率下降）是每天都在付的。
死锁的代价是偶尔重启一次。
——期望值算下来，不管更划算。
```

UNIX、Linux、Windows 基本就是这个态度。

```text
它们提供工具（lockdep、调试器、/proc 里的锁信息），
但不提供「保证不死锁」的机制。
```

## 10. 死锁、饥饿、活锁

三个词经常混，其实很好分。

```text
死锁（deadlock）：一组进程互相等，全体静止。谁都动不了。
饥饿（starvation）：某个进程长期得不到资源，但系统整体在动。
活锁（livelock）：大家都在动，但都在做无用功，谁也前进不了。
```

画出来对比。

```text
死锁：  P1 ⇄ P2        两边都不动
饥饿：  P3 一直在排队   别人一直插队，P3 永远排不上
活锁：  P1 让 P2，P2 让 P1，让完又同时重试，再次撞上
```

饥饿的经典例子。

```text
读者优先的读者-写者：写者永远等不到 readcount 归零。
短作业优先（SJF）：长作业可能永远排在后面。
低优先级进程：高优先级源源不断地来。
```

活锁的经典比喻。

```text
两个人在窄走廊迎面遇上，
都往左让，又都往右让，
来回几次，谁也没过去。
```

代码里的活锁。

```text
两个线程都 trylock 失败 → 都释放已持有的锁 → 都退避一个固定时间 → 同时重试 → 又同时失败。
解法：退避时间加随机。
```

真实世界里最有名的活锁是共享信道的冲突。

```text
两台主机同时发帧 → 冲突 → 都退避重发 → 又同时发 → 又冲突。
以太网的解法是二进制指数退避：每次冲突，退避窗口翻倍，并且随机。
```

退避窗口翻倍解决的是「退避时间太短」。

```text
随机解决的是「两边算出了同一个退避时间」。
两个机制缺一不可。
```

三者的共同点只有一条。

```text
都不是「资源不够」，都是「调度或等待策略」出了问题。
```

差别在于「系统还在不在动」。

```text
死锁：不动了。
饥饿：在动，但有人永远轮不到。
活锁：在动，但整体没有进展。
```

## 11. 容易混淆的点

**安全状态、不安全状态、死锁。**

```text
安全：一定不死锁。
不安全：可能死锁，也可能平安跑完。
死锁：已经卡住。
```

所以「不安全」不等于「死锁」。

```text
这是 408 最爱考的一句判断题。
银行家算法拒绝一次请求，是因为「会进入不安全状态」，
不是因为「已经死锁」。
```

**预防、避免、检测。**

```text
预防：破坏四个条件之一。分配前不需要计算，但资源利用率低。
避免：不破坏条件，每次分配前算安全性。要预知 Max。
检测：分配时不管，事后找环，找到再解除。
```

三种策略的「什么时候付代价」完全不同。

```text
预防：每天都付（利用率低）。
避免：每次分配都付（算安全性）。
检测：出事才付（回滚损失）。
```

再加一条，考试里常用来当选项。

```text
预防和避免都是「事前」的策略，区别在于要不要算。
检测和解除是「事后」的策略，区别在于要不要回滚。
```

**Need 的减法。**

```text
Need = Max - Allocation     ✓
Need = Max - Available      ✗
```

**银行家三步检查的顺序。**

```text
① Request ≤ Need
② Request ≤ Available
③ 试分配 + 安全性检查
```

顺序不能换。

```text
先检查 ① 是因为「申请超过自己声明的最大需求」是错误请求，不是资源不够。
先检查 ② 是因为连资源都没有，就没必要算安全性。
```

**死锁一定在环上，但环不一定死锁。**

```text
单实例：环 ⟺ 死锁。
多实例：环 ⟹ 可能死锁。
```

## 12. 小结 + 下一篇

四句话收束。

```text
① 死锁 = 组内互相等。四个必要条件同时成立才会发生。
② 预防破坏条件，避免算安全序列，检测找环，解除撤销进程。
③ 银行家只适用于「多类资源、多实例、Max 事先已知、进程数固定」的理想世界。
④ 真实系统用锁顺序 + 超时 + 检测回滚，通用 OS 大多选择鸵鸟。
```

回到开头那两台打印机。

```c
/* 改法一：有序分配 */
P1: lock(A); lock(B);
P2: lock(A); lock(B);      // 都先拿 A，环不可能形成

/* 改法二：一次性申请 */
P1: lock_all(A, B);
P2: lock_all(A, B);        // 要么全拿到，要么一个都不拿

/* 改法三：超时放弃 */
P1: if (!trylock(B, timeout)) { unlock(A); retry(); }
```

三种改法，对应三个被破坏的条件。

```text
有序分配 → 破坏循环等待
一次性申请 → 破坏请求并保持
超时放弃 → 破坏不可剥夺
```

下一篇换一块：从「进程之间怎么互相等」，转到「进程看到的地址怎么落到物理内存」。

```text
操作系统系统讲解 12：内存管理基础与连续分配
```

那一篇会回答：

```text
同一个程序，为什么换个位置加载还能跑？
内部碎片和外部碎片，分别是谁造成的？
最佳适应算法为什么实际上最差？
```
