先看一行汇编：

```asm
ADD R1, R2
```

这一行在 CPU 里，不是"一个动作"。

是六七个节拍。

```text
T0  PC → MAR，发读命令
T1  M(MAR) → MDR，PC + 1 → PC
T2  MDR → IR，译码
T3  R1 → A
T4  R2 → B
T5  (A) + (B) → R1
```

每个节拍里，谁决定"这一拍把 PC 送到 MAR"、"下一拍把 MDR 送到 IR"？

是控制器（control unit，CU）。

数据通路是路，控制器是红绿灯。

**先放一句反直觉的话在这里：**

```text
微程序控制器，是用软件的方式实现硬件控制。
```

它把"什么时候发什么控制信号"存成一张表。

要改指令，改表就行，不用改电路。

代价是：每条机器指令，都要多查一次控制存储器。

这一篇就把这两条路线拆开，一条一条数清楚。

## 1. 控制器在一条指令里做的四件事

控制器的职责，压成四条：

```text
① 取指令   给出地址，发出读命令，把指令取进 IR
② 译码     看懂操作码，判断这是什么指令、用什么寻址方式
③ 发信号   按节拍产生控制信号，指挥各个部件动作
④ 控时序   决定一个节拍多长、一条指令分几个节拍
```

前两条好理解。

后两条才是控制器真正的难点。

因为它管的是"顺序"和"时刻"，不是"数据"。

时序分三层：

```text
指令周期    取出一条指令并执行完，需要的全部时间
  └ 机器周期（CPU 周期）  完成一个独立操作的时间，如取指周期、间址周期、执行周期
      └ 时钟周期（节拍、T 周期）  机器周期再等分，一个节拍内完成一个或几个微操作
```

三层的包含关系：

```text
1 个指令周期 = 若干个机器周期
1 个机器周期 = 若干个时钟周期
```

一句"节拍"，指的就是最里面那层。

指令周期和机器周期的划分，有两种做法。

```text
定长机器周期：所有机器周期包含相同节拍数，控制简单，有浪费
不定长机器周期：按需要给不同的机器周期分配不同节拍数，快，控制复杂
```

408 题目里如果出现"每个机器周期含 4 个节拍"，那就是定长。

如果出现"取指 3 拍、执行 2 拍"，那就是不定长。

控制器要在这套时序骨架上，一拍一拍地发信号。

## 2. 最小模型：控制信号的两种来源

控制信号不是凭空来的。

它由三样东西决定：

```text
操作码   现在执行的是哪条指令
节拍     现在走到第几步
状态     运算结果是不是零、有没有进位、有没有中断请求
```

写成函数：

```text
控制信号 = f(操作码, 节拍, 状态)
```

把这个函数做成电路，就是硬布线控制器（hardwired control）。

把这个函数做成一张表，就是微程序控制器（microprogrammed control）。

两条路线的分岔点只在这里：

```text
硬布线：f 用门电路实现     → 信号算出来
微程序：f 用存储表实现     → 信号查出来
```

一张对照图：

```text
                    ┌──────────────┐
   操作码 ──────────►│              │
   节拍   ──────────►│  控制器 CU   │────────► 控制信号
   状态   ──────────►│              │
                    └──────┬───────┘
                           │
              ┌────────────┴────────────┐
              │                         │
        ┌─────┴─────┐            ┌──────┴──────┐
        │ 组合逻辑  │            │ 控制存储器  │
        │  + 时序   │            │     CM      │
        └───────────┘            └─────────────┘
           硬布线                  微程序
```

两条路线都能用。

区别在"改起来贵不贵"和"跑起来快不快"。

## 3. 硬布线控制器：组合逻辑遇到时序信号

硬布线控制器，也叫组合逻辑控制器。

它的核心是一个组合逻辑网络。

输入：

```text
IR 的操作码字段（经译码器变成一个个"这是 ADD""这是 LOAD"的信号）
节拍信号 T0、T1、T2……
状态标志 ZF（结果为零）、CF（进位）、中断请求
```

输出：

```text
PCout、MARin、MDRout、IRin、R1out、ALUadd、MemRead、MemWrite……
```

每个输出信号，都是一条逻辑表达式。

举个例子，取指周期的 T0 拍要把 PC 送到 MAR：

```text
PCout = FETCH · T0
MARin = FETCH · T0
```

翻译成人话：

```text
如果当前是取指周期，并且正处在 T0 拍，就把 PC 送上总线、打进 MAR。
```

执行周期的加法指令：

```text
R1out = ADD · T3
Ain   = ADD · T3
R2out = ADD · T4
Bin   = ADD · T4
ALUadd = ADD · T5
R1in  = ADD · T5
```

这些表达式用与门、或门、非门搭出来，或者写成可编程逻辑阵列（PLA）。

所以硬布线的本质是：

```text
把"哪条指令、哪一拍、发什么信号"写成布尔表达式，再用门电路固化。
```

它的时序结构长这样：

```text
        ┌────────────┐
  IR ──►│  操作码译码 │──┐
        └────────────┘  │
        ┌────────────┐  ├──►┌──────────┐      ┌──────────┐
  CLK ─►│ 节拍发生器  │──┼──►│ 组合逻辑 │─────►│ 控制信号 │
        └────────────┘  │   │   阵列   │      └──────────┘
  标志 ─────────────────┘   └──────────┘
```

优点只有一个，但很硬：

```text
快。
```

信号只经过几级门延迟就出来，与时钟周期同量级。

缺点也只有一个，但很贵：

```text
改不了。
```

指令增加一条、操作码换一个编码，逻辑表达式就要重写，电路就要重做。

所以硬布线控制器适合指令系统稳定的机器。

精简指令集计算机（RISC）正好是这种机器：指令少、格式规整、寻址方式少。

RISC 用硬布线，几乎是必然选择。

有人会问：用 PLA 或者 ROM 存一张真值表，算硬布线还是微程序？

```text
算硬布线。
因为控制信号仍由组合逻辑"算"出来，只是逻辑被固化进了阵列。
```

判断标准不是"用没用存储阵列"，而是"控制信号的产生方式"。

```text
组合逻辑算 → 硬布线
查微指令表 → 微程序
```

ROM 里存的是真值表，不是微指令，这两者不是一回事。

## 4. 微程序控制器：从微命令到控制存储器

微程序控制器的思路，来自一个类比。

既然一条机器指令可以拆成几步，那能不能把"每一步发什么信号"当成一条"指令"存起来？

能。

于是有了五层概念，一层比一层大：

```text
微命令 microcommand   一个控制信号，如 PCout
微操作 micro-operation 一个微命令（或几个）控制下完成的最小操作，如 PC → MAR
微指令 microinstruction 一个节拍内的一组微命令 + 下地址信息
微程序 microprogram    完成一条机器指令的一串微指令
控制存储器 CM           存放全部微程序的只读存储器
```

包含关系：

```text
1 条机器指令  →  1 段微程序（含若干条微指令）
1 条微指令    →  若干条微命令（并行发出）
1 条微命令    →  1 个控制信号
```

注意这里的"1 条机器指令对应 1 段微程序"。

取指那一小段是公共的，所有机器指令共用一段取指微程序，执行部分才按操作码分派。

所以更准确的说法是：

```text
机器指令 → 微程序，是 1 对 1；
但取指微程序是 1 段对多条指令的公共段。
```

控制存储器（control store，CM）在 CPU 内部。

```text
它不在主存里，不占主存地址空间。
它存的是微指令，不是机器指令。
它的地址由微地址寄存器 μAR 给出。
它的读出速度要跟得上一个节拍。
```

一条微指令从 CM 读出来，控制字段直接（或经译码后）变成控制信号。

下地址字段决定下一条微指令在哪。

微程序控制器的完整结构：

```text
                 ┌──────────────────────────┐
   操作码 ──────►│ 微地址形成逻辑            │
   标志   ──────►│ （入口地址 / 顺序 / 转移）│
                 └────────────┬─────────────┘
                              │ 微地址
                              ▼
                 ┌──────────────────────────┐
                 │  控制存储器 CM（ROM）     │
                 │  微指令 1                 │
                 │  微指令 2                 │
                 │  ……                       │
                 └────────────┬─────────────┘
                              │ 微指令
                              ▼
                 ┌──────────────────────────┐
                 │  微指令寄存器 μIR         │
                 └──────┬────────────┬──────┘
                        │控制字段     │下地址字段
                        ▼             ▼
                   控制信号      微地址形成逻辑
```

一条机器指令的执行，就变成两件事：

```text
① 找到这条机器指令对应的微程序入口
② 一条一条执行微指令，直到最后一条
```

入口地址怎么来？

操作码经译码后，查一张"操作码 → 微程序入口地址"的映射表。

这张表可以用一小块 ROM 实现，也可以直接用操作码拼上高位地址。

### 4.1 微指令格式：水平型与垂直型

微指令的格式，决定"一拍能干多少事"。

最简的一种分法，把控制字段和下地址字段分开：

```text
┌──────────────────────────┬──────────────┐
│      控制字段            │  下地址字段  │
│  （一堆微命令的编码）    │  （后继地址）│
└──────────────────────────┴──────────────┘
```

控制字段怎么编，有三种方式。

```text
直接控制（直接编码）：每一位对应一个微命令，1 表示发，0 表示不发
字段直接编码：把互斥的微命令分成若干段，每段用几位编码，段内译码
字段间接编码：一个字段的含义由另一个字段解释，进一步压缩位数
```

直接控制最直观，也最长。

字段直接编码最短，但要多一级译码，速度稍慢。

按控制字段的组织方式，微指令分两型。

**水平型微指令（horizontal microinstruction）**

```text
一条微指令里，多个微命令可以同时有效。
微指令长，微程序短。
并行度高，执行快。
编写难，位数浪费多（很多位常年是 0）。
```

**垂直型微指令（vertical microinstruction）**

```text
一条微指令里，通常只有一个（或极少数）微命令有效。
格式像机器指令：操作码 + 地址码。
微指令短，微程序长。
并行度低，执行慢。
编写容易，接近写汇编。
```

两型的对照：

| 对比项 | 水平型微指令 | 垂直型微指令 |
|---|---|---|
| 并行能力 | 一条微指令可含多个微命令 | 一条微指令一般一个微操作 |
| 微指令长度 | 长 | 短 |
| 微程序长度 | 短 | 长 |
| 执行速度 | 快 | 慢 |
| 编写难度 | 难 | 易 |
| 典型用途 | 追求性能的机器 | 追求简单、规整的机器 |

记忆的锚点是一句反比：

```text
微指令越长，微程序越短。
微指令越短，微程序越长。
```

因为总工作量固定，摊到每条微指令上的多少，决定了条数。

408 里还有一类"混合型"（diagonal），介于两者之间：控制字段分段，段内直接编码，段间并行。

题目一般只考水平型和垂直型的定性对比，以及字段编码的位数计算。

### 4.2 微地址怎么形成

微地址就是"下一条微指令在 CM 的哪个单元"。

形成方式有四种，实际机器是组合使用。

```text
① 下地址字段直接给出        微指令里带 8 位下地址，直接送 μAR
② 微程序计数器 μPC 加一     顺序执行时 μPC + 1
③ 按操作码转移              机器指令的第一条微指令，地址由操作码译码得到
④ 按状态标志转移            根据 ZF、CF 等选择两个后继地址之一
```

画成图：

```text
        ┌──────────────┐
        │ 下地址字段   │──┐
        └──────────────┘  │
        ┌──────────────┐  │    ┌─────────┐
        │ μPC + 1      │──┼───►│ 多路    │───► μAR
        └──────────────┘  │    │ 选择器  │
        ┌──────────────┐  │    └─────────┘
        │ 操作码入口   │──┤         ▲
        └──────────────┘  │         │
        ┌──────────────┐  │    ┌────┴────┐
        │ 转移地址     │──┘    │ 转移控制 │
        └──────────────┘       └─────────┘
```

多路选择器的控制端，就是"顺序、转移、入口"这几种情况的选择信号。

微地址寄存器 μAR 的位数，决定了 CM 的容量上限：

```text
CM 单元数 ≤ 2^(μAR 位数)
```

反过来说，微指令总数定了，μAR 的位数就定了：

```text
μAR 位数 = ⌈log2(微指令总数)⌉
```

这里有一个高频陷阱。

题目给了"下地址字段 8 位"，很多人就直接写"CM 最多 256 条微指令"。

不一定。

下地址字段只负责"直接给出后继地址"这一种情况。

顺序执行靠 μPC 加一，转移靠专门的转移逻辑，它们都可以越过下地址字段的 8 位范围。

但如果 CM 里有 320 条微指令，而所有跳转都靠下地址字段，那就必须扩到 9 位。

判断标准是：

```text
看微地址是"全部由下地址字段给出"，还是"下地址字段 + μPC + 转移"共同给出。
前者受字段位数限制，后者受 μAR 位数限制。
```

## 5. 走查：ADD 的微操作序列

现在把一条 `ADD R1, R2` 拆开，写到节拍一级。

前提假设（简化示意）：

```text
单总线结构
ALU 两个输入来自暂存器 A、B，输出可送回总线
存储器读/写各占一拍
R1、R2 是通用寄存器
```

微操作序列：

```text
取指周期（公共微程序）
T0: PC → MAR，Read
T1: M(MAR) → MDR，PC + 1 → PC
T2: MDR → IR，op(IR) → 微地址形成逻辑

执行周期（ADD 的微程序）
T3: R1 → A
T4: R2 → B
T5: (A) + (B) → R1
```

六拍，六条微指令。

注意 T0 到 T2 里的细节。

T1 拍同时做两件事：数据从存储器进 MDR，PC 加一。

这两件事不冲突，因为 PC 加一不需要总线。

T3 和 T4 是"把两个操作数分别搬进 ALU 的两个输入暂存器"。

单总线一次只能搬一个，所以必须两拍。

T5 拍 ALU 做加法，结果经总线写回 R1。

换个有存储器操作数的指令 `ADD R1, (R2)`：

```text
T0: PC → MAR，Read
T1: M(MAR) → MDR，PC + 1 → PC
T2: MDR → IR，译码

T3: R2 → MAR，Read          ← 先算地址，发读命令
T4: M(MAR) → MDR，R1 → A     ← 等存储器，同时把 R1 送 A
T5: MDR → B
T6: (A) + (B) → R1
```

七拍。

比寄存器版本只多一拍：多了一次"送地址"。

收数那一拍，正好和"把 R1 送进 A 暂存器"并在一起，不额外占拍。

这就是寻址方式带来的成本，在微操作序列里一眼能看出来。

把这段微程序写成水平型微指令，控制字段用直接编码（简化示意）：

```text
微指令  有效微命令                          下地址
μ0      PCout, MARin, MemRead                μ1
μ1      MDRout, IRin, PC+1                   μ2
μ2      （译码，无控制信号）                  μ3
μ3      R1out, Ain                           μ4
μ4      R2out, Bin                           μ5
μ5      ALUadd, R1in, 结束                   μ0（下一条指令）
```

一条微指令能同时发三个微命令，这就是水平型的并行。

如果换成垂直型，每一拍要拆成好几条微指令：

```text
μ0: PCout
μ1: MARin
μ2: MemRead
μ3: MDRout
μ4: IRin
……
```

同样一段，从 6 条变成 15 条以上。

微指令短了，微程序长了。

## 6. 408 怎么考

这一节的题型，只有四类。

```text
① 硬布线与微程序的定性对比（选择题）
② 微指令编码的位数计算（选择题、综合题）
③ 微操作序列的书写与节拍数（综合题）
④ 控制存储器容量、微地址位数（选择题）
```

一道一道来，都能手算。

### 6.1 例题一：控制存储器容量与微地址位数

题目（自拟）：

```text
某机采用微程序控制，指令系统共 64 条机器指令。
每条机器指令对应的微程序平均含 5 条微指令。
另有一段公共取指微程序，含 6 条微指令，所有指令共用。
微指令字长 32 位，其中下地址字段 8 位。
求：
(1) 控制存储器的最小容量（按字节计）
(2) 微地址寄存器至少需要多少位
(3) 下地址字段 8 位是否够用
```

第一问，先数微指令总条数：

```text
64 × 5 = 320
320 + 6 = 326 条
```

容量：

```text
326 × 32 = 10432 位
10432 ÷ 8 = 1304 B
```

第二问：

```text
2^8 = 256 < 326 ≤ 512 = 2^9
所以 μAR 至少 9 位
```

第三问：

```text
8 位下地址只能直接寻址 256 个单元，不够 326 条。
若所有后继地址都由下地址字段给出，必须扩到 9 位。
若采用 μPC 顺序加一 + 条件转移，下地址字段只负责转移目标，可以仍用 8 位，
但此时能直接跳转的范围只有 256 条，需要分段或两级转移。
```

这道题的三个坑：

```text
坑一：漏掉公共取指微程序的 6 条（得 320，不是 326）
坑二：把"微指令条数"算成"机器指令条数"（得 40，错得离谱）
坑三：直接拿 8 位当答案（256 条，不够）
```

### 6.2 例题二：字段直接编码的位数

题目（自拟）：

```text
某微程序控制器有 30 个微命令，分成 4 个互斥组：
第 1 组 8 个，第 2 组 8 个，第 3 组 8 个，第 4 组 6 个。
求：
(1) 直接控制编码需要多少位
(2) 字段直接编码需要多少位
```

第一问，一位一个微命令：

```text
30 位
```

第二问，每组要留一个"全不操作"的状态：

```text
第 1 组：8 + 1 = 9 种状态，⌈log2 9⌉ = 4 位
第 2 组：4 位
第 3 组：4 位
第 4 组：6 + 1 = 7 种状态，⌈log2 7⌉ = 3 位
总位数 = 4 + 4 + 4 + 3 = 15 位
```

验算：

```text
2^4 = 16 ≥ 9 ✓
2^4 = 16 ≥ 9 ✓
2^4 = 16 ≥ 9 ✓
2^3 = 8  ≥ 7 ✓
```

省了 15 位。

但要注意那个"加一"。

组内 8 个微命令，8 种编码刚好用完，就没有"这一组什么都不发"的编码了。

一个节拍里如果这一组不该有任何动作，就没法表示。

所以必须留一个空状态，9 种状态要 4 位。

这是 408 最爱设的一个陷阱。

### 6.3 例题三：微操作序列与节拍数

题目（自拟）：

```text
单总线数据通路，指令 ADD R1, (R2) 的功能是 R1 ← R1 + M[R2]。
存储器读写各占一个节拍，PC 加一与访存可同拍完成。
写出完整的微操作序列，并给出最少节拍数。
```

答案：

```text
T0: PC → MAR，Read
T1: M(MAR) → MDR，PC + 1 → PC
T2: MDR → IR
T3: R2 → MAR，Read
T4: M(MAR) → MDR，R1 → A
T5: MDR → B
T6: (A) + (B) → R1
```

七拍。

如果题目改成 `ADD R1, R2`，答案少一拍：

```text
T3: R1 → A
T4: R2 → B
T5: (A) + (B) → R1
```

六拍。

如果题目改成"多总线结构，A、B 可同时装入"，那 T3、T4 合并成一拍，再少一拍。

所以做这类题，第一步不是背序列，是看数据通路：

```text
几条总线？
ALU 有几个输入暂存器？
存储器读写要几拍？
PC 加一和访存能不能同拍？
```

这四问答完，序列自然就出来了。

### 6.4 硬布线与微程序的对比题

选择题常问"下列说法正确的是"。

标准对比记这张表就够：

| 对比项 | 硬布线控制器 | 微程序控制器 |
|---|---|---|
| 控制信号来源 | 组合逻辑电路直接产生 | 控制存储器中的微指令 |
| 速度 | 快（几级门延迟） | 慢（要读 CM，多一个层次） |
| 修改与扩展 | 难，要改电路 | 易，改微程序即可 |
| 规整性 | 差（逻辑杂乱） | 好（像写程序） |
| 典型机器 | RISC | CISC |
| 芯片面积 | 逻辑门占面积 | CM 占面积（ROM 阵列规整） |

一句话总结：

```text
硬布线用空间换时间，微程序用时间换灵活。
```

## 7. 真实芯片里长什么样

**x86：微码的主场。**

x86 是典型的复杂指令集（CISC）。

一条 `ADD` 很规矩，但一条 `REP MOVSB`、一条带复杂寻址的指令，硬件很难用一组固定逻辑直接实现。

所以现代 x86 处理器在前端做了一件事：

```text
把一条 x86 指令翻译成一个或多个微操作（μop），再交给后端执行。
```

简单的算术指令，译码器直接给出 1 个 μop。

复杂的字符串指令、系统指令，由微码序列器（microcode sequencer）从微码 ROM 里一条条读出来。

这跟本节讲的微程序控制器，是同一个思路的现代版本：

```text
复杂的控制序列，不写成电路，存在一张表里。
```

更关键的一点：这块存储是可写的（writable control store）。

操作系统启动时可以加载微码更新（microcode update），修处理器的勘误，也用于安全缓解。

Linux 上 `intel-microcode` / `amd-ucode` 这两个包干的就是这件事。

改不了电路，就改表。

这正是微程序"可修改"优势的现实版。

（简化示意：现代 x86 前端还有 μop cache、DSB 等结构，微码只是其中一条路径。）

**ARM：硬布线的主场。**

ARM 的经典核心（Cortex-M 系列、早期的 ARM7/ARM9）走的是硬布线 + 有限状态机。

原因很直接：

```text
指令规整、长度固定或半固定、寻址方式少。
用组合逻辑直接出控制信号，面积小、功耗低。
```

嵌入式场景对功耗和面积敏感，硬布线更划算。

到了高性能的 Cortex-A 系列，前端也会变得更复杂，取指、译码、发射分工明确，控制逻辑里同样出现查表结构。

但"简单指令用硬布线、复杂序列用表"这个分工，一直没变。

**一句话对照：**

```text
x86：微码 + μop，兼容性优先。
ARM：硬布线为主，能效优先。
```

这两种选择，背后是第 15 篇讲过的 CISC 与 RISC 之争。

控制器不是孤立的技术选择，它是指令系统的影子。

## 8. 反直觉：微程序是"用软件的方式实现硬件控制"

回头说那个反直觉的点。

直觉上，控制器是"硬件"，应该用电路实现。

微程序控制器偏不。

它把控制信号写成一张表，存在 ROM 里，然后用一个"取微指令、译码、执行"的小引擎去跑这张表。

这个结构，和 CPU 执行程序几乎一模一样：

```text
程序     = 指令序列        →  微程序 = 微指令序列
PC       = 指令地址        →  μAR    = 微指令地址
IR       = 指令寄存器      →  μIR    = 微指令寄存器
译码器   = 指令译码        →  微指令译码 = 控制字段翻译
存储器   = 主存            →  CM     = 控制存储器
```

所以微程序控制器是"CPU 里的 CPU"。

它是用一套硬件，去解释另一套"软件"。

**这就是"用软件的方式实现硬件控制"的含义。**

好处立刻显现：

```text
要加一条新指令？写一段新微程序，改一下入口地址表。
要修一条指令的时序？改几条微指令。
要兼容老指令？留着那段微程序就行。
```

x86 能背着几十年的历史包袱往前走，微码功不可没。

代价也很具体：

```text
每条机器指令，都要先读微指令，再按微指令发控制信号。
硬布线是一步：门电路直接出信号。
微程序是两步：读 CM，再出信号。
```

多出来的这一步，就是一个存储器访问的延迟。

所以微程序控制器天然比硬布线慢。

慢多少？

```text
硬布线：控制信号延迟 ≈ 几级门延迟
微程序：控制信号延迟 ≈ CM 读出时间（一个节拍量级）
```

在同一个时钟频率下，这就是"能不能再快一点"的差别。

还有一个常被忽略的代价：

```text
微程序控制器把"控制"变成了数据。
数据就可能被改。
所以现代 CPU 的微码更新既是功能，也是攻击面。
```

这就是为什么微码更新要签名校验。

能改表的系统，必须能证明"这张表是谁给的"。

## 9. 容易混淆的点

**第一，微指令不是机器指令。**

```text
机器指令：程序员可见，存在主存，由 PC 指向
微指令：程序员不可见，存在 CM，由 μAR 指向
```

**第二，微程序不占主存空间。**

CM 在 CPU 内部，是独立的存储器。

题目里问"控制存储器容量"，不要和主存容量混在一起算。

**第三，微命令与微操作不是一回事。**

```text
微命令是信号（PCout 有效）
微操作是动作（PC 的内容被送到总线）
```

一个微命令控制一个微操作，但一个微操作可能需要几个微命令配合。

408 的选择题里，"微命令"和"微操作"经常被互换着考。

**第四，水平型与垂直型的"长短"方向容易记反。**

```text
水平型：微指令长、微程序短、并行、快
垂直型：微指令短、微程序长、串行、慢
```

记法：水平型"横着铺开"，一条里塞很多命令，所以长。

**第五，一条机器指令对应一段微程序，但取指段是公共的。**

数微指令条数时，别忘了加公共段。

这是例题一最大的坑。

**第六，微地址位数看 μAR，不看下地址字段。**

```text
CM 有 326 条微指令 → μAR 9 位
下地址字段给几位，是设计选择，不是容量上限
```

除非题目明确说"后继地址全部由下地址字段给出"。

**第七，字段直接编码要留空状态。**

n 个互斥微命令，需要 ⌈log2(n+1)⌉ 位，不是 ⌈log2 n⌉ 位。

**第八，微程序控制器也能很快。**

"微程序慢"是相对硬布线说的。

如果 CM 用高速 ROM、微指令很短、并行度高，微程序控制器一样能跑很高主频。

现代 x86 就是证据。

## 10. 两条路线怎么选

一张决策图：

```text
指令系统复杂、要向后兼容、要能打补丁？
        │
        ├── 是 ──► 微程序（或混合：简单指令硬布线，复杂指令微码）
        │
        └── 否 ──► 指令少而规整、追求能效与面积？
                      │
                      └── 是 ──► 硬布线
```

现实中的机器，很少是纯粹的一种。

```text
x86：前端译码 + 微码 + μop cache，混合
ARM 低端：纯硬布线
ARM 高端：硬布线为主，复杂序列查表
RISC-V 开源核：硬布线的有限状态机
```

所以 408 题里问"RISC 一定用硬布线吗"，答案是"通常，但不是必然"。

微程序的价值不在快，在"改得起"。

硬布线的价值不在灵活，在"快得起来"。

两者之间没有优劣，只有匹配。

## 11. 小结

控制器干四件事：

```text
取指令、译码、发控制信号、控时序
```

控制信号的函数形式：

```text
控制信号 = f(操作码, 节拍, 状态)
```

两种实现：

```text
硬布线：f 用门电路算出来，快、难改，RISC 常用
微程序：f 用 CM 查出来，慢、易改，CISC 常用
```

微程序这条线的五个概念，从小到大：

```text
微命令 → 微操作 → 微指令 → 微程序 → 控制存储器
```

两个必背公式：

```text
CM 容量 = 微指令总条数 × 微指令字长
μAR 位数 = ⌈log2(微指令总条数)⌉
```

一个必背的编码规则：

```text
字段直接编码，n 个互斥微命令 → ⌈log2(n+1)⌉ 位
```

一个必背的微操作序列（`ADD R1, R2`，单总线）：

```text
T0: PC → MAR，Read
T1: M(MAR) → MDR，PC + 1 → PC
T2: MDR → IR
T3: R1 → A
T4: R2 → B
T5: (A) + (B) → R1
```

最后是那句反直觉的话：

```text
微程序控制器用软件的方式实现硬件控制。
改指令只要改表，代价是每条指令多查一次控制存储器。
```

下一篇讲打断。

一条指令正走到 T3，忽然来了一个时钟中断，或者执行到 `DIV` 发现除数为零。

CPU 要先把现场保存好，才能跳走。

少保存一个寄存器，回来就错。
