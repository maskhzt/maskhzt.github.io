一台八核机器，跑一个程序。

它一定快 8 倍吗？

不一定。

```text
单线程程序：八核只用上一个，加速比 1
完美并行的程序：也到不了 8，因为还有串行部分和同步开销
```

流水线也有同样的问题。

k 段流水线，理想加速比是 k。

实际到不了。

**先放一句反直觉的话在这里：**

```text
流水线加速比的上限是 k，但实际到不了 k。
填充、排空、冒险停顿都会吃掉一部分，段数越多，这部分占比越大。
```

这一篇就把这三个量算清楚：

```text
加速比 S = 串行时间 / 流水线时间
吞吐率 TP = 指令条数 / 总时间
效率 E = 有效面积 / 总面积
```

## 1. 一个数字：为什么八核不是八倍

先看一个具体的账。

```text
一个程序，60% 的代码可以完美并行，40% 只能串行。
四核。
```

Amdahl 定律：

```text
加速比 = 1 / (串行比例 + 并行比例 / 核数)
       = 1 / (0.4 + 0.6 / 4)
       = 1 / 0.55
       ≈ 1.82
```

四核，1.82 倍。

就算核数无穷大：

```text
加速比上限 = 1 / 0.4 = 2.5
```

天花板是 2.5，不是无穷。

为什么串行部分这么致命？

因为并行只压缩"可并行"的那一段，串行段一点不动。

```text
总时间 = 串行时间 + 并行时间 / 核数
核数 → ∞ 时，总时间 → 串行时间
```

所以 Amdahl 定律的真正含义是：

```text
并行化的收益，被"不能并行的部分"封顶。
```

这条规律不只管多核，也管流水线。

流水线里"不能重叠的部分"，就是填充、排空和停顿。

```text
填充（fill）：前 k − 1 拍流水线没满，是"启动成本"
排空（drain）：最后 k − 1 拍只有尾巴在走，是"收尾成本"
冒险停顿：中间的空隙
```

三项加起来，就是"到不了 k"的全部理由。

## 2. 最小模型：时空图与面积

设：

```text
k = 流水段数
n = 指令条数
τ = 一个时钟周期（一段的时间）
```

加速比的定义有个隐含前提。

```text
串行与流水线执行的是同一批指令、完成同样的功能。
```

如果流水线靠改语义来重叠，这个比值就没有意义了。

所以做题时不要自己给流水线"加戏"。

串行执行（不用流水线），每条指令要走 k 段，总时间：

```text
T_串行 = n · k · τ
```

流水线执行，时空图：

```text
指令    1    2    3    4    5    6    7    8    9
I1     IF   ID   EX  MEM   WB
I2          IF   ID   EX  MEM   WB
I3               IF   ID   EX  MEM   WB
I4                    IF   ID   EX  MEM   WB
I5                         IF   ID   EX  MEM   WB
```

第一条在 k = 5 拍完成。

之后每拍一条，共 n − 1 拍。

```text
T_流水 = (k + n − 1) · τ
```

于是加速比：

```text
S = T_串行 / T_流水
  = n·k·τ / ((k + n − 1)·τ)
  = n·k / (k + n − 1)
```

这就是 408 必背的那个公式。

再看"面积"。

时空图里每一个小格，代表"一段 × 一拍"的硬件资源。

```text
总格子数 = 宽 × 高 = (k + n − 1) × k
有效格子数 = 每条指令真正干活的格子 = n · k
```

为什么用"面积"定义效率？

因为流水线的成本，就是"段 × 拍"这个二维资源。

一段硬件在一拍里闲着，就是浪费了一个格子。

所以效率的物理含义是：

```text
流水线的硬件，有多大比例的时间在真正干活。
```

这和 Cache 的命中率是两种完全不同的"利用率"，别混。

效率：

```text
E = 有效面积 / 总面积
  = n·k / (k·(k + n − 1))
  = n / (k + n − 1)
```

画出来看得更清楚（k = 5，n = 4，总 8 拍，`-` 表示该段这一拍空转）：

```text
拍   c1   c2   c3   c4   c5   c6   c7   c8
WB   -    -    -    -    I1   I2   I3   I4
MEM  -    -    -    I1   I2   I3   I4   -
EX   -    -    I1   I2   I3   I4   -    -
ID   -    I1   I2   I3   I4   -    -    -
IF   I1   I2   I3   I4   -    -    -    -
```

左上角那块空三角，是填充（fill）。

右下角那块空三角，是排空（drain）。

```text
填充格子数 = k(k−1)/2
排空格子数 = k(k−1)/2
有效格子数 = n·k
总面积     = k·(k+n−1)
```

n 越大，两块三角形占总面积的比例越小。

所以"指令很多"是流水线高效的前提。

## 3. 三个量：S、TP、E

**加速比（speedup）**

```text
S = 串行执行时间 / 流水线执行时间
理想值 = k
实际值 = n·k / (k + n − 1)
```

**吞吐率（throughput）**

```text
TP = 完成的指令条数 / 总时间
   = n / ((k + n − 1)·τ)
```

单位是"条/秒"。

当 n → ∞：

```text
TP_max = 1 / τ
```

也就是每拍一条。

**效率（efficiency）**

```text
E = 有效面积 / 总面积
  = n / (k + n − 1)
```

三个量的关系：

```text
S = k · E
TP = E / τ
```

验算一下 S = k·E：

```text
k · E = k · n / (k + n − 1) = n·k / (k + n − 1) = S ✓
```

还有一个常考的换算：只给 TP 和 τ，求效率。

```text
E = TP × τ
```

例：TP = 0.8 条/ns，τ = 1 ns，则 E = 0.8，即 80%。

这个式子从 TP = E / τ 移项就能得到。

做题时如果只给了吞吐率和时钟频率，先用它求效率，再求加速比。

这个关系很好用。

算不出面积，就用 S = k·E 反推。

三个量说的是三件事。

```text
加速比：同样的活，快了几倍 —— 看时间
吞吐率：单位时间干多少活 —— 看速率
效率：硬件有多少格子真在干活 —— 看利用率
```

一个类比：

```text
S 是"这辆车比走路快几倍"
TP 是"每小时能送多少货"
E 是"车厢坐了几成"
```

三者不能互相替代。

一台机器可能 S 很高但 E 很低（段数多、指令少）。

也可能 E 很高但 S 不高（段数少）。

408 里三个量经常一起问，因为出题人想看你有没有分清它们。

## 4. 手算：n = 100，k = 5

设 τ = 1 ns。

串行：

```text
T_串行 = 100 × 5 × 1 ns = 500 ns
```

流水线：

```text
T_流水 = (5 + 99) × 1 ns = 104 ns
```

加速比：

```text
S = 500 / 104 ≈ 4.81
```

吞吐率：

```text
TP = 100 / 104 ns ≈ 0.96 条/ns
```

效率：

```text
E = 500 / (5 × 104) = 500 / 520 ≈ 96.2%
```

三个数字放在一起看：

```text
S = 4.81（上限 5）
E = 96.2%
TP ≈ 0.96 条/ns（上限 1 条/ns）
```

差的 3.8%，就是那 4 拍填充。

### 4.1 各段不等长：瓶颈段

真实流水线，每段不可能一样长。

假设五段的延迟是：

```text
IF 2 ns，ID 1 ns，EX 3 ns，MEM 1 ns，WB 1 ns
```

时钟周期由最慢的段决定：

```text
τ = 3 ns
```

串行时间：

```text
每条指令 = 2 + 1 + 3 + 1 + 1 = 8 ns
n = 100 → T_串行 = 800 ns
```

流水线：

```text
T_流水 = (5 + 99) × 3 ns = 312 ns
```

加速比：

```text
S = 800 / 312 ≈ 2.56
```

效率：

```text
E = 800 / (5 × 312) = 800 / 1560 ≈ 51.3%
```

验算 S = k·E：

```text
5 × 0.513 = 2.56 ✓
```

效率掉到一半。

原因：

```text
EX 段 3 ns，其他段只有 1~2 ns。
每一拍里，除了 EX，其他四段都在等。
```

这叫瓶颈段（bottleneck stage）。

对策：

```text
① 把瓶颈段再细分（EX 拆成两级），但段数 k 变了，公式也要重算
② 把瓶颈段的活儿分一部分给别的段
③ 重复设置瓶颈段（并行两个 EX）
```

408 里最常见的问法是：

```text
给定各段延迟，问时钟周期取多少、加速比多少、瓶颈是哪一段。
```

时钟周期永远取最长的那段。

不是平均值。

### 4.2 加上停顿

如果 20% 的指令各需要 1 拍停顿：

```text
停顿拍数 = 100 × 20% = 20 拍
T_流水 = 104 + 20 = 124 ns
S = 500 / 124 ≈ 4.03
E = 500 / (5 × 124) = 500 / 620 ≈ 80.6%
```

从 4.81 掉到 4.03。

掉的那 0.78，是冒险的价钱。

所以 408 的流水线题，步骤固定：

```text
第一步：算 T_串行 = n·k·τ（或 n·Σ各段延迟）
第二步：算 T_流水 = (k + n − 1)·τ + 停顿拍数
第三步：S = T_串行 / T_流水
第四步：TP = n / T_流水
第五步：E = 有效面积 / 总面积 = S / k
```

### 4.3 单位换算的坑

τ 常常给 ns，主频常常给 GHz，两者要统一。

```text
τ = 1 ns   → 主频 = 1 GHz
τ = 0.5 ns → 主频 = 2 GHz
τ = 0.25 ns→ 主频 = 4 GHz
```

换算关系：

```text
主频(GHz) = 1 / τ(ns)
```

如果题目给"主频 2 GHz"，那 τ = 0.5 ns。

如果又给"5 段流水线，执行 100 条指令"：

```text
T = (5 + 99) × 0.5 ns = 52 ns
```

不要写成 104 ns（那是 τ = 1 ns 的结果）。

单位错一位，整题白算。

## 5. 段数 k 怎么选

直觉上，段数越多，每段越短，时钟越快。

但有三项成本随 k 增长。

**第一项：流水段寄存器。**

```text
每段之间都要一组寄存器。
k 段就有 k − 1 组。
寄存器的建立时间、传输延迟要算进 τ 里。
```

**第二项：冒险的罚。**

```text
分支在越靠后的段定论，预测错误罚越多。
load-use 的间隔不变，但相对占比变大。
```

**第三项：时钟偏斜与功耗。**

```text
时钟要同步送到每一段，k 越大，偏斜越难控制。
每一段的时钟树都要吃掉功耗。
```

算一个具体的模型。

设总组合逻辑延迟 100 ns，每段寄存器开销 1 ns。

```text
k = 5 ：τ = 100/5 + 1 = 21 ns，T_流水 = (5 + 99) × 21 = 2184 ns
k = 10：τ = 100/10 + 1 = 11 ns，T_流水 = (10 + 99) × 11 = 1199 ns
k = 20：τ = 100/20 + 1 = 6 ns， T_流水 = (20 + 99) × 6 = 714 ns
k = 50：τ = 100/50 + 1 = 3 ns， T_流水 = (50 + 99) × 3 = 447 ns
k = 100：τ = 100/100 + 1 = 2 ns，T_流水 = (100 + 99) × 2 = 398 ns
```

串行时间固定：

```text
T_串行 = 100 ns × 100 条 = 10000 ns
```

加速比：

```text
k = 5  → S = 4.58
k = 10 → S = 8.34
k = 20 → S = 14.0
k = 50 → S = 22.4
k = 100→ S = 25.1
```

看最后两行。

```text
k 从 50 加到 100，段数翻倍，加速比只从 22.4 涨到 25.1。
```

因为寄存器开销 1 ns 不变，而每段的有效工作从 2 ns 变成 1 ns。

开销占比从 1/3 涨到 1/2。

```text
段数越多，寄存器开销占比越大，加速比的边际收益越小。
```

这就是"段数不是越多越好"的算术证明。

真实 CPU 的段数，通常在 5 到 20 之间。

举两个量级（简化示意）。

```text
经典 5 段 RISC：IF / ID / EX / MEM / WB，教科书模型
现代高性能核：前端取指译码 + 后端发射执行，十几级
```

为什么现代核不干脆做到 30 级？

因为分支预测错误罚会跟着涨。

```text
20 级流水线，分支在 EX 定论，罚拍接近 15。
预测准确率 95%，每条分支平均罚 0.75 拍。
```

这个开销，抵消了高主频带来的收益。

### 5.1 三种"超"

**超标量（superscalar）**

```text
一个时钟周期发射多条指令。
有多条流水线、多个执行单元。
CPI 可以小于 1（IPC 大于 1）。
```

比如 4 发射，理想 IPC = 4。

**超流水（superpipelining）**

```text
把每一段再细分，时钟频率更高。
段数变多，每段变短。
本质是"用更细的粒度换更快的时钟"。
```

**超长指令字（VLIW，very long instruction word）**

```text
编译器把多条可并行的操作打包成一条很长的指令。
硬件只管按字段并行执行，不需要复杂的调度逻辑。
```

三者的区别：

```text
超标量：硬件找并行
超流水：把段切细，提高时钟
VLIW：编译器找并行，硬件简单
```

举个具体的对照。

```text
4 发射超标量：一拍取 4 条，硬件判断哪 4 条能同时走
4 级超流水：四拍完成一条，但时钟快 4 倍
4 槽 VLIW：一条指令里塞 4 个操作，编译器保证不冲突
```

三者都能提高吞吐，代价不同：

```text
超标量：硬件复杂度最高（要动态调度）
超流水：对时钟与寄存器要求最高
VLIW：对编译器要求最高，硬件最简单
```

还要注意 k 与冒险的耦合。

```text
k 越大，分支定论的位置越靠后，罚拍越多。
k 越大，load-use 的 1 拍不变，但它在总周期里的占比变小。
```

所以"加深流水线"和"减少冒险"经常是矛盾的。

一句话就够，408 只考定性。

## 6. 408 怎么考

题型四类：

```text
① 给 n、k、τ，算 S、TP、E
② 给各段延迟，找瓶颈段，算时钟周期
③ 加停顿或分支预测错误，重算 S
④ Flynn 分类与多机结构判断
```

### 6.1 例题一：基本三量

题目（自拟）：

```text
5 段流水线，τ = 2 ns，执行 200 条指令，无冒险。
求 T_串行、T_流水、S、TP、E。
```

```text
T_串行 = 200 × 5 × 2 = 2000 ns
T_流水 = (5 + 199) × 2 = 408 ns
S = 2000 / 408 ≈ 4.90
TP = 200 / 408 ns ≈ 0.49 条/ns = 4.9 × 10^8 条/s
E = S / k = 4.90 / 5 = 98.0%
```

验算 E：

```text
2000 / (5 × 408) = 2000 / 2040 ≈ 0.980 ✓
```

### 6.2 例题二：瓶颈段

题目（自拟）：

```text
某流水线分 4 段，各段延迟为 2 ns、4 ns、2 ns、2 ns。
执行 50 条指令，无冒险。
求时钟周期、T_流水、S、TP、E。
```

时钟周期取最长段：

```text
τ = 4 ns
```

串行时间（按各段实际延迟相加）：

```text
每条 = 2 + 4 + 2 + 2 = 10 ns
T_串行 = 50 × 10 = 500 ns
```

流水线：

```text
T_流水 = (4 + 49) × 4 = 212 ns
```

三个量：

```text
S = 500 / 212 ≈ 2.36
TP = 50 / 212 ≈ 0.236 条/ns
E = S / k = 2.36 / 4 = 59.0%
```

注意一个陷阱。

```text
T_串行 用的是"各段实际延迟之和"，不是 k × τ。
因为串行执行时，每条指令不需要按最慢段对齐。
```

如果题目统一说"每段都是 τ"，那才用 n·k·τ。

这是两种口径，做题时看清题设。

### 6.3 例题三：加停顿与分支

题目（自拟）：

```text
5 段流水线，τ = 1 ns，执行 200 条指令。
其中 15% 是 load/store，每条造成 1 拍结构冒险停顿。
分支占 10%，预测准确率 90%，错误罚 2 拍。
求 S 与 E。
```

基准：

```text
T_串行 = 200 × 5 × 1 = 1000 ns
T_流水基准 = (5 + 199) × 1 = 204 ns
```

停顿：

```text
结构冒险：200 × 15% = 30 拍
控制冒险：200 × 10% × 10% = 2 次错误，2 × 2 = 4 拍
合计 34 拍
```

总时间与三量：

```text
T_流水 = 204 + 34 = 238 ns
S = 1000 / 238 ≈ 4.20
TP = 200 / 238 ≈ 0.84 条/ns
E = 1000 / (5 × 238) = 1000 / 1190 ≈ 84.0%
```

对照无停顿的 4.90：

```text
4.90 → 4.20，掉了 14%
```

停顿 34 拍，占基准 204 拍的 16.7%。

加速比掉的比例差不多。

### 6.4 例题四：多机加速比

题目（自拟）：

```text
某程序 60% 的代码可完美并行，40% 必须串行。
(1) 4 核时加速比多少？
(2) 核数无穷大时上限多少？
(3) 要让加速比达到 3，可并行比例至少多少？
```

(1)

```text
S = 1 / (0.4 + 0.6/4) = 1 / 0.55 ≈ 1.82
```

(2)

```text
S_max = 1 / 0.4 = 2.5
```

(3) 设可并行比例为 p：

```text
1 / (1 − p + p/4) = 3
1 − p + p/4 = 1/3
1 − 0.75p = 0.3333
0.75p = 0.6667
p ≈ 0.889
```

至少要 88.9% 的代码能并行。

这道题的三个答案，依次说明：

```text
多核的收益被串行部分卡住
核数不是万能的
并行比例的要求非常苛刻
```

## 7. 真实芯片里长什么样

**发射宽度与 IPC。**

现代高性能核心早就不止"每拍一条"。

```text
取指、译码、发射、执行，每一级都可以是多个宽度。
Apple M1 的 Firestorm 核心，公开资料里是 8 宽解码。
AMD Zen、Intel Core 的发射宽度在 4 到 6 之间。
```

（简化示意：厂商口径与微架构版本差异很大，这里只取量级。）

`perf stat` 里能看到实际的 IPC：

```text
    1,000,000,000      cycles
      800,000,000      instructions     # 0.80  insn per cycle
```

```text
IPC < 1：流水线没喂饱（冒险、缺失、依赖）
IPC > 1：超标量在起作用
```

同样 3 GHz 的两颗核，IPC 1.2 和 2.0，性能差 1.67 倍。

所以性能粗略写成：

```text
性能 ≈ 主频 × IPC × 核数（在可并行前提下）
```

三个因子各有天花板。

```text
主频：功耗墙，2005 年之后基本停在 3~4 GHz
IPC：指令级并行的极限，受依赖与冒险限制
核数：受 Amdahl 定律与一致性开销限制
```

这就是第 01 篇那句"主频不是性能的全部"的算术版。

Intel 的 Top-down 分析方法，把"没喂饱"拆成四类（简化示意）：

```text
 retiring      正常退休
 bad speculation 分支预测错误
 frontend bound  取指/译码供不上
 backend bound   执行单元等数据
```

这四类正好对应第 19 篇的三种冒险。

**内存墙与多核。**

主频从 2005 年之后基本停在 3~4 GHz。

```text
不是做不上去，是功耗和散热受不了。
```

于是性能提升换了两条路：

```text
① 每拍干更多活（超标量、SIMD）
② 一颗芯片塞更多核（多核）
```

`perf stat` 里还能看到跨核迁移：

```text
    123      cpu-migrations
```

数字大，说明进程在核之间来回跑，Cache 局部性差。

（简化示意：具体阈值要看负载类型。）

## 8. 反直觉：上限是 k，但到不了 k

回到那句话：

```text
加速比的上限是 k，但实际到不了 k。
```

从公式看，这是显然的：

```text
S = n·k / (k + n − 1) = k / (1 + (k − 1)/n)
```

分母永远大于 1（只要 k > 1）。

所以 S 永远小于 k。

差多少？

```text
n = 100，k = 5  ：S = 4.81，差 3.8%
n = 100，k = 20 ：S = 16.8，差 16%
n = 10， k = 5  ：S = 50/14 ≈ 3.57，差 29%
```

```text
n 越小、k 越大，差得越多。
```

因为填充和排空的固定成本是 k − 1 拍。

它占 (k + n − 1) 的比例：

```text
(k − 1) / (k + n − 1)
n 固定，k 越大，这个比例越大
```

再加上冒险停顿，实际加速比还要再低一截。

所以真实的加速比，往往只有理论值的一半到三分之二。

举个量级（简化示意）。

```text
教科书模型：n = 1000，k = 5，S ≈ 4.99
真实处理器：同样 5 段，因停顿与缺失，S 常在 2 到 4 之间
```

差距来自两处：

```text
一是 CPI 大于 1（冒险与缺失）
二是流水线的段并不等长（瓶颈段拖慢时钟）
```

所以做 408 题时用公式，看真实芯片时看 IPC。

```text
段数 k 是一个"收益递减"的参数。
前几段收益最大，后面越来越像在交税。
```

这种收益递减，在流水线和多核上完全同构。

```text
流水线：k 段的加速比上限是 k，实际 S = nk/(k+n−1)
多核：   p 核的加速比上限是 1/(1−p)，实际还要扣同步与通信
```

两者都是"阿姆达尔式"的收益递减。

## 9. 多处理机：四种 Flynn 分类

Flynn 分类按两个维度切：

```text
指令流（instruction stream）：单 or 多
数据流（data stream）：单 or 多
```

| 类型 | 全称 | 指令流 | 数据流 | 典型例子 |
|---|---|---|---|---|
| SISD | single instruction, single data | 单 | 单 | 传统单核 CPU |
| SIMD | single instruction, multiple data | 单 | 多 | 向量机、GPU、AVX |
| MISD | multiple instruction, single data | 多 | 单 | 理论上存在，无实用 |
| MIMD | multiple instruction, multiple data | 多 | 多 | 多核、多处理机、集群 |

记忆法：

```text
SISD：一条指令算一个数 —— 你写的普通 C 代码
SIMD：一条指令算一排数 —— 向量加法
MIMD：多条指令各算各的 —— 多核并行跑两个线程
MISD：多条指令算同一个数 —— 找不到用途
```

SISD 是"标量"的世界。

一条指令只处理一个数据，靠提高主频和 IPC 提升性能。

SIMD 是"向量"的世界。

一条指令处理一排数据，靠加宽寄存器提升性能。

MIMD 是"任务"的世界。

多个核各跑各的线程，靠加核提升性能。

三者的优化手段完全不同：

```text
SISD：提频率、提 IPC、加深流水线
SIMD：加宽向量寄存器、让编译器向量化
MIMD：加核、改算法让任务能并行
```

所以"这颗 CPU 快不快"这个问题，要先问"跑什么程序"。

MISD 为什么没有实用价值？

```text
让多条指令同时处理同一个数据，本质上只有容错计算（多份相同结果比对）。
它不是"并行加速"，是"冗余校验"。
```

SIMD 值得多说一句。

```text
4 个 32 位整数打包进 128 位寄存器，一条指令做 4 个加法。
理论加速比 4，实际受数据对齐、混合类型影响。
```

这就是 SSE、AVX、NEON 干的事。

算一下 SIMD 的理论收益。

```text
128 位寄存器，装 4 个 32 位整数。
一条加法指令处理 4 个数据。
理想加速比 4。
```

实际收益通常低于 4，原因有三个：

```text
数据要按对齐方式打包，不是所有循环都能向量化
循环里有分支或跨迭代依赖时，向量化会失败
打包（gather）和解包（scatter）本身有开销
```

所以编译器会先判断"这个循环值不值得向量化"。

`-O3 -mavx2` 这类选项干的就是这件事。

再看一个常考的对比。

```text
SISD：一条指令，一个数据，一个结果
SIMD：一条指令，一排数据，一排结果
```

前者靠"提高时钟"，后者靠"提高并行宽度"。

两条路的成本完全不同。

（简化示意：真实向量指令还有掩码、混合、跨步访问等细节。）

MIMD 再细分：

```text
共享内存多处理机（SMP / UMA）
分布式内存多处理机（MPP / 集群）
```

区别在"内存怎么访问"。

补一句 GPU 的归类。

GPU 常被放进 SIMD，严格说是 SIMT（single instruction, multiple threads）。

```text
几十个线程锁步执行同一条指令，各自有自己的寄存器。
遇到分支时，两条路径要串行执行，叫分支发散（divergence）。
```

所以 GPU 的效率高度依赖"同一批线程走同一条路"。

（简化示意：不同厂商的 warp / wavefront 宽度不同。）

## 10. 共享内存、消息传递与 Cache 一致性

**共享内存（shared memory）**

```text
所有处理器访问同一个物理地址空间。
一个处理器写的变量，另一个处理器能直接读到。
```

按访问延迟再分：

```text
UMA（uniform memory access）：访问任何内存的延迟相同，对称多处理 SMP
NUMA（non-uniform memory access）：访问本地内存快、远端内存慢
```

**消息传递（message passing）**

```text
每个处理器有自己的私有内存。
要交换数据，必须显式发消息（send / receive）。
```

典型是集群（cluster），编程接口如 MPI。

两者对比：

```text
共享内存：编程简单，硬件复杂（一致性）
消息传递：编程复杂，硬件简单（可扩展）
```

举个编程模型的对比：

```text
共享内存：两个线程读写同一个变量，加锁就行
消息传递：两个进程各有变量，必须 send / recv 显式传
```

前者靠硬件保证一致性，后者靠程序员保证顺序。

复杂度没有消失，只是换了个地方。

**Cache 一致性（cache coherence）**

共享内存的麻烦在这里。

```text
处理器 A 把 x 读到自己的 Cache，改了。
处理器 B 的 Cache 里还有旧的 x。
B 读到的就是脏数据。
```

解决办法是协议。

```text
监听协议（snooping）：每个 Cache 盯着总线，有人写就作废自己的副本
目录协议（directory）：用一个目录记录"哪块数据被谁缓存了"，按需通知
```

一句话记：

```text
Cache 一致性协议，保证多个 Cache 看到的是同一份数据。
```

MESI 是最常见的一种，四个状态：

```text
M（modified）  本核改过，和内存不一致，独占
E（exclusive） 和内存一致，独占
S（shared）    和内存一致，可能多核共享
I（invalid）   无效
```

写的时候要先把其他核的副本打成 I。

这需要核间通信，是并行程序的隐性开销。

（简化示意：真实协议还有 MOESI 等变体，状态转换更复杂。）

**多核芯片的实际布局**

```text
每个核：私有 L1（指令 + 数据）、私有 L2
所有核：共享 L3
核间：环形总线或网格（mesh）互连
```

共享 L3 是"最后一级共享"，也是核间通信的落脚点。

还有一个坑叫**伪共享**（false sharing）：

```text
两个核改的是不同变量，但这两个变量在同一 Cache 行里。
一致性协议按行作废，于是两个核互相把对方的行打无效。
性能暴跌，但代码看起来完全正确。
```

对策是填充（padding），把两个变量隔到不同行。

举个量级（简化示意）：

```text
两个线程各改一个 int，恰好落在同一个 64 字节 Cache 行。
每次写都要把对方的副本打无效，再重新取。
实测可能比单线程还慢，因为核间通信比计算本身贵。
```

填充的办法：

```text
把两个变量隔开 64 字节
或者让每个线程改私有副本，最后再合并
```

**NUMA 的直觉。**

```text
每个 CPU 有自己的本地内存，访问快。
访问别人的内存要过互连，慢 1.5 到 2 倍。
```

所以在 NUMA 机器上，进程调度要考虑"内存亲和性"。

Linux 的 `numactl` 就是干这个的。

```text
把进程绑在它数据所在的节点上，避免跨节点访问。
```

这也是"共享内存不等于均匀访问"的现实注脚。

一句话总结两条路线：

```text
共享内存：硬件替你做一致性，你付出可扩展性的代价。
消息传递：你自己做一致性，换来几乎无上限的扩展。
```

选哪条，取决于"核数"和"程序员的时间"哪个更贵。

## 11. 一道综合题：从流水线到多核

题目（自拟）：

```text
某 CPU 主频 2 GHz，5 段流水线，理想 CPI = 1。
实测统计：
load/store 占 25%，每条造成 1 拍结构冒险停顿；
分支占 15%，预测准确率 90%，错误罚 2 拍；
Cache 缺失平均每条摊 0.3 拍。
(1) 实际 CPI
(2) MIPS
(3) 预测准确率提到 98% 后的 CPI 与 MIPS
(4) 该程序 80% 可并行，双核加速比
```

(1) 逐项累加：

```text
基准 CPI   = 1.00
结构冒险   = 0.25 × 1 = 0.25
控制冒险   = 0.15 × 0.10 × 2 = 0.03
Cache 缺失 = 0.30
CPI = 1.00 + 0.25 + 0.03 + 0.30 = 1.58
```

(2)

```text
MIPS = 主频 / (CPI × 10^6)
     = 2×10^9 / (1.58 × 10^6)
     ≈ 1265.8
```

(3)

```text
控制冒险 = 0.15 × 0.02 × 2 = 0.006
CPI = 1.00 + 0.25 + 0.006 + 0.30 = 1.556
MIPS = 2×10^9 / (1.556×10^6) ≈ 1285.3
```

只涨了 1.5%。

```text
因为控制冒险本来只占 0.03 拍。
优化一个小项，收益不会大。
```

(4) Amdahl：

```text
S = 1 / (0.2 + 0.8/2) = 1 / 0.6 ≈ 1.67
```

双核 1.67 倍，不是 2 倍。

这道题把这一篇和第 01、19 篇串起来了：

```text
CPI 拆成"基准 + 各类冒险 + 缺失"
MIPS 从 CPI 和主频算
多核加速比从 Amdahl 算
```

一个小提醒：

```text
CPI 的加法只在"各类停顿线性叠加"时成立。
真实机器里冒险可能重叠（停顿期间 Cache 缺失不额外收费），
题目都会明确说"各类停顿独立计算"。
```

## 12. 容易混淆的点

**第一，S、TP、E 不是三个独立指标。**

```text
S = k · E
TP = E / τ
```

知道两个就能推第三个。

**第二，T_串行 的口径要看题设。**

```text
题设"每段都是 τ" → T_串行 = n·k·τ
题设"各段延迟不同" → T_串行 = n·Σ各段延迟
```

两种混用是常见错。

**第三，时钟周期取最长段，不是平均段。**

```text
τ = max(t1, t2, ..., tk)
```

**第四，效率的分子是"有效面积"，不是"有效时间"。**

```text
E = 有效面积 / 总面积 = n·k / (k·(k+n−1))
```

数值上等于 S/k，但物理含义是面积利用率。

**第五，段数 k 不是越大越好。**

```text
寄存器开销、冒险罚拍、时钟偏斜都随 k 涨。
```

**第六，超标量和超流水不是一回事。**

```text
超标量：一拍发射多条（横向变宽）
超流水：一段切更细（纵向变细）
```

**第七，SIMD 不是"多核"。**

```text
SIMD 是一个核里的一条指令处理多个数据。
MIMD 才是多个核各跑各的。
```

**第八，超线程（SMT）不是多核。**

```text
超线程是一个物理核上跑两个逻辑线程，共享执行单元。
它能填满流水线空隙，但不增加执行单元。
```

**第九，Cache 一致性和内存一致性不是一件事。**

```text
Cache 一致性：多个 Cache 的同一地址，值要一致
内存一致性：多个核看到的读写顺序要符合某种模型
```

前者是"值"，后者是"顺序"。

**第十，多核加速比不能套流水线公式。**

```text
流水线：S = n·k/(k+n−1)，k 是段数
多核：  S = 1/((1−p) + p/m)，m 是核数，p 是并行比例
```

两个公式形状像，含义完全不同。

**第十一，加速比的分子分母要对齐。**

```text
S = 串行时间 / 流水线时间
两个时间必须包含同样的工作量、同样的 I/O 与同样的缺失代价
```

只把 CPU 时间放进分子、把 I/O 时间漏在分母外，算出来的 S 没有意义。

**第十二，多核的"核"和流水线的"段"不是一回事。**

```text
段：同一条指令的不同阶段，时间上切分
核：不同指令流的不同处理器，空间上切分
```

段数再多，也只服务一条指令流。

核数要起作用，程序得真的有多个指令流。

## 13. 小结

三个量：

```text
S  = T_串行 / T_流水 = n·k / (k + n − 1)
TP = n / T_流水
E  = 有效面积 / 总面积 = S / k
```

一个关系：

```text
S = k · E，TP = E / τ
```

一个手算流程：

```text
① 定 τ（最长段）
② T_串行 = n·k·τ 或 n·Σ各段延迟
③ T_流水 = (k + n − 1)·τ + 停顿拍数
④ 算 S、TP、E
```

三种"超"：

```text
超标量：一拍多条，硬件找并行
超流水：段内再分，提高时钟
VLIW：编译器打包，硬件简单
```

四种 Flynn 分类：

```text
SISD 单指令单数据   普通单核
SIMD 单指令多数据   向量、GPU
MISD 多指令单数据   无实用
MIMD 多指令多数据   多核、集群
```

多机的两条路线：

```text
共享内存：UMA / NUMA，要 Cache 一致性协议
消息传递：私有内存，显式收发消息
```

最后是那句反直觉的话：

```text
流水线加速比的上限是 k，但实际到不了。
填充、排空、冒险各吃一口，段数越多，被吃的比例越大。
```

地址线、数据线、控制线，一组线连起所有部件。
