四行汇编：

```asm
LOAD  R1, 0(R2)
ADD   R3, R1, R4
SUB   R5, R3, R6
AND   R7, R5, R8
```

每条指令都要用前一条的结果。

按顺序执行，一条一条来，4 条指令要 4 × 5 = 20 拍。

流水线里呢？

```text
理论最短：5 + 4 − 1 = 8 拍
实际：9 拍
```

多出来的那一拍，是 `LOAD` 和 `ADD` 之间的那次停顿。

**先放一句反直觉的话在这里：**

```text
转发（forwarding）能消掉大部分数据冒险，但消不掉 load-use。
```

因为 `LOAD` 的数据要到访存阶段结束才拿得到。

下一条指令的执行阶段，等不及。

这一篇就把"为什么等不及"算给你看。

## 1. 从一条指令的五段说起

经典的五段流水线（five-stage pipeline），把一条指令拆成五段：

```text
IF   取指   PC → 存储器 → 指令寄存器
ID   译码   译码，读寄存器堆，算转移地址
EX   执行   ALU 运算
MEM  访存   读/写数据存储器
WB   写回   结果写回寄存器堆
```

每段之间放一个流水段寄存器（pipeline register）：

```text
   ┌────┐  ┌────┐  ┌────┐  ┌────┐  ┌────┐
──►│ IF │─►│ ID │─►│ EX │─►│MEM │─►│ WB │──►
   └────┘  └────┘  └────┘  └────┘  └────┘
      ▲        ▲       ▲       ▲       ▲
   每一拍，所有段同时工作，结果推进一格
```

流水段寄存器不是装饰。

它的作用是"锁住上一拍的结果"，让五个段能同时干活而互不干扰。

代价是每一段都要多一份寄存器的延迟。

所以流水线不缩短单条指令的时间。

```text
单条指令还是 5 拍，一拍不多一拍不少。
流水线缩短的是"平均每条指令"的时间。
```

时空图画出来是这样：

```text
指令    1    2    3    4    5    6    7    8
I1     IF   ID   EX  MEM   WB
I2          IF   ID   EX  MEM   WB
I3               IF   ID   EX  MEM   WB
I4                    IF   ID   EX  MEM   WB
I5                         IF   ID   EX  MEM   WB
```

横着看是一条指令的五段。

竖着看是一拍里有五条指令在干不同的活。

数一数：

```text
第 1 条在 5 拍完成。
之后每一拍完成一条。
n 条指令、k 段：总时间 = k + (n − 1) 拍
```

这个式子值得单独看一眼。

```text
k 是填充（fill）的拍数：前 k − 1 拍里，流水线还没填满
n − 1 是稳态之后的拍数：每拍完成一条
```

画时空图时，数最右下角那个格子的横坐标，就是总周期。

理想情况下，CPI = 1。

每拍一条，这就是流水线的全部收益。

代价是三样：

```text
① 单条指令的延迟没变短（还是 5 拍），甚至因为寄存器变长了一点
② 需要额外的流水段寄存器，面积和功耗都涨
③ 会出现冒险，让"每拍一条"变成"有时一拍零条"
```

第三样是这一篇的主题。

前两样是第 20 篇算账时要用的。

补一句"为什么单条指令不变慢"。

因为五个段是同时工作的，一条指令在 EX 的时候，另一条在 ID，还有一条在 IF。

时钟一拍，所有段一起往前走一格。

所以吞吐量上去了，延迟没下来。

这就是流水线最本质的交换：

```text
用"多条指令重叠"换"吞吐量"，
不换"单条指令的延迟"，还要多付寄存器与冒险的钱。
```

## 2. 最小模型：三种冒险

冒险（hazard）的定义很朴素：

```text
下一条指令没法按计划在下一拍进入下一段。
```

三种来源，对应三种"缺"：

| 类型 | 英文 | 缺什么 | 典型例子 |
|---|---|---|---|
| 结构冒险 | structural hazard | 缺部件 | 取指和访存抢存储器 |
| 数据冒险 | data hazard | 缺数据 | `ADD` 后面紧跟 `SUB` |
| 控制冒险 | control hazard | 缺地址 | 分支、跳转、异常返回 |

对策也正好三套：

```text
结构冒险：加部件（分离 Cache、多端口），或者停一拍
数据冒险：转发（forwarding），转发救不了的停一拍
控制冒险：预测、延迟槽、冲刷，最差就是停
```

判断顺序：

```text
先看是不是抢部件 → 结构冒险
再看是不是等数据 → 数据冒险
最后看是不是不知道下一条在哪 → 控制冒险
```

这个顺序，就是做 408 综合题的第一步。

一个生活类比：汽车装配线。

```text
工位就那么多（结构不够）
零件还没送到（数据不够）
下一辆车不知道装哪种型号（控制不够）
```

装配线的产量，永远被这三个问题里最慢的那个卡住。

流水线也一样。

```text
CPI 不是 1，而是 1 加上三种冒险各自贡献的零头。
```

## 3. 结构冒险：抢同一个部件

最经典的结构冒险，发生在取指和访存之间。

五段流水线里，IF 要读存储器拿指令，MEM 要读存储器拿数据。

如果只有一个存储器、一个端口：

```text
     c3    c4
I1   EX   MEM     ← 这一拍 I1 在读数据存储器
I2   ID   EX
I3   IF   ID
I4        IF      ← 这一拍 I4 要读存储器取指令
```

具体到拍子上：

```text
c4：I1 在 MEM 段读数据，同时 I4 在 IF 段要读指令。
    同一个存储器，同一拍，两个请求。
```

相隔三条指令，照样撞车。

因为 IF 每拍都要读，MEM 也每拍都可能读。

只能一个先用，另一个等。

**对策一：分离 Cache。**

```text
指令 Cache（I-Cache）和数据 Cache（D-Cache）分开。
IF 走 I-Cache，MEM 走 D-Cache，各走各的。
```

这是现代处理器的标准做法。

L1 一定是"哈佛结构"：指令与数据分开。

注意分的是 Cache，不是主存。

主存还是那一个，但因为 Cache 命中率高，绝大多数访问在 L1 就分流了。

**对策二：加端口。**

一个存储器做双端口，一拍读两次。

成本高，面积大，只在少量场合用。

**对策三：停顿。**

让后一条指令等一拍。

这叫插入一个气泡（bubble）。

算一下停顿的影响。

题目（自拟）：

```text
5 段流水线，只有一个存储器端口，指令与数据不分开。
程序共 100 条指令，其中 30% 是 load/store。
其他冒险不计。
求：总周期数与 CPI。
```

先算无冒险的基准：

```text
100 + 5 − 1 = 104 拍
```

每条 load/store 在 MEM 段都要和 IF 抢一次存储器，停 1 拍：

```text
30 条 × 1 拍 = 30 拍
总周期 = 104 + 30 = 134 拍
CPI = 134 ÷ 100 = 1.34
```

分离 Cache 之后：

```text
总周期 = 104 拍
CPI = 1.04
加速比 = 134 ÷ 104 ≈ 1.29
```

一个部件的有无，值 29%。

这就是结构冒险为什么值得用硬件消除，而不是靠停。

再补一种做法：多体交叉存储器。

```text
主存分成多个体，低位交叉编址。
IF 读一个体，MEM 读另一个体，同一拍互不干扰。
```

这和第 08 篇讲低位交叉编址是同一个思路。

只是那里为的是带宽，这里为的是"两条指令同时访存不打架"。

结构冒险还有一个不显眼的形式：寄存器堆。

```text
寄存器堆通常只有一个写端口。
两条指令同一拍都要写回 → 也是结构冒险。
```

五段流水线里 WB 段只有一条指令在写，所以不会冲突。

但超标量（一拍发射多条）就会撞上，于是寄存器堆要做多写端口。

## 4. 数据冒险：RAW、WAR、WAW 与转发

数据冒险分三种，按"读写的先后"命名。

```text
RAW（read after write，写后读）：后一条要读前一条写的值 —— 真依赖
WAR（write after read，读后写）：后一条要写前一条读过的值 —— 反依赖
WAW（write after write，写后写）：后一条要写前一条写过的值 —— 输出依赖
```

只有 RAW 是"真的缺数据"。

WAR 和 WAW 是"名字冲突"。

举例说明区别。

```asm
; RAW
ADD R1, R2, R3     ; 写 R1
SUB R4, R1, R5     ; 读 R1，要的是刚写进去的值

; WAR
SUB R4, R1, R5     ; 读 R1
ADD R1, R2, R3     ; 后写 R1，不能抢在 SUB 读之前写

; WAW
ADD R1, R2, R3     ; 写 R1
SUB R1, R4, R5     ; 再写 R1，最终值必须是后一条的
```

WAR 和 WAW 的解决办法是**寄存器重命名**（register renaming）：

```text
把第二个 R1 换成 R9，冲突就没了。
程序语义不变，名字换了。
```

在顺序执行的五段流水线里：

```text
WAR 不会发生（读总在写之前，顺序保证）
WAW 不会发生（写回按顺序）
```

所以 408 的五段流水线题，只考 RAW。

RAW 的典型：

```asm
ADD R1, R2, R3     ; 写 R1
SUB R4, R1, R5     ; 读 R1 —— RAW
```

`SUB` 在 ID 段读寄存器，`ADD` 在 WB 段才写回。

按顺序，`SUB` 要等到 `ADD` 写回后才能读到正确的 R1。

中间差 3 拍。

**转发（forwarding / bypassing）** 就是来解决这 3 拍的。

思路很直接：

```text
ALU 的结果在 EX 段末尾就有了，不必等到 WB。
直接从这个中间结果拉一根线，送到需要它的地方。
```

三条转发路径：

```text
① EX/MEM 寄存器 → EX 段输入端（上一条指令的 ALU 结果）
② MEM/WB 寄存器 → EX 段输入端（上上条的 ALU 结果或 load 结果）
③ MEM/WB 寄存器 → MEM 段写数据端（store 要写的数据）
```

画成图：

```text
              ┌──────────────────────────┐
              │        转发通路           │
              ▼                          │
   ┌────┐  ┌────┐  ┌────┐  ┌────┐  ┌────┐│
──►│ IF │─►│ ID │─►│ EX │─►│MEM │─►│ WB ││
   └────┘  └────┘  └────┘  └────┘  └────┘│
                       ▲        │        │
                       └────────┘        │
                    EX/MEM → EX          │
                       ▲                 │
                       └─────────────────┘
                     MEM/WB → EX
```

有了转发，`ADD` 后跟 `SUB`：

```text
        c3    c4
ADD     EX   MEM
SUB          EX ← 从 EX/MEM 转发拿到结果
```

`ADD` 在 c3 末尾算出结果，放进 EX/MEM 寄存器。

`SUB` 在 c4 的 EX 段开头就能拿到。

零停顿。

两条转发路径同时可用时，选新的：

```text
如果 EX/MEM 和 MEM/WB 里都有同一个寄存器的值，用 EX/MEM 的。
因为它来自更近的那条指令，值更新。
```

这是转发控制逻辑里一个必考的细节。

转发能不能用，判断分三步。

```text
第一步：消费者在第几段用这个寄存器（EX 段还是 MEM 段）
第二步：生产者什么时候把结果放进哪个流水段寄存器
第三步：比较两个时刻，生产者不晚于消费者，就能转发
```

整理成一张对照：

```text
生产者 ADD  ：EX 段末尾出结果 → 结果进 EX/MEM
生产者 LOAD ：MEM 段末尾出结果 → 结果进 MEM/WB

消费者用 ALU 输入  ：EX 段开头要
消费者用 store 数据 ：MEM 段开头要

ADD  → EX 消费者：能
ADD  → MEM 消费者：能
LOAD → EX 消费者：差一拍，不能
LOAD → MEM 消费者：刚好，能
```

最后两行，就是 load-use 题的全部答案。

转发也有救不了的情况，那是第八节的事。

## 5. 控制冒险与停顿

控制冒险来自"不知道下一条在哪"。

```asm
BEQ R1, R2, target
ADD R3, R4, R5      ; 取不取？
```

`BEQ` 在 ID 段算出转移地址、在 EX 段才知道跳不跳。

而 IF 每一拍都要取一条指令。

于是问题来了：

```text
BEQ 还在 ID 的时候，IF 已经取了 ADD。
如果最后跳了，ADD 就白取了，后面那条也白取了。
```

三条对策，从差到好：

```text
① 停：等分支结果出来再取。最简单，最慢。
② 预测：猜一个方向先取，猜错了再冲刷。
③ 延迟槽：把一条一定有用的指令放在分支后面，硬件不用猜。
```

分支不是一种指令，是三类。

```text
条件分支（BEQ、BNE）：跳不跳要看比较结果
无条件跳转（J、JMP）：一定跳，只需要目标地址
间接跳转（JR、函数返回）：目标地址在寄存器里
```

三类的冒险程度不同：

```text
无条件跳转：目标地址在 ID 段就能算出，罚 1 拍
条件分支：要等 EX 段的比较结果，罚 2 拍
间接跳转：要等寄存器读出，往往更晚
```

所以同一个"分支"，问"罚几拍"之前，先问"是哪一类"。

**停顿方案**：

```text
分支在 EX 段出结果，前面已经取了两条。
停 2 拍，等结果，再决定取哪。
```

**预测方案**：

```text
静态预测：总是预测不跳（或总是跳），简单，准确率一般
动态预测：用历史记录猜，准确率高，硬件复杂
```

静态预测有两种常见策略。

```text
总是预测不跳：实现最简单，顺序取指不断流
向后跳预测跳、向前跳预测不跳（BTFN）：利用循环的规律
```

循环的规律很好用。

```text
for 循环的回头分支，绝大多数时候是跳的。
只有循环退出那一次不跳。
```

所以"向后跳就猜跳"在循环上准确率很高。

代价是函数调用、if 语句这些前向分支容易猜错。

**延迟槽（delay slot）**：

```text
在分支指令后面固定跟一条"无论跳不跳都要执行"的指令槽。
编译器负责往槽里填一条有用的指令，填不出来就填 nop。
```

MIPS 的经典做法，后来因为深流水线和乱序执行而淡出。

**冲刷（flush）**：

```text
预测错了，把已经取进来、已经译码的指令全部作废。
作废的代价 = 预测错误罚（misprediction penalty）。
```

罚多少？

```text
罚拍 ≈ 分支定论的那一段，与 IF 之间隔了几段
5 段机、EX 段定论 → 罚 2 拍
5 段机、ID 段定论（专门加了比较器）→ 罚 1 拍
深流水线（15 段以上）→ 罚 10 拍以上
```

算一下预测的收益。

题目（自拟）：

```text
分支指令占 20%，预测准确率 90%，预测错误罚 2 拍。
求每条指令平均多花几个周期。
```

```text
每条指令的分支概率 = 0.20
预测错误概率 = 0.10
平均罚拍 = 0.20 × 0.10 × 2 = 0.04 拍/条
```

CPI 从 1.00 变成 1.04。

如果换成立即停顿（不预测，每条分支停 2 拍）：

```text
0.20 × 2 = 0.40 拍/条
CPI = 1.40
```

一个预测器，值 0.36 个 CPI。

这也是为什么现代 CPU 愿意在预测器上砸几百万个晶体管。

分支预测还有一个副作用：精确异常变难。

```text
预测错误时，后面的指令已经执行了一部分，可能改了寄存器。
异常发生时，必须保证"异常指令之后的指令没有效果"。
```

所以流水线要能把"已经做了但还没提交"的结果撤销。

这就是第 18 篇说的"精确异常"在流水线里的实现代价。

### 5.1 走查：四行指令的完整时空图

回到开篇那四行：

```asm
I1  LOAD  R1, 0(R2)
I2  ADD   R3, R1, R4
I3  SUB   R5, R3, R6
I4  AND   R7, R5, R8
```

逐拍推：

```text
c1  I1 IF
c2  I1 ID，I2 IF
c3  I1 EX，I2 ID，I3 IF
c4  I1 MEM，I2 停（等 R1），I3 停在 IF，I4 取不进来
c5  I1 WB，I2 EX（从 MEM/WB 转发拿到 R1），I3 ID，I4 IF
c6  I2 MEM，I3 EX，I4 ID
c7  I2 WB，I3 MEM，I4 EX
c8  I3 WB，I4 MEM
c9  I4 WB
```

时空图：

```text
指令   1    2    3    4    5    6    7    8    9
I1    IF   ID   EX  MEM   WB
I2         IF   ID   ─    EX  MEM   WB
I3              IF   ─    ID   EX  MEM   WB
I4                       IF   ID   EX  MEM   WB
```

`─` 表示停在原地（stall）。

数出来：

```text
停顿 1 拍（第 4 拍）
总周期 = 4 + 5 − 1 + 1 = 9 拍
CPI = 9 ÷ 4 = 2.25
```

如果没有转发呢？

`I2` 要等 `I1` 写回（c5 末尾），`I2` 的 EX 得排到 c6，停 2 拍。

`I3` 等 `I2` 写回，又是 2 拍。

`I4` 同理，2 拍。

总停顿 6 拍，总周期 14 拍。

```text
有转发：9 拍
无转发：14 拍
差 5 拍，其中 1 拍是 load-use 消不掉的
```

这就是转发的价值。

## 6. 408 怎么考

四类题：

```text
① 判断某两条指令之间是什么冒险
② 问转发能不能解决，需要停几拍
③ 画时空图，数总周期数与 CPI
④ 算结构冒险或分支预测带来的额外周期
```

### 6.1 例题一：数冒险与停顿

题目（自拟）：

```text
5 段流水线，采用完全转发。
指令序列：
I1  ADD   R1, R2, R3
I2  LOAD  R4, 0(R1)
I3  SUB   R5, R4, R6
I4  AND   R7, R1, R8
I5  OR    R9, R5, R7
求：有几处数据冒险、共停顿几拍、总周期数。
```

逐对分析：

```text
I1 → I2：I2 用 R1 算地址。I1 的 EX 在 c3，I2 的 EX 在 c4，
         转发 EX/MEM → EX 够用。0 停。
I2 → I3：LOAD 后紧跟用其结果的指令，load-use。1 停。
I3 → I4：无依赖。
I4 → I5：I4 写 R7，I5 读 R7。EX/MEM → EX 转发够用。0 停。
I3 → I5：I3 写 R5，I5 读 R5。距离 2，MEM/WB → EX 转发。0 停。
```

结论：

```text
数据冒险 2 处（I1→I2 的 RAW、I2→I3 的 load-use），
其中需要停顿的只有 1 处（load-use），停 1 拍。
```

总周期：

```text
5 条 + 5 段 − 1 = 9
加 1 拍停顿 = 10 拍
CPI = 10 ÷ 5 = 2.0
```

逐拍验算：

```text
c1  I1 IF
c2  I1 ID，I2 IF
c3  I1 EX，I2 ID，I3 IF
c4  I1 MEM，I2 EX，I3 ID，I4 IF
c5  I1 WB，I2 MEM，I3 停，I4 停在 IF，I5 取不到
c6  I2 WB，I3 EX，I4 ID，I5 IF
c7  I3 MEM，I4 EX，I5 ID
c8  I3 WB，I4 MEM，I5 EX
c9  I4 WB，I5 MEM
c10 I5 WB
```

最后一条在 c10 写回，总周期 10 ✓。

### 6.2 例题二：转发能不能解决

题目（自拟）：下列四组相邻指令，判断转发能否消除停顿、各需停几拍。

```text
(a) ADD  R1, R2, R3    →  SUB  R4, R1, R5
(b) LOAD R1, 0(R2)     →  SUB  R4, R1, R5
(c) ADD  R1, R2, R3    →  STORE 0(R4), R1
(d) LOAD R1, 0(R2)     →  BEQ  R1, R3, L
```

答案：

```text
(a) 能，0 停。EX/MEM → EX
(b) 不能，1 停。load-use，数据在 MEM 末尾才有
(c) 能，0 停。ADD 结果在 c3 末尾有，STORE 的 MEM 在 c5，
    用 MEM/WB → MEM 转发写数据
(d) 不能，1 停。BEQ 在 EX 段比较 R1，等不到 LOAD 的 MEM 结果
```

规律：

```text
消费者在 EX 段用数据 → ALU 结果能转发，load 结果要等 1 拍
消费者在 MEM 段用数据 → load 结果也能转发，0 停
```

(c) 是很多人会答错的一问。

`STORE` 的数据是在 MEM 段才写出去的。

`ADD` 的结果在 EX 末尾就有了，中间隔了 ID、EX 两拍。

时间上完全来得及。

再补一个常考的：

```text
(e) LOAD R1, 0(R2)  →  STORE 0(R3), R1
```

答案：0 停。

`STORE` 要用的 R1 在 MEM 段，而 `LOAD` 的数据在 MEM 末尾进 MEM/WB。

MEM/WB → MEM 恰好接得上。

### 6.3 例题三：结构冒险的周期数

题目（自拟）：

```text
5 段流水线，指令与数据共用一个存储器（单端口）。
程序 200 条指令，其中 load/store 占 25%，分支占 10%。
分支采用"预测不跳 + 错误罚 2 拍"，预测准确率 80%。
其他冒险不计。
求总周期数与 CPI。
```

分三块算：

```text
基准：200 + 5 − 1 = 204 拍
结构冒险：200 × 25% = 50 条 load/store，各停 1 拍 → +50 拍
控制冒险：200 × 10% = 20 条分支，错误率 20%，
          20 × 0.2 = 4 次预测错误，每次罚 2 拍 → +8 拍
```

合计：

```text
204 + 50 + 8 = 262 拍
CPI = 262 ÷ 200 = 1.31
```

如果把指令 Cache 与数据 Cache 分开：

```text
204 + 8 = 212 拍
CPI = 1.06
```

对照两块的占比：

```text
结构冒险：50 拍，占额外开销的 86%
控制冒险：8 拍，占 14%
```

结论：

```text
先加 Cache，再谈预测器。
结构冒险是"花钱就能消掉"的，控制冒险是"猜得准才能消掉"的。
```

### 6.4 例题四：load-use 的传染性

题目（自拟）：

```text
5 段流水线，完全转发。
I1  LOAD  R1, 0(R2)
I2  ADD   R3, R1, R4
I3  LOAD  R1, 0(R5)
I4  SUB   R6, R1, R7
求总周期数。
```

两处 load-use，直觉答案是停 2 拍、总周期 8 + 2 = 10。

先用逐拍法验一遍：

```text
c1  I1 IF
c2  I1 ID，I2 IF
c3  I1 EX，I2 ID，I3 IF
c4  I1 MEM，I2 停，I3 停在 IF
c5  I1 WB，I2 EX，I3 ID，I4 IF
c6  I2 MEM，I3 EX，I4 ID
c7  I2 WB，I3 MEM，I4 停（等 I3 的 load 数据）
c8  I3 WB，I4 EX
c9  I4 MEM
c10 I4 WB
```

总周期 10，停顿 2 拍。

答案对上了。

但停的位置和直觉不一样：

```text
第一次在 c4，I2 等 I1。
第二次在 c7，I4 等 I3。
```

为什么第二次不是 c6？

因为 `I4` 被前一次停顿推后了一拍。

`I2` 在 c4 停，`I3` 也卡在 IF，`I4` 只能到 c5 才取进来。

所以 `I4` 的 EX 本来就排在 c7，正好撞上 `I3` 的 MEM 末尾。

这题的教训：

```text
load-use 的停顿会"传染"给后面的指令。
数停顿不要只在相邻两条之间数，要按绝对时刻排。
```

如果 `I4` 和 `I3` 之间再隔一条无关指令：

```text
I1  LOAD  R1, 0(R2)
I2  ADD   R3, R1, R4
I3  LOAD  R1, 0(R5)
I4  AND   R8, R9, R10   ← 无关指令
I5  SUB   R6, R1, R7
```

`I5` 的 EX 在 c8，`I3` 的 MEM 在 c7，转发接得上。

总停顿还是只有第一次的那 1 拍。

一条无关指令，省掉一次停顿。

这就是编译器指令调度（instruction scheduling）的最小例子。

## 7. 真实芯片里长什么样

**分支预测器。**

现代 CPU 在这一块花的晶体管，比 ALU 还多。

一个典型结构：

```text
BTB（branch target buffer）：记录"这个地址上次跳到哪"
BHT（branch history table）：记录"这个分支上次跳没跳"
2 位饱和计数器：连续两次猜错才翻转预测方向，抗噪
```

2 位计数器的状态机（简化示意）：

```text
        猜错              猜错
  强不跳 ────► 弱不跳 ────► 弱跳 ────► 强跳
    ▲            │            ▲           │
    └────────────┘            └───────────┘
        猜对                     猜对
```

再往上还有两级自适应、TAGE 之类的预测器。

```text
用多条不同长度的历史，分别预测，再挑一个最可信的。
```

准确率能做到 95% 以上。

预测错了，就要冲刷前端。

这就是前端停顿（frontend stall）的主要来源之一。

**流水线深度的历史。**

Pentium 4 为了冲高主频，把流水线拉到二十级以上。

结果分支预测错误的罚拍变得非常大，猜错一次的代价抵得上十几拍。

Core 架构把深度降回十几级，靠更宽的发射和更好的预测器提升 IPC。

这段历史说明一件事：

```text
段数 k 与罚拍是绑在一起的。
拉长流水线换频率，代价是每次猜错的罚更贵。
```

（简化示意：具体级数各家口径不同，这里只取公开资料里常见的量级。）

**`perf stat` 里的冒险证据。**

Linux 上跑：

```bash
perf stat -e cycles,instructions,branches,branch-misses \
          -e stalled-cycles-frontend,stalled-cycles-backend ./a.out
```

输出大致长这样（简化示意）：

```text
    1,234,567,890      cycles
      987,654,321      instructions              # 0.80  insn per cycle
       45,678,901      branches
        1,234,567      branch-misses             # 2.70% of all branches
      123,456,789      stalled-cycles-frontend   # 10.00% frontend cycles idle
      234,567,890      stalled-cycles-backend    # 19.00% backend cycles idle
```

三个数字对应三种冒险：

```text
stalled-cycles-frontend   前端空转：取指供不上（控制冒险、I-Cache 缺失）
stalled-cycles-backend    后端空转：等数据（数据冒险、D-Cache 缺失）
branch-misses             分支预测错误次数
```

`insn per cycle` 就是 IPC。

```text
理想值 = 流水线宽度（4 发射就是 4）
实际值远小于它，差额就是冒险与缺失吃掉的
```

这些数不是理论，是硬件性能计数器（performance counter）数出来的。

（简化示意：`perf` 的事件定义因微架构而异，frontend/backend 的划分不是硬标准。）

## 8. 反直觉：转发消不掉 load-use

回到那句话：

```text
转发能消掉大部分数据冒险，但消不掉 load-use。
```

为什么？

看时间：

```text
        c3     c4     c5
I1 LOAD EX    MEM     WB
I2 ADD        EX ←── 需要 R1
```

`LOAD` 的数据什么时候有？

```text
EX 段：算出地址
MEM 段：从存储器读出数据，放进 MEM/WB 寄存器
```

数据在 c4 的**末尾**才进 MEM/WB 寄存器。

而 `ADD` 的 EX 段在 c4 的**开头**就要用。

差半个周期。

硬件没法"半个周期后用"，只能停一拍，让 `ADD` 的 EX 挪到 c5。

这时数据已经在 MEM/WB 里，转发通路能用。

对比 `ADD` 后跟 `SUB`：

```text
        c3     c4
I1 ADD  EX    MEM
I2 SUB        EX ←── 从 EX/MEM 转发
```

`ADD` 的结果在 c3 末尾进了 EX/MEM 寄存器。

`SUB` 在 c4 开头就要用。

正好赶得上。

**差别只有一处：结果产生在哪一段的末尾。**

```text
ALU 结果：EX 末尾 → 下一条的 EX 开头正好用
LOAD 结果：MEM 末尾 → 下一条的 EX 开头差一拍
```

所以 load-use 至少停 1 拍。

这一拍能不能彻底消掉？

能，但要改硬件或改代码：

```text
① 改代码：编译器把无关指令填到 LOAD 后面（指令调度）
② 改硬件：load 前递、访存流水化，让数据早半拍出来
③ 改结构：LOAD 的 MEM 段拆两拍，数据在第二拍开头就到
```

这三种都不是"转发"。

转发只能搬数据，不能搬时间。

换个说法更清楚：

```text
转发改变的是数据的搬运路径，不改变指令的先后次序。
只要次序不变，LOAD 后面那条就必须等到下一拍才能进 EX。
```

要让次序变，就得乱序执行（out-of-order execution）。

那是另一个层次的复杂度，408 不考，但它是现代高性能 CPU 的标配。

所以这一篇最值钱的一句话是：

```text
转发解决的是"数据在哪"，不是"数据什么时候有"。
```

## 9. 容易混淆的点

**第一，数据相关不等于数据冒险。**

```text
相关（dependence）：两条指令用了同一个寄存器，客观存在
冒险（hazard）：在这个具体流水线里，相关导致了停顿
```

有相关性，但有转发，就不一定有冒险。

**第二，RAW 才是真依赖。**

```text
RAW：真数据依赖，改名也消不掉，只能转发或停
WAR / WAW：名字冲突，换寄存器就能消
```

五段顺序流水线里只考 RAW。

**第三，转发不停顿，停顿不转发。**

```text
转发：不改时序，只是把数据从旁路送过去
停顿：改时序，插一个气泡，后面的指令全部顺延
```

**第四，气泡和冲刷不是一回事。**

```text
气泡（bubble）：停顿产生，让流水线空转一拍，指令还在
冲刷（flush）：预测错误或异常产生，把已经取的指令作废
```

气泡是"等"，冲刷是"扔"。

**第五，停顿拍数不等于总周期数。**

```text
总周期 = n + k − 1 + 停顿拍数
```

只算 n + k − 1 是最常见的丢分点。

**第六，load-use 停 1 拍，不是 2 拍。**

```text
停 1 拍后，LOAD 的数据在 MEM/WB 寄存器里，转发可用。
停 2 拍是"完全没有转发"时的答案。
```

**第七，结构冒险不一定是"两条指令抢同一个大部件"。**

```text
寄存器堆只有一个写端口，两条指令同拍写回 → 也是结构冒险
```

**第八，分支预测错误罚不是固定值。**

```text
罚拍 = 分支定论那一段 与 IF 之间隔的段数
5 段机、EX 定论 → 罚 2
5 段机、ID 定论 → 罚 1
```

题目给了微架构，要自己推，不能背"罚 1 拍"。

**第九，转发路径有多条，优先级不同。**

```text
EX/MEM 与 MEM/WB 同时命中同一个寄存器 → 用 EX/MEM
```

因为 EX/MEM 来自更近的那条指令。

**第十，流水线越深不一定越快。**

```text
深流水线：主频高，但填充/排空更久，预测错误罚更贵
浅流水线：主频低，但冒险代价小，IPC 容易做高
```

两者的乘积才是性能。

**第十一，"完全转发"是题设，不是现实。**

```text
真实芯片的转发通路受布线延迟、时钟频率限制，
有些结果要跨芯片模块送，转发反而更慢。
```

所以做 408 题时按题设算，别拿现实抬杠。

**第十二，停顿不等于程序变慢的那个"停顿"。**

```text
流水线停顿（stall）是硬件术语，指某一拍没有新指令进入下一段。
程序里的"卡住"可能来自缺页、I/O、调度，跟流水线停顿不是一回事。
```

## 10. 停顿在电路里怎么实现

前面都在说"停一拍"。

硬件上，停一拍是什么意思？

流水线里有一组控制信号，做三件事：

```text
① 冻结 PC 和 IF/ID 寄存器：不让新的指令进来
② 冻结 ID/EX 寄存器：不让当前指令往前走
③ 往 EX 段灌一个"空操作"：控制信号全 0，什么也不写
```

这个"空操作"就是气泡。

它占了流水线的一拍，但什么也不做。

停顿时空图长这样：

```text
       c3    c4    c5    c6
I1     EX   MEM    WB
I2          ─     ID    EX     ← c4 是气泡
I3                ─     ID     ← 被挡住一拍
```

`I2` 在 c4 没有前进，`I3` 在 c5 也补不上来。

这个空隙会随着后面的指令一路往后传。

所以叫它"气泡"：占着位置，不干活。

气泡的控制字有个专门的名字：把寄存器写使能、存储器写使能全部清 0。

```text
气泡不会写寄存器，不会写存储器，不会改标志。
所以它对程序状态没有任何影响，只是浪费一拍。
```

冲刷（flush）不同。

```text
冲刷是把已经取进来、已经译码的指令的"有效位"清掉。
它连气泡都不是，是"这条指令不存在"。
```

两者在时空图上都表现为空隙。

但一个来自冒险，一个来自预测错误。

这也解释了为什么预测错误比停顿更贵：

```text
停顿：只浪费等待的那几拍，指令还在流水线里
冲刷：把已经做的工作全部丢掉，还要重新取指
```

## 11. 编译器怎么帮忙

冒险是硬件的事，但软件也能分担。

三招：

```text
① 指令调度：把无关指令塞进 load 的停顿槽
② 循环展开：减少分支次数，增加调度空间
③ 寄存器重命名：用新寄存器消除 WAR/WAW
```

指令调度的例子。

原始循环（简化示意）：

```asm
L:  LOAD  F1, 0(R1)      ; a[i]
    LOAD  F2, 0(R2)      ; b[i]
    MUL   F3, F2, F4     ; b[i] * c
    ADD   F1, F1, F3
    STORE 0(R1), F1
    ADDI  R1, R1, 4
    ADDI  R2, R2, 4
    BLT   R1, R3, L
```

第一条 `LOAD` 后面紧跟 `LOAD`，第二条后面紧跟 `MUL`。

两处 load-use，各停 1 拍。

调度之后（简化示意）：

```asm
L:  LOAD  F1, 0(R1)      ; a[i]
    LOAD  F2, 0(R2)      ; b[i]
    LOAD  F5, 4(R1)      ; 提前取下一条的 a[i+1]
    MUL   F3, F2, F4     ; 此时 F1 已经就绪
    ADD   F1, F1, F3
    STORE 0(R1), F1
```

把后面的 `LOAD` 提前，填掉前面的等待。

理想情况下，停顿从两次变成零次。

代价有三条：

```text
需要更多寄存器（F5 就是多出来的那份）
编译器要看得足够远
不能改变程序语义（尤其不能改变异常发生的顺序）
```

所以"完全转发 + 零停顿"这种题设，现实里要靠软硬件一起努力。

这也是现代编译器会做软件流水（software pipelining）的原因。

循环展开的收益可以算。

```text
原循环：每轮 1 次分支，每次预测错误罚 2 拍
展开 4 次：每 4 轮 1 次分支，分支开销降到 1/4
```

代价是代码变长，指令 Cache 压力变大。

```text
展开太多，I-Cache 装不下，反而变慢。
```

所以展开因子一般取 2 到 8。

## 12. 小结

一条指令五段：

```text
IF → ID → EX → MEM → WB
n 条指令、k 段，理想总时间 = k + n − 1
```

三种冒险，三套对策：

```text
结构冒险：分离 Cache、加端口、停顿
数据冒险：转发；load-use 停 1 拍
控制冒险：预测、延迟槽、冲刷；最差是停
```

三个必背的数字：

```text
load-use 至少停 1 拍
5 段机、EX 定论的分支，预测错误罚 2 拍
无转发时，相邻 RAW 停 2 拍
```

一个必会的方法：

```text
画时空图。
横轴是拍，纵轴是指令，`─` 表示停。
数最后一条的 WB 落在第几拍，就是总周期。
```

最后是那句反直觉的话：

```text
转发解决"数据在哪"，不解决"数据什么时候有"。
LOAD 的数据在 MEM 末尾才出来，下一条的 EX 在开头就要，差半拍，只能停。
```

下一篇算账。

流水线到底能快多少？
