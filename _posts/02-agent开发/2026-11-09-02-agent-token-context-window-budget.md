01 篇讲完了消息的形状。

现在换一个更物理的问题。

代码来源：

```text
labs/L01_agent_loop/run.py
```

```python
print(f">> 历史里现在有 {len(messages)} 条消息：", [m.role for m in messages])
```

场景 1 跑完，历史是 7 条。

场景 2 跑完，大概 8 条。

场景 3 跑 3 步，也接近 10 条。

这还只是一次简单任务。

如果一次任务跑 30 步呢？

```text
30 步 × 2 条 = 60 条消息，外加开头的 system 和 user。
```

再乘上每条消息的长度。

这个数字，大概率会超过模型的上下文窗口。

于是你会遇到一个非常具体的报错：

```text
This model's maximum context length is 128000 tokens.
However, your messages resulted in 130412 tokens.
```

或者更隐蔽的一种：

```text
不报错，但模型开始漏掉开头的指令。
```

这一篇只做一件事：

```text
把「一次请求有多长」变成一个你能算的数字。
```

## 1. token 是什么

模型不读字。

它读 token。

```text
token 是模型处理文本的最小单位。
```

它不是字符，也不是单词。

它是分词器（tokenizer）切出来的碎片。

同样是「苹果」：

```text
对人是 2 个汉字
对分词器可能是 1 个 token，也可能是 2 个
```

同样是 `calculator`：

```text
对人是 10 个字母
对分词器可能是 1 个 token，也可能是 3 个
```

所以下面这个等式是错的：

```text
token 数 = 字符数 ÷ 2
```

它只是**一个粗糙的估算**，在很多场景下勉强够用。

真正准确的办法只有一个：

```text
用你要用的那个模型的分词器数。
```

但工程上，你不可能每次请求前都精确数一遍。

所以你需要一个估算公式，加上一个安全余量。

## 2. 中英文的差别有多大

经验值（不同模型差异很大，只用于估算）：

```text
英文：约 4 个字符 = 1 个 token
中文：约 1~2 个汉字 = 1 个 token
代码：比自然语言更费，约 2~3 个字符 = 1 个 token
JSON：括号、引号、字段名都算，通常比自然语言更费
```

举一个具体的例子。

```text
你是一个会使用工具的中文助手。需要算数时调用 calculator 工具。
```

31 个汉字，加一个英文单词。

估算大概 35~45 个 token。

再看一段 JSON：

```json
{"role": "assistant", "content": null, "tool_calls": [{"id": "call_a1b2c3", "type": "function", "function": {"name": "calculator", "arguments": "{\"expression\": \"12 + 8\"}"}}]}
```

不到 200 个字符。

但 token 数很可能超过 100。

因为：

```text
字段名要算
标点要算
转义的反斜杠要算
嵌套的引号要算
```

**这就是为什么工具 schema 比你想的贵。**

一个工具只有一个 `expression` 参数。

但它的完整 schema 可能是这样的：

代码来源：OpenAI tools 参数的形状

```json
{
  "type": "function",
  "function": {
    "name": "calculator",
    "description": "计算一个四则运算表达式，返回结果字符串。",
    "parameters": {
      "type": "object",
      "properties": {
        "expression": {
          "type": "string",
          "description": "要计算的表达式，例如 \"(12+8)*3\""
        }
      },
      "required": ["expression"]
    }
  }
}
```

这差不多 400 个字符。

估算 120~180 个 token。

一个工具就这么多。

十个工具呢？

```text
1200~1800 个 token，每次请求都要发。
```

而且不管这次用不用得上。

## 3. 上下文窗口是什么的上限

上下文窗口（context window）这个词，很容易被理解成「记忆容量」。

不对。

它的准确含义是：

```text
一次请求里，模型能接收的 token 总数上限。
```

注意三个关键词。

```text
一次       不是累计，是单次
请求       不是会话
接收       指的是输入
```

这就带来一个反直觉的结论：

```text
上下文窗口不是「模型能记住多少」，
是「你一次能递给它多少」。
```

你递得再多，它也不会自动记住。

下次请求，你还得再递一遍。

## 4. 输入和输出抢的是同一个池子

这是最容易踩的坑。

很多人以为：

```text
上下文窗口 = 输入上限
输出上限 = 另算
```

不一定。

在大多数 API 里，输入 + 输出 ≤ 上下文窗口。

```text
input_tokens + output_tokens ≤ context_window
```

有些供应商会把输出上限单独限制成一个更小的值（比如 `max_tokens`）。

但**总的池子是共用的**。

所以如果你塞了 127k 输入，而窗口是 128k：

```text
你只剩 1k 给输出。
```

模型很可能说到一半被截断。

返回的 `finish_reason` 会是 `length` 而不是 `stop`。

代码来源：OpenAI 的 finish_reason 取值

```json
{"finish_reason": "length"}
```

看到 `length`，不要以为模型不想说了。

是它没地方说了。

**工程上的规矩：**

```text
先给输出留够空间，再决定能塞多少历史。
```

不是反过来。

## 5. 一次请求的预算被谁花掉

把一次请求拆开，预算被五个部分花掉。

```text
① system prompt
② 工具 schema
③ 历史消息
④ 本轮用户输入
⑤ 预留给输出
```

画成图：

```text
┌──────────────────────────────────────────────┐
│              上下文窗口（例如 128k）           │
├──────────┬─────────┬──────────┬──────┬───────┤
│  system  │  tools  │ history  │ user │output │
│   ~500   │  ~1200  │   ?      │ ~50  │ ~2000 │
└──────────┴─────────┴──────────┴──────┴───────┘
```

你会发现，真正「不固定」的只有 history。

另外四项，你都可以在设计阶段就控制住。

```text
system     写多长是你决定的
tools      加几个工具是你决定的
user       用户输入，你可以截断
output     你要留多少，是你决定的
```

所以预算管理的核心，只有一个：

```text
history 怎么控。
```

这就是 06 篇「上下文工程」要解决的问题。

现在先把账算清楚。

## 6. 一个能算的例子

拿 L01 场景 1 举例。

第 1 次请求：

```text
system       31 个汉字        ≈ 40 token
tools        1 个工具的 schema ≈ 150 token
user         28 个汉字        ≈ 30 token
output 预留                   2000 token
────────────────────────────────────────
合计                           ≈ 2220 token
```

很轻松。

第 2 次请求，历史多了 2 条：

```text
system                       ≈ 40
tools                        ≈ 150
history:
  user 原始请求               ≈ 30
  assistant(tool_calls JSON)  ≈ 60
  tool 结果 "20"              ≈ 10
user（无）                     0
output 预留                   2000
────────────────────────────────────────
合计                           ≈ 2290
```

第 3 次请求，再涨一点。

三次请求，加起来不到 7k。

看起来毫无压力。

**但这是任务只有 3 步的情况。**

把步数换成 50 步：

```text
50 步 × (assistant 60 + tool 10) = 3500 token
```

还是不大。

因为工具返回的结果很短。

换成真实场景：

```text
工具返回的是一段 2000 字的文档片段。
```

每步多 3000 token。

50 步：

```text
150,000 token
```

直接超过 128k。

这就是为什么：

```text
真实 agent 的上下文问题，
几乎全部来自「工具返回了太多东西」。
```

不是来自用户说了太多话。

**这是本系列第二个可以拿去面试的细节。**

### 6.1 同一个任务，两种工具，两本账

把工具的输出换一下，账就变了。

```text
T1  calculator("12 + 8") → "20"                 5 token
T2  search("2024 年的营收") → 2000 字文档片段   3000 token
```

同样是 10 步任务，同样每步 +2 条消息：

```text
               每步增量      10 步总计
T1 算数工具     ~70            ~1100
T2 文档工具     ~3100          ~30000
```

差 27 倍。

而任务本身没有变复杂。

所以你会看到一个很反直觉的排障现象：

```text
"这个 agent 只是多接了一个搜索工具，怎么就爆了？"
```

因为它不是"多接了一个工具"。

它是"每步多搬了 3000 token 进历史"。

顺便说一句，这就是为什么 06 篇要讲裁剪。

不是因为对话太长。

是因为**观测太长**。

## 7. 历史为什么会线性增长

01 篇已经说过增长规律：每步 +2 条。

```text
+ assistant（模型的话）
+ tool（工具结果）
```

画出来：

```text
步数   消息数   token（估算）
 1      4       800
 2      6       1100
 3      8       1400
 5      12      2000
10      22      3500
20      42      6500
50      102     15500
```

如果工具返回内容大，把每步的增量从 300 改成 3000：

```text
10 步  → 30000
20 步  → 60000
50 步  → 150000   ← 爆了
```

所以你会看到一个很具体的现象：

```text
小工具 agent 跑 100 步都没事。
读文档 / 查数据库的 agent，跑 15 步就爆。
```

原因不在循环。

在观测的体积。

代码来源：

```text
labs/L01_agent_loop/README.md
```

```markdown
### ④ `max_steps` 是保险丝

模型可能无限循环（"再查一次""再查一次"）。没有保险丝，这个 while 会跑到你
API 余额见底。**所有生产级 agent 都必须有步数 / 时间 / 金额三道刹车。**
```

这段说的是步数、时间、金额三道刹车。

但它们背后其实是同一个变量：

```text
这一次任务，最多允许花多少 token。
```

步数 × 每步 token = 任务总 token。

所以「加一道步数刹车」，在预算视角下就是：

```text
给历史长度设一个上限。
```

而「加一道金额刹车」，是给这个上限乘上单价。

三件事，一个账本。

## 8. 超限的两种表现

超过上下文窗口，不一定报错。

有两种表现。

### 8.1 硬报错

```text
API 返回 400，错误信息里带 "maximum context length"。
```

这是好事。

至少你知道发生了什么。

### 8.2 静默截断

有些客户端、网关或框架，会在你不知情的情况下：

```text
截掉最老的消息
截掉最长的工具结果
把超长内容做一个摘要
```

然后请求成功了。

但模型看到的历史，已经不是你以为的那份。

于是出现这类灵异现象：

```text
"它怎么忘了任务是删重复文件？"
"它怎么不记得我说过不要用 sudo？"
```

不是模型忘了。

是那两条消息在发出去之前，就被截掉了。

**工程上的规矩：**

```text
如果一定要截断，必须由你的代码显式做，并且记录下来。
```

不要交给你不了解的黑盒。

因为：

```text
静默截断 = 你失去了对「模型看到了什么」的掌控。
```

而 agent 调试，本质上就是在对齐「你以为它看到了什么」和「它实际看到了什么」。

## 9. 裁剪的三个策略

先给结论：

```text
裁剪不是「丢掉最老的」，是「保住协议完整的部分」。
```

### 9.1 策略一：只留最近 N 条

最简单。

```python
messages = messages[:1] + messages[-20:]
```

保留 system，加上最近 20 条。

问题：

```text
可能会把 assistant(tool_calls) 和它的 tool 结果拆开。
```

拆开就 400。

必须在裁剪后做一次修复：

```text
如果第一条不是 assistant 的 tool 结果配对起点，
就继续往前找，直到找到边界。
```

### 9.2 策略二：保留首尾

```text
system + 前几条（任务目标） + 最近 N 条
```

好处：

```text
开头的任务目标不会丢。
```

坏处：

```text
中间的结论会丢。
```

如果第 5 步得出过一个关键结论（比如"这个目录下没有 .tmp 文件"），裁剪后模型可能又去查一遍。

### 9.3 策略三：摘要 + 最近 N 条

```text
把中间那段压成一条摘要消息。
```

摘要里放什么：

```text
已经确认的事实
已经排除的假设
还没完成的步骤
关键的工具输出（数值、路径、ID）
```

不放什么：

```text
寒暄
重复的失败尝试
大段原文
```

这是最常用的方案。

但摘要本身也是一次模型调用。

意味着：

```text
成本和延迟都要算进去。
```

而且摘要可能丢细节。

所以摘要里的关键事实，最好是**从工具结果里抄过来的原文**，不是模型转述的。

## 10. 多给上下文为什么反而更差

这是这一篇最重要的一个反直觉点。

直觉是：

```text
信息越多，模型判断越准。
```

实际经常相反。

四个机制。

### 10.1 噪声

上下文里塞了 50 段文档。

其中 3 段相关。

模型要在 50 段里找那 3 段。

找错的概率，比只给 3 段高。

### 10.2 冲突

第 3 段说「用 A 方案」。

第 41 段说「不要用 A 方案」。

两段都是你给的事实。

模型必须选一个。

它选哪个，你不知道。

### 10.3 注意力稀释

模型的注意力不是均匀分配的。

给 100k token，不代表每个 token 都被同等对待。

### 10.4 中间丢失

有个被反复观察到的现象，通常叫「lost in the middle」：

```text
开头和结尾的信息，模型用得最好。
中间的信息，最容易漏。
```

所以关键的指令，要放在**开头（system）**或**结尾（最后一条 user）**。

不要放在中间。

画成图：

```text
注意力
 高 │█                        █
    │██                      ██
    │ ██                    ██
 低 │   ████████████████████
    └──────────────────────────
      开头      中间       结尾
```

**结论：**

```text
上下文不是越多越好。
是越「相关 + 越少 + 关键信息越靠边」越好。
```

## 11. temperature 不是记忆开关

顺便澄清一个常见误解。

`temperature` 控制的是采样。

```text
temperature 低   → 输出更确定，更接近高概率词
temperature 高   → 输出更随机，更有"创意"
```

它和记忆、上下文、token 都没关系。

而且：

```text
temperature = 0 也不保证每次输出一样。
```

因为底层还有硬件、批处理、数值精度等带来的不确定性。

所以「可复现」这件事，不能靠 temperature。

只能靠：

```text
把完整的 messages 存下来，重放。
```

14 篇讲可观测性时会展开。

现在记住一句话：

```text
temperature 管的是「这次说得像不像上次」，
不是「这次记不记得上次」。
```

## 12. 五个可以立刻用的规矩

把这一篇压成五条。

第一条：

```text
先给输出留空间。
```

`max_tokens` 或等价参数，一开始就设，别等爆了再调。

第二条：

```text
system 越短越好。
```

system 里只放规则，不放例子，不放长文档。

例子和文档，该按需检索。

第三条：

```text
工具 schema 是要花钱的。
```

每加一个工具，每次请求都多一笔固定开销。

不用的工具，不要注册。

**顺便说一句输出这一侧。**

模型生成是逐 token 的。

```text
输入：一次性算完（prefill）
输出：一个 token 一个 token 生成（decode）
```

所以两件事同时成立：

```text
输出越长，越慢。
输出越长，越贵。
```

这也解释了一个常见现象：

```text
同一个 agent，让它"详细解释每一步"，
响应时间可能翻倍，成本也可能翻倍。
```

所以「输出格式」不是体验问题，是性能问题。

工程上的做法：

```text
system 里明确要求简洁
需要结构化时，让它只吐 JSON，不吐解释
需要解释时，单独一次请求
```

第四条：

```text
工具返回要有上限。
```

`calculator` 返回 2 个字符，没事。

查数据库返回 5000 行，必须截断。

截断时要告诉模型：

```text
（结果过长，只显示前 20 行，共 312 行）
```

第五条：

```text
每次请求前，估一下 token。
```

不用精确。

用一个粗估公式 + 20% 余量，就够你在设计阶段发现"这个方案根本跑不起来"。

### 12.1 估完之后，拿真实数字校准

估算只是第一步。

真模型每次响应都会带用量。

代码来源：OpenAI Chat Completions 的 usage 形状

```json
{
  "usage": {
    "prompt_tokens": 412,
    "completion_tokens": 18,
    "total_tokens": 430
  }
}
```

这个数字比你估的准。

但它只在**请求成功之后**才有。

所以正确的做法是两条线一起用：

```text
请求前：用粗估做闸门（超了就裁剪、就报错）
请求后：用 usage 记账、校准系数
```

校准的方法是比：

```text
实际 prompt_tokens / 你的估值 = 校准系数
```

跑几十次，你会得到一个稳定的系数。

比如你估 400，实际 520，系数就是 1.3。

以后估值乘 1.3，再留 20% 余量。

### 12.2 重试会把账翻倍

一个很容易忽略的点。

```text
一次请求失败重试 3 次 = 3 倍的输入 token。
```

如果第 1 次其实成功了、只是超时没收到响应，你还要再多付一次。

所以 15 篇讲重试时会强调：

```text
只重试可重试的错误（超时、429、5xx）。
不要重试参数错误（400）。
```

参数错误重试一百次，也是错一百次。

钱照付。

### 12.3 成本 ≈ 输入 token × 输入单价 + 输出 token × 输出单价

公式就这么长。

但有两个工程含义。

第一个：**输出通常比输入贵。**

所以"让它少说点废话"不只是体验问题，也是成本问题。

第二个：**输入里最贵的是历史。**

因为历史每一轮都重发。

一个 30 步的任务，第 1 步产出的那条 tool 结果，会被重发 29 次。

这就是为什么"裁剪"不是优化项，是必需项。

### 12.4 先给预算分个配比

不要求精确，但要有配比。

一个能用的默认值：

```text
输出预留       ≥ 2000 token      （先扣，剩下才是输入额度）
system         ≤ 500             （超过就该拆成知识库）
tools schema   ≤ 输入的 20%      （工具越多，这格越危险）
history        ≤ 剩下的全部       （真正浮动的部分）
单条观测       ≤ 2000             （超了就截断并告知模型）
```

换成代码：

```python
def budget_plan(window: int, max_output: int = 2000) -> dict:
    """算出这一次请求，各部分大概能用多少。"""
    input_budget = window - max_output
    if input_budget <= 0:
        raise ValueError("输出预留比窗口还大，这个配置不可能成功")
    system = min(500, input_budget // 10)
    tools = int(input_budget * 0.2)
    return {
        "input": input_budget,
        "system": system,
        "tools": tools,
        "history": input_budget - system - tools,
        "max_output": max_output,
    }
```

按 128k 窗口算一次：

```text
input 126000 / system 500 / tools 25200 / history 100300 / output 2000
```

这套配比不是标准答案。

但它能提前告诉你两件事：

```text
1. 工具加到 10 个时，tools 那 20% 会吃掉多少。
2. 历史一旦超过 history 那格，就必须裁。
```

先有格子，再谈优化。

没有格子，你只会等到报错那天才开始想这件事。

## 13. 一个粗估函数

给出最小实现。

```python
def rough_tokens(text: str) -> int:
    """极粗的 token 估算：中文按 1 字 1 token，其他按 4 字符 1 token。

    只用于设计阶段的量级判断，不要用于计费。
    精确值请用模型供应商的 tokenizer 或响应里的 usage 字段。
    """
    cjk = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    other = len(text) - cjk
    return cjk + other // 4


def estimate_request(messages, tools_schema: str, max_output: int) -> int:
    """估算一次请求会占用多少上下文。"""
    history = sum(rough_tokens(m.content) for m in messages)
    tool_calls = sum(
        rough_tokens(c.name) + rough_tokens(str(c.args))
        for m in messages for c in m.tool_calls
    )
    return history + tool_calls + rough_tokens(tools_schema) + max_output
```

这个函数不准。

但它能回答一个关键问题：

```text
我这个方案，是 2k 的量级，还是 200k 的量级？
```

如果你估出来是 200k，不要急着优化 prompt。

先问：

```text
是不是每次都在重发一份巨大的文档？
```

大概率是。

## 14. 读代码时怎么判断

看到一段 agent 代码，问五个问题。

```text
1. 有没有给输出预留空间？
2. 工具 schema 是每次都全发，还是按需发？
3. 历史什么时候裁剪？裁剪时有没有保住 tool 调用对？
4. 工具返回有没有长度上限？
5. 请求发出去之前，有没有记录这次大概多少 token？
```

五个都是「有」，这段代码在真实场景里才站得住。

第 3 个最容易出错。

第 5 个最容易被跳过。

而第 5 个恰恰是排障最快的：

```text
有 token 记录，你才能解释"为什么第 17 轮开始胡说"。
没有记录，你只能猜。
```

## 15. 小结

这一篇讲的是 agent 的物理约束：

```text
token
上下文窗口
单轮预算
```

核心结论：

```text
上下文窗口不是记忆，是单次请求的预算。
预算由五样东西分：system、tools、history、input、output。
真正不可控的只有 history。
```

三个要记住的数字感：

```text
一个工具 schema ≈ 100~200 token，每次请求都发
一次工具调用 ≈ 100 token 来回
一段 2000 字文档 ≈ 1500~3000 token
```

一个反直觉的点：

```text
上下文不是越多越好。
多给上下文，可能让模型更差。
```
