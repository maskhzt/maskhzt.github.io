这篇是一个新的开始。

前面那套 C++ 系统补课，解决的问题是：

```text
读懂别人写的 C++ 源码。
```

这一套要解决的问题不一样：

```text
从零写一个能用的 agent，并且知道它为什么能用。
```

两者看起来隔着很远。

但它们踩的是同一个坑。

最近后台收到的 agent 问题，大概长这样：

```text
循环写出来了，但模型不调用工具。
调用了，参数是错的。
参数对了，工具报错把程序炸了。
不炸了，但聊到第 20 轮开始胡说。
不胡说了，但我不知道改完之后它到底变好还是变坏。
```

这五句话，分别对应五个不同的层。

如果你不知道自己在第几层，就会用同一招去解所有问题。

- 模型不调工具 → 你去改 prompt
- 参数错 → 你还去改 prompt
- 工具炸了 → 你还去改 prompt

改到最后 prompt 变成两千字，问题还在。

## 1. Agent 的知识为什么显得不系统

C++ 那篇讲过「知识点叠在一起」的问题。

Agent 有完全一样的病，而且更严重。

因为 Agent 的知识不是一层，是六层挤在一行里。

看一段真实代码。

代码来源：

```text
labs/L01_agent_loop/agent.py
```

```python
def run_agent(model, tools, messages, max_steps=10, verbose=True):
    for step in range(1, max_steps + 1):
        reply = model.chat(messages)
        messages.append(reply)

        if not reply.tool_calls:
            return reply.content

        for call in reply.tool_calls:
            observation = _execute(call, tools)
            messages.append(
                Message(role="tool", content=observation, tool_call_id=call.id)
            )
```

只有 12 行。

但里面同时有：

```text
函数签名和默认参数
for 循环与步数上限
模型接口 model.chat
消息列表的追加顺序
if 判断"这是答案还是工具请求"
tool_calls 的遍历
工具执行与异常兜底
tool_call_id 的对账
循环的出口
保险丝
```

十二行代码，压了十一个概念。

这不是作者故意写密。

这是 agent 这种程序**天然的形状**。

一个循环，同时是控制流、协议、容错和计费。

所以你单独学任何一个概念，放到这 12 行里都会糊。

## 2. 先看一行更像天书的

再看一眼真实 API 的响应。

代码来源：OpenAI Chat Completions 的 `tool_calls` 形状（字段名真实存在）

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_a1b2c3",
      "type": "function",
      "function": {
        "name": "calculator",
        "arguments": "{\"expression\": \"12 + 8\"}"
      }
    }
  ]
}
```

这一小段里有什么：

```text
role 的四种取值之一
content 可以为 null
tool_calls 是一个数组（一轮可以多个）
id 是给下一次请求对账用的
type 目前只有 function
arguments 是字符串，不是对象
字符串里还要再解析一层 JSON
```

如果你不知道 `arguments` 是字符串，你会写出：

```python
call["function"]["arguments"]["expression"]
```

然后得到一个 `TypeError`。

这不是你笨。

这是**协议的形状**和**你脑子里的模型**对不上。

## 3. 为什么不能从框架开始

市面上的 agent 教程，通常这么开头：

```text
pip install langchain
from langchain.agents import create_agent
agent.invoke("帮我查天气")
```

跑通了。然后呢？

然后你想改一个行为：让它在调用工具前先打印参数。

你打开框架源码，看到：

```text
RunnableSequence
  |-- PromptTemplate
  |-- ChatModel
  |-- OutputParser
  |-- AgentExecutor
        |-- max_iterations
        |-- early_stopping_method
        |-- handle_parsing_errors
```

你不知道 `handle_parsing_errors` 对应你手写循环里的哪一行。

于是只能搜文档、试参数、看 issue。

这就是「会调 API」和「会写 agent」的区别。

框架没有发明任何东西。

它把你那 12 行，变成了 12 个类，外加回调、重试、序列化、流式输出。

**你手写过一遍，框架就只是脚手架的另一种写法。**

反过来，没手写过的人，遇到框架跑不通，只能一层层翻文档碰运气。

## 4. 这张地图有六层

这套讲解把 Agent 知识分成 6 层。

```text
第 1 层：契约     —— 模型是什么，消息长什么样
第 2 层：机制     —— token、上下文窗口、单轮预算
第 3 层：可靠     —— 工具协议、循环、报错、自愈、刹车
第 4 层：能力     —— 上下文工程、记忆、RAG、规划、多 Agent
第 5 层：生产     —— 评测、安全、可观测性、成本
第 6 层：回归     —— 接真模型、拼成成品
```

后面每一篇都在这张地图上。

先一层一层说清楚。

## 5. 六层，一层一层说

把地图摊开。

下面是六层各自要回答的问题。

### 5.1 第 1 层：契约

这一层只回答一个问题：

```text
模型到底是什么东西？
```

答案是：

```text
一个无状态的函数。
```

签名大概是这样：

```text
messages  ->  message
```

你把一整段历史递进去，它吐一条新的出来。

它不记得上一次。

它甚至不知道有上一次。

代码来源：

```text
labs/L01_agent_loop/agent.py
```

```python
# 1. 把完整历史发给模型
reply = model.chat(messages)
```

注意 `messages` 是复数。

每一次调用，你都在重发**全部**历史。

所以这一层要搞清楚：

```text
role 有哪四种？
assistant 消息里为什么可以没有 content？
tool_calls 是什么结构？
tool_call_id 为什么必须原样带回？
消息顺序错了会怎样？
```

这一层学不稳，后面所有东西都会飘。

因为 agent 的一切「记忆」「上下文」「压缩」，本质都是在决定：

```text
这一次，往 messages 里放什么。
```

第 1 层的目标是：

```text
看到一段 agent 代码，能立刻说出它这一轮发给模型的 messages 长什么样。
```

### 5.2 第 2 层：机制

第 1 层说的是「发什么」。

第 2 层说的是「发得下吗、多少钱」。

模型读的不是字，是 token。

一个 token 大约是什么？

```text
英文：大概 3~4 个字符
中文：大概 1~2 个汉字（不同模型差很多）
代码：比自然语言更费
JSON：括号引号都算
```

所以同一段对话，你看到的字数和模型看到的长度不是一回事。

而模型有一个硬上限：

```text
上下文窗口（context window）
```

超过就报错，或者被悄悄截断。

这一层要搞清楚：

```text
token 怎么估？
上下文窗口和输出上限是两回事吗？
system prompt 占多少？
工具说明书占多少？
历史占多少？
为什么"多给点上下文"有时反而更差？
temperature 改的是什么？
```

很多人以为上下文窗口是「记忆容量」。

不是。

它是**单次请求的预算**。

预算花完，不是模型忘了，是请求根本发不出去。

第 2 层的目标是：

```text
在写第一行 agent 代码之前，先会估这一次调用大概多少 token。
```

### 5.3 第 3 层：可靠

这是整个系列最硬的一层。

也是「demo」和「能用」的分界线。

这一层要搞清楚：

```text
工具怎么描述，模型才看得懂？
JSON Schema 里哪些字段是必须的？
模型只输出"意图"，谁来执行？
执行结果怎么回填？
工具报错了，为什么不能抛异常？
重试应该重试什么，不应该重试什么？
max_steps 为什么必须有？
```

先看一个最容易被忽略的细节。

代码来源：

```text
labs/L01_agent_loop/agent.py
```

```python
# 2. 先把模型的这句话记进历史（顺序不能反：工具结果必须排在它后面）
messages.append(reply)
```

为什么这行必须在执行工具**之前**？

因为协议要求：

```text
assistant(带 tool_calls) 必须先存在，
后面那条 role="tool" 的结果才挂得上。
```

顺序反了，用假模型照样跑。

这是教学陷阱。

接真模型的那一刻，API 会直接甩你 400。

这就是「可靠」这一层的价值：

```text
它不让你在 demo 里自我感觉良好。
```

第 3 层的目标是：

```text
让 agent 在模型犯错、工具失败、网络抖动时，仍然能给出一个可解释的结果。
```

### 5.4 第 4 层：能力

前三层保证 agent「能跑、不崩、不烧钱」。

第 4 层开始，才谈「能干大事」。

这一层要搞清楚：

```text
历史太长，丢什么、留什么、怎么摘要？
怎么让它记住昨天的事？
怎么让它读你的文档？
多步任务怎么拆？
什么时候该拆成多个 agent，什么时候不该？
```

这一层有一个共同的本质：

```text
全部是在管理"往上下文里放什么"。
```

记忆是放什么。

RAG 是放什么。

规划是把"放什么"变成"分几次放"。

多 Agent 是把"放什么"拆给不同的上下文。

所以第 2 层（token 预算）没学好，第 4 层会全部变成玄学。

第 4 层的目标是：

```text
面对一个真实任务，能说出"这个任务需要几次模型调用、每次带什么上下文"。
```

### 5.5 第 5 层：生产

这一层最不性感，但最值钱。

要搞清楚：

```text
改了一行 prompt，怎么知道变好还是变坏？
文档里藏了一句"忽略之前的指令"，怎么防？
工具能删文件，权限怎么分级？
线上出问题了，怎么复现当时那一轮？
一次任务到底花了多少钱？
```

这一层里最重要的是评测（eval）。

因为：

```text
没有 eval 的人，是在凭感觉调 agent。
```

凭感觉调，你会遇到一个死循环：

```text
改 A，B 坏了。
改 B，A 又坏了。
你不知道现在这版比上一版好还是差。
```

有 eval 就不一样：

```text
20 条固定用例，跑一遍，看通过数。
从 13/20 到 15/20，就是变好。
```

第 5 层的目标是：

```text
每一次改动，都能用一个数字回答"有没有变好"。
```

### 5.6 第 6 层：回归

最后一层是收口。

要搞清楚：

```text
假模型和真模型的协议差在哪？
超时、限流、断网怎么处理？
流式输出怎么和工具调用共存？
怎么把前面 16 篇拼成一个真东西？
```

这一层不是新知识。

它是把前面所有层，放回真实世界跑一遍。

真实世界会教你一些教程不教的东西：

```text
模型今天特别慢
接口偶尔 429
参数偶尔是字符串 "100" 而不是数字 100
上下文快到上限时模型开始漏指令
```

第 6 层的目标是：

```text
从"我写了个 agent"，变成"我有个能交给别人用的 agent"。
```

## 6. 三张图：一个循环、一次请求、一个任务

地图有了，还需要三张「尺度不同」的图。

因为 agent 的 bug，经常是**尺度错位**造成的：

```text
你在看循环，问题在请求。
你在看请求，问题在任务。
```

### 11.1 一个循环（微秒到秒级）

```text
        ┌──────────────────┐
        │    messages[]    │◄──────────────┐
        └────────┬─────────┘               │
                 │ ① 整个历史发过去         │
                 ▼                         │
          ┌─────────────┐                  │
          │    模型      │                  │
          └──────┬──────┘                  │
                 │ ② 只可能回两种            │
        ┌────────┴────────┐                │
        │                 │                │
  有 tool_calls      没有 tool_calls       │
        │                 │                │
        ▼                 ▼                │
  ③ 执行工具          ④ 这是答案            │
     结果 append 进历史 ─── 循环结束         │
        │                                  │
        └──────────────────────────────────┘
```

这就是 `run_agent` 的全部。

### 11.2 一次请求（毫秒到分钟级）

```text
你拼好的 messages
      │
      ▼
  tokenize（变成 token）
      │
      ▼
  模型前向计算
      │
      ▼
  采样出下一个 token
      │
      ▼
  重复，直到 stop 或上限
      │
      ▼
  反 tokenize（变回文本 / JSON）
```

这张图解释了为什么：

```text
输出越长越慢
temperature 影响采样，不影响"事实"
同一个 prompt 两次结果可能不同
```

### 11.3 一个任务（分钟到小时级）

```text
用户的一句话
      │
      ▼
  规划（拆成几步）
      │
      ▼
  第 1 步：请求 → 工具 → 观测
      │
      ▼
  第 2 步：请求 → 工具 → 观测
      │
      ▼
  ...
      │
      ▼
  汇总 → 交付
```

这张图里才有：

```text
预算、超时、断点、失败回滚、人工审批
```

三张图对不上，就会出现这类 bug：

```text
循环里每一步都对，整个任务还是错的。
```

原因通常是：任务层的状态（做到第几步了、哪些结论已经确定）没有回填到循环层的 messages 里。

## 7. 六种失败，六层病根

地图的作用不是好看。

是让你在出事的时候，知道该去哪一层找。

下面是 agent 最常见的六种失败。

每一种都标了病根在哪一层。

### 6.1 消息顺序错了（契约层）

症状：

```text
API 返回 400，错误信息里提到 tool 消息或 tool_call_id
```

或者更隐蔽：模型开始答非所问。

病根：

```text
assistant(带 tool_calls) 和它的 tool 结果被拆开了。
```

有一种很典型的写法：

代码来源：

```text
labs/L01_agent_loop/agent.py
```

```python
# 错误示范：先记工具结果，再记模型的话
messages.append(Message(role="tool", content=observation, tool_call_id=call.id))
messages.append(reply)
```

假模型不检查顺序，照样跑。

真模型会当场拒收。

修的地方不在模型，在循环里那两行 append 的顺序。

### 6.2 上下文爆了（机制层）

症状：

```text
maximum context length 报错
```

或者：

```text
不报错，但模型开始忘掉开头的规则。
```

病根：

```text
历史线性增长，工具返回没有上限。
```

修的地方不在 prompt，在预算和裁剪。

### 6.3 停不下来（可靠层）

症状：

```text
模型一直在调同一个工具。
```

或者：

```text
任务看起来完成了，模型还在"再查一次"。
```

病根：

```text
循环没有合格的出口，或者有出口但没人触发。
```

修的地方是保险丝：

```text
max_steps
单次任务超时
单次任务金额上限
```

三道都要有。

只有步数，挡不住"每步都很贵"。

### 6.4 参数幻觉（可靠层 + 机制层）

症状：

```text
工具收到 {"expression": "12 + "} 这种半截 JSON
```

或者：

```text
模型把数字写成了字符串 "100"
```

病根：

```text
模型生成的是文本，不是对象。
schema 约束了形状，但没有约束"一定合法"。
```

修的地方是适配器：

```text
json.loads 兜住解析失败
把错误信息原样回填给模型
让它自己改
```

### 6.5 被注入（生产层）

症状：

```text
你让它总结一份文档，它开始执行文档里写的命令。
```

病根：

```text
模型分不清"指令"和"数据"。
```

修的地方不在 prompt。

在权限、审批、沙箱。

13 篇会专门讲。

### 6.6 不知道有没有变好（生产层）

症状：

```text
改了一版，感觉好点了。
改了两版，不知道哪版更好。
```

病根：

```text
没有 eval，没有基线。
```

修的地方是 09 篇。

把这六种失败排在一起，你会发现一个规律：

```text
只有 6.4 的一半，勉强算模型的问题。
其余五种，全是工程问题。
```

所以「模型不行」这个结论，八成下得太早。

### 7.1 顺手对一张表：你手写的 ↔ 框架里的

这一节是给「已经会用框架、但心里没底」的人看的。

把 `run_agent` 拆成八件事，左右对照。

| 你手写的 | LangChain 里的 | 说明 |
|---|---|---|
| `for step in range(max_steps)` | `AgentExecutor` 的内部循环 | 同一个 while |
| `messages` 列表 | `state["messages"]` / Memory | 都是「你负责喂历史」 |
| `ToolCall` / `reply.tool_calls` | `tool_calls`（新）/ `AgentAction`（旧） | 字段名不同，语义一样 |
| `tool_call_id` | 同名 | 这条各家最没歧义 |
| `tools` 字典 | `tools=[BaseTool...]` | 都是注册表 |
| `try/except` 转观测 | `handle_tool_error=True` | 错误变反馈 |
| `max_steps` | `max_iterations` | 保险丝 |
| `model.chat(messages)` | `llm.invoke(messages)` | 唯一的真实接口 |

右边那一列，没有一行是框架发明的。

它们只是把左边这八件事，变成了八个类，外加配置、回调、重试、序列化。

所以：

```text
你手写过一遍，读框架源码就只是在对答案。
没手写过的人，遇到框架跑不通，只能一层层翻文档碰运气。
```

这张表的每一行，后面都有一篇对应。

现在不用背。

等你读到那一篇，回来扫一眼，会有「原来是它」的感觉。

## 8. 五个最常见的误解

这一节提前把后面要反复纠正的东西列出来。

看到它们，先停下来。

### 误解一：模型记得上下文

不对。

模型是无状态的。

你看到的"记得"，是客户端每次把历史重发了一遍。

所以：

```text
"它怎么忘了" → 去看这次发出去的 messages 里还有没有。
```

### 误解二：工具是模型在跑

不对。

模型只输出一段 JSON。

执行的是你的 `_execute()`。

代码来源：

```text
labs/L01_agent_loop/agent.py
```

```python
observation = _execute(call, tools)
```

这一行跑在你的进程里。

模型甚至不知道它执行成功了没有，直到你把结果发回去。

### 误解三：RAG 就是向量数据库

不对。

RAG 是流程：

```text
先检索，再把片段塞进上下文。
```

向量库只是检索器的一种。

关键词检索、BM25、按标题查，都算。

### 误解四：框架会替你管好循环

不对。

框架会替你管好**它认为该管的那部分**。

剩下那部分，出问题时只有你知道它长什么样。

所以才有 L01：先手写一遍。

手写过，框架才只是"换皮"。

### 误解五：agent 越复杂越强

不对。

多一个 agent，多一份上下文复制、多一次出错机会、多一笔成本。

12 篇会讲什么时候该拆。

结论提前说：

```text
多数任务，一个 agent 加几个好工具就够了。
```

### 10.1 入门只需要两种语言的一点点

很多人卡在第一步，不是因为 agent 难。

是因为不知道「该先学多少编程」。

答案比你想的少得多。

**Python 这边，只需要这些：**

```python
# 1. 函数
def add(a, b):
    return a + b

# 2. 字典和列表
tools = {"calculator": add}
names = ["a", "b"]

# 3. 循环和条件
for step in range(3):
    if step > 1:
        break

# 4. try / except
try:
    risky()
except Exception as exc:
    print(type(exc).__name__, exc)

# 5. f-string
print(f"{step} 步")
```

就这些。

不需要类，不需要装饰器，不需要异步，不需要类型系统。

L01 的 `agent.py` 里出现了 `@dataclass`，那是为了可读性。

你完全可以先用普通字典写：

```python
message = {"role": "user", "content": "你好"}
```

它一样能跑。

**另一种「语言」是 JSON。**

```json
{
  "role": "assistant",
  "tool_calls": [
    {"id": "c1", "name": "calculator", "args": {"expression": "1+1"}}
  ]
}
```

你不需要会写 JSON 生成器。

只需要看得懂：

```text
花括号是对象
方括号是数组
双引号包住键和字符串
逗号分隔，最后一项后面不能有逗号
```

会这两样，就能开始读这个系列的代码。

剩下的，边做边补。

框架、异步、向量库、部署，都是后面的事。

顺序反了，会在一堆概念里淹死。

## 13. 以后读 Agent 代码的五个问题

在学这个系列的过程中，每次看到一段 agent 代码，都可以问五个问题。

第一个：

```text
这一轮的 messages 长什么样？
```

第二个：

```text
模型被允许输出哪几种东西？
```

第三个：

```text
工具是谁执行的？失败会怎样？
```

第四个：

```text
循环什么时候停？谁来停？
```

第五个：

```text
这次调用大概多少 token、多少钱？
```

这五个问题会贯穿整个系列。

能秒答这五个问题，你读任何 agent 框架的源码，都只是在对答案。

### 13.1 拿一段真实代码试一遍

用这五个问题，读 `run_agent` 的核心四行。

代码来源：

```text
labs/L01_agent_loop/agent.py
```

```python
reply = model.chat(messages)
messages.append(reply)
if not reply.tool_calls:
    return reply.content
```

第一个问题：这一轮的 messages 长什么样？

```text
system + user + 之前所有的 assistant / tool 交替。
顺序是硬约束：一条 assistant(tool_calls) 后面
必须紧跟它的 tool 结果。
```

第二个问题：模型被允许输出哪几种东西？

```text
两种：纯文本（含 content 为 null 的情况），
或者带 tool_calls 的结构。
```

第三个问题：工具是谁执行的？失败会怎样？

```text
不是在这四行里执行的。
执行在下面的循环体和 _execute 里，
失败会被转成一条 role=tool 的观测，不抛异常。
```

第四个问题：循环什么时候停？谁来停？

```text
两种停法：
模型不再要工具（return reply.content），
或者步数耗尽（for 循环结束，走保险丝）。
```

第五个问题：这次调用大概多少 token、多少钱？

```text
四行看不出来。
但你能顺着想到：
messages 在增长，token 在增长，
所以 02 篇的预算问题，从这四行就开始了。
```

五个问题，四行代码。

这就是「读代码」和「看懂代码」的区别。

前者是逐行翻译。

后者是每一行都知道它在整个系统里的位置。

## 14. 第一个反直觉的点

这一篇快结束了，先留一句话。

后面 17 篇都会反复回到它：

```text
模型是无状态的。
所以"记忆"不是模型的能力，
是你每一轮往里塞的东西。
```

这句话听起来简单。

但它会推翻很多人的直觉：

```text
"上下文"不是模型的脑子，是你递过去的文件夹。
"记忆"不是它记住了，是你没把它删掉。
"遗忘"不是它忘了，是你这次没塞进去。
```

从这个角度再看 agent：

```text
agent = 模型 + 一个循环 + 一套工具 + 一份被精心维护的历史。
```

四样东西里，只有一样是模型。

另外三样，全是你写的。

这就是这个系列要讲的事。
