用户发来一句话。

「帮我把这份周报整理成三条结论，每条配一个数据来源，然后写进 notes.md。」

模型回了两个字：

「好的。」

然后结束了。

## 1. 一句话的任务，五步才做完

上面那句话拆开，至少是五件事。

```text
第 1 步  读周报（read_file）
第 2 步  找出可以当结论的三组事实
第 3 步  给每条结论配来源（可能是再查一次文档）
第 4 步  写成三条带出处的文字
第 5 步  写进 notes.md 并确认写入成功
```

五步，意味着五次模型调用、四次工具执行、四轮观测回填。

而模型在第二轮看到的，已经不是那句话了。

它看到的是：system prompt、那句话、它自己的第一句回复、第一条工具结果。

到第五轮，开头那句话已经被七八条消息压在中间。

模型没有「记得这件事」的能力。

每一轮它重读你发过去的历史。

当历史变长，「最开始那句话」在它眼里的权重，和最新一条工具结果完全不是一回事。

这就是长任务会迷路的物理原因。

把消息数量摊开看更直观。

```text
第 1 轮   system + user                       2 条
第 2 轮   + assistant + tool                  4 条
第 3 轮   + assistant + tool                  6 条
第 5 轮   + assistant + tool                  10 条
第 8 轮   + assistant + tool                  16 条
```

原始任务在第 2 位。

最新一条工具结果在第 16 位。

模型没有「按重要性排序」的能力，它只有注意力权重。

而注意力离得越远越弱，这是长上下文里普遍存在的现象，具体衰减曲线以你要用的模型实测为准。

所以你看到的现象是：

```text
前三步还记得要三条结论
第五步开始只写了两条
第七步开始忘了要出处
```

不是它变笨了。

是它读到的东西变了。

## 2. 长任务失败的四条路

### 2.1 上下文漂移

现象：前几步做得对，第 6 步开始做一件没人要求的事。

原因不神秘。

每一条工具结果都会重新塑造模型对「现在该干什么」的判断。

读到一个表格，它想分析表格。

发现一个文件不存在，它想换个路径找。

前面说过「只整理三条结论」，但那条指令现在的相对位置已经很靠后了。

所以它开始处理「眼前这个东西」。

一段真实跑出来的 trace 长这样。

```text
第 1 步  模型：我先读周报            → read_file("周报.md")
         观测：文件不存在
第 2 步  模型：换个路径找找          → list_dir(".")
         观测：draft.md  notes/
第 3 步  模型：读 draft.md 吧        → read_file("draft.md")
         观测：（1200 字周报正文）
第 4 步  模型：先总结成本部分        → 好的，本周成本…
第 5 步  模型：再总结延迟部分        → …
```

到第 5 步，它已经在做「分章节总结」。

用户要的是「三条结论 + 每条一个来源」。

它做的事很合理，只是不是那件事。

这就是漂移：每一步都能自圆其说，整体偏离。

判断信号：中间产物越来越长，而离任务描述里的关键词越来越远。

### 2.2 目标遗忘

比漂移更彻底。

它记得手上这一步，忘了整件事。

```text
用户要：三条结论 + 每条一个来源
它做到：一条结论，写得很详细，没有来源
```

它没有犯错，它只是把一个子任务当成了全部任务。

### 2.3 局部最优

第三种最隐蔽。

第 3 步时它发现了一条更省事的路：不用查文档，直接总结。

于是它放弃了已经做完的第 2 步的成果，从头开始走那条近路。

结果更快，但更糙，而且丢掉了已经拿到的证据。

局部最优在 agent 里的表现不是「做得不好」，是「做的不是原来那件事」。

具体长这样：

```text
原计划：查三个来源 → 交叉验证 → 写结论
第 3 步时发现：第一个来源里已经有一句总结
于是它跳过了验证，直接把那句总结当结论交上去
```

快是真快。

问题是那句总结是个旧数字，另外两个来源里有一个更新的。

它没作弊，它只是找了个更省事的路。

而这个选择在当下完全合理。

要拦住它，靠的不是 prompt 里写「不要偷懒」。

靠的是清单上第 3 项写着「三个来源数字一致才算完成」。

判据写死了，捷径就走不通。

### 2.4 步数耗尽

最贵的一种。

`max_steps` 到了，循环被保险丝（fuse）掐断。

返回值是那句「达到最大步数」。

前面九步全部作废，因为没有任何中间产物被保存下来。

用户拿到的是一句道歉，而不是「前两条结论已经写好了，第三条缺来源」。

四条路指向同一件事：

```text
模型需要的不是"更努力地想"。
它需要一个能读、能改、能打勾的东西，替它记住做到哪了。
```

## 3. 两种规划，两种失败模式

### 3.1 先规划后执行

第一种做法是 plan-and-execute。

先让模型输出一份完整计划，再按计划逐步执行。

```text
任务 → 计划（1. 2. 3. 4.）→ 执行第 1 步 → 执行第 2 步 → ... → 汇总
```

它的好处是结构清楚：你能在动手前看到全貌，能人工审一遍，能预估步数。

它的失败模式有两个。

第一个：**计划一开始就错**。

因为出计划的时候，模型还没读过任何材料。

它对任务的了解只有用户那一句话。

于是计划常常是「看起来合理但和真实数据对不上」：它假设周报里有数据表格，实际是纯文字。

第二个：**执行时死抠计划**。

计划里写了「查三个来源」，实际第一个来源就够了。

它还是去查了另外两个，因为计划上是这么写的。

计划从地图变成了枷锁。

### 3.2 边做边规划

第二种是 ReAct 式：每一步先想一句，再决定调什么工具，看结果，再想。

```text
想 → 做 → 看 → 想 → 做 → 看 → ...
```

它的好处是贴合现实：信息不足时能改方向，遇到意外能绕。

它的失败模式也有两个。

第一个：**绕圈**。

同一个工具用不同参数调了四次，每次都不满意，因为每次都不知道自己在找什么。

第二个：**没有全局视角**。

每一步都局部合理，整体做完发现少了一半要求。

因为「整体」从来没有被写下来过。

### 3.3 实际的做法是混合

不是二选一。

主流做法是：**粗计划 + 细执行**。

```text
先出 3~7 项清单（粗）
每一项执行时用 ReAct（细）
每完成一项，回头看一眼清单
```

清单是骨架，ReAct 是肌肉。

骨架保证不忘目标，肌肉保证能处理意外。

两种方式的差别，画成图更清楚。

```text
先规划后执行
  任务 ──▶ [完整计划] ──▶ 执行1 ──▶ 执行2 ──▶ 执行3 ──▶ 汇总
              ▲                                       │
              └──────── 计划不会变（问题就在这）────────┘

边做边规划（ReAct）
  任务 ──▶ 想 ──▶ 做 ──▶ 看 ──▶ 想 ──▶ 做 ──▶ 看 ──▶ 汇总
                                        （没有全局图，容易漏要求）

混合
  任务 ──▶ [清单 3~7 项] ──▶ 每项内部 ReAct ──▶ 打勾 ──▶ 下一项
                │                                   │
                └────────── 允许重规划 ◀────────────┘
```

三种画法的区别，落到一个问题上：

```text
「整体」被写下来了吗？
「局部」允许改吗？
```

先规划后执行：写了整体，不许改局部。

ReAct：没写整体，随便改局部。

混合：写了整体，允许改整体。

最后一种才同时解决遗忘和意外。

而清单要能被模型看到，就必须是一个工具。

## 4. todo 列表为什么有效

这一节是全篇的核心。

先说清楚模型的工作状态。

模型是无状态的。

它没有「工作记忆」这种东西。

每一轮它能用的，只有你这次发过去的 messages。

所以「我做到第几步了」这件事，如果只存在于模型的推理里，那它在下一轮就不存在了。

**反直觉的点在这里：**

> 规划的价值不在「想得更远」，在**把状态从模型脑子里搬到外面**。

搬出来之后，会发生三件事。

### 4.1 状态变成可读的 token

清单被写进文件，或者被拼进这一轮的上下文。

于是模型读到的是：

```text
进度 2/5
[x] 1. 读周报（证据：notes/draft.md，1200 字）
[x] 2. 找出三组可当结论的事实（证据：三组，分别关于成本、延迟、稳定性）
[ ] 3. 给每条结论配来源
[ ] 4. 写成三条带出处的文字
[ ] 5. 写进 notes.md
```

这不是「记忆」，这是**输入**。

它和 system prompt 一样可靠，因为它每一轮都会重新出现。

### 4.2 每打一个勾，等于给自己一个观测

工具结果回填这件事，05 篇讲过。

打勾也是同一种机制。

`todo_write` 的返回值就是渲染后的清单。

模型下一次调用会看到它，于是它知道自己刚完成了一项。

这个反馈回路不需要模型有记忆，只需要你有工具。

注意 `evidence` 在这里的作用。

它不只是审计记录，它是模型下一轮判断「这一项真的完成了吗」的唯一依据。

一个只写「已完成」的清单，和一个写着「证据：draft.md，1200 字」的清单，对下一步的价值差一个量级。

前者是一句声明，后者是一条可复用的观测。

### 4.3 终止条件从「说完了」变成「清单空了」

这是最被低估的收益。

没有清单时，循环的出口是：

```python
if not reply.tool_calls:
    return reply.content
```

模型只要不调工具，就结束了。

所以它想收工随时能收工。

有清单之后，出口变成：

```text
没有工具调用了，且清单上所有项都打勾了
```

否则不结束，还要把它推回去继续做。

这一步把「模型自觉」换成了「程序判断」。

而程序判断是可以写单元测试的。

## 5. todo 的最小数据结构

一个 Todo 需要四个字段。

```text
id        稳定编号，跨轮引用用
title     这一步要做什么（可验证的动词短语）
done      打没打勾
evidence  打勾的证据（来自哪次工具观测）
```

为什么需要 `id`：模型在第 5 轮说「把第 3 项改一下」，你得知道第 3 项是哪个。用数组下标也行，但下标会随增删漂移。

为什么需要 `evidence`：这是防止「自我表扬」的唯一手段。下一节细说。

### 5.1 写入用整体覆盖，不用增量补丁

两种工具设计：

```text
增量式：todo_mark(id=3, done=True)
整体式：todo_write(items=[... 完整清单 ...])
```

推荐整体式。

原因是模型做增量的可靠性和做整体覆盖完全不在一个量级。

增量要求它准确记住 id、准确记住当前状态。

整体覆盖只要求它把清单重新写一遍，错了下一次还能全量纠正。

代价是每次多花几十个 token。

这个代价值得。

### 5.2 工具长什么样

`todo_write` 的 schema 不长，03 篇讲的 JSON Schema 规则在这里全用得上。

```json
{
  "name": "todo_write",
  "description": "整体覆盖当前任务清单。每次传入完整清单，已完成的项保留 done=true 并填 evidence。",
  "parameters": {
    "type": "object",
    "properties": {
      "items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "title":    {"type": "string"},
            "done":     {"type": "boolean"},
            "evidence": {"type": "string"}
          },
          "required": ["title"]
        }
      }
    },
    "required": ["items"]
  }
}
```

注意 description 里那句「传入完整清单」。

工具说明书是给模型看的，这句话比在代码里做十次校验都有效。

要不要再来一个 `todo_read`？

大多数情况下不用。

`todo_write` 的返回值就是渲染后的清单，写一次等于读一次。

少一个工具，模型少一次选错的机会。

### 5.3 三个别加的字段

清单很容易被越写越复杂。

这三种字段建议先别加：

```text
优先级   模型会给自己喜欢的项排前面，而不是给关键的项
耗时估计 它估不准，而且会拿估计去说服自己砍需求
备注    会长成第二个上下文，写满没人读
```

先只留 `title / done / evidence`。

等你在 eval 里真的看到「因为缺某个字段导致失败」，再加。

这正是 09 篇那条纪律：用例先于功能。

## 6. 最小代码：50 行的清单循环

先看要被替换掉的那个循环。

代码来源：

```text

```

```python
for step in range(1, max_steps + 1):
    reply = model.chat(messages)
    messages.append(reply)

    if not reply.tool_calls:
        return reply.content
```

改成带清单的版本。

代码来源：

```text
labs/L01_agent_loop/planning.py（本篇新建，放在 L01 目录下即可运行）
```

```python
from dataclasses import dataclass
from agent import Message, _execute
from tools import TOOLS

@dataclass
class Todo:
    id: int
    title: str
    done: bool = False
    evidence: str = ""

class TodoList:
    def __init__(self) -> None:
        self.items: list[Todo] = []
    def write(self, items: list[dict]) -> str:
        for it in items:                       # 打勾必须带证据，否则拒绝写入
            if it.get("done") and not it.get("evidence"):
                return "错误：done=true 的项必须填 evidence（来自工具观测），否则不算完成。"
        self.items = [Todo(i + 1, it["title"], bool(it.get("done")), it.get("evidence", ""))
                      for i, it in enumerate(items)]
        return self.render()
    def remaining(self) -> int:
        return sum(1 for t in self.items if not t.done)
    def render(self) -> str:
        rows = [f"{'[x]' if t.done else '[ ]'} {t.id}. {t.title}"
                + (f"（证据：{t.evidence}）" if t.evidence else "") for t in self.items]
        return f"进度 {len(self.items) - self.remaining()}/{len(self.items)}\n" + "\n".join(rows)

TODOS = TodoList()
TOOLBOX = {**TOOLS, "todo_write": lambda items: TODOS.write(items)}

def run_agent(model, tools, messages, todos, max_steps=12):
    for step in range(1, max_steps + 1):
        progress = Message("user", f"<progress>\n{todos.render()}\n</progress>")
        reply = model.chat(messages + [progress])       # 只对这一轮可见，不写回历史
        messages.append(reply)

        if not reply.tool_calls:
            if todos.remaining() == 0:
                return reply.content
            messages.append(Message("user", f"清单上还有 {todos.remaining()} 项没打勾，继续。"))
            continue

        for call in reply.tool_calls:
            obs = _execute(call, tools)
            messages.append(Message(role="tool", content=obs, tool_call_id=call.id))

    return f"（达到最大步数 {max_steps}，剩余 {todos.remaining()} 项未完成）"
```

三处关键。

### 6.1 进度是临时注入的，不进历史

`model.chat(messages + [progress])`。

注意没有 `messages.append(progress)`。

如果你把进度写进历史，跑八步之后历史里就有八份进度快照。

七份是过期的。

模型会看到「进度 1/5」「进度 2/5」「进度 3/5」同时在上下文里，然后它可能按最旧的那份办事。

而且这玩意儿很占 token。

清单的作用是**每轮重读一份最新的**，不是**攒一堆历史**。

### 6.2 想收工会被拦回去

`if todos.remaining() == 0` 才允许返回。

不满足就追加一条 user 消息，把模型推回去继续干。

这是全篇最有价值的一行判断。

它把循环的出口从「模型说完了」搬到了「清单空了」。

不过它有一条件，写在后面第 9 节：

清单必须允许被改。

否则模型会为了「让清单空」而给自己打假勾，而不是真的做完。

出口判断和打勾证据，必须成对出现。

只有前者，你会得到一个会撒谎的系统。

只有后者，你会得到一个永远跑不完的系统。

### 6.3 步数耗尽时交半成品

最后那行返回值带了剩余项数。

比原来的「（达到最大步数 10，强制停止）」多了一个信息：还差几项。

用户至少知道做到哪了。

### 6.4 为什么 todo_write 必须带 call_id

一个实操细节。

用 `labs` 的 `ScriptedModel` 跑这段代码时，`tool_call("todo_write", items=[...])` 会报 `unhashable type: 'list'`。

因为假模型用参数元组算 `call_id`，而列表不可哈希。

真实 API 里 `arguments` 是一个 JSON 字符串，没有这个问题。

所以在练习代码里显式传：`tool_call("todo_write", call_id="t1", items=[...])`。

这不是设计缺陷，是假模型的一个边界。

## 7. 把「步」定义成可验证的

清单最容易写坏的地方在这里。

看三种典型写法。

```text
坏：整理周报
坏：分析数据并得出结论
坏：完成报告
```

这三种都打不了勾。

因为「整理」到什么程度算完成，没有判据。

好的写法必须包含三样东西：

```text
一个动词：算出 / 列出 / 读到 / 写到 / 比对 / 确认
一个对象：对什么做
一个判据：什么算完成（数字、条数、文件名、布尔值）
```

改一遍：

```text
好：用 calculator 算出 Q3 成本环比，得到百分比数字
好：从 notes/draft.md 里列出三条带数据的事实
好：把三条结论写进 notes.md，并确认写入了 3 个以 [1][2][3] 开头的段落
```

判据可能是「数字出现了」「条数对上了」「文件里有这段话」。

关键是：**判据必须能在工具返回值里被检查**。

```python
def is_checkable(title: str) -> bool:
    has_verb = any(v in title for v in ("算出", "列出", "读到", "写到", "比对", "确认", "生成"))
    has_crit = any(c.isdigit() for c in title) or "条" in title or "格" in title
    return has_verb and has_crit
```

这个函数很粗糙，但它能用。

它可以当规划器的第一道自动检查：模型给出的清单里，可验证项少于 80% 就打回重写。

一条更实用的判断句：

```text
如果这一步失败了，你能不能在日志里一眼看出它失败了？
```

看不出来，这一步就写错了。

### 7.1 三组改写

「整理周报，提炼三条结论」这一句，三种拆法：

```text
拆法 A（不可用）
1. 分析周报
2. 提炼结论
3. 输出

拆法 B（勉强）
1. 读周报
2. 写三条结论

拆法 C（可用）
1. 读 draft.md，确认读到 3 个含数字的段落
2. 从这 3 段里各取一个数字，写成 3 条结论
3. 给 3 条结论各配一个段号作为来源
4. 写入 notes.md，确认文件里有 3 个 [1][2][3] 标记
```

A 的问题是没有判据。

B 的问题是有判据但没写出来：「三条」在自己的脑子里。

C 每一项都能在下一步的观测里被检查，包括最后那一项——写入之后读一次文件，数一数有几个标记。

### 7.2 判据要能落到工具返回值上

「确认读到 3 个含数字的段落」这一项，判据是 3。

工具返回的是一段文本，模型要能从里面数出 3。

如果工具返回的是「读取成功」这种废话，这一项就没法打勾。

所以可验证性有一个隐藏前提：

```text
工具返回的东西，必须包含判断所需的那个量。
```

这解释了为什么 `read_file` 最好带上字数、行数、标题列表。

不是为了给人看，是为了让下一步能打勾。

工具设计在这里和规划耦合了。

返回一句话的工具，会让整张清单变成一句口号。

## 8. 谁有权打勾

这一节讲一个很容易做错的机制。

清单上的勾，谁打？

如果答案是「模型自己说完成了就打」，那这张清单会退化成自我表扬。

模型很擅长说「已完成」。

尤其在它想结束的时候。

所以规则是：

```text
done=true 必须有 evidence
evidence 必须是某次工具观测的产物
没有 evidence 的勾，写入直接失败
```

代码里那句 `return "错误：...否则不算完成。"` 就是干这个的。

它把「打勾」从一个声明变成了一个需要证据的动作。

模型想做假，就得先编一个工具结果。

而编造的工具结果会和真实观测对不上，下一步就露馅。

这跟 05 篇讲的自愈是同一套哲学：

```text
错误不是异常，是一条要喂回模型的观测。
```

`evidence` 也是同样的用法。

它不只是给人看的审计记录，它还是模型下一轮的输入。

写成「证据：60」的项，比写成「证据：已完成」的项，对下一步有用得多。

一个副作用值得提前知道。

模型被拒一次之后，有些会开始编证据。

判断信号是：`evidence` 里出现了工具从没返回过的字眼。

所以拒绝打勾的错误信息里，最好把「可用的观测」列出来：

```text
错误：done=true 必须填 evidence。你最近的观测是：
1) calculator → 60
2) read_file → draft.md，1200 字
请引用其中之一。
```

这样它编不出来，也不需要编。

## 9. 计划变了怎么办

计划一定会变。

这不是执行失败，这是长任务的常态。

三种必须重规划的触发条件：

```text
一、新信息推翻了某个假设（周报里没有表格，只有文字）
二、某一步连续失败两次（路径不对，工具调不通）
三、剩余步数不够做完剩下的项
```

处理方式有一条铁律：

```text
已完成的项，保留
未完成的项，可以改、可以删、可以加
改动要记一句"为什么改"
```

「为什么改」不用长。

```text
[ ] 3. 给每条结论配来源（原计划查文档，改为从周报脚注取，文档里没有）
```

这句话会在最后汇总时救你。

因为它解释了为什么最终答案的出处和用户预期的不一样。

重规划后的清单长这样。

```text
[x] 1. 读 周报.md（证据：文件不存在，实际是 draft.md）
[ ] 2. 从 draft.md 脚注里取 3 个来源（原计划查"来源"章节，该章节不存在）
[ ] 3. 写结论
```

「为什么改」写进了 title 里。

这比单独开一个字段更可靠，因为 title 每一轮都会被注入到上下文。

单独字段只存在于文件里，模型看不到。

### 9.1 两个反模式

```text
不敢改：一路撞墙，撞到 max_steps
乱改：每步都改，清单从头到尾没稳定过
```

判断有没有乱改，有个粗糙但有效的指标：

```text
重规划次数 / 总步数
```

超过 0.3，说明计划的初始质量有问题。

不是执行的问题，是你让它拆任务时给的信息不够。

这时候该改的是规划那一步的 prompt，不是执行循环。

## 10. 并行与依赖

清单里有些项可以同时做。

「读 A 文件」「读 B 文件」互不影响。

协议上完全支持：一条 assistant 消息里可以带多个 `tool_calls`。

代码来源：

```text
labs/L01_agent_loop/check.py
```

```python
parallel = Message(role="assistant", content="", tool_calls=[
    ToolCall(id="c1", name="calculator", args={"expression": "1+1"}),
    ToolCall(id="c2", name="calculator", args={"expression": "2+2"}),
])
model = ScriptedModel([parallel,
                       lambda m: Message("assistant", "两个都算完了")])
run_agent(model, t, msgs, max_steps=4, verbose=False)
```

一轮两个调用，产生两条 `role="tool"` 消息，`tool_call_id` 各自对上。

`check.py` 的 C 项验收考的就是这个。

### 10.1 什么能并行

判断条件只有两条：

```text
没有共享写入（不写同一个文件、不改同一个状态）
没有先后依赖（B 不需要 A 的输出）
```

满足就能并行。

### 10.2 依赖怎么表达

在清单项上加一个字段：

```json
{"title": "读 A 文件", "depends_on": []}
{"title": "读 B 文件", "depends_on": []}
{"title": "汇总两条并写进 report.md", "depends_on": [1, 2]}
```

然后每轮把「现在能做的集合」算出来，注入进度里：

```python
def ready(todos) -> list[int]:
    done = {t.id for t in todos.items if t.done}
    return [t.id for t in todos.items
            if not t.done and set(t.depends_on) <= done]
```

```text
本轮可执行：1、2
本轮不可执行：3（等 1、2）
```

这段注入能显著减少「提前做第 3 步」的错误。

模型不是不知道依赖，是它不会主动去算。

### 10.3 写操作必须串行

一个反直觉但必须接受的约束。

两个并行的写操作，谁先落地不确定。

模型这一轮写了 A，下一轮写 B，如果两条消息在同一轮发出，B 可能在 A 之前生效。

结果是内容互相覆盖，而观测显示两次都成功。

所以规则是：

```text
读可以并行，写必须串行。
```

宁可慢一步，不要出现「两次都成功但结果只剩一半」。

### 10.4 并行还有个隐藏代价

一轮发三个工具调用，看起来省了两次模型往返。

但它们的观测是一起回来的。

如果第一个就失败了，后面两个的结果你已经付过钱。

而且模型要在同一条消息里看到三个结果，判断变难。

所以并行的判据再加一条：

```text
只在"每个都能独立判定成功或失败"时才并行。
```

三个文件读取可以并行。

「读文件 → 改文件 → 再读一遍确认」不能。

后者看起来是三步读，实际是一条链。

链上任何一环失败，后面的结果都是废的。

## 11. max_steps 与清单数量互相校验

`max_steps` 和清单是同一个系统的两个约束。

一个管钱，一个管进度。

粗算公式：

```text
max_steps >= 2 * 未完成项数 + 2
```

为什么像 2 倍：每一项通常要一次工具调用 + 一次打勾写入。

为什么 +2：开头一次规划写入，结尾一次收尾。

对不上会怎样：

```text
清单 8 项，max_steps 还是默认的 10
→ 做到第 5 项就被掐断
→ 前 4 项白做（如果没落盘）
```

所以循环里要加一道检查：

```python
def budget_ok(todos, step, max_steps) -> str | None:
    if todos.remaining() > max_steps - step:
        return (f"剩余步数 {max_steps - step} 不够做完 {todos.remaining()} 项。"
                "请立即缩小范围：要么删掉不关键的项，要么先交付已完成部分并说明缺口。")
    return None
```

把这句话在合适的时机喂给模型，它会自己砍需求。

比你在外面硬截断好得多。

### 11.1 宁可交半成品

这条要写进 system prompt。

```text
如果时间或步数不够，优先交付已经确认的部分，
并明确说明哪几项没做完、为什么。
不要为了做完而编造。
```

因为「达到最大步数」对用户来说是零信息。

「三条结论写好了两条，第三条缺 X 来源」是有用的交付。

半成品也要有固定格式。

```text
已完成：第 1、2 条结论（含来源）
未完成：第 3 条（缺 Q3 成本数据，原始文件里没有这一项）
原因：draft.md 只覆盖 Q1 和 Q2，Q3 需要另外一份材料
```

三行，分别回答「有什么」「缺什么」「为什么缺」。

没有第三行，用户会以为你没做完是因为笨。

有了第三行，他会去补那份材料。

区别在于下一次。

### 11.2 检查放在哪一步

别在 system prompt 里预先声明一个固定预算。

一开始就告诉它「你只有 9 步」，它会变得保守，把计划砍到 2 项。

推荐的位置是两个：

```text
每次 todo_write 之后        刚写完清单，正好核一次预算
剩一半步数、还剩大半项时    这时候必须决策：砍范围还是收工
```

```python
if step == max_steps // 2 and todos.remaining() > 2:
    messages.append(Message("user", "步数过半，剩余项还多。请现在决定：砍范围，或先交付已完成部分。"))
```

这句注入是「中途决策点」。

它的价值不在于省钱，在于让「交付什么」变成一个显式的决定，而不是被保险丝随机掐断。

## 12. 怎么让模型拆得像样

清单的质量，八成取决于规划那一步的 prompt。

四样东西缺一不可。

```text
输出格式   JSON，items 数组，每项有 title
项数约束   3~7 项；超过 7 项要求合并，少于 3 项要求说明为什么不用拆
动词约束   要"算出 / 列出 / 写到 / 读到 / 确认"，不要"分析 / 优化 / 整理"
一个反例   一段"看起来像计划但不能用"的清单
```

反例比正例有用。

因为模型模仿反例的速度更快，反例也短。

```text
反例（这样写等于没拆）：
1. 分析周报
2. 得出结论
3. 输出结果
```

正例只需要一个，够它对齐格式。

### 12.1 一条容易被漏掉的规则

```text
如果任务缺少关键信息（文件名、时间范围、输出位置），
第一项必须是"确认 X"，而不是直接执行。
```

没有这条规则，模型会编。

它不会问你文件在哪，它会假设 `周报.md` 存在。

然后第一步就失败，然后它开始猜别的路径。

加了这条规则，第一项会变成「确认周报文件路径」，一次工具调用就解决。

这条规则对规划器的评测也有用，后面评测那一节会再提一次。

### 12.2 拆完要自检

拆完不要直接用。

用规则或同一个模型自检三条：

```text
每项都有动词和判据吗？
项数在 3~7 之间吗？
任务的每个要求都有对应项吗？
```

自检失败就打回重写。

最多两次。

两次之后还不行，就退化成「只出第一步，边做边补」。

这比硬塞一个错的完整计划好。

因为错计划最贵的代价不是做错，是它让你以为已经想清楚了。

## 13. 规划器本身怎么评测

规划器也是可以被评测的。

用的还是 09 篇那套：固定用例、判分函数、通过数。

只是判分对象从「最终答案」变成了「计划本身」。

测四件事。

### 13.1 项数

```text
3~7 项：正常
1~2 项：没拆，或者任务确实简单
8 项以上：大概率把流水账当计划了
```

项数是最便宜的结构信号。

单独用它当判分不够，但当第一道筛子足够。

### 13.2 可验证性

用上一节那个 `is_checkable`，或者让 judge 判：

```text
rubric：每一项是否有一个能在工具返回值里检查的完成判据？
pass：动词 + 对象 + 判据齐全
fail：出现"整理""分析""优化"这类无判据动词
```

judge 在这里比人稳，因为它的标准是结构化的。

但记得锁定 judge 的版本。

一个能用的 rubric 长这样。

```text
你是严格的计划评审。只输出 JSON：{"verdict": "pass 或 fail", "reason": "一句话"}

对每一项检查：
- 有没有一个动词，说明这一步要产生什么？
- 有没有一个量，让下一步能判断它完成了？

按这些规则判 fail：
- 出现"分析""整理""优化""处理"却没有说明产出
- 一项里塞了两个以上不相干的动作
- 判据是"看起来不错"这种主观描述
```

注意最后那条 fail 规则。

没有它，judge 会给「整理得比较好」这种项打 pass。

因为它在语义上确实像一件事。

### 13.3 覆盖率

原任务的每个子句，是否都有对应的清单项。

用规则判会很脆（措辞变化），用 judge 判更合适。

```text
用户任务：整理三条结论 + 每条配来源 + 写进 notes.md
检查：清单里是否有"三条"相关的项、是否有"来源"相关的项、是否有"notes.md"相关的项
```

覆盖率低，说明它只拆了它看得懂的部分。

这是规划器最常见的失败。

### 13.4 步数经济性

```text
实际步数 / 清单项数
```

理想值在 1.5 到 2.5 之间。

超过 3，说明每一项都在反复试错。

低于 1.2，说明清单是事后补的，不是真拿它做事的。

### 13.5 用例怎么来

十条真实任务描述就够。

来源和 09 篇一样：真实失败优先。

特别注意要放几条「信息不足」的任务进去。

比如：「帮我把上周的数据整理一下」——没有说是哪个文件。

好的规划器会先加一项「确认数据在哪」，而不是直接开始编。

这一点用 judge 判特别有效：

```text
rubric：任务信息不足时，计划的第一项是否为"澄清/定位"，而不是直接执行？
```

### 13.6 结果怎么存

和 09 篇一样，落盘，别只在终端里看。

一条记录至少要有：

```json
{"task": "整理周报", "items": 5, "checkable": "4/5",
 "covered": "3/3", "steps": 9, "verdict": "pass",
 "judge": {"model": "固定版本", "rubric": "v2"}}
```

`items` 和 `checkable` 是结构指标，算出来的。

`covered` 和 `verdict` 里带 judge 的那些，要标版本。

这样两份记录才能比。

比的时候先看 `checkable` 和 `covered`，再看 `steps`。

因为前两个掉了，说明计划本身变差了。

`steps` 掉了，可能只是执行变快了。

## 14. 常见错误与读码清单

### 14.1 把 todo 当装饰

写了清单，从来不更新。

跑完十步，清单上还是五个空格。

这种清单对模型唯一的贡献是占 token。

判断信号：`todo_write` 在整个 trace 里只出现一次。

### 14.2 每轮把清单塞进历史

前面说过，这里再说一次，因为它极其常见。

```python
messages.append(progress)     # 错
model.chat(messages + [progress])   # 对
```

跑八步之后，前者会在上下文里留下八份快照。

其中七份过期。

### 14.3 清单项太粗或太细

```text
太粗：完成项目
太细：打开 notes.md 的第 1 行
```

太粗打不了勾，太细把一次工具调用拆成五项。

判据：一项大概对应一次到两次工具调用。

### 14.4 用清单替代执行

清单上写着「已读取周报」，但从来没调用过 read_file。

这是最危险的一种，因为它看起来一切正常。

`evidence` 字段就是为这个设计的。

没有观测的勾，一律不算。

### 14.5 把思考写进清单

清单项是动作，不是感想。

```text
坏：思考一下该怎么总结
好：从 draft.md 里挑出三条带数据的句子
```

「思考」这类项永远不会有一个可检查的判据，于是它永远打不了勾，或者被打假勾。

### 14.6 读别人的规划器，问五个问题

```text
1. 清单存在哪？上下文里、文件里、还是外部状态里？
2. 每项有没有可验证的完成判据？
3. 打勾需不需要证据？谁来判断？
4. 循环的终止条件是"模型不调工具"还是"清单空了"？
5. 步数不够时，它是交半成品还是交一句道歉？
```

第 4 个问题最能区分玩具和工具。

## 15. 小结与下一篇

这一篇没有讲「怎么让模型想得更远」。

因为那个方向多半是死路。

模型想多远，取决于它这一轮看到什么。

所以要做的事情是反的：

```text
把它该记住的东西，写到它能读到的地方。
把它该做到哪一步，变成一行能打勾的文字。
把"做完了吗"这个问题，从模型嘴里搬到程序里。
```

三句话，就是这一篇的全部。

清单的最小形态：

```text
id + title + done + evidence
```

循环的三个改动：

```text
每轮注入最新进度（不进历史）
没有工具调用且清单空了才结束
步数不够就缩小范围，交半成品
```

还有一句要记住的话：

**规划的价值不在「想得更远」，在把状态从模型脑子里搬到外面。**

模型脑子里没有抽屉。

你得给它一张纸。

下一篇讲另一件事：让 agent 读你的文档。

```text
Agent 系统讲解 11：RAG：切分、检索与引用
```

那一篇要回答的是：

```text
怎么让 agent 读你的文档，并且说得出出处。
```

它和这一篇有一个共同点：

```text
都是在决定"这一轮往上下文里放什么"。
```

区别是，这一篇放的是进度。

下一篇放的是证据。

还有一个不明显的联系。

RAG 的检索结果，通常也会被塞成「第 1 段、第 2 段」。

那是另一种清单：不是进度的清单，是证据的清单。

两者都要求同一件事——每一条都要能对回一个真实的来源。

进度对回工具观测，答案对回文档片段。

对不回去的，都不算数。
