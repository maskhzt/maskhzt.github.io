一个 agent 跑到第 20 轮，模型突然问：

```text
你想让我做什么来着？
```

这不是模型退化。

是你在第 12 轮裁剪历史的时候，把它最初那句话删掉了。

前五篇讲的是：怎么让循环跑起来、怎么让工具不炸、怎么在报错里自愈。

这一篇开始，问题变了。

不是「它能不能做」，而是「它还记得要做什么吗」。

## 1. 上下文不是记忆，是预算

先把两个词分开。

上下文（context）：这一次请求里，真实发出去的全部 token。

记忆（memory）：你手里存着的、可能发出去的东西。

两者的关系是：

```text
记忆是你硬盘里的文件夹。
上下文是你这一次塞进信封的纸。
```

信封有大小。

纸多了塞不下，纸少了说不清。

模型不会自己去翻你的文件夹。

它只能看信封。

所以每一轮，你都站在同一个岔路口：

```text
这一轮，我发什么？
```

前五篇里，这个答案很简单：全发。

`messages` 里有什么，就发什么。

因为那时候历史只有 4 条、6 条。

到了第 30 轮，`messages` 有 60 条。

你还是全发吗？

不一定发得出去。

就算发得出去，也不一定更好。

这就是上下文工程（context engineering）要处理的事。

它不是「写更长的 prompt」。

它是**在有限的预算里，决定发什么、不发什么**。

换个说法。

```text
上下文是工作台，不是仓库。
仓库再大，工作台上也只能摊开那么多东西。
```

你每次做菜，都要决定这道菜拿哪几样。

拿多了，台面放不下，还会碰倒别的。

拿少了，做到一半得回去翻柜子。

上下文工程就是这件事：**这一次，台面上放什么**。

它不回答「你有哪些知识」。

它回答「这一次用哪些」。

## 2. 一次请求的预算怎么被瓜分

上下文窗口（context window）是一个硬上限。

常见量级从 8k 到 1M token，差别很大，以你要用的模型文档为准。

这个上限要装五样东西。

```text
┌──────────────── 上下文窗口（硬上限） ────────────────┐
│ ①system │ ②工具schema │ ③历史 messages │ ④本次输入 │ ⑤输出余量 │
└──────────────────────────────────────────────────────┘
```

一样一样说。

① **system prompt**：你是谁、规矩是什么、边界在哪。

这一块通常最小，但每一轮都在。

② **工具 schema**：每个工具的说明书。名字、参数、参数类型、描述。

工具少的时候不显眼。

工具一多，它能吃掉很大一块。

20 个工具、每个说明书 300 token，就是 6000 token。

你还没开始说话，预算已经少了一大截。

这一点 03 篇（[工具协议与 JSON Schema](/posts/agent-tool-protocol-json-schema/)）讲过形状，这里只算账。

③ **历史 messages**：这是最大的一块，也是唯一可以动的一块。

④ **本次用户输入**：通常最小。但如果用户粘了一篇文档进来，它可能比历史还大。

⑤ **输出余量**：最容易被忘掉的一块。

模型要说话，话也要占位置。

输入把窗口塞满，输出就会被截断。

截断的样子很难看：JSON 少一个右括号，回答停在半句。

一句经验：

```text
输入预算 = 窗口 - 你希望这次输出多长
```

不是「窗口 - 一点余量」。

是你心里得有一个输出的目标长度。

输出被截断的样子有两种。

```text
硬截断：JSON 少一个右括号，解析直接失败。你马上知道出事了。
软截断：话停在"因此我们可以得出"后面。没人知道它本来要说什么。
```

第二种更常见。

因为你没设输出上限，模型自己决定在哪停。

它停的地方通常不是你想停的地方。

所以「留给输出的空间」要落成一个具体数字。

```text
要它输出一段 300 字的回答 → 留 500 token
要它输出一条 JSON 记录     → 按字段数估，留 800 token
要它写一份完整报告         → 这个任务本身就不该把历史塞满
```

一句：

```text
上下文预算不是"能塞多少塞多少"。
是"先扣掉输出，再决定输入"。
```

量级上，一个普通对话 agent 大概是：

```text
system        5% ~ 15%
工具 schema   5% ~ 20%（工具越多越高）
历史         40% ~ 70%
本次输入      1% ~ 5%
输出余量     10% ~ 25%
```

这些比例不是标准，只是让你有个手感。

真实项目里，历史那一格通常最先爆。

因为它在长。

算一遍，手感会更实。

假设这次请求的窗口是 8k token，你要塞进去的东西是：

```text
system（一段 300 字的规矩）          ≈ 300 token
两个工具的 schema                     ≈ 400 token
6 条历史（两轮工具调用加结果）         ≈ 500 token
用户这一句                            ≈ 40 token
------------------------------------------------
输入合计                              ≈ 1,240 token
留给输出                              ≈ 6,760 token
```

这个例子里，输入占了不到两成。

再往前走 20 轮。

历史从 500 涨到 5,000，输入就到 5,700 左右。

输出余量从 6,760 掉到 2,300。

再往后，历史 7,700。

输入已经超过窗口。

请求发不出去。

爆掉的样子不壮观。

它不会在代码里抛异常。

它只是某一次请求返回 400，报错大意是超过了最大上下文长度。

或者更阴：刚好塞得下，输出被截在半句。

## 3. 用 run.py 场景 1 把 messages 走一遍

先看真实的代码。

代码来源：

```text
labs/L01_agent_loop/run.py
```

```python
messages = [
    Message("system", SYSTEM),
    Message("user", "帮我算一下 (12 + 8) * 3 等于多少？"),
]
```

这时候是 2 条。

一条 system，一条 user。

然后 `run_agent` 开始跑。

代码来源：

```text
labs/L01_agent_loop/agent.py
```

```python
reply = model.chat(messages)
messages.append(reply)

if not reply.tool_calls:
    return reply.content

for call in reply.tool_calls:
    observation = _execute(call, tools)
    messages.append(
        Message(role="tool", content=observation, tool_call_id=call.id)
    )
```

每一步，这个列表长两条：一条 assistant，一条 tool。

把镜头放慢，看它怎么从 2 条长到 7 条。

```text
发第 1 次之前（2 条）
  [0] system      "你是一个会使用工具的中文助手……"
  [1] user        "帮我算一下 (12 + 8) * 3 等于多少？"

第 1 步跑完（4 条）
  [2] assistant   tool_calls: s1_a → calculator("12 + 8")
  [3] tool        "20"                       tool_call_id: s1_a

第 2 步跑完（6 条）
  [4] assistant   tool_calls: s1_b → calculator("20 * 3")
  [5] tool        "60"                       tool_call_id: s1_b

第 3 步跑完（7 条）
  [6] assistant   "结果是 60。"
```

跑完之后 `run.py` 会打印：

```text
>> 历史里现在有 7 条消息： ['system', 'user', 'assistant', 'tool', 'assistant', 'tool', 'assistant']
```

七个位置，四个角色。

注意几件事。

第一，第 5 条 tool 消息里是 `"60"`，不是 `"60"` 这个数字。

工具返回值被 `str()` 过一遍，观测永远是字符串。

第二，`assistant` 出现了三次。

其中两次 `content` 是空的，只有 `tool_calls`。

这是协议允许的，[01 篇](/posts/agent-model-message-contract/)说过。

第三，模型从来没有「记住」过任何东西。

第 3 步它能写出「结果是 60」，是因为你把这 6 条历史又发了一遍。

```text
它看到的不是"上一步的结果"。
它看到的是"从第 0 条到第 6 条的全部"。
```

接着问一个细节。

**为什么一次工具调用要占两条消息？**

有人会想：合成一条不行吗，反正内容都在。

不行。

合成一条，你就分不清「这句话是模型说的」还是「这句话是工具算的」。

模型说的可能是编的，工具说的是它自己算的。

```text
assistant  我要算 12 + 8
tool       20
```

两条消息，两种可信度。

一条消息，可信度混在一起，下次裁剪你就不知道该不该删它。

还有一个更实际的原因：一轮里可能有多个调用。

```text
assistant  tool_calls: [q1, q2, q3]
tool       q1 的结果
tool       q2 的结果
tool       q3 的结果
```

三个结果得各自对应回一个请求。

所以它们是三条独立的消息，各自带 `tool_call_id`。

一条消息装不下三个编号。

这是 [04 篇](/posts/agent-tool-call-loop/)讲过的形状：一个请求配一条观测。

第四，这 7 条里只有 2 条是人写的。

`system` 是你写的，`user` 是用户写的。

剩下 5 条，全是模型和工具产出的。

所以「上下文工程」听起来像编辑工作，不是错觉。

你确实在编辑一份别人写的稿子，而且每一轮都要重新排版。

这就是上下文工程的入口：

这 7 条里，哪几条下一次还值得发？

## 4. 三种裁剪策略

历史长了，只有三条路可走。

### 4.1 只留最近 N 条

最直觉的一种。

```text
messages = messages[-8:]
```

或者保留 system，剩下的取尾巴：

```text
messages = messages[:1] + messages[-8:]
```

优点：一行代码，永远不超预算。

失效场景：任务目标在第 2 条。

到了第 10 轮，它早就被扔了。

模型开始很认真地算一个表达式，但它不知道这个表达式是为了什么。

它可能把中间结论当成最终答案交回来。

它可能忘了你要求「用中文回答」。

它可能忘了「不要动 production 数据库」。

这种失败最难查。

因为每一步看起来都对。

**反直觉的点：模型「忘了」任务目标，多数时候不是窗口不够，而是你在裁剪时把开头那句删了。**

### 4.2 保留首尾

比第一种聪明一点。

```text
messages = messages[:2] + messages[-6:]
```

开头两条：system 和最初的 user。

最后六条：最近的上下文。

失效场景：中间那一大段工具链。

假设任务是「先查 A 表，再根据 A 的结果查 B 表，最后汇总」。

模型在第 8 步的时候看不到第 3 步查到的 A。

它有三种反应，全都很糟：

```text
重查一遍（浪费钱，还可能查到不一样的数）
以为没查过（重新规划，把已完成的步骤再做一次）
编一个 A（最糟，它会用"大概是"来填空）
```

第三种不是危言耸听。

历史里出现空洞时，模型的默认行为是补一个听起来合理的东西。

### 4.3 摘要 + 最近 N 条

中间那段不是删，是压。

```text
summary = model.chat("把这以下历史压缩成 200 字要点：" + 中间那段)
messages = [system] + [user: summary] + messages[-6:]
```

优点：信息密度高，能保住长任务的主线。

失效场景有三个。

```text
一、摘要有损，而且损失不可预测。数字、路径、ID、报错原文最容易被摘成"进行了若干次计算"。
二、摘要要额外调一次模型。每一轮都摘要，延迟和费用都翻倍。
三、摘要会把"未完成"的状态摘没。"正在等 B 表返回"这种状态，很容易被写成"已查询相关数据"。
```

第三条最致命。

模型以为自己已经做完了。

工程上的常见做法是：摘要不每轮做，只在历史超过阈值时做一次，然后把摘要固定下来。

```text
历史 < 60% 预算 → 不动
历史 > 60% 预算 → 摘要一次，丢弃原始中段
```

阈值不是重点。

重点是**摘要这个动作本身要被记录**。

不然后面查 bug 的时候，你不知道模型看到的是原文还是摘要。

### 4.4 策略不是单选题

真实项目里不会只用一种。

常见的组合是这个。

```text
开头：system + 最初的任务目标（永不裁）
中间：超过阈值就压成结构化笔记（不是散文）
结尾：最近 N 条，且不拆散 tool 调用对
```

再加一条时机规则。

```text
每轮都检查长度。
只有超过阈值才动手。
没超就别裁 —— 裁剪本身也有风险。
```

「没超就别裁」值得多说一句。

有些人一开始就写死 `messages[-10:]`。

历史只有 4 条的时候，它什么也不做，看起来没问题。

到了 40 条，它每轮都在删。

删什么、什么时候删，应该由长度决定，不由代码里那个数字决定。

还有一个决定要提前想清楚：裁剪发生在哪一侧。

```text
删中间：保住目标和最近状态，丢掉过程
删前面：保住过程，丢掉目标
删后面：几乎总是错的，最近的消息最该留
```

三条里，只有「删中间」是常见正确解。

因为它同时保住了两头注意力最强的地方。

### 4.5 第四种做法：不裁，改形状

除了删和压，还有一条路：改消息的形状。

不是保留 60 条，而是从一开始就不产生 60 条。

具体做法：

```text
每轮结束，把"这一轮发生了什么"写成一条结构化消息。
这一轮的原始消息直接丢掉。
messages 永远只有：system + 目标 + 笔记 + 最近一轮。
```

这样长度恒定。

代价是模型看不到原始观测，只能看到你写下的摘要。

好处是 token 可预测，你随时能算出发出去多少。

什么时候适合？

```text
适合：步骤重复、结论比过程重要的任务（巡检、批量处理、抽取）
不适合：需要精确回溯的任务（调试、审计、反复改口）
```

一句判断：

```text
如果模型从来不需要"再看一眼原始数据"，就别留原始数据。
```

这条和「保留首尾」不冲突。

它们是两种不同的取舍：一个裁的是长度，一个裁的是形状。

## 5. 什么绝对不能丢

三种策略都在删东西。

但有些东西删了，agent 就不是变笨，是变质。

五类不能丢。

```text
1. 任务目标
2. 已经确认的结论
3. 未完成的工具调用链
4. 硬约束（输出格式、禁止的动作、权限边界）
5. 用户最近一次修正
```

一条一条说。

**任务目标**：用户最初那一句，或者他最后一次改口之后的目标。

这句话通常只有一行。

留一行不贵。

丢了它，后面所有推理都在服务一个不存在的问题。

**已经确认的结论**：算出来的数、查到的路径、定下的方案。

注意「确认」两个字。

模型自己猜的不算。

工具返回的、用户说的、你程序算的，才算。

**未完成的工具调用链**：一轮里模型发了三个 `tool_calls`，你只执行了一个，剩下两个还没回来。

这时候裁掉前面那条 `assistant(tool_calls)`，剩下两条 `tool` 结果就是孤儿。

真实 API 会直接 400。

报错大意是：`tool` 消息必须回应前面带 `tool_calls` 的消息。

**硬约束**：输出必须是 JSON、不许调用删除类工具、金额单位是分不是元。

这类东西写起来很短，破坏力很大。

**用户最近一次修正**：「刚才说的那个城市，改成上海」。

这一条要覆盖历史里所有相反的说法。

裁剪的时候，前面的「我在杭州」可以丢。

后面这句不能丢。

一句判断标准：

```text
删掉这条，模型会不会做出一件"你明确说过不要做"的事？
会 → 不能删。
```

举个具体现场。

第 9 步，模型一次发了三个调用。

```text
assistant  tool_calls: [q1, q2, q3]
tool       q1 → "库存 12"
tool       q2 → "价格 30"
tool       q3 → "错误：仓库接口超时"
```

`q3` 失败了。

第 10 步，模型基于「q3 超时」决定改用另一个接口。

这时候如果你把 `q3` 那条观测裁掉，只留 `q1`、`q2`：

模型会看到「库存 12、价格 30」，然后假设仓库也有货。

它不会知道自己曾经失败过。

它会把一个不确定的结论，当成确定的说出来。

这一类错误在日志里几乎看不出来。

因为每一步的输出都很像样。

这就是为什么「未完成的工具调用链」要单独列一条。

它不是历史，它是**状态**。

状态丢了，agent 会退回到一个更早的、看起来更干净的世界里。

反过来问一句：什么可以放心丢？

```text
寒暄（"好的""收到""谢谢"）
重复的确认（同一个结论被复述了三遍）
已经被结论吸收的中间过程（算完的原始表达式）
失败的尝试，且已经被新方案取代
```

最后一条要小心。

「试过 A 接口，超时」这句话要留。

重试三次的完整 traceback 可以丢。

一句：

```text
过程可以丢，过程留下的结论不能丢。
```

## 6. 顺序效应：开头和结尾最强

同一个信息，放在不同位置，被用到的概率不一样。

这不是玄学，是注意力的分布。

公开研究里管中间那段叫「lost in the middle」。

```text
位置        注意力
开头  ██████████  强
中间  ███         最容易丢
结尾  █████████   强
```

对工程的三条直接推论。

第一，硬约束写两遍。

system 里写一次，最后一条 user 里再写一次。

```text
system: 输出必须是 JSON，字段 name / price / stock。
...
最后一个 user 消息: 记得，只输出 JSON。
```

听起来很傻。

但它有效，而且比「把 system 写得更长」有效。

第二，把进度贴在末尾。

不要指望模型自己从 40 条历史里总结出「现在做到第几步」。

你在末尾追加一条：

```text
[进度] 目标：(12+8)*3
已完成：12 + 8 = 20
下一步：计算 20 * 3
```

这条消息是给模型看的，不是给用户看的。

第三，关键 ID 不要埋在中间。

订单号、文件路径、`tool_call_id`，都往两头放。

**反直觉的点：把 30 条历史一字不删地全发过去，效果常常不如「开头两条 + 一条结构化进度 + 最后六条」。**

因为多出来的那些消息，不是在中性地「提供信息」。

它们在稀释注意力。

### 6.4 一次请求的实际排布

把这些规则落到一次请求上，长这样。

```text
[system]
  你是谁
  硬约束（输出格式、禁止项）
  可用工具的一句话说明

[system 或 user]
  从长期记忆里召回的相关几条

[user]
  最初的任务目标（原话，不要改写）

[assistant / tool ...]
  最近 N 条，成组出现的工具调用

[user]
  当前进度：已完成什么，下一步做什么
  再说一遍硬约束
```

注意最后那条 `user`。

它明明是「系统写给模型的」，却用 `user` 角色。

为什么？

有的接口对连续多条 system 消息的处理不一致，对 user 消息最宽容。

以你要用的模型文档为准。

排布的价值在于：不改任何逻辑，只改拼接顺序，输出就会变。

## 7. 把长历史压成结构化笔记

摘要这个词容易误导。

它听起来像写作文：把一堆事写成一段通顺的话。

不要写成散文。

写成字段。

```json
{
  "goal": "算出 (12 + 8) * 3",
  "constraints": ["用中文回答", "只用 calculator 工具"],
  "done": ["12 + 8 = 20", "20 * 3 = 60"],
  "open": [],
  "next": "给出最终答案",
  "pointers": ["tool_call_id: s1_a", "tool_call_id: s1_b"]
}
```

为什么字段化比散文好，三条。

**可校验**：`goal` 空了，程序能发现。一段散文里目标丢了，没人看得出来。

**可增量更新**：做完一步，往 `done` 里追加一项，从 `next` 里改一行。不用重写全文。

**可丢弃**：`open` 空了，整块可以安全删掉。散文你不知道哪句还有用。

还有一个字段值得单说：`pointers`。

它是回捞用的。

压缩会丢细节，但你要留一根线，能在需要时回到原文。

```text
摘要里写："12 + 8 = 20（见 s1_a）"
需要时按 s1_a 去原始日志里捞完整观测
```

这就是「有损压缩 + 指针」的常规做法。

它比「无损压缩」现实得多。

因为无损压缩在上下文里不存在。

### 7.4 笔记怎么更新

笔记是活的，每一步都要动。

不是让模型重写全文。

是三个动作，按顺序。

```text
1. 从这一步的观测里，抽出"新的结论"
2. 追加到 done
3. 把 next 改成下一步
```

走一遍。

第 1 步之前：

```json
{"goal": "算出 (12 + 8) * 3", "done": [], "open": [], "next": "计算 12 + 8"}
```

第 1 步之后：

```json
{"goal": "算出 (12 + 8) * 3", "done": ["12 + 8 = 20"], "open": [], "next": "计算 20 * 3"}
```

第 2 步之后：

```json
{"goal": "算出 (12 + 8) * 3",
 "done": ["12 + 8 = 20", "20 * 3 = 60"],
 "open": [], "next": "给出最终答案"}
```

三次更新，每次都只动两个字段。

这就是结构化笔记的好处：更新是覆盖字段，不是重写文章。

谁来做这个更新？

两种选择。

```text
规则：你知道工具返回什么，自己拼。便宜、确定、只适合简单任务。
模型：把这一步的观测丢给模型，让它输出新的笔记。灵活、多一次调用、可能写错。
```

模型那一路，其实就是 08 篇要讲的结构化输出。

笔记本身也是一个 schema：`goal` / `done` / `open` / `next` 四个必填字段。

校验不过，说明笔记坏了，不是任务坏了。

## 8. 多给上下文为什么反而更差

直觉是：信息越多，判断越准。

在 agent 里，这条不成立。

四个机制。

**噪声**：无关片段会改变模型的注意力分配。

它们不是「不参与」，而是「参与了但没用」。

它们会出现在模型的理由里，变成奇怪的限定条件。

一个具体的例子。

用户问：「这套方案能不能上生产？」

你检索了 20 段文档。

2 段讲部署要求，18 段讲历史事故。

模型很可能给你一个以「风险很大，建议再评估」开头的回答。

那 18 段没有回答问题。

但它们改变了回答的形状。

**冲突指令**：历史里有一句「回答尽量简短」，第 15 轮用户说「详细讲讲」。

两条都在上下文里。

模型会给你一个又长又压缩的东西。

**成本**：输入按 token 计费。

每一轮都发 60 条历史，第 30 轮的费用是第 1 轮的很多倍。

**延迟**：输入越长，首 token 越慢。

用户等的是「它开始说话」的那一秒。

一句总结：

```text
上下文的收益是递减的。
成本是线性甚至超线性的。
两者的交叉点，比你以为的靠左。
```

所以「多给点上下文」不是一个安全动作。

它是一次有代价的取舍。

## 9. 裁剪是对协议的操作

这是这一篇最硬的一节。

前面所有策略，看起来都像在操作一个「字符串列表」。

不是。

`messages` 是一个**有引用关系的结构**。

```text
assistant(tool_calls: [s1_b])
        │
        └── tool(tool_call_id: s1_b)
```

这条边不能断。

断了会得到两种残骸。

```text
形状一：孤儿观测
  [2] tool  "20"   tool_call_id: s1_a     ← 它的 assistant 被删了
  模型看到一条没有请求的结果。

形状二：悬空调用
  [4] assistant  tool_calls: [s1_b]        ← 它的 tool 结果被删了
  模型看到一个没有结果的请求，可能下一轮重复执行。
```

形状一在真实 API 上通常直接失败。

OpenAI 那边会返回 400，大意是 `tool` 消息必须跟在带 `tool_calls` 的 `assistant` 消息后面。

在假模型上呢？

`ScriptedModel` 根本不看 `messages` 的内容，它按剧本吐。

所以这种 bug 在 L01 里完全测不出来。

这是教学顺序的必然：你先把循环跑通，再学协议约束。

但接真模型那天，它会一次性全部还给你。

报错长这样（大意）：

```text
400 Bad Request
messages[3] with role 'tool' must be a response to a
preceding message with 'tool_calls'
```

读到这句，你要做的不是改 prompt。

是回去看裁剪函数的切点。

这类错误有个共同特点：

```text
只在接真模型后出现。
只在历史变长后出现。
只在代码里有裁剪逻辑时出现。
```

三个条件同时满足才复现。

所以它很难在开发阶段撞上。

一句经验：

```text
只要代码里有 messages[-N:] 或 messages[:N]，
就该有一条测试专门检查切点。
```

一句判断：

```text
裁剪的最小单位不是「一条消息」。
是「一个 assistant + 它全部的 tool 结果」。
```

一轮里模型发了 3 个 `tool_calls`，这 4 条消息（1 + 3）必须同进同出。

要么全留，要么全删。

没有中间态。

## 10. 一个能用的裁剪函数

下面这个函数，输入是 `run.py` 场景 1 跑完的那 7 条消息。

```python
from agent import Message


def trim(messages, keep_recent=4, keep_head=1):
    """保留前 keep_head 条（通常是 system）+ 最近 keep_recent 条。

    唯一的硬约束：尾部不能从一条 tool 消息开始。
    """
    n = len(messages)
    if keep_recent >= n:
        return list(messages)

    start = max(n - keep_recent, keep_head)

    # 切点落在 tool 上，说明它的 assistant(tool_calls) 被切走了
    # 往前退，直到退到那句 assistant —— 这一组同进同出
    while start > keep_head and messages[start].role == "tool":
        start -= 1

    return messages[:keep_head] + messages[start:]
```

把 7 条历史喂进去，`keep_recent=4`：

```text
n = 7
start = max(7 - 4, 1) = 3
messages[3].role == "tool"   → start = 2
messages[2].role == "assistant" → 停
结果 = messages[:1] + messages[2:] = 6 条
```

留下的 6 条：

```text
['system', 'assistant', 'tool', 'assistant', 'tool', 'assistant']
```

你要的是 1 + 4 = 5 条。

实际留下 6 条。

多出来那一条，就是 `assistant(tool_calls: s1_a)`。

**协议优先于预算。**

这个「超出预算」是有意的。

如果连退都退不了（比如 `keep_head` 本身就卡在一条 tool 消息上），函数会原样返回。

那说明你的起始历史本身就是坏的。

让它报错比让它悄悄截断好。

再看一个并行调用的例子。

`check.py` 的 C 项里，一轮发了两个 `tool_calls`：

```text
['system', 'user', 'assistant', 'tool', 'tool']
```

`keep_recent=2` 时，切点在最后一条 tool 上。

退一步，退到 `assistant`。

结果还是 4 条：`['system', 'assistant', 'tool', 'tool']`。

两条观测一起留下。

这就是「最小单位是一组」的具体含义。

这个函数只有 15 行。

它没有做摘要，没有做排序，没有做打分。

它只做了一件事：不把协议拆散。

剩下的事，都可以后面再加。

### 10.1 怎么测这个函数

手动看输出不够。

你需要的是一条断言：结果里不能有孤儿观测。

```python
def assert_no_orphan(messages):
    seen = set()
    for m in messages:
        if m.role == "assistant":
            seen |= {c.id for c in m.tool_calls}
        if m.role == "tool":
            assert m.tool_call_id in seen, f"孤儿观测：{m.tool_call_id}"
```

然后拿它刷一批输入。

```python
for keep in range(1, 10):
    assert_no_orphan(trim(history, keep_recent=keep))
```

更狠一点：把每一种切点都试一遍。

```text
拿一段 40 条的历史，keep_recent 从 1 试到 39。
任何一个数字都不许出现孤儿。
```

这个测试只有 8 行。

它挡住的是一类只在线上出现的 400。

顺手也测一下「悬空调用」：结果里若最后一条带 `tool_calls`，后面必须跟着对应的 `tool`。

真模型上这会被当成「还没执行完」，然后一直等。

## 11. 容易混淆的点

**上下文 ≠ 记忆。**

上下文是这一次请求的输入。

记忆是你硬盘上的东西。

记忆不塞进上下文，等于不存在。

**裁剪 ≠ 摘要。**

裁剪是无损地删除整块。

摘要有损地重写。

前者可能丢关键信息，后者可能创造不存在的信息。

一种的失败是「它不知道」，另一种的失败是「它记错了」。

后者更难查。

**上下文窗口 ≠ 输出上限。**

窗口是输入 + 输出的总预算。

`max_tokens` 之类的参数只约束输出。

两个数字都要看。

**token ≠ 字符。**

中文、英文、代码、JSON，同样的字数换算出来的 token 差很多。

估算工具要用你目标模型自己的 tokenizer，别用别人的。

**「模型忘了」≠「模型不行」。**

九成情况下，是这一轮没发。

**历史长 ≠ 信息多。**

60 条消息里可能有 40 条是「好的」「继续」「明白了」。

这些不是上下文，是噪声。

**裁剪 ≠ 遗忘。**

裁剪是你主动做的一次选择。

遗忘是它发生了而你不知道。

前者可以复盘，后者只能猜。

**发出去 ≠ 看进去。**

历史在上下文里，不代表模型用上了。

中间那 20 条，物理上在里面，注意力上不在。

**裁剪掉 ≠ 忘了。**

这一轮删了，下一轮想再用，得从别处拿回来。

从哪拿？

从记忆里，07 篇那套东西。

## 12. 回到真实工程

`labs/` 里没有裁剪代码。

`run_agent` 是「全发」版本。

这是对的：第一课不该把两件事混在一起。

但你可以现在就在外面套一层。

接真模型的时候，裁剪的位置只有一处：

```text
拼 messages → 裁剪 → 发请求 → 收 reply → append → 再裁剪
```

不是「在 append 之前裁」。

因为 append 之后的那一瞬间，`messages` 才是完整的一轮。

还有三件工程上的事。

**第一，记录裁剪。**

真实的 API 响应里通常带 usage 字段，形如 `prompt_tokens` / `completion_tokens`。

把裁剪前后的条数、估算 token、实际 `prompt_tokens` 一起写进日志。

不然你永远不知道「它为什么变笨了」。

**第二，保留原始历史。**

裁剪后的 `messages` 是发出去的。

原始的历史是给调试用的。

两份都留。

出问题时，你要能回答「它当时到底看到了什么」。

**第三，裁剪要可复现。**

阈值、策略、摘要的 prompt，都写进配置。

不要让它取决于「这次跑的时候历史刚好有多长」。

14 篇（可观测性与成本）会把 trace 讲细，那时再回来看这一节。

这里先记住一条：

```text
裁剪是这个系统里最容易被忽略的、会改变行为的动作。
```

它不报错。

它只是让输出慢慢变差。

**第四，裁剪和记忆分工。**

裁剪管这一次，记忆管跨次。

一个东西该不该留，先问它活多久。

```text
活一次请求 → 属于上下文，不用管
活一次会话 → 属于 messages，靠裁剪
活很多次会话 → 属于记忆，靠写入
```

三层混在一起，会出两种错。

```text
把长期偏好塞进 messages 末尾（每轮重发，白花钱）
把当前任务的中间结果写进 memory.md（三个月后还在污染召回）
```

落到代码上，只在 `run_agent` 里改一行：

```python
reply = model.chat(prepare(messages, budget=8000, reserve_output=800))
```

`prepare` 就是这一篇所有规则的落点：先留头，再留尾，不拆组，最后按上限收敛。

## 13. 读代码时怎么判断

看到一段 agent 代码，问五个问题。

```text
1. 它把哪些消息发给了模型？全发还是有裁剪？
2. 裁剪的切点在哪？会不会落在 tool 消息上？
3. 任务目标在哪里？裁剪之后还在不在？
4. 摘要怎么写的？有没有保留指针？
5. 裁剪之后重新算过 token 吗？还是用一个旧数字？
```

第五个问题很多人漏。

裁剪完不重算，等于没裁。

因为你不知道省了多少，也不知道还够不够。

还有一个更根本的问题：

```text
这段代码，有没有一个地方叫「拼装这一轮的上下文」？
```

有，说明作者想过这件事。

没有，说明它是 `messages.append` 一路 append 到底。

那种代码能跑 demo，跑不了长任务。

读框架源码时，可以按这三处找。

```text
它在哪里构造 messages？        —— 通常在调用模型的前一行
它有没有 token 预算相关参数？  —— max_tokens 只是输出，别搞混
它的裁剪里有没有判断 role？    —— 有没有意识到 tool 消息不能单独出现
```

第三条最关键。

有，说明作者踩过那个 400。

没有，说明它只在短对话上测过。

你甚至可以由此判断一个实现的成熟度。

```text
短对话能跑      → 循环写对了
长对话能跑      → 裁剪写对了
长对话 + 工具   → 协议处理对了
```

三层，测试成本递增，出错代价也递增。

## 14. 小结

这一篇讲的是：历史变长之后，你每一轮都要做一次决定。

```text
上下文不是记忆，是预算。
预算被五块瓜分，历史是最大也最能动的那块。
三种裁剪策略，各有各的失效方式。
任务目标、已有结论、未完成的工具链、硬约束、最近修正，不能丢。
开头和结尾注意力最强，中间最容易丢。
长历史要压成字段，不是压成散文。
多给上下文有成本，而且会稀释注意力。
裁剪是在操作一个有引用关系的结构，不能拆散 assistant(tool_calls) 和它的 tool 结果。
```

一句话版本：

```text
裁剪的目标不是「留下最重要的信息」。
是「留下最重要的信息，同时保持协议合法」。
```

下一篇处理另一个方向的同一个问题。

这一篇问的是：这一轮发什么。

下一篇问的是：会话结束了，下次怎么还记得。

```text
Agent 系统讲解 07：记忆，从 messages 到跨会话
```

那一篇里有一个反直觉的结论：

大多数 agent 记不住，不是检索不行。

是根本没写进去。
