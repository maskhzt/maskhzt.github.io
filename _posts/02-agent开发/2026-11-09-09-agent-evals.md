一个读者贴过来一段 system prompt。

两千三百字。

他问：还能再加一句吗。

我问：加完之后，你怎么知道它变好了。

他说：跑几个例子看看。

跑几个例子。

这句话里藏着后面所有问题的种子。

## 1. 改了一行 prompt，然后呢

场景很常见。

你发现 agent 把「12 除以 4」算成了 4。

你看了一眼 prompt，加了一句：

```text
需要算数时，必须先调用 calculator 工具，不许心算。
```

再跑三次，三次都对。

你觉得修好了。

一周之后，另一个用户报：问它「帮我看看这段代码有什么问题」，它不回答，直接调了 calculator。

因为那句「需要算数时必须调用工具」，被模型理解成了「不确定的时候先调个工具」。

你的修改确实修好了 A。

它同时把 B 弄坏了。

而你在修改的那一刻，**没有任何东西能告诉你 B 坏了**。

这不是 prompt 写得不好。

这是你缺一个对照组。

再说清一点，「三次都对」为什么不算证据。

三次采样只能说明：在这三个输入上，这一次的输出撞对了。

它当时用的模型版本、当时那句 prompt、当时上下文里的历史，全都不可复现。

明天你改一个字，这三次里过一次、两次、三次，你都无法区分是改动有效还是抽样变了。

对照组不是「多试几次」。

对照组是：同一批输入、同一套判分、先后两个版本，各跑一遍，对比结果。

少任何一个要素，你得到的都不是证据，是印象。

## 2. 凭感觉调，会陷进三个死循环

### 2.1 死循环一：改 A 坏 B

prompt 是一整个字符串。

它不是十个独立开关，是一条被模型整体读进去的指令。

你加一句「必须调用工具」，改的不只是算数行为。

它同时改了：模型的谨慎程度、它对「不确定」的处理、它愿不愿意先问一句。

一句话，十几个行为同时移动。

而你的观察样本是三次手工试跑。

三次里看不见的行为，就当没发生。

于是你进入第一个循环：

```text
改 A → A 好了，B 坏了但你不知道
改 B → B 好了，A 又坏了
再改 A → 这次两个都坏了，而且你不知道是哪一句导致的
```

三个月后，prompt 变成四千字，每一句都是为了修上一句造成的伤。

没有人敢删任何一句。

因为删了不知道会坏什么。

### 2.2 死循环二：不可复现

第二个循环更隐蔽。

你今天跑了一次，通过了。

明天跑同样的问题，不通过。

为什么？

```text
temperature 不为 0，采样本来就不同
模型服务端悄悄换了版本
上下文里多了一段历史，长度变了
工具返回的字符串顺序变了
你自己改了一行无关代码，消息顺序动了
```

只要其中任何一条成立，你今天的结论就不成立。

最要命的不是它不稳定。

是你**只跑了一次**，就把这一次当成了期望值。

跑一次通过叫运气，跑一次失败叫 bug —— 这是两种完全不同的判断，却用了同一个动作。

### 2.3 死循环三：无法比较两版

第三个循环是结构性的。

你手上有 prompt_v3 和 prompt_v4。

你想知道哪个好。

你打开 v3 试了五个问题，又打开 v4 试了同样五个问题。

然后你开始回忆：刚才 v3 第三个问题是怎么答的来着？

人脑存不住二十条输出。

你实际在比的是「哪个版本给我的印象更好」。

而印象会被最近一次失败主导。

于是你选了一个「感觉更稳」的版本。

这个决定和抛硬币的区别，只在于你为它编了一个理由。

三个循环指向同一件事：

```text
你不是需要更准的直觉。
你是需要一把不动的尺子。
```

## 3. eval 的最小形态：三件东西

评测（eval）这个词被用得很大。

最小形态其实只有三件东西：

```text
一组固定的输入
一个能判对错的函数
一个通过数
```

就这样。

不需要框架，不需要向量库，不需要数据库，不需要实验平台。

一个 `.py` 文件，二十条用例，一个 `if`。

把这三件东西拼起来，你会得到一行输出：

```text
15/20
```

这一行就是你的尺子。

它的价值不在绝对值。

15 分不高，也不低，它只是一个坐标。

价值在**下一次**：改动之后跑一遍，变成 17/20。

那一刻你第一次拥有了「变好了」这个判断，而不是「感觉变好了」。

### 3.1 为什么先要布尔，不要分数

新手最容易在这里走偏。

一上来就想设计一个 0 到 100 的综合评分。

答案相关性 40%、工具正确性 30%、格式 20%、语气 10%。

加权求和。

看起来很专业。

然后你发现分数从 82 掉到 79，你不知道是哪一项掉的，因为权重把差异抹平了。

正确的顺序是反的：

```text
先让每条用例只能 PASS 或 FAIL。
先让总数能回答"有没有坏"。
再考虑给失败分类、给类别单独算分。
```

布尔判分逼你把「好」写成一句能被机器检查的话。

写不出来，说明你自己也没想清楚。

**反直觉的点在这里：**

> eval 写的不是「测试」，是你对「好」的定义。
> 定义不清，数字再好看也没用。

测试是"实现对不对"，eval 是"什么叫好"。

前者有标准答案，后者没有。

所以 eval 的第一步不是写代码，是把"好"写成一句能被机器检查的话。

### 3.2 为什么是 20 条

20 不是一个魔法数字。

它是一个工程折中。

```text
少于 10 条：改一次可能全过，什么都没测到
20 条左右：改完立刻能跑，几十秒出结果，你愿意每次都跑
100 条以上：开始有统计意义，但你不会每次改都跑
```

真正的约束不是数量，是**你必须愿意每次都跑**。

一个 200 条但你三周才跑一次的 eval，等于没有。

一个 20 条但你每改一行都跑的 eval，才是护栏。

数字先小，用例先真。

## 4. 最小代码：一个 40 行的 evals.py

下面这份能直接跑，不联网，不需要 API key。

它复用了 `labs` 里的假模型。

代码来源：

```text
labs/L01_agent_loop/fake_llm.py
```

```python
class ScriptedModel:
    """按剧本逐条吐回复的假模型。剧本用完就报错（说明你的循环步数和预期不一致）。"""

    def __init__(self, script: list):
        self._script = list(script)
        self._turn = 0

    def chat(self, messages: list[Message]) -> Message:
        if self._turn >= len(self._script):
            raise RuntimeError(
                f"剧本只有 {len(self._script)} 幕，但循环还要第 {self._turn + 1} 幕。"
            )
        item = self._script[self._turn]
        self._turn += 1
        return item(messages) if callable(item) else item
```

eval 骨架长这样。

代码来源：

```text
labs/L01_agent_loop/evals.py（本篇新建，放在 L01 目录下即可运行）
```

```python
from dataclasses import dataclass
from agent import Message, run_agent
from fake_llm import ScriptedModel, last_tool_result, tool_call
from tools import TOOLS

SYS = "你是会使用工具的助手。需要算数时调用 calculator。"


@dataclass
class Case:
    name: str
    user: str
    script: list          # 这一条用例的剧本（换成真模型时删掉，直接调 model.chat）
    want: str             # 判分依据：期望出现在最终答案里的关键事实


def _script(expr: str, broken: bool) -> list:
    if broken:            # 故意做坏的一版：不调工具，直接编一个答案
        return [lambda m: Message("assistant", "这个我算不出来")]
    return [tool_call("calculator", expression=expr),
            lambda m: Message("assistant", f"结果是 {last_tool_result(m)}")]


ROWS = [("1 + 1", "2", 0), ("12 + 8", "20", 0), ("7 * 6", "42", 0),
        ("100 / 4", "25", 0), ("9 - 4", "5", 0), ("(12 + 8) * 3", "60", 0),
        ("2 ** 10", "1024", 0), ("17 % 5", "2", 0), ("8 / 2", "4", 0),
        ("3 * 3", "9", 0), ("45 + 55", "100", 0), ("144 / 12", "12", 0),
        ("10 + 10", "20", 0), ("99 - 33", "66", 0), ("81 / 9", "9", 0),
        ("6 * 7", "42", 1), ("13 + 29", "42", 1), ("5 - 8", "-3", 1),
        ("7 / 2", "3.5", 1), ("2 * 3 * 4", "24", 1)]      # 最后 5 条故意坏掉

CASES = [Case(f"计算 {e}", f"{e} 等于多少", _script(e, bool(b)), w) for e, w, b in ROWS]


def run_case(c: Case):
    msgs = [Message("system", SYS), Message("user", c.user)]
    answer = run_agent(ScriptedModel(c.script), TOOLS, msgs, max_steps=4, verbose=False)
    used = [m for m in msgs if m.role == "tool"]          # 顺手采一层轨迹
    return answer, used


def score(c: Case, answer: str, used: list) -> bool:
    if not used:                     # 该调工具却没调：工具选择这层直接判失败
        return False
    return c.want in answer          # 最终答案里必须出现关键事实


if __name__ == "__main__":
    passed = 0
    for c in CASES:
        answer, used = run_case(c)
        ok = score(c, answer, used)
        passed += ok
        print(f"{'PASS' if ok else 'FAIL'}  {c.name}  -> {answer}")
    print(f"\n{passed}/{len(CASES)}")
```

整个文件 55 行，其中 20 条用例的数据占 7 行。

逻辑骨架不到 40 行：一个 dataclass、一个跑用例的函数、一个判分函数、一个主循环。

Windows 终端里中文可能乱码。

在文件头加一行 `import console_setup` 就好，L01 目录里已经有这个文件。

跑出来的最后一行是：

```text
15/20
```

十五通过，五失败。

那五条是特意做成「模型不调工具、直接编答案」的。

也就是说这份代码不是演示「永远满分」，而是演示**失败能被看见**。

一个永远 20/20 的 eval 是坏 eval。

它测不出任何东西，只证明你的判分函数太松。

### 4.1 这份代码里每个字段为什么在

`Case.name` 用来在失败列表里认出是哪一条。

不要用序号当名字，`case_7` 三个月后没人知道它是什么。

`Case.user` 是你唯一该写死的输入。

如果一条用例的 `user` 里塞了三件事，那它是三条用例被压成了一条。

`Case.script` 是假模型时代的过渡物。

换成真模型后它会被删掉，`run_case` 里只剩一次 `run_agent` 调用。

留着它是因为：**先把 eval 的形状跑通，再接真模型**。

`Case.want` 是判分依据，不是标准答案。

它写的是「答案里必须出现的关键事实」，不是「一句话一字不差」。

这两者的区别决定了你的 eval 是能用还是天天误报。

### 4.2 为什么判分函数要接收轨迹

注意 `score(c, answer, used)` 的第二个参数。

表面上你只关心最终答案。

实际上你应该在同一个函数里，把「有没有调工具」「调了几次」一起判掉。

原因很简单：

```text
答案对了，但过程是错的 → 今天对，明天错
```

一个不调工具却蒙对答案的模型，在 eval 里必须算失败。

否则你会训练出一个「会猜」的系统，并且用它通过验收。

## 5. 一次 eval 跑的完整生命周期

把一次 eval 拆开，是七个动作。

```text
① 读用例集（固定文件，进 git）
        │
        ▼
② 每条用例：拼 messages（system + user）
        │
        ▼
③ 调 run_agent（带 max_steps 和超时）
        │
        ▼
④ 收集产物：final_answer / tool_calls / steps / tokens / latency
        │
        ▼
⑤ score() 判分：布尔 + 失败原因
        │
        ▼
⑥ 逐条写进 results.jsonl（可 diff 的文件，不是终端里滚过去的一屏）
        │
        ▼
⑦ 汇总：通过数 / 分区通过数 / 与 baseline 比
```

第三步和第四步之间，有一个容易被忽略的点。

`run_agent` 的返回值只有最终答案。

但你要测的东西不止答案。

代码来源：

```text
labs/L01_agent_loop/agent.py
```

```python
for step in range(1, max_steps + 1):
    reply = model.chat(messages)
    messages.append(reply)

    if not reply.tool_calls:
        return reply.content

    for call in reply.tool_calls:
        observation = _execute(call, tools)
        messages.append(
            Message(role="tool", content=observation, tool_call_id=call.id)
        )
```

这个循环丢掉了三样东西：

```text
走了几步
调了哪些工具、参数是什么
一共花了多少 token
```

所以你需要在循环外面再包一层，或者给 `run_agent` 加一个可选的 `trace` 参数。

不改 `agent.py` 也能测：

```python
def run_case(c: Case, model) -> dict:
    msgs = [Message("system", SYS), Message("user", c.user)]
    t0 = time.perf_counter()
    answer = run_agent(model, TOOLS, msgs, max_steps=c.max_steps, verbose=False)
    return {
        "case": c.name,
        "answer": answer,
        "passed": score(c, answer),
        "steps": len([m for m in msgs if m.role == "assistant"]),
        "tools": [t.name for m in msgs if m.role == "assistant" for t in m.tool_calls],
        "tool_ids": [m.tool_call_id for m in msgs if m.role == "tool"],
        "latency_ms": round((time.perf_counter() - t0) * 1000),
    }
```

`msgs` 就是那条追踪（trace）。

循环把每一步都写进去了，你只是从来没读它。

读完 `msgs` 你能回答：调了几次工具、有没有哪个 `tool_call_id` 没对上、模型在第几步开始重复。

一次 eval 的产物应该是一条 JSON：

```json
{"case": "计算 (12 + 8) * 3", "passed": true, "steps": 3,
 "tools": ["calculator", "calculator"], "latency_ms": 12}
```

字段名你自己定。

但一定要落盘。

落盘才能 diff，diff 才能回答「是哪一条变了」。

## 6. 用例从哪来

这是全篇最实际的一节。

用例的来源只有一个优先级：

```text
真实失败案例  >  你编出来的案例
```

编出来的案例有个通病：它们测的是你担心的东西，不是你实际踩到的东西。

你担心模型不会算数，于是编了十道算术题。

而线上真正失败的是「用户问『这个多少钱』，模型去调了 calculator，把价格字符串当表达式解析」。

你编不出来，因为它不合逻辑。

但它真实发生过。

所以用例的第一来源是失败本身：

```text
线上报错日志
用户重问、用户放弃的那一刻
你自己用的时候想骂人的那一次
review 别人 prompt 时发现的边界
```

### 6.1 一条 bug 一条用例

这条纪律听起来很笨，但它救过很多人。

一个 bug 修完，立刻写一条能复现它的用例。

规矩是：

```text
一条用例只测一个失败模式
用例失败时，你能一句话说出它为什么失败
```

如果你写完发现「这条用例可能是因为 A，也可能是因为 B」，那它其实是两条用例，你只是懒得拆。

不拆的代价：修好 A 之后它通过了，你以为 B 也好，其实 B 还在。

举个真实的例子。

线上日志里有这么一条：

```text
user: 这个套餐 199 打八折是多少
assistant: 我先帮您算一下
tool: calculator({"expression": "199 打八折"})
observation: 错误：SyntaxError: invalid character '打'
assistant: 抱歉，我不能处理这个请求
```

这里能拆出三条用例，不是一条：

```text
一条测"自然语言里的算术能不能先翻译成表达式"
一条测"工具报错后能不能换方案重试"
一条测"重试失败后能不能给出可读的解释，而不是道歉了事"
```

三条各自能单独变红。

合成一条，你永远不知道修好的是哪一段。

而且你会误判：换了 prompt 之后它答对了，你以为「自愈能力变好了」，其实只是第一步的翻译变好了，一次错误都没触发。

### 6.2 用例会腐坏

用例集不是写完就完的资产。

它会慢慢烂掉，原因有五个：

```text
模型升级，原来的行为变了 → 用例判失败，但其实是"更好了"
工具改名或改参数 → 用例调不动了
判分函数写得太死 → 措辞一变就误报
失败用例被删掉 → 回归保护消失
用例里写死了时间、随机数 → 明天跑就失败
```

每年清一次，每次改判分函数都重跑一遍全量。

删用例的理由只能是「它测的行为已经不存在了」。

不能是「它老是失败」。

### 6.3 不要把用例写成对实现的断言

这一条经常被违反。

比如你想测「模型会用工具」，就写：

```python
assert len(used) == 2
```

这条断言测的是实现，不是行为。

模型完全可以用一次工具算完整个表达式，结果更对、更快，但你的用例判它失败。

正确的写法是断言结果，外加一个宽松的过程约束：

```python
assert "60" in answer
assert 1 <= len(used) <= 3        # 调了，但没死循环
```

判断标准只有一句：

```text
这条断言，会因为"更好的实现"而失败吗？
```

会，就写错了。

## 7. 判分方式的谱系

判分函数不是只有一种写法。

它是一条谱系，从死板到灵活。

| 方式 | 适合什么 | 主要坑 |
|---|---|---|
| 精确匹配 | 标签、数字、枚举、固定格式 | 措辞一变就判错，中文标点空格全算差异 |
| 包含关键事实 | 开放问答题，答案有明确事实点 | 假阳性：关键词出现但结论相反 |
| 结构化字段比对 | 有 schema 的输出、工具参数 | 浮点容差、列表顺序、缺字段静默通过 |
| 语义相似度 | 同义改写多、句式自由的问答 | 相似不等于正确；换 embedding 模型分数不可比 |
| LLM-as-judge | 好坏、语气、有用性这类无法规则化的维度 | 有偏好、不稳定、必须给 rubric、必须锁版本 |

下面逐个说。

### 7.1 精确匹配

最省事的判分。

```python
def score(case, answer, used):
    return answer.strip() == case.want.strip()
```

适合的场景：答案是分类标签、数字、枚举、固定格式的 ID。

不适合的场景：任何自然语言回答。

模型说「等于 60」而你说「60」，它就失败了。

模型说「60。」（带句号），也失败。

所以精确匹配几乎总要配一步归一化：

```python
def norm(s: str) -> str:
    return re.sub(r"[\s，。、；：！？,.;:!?]", "", s.strip().lower())
```

归一化本身是个无底洞。

你每加一条规则，就在给某一类错误开后门。

比如你去掉空格，那「1 0」和「10」就分不出来了。

经验判断：精确匹配只用在**输出被 schema 约束过**的地方（08 篇讲过结构化输出）。

那里输出是字段，不是句子。

### 7.2 包含关键事实

开放问答最常用的写法。

```python
def score(case, answer, used):
    return all(fact in answer for fact in case.want_all)
```

坑在假阳性。

问：「这个套餐能退吗？」

正确答案：「不能退，超过 7 天不退。」

模型答：「不是不能退，要看情况。」

里面有「不能退」三个字，判分通过。

但结论是反的。

两种缓解办法：

```text
一、关键事实里带上否定词和主体，不要只放"退"
二、对结论类用例，加一条反向检查：答案里不能出现指定短语
```

```python
def score(case, answer, used):
    hit = all(f in answer for f in case.want_all)
    bad = any(b in answer for b in case.must_not)
    return hit and not bad
```

`must_not` 这个字段值得每条用例都留一个位置。

它是最便宜、最有效的假阳性过滤器。

### 7.3 结构化字段比对

当输出是 JSON，判分就变成逐字段比。

```python
def score(case, answer, used):
    try:
        got = json.loads(answer)
    except json.JSONDecodeError:
        return False                     # 解析失败本身就是一类失败
    for k, want in case.fields.items():
        if k not in got:
            return False
        if isinstance(want, float):
            if abs(got[k] - want) > 1e-6:
                return False
        elif got[k] != want:
            return False
    return True
```

三个必须处理的细节：

```text
浮点用容差，不要用 ==
列表要不要保序，先想清楚再写断言
多出来的字段算不算错 —— 建议算，模型乱加字段是真问题
```

这一层的好处是失败原因非常具体。

不是「答案不对」，是「字段 amount 期望 25，实际 \"25\"」。

### 7.4 语义相似度

用 embedding 把答案和参考答案变成向量，算余弦相似度。

```python
sim = cosine(embed(answer), embed(reference))
return sim > 0.82
```

适合：同一件事有很多种说法，而精确匹配会大面积误报。

三个坑：

```text
一、"可以退款" 和 "不可以退款" 的向量极其接近
二、0.82 这个阈值是拍的，换数据集就得重标
三、换一个 embedding 模型，历史分数全部不可比
```

第一条是致命的。

相似度衡量的是「说的是不是同一件事」，不是「结论对不对」。

所以它只能当**粗筛**，不能当最终判分。

用法建议：相似度低的一定失败；相似度高的人工看一眼再决定。

### 7.5 LLM-as-judge

用模型当裁判。

它适合那些你写不出规则的维度：有用性、语气、是否真的解决了问题、有没有编造。

典型调用形状：

```python
JUDGE_PROMPT = """你是严格的评审。只输出 JSON。

评分标准（rubric）：
- pass：回答直接解决了问题，且没有编造事实
- fail：答非所问、结论错误、或包含无法从材料推出的断言

反例（这些都必须判 fail）：
- 回答很客气但没给结论
- 回答给了结论但和材料矛盾
- 回答里出现"根据我的经验"这类无出处断言

用户问题：{q}
助手回答：{a}
参考事实：{facts}

只输出一个 JSON 对象，字段是 verdict（pass 或 fail）和 reason（一句话）。
"""

# 期望输出长这样：
# {"verdict": "pass", "reason": "直接给出了退款时限"}
```

它最灵活，坑也最多。

下一节专门说。

## 8. LLM-as-judge 的四个坑

### 8.1 偏好

judge 有系统性偏好，而且很稳定：

```text
更长的答案
排版更漂亮的答案（有列表、有小标题）
和自己风格接近的答案
放在前面的答案（成对比较时）
```

这些偏好不会因为你说「请客观」就消失。

对策是改 rubric，不是改语气。

比如加一条硬约束：

```text
- 若回答超过 200 字但没有新增事实，判 fail
```

### 8.2 不稳定

即使 temperature 设成 0，judge 也不保证每次一样。

尤其在长 rubric、多档评分、输入接近边界的时候。

工程做法有三条：

```text
同一条用例跑 2~3 次，取多数
判分结果只保留 pass/fail，不让它输出 0~100（分档越细，抖动越大）
把边界用例单独拎出来人工看
```

### 8.3 没 rubric 就是让它自由发挥

这是最常见的错误。

很多人写 judge 的 prompt 就一句：

```text
请判断这个回答好不好。
```

那 judge 判的是「读起来舒不舒服」。

它会稳定地给漂亮的废话高分。

rubric 要写成三样东西：

```text
档位：pass / fail 各是什么意思（最多三档）
判据：依据什么判断，允许看哪些材料
反例：什么样的回答看起来好但必须判 fail
```

反例比档位更重要。

因为 judge 的错误几乎都发生在「看起来像对的」那一类上。

### 8.4 版本漂移

judge 也是一个模型，也会换版本。

你今天用 A 模型当裁判，跑出 15/20。

下个月 A 模型升级，同一批用例跑出 12/20。

这 3 分是 agent 退化了，还是裁判变严了？

你分不出来。

所以 judge 的版本必须钉死，并且写进记录：

```text
judge 模型 ID + judge prompt 的 hash + rubric 版本
```

```json
{"judge": {"model": "固定版本号", "prompt_sha256": "9f2c...", "rubric": "v3"}}
```

换裁判 = 换尺子 = 历史分数全部不可比。

换了就要重跑全量，重新建 baseline。

### 8.5 judge 的第一天：先和人对一遍

judge 上线之前，做一件事。

人工标 30 条（你标，或者找一个同事标）。

然后算 judge 和人的一致率。

```text
一致率 > 85%：可以用它做回归信号
70%~85%：可以用，但失败用例必须人工复核
< 70%：别用，你的 rubric 还没写清楚
```

这一步花两小时，能省掉后面两个月的误判。

**judge 是代理指标，不是真值。**

这句话要写在 eval 脚本的注释里。

## 9. 测什么：六个层面

一个 agent 的输出不只是一段话。

至少有六层可以测。

```text
第 1 层  最终答案   对不对、有没有关键事实、有没有编造
第 2 层  工具选择   该调的时候调了吗、调错工具了吗
第 3 层  参数       参数对不对、类型对不对、有没有幻觉参数
第 4 层  步数       几步完成的、有没有绕路、有没有触到保险丝
第 5 层  成本       token 用量（输入输出分开记）
第 6 层  时延       单次调用耗时、整体任务耗时
```

前四层和 `labs` 里的循环直接相关，后两层需要记账。

### 9.1 工具选择的判法

```python
def tool_score(case, used_names):
    want = set(case.want_tools)
    got = set(used_names)
    if case.strict:
        return got == want              # 严格模式：不多不少
    return want <= got                  # 宽松模式：至少要用到这些
```

默认用宽松模式。

只有在「多调了工具就说明它没读懂问题」时，才用严格模式。

比如一个纯问答用例，它却调了 calculator —— 那就是没读懂。

### 9.2 步数怎么判

不要断言「必须 3 步」。

断言一个区间：

```python
assert case.min_steps <= steps <= case.max_steps
```

步数是最灵敏的退化信号。

答案还是对的，但步数从 3 涨到 9，说明它在试错。

试错型成功在线上就是慢和贵，而且下一次未必成功。

步数还有一个用法：和 `max_steps` 一起看。

`max_steps` 是保险丝（fuse），不是目标。

如果 20 条用例里有 4 条正好停在 `max_steps` 上，那不是「刚好够用」。

那说明这 4 条是被强行掐断的，返回值是那句「达到最大步数」，而不是答案。

这种用例必须判失败，哪怕返回的字符串里恰好包含了你想要的关键词。

### 9.3 成本

记 token，不记钱。

```text
输入 token：system + 历史 + 工具结果
输出 token：模型回复（含 tool_calls 的 JSON）
```

不写具体价格，原因在契约里：单价会变。

你只要记「这一版比上一版多了 30% 输入 token」，这个结论永远有效。

### 9.4 时延

时延要分 p50 和 p95。

p50 好看没用，用户骂的是 p95。

另外：用假模型跑出来的时延只反映你的代码开销。

网络、限流、排队，全在假模型里看不见。

所以时延这一层，离线 eval 只能说「没变慢」，不能说「很快」。

以你的场景实测为准。

## 10. 分层 eval 与基线数字

### 10.1 三层，三个用途

```text
冒烟集   5 条   每次保存都跑，10 秒内出结果，只防"整个崩了"
主集     20 条  改 prompt / 换模型时跑，几十秒
全量集   100+条 发版前跑，几分钟
```

冒烟集的意义被严重低估。

它的判据不是「测得多细」，而是「快到你懒得跳过它」。

主集是你日常真正在看的那个数字。

全量集负责覆盖率，它不该出现在你的日常循环里。

### 10.2 基线：把尺子存下来

通过数不是基线。

基线是一个文件。

```json
{
  "agent": "L01-agent",
  "version": "prompt-v4",
  "cases_sha": "3a71c0",
  "scorer_sha": "b908ef",
  "judge": null,
  "passed": 17,
  "total": 20,
  "zones": {"answer": "17/20", "tools": "19/20", "params": "20/20", "steps": "20/20"}
}
```

这个文件进 git。

每一次改动，生成一份新文件，和前一份比。

```text
prompt-v3  15/20    answer 15  tools 18
prompt-v4  17/20    answer 17  tools 19   +2 (case: 两位相加, 括号优先)
prompt-v5  16/20    answer 16  tools 17   -1 (case: 除零)  ← 回滚
```

看到第三行了吗。

v5 的通过数只掉了一条，但工具正确性掉两条。

如果只看总数，你会觉得「差不多」。

如果看分区，你会看到它在某类问题上退化得更明显。

### 10.3 通过数相同，也可能换了一批

这是最容易被忽略的一条。

v3 是 17/20，v6 也是 17/20。

你宣布「没有退化」。

但 v3 失败的是第 3、7、11 条，v6 失败的是第 1、5、9 条。

那 2 分是换了一批。

所以对比必须落到用例级别：

```text
新增通过：case_2, case_14
新增失败：case_5, case_9
```

这两行比一个总分有用十倍。

### 10.4 回归纪律

```text
任何改动，跑主集。
分数掉了，必须能说出是哪条、为什么。
说不出原因，就回滚。
```

第二条最难执行。

因为它逼你承认：你不知道自己改的那句话到底改了什么。

而这正是 eval 想让你看见的事。

## 11. eval 集不能当训练集

这条要单独成一节，因为它的破坏力最大。

你写 prompt 的时候，面前就摆着那 20 条用例。

第 7 条一直不过。

你盯着它，加了一句：

```text
如果问题里出现"除以零"，直接回答"除数不能为零"，不要调用工具。
```

第 7 条过了。

你很高兴。

你没意识到的是：你把一条**特例**写进了 prompt。

它在真实世界里几乎不会触发，因为它只对第 7 条的措辞有效。

这就是过拟合。

```text
20 条用例，被你调了 40 次之后，
它已经不是"没见过的输入"，而是"你的训练集"。
```

分数会一直涨。

涨到一个你自己都相信的数字。

然后上线，真实失败率一点没降。

### 11.1 留出集

标准做法是切一刀。

```text
dev   10 条  调 prompt 时随便看、随便跑
test  10 条  只在发版前跑，平时不看
```

切法要注意两点：

```text
test 里的用例要覆盖同样的失败类型，不能只放简单的
test 一旦用过一次来调 prompt，它就污染了，要换新的
```

### 11.2 用例只增不删

旧用例是你的历史。

它记录了「这一版曾经在这里错过」。

删掉它，等于允许自己再错一次。

所以你只有两个动作：

```text
新增：新出现的失败，加一条用例
修订：判分依据写错了，改判分函数（并重跑全量建新 baseline）
```

没有「删除」这个动作。

### 11.3 好用例的特征

```text
输入短，像用户真会说的话
判分依据能用一句话说清
失败时不需要解释就能看懂原因
来自一次真实失败
```

四条里最容易违反的是第一条。

很多人把用例写成需求文档，一段话三百字，里面三个条件。

那不叫用例，那叫考卷。

## 12. 离线 eval 与线上抽样

### 12.1 离线 eval 的边界

离线 eval 有三个优点：可复现、便宜、快。

它有一个结构性缺点：**用例是你选的，分布不是你用户的分布。**

所以离线 eval 通过，只说明「这 20 条上没退化」。

它不说明「线上会更好」。

差距来自两处：

```text
输入分布：你的用例是挑出来的，用户的输入不是
上下文：线上历史更长、更脏、夹着上一轮的失败
```

第二条经常被忽略。

你测的每一条用例都是「干净的第一次提问」。

而线上第 20 轮的一次提问，前面挂着 19 轮对话。

同一个 prompt，在干净的上下文里对，在臃肿的上下文里错。

离线 eval 如果不带上下文长度这个维度，就永远测不出这类退化。

所以主集里至少要有几条「带前置历史」的用例。

### 12.2 线上抽样

线上要拿的是三样东西：

```text
影子评估：抽样 1%~5% 的真实请求，跑同一套判分函数
行为指标：重问率、任务放弃率、平均步数、工具错误率
人工抽检：每天看 5~10 条真实对话
```

行为指标常常比判分函数更早发现问题。

用户重问，说明第一次没解决。

用户放弃（对话中断在第三步），说明它卡住了。

这两个信号不需要 judge，不需要标注，直接可算。

### 12.3 闭环

线上和离线不是两套系统。

它们是一条流水线：

```text
线上失败 → 脱敏 → 写成一条离线用例 → 进主集
        → 下个版本必须通过 → 全量跑 → 发版
```

这条流水线转起来，你的 eval 集才会长大。

不转起来，半年后它还是那 20 条。

而你的用户已经换了一批人，问的是另一批问题。

### 12.4 脱敏这件事

在把线上对话变用例之前，先做脱敏。

```text
手机号、邮箱、订单号、身份证、地址
粘贴进来的代码里可能带 token
工具返回里可能带内部路径
```

不脱敏就存进 git，等于把用户数据写进版本历史。

删都删不干净。

建议的做法是：用例文件只保留「问题 + 判分依据」，原始对话另存且不进库。

判分需要的事实，用手抄一遍再写进去。

手抄这个动作会让你重新判断一次「这条用例到底在测什么」，顺手也是质检。

## 13. 把 eval 接进你的工作流

eval 只有被跑起来才有价值。

所以最后一步是工程问题：怎么让它每次都能、且都愿意被跑。

### 13.1 时间预算三十秒

主集 20 条，单条跑完 1 秒左右，全量 30 秒以内。

这个预算是设计出来的，不是碰巧。

超了 30 秒，你就会开始「这次先不跑了」。

三条提速手段：

```text
一、并发跑（注意 API 限流，失败要重试，别把限流当成 agent 退化）
二、假模型阶段天然快，用来测循环
三、真模型阶段只跑主集，全量放到发版前
```

### 13.2 缓存能提速，也能骗你

同一条用例、同一个 prompt、temperature 0，结果理论上一样，可以缓存。

缓存一旦用错，就会掩盖退化：

```text
改了 prompt 但缓存 key 里没带 prompt 的 hash → 你跑的还是旧的
改了工具实现但缓存 key 里只有用例名 → 同上
temperature 不固定却缓存 → 你缓存的是某一次运气
```

缓存 key 必须包含：用例内容 + prompt hash + 模型版本 + temperature + 工具版本。

少一样，这个缓存就是个安慰剂。

### 13.3 超时和崩溃要算失败，不要算跳过

最容易自欺的一步。

一条用例超时了，脚本跳过它，最后打印 `19/19`。

看起来满分。

实际是 19 条通过、1 条根本不知道。

规矩很简单：

```text
超时 = fail
抛异常 = fail（记录 traceback）
解析失败 = fail
跳过必须是显式新增的一个状态，且单独计数
```

最后一行很重要。

如果你的脚本必须跳过某条，让它在输出里显示成 `SKIP`，并且总分写成 `17/20 (2 skip)`。

不要让跳过变成隐形的减分。

### 13.4 结果怎么呈现

顺序有讲究。

```text
先看新增失败（这次坏了什么）
再看新增通过（这次修好了什么）
最后看总数（那是标题，不是内容）
```

反过来的顺序就是「只看标题」。

而标题通常不变。

### 13.5 挂到哪

```text
保存代码时不想跑：太吵，会被关掉
每次改 prompt / 换模型：手动跑，必须跑
发版前：脚本强制跑全量，不通过不让发
```

最有效的其实是第二条变成习惯。

因为 eval 治的是你的判断，不是你的服务器。

## 14. 容易混淆的点与读码清单

### 14.1 eval 不是单元测试

单元测试断言实现：给定输入，函数必须返回这个值。

eval 断言行为分布：给定一批输入，通过率不能低于这个数。

区别在于「允许的差异」。

单测里一点差异都是 bug。

eval 里同一件事说成两种话，都应该算对。

所以 eval 的判分函数天生比断言松，也天生更容易写错。

### 14.2 20 条的置信区间很宽

这一条是数学，不是态度。

15/20 和 17/20 的差别，在 20 个样本上很可能落在噪声里。

工程含义：

```text
掉 1 条：先看是哪条，别急着回滚
掉 3 条以上：大概率是真的退化
涨 1 条：不要宣布胜利
```

所以主集之外还要有全量集。

全量集的作用不是更准，是**让小数点的差别有意义**。

### 14.3 假模型的 eval 只测循环

用 `ScriptedModel` 跑 eval，测的是你的代码：消息顺序、`tool_call_id` 对账、保险丝、步数。

它测不到模型的判断力。

所以假模型阶段的 eval 通过率不能拿来对外说。

它的用途是：**在接真模型之前，把你的脚手架钉死**。

这样接上真模型之后，掉分只可能是模型或 prompt 的问题。

### 14.4 改判分函数等于换尺子

你发现某条用例总是误报，于是放松了判分。

分数立刻从 15 涨到 18。

这 3 分不是进步。

改判分函数之后必须做两件事：

```text
重跑全量用例（包括那些原本失败的）
重写 baseline，并在文件里注明 scorer_sha 变了
```

否则你以后所有的对比，都建立在一把会自己动的尺子上。

### 14.5 读别人的 eval 代码，问五个问题

```text
1. 用例从哪来？是真实失败还是编的？
2. 判分函数测的是答案，还是过程，还是两者？
3. 有没有 baseline 文件？还是只有一个终端里的数字？
4. 用了 judge 吗？judge 的版本钉住了吗？
5. 失败的用例后来去哪了？被删了吗？
```

五个问题里，第 1 和第 5 最能暴露一个 eval 的真实质量。

一个用例全来自想象、失败用例不断被删的 eval，数字再漂亮也不能信。

## 15. 小结与下一篇

回到开头那位读者。

他真正缺的不是一句更好的 prompt。

他缺的是：改完之后，有一个东西能告诉他 16/20 变成了 17/20，并且能指出是哪一条变了。

这一篇讲的就是那个东西的最小形态。

三件东西：

```text
一组固定的输入
一个能判对错的函数
一个通过数
```

四个纪律：

```text
用例来自真实失败，一条 bug 一条用例
判分先用布尔，再谈分档
baseline 落盘进 git，比用例级别而不是只比总数
dev / test 分家，用例只增不删
```

一句要记住的话：

**eval 写的不是「测试」，是你对「好」的定义。**

定义不清，数字再好看也没用。

你会得到一个 20/20 的 eval，和一个照样被用户骂的 agent。

反过来，哪怕只有 10 条用例，只要每条都在回答「什么样算好」，它就比你的直觉可靠。
