有人问了一个很具体的问题。

他把公司的会员服务手册丢给 agent，问「退款多久到账」。

agent 回答：「一般情况下 7 到 15 个工作日。」

手册里写的是「3 到 5 个工作日」。

他没生气，他奇怪的是另一件事：

「它看起来读过，但又像没读。」

## 1. agent 读不到你的文档

这是同一个现象的两面。

模型没有你的文档。

它的参数里可能有「退款一般 7 到 15 个工作日」这种常识，于是它答得很顺。

它答的不是你的规定，是它的先验。

要让它答你的规定，只有一条路：把手册里相关的那几段，塞进这一轮的上下文。

于是问题从「模型聪不聪明」变成了三个工程问题：

```text
怎么把一本手册切成能被挑出来的小块
怎么在提问时挑对那几块
怎么让它答完之后说得出用了哪一块
```

这三件事合起来叫检索增强（RAG）。

## 2. RAG 不是向量数据库

先把一个流传很广的等式拆掉。

```text
RAG ≠ 向量数据库
```

向量数据库只是**一种检索器**的存储后端。

检索器可以有很多种：

```text
关键词检索       BM25 / TF-IDF，按词命中打分
向量检索         把问题和片段编码成向量，算余弦相似度
混合检索         两路都跑，用 RRF 之类的办法融合排名
结构化检索       SQL 查询、按字段过滤
图检索           沿实体关系走
```

它们都能"找出相关片段"。

选哪个，取决于你的问题长什么样。

```text
用户问"错误码 E1024 什么意思"        → 关键词更准，向量容易糊
用户问"钱退回来要几天"               → 手册写的是"到账时效"，向量更准
用户问"上个月华东区的退款率"         → 得查表，检索器要找的是数据库
```

所以判断一个系统是不是 RAG，不看它装了什么库。

看它有没有这条链路：

```text
先检索 → 把片段塞进上下文 → 生成时带上出处
```

三样缺一样，它就不是 RAG。

缺最后一样的最多，也最要命。

还有一个常见的替代：把整篇文档塞进长上下文。

那确实能让模型答对，但它不是 RAG，而且有两个硬伤：

```text
文档一多就塞不下
塞得下的时候，模型对中间段落的利用率明显下降
```

所以「上下文够长」不是 RAG 的替代品，它只是把检索换成了"人工预检索"。

而人工预检索在文档数量超过十份时就失效了。

## 3. 完整数据链路

八步，一步都不能省。

```text
① 加载 load       把 pdf / md / html / 表格 读成纯文本 + 元数据
        │
        ▼
② 切分 split      按标题或长度切成 chunk，每块带 id 和标题路径
        │
        ▼
③ 索引 index      建关键词索引 / 向量索引 / 两者都建
        │
        ▼
④ 检索 retrieve   问题 → top-k 候选 + 分数
        │
        ▼
⑤ 重排 rerank     候选逐条判"能不能回答问题"，留下 3~5 条
        │
        ▼
⑥ 组装 assemble   编号、拼 prompt、控制总长度
        │
        ▼
⑦ 生成 generate   模型只根据这些片段回答
        │
        ▼
⑧ 引用 cite       答案里的 [1] 对回 chunk id，末尾给出处
```

大多数"效果不好"的 RAG，问题出在②和⑧。

②切坏了，④再准也挑不出完整的一段。

⑧没做，你连"它是从哪抄的"都不知道，出了问题没法查。

中间几步当然也重要，但它们是可以替换的零件。

切分和引用是这条链路的两个端点，端点歪了，中间怎么调都歪。

八步里每步最常出的错，列在一起看：

```text
① 加载   pdf 转文本时表格结构丢了，数字挤成一串
② 切分   按长度切，标题和正文分家
③ 索引   只建了向量，没建关键词，错误码永远搜不到
④ 检索   k=20 一把梭，不设阈值
⑤ 重排   没有，直接拿 top-3 进上下文
⑥ 组装   没有编号，或者编号和 hits 顺序对不上
⑦ 生成   prompt 里没写"资料里没有就说没有"
⑧ 引用   让模型自己写出处，出处全是编的
```

这八行是一个检查清单。

你的 RAG 效果不好，先逐行对一遍，比换 embedding 模型快得多。

### 3.1 在 agent 里，RAG 通常是一个工具

上面这条链路，落到 agent 里只有两种接法。

第一种：它是一个工具。

代码来源：

```text
labs/L01_agent_loop/tools.py
```

```python
# 工具注册表：名字 -> 函数。模型输出的 name 就是靠这个字典映射到真实代码的。
TOOLS = {
    "calculator": calculator,
}
```

RAG 接进来就是多一行：

```python
TOOLS = {"calculator": calculator, "search_docs": search_docs}
```

`search_docs(query)` 内部跑完「检索 → 组装」，把带编号的片段作为观测返回。

好处是模型自己决定要不要查：

```text
闲聊不查，省 token
多轮里可以换关键词再查一次
查到的片段和别的工具结果一样，都进 messages
```

坏处也要认：

```text
它可能不查，直接凭先验答（开头那个"7 到 15 个工作日"就是这么来的）
它可能反复查，所以要限次数
```

第二种：检索是硬前置，在调模型之前先检索，片段直接拼进 prompt。

这种叫管道（pipeline），不是工具。

它可控，但不会追问，也不会自己换关键词。

判断标准只有一句：

```text
你的场景是"每问必查"，还是"有时要查"？
```

每问必查（客服问答、法规查询）→ 管道更稳。

有时要查（通用助手、代码助手）→ 工具更灵活。

两者的数据链路是同一条。

区别只在"谁来触发第四步"：模型，还是你的代码。

## 4. 切分：按结构切，还是按长度切

三种切法。

### 4.1 按结构切

Markdown 按标题，HTML 按标签，PDF 按章节，代码按函数。

```text
# 会员服务手册
## 退款政策
### 退款时效
```

切成：

```text
[2] 会员服务手册 / 退款政策
[3] 会员服务手册 / 退款政策 / 退款时效
```

好处是每一块都是完整语义单元。

你问「退款时效」，命中的那一块标题里就写着「退款时效」。

坏处是长度不可控。

有的小节 50 字，有的 3000 字。

3000 字那块塞进上下文，会挤掉别的东西。

### 4.2 按长度切

固定窗口，比如每 400 字一块，重叠 50 字。

好处是长度可控，能算准 token。

坏处很致命：它不认识语义边界。

它会把一张表格切成两半，把「不支持退款」和「除以下情况」分到两块里。

于是检索命中前半块，模型读到「除以下情况」，然后开始编。

### 4.3 按语义切

用相邻句子的向量相似度找断点，相似度突然掉下去的地方就是段落边界。

成本高，效果取决于 embedding 模型，而且不可预测。

新手不建议从这里开始。

### 4.4 实际做法：两级

```text
第一级：按结构切（标题 / 章节 / 函数）
第二级：结构块超过上限时，再按长度二次切，带 10%~20% 重叠
```

先结构，后长度。

结构保语义，长度保预算。

顺序反了就成了 4.2 那种事故。

### 4.5 PDF 和表格是另一类问题

这两类材料的切分，和 Markdown 完全不是一回事。

```text
PDF：换行是排版产生的，不是语义产生的
表格：一行的含义依赖表头，切走表头之后数字就没有意义
```

PDF 的典型事故：

```text
原文：审核通过后 3 到 5 个工作日到账
抽出来：审核通过后 3 到
       5 个工作日到账
```

两行被切成两块，第一块里只有「审核通过后 3 到」。

它命中了「审核通过」这个关键词，于是被召回。

模型看到的是一个没有结论的半句，然后把下一块的「5 个工作日」和上一块的「3 到」拼起来——拼对了它是运气，拼错了就是幻觉。

表格的典型事故更常见。

```text
| 套餐 | 价格 | 退款比例 |
| 月付 | 30   | 100%    |
| 年付 | 300  | 70%     |
```

按长度切在第二行中间断掉。

下半块只有「300 | 70%」，没有表头。

模型看到两个数字，不知道哪个是价格、哪个是比例。

处理办法只有一条：

```text
表格整体作为一个 chunk，不切
chunk 里保留表头，或者把每行重写成"月付 价格30 退款比例100%"
```

后者更啰嗦，但检索和生成都更稳。

写进 chunk 的东西，最好是一句能独立读懂的话。

读不懂的那半句，就是下一个幻觉的原料。

## 5. chunk 大小、重叠和标题层级

三个参数，值得单独讲。

### 5.1 大小

常见区间是 200 到 800 个 token，中文大约 300 到 500 字。

具体怎么选，看你问什么：

```text
问"某条规定是什么"      → 小块更好，命中精度高
问"这份文档讲了什么"    → 大块更好，上下文完整
问"这两个条款冲突吗"    → 必须两块一起进上下文，靠重排和 top-k 保证
```

小块的问题是上下文碎。

「3 到 5 个工作日」这句话，如果所在块里没有「审核通过后」这个前提，模型会答成「提交申请后 3 到 5 天」。

差了整整一个审核环节。

这就是切分导致的幻觉：不是模型编的，是你给的信息不全。

### 5.2 重叠

重叠的作用是防止一句话被切断。

```text
块 A：…审核通过后 3 到 5 个工作日
块 B：3 到 5 个工作日到账，退回原支付渠道…
```

10% 到 20% 的重叠够用。

重叠太大会有两个副作用：

```text
同一段内容被召回两次，白占 token
模型看到重复内容，倾向于把它当成"更重要"
```

### 5.3 标题层级必须写进 chunk

这一条是最容易被省略、也最容易被低估的。

看两种 chunk 的文本：

```text
坏：审核通过后 3 到 5 个工作日到账，退回原支付渠道。
好：《会员服务手册 / 退款政策 / 退款时效》
    审核通过后 3 到 5 个工作日到账，退回原支付渠道。
```

第二种多了一行标题。

这一行有三个作用：

```text
一、检索时能命中"退款"这个词（正文里可能一次都没出现）
二、模型知道这段话属于哪一节，回答时不会串到发票去
三、引用时你能直接给出"会员服务手册 · 退款时效"，而不是"某段文字"
```

代价是每块多几十个 token。

这个代价一定要付。

**反直觉的点在这里：**

> RAG 的瓶颈通常在**切分**，不在检索算法。
> 切坏了，再好的 embedding 也救不回来。

这句话有物理原因。

检索只能在已有的块里挑。

块本身缺了前提、缺了标题、被切断了，检索器挑得再准，挑出来的也是残片。

而残片进上下文之后，模型会把残片补全成一句通顺的话。

补全的部分，就是幻觉。

## 6. 最小代码：50 行离线 RAG

不用向量库，不用 embedding，不联网。

先准备一份样例文档，`handbook.md`：

```text
# 会员服务手册

## 退款政策

会员开通后 7 天内可以申请退款，超过 7 天不支持退款。
已使用的权益按天折算，从退款金额里扣除。

### 退款时效

审核通过后 3 到 5 个工作日到账，退回原支付渠道。
节假日顺延。

## 发票

电子发票在付款后 24 小时内开具。
```

代码。

代码来源：

```text
labs/L01_agent_loop/mini_rag.py（本篇新建，一个文件即可运行）
```

```python
import re
from dataclasses import dataclass

@dataclass
class Chunk:
    id: int
    heading: str
    text: str

def split_markdown(doc: str) -> list[Chunk]:
    chunks, stack, buf = [], {}, []
    def flush():
        body = "\n".join(buf).strip()
        if body:
            path = " / ".join(stack[i] for i in sorted(stack)) or "(开篇)"
            chunks.append(Chunk(len(chunks) + 1, path, body))
        buf.clear()
    for line in doc.lstrip("\ufeff").splitlines():
        if line.startswith("#"):
            flush()
            level = len(line) - len(line.lstrip("#"))
            stack[level] = line.lstrip("# ").strip()
            for k in [k for k in stack if k > level]:
                del stack[k]
        else:
            buf.append(line)
    flush()
    return chunks

def grams(s: str) -> set[str]:
    s = re.sub(r"[\s\W_]+", "", s)
    return {s[i:i + 2] for i in range(len(s) - 1)}

def score(query: str, c: Chunk) -> float:
    q, d = grams(query), grams(c.heading + c.text)
    return 0.0 if not q or not d else len(q & d) / (len(q) ** 0.5 * len(d) ** 0.5)

def retrieve(query: str, chunks: list[Chunk], k=3, min_score=0.05) -> list[Chunk]:
    ranked = sorted(((score(query, c), c) for c in chunks), key=lambda p: p[0], reverse=True)
    return [c for s, c in ranked if s >= min_score][:k]

def build_prompt(query: str, hits: list[Chunk]) -> str:
    if not hits:
        return f"资料里没有相关内容。只回答：资料里没有。\n问题：{query}"
    ctx = "\n\n".join(f"[{i}] 《{c.heading}》\n{c.text}" for i, c in enumerate(hits, 1))
    return f"只根据资料回答，结论后标出处编号 [n]。资料里没有的说「资料里没有」。\n\n{ctx}\n\n问题：{query}"

def citations_ok(answer: str, hits: list[Chunk]) -> bool:
    used = {int(n) for n in re.findall(r"\[(\d+)\]", answer)}
    return bool(used) and used <= set(range(1, len(hits) + 1))
```

五十行，零依赖。

它做了三件事：按标题切、按二元组打分、编号拼 prompt。

### 6.1 为什么用二元组

中文没有空格，按词切要先分词。

二元组（bigram）绕开了分词：

```text
"退款多久能到账" → 退款 款多 多久 久能 能到 到账
```

命中的是两个字的重合，粗，但能用。

而且它对专有名词特别友好：「E1024」会被切成 `E1`、`10`、`02`、`24`，只要文档里有同样的串就能命中。

代价是没有词形归一，也不懂同义词。

这就是为什么生产系统会用 BM25 或向量。

但这个 50 行的版本能让你先看清链路的形状。

### 6.2 跑起来是什么样

```text
切出 3 块
  [1] 会员服务手册 / 退款政策
  [2] 会员服务手册 / 退款政策 / 退款时效
  [3] 会员服务手册 / 发票

命中： [(2, '会员服务手册 / 退款政策 / 退款时效'), (1, '会员服务手册 / 退款政策')]

[1] 《会员服务手册 / 退款政策 / 退款时效》
审核通过后 3 到 5 个工作日到账，退回原支付渠道。
节假日顺延。

[2] 《会员服务手册 / 退款政策》
会员开通后 7 天内可以申请退款，超过 7 天不支持退款。
已使用的权益按天折算，从退款金额里扣除。

问题：退款多久能到账
```

注意 [1] 的标题路径。

「退款」这个词在正文里出现了，所以就算没有标题也能命中。

但如果正文里写的是「审核通过后三个工作日到账」，标题就是唯一的命中依据。

还有一个小细节：`doc.lstrip("\ufeff")`。

Windows 编辑器存的 Markdown 常常带 BOM。

不去掉，第一行不是 `#` 开头，整份文档会多切出一个「(开篇)」块，内容是一个看不见的字符。

这种块不会命中任何问题，但它会占一个编号，让你在排查引用时困惑半天。

### 6.3 这个 50 行版本的三个缺陷

```text
一、没有任何同义词能力：问"钱什么时候退回来"命中不了
二、没有索引：每次调用都全量扫一遍，文档大了会慢
三、没有重排：分数接近的两块，顺序完全由打分函数决定
```

第二条在几百个 chunk 时感觉不到，几万个 chunk 时会要命。

第三条下一节就讲。

### 6.4 这三样为什么先不做

```text
没有 embedding      要先看清链路的形状，向量会掩盖切分的问题
没有持久化索引      几十个 chunk 全量扫一遍只要几毫秒
没有重排            候选只有 4 条，重排的收益看不出来
```

这三样在生产里都要加。

但顺序不能反。

先切分，再检索，最后重排。

反过来做的人，会在"embedding 换哪个"上耗掉一周，而问题一直出在标题没进 chunk。

还有一个现实问题：token。

50 行版本拼出来的 prompt 只有几百个 token，随便塞。

真实文档里 3 条 chunk 可能就是 2000 token。

所以组装那一步必须有一个上限：

```text
预算 = 上下文窗口 - 输出预留 - system prompt - 历史
hits 超预算时，按分数从低到高整条砍，不要截断单条
```

截断单条是最坏的做法。

半句话进上下文，比没有这句话更容易引出幻觉。

## 7. 检索：top-k、阈值、元数据过滤

### 7.1 top-k 不是越大越好

常见值是 3 到 10。

```text
k 太小：该命中的没进候选，模型只能编
k 太大：噪声淹没有效信息，还白花 token
```

k 应该由重排来兜底：**召回阶段取大一点（20~50），重排之后只留 3~5 条**。

直接拿 top-3 进上下文，等于把召回和取舍合成一步。

那一步通常做不好。

### 7.2 阈值怎么定

绝对阈值很不稳。

```python
if score > 0.7:   # 换一个打分函数，这行就废了
```

稳一点的做法是用相对判据：

```text
top1 的分数 < 该查询的历史下四分位 → 当作没命中
或者：top1 与 top5 的分数差 < 0.02 → 说明没有明显更相关的，可能整批都不相关
```

更稳的做法是让模型自己说「资料不足」。

因为它能看到全部候选，而阈值只看到一个数。

### 7.3 元数据过滤

每个 chunk 除了文本，还要带字段：

```text
doc_id      哪份文档
section     标题路径
updated_at  更新时间
acl         谁能看
source_url  原始链接（做引用要用）
```

两个作用：

```text
一、缩范围：先按 doc_id / 时间过滤，再打分，准确率和速度都上去
二、控权限：不同用户只能检索自己能看的文档
```

权限过滤必须在检索之前。

放在生成之后过滤，等于让模型先读了一遍不该读的东西。

### 7.4 关键词和向量怎么选

一句话：看你的问题里有没有"必须精确命中"的东西。

```text
错误码、订单号、函数名、缩写、人名   → 关键词
同义改写、口语化提问、跨语言          → 向量
两者都有                             → 混合，用 RRF 融合两路排名
```

RRF 的思路很简单：不看分数，只看排名。

```text
score = Σ 1 / (60 + rank_i)
```

一个片段在两路里都排前面，融合后一定靠前。

它避免了"关键词分数 12 分、向量分数 0.8 分怎么相加"这种没有答案的问题。

### 7.5 BM25 为什么比"数词"好

最小版本用的是二元组重合度。

它有两个问题：长文档天然占便宜，常见词（「的」「会员」）权重和大词一样。

BM25 修的就是这两点：

```text
一、按词频饱和：同一个词出现 10 次不比 3 次重要 3 倍
二、按文档长度归一：长文档不天然占优
三、按逆文档频率加权：在每块里都出现的词，权重很低
```

第三条最有用。

「会员」这个词在手册的每一节都有，它区分不了任何东西。

而「到账」只出现在退款那一节，它几乎就是答案的信号。

自己实现一个可用的 BM25 不到五十行，但没必要。

大多数检索引擎、数据库、搜索库都自带它。

你只要记住一件事：**打分函数的作用是排序，不是判断相关性。**

判断是重排和模型的活。

## 8. 重排为什么需要

检索阶段用的是"双塔"式打分：问题和文档分别编码，最后算一个相似度。

它们从头到尾没见过对方。

所以检索擅长的是「大致相关」，不擅长「这条能不能回答这个问题」。

重排反过来：把问题和每一条候选放在一起看。

```text
输入：问题 + 一条候选
输出：这条能不能回答问题（分数或 是/否）
```

三种实现，按成本排：

```text
规则重排     关键词必须出现在候选里、时间必须够新
小模型重排   专门的 cross-encoder 类模型
LLM 重排     让模型逐条判"能否回答"，最贵也最准
```

重排的收益通常比换检索器大。

因为检索器的候选里往往已经有正确的那条，只是排在第 7 位。

重排把它从第 7 位提到第 1 位，问题就解决了。

一个实用细节：重排的输入要带标题。

```text
《退款政策 / 退款时效》
审核通过后 3 到 5 个工作日到账。
```

只给正文，重排模型也会像人一样困惑：这说的是退款还是发货？

### 8.1 重排的代价和取舍

重排不是免费的。

```text
时间：候选 50 条，逐条判，延迟从几十毫秒涨到几百毫秒甚至更多
钱：如果重排用 LLM，按 token 计费，而它看不到最终答案
复杂度：多一个模型、多一次调用、多一种失败
```

所以重排的用法有三个梯度：

```text
只有 5 条候选        → 不用重排，直接给
候选 20~50 条        → 用小模型或规则重排
候选多、问题复杂      → LLM 逐条判"能否回答"，但只判前 20 条
```

如果延迟是硬指标，就先做规则重排。

规则能挡掉的错误比想象中多：时间不对、文档不对、权限不对、明显是另一节的内容。

## 9. 塞进上下文的三种姿势

### 9.1 原文片段

最常用。

```text
[1] 《退款政策 / 退款时效》
审核通过后 3 到 5 个工作日到账，退回原支付渠道。
节假日顺延。
```

优点：保真、可引用、出错能查。

缺点：费 token，而且模型可能被无关句子带偏。

适用：法规、条款、代码、任何"必须原话"的场合。

### 9.2 摘要

先让模型把每块压缩成两句，再塞进去。

```text
[1] 退款到账时效：审核通过后 3~5 个工作日，退回原渠道，节假日顺延。
```

优点：省 token，一屏能放更多块。

缺点：摘要会丢前提，而且你没法引用原话。

摘要这一步本身也可能出错，错误会被下游当成事实。

适用：探索型问答、需要覆盖很多文档时。

### 9.3 结构化引用

把片段抽成字段。

```json
{"source": "会员服务手册/退款政策/退款时效", "field": "到账时效",
 "value": "3-5 个工作日", "channel": "原支付渠道", "note": "节假日顺延"}
```

优点：可计算、可比对、能直接进表格。

缺点：抽取本身是一次有损转换，抽错了比没抽更糟。

适用：数值问答、政策对比、需要聚合统计的场合。

### 9.4 怎么选

问一句：

```text
用户要的是"原话"，还是"事实"？
```

要原话（合同、条款、报错信息）→ 原文片段。

要事实（几天、多少钱、谁负责）→ 结构化或摘要。

要判断（这两条冲突吗）→ 原文片段，而且必须两块一起给。

## 10. 引用溯源：没有出处的回答不算 RAG

这一节是整篇的重点。

### 10.1 引用的三个层次

```text
第一层：答案里带编号 [1]
第二层：末尾列出 [1] 对应哪份文档、哪一节
第三层：编号能对回具体的 chunk id，点开能看到原文
```

大多数系统停在第一层。

模型会写 `[1]`，但那个 1 是它编的，和你给它的编号没关系。

第三层才有工程价值。

因为它让"这句话是从哪来的"变成一个可以程序检查的问题。

### 10.2 怎么校验

```python
def citations_ok(answer: str, hits: list[Chunk]) -> bool:
    used = {int(n) for n in re.findall(r"\[(\d+)\]", answer)}
    return bool(used) and used <= set(range(1, len(hits) + 1))
```

三件事被这一行拦住了：

```text
答案里一个编号都没有          → 不是 RAG 的回答
编号超出你给的片段数量        → 编的
编号是 0 或负数              → 编的
```

它拦不住的是「编号合法但引用错了」。

```text
答案：[1] 说退款要 7 到 15 个工作日
而 [1] 的原文写的是 3 到 5 个工作日
```

这种要靠引用正确率来测，12 节讲。

还有一种更细的错：编号对，片段也对，但被引用的是片段里不承重的那半句。

```text
答案：[2] 会员超过 7 天也可以退款
片段 [2]：会员开通后 7 天内可以申请退款，超过 7 天不支持退款。
```

编号合法、片段相关、结论反了。

校验代码抓不到这种，判分函数也未必抓得到，只有人工抽检能发现。

所以引用正确率必须配一次人工标定，不能全靠自动。

### 10.3 prompt 里怎么写

```text
只根据下面的资料回答。
每个结论后面必须标出处编号，格式 [1]、[2]。
只能用资料里出现过的编号，不要自己编号。
资料里没有的内容，直接说「资料里没有」，不要补充。
```

三句话缺一不可。

第二句管格式，第三句管编号来源，第四句管"不知道"的出口。

### 10.4 输出格式

```text
退款审核通过后 3 到 5 个工作日到账 [1]，退回原支付渠道 [1]。
超过 7 天不支持退款 [2]。

出处：
[1] 会员服务手册 · 退款政策 / 退款时效
[2] 会员服务手册 · 退款政策
```

注意两件事。

第一，出处列表是程序拼的，不是模型写的。

模型只负责在句子里放编号，末尾的出处由你从 `hits` 里生成。

第二，同一个编号可以出现多次。

不要逼模型每次都用新编号，那会诱导它编。

### 10.5 引用顺手解决了三个问题

引用看起来只是给答案加个尾巴。

实际上它同时修了三件事。

```text
一、可审计：用户问"你凭什么这么说"，你能给出原文
二、可评测：引用对不对是程序能判的，不用人读每一条
三、可约束：要求每句带编号，会逼模型只用资料里的内容
```

第三条最容易被忽略。

一个被要求「每句话都要标出处」的模型，编造的成本变高了，因为它得同时编内容和编号。

而且编号会被校验，编错了当场暴露。

所以引用不只是展示。

它是一种约束生成的手段。

## 11. 10 段 vs 3 段

一个具体的选择：上下文里放几段。

```text
放 10 段：召回率高，但噪声大，token 多
放 3 段：精准，但漏掉就没了
```

实测里的常见现象：

```text
从 3 段加到 10 段，召回率涨，答案准确率不一定涨
加到 20 段，准确率经常开始跌
```

原因有两个。

第一个是噪声：不相关的段落里也有"退款"两个字，模型会把它们混进去。

第二个是位置：长上下文里，中间那段的信息最容易被忽略，开头和结尾的被利用得更好。

所以实践中：

```text
条数：3~5 条
顺序：最相关的放第一条和最后一条
总量：给检索结果一个 token 上限，超了就砍，不要硬塞
```

以你的场景实测为准。

有些任务（比如法律条款比对）必须一次给 6 条以上，那就得接受更长的上下文和更高的成本。

一个具体的对比例子。

```text
放 10 段：
[1] 退款政策（含退款时效）
[2] 退款政策 / 退款时效
[3] 发票（含"退款后发票作废"）
[4] 账号注销（含"退款需先注销"）
[5] 会员等级（含"退款影响等级"）
...

模型可能开始讨论"退款对等级和发票的影响"，而用户只问了几天到账。
```

```text
放 3 段：
[1] 退款政策 / 退款时效
[2] 退款政策
[3] 发票（仅在问题涉及发票时才给）

模型没有别的可聊，只能回答时效。
```

第二种的答案短、准、可引用。

第一种的答案更长，看起来更"周到"，但它答了一个没人问的问题。

而上下文越长，这种"多答"的概率越高。

## 12. RAG 的 eval：三个指标分开测

RAG 出问题，可能是检索错了，也可能是检索对了但模型没用。

合成一个"答案正确率"你就分不清。

所以要分开测三件事。

### 12.1 检索命中率

先人工标：每个测试问题，正确的 chunk 是哪几个。

```python
def recall_at_k(questions, chunks, k=5) -> float:
    hit = 0
    for q in questions:
        got = {c.id for c in retrieve(q.text, chunks, k=k)}
        if got & set(q.gold_chunk_ids):
            hit += 1
    return hit / len(questions)
```

这个指标只和切分、检索器有关。

换切分方式时只看它。

### 12.2 答案正确率

用 09 篇那套：关键事实 + 结构化比对 + judge。

注意：测的时候要关掉检索的变化，固定同一批 hits。

否则你分不清是检索变好还是生成变好。

### 12.3 引用正确率

对答案里的每个编号，检查对应片段是否真的支持这句话。

两种做法：

```text
规则：这句话的关键事实，是否出现在对应片段里
judge：给"句子 + 片段"，问"这个片段支持这句话吗"
```

分母是编号总数，不是答案数。

一条答案里有三个编号，错一个就算这条有引用错误。

一个骨架：

代码来源：

```text
labs/L01_agent_loop/eval_rag.py（本篇新建）
```

```python
def citation_precision(answer: str, hits: list[Chunk]) -> float:
    used = [int(n) for n in re.findall(r"\[(\d+)\]", answer)]
    if not used:
        return 0.0
    ok = 0
    for n in used:
        if not 1 <= n <= len(hits):
            continue                       # 越界编号：直接算错
        sent = sentence_around(answer, n)  # 这个编号所在的那一句
        if supports(sent, hits[n - 1].text):   # 片段是否支持这句话
            ok += 1
    return ok / len(used)
```

`supports()` 用规则或 judge 都行。

规则版本可以很简单：这句话里的数字，片段里有没有。

```python
def supports(sentence: str, chunk: str) -> bool:
    nums = re.findall(r"\d+", sentence)
    return all(n in chunk for n in nums) if nums else True
```

这个规则会漏掉很多情况，但它免费、稳定、可解释。

先用它把「引用完全不对」的抓出来，剩下的交给 judge。

### 12.4 还要测"该说没有的时候"

这是最常被漏掉的一组用例。

```text
问题：会员能开纸质发票吗？
文档：只有电子发票
期望：资料里没有 / 不能，并说明文档只提到电子发票
```

判分方式检查两件事：

```text
有没有出现"资料里没有"（或等价说法）
有没有编出一个答案
```

没有这组用例，你的 eval 会奖励"敢答"的系统。

### 12.5 分层看

```text
recall 低 → 切分或检索器的问题，先别动 prompt
recall 高但答案错 → 重排或生成的问题
答案对但引用错 → 编号机制的问题
```

这三行能省掉大量瞎调。

## 13. 幻觉与「文档里没有」

### 13.1 三种"没有"

```text
一、文档里确实没有          → 应该说没有
二、文档里有，但没检索到     → 检索问题，不是幻觉
三、检索到了，模型没用       → 生成问题
```

三种在用户眼里长得一样：答案不对。

所以在日志里要能分开。

```json
{"q": "退款多久到账", "hits": 2, "answer": "...", "cited": [1],
 "recall_ok": true, "used_cited": true}
```

`recall_ok=false` 说明该命中的没命中。

`used_cited=false` 说明它答了但没引用。

这两个字段能把大多数问题定位到具体环节。

### 13.2 给它一个体面的出口

模型编，很多时候是因为没有别的出路。

prompt 里必须写清楚：

```text
如果资料不足以回答，回答："资料里没有这个信息。"
不要用常识补充，不要猜测。
```

再加一个程序侧的分支：`hits` 为空时，根本不调模型。

```python
if not hits:
    return "资料里没有这个信息。"     # 省钱，也彻底消灭这一类的编造
```

这一行比十句 prompt 都有效。

### 13.3 引用是最好的护栏

要求每句话带编号，编造的成本就变高了。

因为它要同时编内容和编号，而且编号会被程序校验。

校验不过就重试一次，重试还不过就直接返回"资料不足"。

这个兜底比"请勿幻觉"这种话有用得多。

### 13.4 说"没有"也要给出依据

一个细节，但影响体验。

```text
差：资料里没有。
好：资料里只提到电子发票（[1]），没有提到纸质发票。
```

第二种也在说"没有"，但它告诉用户：我查了，查到了什么。

用户才知道是该补文档，还是该换个问法。

### 13.5 一个完整的对照

```text
用户：会员能开纸质发票吗？

版本 A（没有引用约束）
  可以的，您可以在付款后 7 个工作日内申请纸质发票。
  → 文档里根本没有纸质发票这一项。纯编。

版本 B（有引用约束，但没校验）
  纸质发票需要 7 个工作日邮寄 [3]。
  → [3] 是"账号注销"那一块。编号合法，引用全错。

版本 C（有校验 + 无命中分支）
  资料里只提到电子发票（[1]：电子发票在付款后 24 小时内开具），
  没有提到纸质发票。
  → 用户知道答案是没有，而且知道依据是哪一句。
```

三个阶段对应三种工程投入。

A 是大多数 demo。

B 是加了 prompt 但没加校验的常见中间态，它比 A 更危险，因为看起来专业。

C 才是能上线的形态。

区别不在于模型更强，在于程序在模型之外多做了两件事：拼出处、验编号。

## 14. 常见错误与读码清单

### 14.1 只按长度切

切完标题丢了，chunk 变成一堆没有上下文的句子。

表现：检索命中率看着还行，答案总是缺前提。

### 14.2 切完不存 id

`chunk.text` 存了，`chunk.id` 没存或者没稳定下来。

表现：引用永远对不回去，只能显示"某段文字"。

id 要稳定：同一份文档重新切一次，id 不能全变。

否则你的 eval 标注全废。

### 14.3 top-k 拍脑袋

直接写 20，理由是"多给点总没坏处"。

结果上下文里一半是噪声，成本还翻倍。

先重排，再决定留几条。

### 14.4 把整篇文档塞进上下文

那不叫 RAG，那叫长上下文。

文档能塞下的时候它确实更简单，但两个问题：

```text
文档一多就塞不下
塞进去之后，模型对中间部分的利用率明显下降
```

### 14.5 拿"用了向量库"当验收标准

向量库只是零件。

验收标准应该是三个数字：检索命中率、答案正确率、引用正确率。

### 14.6 权限过滤放在检索之后

先检索出 10 条，再过滤掉 3 条没权限的。

问题不是少了 3 条，是模型已经看过它们了。

过滤必须在打分之前。

### 14.7 让模型自己写"出处"

模型写的出处是文本，不是 id。

它会把标题写得似是而非，比如把「退款时效」写成「退款说明」。

出处必须由程序从 `hits` 里生成。

### 14.8 读别人的 RAG 代码，问五个问题

```text
1. chunk 里带标题路径吗？id 稳定吗？
2. 检索是关键词、向量，还是混合？k 是多少？
3. 有重排吗？重排之后留几条？
4. 答案里的编号，是模型写的还是程序校验过的？
5. 检索命中率和引用正确率，分别测过吗？
```

第 1 和第 4 最能看出这套系统是演示还是能上线。

再补一句判断：

```text
它的 eval 里有没有"文档里没有"的用例？
```

没有这一组，说明它从没被要求过"承认不知道"。

那它的通过率再高，也只证明它敢答。

## 15. 小结与下一篇

回到开头那个回答。

「一般情况下 7 到 15 个工作日。」

它的问题不是模型不聪明，是那一轮上下文里没有「3 到 5 个工作日」。

要么没检索到，要么检索到了没进上下文，要么进了上下文但没被要求引用。

三个环节，对应三种修法。

这一篇的骨架：

```text
加载 → 切分 → 索引 → 检索 → 重排 → 组装 → 生成 → 引用
```

四个结论：

```text
RAG 不是向量数据库，是这条链路
切分是瓶颈，标题层级必须进 chunk
检索给候选，重排做取舍，上下文只放 3~5 条
引用不是装饰，它是可以被程序校验的判分依据
```

一句要记住的话：

**RAG 的瓶颈通常在切分，不在检索算法。**

以及一句同样重要的：

```text
没有出处的回答，不算 RAG 的回答。
```

下一篇讲的是另一件事：一个 agent 干不完的活，什么时候该拆给几个 agent。

```text
Agent 系统讲解 12：多 Agent：什么时候该拆
```

那一篇会先讲清楚"不该拆"的场景。

因为大多数多 Agent 系统，都是在解决一个原本不存在的问题。

而在那之前，你可以先把这一篇的 50 行跑起来。

改一改 `handbook.md`，问它一个文档里没有的问题。

看它是老老实实说「资料里没有」，还是给你编一个 7 到 15 天。

那个瞬间，你会明白这一篇为什么要花这么长讲引用。
