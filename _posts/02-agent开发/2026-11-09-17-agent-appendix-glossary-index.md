## 2. 术语表

按主题分组，不按字母。

每个词第一次出现在哪篇，也标了。

### 2.1 角色与消息（01 篇）

**模型（model / LLM）**
一个**无状态**函数：给 `messages`，返回一条 message。不记得上一次，不执行代码。

**Agent**
模型 + 一个循环 + 一套工具 + 终止条件。是一个程序，不是一个模型。

**消息（message）**
`{role, content, tool_calls, tool_call_id}` 四件套。agent 的全部可恢复状态都在消息列表里。

**四种角色（role）**
`system` 规则层、`user` 输入层、`assistant` 模型说过的话、`tool` 工具执行结果。

**工具调用（tool call）**
模型输出的结构化请求。注意：模型没有调用任何东西，它只是生成了一段符合 schema 的文本。

**调用编号（`tool_call_id`）**
把工具结果对回请求的唯一凭据。一轮多个调用时，靠它对账，不靠顺序。

**观测（observation）**
工具执行结果，作为 `role="tool"` 的消息回填进历史。

### 2.2 预算（02 篇）

**token**
模型处理文本的最小单位。不是字符，不是单词。

**上下文（context）**
这一次请求里，真实发出去的全部 token。

**上下文窗口（context window）**
单次请求能接收的 token 总数上限。不是「记忆容量」。

**单轮预算**
一次请求里，system、工具 schema、历史、本次输入、预留输出五样东西分掉的那个池子。

**静默截断**
客户端或框架在你不知情时裁掉历史。它让你失去对「模型看到了什么」的掌控。

**lost in the middle**
开头和结尾的信息用得最好，中间最容易漏。所以关键指令要放两端。

### 2.3 工具与循环（03–05 篇）

**工具 schema**
工具的说明书：名字、描述、参数结构。模型只看得见这个，看不见你的函数体。

**注册表（registry）**
「名字 → 函数」的字典。没注册 = 模型永远调不动。

**循环（loop）**
把历史发给模型 → 模型回话 → 执行工具 → 回填 → 再来一轮。

**回填（append）**
把 `assistant(tool_calls)` 先进历史，再把 `tool` 结果接在后面。顺序反了真模型就 400。

**保险丝（fuse）**
步数、时间、金额三道刹车。没有它，循环会跑到你余额见底。

**自愈（self-heal）**
工具报错不抛异常，而是变成一条可读的观测，让模型下一轮自己改。

**幂等（idempotent）**
同一个操作做两次和做一次效果一样。重试写操作的前提。

### 2.4 上下文与记忆（06–07 篇）

**上下文工程（context engineering）**
在有限预算里，决定这一次发什么、不发什么。不是「写更长的 prompt」。

**裁剪（trimming）**
删历史。关键是**不能拆散** `assistant(tool_calls)` 和它的 `tool` 结果。

**摘要压缩**
把中间那段历史压成一条摘要消息。摘要本身也是一次模型调用，要算成本和延迟。

**记忆（memory）**
跨会话保存下来的事实、偏好、事件。和上下文不是一回事：记忆是硬盘，上下文是这一次塞进信封的纸。

**召回（recall）**
按需把记忆取回来，塞进这一轮的上下文。

### 2.5 输出与评测（08–09 篇）

**结构化输出**
让模型吐出能直接喂给程序的 JSON。

**三段循环**
解析 parse → 校验 validate → 修复 repair。三段必须分开写，因为失败的样子不一样。

**修复（repair）**
把错误原样回给模型，而不是说「请重试」。

**评测（eval）**
一组固定用例 + 一个判分函数 + 一个通过数。写的是你对「好」的定义。

**基线（baseline）**
上一次的分数。没有基线，你无法回答「这版比上版好吗」。

**LLM-as-judge**
用模型给模型打分。要给 rubric、固定 judge 版本、接受它的偏好。

### 2.6 能力扩展（10–12 篇）

**规划（planning）**
把大任务拆成可验证的步。价值不在「想得更远」，在把状态从模型脑子里搬到外面。

**todo 列表**
外部化的任务状态：`id + title + done + evidence`。每完成一项打勾，就是给自己一个观测。

**RAG（检索增强生成）**
先检索，再把片段塞进上下文。不是「向量数据库」的同义词。

**切分（chunking）**
把文档切成检索单元。RAG 的瓶颈通常在这里。

**重排（rerank）**
检索给候选，重排做取舍。

**引用（citation）**
回答里标出处，并可被程序校验。没有出处的回答不算 RAG 的回答。

**多 Agent**
把任务拆给多个独立上下文的 agent。收益来自上下文隔离，不是「多个脑子更聪明」。

### 2.7 生产（13–16 篇）

**提示注入（prompt injection）**
文档、工具结果、用户输入里藏指令，劫持模型。三个入口里，工具返回最危险。

**权限分级**
只读 / 写入 / 危险三类工具，对应不同审批要求。

**沙箱（sandbox）**
路径白名单、命令白名单、禁网、资源上限。

**纵深防御**
不靠单点。输入侧、工具侧、权限侧、输出侧各拦一次。

**追踪（trace）**
一次任务全过程的树形记录。一次任务一个 trace，一次模型调用或工具执行一个 span。

**可复现**
存下完整 messages，才能重放。这是 agent 调试最贵的能力。

**成本账本**
输入 token × 输入单价 + 输出 token × 输出单价，按任务、用户、功能聚合。

**适配器（adapter）**
把供应商 API 的形状，翻译成 `model.chat(messages) -> Message`。换模型只改这里。

## 7. 常见报错，先翻哪篇

```text
400 messages with role 'tool' must be a response to
    a preceding message with 'tool_calls'
    → 01、04。顺序错了，或者 tool_call_id 对不上。

400 Invalid type for ... arguments: expected a string
    → 04、15。你把 dict 直接发出去了，要 json.dumps。

This model's maximum context length is ...
    → 02、06。历史太长，先看是不是工具返回太大。

模型一直不调工具
    → 03。schema 没发，或者描述写得太烂。

模型把参数写成了字符串
    → 08、15。参数也是结构化输出，要校验。

TypeError: string indices must be integers
    → 08、15。漏了 json.loads(arguments)。

工具报错，整个进程崩了
    → 05。异常没被兜成观测。

循环跑了几十步还在跑
    → 02、05。保险丝没装，或者装错了位置。

改完不知道是变好还是变坏
    → 09。没有 eval。

线上出事，复现不了
    → 14。没有存完整 messages。
```

## 9. 五个最容易忘的结论

这五句，值得抄在便签上。

```text
模型是无状态的。
所以"记忆"是你每一轮往里塞的东西。

模型不调用工具，它只生成一段 JSON。
执行的是你。

上下文窗口不是记忆，是单次请求的预算。

让程序不崩不是健壮性。
让模型看见错误、并且知道怎么改，才是。

安全边界画在代码里，不画在 prompt 里。
```

### 五组看起来互相矛盾的结论

整套系列里，有几组话说得像在打架。

它们不矛盾，是**条件不同**。

**第一组：上下文越多越好 ↔ 越多越差**

```text
相关、放在两端、密度高 → 多比少好。
无关、堆在中间、互相冲突 → 少比多好。
```

判断标准不是「多不多」，是「这一段有没有用」。

**第二组：出错要重试 ↔ 有些错永远别重试**

```text
网络抖动、429、5xx → 重试有用（要退避）。
参数错、schema 错、任务无解 → 重试一百次也是错一百次。
```

判断标准只有一句：

```text
这次重试，和上次有什么不同？
```

**第三组：约束越强越好 ↔ 约束越强表达力越弱**

```text
schema 能保证形状，保证不了内容。
约束到极致，模型只能装下你要的那几个字段。
```

判断标准：形状要死，内容要活。

**第四组：多 Agent 更强 ↔ 多数任务单 Agent 更好**

```text
上下文真的塞不下 → 拆。
工具多到互相干扰 → 拆。
需要并行 → 拆。
其余情况 → 不拆。
```

判断标准：拆的收益是不是大于「上下文复制 + 信息丢失 + 成本翻倍」。

**第五组：eval 越多越好 ↔ 会对着 eval 过拟合**

```text
用例越多，越能反映真实分布。
但你会不自觉地针对这 20 条调。
```

判断标准：留一份不参与调参的留出集。

五组看完，会发现它们其实是同一种思维方式：

```text
先问"在什么条件下"，
再问"该选哪边"。
```

这也是这套系列一直在做的事。

## 10. 往下学什么

这套系列覆盖的是「从零到能用」。

再往前，有五个方向。

**框架**：LangChain、LangGraph、LlamaIndex。

读懂它们的前提，是你知道它们只是把你手写的东西换了个名字。

**协议**：MCP（Model Context Protocol）。

它解决的是「工具从哪来」，是工具生态的标准化。读完 03 篇再看，会很快。

**多模态**：图像、音频进上下文。

会改变的是「消息的形状」，不会改变循环。

**部署**：并发、队列、限流、灰度。

这是工程问题，不是 agent 问题。

**评测工程**：更大规模的数据集、人工标注、线上 A/B。

09 篇是起点，不是终点。

一条建议：

```text
不要因为"还有这么多没学"而回头重读。
先做出一个有人真的在用的东西。
问题会自己告诉你下一步该学什么。
```

## 11. 版本与勘误

这一套写于 2026 年 11 月。

几条会过期的内容，先标出来：

```text
具体 API 的字段名（03、15）    → 以你用的供应商文档为准
上下文窗口的量级（02）        → 以你用的模型文档为准
价格（全文未写具体数字）      → 以你的账单为准
模型的能力边界（09、13）      → 会变，评测要跟着重跑
```

不会过期的，是那六层。

```text
契约、机制、可靠、能力、生产、回归。
```

换模型、换框架、换语言，这六层不变。

## 12. 最后一页

十七篇加这一页，走完了。

回到最开始那个问题：

```text
为什么 agent 的知识显得不系统？
```

因为它有六层，而教程通常只讲一层。

有人只讲 prompt，你会以为 agent 就是写 prompt。

有人只讲框架，你会以为 agent 就是调 API。

有人只讲 RAG，你会以为 agent 就是向量库。

现在你知道：

```text
agent = 模型 + 一个循环 + 一套工具 + 一份被精心维护的历史
```

四样东西里，只有一样是模型。

另外三样，全是你写的。

这就是这套系列想让你看见的东西。

不是因为模型不重要。

是因为**模型之外的那三样，才是你能改进的地方**。
