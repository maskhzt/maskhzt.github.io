上个月我把一个任务拆成了三个 agent。

一个查资料，一个算账，一个写结论。

听起来很专业。

结果原来四十秒能跑完的任务，跑了两分半。

结论还是错的。

错在一个特别蠢的地方：查资料的那个 agent 发现了一条关键约束，它写在过程里，没写进结论。

写结论的 agent 没看见。

```text
主 agent 以为子 agent 会说"这个方案不成立，因为 X"。
子 agent 实际说的是"方案已确认"。
X 留在它自己的上下文里，随进程一起消失。
```

那次之后我才想明白一件事。

多 Agent 不是更高级的写法。

它是更贵、更难调、更容易丢信息的一种写法。

只有在你确实需要它换来的那样东西时，才值得。

这篇只做一件事：把"什么时候该拆"从感觉变成判断。

## 1. 这个问题解决什么

先给结论。

多 Agent 解决的问题只有一个：

```text
一个上下文装不下、或者装下了也做不好。
```

注意这句话里没有"更聪明"。

拆成多个 agent，模型数量变多了，但每个模型还是那个模型。

没有任何一个子 agent 比主 agent 聪明。

它只是在**另一个上下文里**工作。

所以判断该不该拆，只需要问一个问题：

```text
我现在遇到的是"一个上下文不够用"，
还是"这个任务本来就复杂"？
```

这两个问题看着像，其实完全不同。

第一个是工程约束，拆能解决。

第二个是任务属性，拆只会把复杂度乘以层数。

举个具体的例子。

一个任务要读完 20 个文档再写综述。

这属于第一种：一个上下文装不下 20 个文档。

同一个任务，如果只是要"判断这段代码有没有并发 bug"。

这属于第二种：它不需要 20 个上下文，它需要一个能一直盯着同一段代码的脑子。

拆成"读代码 agent + 判断 agent"，读的那个把代码摘要给判断的那个。

判断的那个拿到的已经不是代码，是摘要。

它没法判断。

这就是"复杂度乘以层数"的具体样子。

先把术语定下来。

委派（delegation）：主 agent 把一段子任务交给另一个 agent 执行，拿回结果，继续自己的循环。

注意"拿回结果"这四个字。

拿回的是结果，不是那个 agent。

子 agent 跑完就消失了，它的 messages 也跟着消失。

所以拆分的本质不是"多了一个员工"，是"多了一次独立的上下文会话"。

子 agent 不是新物种。

它就是一个普通的 `run_agent` 调用，只是 `messages` 是新建的。

这句话很重要。

因为它意味着：拆与不拆，代码上只差一次函数调用，架构上却差了一个数量级的调试成本。

## 2. 单个 agent 撞墙的四个信号

拆的理由必须是信号，不能是审美。

下面四个信号，出现任意一个，才值得开始考虑拆。

### 2.1 信号一：上下文塞不下

这是最硬的信号，因为它可以被算出来。

一次任务的 messages 里，token 会这样涨：

```text
system prompt        固定成本
工具说明书           每个工具几百 token，随工具数线性涨
历史对话             随步数线性涨
工具观测             最凶的一项，一次读文件就能顶几千 token
```

如果你的任务需要读 30 个文件再总结，那么无论怎么裁剪，主线上下文都会被撑爆。

[06 篇](./2026-11-09-06-agent-context-engineering.md)讲过裁剪和摘要压缩。

但裁剪有个上限。

你不能把 30 个文件压成 3 句还不丢证据。

这时候拆是对的：

```text
每个子 agent 读 5 个文件，
把自己的 5 份笔记压成 300 字交回来。
主 agent 只看见 6 条 300 字。
```

主线的上下文从"30 个文件"变成"6 份笔记"。

这是真正的省钱、省窗口。

算一次账。

30 个文件，平均每个 800 token，就是 24000。

而上下文是每轮重发的。

读到第 20 个文件时，前面 19 个文件的内容还躺在 messages 里。

第 20 轮的请求，光历史就接近 16000 token。

拆开之后，主线的历史峰值是 6 条摘要，不到 2000。

差值不是 10%，是八倍。

这就是"上下文隔离"这四个字的具体数字。

注意这里省的不是"总 token"，是"主线上下文的峰值"。

总 token 其实变多了：多了子 agent 的 system prompt，多了委派本身的开销。

你买的是峰值下降。

这个区别很重要，第 6 节算总账的时候会用到。

### 2.2 信号二：工具太多导致选错

工具是模型看不见代码、只能看见说明书的。

说明书塞得越多，模型在一堆相似描述里挑错的概率越高。

```text
5 个工具    模型挑错的机会不大
15 个工具   开始需要你在描述里写"什么时候不要用它"
40 个工具   模型会稳定地挑最像的那个，而不是最对的那个
```

这不是模型的缺陷，是上下文的结构问题：

```text
候选集越大，单次选择的准确率越低。
```

一个具体的干扰长这样。

```text
search_files(query)     在文件内容里搜关键词
search_names(name)      在文件名里搜关键词
search_code(symbol)     在代码里搜符号
```

三个工具，描述里都有"搜索"。

模型要选对一个，取决于它把任务理解得多细。

工具到 15 个以上，这种"三个长得像"的组合会出现好几组。

错一次，观测就是空的或错的，后面整条链跟着歪。

工具一多，一个常见的补救办法是把工具分组。

而"分组"本身，就是拆。

```text
主 agent：只看得见 5 个工具，其中一个是 delegate_to_db_agent
子 agent：看得见 12 个数据库工具，别的都看不见
```

工具集被切开了，选择空间就小回去了。

### 2.3 信号三：子任务要完全不同的 system prompt

system prompt 里放的是"你是谁、你的规矩、你的边界"。

有些子任务的规矩，和主线是冲突的。

举一个真实的冲突：

```text
主线：你是一个给用户解释结论的助手，说话要短，要有礼貌。
子任务：你是代码审计员，只输出问题清单，不要解释，不要道歉。
```

把这两套规矩写进同一个 system prompt，结果一定是互相稀释。

模型会变得既不像解释者，也不像审计员。

症状很具体。

你让它"简短解释"，它给你一段 JSON。

你让它"只输出清单"，它在最后加一句"希望能帮到你"。

两套规矩在同一个上下文里抢注意力，谁也没赢。

拆开之后：

```text
主线 system：解释结论
子 agent system：只输出问题清单，JSON 数组，不要别的
```

两个上下文各自干净。

这是拆的最正当理由之一，而且经常被忽略。

因为它跟 token 无关，跟"注意力被稀释"有关。

### 2.4 信号四：需要并行

有些子任务之间没有依赖。

查三个城市的天气，读五个仓库的 README，跑四个互相独立的检查。

串行做，时间就是加法。

并行做，时间就是最大值。

```text
串行：t1 + t2 + t3 + t4
并行：max(t1, t2, t3, t4)
```

这是四个信号里唯一一个"拆了立刻有确定收益"的。

因为收益不在模型身上，在墙上时钟上。

但并行有隐藏成本。

四个子 agent 同时发请求，碰到限流的概率也乘以四。

一个 429 会让整批重试，重试又是四次并发。

所以并行要配并发上限和退避，别裸着上。

但要小心：并行只在子任务互不影响时安全。

两个子 agent 同时改同一个文件，得到的是随机的半个文件。

第 9 节细说。

## 3. 拆的三种形态

拆不是一种东西。

它是三种，成本差很远。

这三种不是"复杂度递增"的关系。

它们是三种不同的取舍：省代码、省上下文、省决策。

选错了，你会用最贵的那种去解决最便宜的问题。

```text
形态 A  工具化的子 agent
        包一层函数，同步调用，主 agent 拿一行字符串

形态 B  委派带独立上下文
        子 agent 有自己的 system prompt、自己的工具集、自己的 messages

形态 C  流水线
        固定角色按固定顺序串起来，人定顺序，没有"主 agent 决策"
```

### 3.1 形态 A：工具化的子 agent

最轻的一种。

主 agent 的上下文里只多了一条工具说明书。

子 agent 内部的循环、报错、重试，对主线完全不可见。

```text
主 messages：
  system
  user
  assistant(tool_calls: delegate(...))
  tool: "结论是 X"
```

适合：子任务很短、结论能用一句话说清、不需要独立人格。

比如"把这个 SQL 跑一下，告诉我行数"。

这种其实连子 agent 都不算，更像一个会多跑几步的工具。

### 3.2 形态 B：委派带独立上下文

真正的多 Agent 从这里开始。

关键差别是：子 agent 有**自己的** system prompt 和**自己的**工具集。

主 agent 传过去的东西只有两样：

```text
task     要它做什么
context  它能用到的背景（不是全部历史）
```

子 agent 看不到主对话。

这是优点，也是最大的信息风险。

优点：它的上下文是干净的，不会被主线的废话干扰。

风险：它不知道主线上已经否定过的方案，会重新试一遍。

### 3.3 形态 C：流水线

三个角色，固定顺序。

```text
检索 agent → 分析 agent → 写作 agent
```

没有主 agent 决策，顺序写在代码里。

这是最容易调的一种，因为控制流是死的。

也是最容易被误用的一种：任务稍微一变，流水线就要改代码。

什么时候用流水线？

当你的任务**形状固定**，只是内容在变。

比如每天跑一次的日报生成。

什么时候不用？

当你不确定下一步该做什么的时候。

那种情况需要的是[10 篇](./2026-11-09-10-agent-planning-decomposition.md)的规划器，不是流水线。

三种形态怎么选？

```text
子任务一句话能说清，结论一句话能带回   → 形态 A
子任务需要自己的规矩和自己的工具        → 形态 B
任务形状固定、每天跑一样的流程          → 形态 C
```

绝大多数人一开始就该用形态 A。

它最便宜，出错时最好查，要改只动一个函数。

形态 B 是主力，也是这篇后半段的重点。

形态 C 最像"系统"，也最容易在需求一变的时候变成技术债。

## 4. 最小代码：把 run_agent 包成工具

先看子 agent 的全部实现。

它真的只是一个函数。

代码来源：

```text
labs/L01_agent_loop/agent.py
```

```python
def run_agent(model, tools, messages, max_steps=10, verbose=True) -> str:
    for step in range(1, max_steps + 1):
        reply = model.chat(messages)
        messages.append(reply)
        if not reply.tool_calls:
            return reply.content
        for call in reply.tool_calls:
            observation = _execute(call, tools)
            messages.append(
                Message(role="tool", content=observation, tool_call_id=call.id)
            )
    return f"（达到最大步数 {max_steps}，强制停止）"
```

这就是子 agent 的全部。

注意它的签名收什么：`model`、`tools`、`messages`。

三样都是你给的。

所以"子 agent 有自己的上下文"这句话，翻译成代码就是：

```text
我给它一个新的 messages 列表。
```

就这一件事。

下面是 `delegate`，二十四行。

```python
SUB_SYSTEM = """你是一个只负责一件小事的子 agent。
你不和用户对话。做完就返回结构化摘要，不要寒暄，不要问问题。"""

def delegate(task: str, context: str = "", max_steps: int = 8) -> str:
    """把一个能独立完成的子任务交给子 agent，只把摘要带回来。

    子 agent 有自己全新的 messages —— 这是拆分的全部价值。
    """
    sub_messages = [
        Message("system", SUB_SYSTEM),
        Message("user", f"任务：{task}\n\n背景（只给必要的）：\n{context}"),
    ]
    try:
        raw = run_agent(
            make_model(),     # 子 agent 用哪个模型由这里决定，可以更小更便宜
            SUB_TOOLS,        # 子 agent 能看见的工具，和主 agent 分开
            sub_messages,
            max_steps=max_steps,
            verbose=False,
        )
    except Exception as exc:
        return f"错误：子 agent 崩溃 {type(exc).__name__}: {exc}"
    return normalize_summary(raw)   # 见第 8 节：拿不到摘要就当失败
```

三行注释值得单独说。

第一行：`make_model()`。

子 agent 不必用主 agent 的模型。

查资料这种活，用便宜的模型就够了。

这一步是省钱的主要来源，很多人忘了。

第二行：`SUB_TOOLS`。

工具集不共享。

子 agent 拿不到主 agent 的写文件权限，就写不坏东西。

这是[13 篇](./2026-11-09-13-agent-security-permissions-sandbox.md)最小权限原则在多 Agent 里的直接应用。

第三行：`normalize_summary`。

子 agent 返回的东西可能是任何形状。

在边界上做一次校验，比在主 agent 里做十次猜测便宜。

接下来把它注册成工具。

```python
TOOLS = {
    "calculator": calculator,
    "delegate": delegate,
}

DELEGATE_SPEC = {
    "name": "delegate",
    "description": "把一个可以完全独立完成的子任务交给子 agent。"
                   "它看不到当前对话，所以 task 必须写完整、自包含。",
    "parameters": {
        "type": "object",
        "properties": {
            "task": {"type": "string", "description": "要它做什么，一句话说清"},
            "context": {"type": "string", "description": "它能用到的背景，别塞整个历史"},
        },
        "required": ["task"],
    },
}
```

`description` 里那句"它看不到当前对话"，是整个设计里最重要的一个提示。

模型看到这句话，才会把 task 写完整。

看不到这句，它会写 `task="继续"`。

然后把主 agent 跑起来：

```python
messages = [
    Message("system", "你是项目经理。遇到需要独立调研的子任务，用 delegate。"),
    Message("user", "帮我评估一下这三个方案，哪个能在这周上线。"),
]
answer = run_agent(model, TOOLS, messages, max_steps=12)
```

就这些。

没有框架，没有编排引擎，没有 DAG。

多 Agent 的骨架就是"一个函数调另一个函数"，加上一句"它看不到我的上下文"。

这段代码里唯一"高级"的地方，是 `SUB_SYSTEM` 那三句话。

它干的事是：把子 agent 的角色和边界写死。

不让它和用户对话，不让它反问，不让它寒暄。

为什么？

因为子 agent 的每一句废话，最后都会变成主 agent 上下文里的一段噪音。

写死它的输出形状，比事后清洗便宜。

## 5. 一次委派的完整生命周期

把时间轴摊开。

```text
主 step 1
  模型 → tool_calls: delegate(task="评估方案 A 的上线风险", context="...")
  ↓
  你执行 delegate()
  ↓
  新建 sub_messages（system + user，无历史）
  ↓
  子 step 1    模型 → 调 read_file
               工具 ← 文件内容
  子 step 2    模型 → 调 calculator
               工具 ← 数字
  子 step 3    模型 → 最终回答（一段 JSON）
  ↓
  子循环结束，sub_messages 被丢弃
  ↓
  主 step 2
  模型 → tool_calls: delegate(task="评估方案 B ...")
  ...
  主 step 5
  模型 → 最终回答
```

这张图里有四个容易被忽略的事实。

第一个：子 agent 的 messages 在返回后就没了。

除非你把它存下来（[14 篇](./2026-11-09-14-agent-observability-and-cost.md)讲怎么存），否则它是一段只活几秒的历史。

出问题的时候，你只有一句结论，没有过程。

第二个：主 agent 看到的是**一条 tool 消息**。

不是三次工具调用，不是两段推理。

就是一条字符串。

所以主 agent 的上下文增长是"每个子任务一条摘要"，不是"每个子任务的全部过程"。

这是上下文隔离的具体收益。

第三个：子 agent 的步数消耗在子循环里。

主 agent 的 `max_steps=12`，不会因为子 agent 跑了 8 步而减少。

```text
总步数 = 主步数 + Σ(每个子任务的步数)
```

一次委派，可能就是主 agent 十步之外多出来的八步。

这个账要单独算。

第四个：子 agent 的 `tool_call_id` 和主 agent 的没关系。

主 agent 那一条 `delegate` 调用的 id，属于主线。

子 agent 内部那八次调用的 id，属于子线。

两条线各有各的编号空间，不要指望能对上。

要对上，只能靠你在记录里写一个父子关系，[14 篇](./2026-11-09-14-agent-observability-and-cost.md)讲怎么记。

顺手说一句 `verbose=False`。

子 agent 的打印不能进主 agent 的 stdout。

不然你会看到十几层缩进的日志混在一起，最后一次工具调用淹没在两百行输出里。

子 agent 的输出要么进 trace，要么丢掉，不要进终端。

## 6. 委派的真正成本

拆有收益，但成本不是零。

是五项，而且都是隐性成本。

### 6.1 上下文复制

主 agent 要把"它能用到的背景"写进 `context` 参数。

写多少？

写少了，子 agent 缺信息，给你一个错误结论。

写多了，你在为同一段话付两次 token。

```text
主上下文里有 2000 token 的背景，
你挑了 800 token 塞进 context，
子 agent 里等于又多了一份 800。
```

更麻烦的是：这 800 token 是**人工挑选**的。

挑选逻辑写在代码里，就是一段新的、需要维护的、会出 bug 的逻辑。

一个真实的挑选逻辑长这样。

```python
context = f"""
用户原始需求：{user_msg}
已确认的约束：{constraints}
不要尝试：{rejected_approaches}
"""
```

三行，每一行都是人肉判断。

`constraints` 从哪来？上一轮谁写的？

`rejected_approaches` 漏了一条，子 agent 就会把已经被否掉的方案再试一遍。

这类 bug 不会报错，只会让结论慢慢变差。

### 6.2 信息在边界丢失

这是最贵的一项，也是开篇那次事故的原因。

子 agent 知道的东西 ≠ 子 agent 说出来的东西 ≠ 主 agent 理解的东西。

```text
子 agent 的上下文        100%
它写进结论的             20%
主 agent 读懂的           15%
```

每过一道边界，信息就掉一层。

这个衰减不是模型的错。

是"摘要"这个动作本身有损。

你让一个 agent 概括自己做的事，它会优先保留"我做成了什么"，弱化"我发现了什么问题"。

因为前者是它的目标，后者是它的副产品。

边界越多，丢得越多。

流水线三个角色，就是两道边界。

所以能少一道边界，就少一道。

### 6.3 错误放大

单 agent 出错，错在一步。

多 agent 出错，错会被下游继承并放大。

```text
子 agent 把"周五"理解成"下周五"
主 agent 基于这个日期排了计划
你看到的结论是完全合理的，只是日期错了
```

这种错最难查。

因为每一步单看都成立，只有全局是错的。

而且这种错会传染。

下游的措辞越自信，你越不会去查上游。

```text
"根据调研结果，方案 A 可以在本周上线。"
```

这句话每个字都合理。

错的只是上游那一句"周五"。

### 6.4 调试难度

单 agent 出问题，你看一条 messages 列表。

多 agent 出问题，你要看 N 条 messages 列表，还要看它们的时间顺序。

```text
哪一步开始错的？
是子 agent 错了，还是主 agent 传的 context 少了？
还是子 agent 对了，但摘要写得含糊？
```

三个问题，三份日志，三种可能。

调试成本不是线性涨的，是乘法涨的。

### 6.5 成本翻倍

token 账很简单：

```text
一个任务 = 主 agent 的所有请求 + 所有子 agent 的所有请求 + 每次委派的 context 复制
```

主 agent 的 system prompt 和工具说明书，每一轮都要重发。

子 agent 也有自己的 system prompt，也要每一轮重发。

```text
拆成 3 个 agent，固定成本就乘了 3 倍。
```

再加上委派本身至少两次模型调用（子 agent 起手一次、收尾一次），

一次委派的成本下限，比你想的高。

算一个具体形状。

一个三个 agent 的流水线：主 agent 跑 5 步，三个子 agent 各跑 4 步。

模型调用次数是 5 + 3×4 = 17 次。

单 agent 做同一件事，大概 8 次。

而 system prompt 和工具说明书这堆固定成本，在 17 次里每次都要重发。

> **反直觉的点**：多 Agent 的收益来自**上下文隔离**，不来自"多个脑子更聪明"。
>
> 如果你拆完发现主线上下文没变短、工具没变少、system prompt 没变干净、也没有并行，
> 那你只是把一次调用变成了三次，顺便把调试难度乘了三。

## 7. 接口设计：主 agent 只拿结论，不拿过程

拆多 Agent，九成的坑在接口上。

接口就一句话：

```text
子 agent 交回来的，必须是结论，不是过程。
```

为什么？

因为主 agent 的上下文是最贵的资源。

你要是把子 agent 的完整 messages 塞回去，那"上下文隔离"这件事就白做了。

```text
错误做法：return json.dumps([m.__dict__ for m in sub_messages])
正确做法：return 一段 300 字以内的结构化摘要
```

错误做法的后果很具体。

子 agent 的完整 messages 通常是几千 token，塞回主线一次，刚省下来的窗口就吃光了。

而且它带着子 agent 的 system prompt 和一堆主 agent 根本用不上的工具调用记录。

主 agent 会开始模仿那个子 agent 的语气。

但只给结论也有风险。

主 agent 拿到"方案 A 不成立"，它没法判断这个结论有多硬。

所以摘要要带三样东西：

```text
结论      一句话，可执行
证据      3 条以内，能被人复核
不确定项  它自己没把握的地方
```

这就是下一节的结构。

这里先定一条硬规矩：

```text
子 agent 不允许返回"过程"。
过程只进 trace，不进主上下文。
```

过程是给调试用的，结论是给决策用的。

两样东西混在一起，两边都做不好。

接口还有第二个决定：失败怎么回。

三种选择，成本差很远。

```text
抛异常              主 agent 的循环直接崩，整个任务失败
返回 "失败"         主 agent 不知道能不能重试，通常就放弃了
返回结构化失败      主 agent 能判断：换参数、换子 agent，还是上报
```

选第三种。

失败也是一种结论，它同样需要证据和不确定项。

## 8. 子 agent 的返回必须结构化

自由文本的摘要，主 agent 读起来"好像懂了"，实际上没法用。

因为下一步它要靠这个结论做判断。

所以返回是一个固定的 JSON。

```json
{
  "conclusion": "方案 A 不成立：第三步需要写权限，当前凭据只有只读。",
  "evidence": [
    "check_perm 返回 readonly",
    "方案 A 的步骤 3 脚本包含 write_file"
  ],
  "confidence": 0.7,
  "uncertainties": ["没验证过换成服务账号能不能绕开"],
  "artifacts": ["labs/report_a.md"]
}
```

五个字段，各有用处。

`conclusion` 是主 agent 真正要读的那一行。

`evidence` 是让它能复核的。没有证据的结论，主 agent 只能信或不信，没有第三种选择。

`confidence` 是让它知道该不该再找一个子 agent 交叉验证。

`uncertainties` 是最容易被删掉、也最该保留的一项。

开篇那次事故，如果子 agent 老实写了 `"uncertainties": ["关键约束 X 只在过程中出现过"]`，主 agent 就有机会追问。

`artifacts` 是文件路径。大块内容不要塞进 JSON，放文件里，摘要里只留路径。

这个思路在第 6 节"信息在边界丢失"那里已经埋了伏笔：

```text
JSON 里放指针，不放正文。
```

还有一条容易被违反的规矩：字段名不要改。

主 agent 的 system prompt 里会提到 `conclusion` 和 `uncertainties`。

你哪天把 `uncertainties` 改名成 `risks`，主 agent 就开始忽略它。

字符串契约比函数签名脆，因为它没有类型检查。

还有一条：给摘要设长度上限。

```text
conclusion     一句话，超过 200 字就该拆成两条
evidence       最多 5 条
uncertainties  最多 3 条
```

没有上限的摘要，会慢慢长成一份报告。

而报告会重新把主线的上下文撑爆。

你就绕回了拆之前的位置，还多付了一次委派的钱。

然后是校验。

模型不一定听话，所以边界上要兜一层。

```python
def normalize_summary(raw: str) -> str:
    """子 agent 的返回必须是这个形状；不是就降级，别让主 agent 猜。"""
    try:
        data = json.loads(raw)
        assert isinstance(data.get("conclusion"), str) and data["conclusion"]
    except Exception:
        return json.dumps({
            "conclusion": raw.strip()[:500],
            "evidence": [],
            "confidence": 0.3,
            "uncertainties": ["子 agent 没按格式返回，这是它的原文截断"],
        }, ensure_ascii=False)
    return json.dumps(data, ensure_ascii=False)
```

注意降级策略：解析失败不是抛异常，是**把失败本身变成一条可读的结论**。

这跟 `_execute` 的设计是同一个思路。

错误也是观测。

[08 篇](./2026-11-09-08-agent-structured-output.md)讲过怎么用 schema 约束和重试修复让模型稳定吐 JSON。

这里只加一条多 Agent 特有的规矩：

```text
子 agent 的 JSON 解析失败，不能让整个主任务失败。
```

一个子任务废了，主 agent 还能换个方式做。

整条链断了，就什么都没有。

## 9. 并行与串行

并行是拆的最硬收益。

但并行只在一种情况下安全：

```text
子任务之间没有共享的可变状态。
```

翻译成人话：

```text
只读的，可以并行。
要写的，必须串行，或者加锁。
```

看代码。

```python
from concurrent.futures import ThreadPoolExecutor

def delegate_many(tasks: list[tuple[str, str]]) -> list[str]:
    """并行跑多个互不依赖的子任务，返回顺序和 tasks 一致。"""
    with ThreadPoolExecutor(max_workers=4) as pool:
        futures = [pool.submit(delegate, task, ctx) for task, ctx in tasks]
        return [f.result() for f in futures]
```

`max_workers=4` 不是随便写的。

它同时是你的**并发上限**和**成本上限**。

四个子 agent 一起跑，遇到限流（429）的概率也一起涨。

所以真实工程里，这个数字要配一个重试和退避。

串行的场景长这样：

```text
子 agent 1 写 report.md
子 agent 2 读 report.md 并追加结论
```

这两个一旦并行，子 agent 2 读到的可能是空文件、半截文件，或者旧版本。

```text
读-改-写 这种链，天然是串行的。
```

还有一种半并行：先并行采集，再串行汇总。

```text
并行：3 个子 agent 各查一个数据源
串行：主 agent 拿 3 份摘要，写最终结论
```

这是最常用的形状。

因为它把"慢的 I/O"并行了，把"需要全局视野的判断"留在了主线。

并行的另一个代价：观测顺序乱了。

串行时，messages 的顺序就是发生顺序。

并行时，四个子 agent 的返回是"谁先完成谁先到"。

主 agent 看到的摘要顺序，和它发出任务的顺序不一样。

模型会因此误判因果。

```text
它以为 B 是在 A 之后做的，其实两个是同时做的。
```

修法很简单：回来之后按发出顺序重排，不要按完成顺序 append。

判断并行还是串行，只看一件事。

```text
子任务会不会写同一份东西？
会   → 串行，或者加锁
不会 → 并行
```

"同一份东西"包括同一个文件、同一条数据库记录、同一份内存里的 state。

也包括"同一个预算"。

四个子 agent 并行烧一份额度，额度会超。

## 10. 什么时候不该拆

这一节比前面九节都值钱。

### 10.1 能用一个工具解决

最容易拆错的情况，是子任务其实只是一个函数。

```text
不该拆：delegate(task="查一下这个文件的第 30 行")
该做：   read_file(path, line=30)
```

判断标准：

```text
这个子任务需要模型做判断吗？
不需要 → 它是工具，不是 agent。
```

一个工具调用只要几毫秒，一次子 agent 要几秒和几百 token。

别用 agent 做工具的事。

### 10.2 上下文还没满

拆的最大理由是上下文不够。

那如果上下文还空着呢？

```text
你的 messages 常年在 3k token，
上下文窗口是它的几十倍，
你却拆了三个 agent。
```

这叫用架构解决一个不存在的问题。

判断标准：

```text
先量一次真实任务的峰值 token。
没到窗口的 50%，别拆。
```

不是 80%，是 50%。

因为你要留出余量给工具观测的尖峰。

### 10.3 子任务强耦合

有些子任务是"你一句我一句"的。

```text
分析 → 发现异常 → 回去重新检索 → 再分析
```

这种循环里，第二步强烈依赖第一步的中间结果。

拆开之后，子 agent 之间要靠 `context` 参数来回传中间结果。

传着传着，你就在手工实现一个共享内存。

```text
强耦合的子任务，拆开只是把一次上下文变成了两次 context 序列化。
```

判断标准：

```text
子任务 B 需要子任务 A 的中间过程（不只是结论）吗？
需要 → 别拆。
```

三条合起来，其实是一条：

```text
拆的理由必须是"上下文"，不是"结构好看"。
```

还有一个可操作的办法：用 eval 判断。

把同一个任务，用单 agent 跑一遍，用拆开的三 agent 跑一遍。

比三样东西：

```text
通过率
P95 时延
单任务 token
```

拆开那个赢了两样，才拆。

一样都不赢，你只是买了个更贵的架构。

还有一种情况：上下文没满，但你怕它以后会满。

那是提前优化。

等它真的满了再拆，你会更清楚该在哪一刀切下去。

## 11. 三个反模式

### 11.1 为了演示而拆

```text
一个 agent 能做完的事，拆成"研究员 + 分析师 + 写手"。
```

这种拆分在 demo 里很好看。

因为每个角色都能单独演示，讲故事也顺。

上线之后，它比单 agent 慢三倍、贵三倍、错得更隐蔽。

判断方法：

```text
把三个角色合并成一个，任务结果会变差吗？
不会 → 这个拆分只是为了演示。
```

更隐蔽的是，这种拆分会让 eval 变好看。

因为每个角色的输出都变短了，看起来"更聚焦"。

但端到端的通过率没变，甚至更低。

[09 篇](./2026-11-09-09-agent-evals.md)讲的端到端用例，就是专门防这个的。

### 11.2 agent 之间互相聊天没有终止条件

最危险的一种。

```text
agent A 把结果发给 B
B 觉得有问题，发回给 A
A 又改一版发给 B
...
```

两个模型互相客气，可以聊到你的额度见底。

这和单 agent 的死循环是同一个病，只是更难发现。

因为看起来"它们在讨论"。

必须有终止条件，而且是硬条件：

```python
MAX_ROUNDS = 3

for round_no in range(1, MAX_ROUNDS + 1):
    reply = b_agent.review(a_agent.draft())
    if reply.verdict == "pass":
        break
else:
    # 循环跑满了还没通过 —— 这不是"继续讨论"，这是失败
    return "错误：评审 3 轮未通过，交人工"
```

注意 `for ... else` 的用法：跑满没 break 就是失败。

不是"再聊一轮"，是**停下来交人**。

两个模型互评，还有一种更隐蔽的失败。

它们会迅速达成一致，然后一起错。

```text
A 说方案可行。
B 说"我同意，补充一点……"
A 说"这个补充很好。"
评审通过。
```

因为互评的 prompt 里通常写着"请礼貌地指出问题"。

模型对"礼貌"的理解，是少否定。

所以互评的价值，取决于你有没有明确要求它给出**反对意见**，而不是"意见"。

### 11.3 递归委派爆栈

子 agent 也能调 `delegate`。

于是它会给自己再派一个子 agent。

再派一个。

```text
主 agent (depth 0)
  └ 子 agent (depth 1)
      └ 孙 agent (depth 2)
          └ 曾孙 agent (depth 3)
              └ ...
```

每一层都有自己的 system prompt 和工具说明书。

token 消耗是指数级的，而你只会看到一句"任务进行中"。

修法是显式的深度上限。

```python
_DEPTH = {"n": 0}      # 真实工程用 contextvar，别用全局变量

def delegate(task: str, context: str = "") -> str:
    if _DEPTH["n"] >= 2:
        return "错误：委派层数已到上限（2 层），这个任务请你自己做完。"
    _DEPTH["n"] += 1
    try:
        return _delegate_inner(task, context)
    finally:
        _DEPTH["n"] -= 1      # 一定要在 finally 里减回去
```

两个细节。

`finally` 里的减一不能省。

省了的话，一次异常就让深度永久卡在 1，之后所有委派都被拒。

上限建议是 2。

一层用于把任务拆小，一层用于把子任务再拆小。

再深就不是拆任务了，是在生成组织架构图。

还有一种变形：A 拆给 B，B 把同一件事拆回 A。

两个 agent 互相委派，深度上限拦不住，因为它们在同一个深度上打转。

拦这个的不是深度，是任务去重。

```text
同一个 task 字符串，只允许被委派一次。
```

简单，但你得先想到。

## 12. 回到真实工程

回头看 L01 的三段演示，它们其实已经包含了多 Agent 需要的一半东西。

代码来源：

```text
labs/L01_agent_loop/run.py
```

```python
def retry(messages):
    return Message(
        role="assistant",
        content=f"刚才算不了（{last_tool_result(messages)}），我换个式子再试。",
        tool_calls=[ToolCall(id="s2_retry", name="calculator",
                             args={"expression": "10 / 2"})],
    )
```

这是场景 2 的自愈。

它证明了一件事：模型看到错误观测后，会换方案。

多 Agent 里，这条规律照样成立，只是范围变了。

```text
单 agent：工具报错 → 模型换参数
多 agent：子 agent 报错 → 主 agent 换个 task，或者换个子 agent
```

所以 `_execute` 的一条设计要原样搬过去：

```text
工具永远返回字符串，永远不抛异常。
```

子 agent 的边界也一样：`delegate` 永远返回字符串，永远不抛异常。

再看保险丝。

代码来源：

```text
labs/L01_agent_loop/agent.py
```

```python
    # 4. 保险丝：模型一直不肯收尾时强制停止，否则它会烧你的钱
    if verbose:
        print(f"\n** 达到最大步数 {max_steps}，强制停止 **")
    return f"（达到最大步数 {max_steps}，强制停止）"
```

多 Agent 的保险丝不是一个，是一组：

```text
每个子 agent 的 max_steps
整个任务的委派次数上限
整个任务的 token 预算
整个任务的墙钟超时
```

四个都要有。

只设 `max_steps` 的话，一个主 agent 调 20 次 `delegate`，每次子 agent 跑 8 步，总步数就是 180。

你的 `max_steps=12` 一点用都没有。

场景 3 里那个 `AlwaysToolModel` 就是这件事的最小演示。

它永远只要求调工具，`max_steps=3` 一到，循环返回一句"强制停止"。

注意它返回的是**字符串**，不是异常。

主 agent 拿到这句话，还能继续处理。

子 agent 撞到步数上限，也应该这样返回。

```text
子 agent 的上限，不应该表现成主 agent 的崩溃。
```

还有一件事，L01 里没有，但拆开之后必须有。

`_execute` 的兜底只管"工具抛异常"。

子 agent 还有一种失败：它没抛异常，但结论是空的、或者自相矛盾。

```text
工具层面的失败，_execute 兜住了。
语义层面的失败，只有校验能兜。
```

两条都要有。

[05 篇](./2026-11-09-05-agent-error-selfheal-fuse.md)讲的是第一条，这篇第 8 节讲的是第二条。

## 13. 读代码时怎么判断

看到一段多 Agent 代码，问五个问题。

第一个：

```text
子 agent 的 messages 是新建的，还是复用了主 agent 的？
```

复用的话，上下文根本没隔离，你只是多花了一次调用的钱。

第二个：

```text
主 agent 拿到的是摘要，还是子 agent 的完整过程？
```

拿到完整过程的，等于没拆。

第三个：

```text
子 agent 能用哪些工具？和主 agent 一样吗？
```

一样的话，最小权限原则没落地。

第四个：

```text
委派深度有上限吗？委派次数有上限吗？
```

两个都没有，就是在等一次爆栈。

第五个：

```text
子 agent 的返回，解析失败会怎样？
```

会让整个任务失败的话，这个系统在真实流量下活不过一周。

五个问题能秒答，你就看懂了这套多 Agent 的真实成本。

答不上来的，多半是"看起来拆了，其实只是加了层函数调用"。

再补一句经验判断。

如果一个多 Agent 系统的代码量，超过它要解决的问题本身的代码量。

那它大概是在做架构，不是在做事。

拆分的价值，应该体现在"少写了多少上下文拼接"上。

不是体现在"多了几个类"上。

## 14. 小结

这篇只回答一个问题。

```text
什么时候该拆？
```

四个信号：

```text
上下文塞不下
工具太多选错
子任务要独立的 system prompt
需要并行
```

三种形态：

```text
工具化的子 agent
委派带独立上下文
流水线
```

五项成本：

```text
上下文复制
信息在边界丢失
错误放大
调试难度
成本翻倍
```

三条不该拆：

```text
一个工具能解决
上下文还没满
子任务强耦合
```

一句要一直记着的话：

```text
多 Agent 的收益来自上下文隔离。
它不是"更多脑子"，是"更干净的上下文"。
```

判断顺序也就出来了。

量一次 token，数一遍工具，看 system prompt 有没有冲突，再看能不能并行。

四样里一个都不占，就别拆。

拆了只会多出四样东西：

```text
更多的钱
更长的链路
更难查的 bug
更少的可复现性
```

下一篇换个方向，讲一件比多 Agent 更该早点做的事：

```text
Agent 系统讲解 13：安全：提示注入、权限和沙箱
```

那一篇会从一条工具返回结果里藏的指令讲起：

```text
为什么"在 prompt 里写不要听别人的"不算防御？
权限该分成几级？
审批怎么做成一次工具调用？
那条 rm -rf 应该在哪一层被拦住？
```

安全边界只能画在代码里。

这句话到时候会展开讲。
