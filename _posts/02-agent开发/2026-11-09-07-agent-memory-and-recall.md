第二天早上，你打开同一个 agent，说：

```text
接着昨天那个任务往下做。
```

它回你：

```text
你好！请问你需要我做什么任务？
```

你没换代码，没换模型。

你只是关了一次终端。

上一篇讲的是：历史太长，这一轮发什么。

这一篇讲的是：进程都没了，下次发什么。

## 1. 会话结束，messages 就没了

先看一眼那个东西到底存在哪。

代码来源：

```text
labs/L01_agent_loop/run.py
```

```python
messages = [
    Message("system", SYSTEM),
    Message("user", "帮我算一下 (12 + 8) * 3 等于多少？"),
]
```

`messages` 是一个 Python 列表。

它在 `scene_1()` 里面。

函数返回，列表就被回收。

进程退出，内存全清。

```text
你的 agent 没有"记忆"这个变量。
它只有"这一次还没被回收的局部变量"。
```

这解释了一堆看起来很神秘的现象。

换个窗口，它不认识你了。

重启服务，它忘了刚才的结论。

同一个任务分两次问，它从头开始。

不是它健忘。

是那 7 条消息已经不在内存里了。

[06 篇](/posts/agent-context-engineering/)说过：模型是无状态的，记忆在 messages 里。

现在要补一句更狠的：

```text
messages 也是有状态的。
它的状态，等于你的进程还活着。
```

## 2. 三种时间尺度的记忆

「记忆」这个词在 agent 里被用得很乱。

先按时间切成三层。

```text
第 1 层：单轮上下文
  活多久：一次请求
  存在哪：你拼出来的 messages
  丢了会怎样：这一句回答变差

第 2 层：会话内历史
  活多久：一个进程 / 一次会话
  存在哪：那个不断 append 的 list
  丢了会怎样：多轮任务做不下去

第 3 层：跨会话记忆
  活多久：几天到几年
  存在哪：磁盘、数据库、别人的服务
  丢了会怎样：每次都要重新自我介绍
```

三层的失效方式完全不同。

第 1 层失效，是裁剪裁错了。

第 2 层失效，是进程重启了。

第 3 层失效，是**你根本没实现**。

大部分人卡在第 3 层。

但他们的注意力全在第 1 层。

他们在调 `messages[-8:]` 还是 `messages[-12:]`。

却从来没有让 agent 往磁盘写过一个字。

把三层放在一起对照，会看得更清楚。

| 层 | 存哪 | 活多久 | 坏掉时你会看到 |
|---|---|---|---|
| 单轮上下文 | 这一次请求的 messages | 一次请求 | 回答跑题、漏掉刚说的约束 |
| 会话内历史 | 进程内存里的 list | 一次会话 | 多轮任务做不下去、重复调工具 |
| 跨会话记忆 | 磁盘 / 数据库 | 天到年 | 每次都要重新自我介绍 |

看最后一列。

三层坏掉，症状完全不同。

```text
"它忘了我刚说的"     → 第 1 层
"它忘了我们在做什么" → 第 2 层
"它不认识我"         → 第 3 层
```

工程上最常见的误判是：把第 3 层的症状，当成第 1 层去修。

于是你去加窗口、去调裁剪阈值、去重写 system prompt。

修好一阵，下次开新会话又回到原点。

一句：

```text
先判断"它忘的是哪一层"，再动手。
```

## 3. 反直觉：不是检索不行，是没写进去

这一篇最重要的结论，先放这里。

> **大多数 agent 的「记不住」，不是检索不行，是根本没写进去。**

你可以自己验一下。

打开你的 agent 项目，找那个存记忆的文件或表。

如果它是空的，那问题不在检索。

如果它连文件都没有，那问题更明显。

为什么大家会误判成「检索不行」？

因为调试路径是这样走的：

```text
1. 用户说「你昨天不是知道吗」
2. 你去看检索代码
3. 检索代码确实存在，也确实返回了 []
4. 你开始调相似度阈值、换 embedding 模型、加 rerank
5. 还是 []
```

第 3 步骗了你。

`[]` 有两种原因：没查到，和没有。

你一直在优化前者。

真实情况通常是后者：

```text
写入的通路，压根没接。
或者接了，但触发条件是"用户说记住"。
而用户从来不说这两个字。
```

一句判断：

```text
先数一遍你的存储里有几条。
个位数 → 写入问题。
上千条但召回不准 → 检索问题。
```

顺序不能反。

先去修写入。

怎么数？不用改业务代码。

```python
from pathlib import Path

def audit(path="memory.md"):
    p = Path(path)
    if not p.exists():
        return {"文件": "不存在", "条目数": 0}
    lines = [l for l in p.read_text(encoding="utf-8").splitlines()
             if l.startswith("- ")]
    return {"文件": str(p), "条目数": len(lines),
            "最近一条": lines[-1] if lines else None}

print(audit())
```

跑一下。

输出 `条目数: 0`，或者「文件不存在」，问题就定位了。

不是检索不行。

是根本没有东西可检索。

这段代码的价值不在逻辑，在于它把一句感觉变成了一个数字。

```text
感觉：它好像记不住。
数字：0 条。
```

## 4. 跨会话记忆的最小实现

最小的跨会话记忆，三个东西就够。

```text
一个文件
一个读函数
一个写函数
```

不用向量库。

不用数据库。

不用 embedding 模型。

文件就是 Markdown。

理由有四条。

```text
人能直接看，能直接改，能直接删。
git 能 diff，能回溯，能 review。
出问题时你能一眼看出它记错了什么。
不需要任何服务，不花钱。
```

选 Markdown 不是因为优雅。

是因为**记忆系统最需要的能力是「可检查」**。

一个你看不见的记忆，你没法修。

代码来源（这一篇的示例文件，不在 labs 里，你可以自己建）：

```text
memory.py
```

```python
import re
from pathlib import Path

PATH = Path("memory.md")


def load_all() -> dict[str, list[str]]:
    """把 memory.md 解析成 {分节: [条目, ...]}。文件不存在就是空记忆。"""
    if not PATH.exists():
        return {}
    out, cur = {}, None
    for line in PATH.read_text(encoding="utf-8").splitlines():
        if line.startswith("## "):
            cur = line[3:].strip()
            out.setdefault(cur, [])
        elif line.startswith("- ") and cur:
            out[cur].append(line[2:].strip())
    return out


def save_all(data: dict[str, list[str]]) -> None:
    """整份重写。文件很小，重写比增量修改安全。"""
    lines = ["# 记忆", ""]
    for sec in ("事实", "偏好", "事件"):
        lines.append(f"## {sec}")
        lines += [f"- {item}" for item in data.get(sec, [])]
        lines.append("")
    PATH.write_text("\n".join(lines), encoding="utf-8")
```

二十几行。

它做了一件很朴素的事：读成 dict，改 dict，写回去。

为什么整数重写，不做增量插入？

因为增量插入的代码会长三倍，而且每加一种格式就要改一次。

记忆文件通常只有几 KB。

重写的成本可以忽略。

## 5. memory.md 的实际格式

光有代码不够，格式要定死。

否则第一次写入就会长成一篇散文。

一个真实的样子（下面这一整块就是文件内容，缩进只是排版）：

    # 记忆

    ## 事实
    - 用户在杭州，时区 Asia/Shanghai <!-- 2026-11-02 -->
    - 正在写一个 18 篇的 Agent 教学系列 <!-- 2026-11-05 -->
    - 手上的代码在 D:\Agent开发学习\labs <!-- 2026-11-05 -->

    ## 偏好
    - 回答要短，不要客套话 <!-- 2026-11-02 -->
    - 代码用 Python，不要 TypeScript <!-- 2026-11-03 -->

    ## 事件
    - 卡在 L02 的工具 schema 上 <!-- 2026-11-02 -->
    - 这周没时间，下周继续 <!-- 2026-11-07 -->

三条格式规则。

```text
一、按类型分节，不按时间分节。
二、一条一行，一行只装一件事。
三、日期放 HTML 注释里。
```

第一条很关键。

按时间分节，你每次都得扫完整份才知道「他现在住哪」。

按类型分节，事实和偏好是按键查的，事件才是按时间看的。

第三条是格式上的小技巧，但很有用。

HTML 注释在渲染时看不见。

所以这份文件既适合人读，也适合程序解析。

```text
人看到：- 回答要短，不要客套话
程序看到：- 回答要短，不要客套话 <!-- 2026-11-02 -->
```

那个日期，在两种类型里含义不一样。

```text
事实 / 偏好里的日期 = 最后一次确认的时间
事件里的日期       = 事情发生的时间
```

这个区别决定了后面「过期」怎么算。

偏好确认了一年还在，说明它稳定。

事件过了一个月，通常就不该再影响判断了。

### 什么时候该换存储

Markdown 文件不是终点。

但换存储的时机，比你以为的靠后。

```text
几十条      → 文件，全量塞进上下文
几百条      → 文件 + 召回，按相关度取前几条
几千条      → 该考虑数据库了（SQLite 也算，不一定是向量库）
十万条以上  → 才轮到专门的向量检索
```

注意第三行。

几千条的时候，很多人的第一反应是「上向量库」。

其实这个规模，加一个字段过滤就够。

```text
按 user_id 过滤 → 剩下的全塞进去
```

真正让向量检索变得必要的，是「同一批记忆里措辞差异很大，而且条数多到不能全塞」。

在那之前，它带来的是额外依赖和不可解释的排序。

迁移的时候，保住两样东西就够了。

```text
一条记忆的唯一 id
写入时间
```

有这两样，任何存储之间都能搬。

没有，你就被锁在原地。

一句：

```text
先用最笨的存法跑到一千条。
跑不到，说明写入策略有问题，换存储也救不了。
```

## 6. 写入策略：记什么

先说结论：

```text
写入策略比检索策略更重要。
```

原因很简单。

写错了，检索再好也是把错的东西找出来。

写漏了，检索再好也找不到。

而检索是可替换的（换模型、换算法），写入是不能外包的（只有你知道什么值得记）。

四个筛子，一条记忆要全过。

```text
1. 以后还会用到吗？
2. 会改变 agent 的行为吗？
3. 是用户明确说的，还是模型猜的？
4. 三个月后还成立吗？
```

一条一条说。

**会不会再用到**：一次性的东西不记。

「帮我算 12+8」不需要记。

「我以后都要用 Python 回答」要记。

**会不会改变行为**：不影响行为的也不记。

用户说「今天心情不好」，这句话对回答风格可能有影响。

但它不是事实，也不稳定。

记成「当前情绪」是危险的：明天它还是「心情不好」。

**是不是用户说的**：这一条最容易被跳过。

模型自己推断出来的东西，不要写进记忆。

比如模型说「用户似乎是后端工程师」。

三个月后你会在记忆里看到一条没人说过的话。

**三个月后还成立吗**：这条筛掉的是时效性事实。

「正在调试 L02」——一周后就不成立了。

「在写一个 18 篇的系列」——三个月后大概率还成立。

一个反面例子，说明不做筛选会怎样：

```text
- 用户说帮我算一下 (12 + 8) * 3 等于多少
- 用户说好的
- 用户说谢谢
- 用户问我上次说的那个事
```

这不是记忆。

这是日志。

日志和记忆的区别是：日志只追加，记忆要维护。

### 三个具体的反例

有三种东西，很好写进去，但都不该写。

**反例一：用户的情绪。**

```text
- 用户今天很不耐烦 <!-- 2026-11-03 -->
```

明天它还在。

模型会拿它调整语气，对一个心情很好的人小心翼翼。

情绪是状态，不是记忆。

它该活在这一次会话里，会话结束就该消失。

**反例二：模型的推断。**

```text
- 用户是后端工程师，团队大概五个人 <!-- 2026-11-03 -->
```

「五个人」是用户说的，还是模型从「我们组不大」猜的？

写进去以后，没人记得它从哪来。

**反例三：一次性的任务参数。**

```text
- 用户要算 (12 + 8) * 3 <!-- 2026-11-03 -->
```

这条三个月后还在。

它不会伤害谁，但它会占一个召回名额。

召回只取前 3 条，它挤掉的可能是一条真正有用的。

一句：

```text
写之前问一遍：三个月后看到这条，我还会觉得它有用吗？
```

## 7. 什么时候记、怎么去重、怎么更新

三个写入时机。

```text
时机 A：用户显式说「记住」
时机 B：每轮结束后，抽取一次
时机 C：会话结束时，批量抽取
```

A 最准，但覆盖太少。

没人会每次都提醒你「记一下」。

B 最全，但每轮都调一次模型，成本和延迟都翻倍。

C 是常见折中。

但会话结束时进程可能已经被杀了，你得保证收尾代码真的会跑。

工程上的组合通常是 B + A：

```text
每轮结束后本地判断有没有"值得记的句子"（关键词 + 长度）
有 → 抽一次
用户说"记住" → 立刻抽，并且跳过判断
```

### 三个触发时机，各自漏什么

A / B / C 三条路都有洞。

```text
A 用户显式说"记住"
  漏：用户不说的时候。而用户几乎从不说。
B 每轮结束抽一次
  几乎不漏，但每次多调一次模型，延迟翻倍。
C 会话结束批量抽
  漏：进程被 kill、用户直接关窗口、超时退出。收尾代码可能根本不跑。
```

所以真实系统里通常是两条一起上。

```text
B 当主路径（每轮判一次要不要抽）
C 当兜底（退出前再扫一遍没抽的）
```

C 要能跑，得有一个「哪些消息已经抽过」的标记。

最省事的做法：记一个游标。

```python
import json
from pathlib import Path

STATE = Path("memory_cursor.json")

def last_done() -> int:
    if not STATE.exists():
        return 0
    return json.loads(STATE.read_text(encoding="utf-8"))["cursor"]

def mark_done(n: int) -> None:
    STATE.write_text(json.dumps({"cursor": n}), encoding="utf-8")
```

会话结束时扫剩下的：

```python
def flush(messages, model, today):
    rest = messages[last_done():]
    if not rest:
        return 0
    n = 0
    for item in extract_memories(model, rest):
        if is_safe(item["text"]):
            remember(item["type"], item["text"], today)
            n += 1
    mark_done(len(messages))
    return n
```

游标有三个好处。

```text
不会重复抽（重复抽 = 同一条被写三遍）
中断之后能接着抽
出问题时能回答"上次抽到哪"
```

有一点要注意：游标别用「历史条数」当基准。

历史会被裁剪，条数会变小。

用递增序号，或者用 `tool_call_id` 这种稳定标识。

第三种触发时机前面没提：定时。

```text
每天凌晨扫一遍当天所有会话，批量抽取、去重、清过期事件。
```

它适合「多用户、多会话」的服务端。

单机 agent 用不上。

一句：

```text
触发时机决定了你的记忆"漏多少"。
不是"准不准"，是"有没有"。
```

最后一条习惯：每次写入打一行日志。

```text
时间、类型、内容、来源会话 id。
```

没有这行日志，你说不清「这条记忆是从哪学来的」。

再说去重。

去重不是「字符串完全一样就跳过」。

而是「同一个主题只留一条」。

```text
主题 = 这条记忆在回答什么问题
```

「用户在杭州」和「用户住在杭州」是同一个主题。

「用户在杭州」和「用户下周三去上海」不是。

最省事的做法是：写入时先按主题扫一遍，有就覆盖。

```python
def remember(section: str, text: str, today: str) -> bool:
    """新增返回 True，覆盖旧的返回 False。"""
    data = load_all()
    items = data.setdefault(section, [])
    fresh = f"{text} <!-- {today} -->"
    for i, item in enumerate(items):
        if item.split(" <!-- ")[0] == text:
            items[i] = fresh          # 同一条：只更新确认时间
            save_all(data)
            return False
    items.append(fresh)
    save_all(data)
    return True
```

这个版本的去重是「原文相同」。

真实项目里要再加一层：主题相同、表述不同，也得覆盖。

做法是把主题抽成 key，值存内容。

```text
key: 用户所在城市
value: 杭州
并非 key 是"用户在杭州"这种整句
```

一句话：

```text
记忆不是一堆句子。
记忆是一组可以被覆盖的键值。
```

再说更新。

用户改主意了，怎么办？

```text
用户在杭州   <!-- 2026-11-02 -->
用户在杭州   <!-- 2026-11-09 -->   ← 只是确认，不是变化
```

```text
用户所在城市 = 杭州   <!-- 2026-11-02 -->
用户所在城市 = 上海   <!-- 2026-11-09 -->   ← 覆盖，旧值不要留
```

第二种情况，必须覆盖。

不要留两条互相矛盾的偏好。

模型看到两条，会挑一条，或者折中。

折中的回答最糟：它会说「你在杭州或上海」。

有一种例外：如果旧值对未来还有意义（比如「以前用 TypeScript，现在改用 Python」），可以在覆盖时保留一句历史。

但那是内容设计，不是数据结构问题。

数据结构上，一个主题一条。

**抽取那一步的 prompt 怎么写？**

这是整个记忆系统里唯一必须调模型的地方。

写坏了，后面全脏。

一个能用的版本：

```text
从下面的对话里，抽出"用户明确说过、以后还会用到"的信息。

规则：
- 只抽用户原话里能直接读到的内容，不要推断，不要补全
- 每条一句话，不超过 40 字
- 按类型标注：[事实] / [偏好] / [事件]
- 没有可抽的，输出 []

输出格式（JSON 数组）：
[{"type": "事实", "text": "用户在杭州"}]

对话：
{conversation}
```

注意三个约束。

```text
"只抽原话"     → 挡住模型的补全
"不超过 40 字" → 挡住把整段对话搬进去
"输出 []"      → 给模型一个"什么都不记"的合法选项
```

第三条最容易被忘。

不给空选项，模型会硬凑一条。

凑出来的那条，就是未来的污染源。

还有一步在模型外面：过黑名单。

```python
BAD = ("密码", "密钥", "身份证", "银行卡", "api_key", "token=")

def is_safe(text: str) -> bool:
    low = text.lower()
    return not any(k in low for k in BAD)
```

模型不知道你的合规要求。

别指望它在 prompt 里自己守住。

先过滤，再写盘。

## 8. 三种记忆类型

前面文件里分了三个分节。

它们不是格式上的分类，是更新策略上的分类。

| 类型 | 例子 | 更新方式 | 过期 |
|---|---|---|---|
| 事实 | 城市、时区、项目名、路径 | 覆盖（upsert） | 很少过期，但要能改 |
| 偏好 | 回答长度、语言、技术栈 | 覆盖，优先级高 | 长期有效 |
| 事件 | 某天做了什么、卡在哪 | 只追加 | 会过期，通常几周 |

这张表是这一篇唯一的一张表。

重点在第三列和第四列。

事实和偏好是「状态」：只关心现在是什么。

事件是「流水」：关心发生过什么。

两者混在一起写，就会出问题。

```text
如果把"卡在 L02"写成事实：
  三个月后模型还会以为你卡在 L02。

如果把"用户偏好简洁"写成事件：
  每次召回都要按日期排序，还容易被更新的无关事件挤掉。
```

所以分节不是为了好看。

它决定了你的 `remember()` 走哪条分支。

```text
事实 / 偏好 → 找同主题，覆盖
事件       → 直接 append，加日期
```

还有第三种情况的处理：事件过期。

不用真的删。

读的时候按日期过滤就行。

```text
事件超过 30 天 → 不参与召回
```

删不删是另一回事，第 11 节说。

## 9. 检索召回：关键词、向量、混合

写进去了，还要能取出来。

三种召回方式，各有各的盲区。

**关键词**：按字面匹配。

优点是精确、便宜、可解释。

你查「时区」，它一定把含「时区」的那条找出来。

盲区是同义词和改写。

用户问「我住哪」，记忆里写的是「所在城市：杭州」。

字面上一个字都不重合。

中文还有个额外问题：没有空格。

所以中文的关键词召回，通常用**二元字组**（bigram）当词。

```python
def _grams(s: str) -> set[str]:
    """中文没有空格，用相邻两字当检索词。"""
    s = re.sub(r"[\s，。：、；！？,.:;!?（）()\[\]\"'`]+", "", s)
    return {s[i:i + 2] for i in range(len(s) - 1)}


def recall(query: str, k: int = 3) -> list[str]:
    """按重合的二元字组打分，取前 k 条。"""
    q = _grams(query)
    scored = []
    for section, items in load_all().items():
        for item in items:
            hit = len(q & _grams(item))
            if hit:
                scored.append((hit, section, item))
    scored.sort(key=lambda x: -x[0])
    return [f"[{s}] {i}" for _, s, i in scored[:k]]
```

`recall("我上次卡在哪个工具上？")` 会命中那条事件。

因为「工具」「卡在」这些二字组重合了。

这个做法很土。

但记忆只有几十条的时候，它比向量库好用。

**向量**：把句子变成向量，按语义距离找。

优点是能跨过表述差异。

「我住哪」和「所在城市：杭州」在向量空间里很近。

代价是三项：

```text
要一个 embedding 模型（多一次网络调用）
要存向量（文件里存不下，得进库）
结果不好解释（为什么这条排第一，你说不清）
```

还有一个容易被忽略的盲区：数字、ID、专有名词。

向量对「订单号 A1234」和「订单号 A1235」几乎没区分度。

关键词对它们极其敏感。

**混合**：先用关键词做粗筛，再用向量排序。

或者反着来。

工程上更常见的做法是：结构化字段走精确匹配，自由文本走向量。

```text
用户问「我的订单 A1234 到哪了」
  → 订单号：精确匹配
  → "到哪了"：语义检索
```

一句提醒：

```text
向量库只是检索器之一。
它不是记忆系统的必要条件。
记忆条数在一百以内时，全量塞进上下文往往更好。
```

全量塞进去，模型自己会挑。

这也是一种召回，只是把选择权交给了模型。

**混合排序怎么定？**

一个够用的打分：

```python
score = 0.6 * 关键词重合度 + 0.3 * 时间新鲜度 + 0.1 * 类型权重
```

三项分别挡住三种错。

```text
关键词重合度 → 挡住"答非所问"
时间新鲜度   → 挡住"拿三个月前的事当现在"
类型权重     → 偏好 > 事实 > 事件（事件最容易过期）
```

权重不用精确。

你要的是「它能排序」，不是「它排得完美」。

而且这三个数要能改。

写在配置里，别写死在函数中间。

一句：

```text
召回的目标不是"找到最相关的那条"。
是"别漏掉该留的那条，也别塞进不相干的"。
```

### recall 的评测怎么做

召回好不好，不能靠感觉。

做法和 09 篇的评测一样：一组固定用例，一个数字。

用例长这样。

```python
CASES = [
    ("我住哪", "用户在杭州"),
    ("我上次卡在什么工具上", "卡在 L02 的工具 schema 上"),
    ("我喜欢什么风格的答案", "回答要短，不要客套话"),
    ("帮我算 1+1", None),            # 不该召回任何东西
]
```

注意最后一条。

没有它，你只知道「能不能找到」。

不知道「会不会乱找」。

评测代码：

```python
def eval_recall(cases, k=3):
    hit = 0
    for query, expect in cases:
        got = [g.split("] ", 1)[-1].split(" <!--")[0] for g in recall(query, k)]
        if expect is None:
            hit += (len(got) == 0)
        else:
            hit += any(expect in g for g in got)
    return hit / len(cases)
```

跑出来是一个 0 到 1 之间的数。

它的用处不是「打分」，是「比较」。

```text
换了分词          → 0.6 到 0.8，变好
k 从 3 调到 5     → 0.8 到 0.82，几乎没变
加了向量召回      → 0.82 到 0.9，值得
```

没有这个数，每次改动都只能凭感觉。

用例不用多。

20 条就能看出趋势。

但有两个要求。

```text
每条用例的"正确答案"必须是你手写的，不是模型生成的。
用例要覆盖三类：事实、偏好、事件。
```

答案让模型生成，你评的就是「模型和模型像不像」，不是「召回到了没有」。

再补两个指标。

```text
误召回率：不该召回的时候，召回了多少条
空召回率：该召回的时候，一条都没给
```

第二个最常见。

而它通常不是检索问题。

是写入没写全，回到第 3 节。

一次跑完只要几秒。

所以别搞成 CI，就手动跑。

```text
改了 recall()、加了分词规则、换了 k，各跑一次。
数变了就是变了，数没变就是没变。
```

## 10. 记忆污染与过期

记忆会变脏。

三个污染源。

**用户改主意**：最常见，也最好修。

覆盖就行。

**记错了**：抽取时理解偏了。

用户说「我不太喜欢开会」，被记成「用户不喜欢工作」。

这种错误不会自己暴露。

它会在某次回答里冒出来，让你觉得「它怎么这么奇怪」。

**模型自己编的**：最危险。

抽取那一步如果让模型自由发挥，它会补全。

「用户在杭州」可能被补成「用户在杭州，做后端，团队五个人」。

后两句没人说过。

三种污染的共同点是：**它们都发生在写入侧，但表现为检索侧的异常**。

所以你从检索侧永远修不完。

缓解办法四条。

```text
1. 每条记忆带来源（用户原话 / 工具结果 / 模型推断）
2. 模型推断的东西默认不写
3. 读的时候按日期排序，新的优先
4. 让用户能看到记忆，并且能改
```

第四条最重要。

一个用户看不见的记忆系统，错误只能靠运气发现。

再加一条工程约束：

```text
写记忆的那次调用，prompt 里只允许输出"用户明确说过的话"。
不许总结，不许补全，不许推测。
```

这句话要写进抽取的 prompt 里。

不是写在文档里。

**一次真实的复盘。**

用户在 11 月 2 日说「我在杭州」。

11 月 9 日说「我搬到上海了」。

如果你的 `remember` 只在原文完全相同时才覆盖，会发生什么？

```text
- 用户在杭州 <!-- 2026-11-02 -->
- 我搬到上海了 <!-- 2026-11-09 -->
```

两条都在。

召回时问「我在哪」，两条都被命中。

模型看到一个矛盾。

它的三种可能反应：

```text
挑第一条（它更像"事实"）→ 答杭州
挑第二条（因为它更新）→ 答上海
折中 → 答"你之前在杭州，最近搬到上海了"
```

第三种看起来最聪明。

但如果用户问的是「明天出门要带伞吗」，这句折中毫无用处。

修法不是改召回。

是把「所在城市」抽成一个 key。

```text
key  = 所在城市
旧值 = 杭州（2026-11-02）
新值 = 上海（2026-11-09）
→ 覆盖，只留上海
```

要改的是写入时的主题抽取。

这就是前面那句「写入策略比检索策略重要」的具体样子。

## 11. 隐私与删除

记忆里有别人的生活。

城市、时区、项目、习惯、卡在哪。

这些拼起来，能定位到一个人。

三条底线。

**第一条：不该记的不记。**

密钥、密码、身份证号、银行卡、家庭住址、健康状况。

这些不是「敏感」，是「不该出现在这个文件里」。

写入前用一个黑名单过一遍。

**第二条：删除必须是真的删。**

用户说「忘掉我的城市」，你要删三个地方。

```text
memory.md 里那一行
检索索引（如果有）
缓存 / 摘要 / 你为了调试存的历史副本
```

只删第一个，等于没删。

下次召回还能从索引里捞出来。

```python
def forget(keyword: str) -> int:
    """删掉所有包含 keyword 的条目，返回删了几条。"""
    data = load_all()
    removed = 0
    for section, items in data.items():
        kept = [i for i in items if keyword not in i]
        removed += len(items) - len(kept)
        data[section] = kept
    save_all(data)
    return removed
```

注意它返回条数。

用户说「忘了」的时候，你要能回一句「删掉了 2 条」。

删了 0 条也是信息：说明你以为记住的，其实没记住。

**第三条：记忆要能被导出。**

用户有权拿走，也有权看。

一个 JSON 或 Markdown 文件就够。

导出功能不难写，难的是你一开始没留这个口子。

因为你的记忆可能散在三个地方：文件、向量库、日志。

### 删除的三种粒度

用户说「忘掉这个」，可能有三层意思。

```text
删一条：忘掉"我在杭州"这条事实
删一类：忘掉我所有的偏好
删全部：忘掉关于我的一切
```

三种意思，对应三个接口。

```text
forget("杭州")          → 删含关键词的条目
forget_section("偏好")  → 删整节
wipe()                 → 清空文件
```

第三种要特别小心。

```text
wipe() 之后，用户下次打开 agent，它又是陌生人。
```

这可能是他想要的。

也可能是他误触了「重置」，而你以为他要删除记忆。

所以「删全部」要一次确认。

还有一个更麻烦的粒度：派生数据。

```text
为了调试存的对话日志
为了加速存的摘要缓存
为了评测存的样本
```

它们都含用户信息。

只删 memory.md，这三处还在。

一句：

```text
删除的难点不是删，是找出所有副本。
```

## 12. RAG 不等于记忆

这两个东西经常被混成一个。

它们读的不是同一种东西。

```text
RAG 读的是你的文档：静态、共享、作者是你。
记忆读的是发生过的事：动态、私有、作者是用户。
```

展开说。

RAG（检索增强生成）解决的是「模型不知道你的资料」。

它的数据源是手册、代码库、wiki。

这些内容对所有人一样。

记忆解决的是「模型不知道你」。

它的数据源是这个用户说过的话、做过的事。

这些内容只对这个人有意义。

混用会出两类事故。

**第一类：隐私泄漏。**

把用户 A 的偏好写进共享文档库。

用户 B 一检索就看到了。

**第二类：权限错配。**

文档库是只读的，记忆是可写的。

一条通路两种权限，最后一定是权限最松的那种生效。

所以工程上要分开：

```text
两条通路，两个存储，两个权限域。
RAG 的写入是"导入"，记忆的写入是"抽取"。
```

### 记忆和 RAG 的边界画在哪

判断一条信息该放哪边，问三个问题。

```text
谁写的？  你或团队 → 文档库      用户 → 记忆
给谁看？  所有人   → 文档库      一个人 → 记忆
会变吗？  偶尔变   → 文档库      天天变 → 记忆
```

三个都指向同一边，就没有争议。

指向不同边的，才是要设计的部分。

一个典型例子：用户的「项目背景」。

```text
项目本身（共享、你维护）             → 文档库
用户在这个项目里负责哪块（私有、会变）→ 记忆
```

两者会同时出现在上下文里。

冲突时谁赢？

```text
文档说：上线时间是 12 月
记忆说：用户上周说"上线推迟到 1 月了"
```

记忆赢。

理由有两条：它更新，且它是这个人说的。

这条规则要写进 prompt，不能指望模型自己判断。

```text
如果"用户说过的话"和"文档里的内容"冲突，
以用户说的为准，并说明文档里的旧值。
```

还有一个边界更实际：谁能删。

```text
文档库：管理员删，用户只能看
记忆：用户自己删，管理员不该看
```

两者共用一张表，这条就守不住。

所以分开的不只是存储，还有权限和生命周期。

混用检索器是另一种偷懒。

```text
能查出来 → 你以为记忆通了
查不出来 → 你去调相似度阈值
```

问题在于两种数据的分布完全不同。

```text
文档：长段落，几个月改一次，所有人共用一份索引
记忆：短句子，天天变，每个用户一份
```

同一个 embedding 模型可以共用。

同一个索引不该共用。

再补一个更隐蔽的混用：把用户上传的文档写进记忆。

他传了一份 PDF，你抽了几段存进 memory.md。

三个月后他删了那份 PDF。

记忆里还留着摘要。

于是「删除」变成两件事：删文件，和删记忆里关于它的摘要。

一开始分开放，删文件就够了。

一句：

```text
RAG 是可共享的知识，记忆是不可共享的经历。
```

一句总结：

```text
RAG 让 agent 懂业务。
记忆让 agent 懂你。
```

11 篇会讲 RAG 的切分、检索和引用，那时再对比着看。

## 13. 容易混淆的点

**写进文件 ≠ 记住了。**

写进去只是第一步。

下次没召回，或者召回了没塞进上下文，等于没记。

完整的链路是四段：

```text
抽取 → 写入 → 召回 → 注入上下文
```

断在哪一段，表现都一样：它不记得。

**摘要 ≠ 记忆。**

摘要是 [06 篇](/posts/agent-context-engineering/)讲的：把这次会话压短。

记忆是这一篇讲的：把这次会话留下来。

摘要活不过进程，记忆能。

**记忆 ≠ 上下文。**

记忆是硬盘上的。

上下文是发出去的。

中间还隔着一次召回和一次预算分配。

**会话内记忆 = 上下文工程。**

同一件事的两个说法。

第 2 层记忆就是那个 `messages` 列表。

它的管理方法在 06 篇。

**错误观测也是一种记忆。**

[05 篇](/posts/agent-tool-error-selfheal-fuse/)讲过：工具报错被当成观测回填。

那是极短期的记忆，只活在这几轮里。

它决定了 agent 会不会重复同一个错误。

**向量库 ≠ 记忆系统。**

向量库是检索器。

记忆系统是「抽取 + 写入 + 召回 + 注入 + 删除」。

少任何一段都不成立。

**召回相关 ≠ 该用。**

召回是按相似度排的。

相似不等于有用。

用户问 Python 性能，召回到一条「用户讨厌 Java」。

相关，但用不上。

**重复写入 ≠ 多条记忆。**

同一条写了两遍，文件里两行。

召回时它们抢名额。

一条记忆的价值被摊成两条的一半。

去重不是洁癖，是保召回质量。

**记忆 ≠ 摘要。**

摘要压的是「这段对话说了什么」。

记忆压的是「这个人是谁」。

前者一次会话一份，后者一个人一份。

## 14. 回到真实工程

`labs/L01_agent_loop/` 里没有记忆模块。

这是对的。

L01 只教循环，多一个文件就多一层干扰。

但现在你已经可以给它加一层了。

接线只有两个点。

```text
点 A：跑任务之前，把相关记忆塞进 messages
点 B：任务结束之后，把这次的新东西抽出来写回
```

点 A 的代码：

```python
def memory_message(query: str):
    """把召回到的记忆做成一条 system 消息，插在 system 后面。"""
    hits = recall(query, k=5)
    if not hits:
        return None
    body = "以下是已知的长期记忆，按相关度排序：\n" + "\n".join(hits)
    return Message("system", body)


messages = [Message("system", SYSTEM), Message("user", question)]
mem = memory_message(question)
if mem:
    messages.insert(1, mem)
```

注意 `insert(1)`，不是 `append`。

记忆是背景，不是这一轮的任务。

放最后会和用户的问题抢注意力。

点 B 在 `run_agent` 返回之后。

```python
answer = run_agent(model, TOOLS, messages, max_steps=10)
extract_and_save(messages, answer)      # 抽取、去重、写入
```

`extract_and_save` 里要做的三件事：

```text
1. 从这一段对话里挑出"值得记"的句子（模型或规则）
2. 过黑名单（密钥、身份证之类）
3. 按类型写进对应分节，同主题覆盖
```

还有一件容易被忽略的事：**记忆会让 agent 的行为变得不可复现。**

同一个问题，昨天和今天的回答可能不一样。

因为记忆变了。

所以调试时要把「这次召回了哪几条」写进日志。

不然后果是：你改了 prompt，效果变差，但你不知道是 prompt 的问题还是记忆的问题。

14 篇会讲 trace，那里是放这个信息的地方。

### 上线前的六条检查

过一遍这六条，再谈「它有记忆了」。

```text
1. 有一条写入通路，而且它真的被调用过（第 3 节的 audit 能证明）
2. 有去重规则，同一个主题不会留两条
3. 有黑名单，密钥类信息进不去
4. 召回结果会被塞进上下文，且塞的位置不是末尾
5. 这次召回了哪几条，日志里看得到
6. 用户说"忘掉"时，真的能删掉
```

六条都不难。

难的是它们分布在六个地方，很容易漏一条。

最常漏的是第 1 条和第 6 条。

一条太新，还没接。

一条太麻烦，先不做。

这两条恰好是最要紧的。

没有 1，你写的是「一个读空文件的系统」。

没有 6，你写的是「一个删不掉隐私的系统」。

## 15. 小结

这一篇讲的是：进程会死，历史会没。

```text
记忆有三种时间尺度：单轮、会话内、跨会话。
第三层最常缺，也最常被误诊成"检索不行"。
最小实现是一个 Markdown 文件加几个小函数。
写入策略比检索策略重要：记什么、什么时候记、怎么去重、怎么更新。
记忆分三类：事实、偏好、事件，更新策略不同。
召回有关键词、向量、混合，向量库只是其中之一。
记忆会污染、会过期，删除必须是真的删。
RAG 读文档，记忆读发生过的事。
```

如果只记一句：

```text
先确认你写过。
再去优化你怎么找。
```
