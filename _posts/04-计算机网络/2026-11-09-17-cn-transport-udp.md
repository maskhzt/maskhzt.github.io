> **读这篇之前，你只需要知道**：IP 地址是一台机器在网络里的门牌号，比如 192.168.1.10；一台机器上可以同时跑好几个上网的程序；"进程"就是正在运行的一个程序，浏览器是一个进程，微信是另一个。
> **这篇讲什么**：数据包已经送到这台机器了，接下来怎么判断它该交给哪个程序——以及为此存在的一个几乎什么都不做的协议 UDP（User Datagram Protocol，用户数据报协议）。
> **一个类比**：把一台主机想成一栋公寓楼，IP 地址是楼的地址，端口号是房号。UDP 像往门缝里塞纸条：塞进去就不管了，不签收、不排队、也不保证对方在家。


一台笔记本电脑上，同时开着浏览器、微信、一个 SSH 会话、一个正在同步的网盘。

网卡每秒收进来几千个包。

网络层拆开 IP 首部，看了一眼目的地址：是我的，收下。

然后它把包往上交，交了差。

问题是：

```text
这几千个包里，
哪些给浏览器？
哪些给微信？
哪些是 SSH 那个会话的？
```

网络层不管这件事。

它只保证"包到了这台主机"。

至于"到了哪个进程"，是传输层要解决的问题。

这一篇讲的就是这个缺口，以及补缺口最省事的那个协议：UDP。

## 1. 网络层把包送到了主机，然后呢

先问一句：为什么光有 IP 地址还不够？
因为 IP 地址只标到"哪台机器"，标不到"机器上的哪个程序"。
一台机器上同时开着四个程序，四个程序都在等数据。
包送到了机器，机器还得决定交给谁。
所以需要一个"机器内部"的编号：端口号（port）。
端口号是一个 16 位整数，"16 位"指这个字段占 2 个字节，能表示 2 的 16 次方即 65536 个不同的编号，取值范围 0–65535。
它只在本机内部有效，标的是"这台机器上的哪个进程"。

先看 IP 首部里那个叫"协议"的字段。

8 位，取值 6 表示里面装的是 TCP，取值 17 表示装的是 UDP，取值 1 表示 ICMP。

这个字段只能把包分到"哪个协议"，分不到"哪个进程"。

```text
IP 首部.protocol = 17
        │
        ▼
   这是 UDP —— 然后呢？
   主机上开了 40 个 UDP 套接字。
   给哪一个？
```

所以分用要做两级：

```text
第一级：IP 首部的协议号 → 交给 TCP 还是 UDP
第二级：TCP/UDP 首部的端口号 → 交给哪个进程
```

缺了第二级，一台主机就只能同时跑一个网络程序。

这在 1970 年代也许能忍，今天不行。

## 2. 复用与分用：一台主机上的多路开关

先问一句：为什么不给每个上网的程序单独配一块网卡？
因为网卡、IP 地址、连到外面的那条线，全机只有一份。
四个程序要同时上网，只能共用这一份。
"多个程序共用一份传输能力"这件事，叫复用。
包从线上下来的那一头，只有一份数据，却要拆给四个程序，这件事叫分用。
方向相反，一个合、一个拆。

两个词，方向相反。

```text
复用（multiplexing）
  发送方：多个进程共用同一个传输层、同一个 IP、同一块网卡。

分用（demultiplexing）
  接收方：传输层按端口号，把数据交给正确的进程。
```

画出来是这样：

```text
        发送方                                接收方
 ┌──────────────┐                      ┌──────────────┐
 │ 浏览器 :50000 │──┐                ┌──│ :50000 浏览器 │
 ├──────────────┤  │                │  ├──────────────┤
 │ DNS    :5353  │──┼─► UDP ─► IP ─► ┼──│ :5353  DNS   │
 ├──────────────┤  │                │  ├──────────────┤
 │ 游戏   :50001 │──┘                └──│ :50001 游戏   │
 └──────────────┘                      └──────────────┘
        复用                              分用
```

一句话记住：复用是"多进一出"，分用是"一进多出"。
分用要查的那张表，就是"端口号 → 进程"的对照表，而这张表只存在于本机。
所以复用分用这两件事，全都发生在主机内部，中间的网络一点都不知道。

有三个细节值得记住。

第一，端口号只在**本机**有意义。

你的 50000 和对面的 50000 毫无关系。

第二，同一个（协议，IP，端口）在同一时刻只能有一个主人。

除非显式开了 `SO_REUSEPORT`，让多个套接字共享同一个端口。

第三，分用有三种做法，408 会拿它出选择题：

```text
无连接分用：只看目的端口。UDP 就是这样。
面向连接分用：看四元组。TCP 是这样。
IP 分用：只看协议号。这是网络层那一级。
```

这三种分用方式，其实对应着三种地址。

```text
MAC 地址   48 位   这块网卡    一跳之内有效，过路由器就换
IP 地址    32 位   这个接口    从源主机到目的主机有效
端口号     16 位   这个进程    只在本机有效
```

越往上层，标识的范围越小，有效期越短。

MAC 只在同一段链路上有意义，路由器转发时会整个换掉。

IP 在整条路径上有意义，但它只认主机，不认进程。

端口只在一台主机内部有意义。出了这台机器，没人知道 50000 是谁。

所以分用只能在主机内部完成：只有主机自己知道哪个端口归哪个进程。

这也解释了一件事——端口号不需要全局唯一。

你的 80 和对面的 80 是两回事，只要本机不冲突就行。

反过来看，这就解释了 NAT 为什么这么麻烦。

它要改 IP 地址和端口号，而这两样东西分别被网络层和传输层的校验和盯着。

改一个地址，两个校验和都得重算。

还有一个常被忽略的后果：NAT 之后，外网看到的源端口是映射后的端口。

服务端日志里记下的"客户端端口"，往往不是客户端真实的那个。

排查问题时拿这个端口去对端查，经常对不上。

## 3. 端口号：16 位，三个区间

先问一句：为什么端口要分成三段，而不是谁想用哪个就用哪个？
因为有些端口必须"人人皆知"。
你要访问一个网站，浏览器得先知道该往哪个号上敲门，而它没有机会先问对方。
所以一小组号码被提前写死，全世界统一。
这套约定的存在，让"我知道你在 80 端口"变成一件不需要协商的事。

端口号 16 位，取值 0–65535。

按用途切成三段：

```text
0     – 1023   熟知端口（well-known）    需要 root 才能绑定
1024  – 49151  登记端口（registered）    普通用户可用，IANA 登记过
49152 – 65535  动态端口（ephemeral）     客户端临时申请，用完就还
```

三段可以这样记：0–1023 是"约定好的"，1024–49151 是"登记过的"，49152 以上是"临时借的"。
49152 这个起点不是随便定的，它要留得足够高，才不会和前面两段撞车。

几个必须脱口而出的：

```text
20 / 21   FTP 数据 / 控制
22        SSH
23        Telnet
25        SMTP
53        DNS
67 / 68   DHCP 服务器 / 客户端
69        TFTP
80        HTTP
110       POP3
123       NTP
143       IMAP
161       SNMP
443       HTTPS
520       RIP
```

有一处容易记混：DHCP 的 67 是服务器监听，68 是客户端监听。

因为客户端还没有 IP，只能广播，服务器从 67 收到，回给 68。

还有一个常被问到的点：**端口号不是进程号。**

进程号是操作系统给的，重启就变；端口号是协议层的标识，由应用自己选。

一个进程可以占多个端口（比如 DNS 服务器同时听 TCP/53 和 UDP/53），一个端口也可以先后被不同进程用。

Linux 上客户端用的临时端口范围不是 49152 起，而是内核参数定的：

```text
$ sysctl net.ipv4.ip_local_port_range
net.ipv4.ip_local_port_range = 32768    60999
```

大约 2.8 万个。

这解释了一个真实故障：压测机把 `TIME_WAIT` 和 `CLOSE_WAIT` 堆满之后，报的错不是"连接被拒绝"，而是 `Cannot assign requested address`——临时端口用光了。

这两个状态先各给一句话，读 18 篇时会展开（详见 [18 篇](/posts/cn-tcp-connection/)）。
TIME_WAIT：主动关闭连接的一方最后停留的状态，连接已经不用了，但那条四元组还要被占一小段时间。
CLOSE_WAIT：对方已经说要关了，本方的程序还没调关闭，连接就挂在那儿不动。
两个状态都占着端口不放，所以端口会被它们吃光。

## 4. 套接字与四元组：连接的身份证

先问一句：凭什么说"这两台机器之间有一条连接"，而不是"一堆包碰巧走在一起"？
因为内核要为每条连接留一份状态，而留状态之前，得先有一个能唯一指认它的名字。
这个名字就是四元组。

术语要分清。

```text
套接字（socket）  = (IP 地址, 端口号)      —— 一个端点
连接（connection） = (源 IP, 源端口, 目的 IP, 目的端口)  —— 一条四元组
```

一条 TCP 连接靠四元组唯一确定。

```text
192.168.1.10 : 50000  ───►  93.184.216.34 : 443
  源 IP        源端口          目的 IP      目的端口
```

为什么要四元组，两个端口不够吗？

看服务器。

一台 Web 服务器的 443 端口同时服务五万个客户端。

如果只按端口分用，这五万个连接全挤在同一个 443 上，内核没法区分谁是谁。

加了源 IP 和源端口，五万条连接就是五万个不同的四元组。

```text
10.0.0.7 : 51000  ─► 93.184.216.34 : 443
10.0.0.8 : 51000  ─► 93.184.216.34 : 443   ← 源 IP 不同，是另一条连接
10.0.0.7 : 51001  ─► 93.184.216.34 : 443   ← 源端口不同，也是另一条
```

**如果没有它会怎样？**

假设内核只按目的端口分用，不看源 IP 和源端口。
一台 Web 服务器的 443 端口上同时挂着五万个连接。
五万个客户端发来的请求，在内核眼里全是"443 端口上的同一条连接"。
服务器准备好的响应，只能随便挑一个套接字塞回去。
结果是：你打开网银，登录成功，刷新出来的却是别人的账户页面。
这不是夸张，而是"分用粒度不够"的必然结果。
四元组存在的唯一理由，就是让每一对通信双方都有一条独立的身份。

反过来，客户端也靠四元组判断"这个包属于哪个连接"。

所以 NAT 设备必须维护一张映射表：把内网的（源 IP, 源端口）换成公网的（源 IP, 源端口）。

表满了，新连接就建不起来。

## 5. UDP 首部：8 个字节就够

先问一句：首部为什么能省到 8 个字节？
因为首部里的每个字节都要跟着数据一起传过去，也要一起参与一次校验。
字段越少，占的带宽越少、解析越快。
UDP 的取舍是：把"要不要可靠"交给上层应用，自己只保留"找到进程"和"发现损坏"这两件事必需的信息。

UDP 首部只有 4 个字段，每个 16 位。

```text
 0                   16                  31
+-------------------+-------------------+
|     源端口 (16)    |    目的端口 (16)   |
+-------------------+-------------------+
|     长度 (16)      |    校验和 (16)     |
+-------------------+-------------------+
|              数据（可选，0 字节起）       |
+---------------------------------------+
```

一共 8 字节。

逐条看：

```text
源端口   16 位   发送方端口，需要回信时用；不需要回信可以填 0
目的端口 16 位   接收方端口，分用就靠它
长度     16 位   UDP 首部 + 数据的总字节数，最小值是 8
校验和   16 位   覆盖伪首部 + 首部 + 数据；IPv4 下可以全 0 表示不用
```

校验和（checksum）先说一句：它是一段数据"加起来的指纹"。
发送方把首部和数据按 16 位一组累加，再取反，得到一个 16 位的数填进这个字段。
接收方用同样的方法连校验和一起算，如果结果全 1 就通过，否则认为数据被改坏了，直接丢弃。
它只能发现"错了"，不能告诉你"哪里错了"，更不能修。

长度字段带来三个数：

```text
长度字段最小 8            → 数据可以为 0（比如只有心跳的空包）
长度字段最大 65535        → 数据最大 65527 字节
减去 IP 首部 20 字节      → 实际数据最大 65507 字节
```

所以一个 UDP 数据报是装不进 65535 字节的数据的。

实际链路上还有 MTU（Maximum Transmission Unit，最大传输单元）：一条链路一次最多能搬多少字节，以太网的典型值是 1500 字节。
超过这个数，IP 层只好把一个数据报切成几片分别发，这件事叫分片（fragmentation）。

以太网 MTU 1500 字节，减去 IP 首部 20、UDP 首部 8：

```text
1500 - 20 - 8 = 1472 字节
```

UDP 载荷超过 1472，IP 层就要分片。

分片这件事对 UDP 特别伤：IP 层分片后，只要丢一片，整个数据报就废了，而 UDP 没有重传，接收方只能整条丢弃。

所以成熟的 UDP 应用都会自己把消息控制在 1472 字节以内，或者干脆在应用层做分片（QUIC 就是这么干的）。

首部里没有"首部长度"这样的字段，这一点常被拿来和 TCP 对比。

因为首部固定 8 字节，不需要告诉对方"数据从第几个字节开始"。

TCP 有数据偏移，IPv4 有首部长度，UDP 什么都没有。

省下来的这几位，换来了一个好处：解析 UDP 首部的代码只有几行。

长度字段还有一处冗余。

```text
IP 总长度 = 20 + UDP 长度（无选项、不分片时）
UDP 长度  = IP 总长度 - 20
```

既然能算出来，为什么还要各写一份？

因为 UDP 不一定只跑在 IPv4 上。

IPv6 里没有"IP 总长度"这个字段，它用的是"载荷长度"，含义还不完全一样。

隧道封装也会改变下层的样子。

UDP 把自己需要的长度自带一份，就不依赖下层的具体格式。

代价是两端都要多做一次一致性检查，两个长度对不上就丢弃。

这也是校验和会把长度字段一起保护起来的原因。

再说一遍 MTU，因为它比长度字段更容易踩。

```text
以太网 MTU      1500 字节
减去 IP 首部      20 字节
减去 UDP 首部      8 字节
可用载荷        1472 字节
```

超过 1472，IP 层就要分片。

分片之后，只要丢一片，整个数据报就废了，而 UDP 不会重传。

接收方看到的是一个"缺了一角"的报文，只能整条丢掉。

成熟的做法只有两个：把消息控制在 1472 以内，或者在应用层自己分片。

## 6. 伪首部：为什么校验和要借 IP 地址

先问一句：UDP 的校验和到底在校什么？
它想回答的是"这段数据从源 IP、源端口出发，到目的 IP、目的端口，一路上有没有被改坏"。
可 UDP 首部里只有端口，压根没有 IP 地址。
于是协议想了个办法：算校验和时，临时从 IP 首部抄一份地址过来，接在 UDP 首部前面一起算。

UDP 算校验和的时候，会临时拼出一个 12 字节的"伪首部"。
伪首部（pseudo header）：一份只在计算时存在、根本不参与传输的临时结构，算完就扔掉。
它的内容全部抄自 IP 首部，作用是"把地址也拉进校验范围"。

它不传输，只参与计算，所以抓包软件里看不到它，只能从 IP 首部现场推出来。

```text
 0                                    31
+---------------------------------------+
|           源 IP 地址 (32 位)           |
+---------------------------------------+
|          目的 IP 地址 (32 位)           |
+---------------------------------------+
|   全 0 (8 位)   |  协议号 17 (8 位)     |
+---------------------------------------+
|           UDP 长度 (16 位)             |
+---------------------------------------+
              共 12 字节
```

注意最后那个"UDP 长度"，和 UDP 首部里的长度字段是同一个值，出现了两次。

为什么要多此一举？

因为 UDP 的首部里**没有地址**。

一台主机收到一个 UDP 报文，如果只校验端口和数据，那么一个"本该发给 10.0.0.9:53、却被错误投递到 10.0.0.5:53"的报文，校验和照样能通过。

伪首部把源 IP、目的 IP、协议号拉进校验范围，就补上了这一层：

```text
IP 地址被改坏了 → 伪首部的和被改坏 → 校验和验不过 → 丢弃
协议号错了（本该给 TCP）→ 伪首部对不上 → 丢弃
长度字段被改 → 两处长度对不上 → 丢弃
```

**这一点值得单独记住：**

> 伪首部根本不在报文里，却决定了这条报文"该不该送到这个地址"。

这个设计有一个直接后果：**任何修改 IP 地址的设备，都必须重算传输层校验和。**

NAT 就是这样。

它把内网源 IP 换成公网 IP，一改地址，UDP 的校验和立刻失效，所以 NAT 设备必须顺手把 UDP 和 TCP 的校验和一起改掉。

这也是为什么很多 NAT 打洞方案会出现"校验和错误"这种看起来莫名其妙的故障。

## 7. 给一条 UDP 报文算校验和

来一条具体的。

```text
源主机   192.168.1.10 : 5000
目的主机 192.168.1.20 : 53
数据     4 字节，内容 "TEST"，即 0x54 0x45 0x53 0x54
```

第一步，算长度。

```text
UDP 长度 = 8 + 4 = 12 = 0x000C
```

第二步，把 IP 地址拆成 16 位一组。

```text
192.168.1.10  →  0xC0A8, 0x010A
192.168.1.20  →  0xC0A8, 0x0114
```

第三步，把 12 个 16 位字排出来（校验和字段先填 0）。

```text
序号  来源              数值
 1    伪首部 源 IP 高16   0xC0A8
 2    伪首部 源 IP 低16   0x010A
 3    伪首部 目的 IP 高16  0xC0A8
 4    伪首部 目的 IP 低16  0x0114
 5    伪首部 0 + 协议 17   0x0011
 6    伪首部 UDP 长度      0x000C
 7    UDP 源端口 5000     0x1388
 8    UDP 目的端口 53      0x0035
 9    UDP 长度            0x000C
10    UDP 校验和（占位）    0x0000
11    数据 "TE"           0x5445
12    数据 "ST"           0x5354
```

数据 4 字节刚好凑成两个 16 位字，不用补零。

第四步，按 16 位无符号累加。

```text
0xC0A8 + 0x010A = 0xC1B2
0xC1B2 + 0xC0A8 = 0x1825A
0x1825A + 0x0114 = 0x1836E
0x1836E + 0x0011 = 0x1837F
0x1837F + 0x000C = 0x1838B
0x1838B + 0x1388 = 0x19713
0x19713 + 0x0035 = 0x19748
0x19748 + 0x000C = 0x19754
0x19754 + 0x0000 = 0x19754
0x19754 + 0x5445 = 0x1EB99
0x1EB99 + 0x5354 = 0x23EED
```

第五步，进位回卷：把超出 16 位的部分加回低 16 位。
这一步叫回卷（wrap around）：16 位装不下 17 位的和，溢出的高位不能丢，要加回最低位。
这是"反码求和"的规定动作，也是接收方验算能对上的前提。

```text
0x23EED  →  0x3EED + 0x2 = 0x3EEF
```

第六步，取反。

```text
0xFFFF - 0x3EEF = 0xC110
```

所以这条报文的校验和是 **0xC110**。

填进首部：

```text
+--------+--------+
| 0x1388 | 0x0035 |
+--------+--------+
| 0x000C | 0xC110 |
+--------+--------+
|  54 45 53 54     |
+--------+--------+
```

接收方怎么验？

把校验和字段也当成一个数加进去，如果结果是 0xFFFF，就通过。

```text
0x3EEF + 0xC110 = 0xFFFF  ✓
```

三条容易踩的规则：

```text
1. 数据是奇数字节时，末尾补一个 0x00 凑成 16 位；
   这个补的字节不写进长度字段，也不传输。
2. 算出来正好是 0x0000，要写成 0xFFFF。
   因为 0x0000 在 IPv4 里表示"我没算校验和"。
3. 校验和字段全 0，IPv4 下合法（表示不用），IPv6 下不合法（必须算）。
```

再补一个实现细节：NAT 改地址时，校验和是"增量更新"的，不是重算。

改一个 16 位字（比如源 IP 的低 16 位），不需要把整条报文重新加一遍。

```text
HC' = ~(~HC + ~m + m')

HC  旧校验和
m   被改的旧 16 位字
m'  改后的新 16 位字
```

这是 RFC 1624 给的写法。

对高转发率的设备来说，这条公式省下的是几个数量级的计算量。

副作用也很真实：一旦某台设备的增量更新算错了，校验和会悄悄地错掉。

而 UDP 遇到校验和错误只会静默丢弃，不报错。

所以这类故障的表现是"偶发丢包"，而不是"连接失败"，非常难查。

还有一个顺序问题：先回卷到 16 位，再取反。

反过来做，结果一样，但中间值会溢出，代码里容易写错。

所以几乎所有实现都是 32 位累加器一路加到底，最后折叠一次、取反一次。

## 8. UDP 的三无性格

先问一句：一个不连接、不确认、不重传的协议，凭什么还能活到今天？
因为在有些场景里，"快"和"简单"比"一个字节都不丢"更值钱。
视频会议里，晚到 300 毫秒的画面已经没用了，重传只会让后面的画面更晚。
DNS 查询里，一问一答两个报文就结束，为它建一次连接的开销比查询本身还大。
所以 UDP 不是"残缺的 TCP"，它是"只保留最小必需品的传输层"。

三个特点，一个比一个直接。

**无连接。**

不发握手，不建状态，有数据就封包发出去。

发送方内核里没有"这条连接"的记录，接收方也不知道"这个报文属于哪次会话"。

所以 UDP 的套接字在 `ss` 里状态是 `UNCONN`。

**不可靠。**

不确认，不重传，不排序，不去重。

```text
丢了？丢了。
乱了？乱了。
重复了？重复了。
```

校验和验不过的报文直接丢，连个通知都没有。

ICMP 有时候会回一个"端口不可达"，但那是可选的，而且经常被防火墙吃掉。

**面向报文。**

应用交给 UDP 多长，UDP 就发多长。

不合并，不拆分，边界原样保留。

```text
TCP 像水管：你倒 100 次水，对面看到的是连续的一股。
UDP 像寄包裹：你寄 100 个包裹，对面收到 100 个包裹，或者 98 个。
```

这带来一个特别容易忽略的坑：

接收方调用一次 `recvfrom`，只取一个报文。

如果缓冲区给得比报文小，多出来的部分被**丢弃**，不会留到下一次读。

所以 UDP 程序里，缓冲区要按最大可能报文开（一般是 65535）。

举一个具体例子，对比两种"面向"的差别。

应用要发三条消息，每条 100 字节，内容分别是 A、B、C。

```text
UDP：
  调用 3 次 sendto，发出 3 个数据报
  接收方 3 次 recvfrom，收到 3 条，边界清晰
  第 2 条丢了，收到的是 A 和 C，中间没有 B 的位置

TCP：
  调用 3 次 write，内核可能合并成一个 300 字节的段
  接收方 1 次 read 可能就读到 300 字节
  少了一段，看到的是"少了几个字节的流"，不是"少了一条消息"
```

这就是"报文边界"的实际含义。

UDP 保留了应用层的切分，TCP 把它抹平了。

所以用 UDP 传结构化数据时，应用必须自己在报文里带长度或分隔符。

还有一条更隐蔽的规则：一次 recvfrom 只取一个报文。

```text
缓冲区 100 字节，来了一个 200 字节的报文
→ 只拷前 100 字节给应用
→ 剩下 100 字节被丢弃，不会留给下一次读
```

用 recvmsg 的时候，MSG_TRUNC 标志会告诉你"实际报文比缓冲区大"。

用 recvfrom 就只能看到一个"看起来正常"的返回值。

所以 UDP 服务的缓冲区一律按 65535 开，这不是浪费，是必须。

## 9. TCP 与 UDP 放在一起看

先问一句：为什么非要把两者摆在一起看？
因为 408 的选择题几乎都在问"这个场景该用哪个"，而选错的根源往往只有一句：把"UDP 快"理解成了"链路速率高"。
一行行对比，比背两句口诀有用。

| 维度 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接，先三次握手 | 无连接，直接发 |
| 可靠性 | 确认 + 重传 + 排序 + 去重 | 都不保证 |
| 首部长度 | 20 字节起（含选项更多） | 固定 8 字节 |
| 传输单位 | 字节流 | 报文，保留边界 |
| 流量控制 | 有（rwnd） | 没有 |
| 拥塞控制 | 有（cwnd） | 没有 |
| 广播 / 组播 | 不支持 | 支持 |
| 建连时延 | 1 个 RTT | 0 |
| 典型应用 | HTTP、SSH、SMTP、FTP | DNS、DHCP、视频、游戏、SNMP |

这张表里最容易被误读的是"快"这个字。

UDP 快，不是因为它的链路速率更高，也不是因为它少拷贝几次内存。

它快在三个地方：

```text
省掉握手：少 1 个 RTT
省掉重传等待：丢了不补，不会因为等一个包而阻塞后面的数据
省掉拥塞控制：网络堵了也照发，不计较别人的死活
```

第三条是双刃剑。

一个用 UDP 猛发的程序，会把同一条链路上的 TCP 连接挤到几乎没有带宽，因为 TCP 会让、它不让。

## 10. UDP 在哪些地方不可替代

按"为什么非它不可"分类，比按应用背有用。

```text
要广播 / 组播   → 只能 UDP。TCP 是点对点的，做不了。
要极低时延     → 视频会议、云游戏。迟到 300 ms 的帧不如不要。
要一问一答     → DNS、DHCP、SNMP。会话极短，建连接的成本占比太高。
要自己掌控     → QUIC、部分游戏协议。在 UDP 之上自建可靠性，绕开内核。
```

**这里就是那个反直觉的点：**

> UDP 明明"不可靠"，DNS 却把整个互联网的入口交给了它。

道理不复杂，只是要算一笔账。

一次 DNS 查询，问一句答一句，总共两个报文。

用 UDP：

```text
客户端 → 服务器   查询
服务器 → 客户端   回答
1 个 RTT 完事。
```

用 TCP：

```text
SYN / SYN+ACK / ACK      ← 建连接，1 个 RTT
查询 / 回答               ← 1 个 RTT
FIN / ACK / FIN / ACK    ← 拆连接，还要时间
至少 2 个 RTT，还多了 9 个报文。
```

如果这个包丢了，UDP 的做法是：客户端等 1–2 秒没收到，重发一次。

反正查询是幂等的，重发一百次结果一样。
幂等（idempotent）：同一个操作做一次和做十次，效果相同。
"查一下某个域名对应哪个 IP"符合这个性质；"从账户里扣 100 块"不符合。
所以 DNS 敢跑在不可靠的协议上，而转账不敢。

而 TCP 的重传要维护定时器、拥塞窗口、接收窗口，服务器要为每个客户端留一块状态。

一台根域名服务器每天处理几百亿次查询，如果每个查询都要建连接、留状态，内存先炸。

```text
UDP 的"无状态"不是缺陷，
在"一问一答"的场景里，它就是性能本身。
```

代价也要说清楚：UDP 的应答可以被伪造源地址，这是 DNS 放大攻击的根源。

所以 DNS 后来加了 0x20 编码、源端口随机化，以及"回答太大就用 TCP 重来"的规则。

DNSSEC 的响应、区域传送（AXFR），都跑在 TCP/53 上。

顺便说一句 QUIC。

HTTP/3 跑在 QUIC 上，QUIC 跑在 UDP 上。

它把可靠传输、拥塞控制、TLS 全搬到了用户态，在 UDP 上面重新实现了一遍。

为什么不用现成的 TCP？

```text
中间设备（防火墙、NAT）对 TCP 的干预太多，改不动。
TCP 的实现在内核里，升级要动整个操作系统。
用户态实现可以跟着浏览器一起发版。
```

这算是"UDP 的极简"带来的另一份红利：留白足够多。

DHCP 更极端：客户端连"自己是谁"都还不知道。

```text
客户端   源 IP 0.0.0.0，目的 IP 255.255.255.255，源端口 68，目的端口 67
服务器   从 67 收到，回给 255.255.255.255:68
```

此时客户端没有 IP，服务器也不知道该发给谁。

只能广播。

TCP 在这种情况下根本没法工作：三次握手要求双方都有确定的地址和端口，广播地址不在这个前提里。

所以 DHCP 只能用 UDP，而且只能用广播，没有第二个选择。

视频和游戏是另一套理由。

```text
30 fps 的视频，33 ms 一帧
丢一帧：画面顿一下，眼睛几乎看不出来
晚一帧：等 200 ms 才到，播放器已经在放下一帧了，这一帧作废
```

对实时流来说，迟到的数据等于没有数据。

TCP 的重传会让后面的数据一起等（队头阻塞），这正是实时应用最怕的。

所以它们宁可丢，也不要等。

还有一个工程上的原因：只有应用自己知道"什么数据重要"。

```text
视频：关键帧（I 帧）重要，P 帧丢了可以凑合
语音：前 20 ms 重要，晚到的音节不如直接静音
游戏：最新位置重要，旧位置没价值
```

这些判断 TCP 做不了。

## 11. 容易混淆的五个点

**端口号不是进程号。**

进程号是操作系统分配的，端口号是协议层标识。

**套接字不是连接。**

套接字是一端（IP + 端口），连接是四元组。

`ss -tan` 里一行是一条四元组。

**UDP 长度字段不是 IP 总长度。**

UDP 长度只算 UDP 首部加数据；IP 总长度还算上了 20 字节 IP 首部。

```text
IP 总长度 = 20 + UDP 长度（无选项、不分片时）
```

**"UDP 不保证顺序"不等于"UDP 会打乱顺序"。**

网络一般不打乱，但协议不承诺。

一旦中间换了路径（比如链路聚合、多路径），乱序就会真的发生。

**校验和可选，只在 IPv4 成立。**

IPv6 取消了首部校验和，但 UDP 的校验和在 IPv6 下是强制的。

## 12. 408 怎么考

传输层前两节的题型很固定：

```text
端口号落在哪个区间、这个端口是干什么的
给定应用场景，选 TCP 还是 UDP
伪首部由哪几部分组成、为什么要它
UDP 长度字段与数据长度的换算
校验和的计算与验证
```

计算题基本只有一种：给你地址、端口、数据，让你算校验和。

下面这道是自拟的，数字挑得好算。

```text
主机 A：10.0.0.5，UDP 源端口 1234
主机 B：10.0.0.9，UDP 目的端口 69
数据区：6 字节，内容为 11 11 22 22 33 33（十六进制）

问：
(1) UDP 首部的长度字段是多少？
(2) 伪首部的 6 个 16 位字分别是什么？
(3) 参与校验和计算的字节数是多少？
(4) 校验和是多少？
(5) 如果这个字段是 0x0000，说明什么？
(6) 目的端口 69 对应哪个应用？
```

解。

（1）长度字段。

```text
UDP 首部 8 + 数据 6 = 14 = 0x000E
```

（2）伪首部。

```text
10.0.0.5  →  0x0A00, 0x0005
10.0.0.9  →  0x0A00, 0x0009

0x0A00  源 IP 高 16 位
0x0005  源 IP 低 16 位
0x0A00  目的 IP 高 16 位
0x0009  目的 IP 低 16 位
0x0011  全 0 + 协议号 17
0x000E  UDP 长度
```

（3）参与计算的字节数。

```text
伪首部 12 + UDP 首部 8 + 数据 6 = 26 字节 = 13 个 16 位字
```

（4）求和。

```text
0x0A00 + 0x0005 = 0x0A05
0x0A05 + 0x0A00 = 0x1405
0x1405 + 0x0009 = 0x140E
0x140E + 0x0011 = 0x141F
0x141F + 0x000E = 0x142D
0x142D + 0x04D2 = 0x18FF      （1234 = 0x04D2）
0x18FF + 0x0045 = 0x1944      （69   = 0x0045）
0x1944 + 0x000E = 0x1952
0x1952 + 0x0000 = 0x1952
0x1952 + 0x1111 = 0x2A63
0x2A63 + 0x2222 = 0x4C85
0x4C85 + 0x3333 = 0x7FB8
```

没有进位，不用回卷。

取反：

```text
0xFFFF - 0x7FB8 = 0x8047
```

校验和为 **0x8047**。

验算：把校验和加回去。

```text
0x7FB8 + 0x8047 = 0xFFFF  ✓
```

（5）字段为 0x0000 表示发送方没有计算校验和，接收方跳过校验。

这是 IPv4 允许的偷懒做法，IPv6 不允许。

（6）69 是 TFTP，落在 0–1023 的熟知端口区间，需要 root 权限才能监听。

再补一个选择题的常见陷阱：

```text
"某应用需要把数据同时发给同一网段的 20 台主机，
 应该用 TCP 还是 UDP？"
```

答案 UDP。

TCP 只支持一对一，组播和广播是 IP 层的能力，传输层只有 UDP 能借用。

## 13. 真实网络里长什么样

先看本机的 UDP 套接字。

```text
$ ss -uanp
State    Recv-Q  Send-Q  Local Address:Port   Peer Address:Port  Process
UNCONN   0       0       127.0.0.53:53        0.0.0.0:*          users:(("systemd-resolve",pid=712))
UNCONN   0       0       0.0.0.0:68           0.0.0.0:*          users:(("dhclient",pid=903))
UNCONN   0       0       192.168.1.10:5353    0.0.0.0:*          users:(("avahi-daemon",pid=845))
```

（简化示意）

三点观察：

```text
状态全是 UNCONN —— 没有连接，只有监听和端点。
127.0.0.53:53 是本地 DNS 转发器，只监听回环。
0.0.0.0:68 是 DHCP 客户端，因为还没地址，只能全零监听。
```

再看 TCP 那一侧，对比一下四元组长什么样。

```text
$ ss -tan
State     Recv-Q  Send-Q  Local Address:Port     Peer Address:Port
ESTAB     0       0       192.168.1.10:51234     93.184.216.34:443
ESTAB     0       0       192.168.1.10:51240     93.184.216.34:443
TIME-WAIT 0       0       192.168.1.10:51241     93.184.216.34:443
```

（简化示意）

同一个目的地址、同一个 443 端口，靠本地端口区分成三条连接。

这就是四元组。

接着看内核统计里的 UDP 错误。

```text
$ netstat -su
Udp:
    12345678 packets received
    2345 packets to unknown port received
    0 packet receive errors
    2 packets sent
    0 receive buffer errors
    0 send buffer errors
    InCsumErrors: 17
```

（简化示意）

两个字段值得盯：

```text
packets to unknown port received
  → 报文到了，但没有进程监听那个端口。ICMP 端口不可达就是这么来的。

InCsumErrors
  → 校验和错误的报文数。这个数一直在涨，通常说明链路上有设备在改包。
```

再抓一次 DNS 查询。

```text
$ tcpdump -i any -nn -vv udp port 53
10:22:31.104512 IP 192.168.1.10.51234 > 8.8.8.8.53: UDP, length 40
    192.168.1.10.51234 > 8.8.8.8.53:
    UDP, length 40
```

（简化示意）

加上 `-X` 能看到 UDP 首部的 8 个字节：

```text
0x0000:  4500 003c 1a2b 4000 4011 8f3e c0a8 010a
0x0010:  0808 0808 c822 0035 0028 c9a1 ...
          ^^^^ ^^^^ ^^^^ ^^^^
          源端口 目的端口 长度 校验和
```

（简化示意）

这里有个坑：抓包时经常看到 `bad udp cksum`。

多半不是真的错，而是网卡做了校验和卸载（checksum offload）：发送时内核还没算校验和就把包交给了网卡，网卡补算。

抓包点在网卡之前，看到的就是"还没填好的校验和"。

关掉它再抓：

```text
$ ethtool -K eth0 tx off rx off
```

最后看几个和 UDP 有关的内核参数。

```text
$ sysctl net.ipv4.ip_local_port_range net.core.rmem_max net.ipv4.udp_mem
net.ipv4.ip_local_port_range = 32768    60999
net.core.rmem_max = 212992
net.ipv4.udp_mem = 38331    51110    76662
```

（简化示意）

`rmem_max` 是单个套接字接收缓冲区的上限。

UDP 没有流量控制，缓冲区满了就直接丢，而且丢得悄无声息。

所以做 UDP 服务时，第一件要调的事是把这个值调大，第二件是看 `netstat -su` 里的 `receive buffer errors`。

Wireshark 里更直观。

```text
1. 过滤 udp.port == 53
2. 点开一条报文 → User Datagram Protocol
3. 能看到 Source Port / Destination Port / Length / Checksum
4. Checksum 那一行如果显示 "unverified" 或绿色对勾，
   说明网卡卸载让它没法验证，不是报文有问题
```

（简化示意）

算一笔临时端口的账，就明白为什么短连接服务要改长连接。

```text
Linux 临时端口约 2.8 万个（32768–60999）
每条短连接在 TIME_WAIT 停留 60 秒
理论上限 ≈ 28000 / 60 ≈ 470 条每秒
```

超过这个速率，端口开始排队，报错是 Cannot assign requested address。

不是带宽不够，也不是 CPU 不够，是端口不够。

这也是 HTTP/1.0 时代代理服务器最常见的故障之一。

再补一个 IPv6 的差异。

IPv6 的伪首部更长，也更严格。

```text
源 IPv6 地址        16 字节
目的 IPv6 地址      16 字节
UDP 长度             4 字节
全 0 + 下一个首部     4 字节
合计                40 字节
```

"下一个首部"取 17 仍然表示 UDP。

IPv4 里"校验和可以不填"的那条后路，在 IPv6 里没有了。

理由是 IPv6 取消了 IP 首部的校验和，传输层要是也不校验，整条路径上就没人检查完整性。

所以 IPv6 下的 UDP 校验和是强制的，填 0 会被当作错误丢弃。

### 自检三问

1. 如果 UDP 首部里没有伪首部，一个"本该发给 10.0.0.9:53、却被错投到 10.0.0.5:53"的报文还能被发现吗？
2. 为什么一条连接要用四元组标识，只用"目的端口 + 源端口"两个数不够吗？
3. 给你两个 IP、两个端口和 4 字节数据，你能算出 UDP 的校验和吗？算出来正好是 0x0000 时该写什么？

## 14. 小结

这一篇的主线，压成几行：

```text
网络层送到主机，传输层送到进程。
分用靠端口号，16 位，分三段。
连接的身份证是四元组，不是端口。
UDP 首部 8 字节：源端口、目的端口、长度、校验和。
校验和要借伪首部的 12 字节，把 IP 地址拉进来。
IPv4 下校验和可以不填（全 0），IPv6 下必须填。
```

