> **读这篇之前，你只需要知道**：信道是一段用来传数据的无线电频率，像一条只够过一辆车的窄路；半双工是同一时刻只能发或只能收，不能又发又收；确认帧（ACK）是接收方回的一张小纸条，上面写着"这一帧我收到了"。
> **这篇讲什么**：无线网卡在发射的时候听不见周围的声音，所以没法"撞了再退"，只能改成"先约好再发"；这一篇讲的就是这套预约的规矩是怎么排出来的。
> **一个类比**：一间有柱子的会议室，坐在柱子两边的人互相看不见。想发言的人先喊一声"我要说三分钟"，由主持人复述一遍"这三分钟归他"；柱子另一边的人听见主持人的话，就先闭嘴等着。


先做一个思想实验。

把一台笔记本的 WiFi 打开，让它一边发、一边"听"。

它听不到任何别人的信号。

不是别人没发，是它自己发的时候，喇叭太响，耳朵聋了。

这就是无线和有线最根本的差别。

有线网卡可以一边发一边听，因为收发在两个方向上是隔离的。

无线网卡不行，因为收发用同一个频率、同一根天线。

所以有线那套"撞了再退"（Collision Detection，冲突检测；冲突就是两路同频信号在空中叠在一起，接收方解不出来）在物理上做不到。

无线只能改成"先约好再发"（Collision Avoidance，冲突避免）。

这一篇讲的就是这套"约"的规矩。

CSMA/CA 的全称是载波监听多路访问/冲突避免（Carrier Sense Multiple Access with Collision Avoidance），四个词对应四件事：先听、大家一起用、撞了要避免、怎么避免。

## 1. 无线为什么不沿用有线的办法

为什么不能"努力做得更好一点"？

因为这里差的不是精度，是物理条件：收发共用同一根天线、同一个频率。

光纤和双绞线有个天然优势：**方向隔离**。

```text
双绞线：1-2 对线发，3-6 对线收，两个方向各走各的
光纤：  一根纤发，一根纤收（或者波分复用）
```

收发物理隔离，所以"边发边听"是免费的。

无线没有这个条件。

```text
802.11 用 2.4 GHz 或 5 GHz 的同一个频段
收发共用一根天线
半双工：要么在发，要么在收，不能同时
```

半双工（half duplex）：收发共用一条通道，同一时刻只能干一件。

对应的全双工是收发各有一条通道，可以同时进行，有线网卡就是这种。

更麻烦的是功率差。

```text
网卡发射功率  约 15–20 dBm
接收灵敏度    约 −90 dBm
两者差        100 dB 以上，即 10^10 倍
```

也就是说，自己发出去的信号，比远处 AP 传来的信号强一百亿倍。

想在这种条件下"听出别人也在发"，等于在打雷的时候听蚊子叫。

物理上不可能。

频段这件事也值得说一句。

```text
2.4 GHz：穿墙好，但微波炉、蓝牙、邻居 AP 都在挤，只有 3 个不重叠信道
5 GHz：  干净、速率高，但穿墙差、覆盖小
```

信道（channel）：一段划定好频率范围的无线电通道，同一信道上的人一起抢，不同信道的人互不干扰。

选频段不是"哪个更好"，是"哪个代价更能接受"。

于是 CSMA/CD 的两条前提，在无线里全破了。

```text
前提一：能边发边听      → 破（半双工 + 自干扰）
前提二：冲突双方都听得见 → 破（隐藏终端）
```

前提破了，结论就得换。

换成 CSMA/CA。

## 2. 最小模型：一个 BSS 长什么样

为什么要先认识这几个名字？

因为后面每一句"谁发给谁"，都得先知道谁是 STA、谁是 AP、这一帧在不在同一个 BSS 里。

802.11 的网络结构，先记住四个词。

```text
STA   station        站点，就是手机、笔记本这些客户端
AP    access point   接入点，那个"路由器"上的天线
BSS   basic service set  基本服务集，一个 AP 加它管的所有 STA
SSID  服务集标识      你看到的 WiFi 名字
```

一句话记住：STA 是你手里的手机或笔记本，AP 是它连的那个盒子，BSS 是"一个 AP 加它管的所有 STA"，SSID 是 WiFi 列表里看到的那个名字。

一个 BSS 就是"一个 AP 和它的势力范围"。

```text
              ┌─────── BSS ────────┐
              │                     │
        STA1 ●│                     │● STA3
              │        ● AP         │
        STA2 ●│        │            │● STA4
              └────────┼────────────┘
                       │
                   ────┴──── 有线骨干（DS）
```

AP 的 MAC 地址还有个专门名字，叫 **BSSID**。

SSID 是给人看的名字，BSSID 是给机器看的地址。

多个 BSS 用有线骨干（**分布系统 DS**）连起来，共用一个 SSID，就叫**扩展服务集 ESS**。

```text
ESS = BSS1 + BSS2 + … + DS
      └─ 同一个 SSID，同一栋楼里走来走去不断网 ─┘
```

AP 干的活不止转发。

```text
1. 发信标（beacon），每隔约 100 ms 广播一次"我在这儿，我叫 XX，支持什么速率"
2. 认证与关联（authentication / association），决定让不让你进来
3. 转发：无线帧 ↔ 有线帧的转换与桥接
4. 给关联的站分配功率、速率、信道
```

所以 AP 本质上是"无线的集线器 + 一座桥"，不是交换机。

这一点在 [11 篇](/posts/cn-wan-bridge-switch/)讲网桥时会再对上一次。

还有两个常被忽略的事实。

```text
信道隔离：相邻 AP 用不同信道才不会互相干扰（2.4G 只有 1/6/11 三个不重叠）
漫游：    同一 ESS 内换 AP，靠信号强度判断，切换过程会掉几十毫秒的包
```

"走到另一个房间视频卡一下"，通常就是漫游在发生。

再补一个模式：**Ad-hoc（IBSS）**。

没有 AP，站和站直连，覆盖很小，实际几乎见不到。

408 只考"有 AP 的基础设施模式"。

## 3. 为什么无线不能做冲突检测

为什么这一节要拆成三层？

因为"做不到"有三种不同的原因：硬件不行、视野不全、后果只能由别人承担。

三层里只要有一层成立，冲突检测就没法用；无线是三层全中。

这一节是整篇的地基，值得拆成三层。

**第一层：硬件做不到。**

半双工 + 同频 + 自干扰。

发送时自己的信号把自己的接收电路灌满了。

**第二层：就算能做到，也听不全。**

这就是**隐藏终端（hidden terminal）**问题。

隐藏终端（hidden terminal）：两个站都能和同一个 AP 正常通信，但它们彼此听不见，于是一个在发的时候，另一个以为信道是空的。

```text
A ●━━━━━━━━━━━● B ●━━━━━━━━━━━● C
  └─ 能互相听见 ─┘   └─ 能互相听见 ─┘

A 和 C 之间：完全听不见
```

A 和 C 都在 B 的覆盖范围内。

A 发的时候，B 收得到。

C 呢？C 听不到 A，以为信道空闲，也开始发。

两个信号在 B 那里撞成一团。

而 A 和 C 谁都不知道撞了，因为它们互相听不见。

这就是"冲突双方都听得见"这个前提破掉的样子。

**第三层：冲突只能在接收方被发现。**

既然发送方听不出来，冲突的后果就只能由 B 来承受：

```text
B 收到一坨叠加的信号 → FCS 校验失败 → 整帧丢弃
B 不回 ACK
A 等不到 ACK → 认为"可能撞了" → 退避重发
```

注意这条链的最后一步：**冲突的证据是"没有 ACK"，不是"听到了冲突"。**

这决定了整个 CSMA/CA 的设计风格：一切都围绕 ACK 转。

假设硬要用 CD 会怎样？

```text
要么在收发之间快速切换（切换时间远大于帧传播时间，来不及）
要么用两套频率（那就不是 802.11 了，是 FDD 的老式蜂窝思路）
```

两条路都要重新设计射频前端，成本远超收益。

于是标准选择了最省事的办法：

```text
不做检测，改用"确认 + 重传"来兜底。
撞了就当丢包，丢了就重发。
```

这就是为什么 802.11 的 MAC 看起来"很像一个不可靠的链路层加固版"。

> **反直觉的点**：无线网卡发出去的那一刻，是它听力最差的一刻。
> 有线网卡的"边听边发"在无线里不是"没实现"，是**物理上不可能**。
> 所以无线不是"检测冲突更弱"，而是"根本没有检测冲突这个动作"。
> 它的"冲突检测"其实退化成了"超时没收到 ACK"。

## 4. CSMA/CA 的完整流程

为什么要把流程拆成七步？

因为无线里"发一帧"不是"把数据推出去"这一个动作，而是"听、等、退、发、等确认"五类动作排成的队。

少掉任何一步，都会退回到"两家人同时说话"的状态。

这七步里会出现两个新词：DIFS 和 SIFS，都是"发之前必须空等的固定时长"，第 5 节细讲。

把一次成功的发送摊开，一共七步。

```text
1. 监听信道（物理载波监听 + 虚拟载波监听）
2. 信道空闲，继续等一个 DIFS
3. DIFS 结束仍空闲，进入退避：从 [0, CW] 里随机取一个数
4. 每过一个时隙减 1；期间信道变忙 → 冻结计数，等下次空闲 DIFS 后接着减
5. 计数减到 0 → 发送这一帧
6. 接收方收全、FCS 正确 → 等一个 SIFS → 回 ACK
7. 发送方在超时前收到 ACK → 成功；超时 → CW 加倍，回到第 3 步
```

两个词先钉死。

退避（backoff）：先随机等一小段时间再发，把大家的发送时刻摊开。

时隙（slot）：退避计数的单位时间，每过一个时隙，计数减 1。

画成时序：

```text
发送方 A                                    接收方 B
   │                                           │
   │  信道空闲                                  │
   │←─ DIFS ─→│                                │
   │← 退避 5 个时隙 →│                          │
   │                │                          │
   │──── DATA ──────────────────────────────►  │
   │                                           │ 校验 FCS
   │                          ←── SIFS ──→      │
   │  ◄────────────────────────────── ACK ────  │
   │                                           │
```

三个动作值得单独说。

**DIFS 之后再退避，不是 DIFS 完就发。**

如果没有随机退避，所有等 DIFS 的站会在同一刻一起发，必然撞。

随机退避的作用是**把发送时刻摊开**。

这就是"避免"（Avoidance）的实际含义。

**退避计数会被冻结，不会被清零。**

信道中途变忙，计数停下来，等下次空闲再接着减。

不清零是为了公平：已经等了一会儿的站，不该因为别人插队而重新排队。

**ACK 只用 SIFS。**

SIFS 比 DIFS 短，所以 ACK 一定抢在别人的新帧之前。

这是"优先级"的实现方式，下一节展开。

802.11 其实有两种协调方式。

```text
DCF  分布式协调  没有中心，大家用 CSMA/CA 抢     ← 实际在用的
PCF  点协调      AP 轮询，谁被点到谁发          ← 几乎没人实现
```

408 只考 DCF。

看到"DIFS、退避、SIFS、ACK"这套组合，就说明在说 DCF。

## 5. 帧间间隔：SIFS、PIFS、DIFS

为什么要定义三种间隔，而不是只定一种"等多久"？

因为无线里有一些帧比别的帧更要紧：ACK 晚到一步，发送方就会误判丢包；而普通数据帧晚一点没人受伤。

给不同的帧排不同的等待时间，就等于给它们排了优先级。

802.11 定义了三种帧间间隔（IFS）。

```text
SIFS  Short IFS   最短   → ACK、CTS、分片后续帧
PIFS  PCF IFS     中等   → AP 在轮询模式下的优先帧
DIFS  DCF IFS     最长   → 普通站的竞争帧
```

规则只有一句：

```text
谁等的间隔短，谁先发。
```

于是优先级自己就出来了：

```text
时间轴 ──────────────────────────────────────►

信道变空闲
   │
   ├── SIFS（10 μs）──►  ACK 在这里发，没人抢得过
   │
   ├────── PIFS ──────►  AP 的轮询帧在这里发
   │
   ├────────── DIFS ──────────►  普通站从这儿才开始竞争
```

SIFS 的站根本不用退避，因为别人还在等 DIFS，它已经发完了。

这就是为什么 ACK 不会被"别人的数据帧"插队。

具体数值（要背的只有两组）：

```text
802.11b（DSSS）  时隙 20 μs   SIFS 10 μs   DIFS 50 μs
802.11a/g（OFDM）时隙 9 μs    SIFS 16 μs   DIFS 34 μs
```

注意 DIFS 和 SIFS 的关系：

```text
DIFS = SIFS + 2 × 时隙

802.11b：10 + 2×20 = 50 ✓
802.11a/g：16 + 2×9 = 34 ✓
```

为什么正好是"两个时隙"？

因为退避计数至少要能减 1 次、还要留出检测信道变化的余量。

这是个设计上的整数，记住等式比记三个数更稳。

还有一点：SIFS 是固定值，不随时隙变。

它只跟物理层有关（解调、天线切换、MAC 处理），所以 802.11b 是 10 μs，802.11a/g 是 16 μs。

记"哪个短"比记具体数值重要。

## 6. 退避与竞争窗口

为什么窗口要能变大变小，而不是定一个固定值？

因为站的数量在变：屋里五个人时，窗口小一点抢得快；屋里五十个人时，窗口不放大就会挤成一团。

CW 自动翻倍，就是这个自适应。

退避值从 `[0, CW]` 里均匀随机取。

CW 是**竞争窗口（contention window）**，它不是固定的。

```text
初始：CW = CWmin
每次失败（没收到 ACK）：CW = 2 × CW + 1
到 CWmax 封顶
发送成功：CW 重置为 CWmin
```

典型值：

```text
802.11b    CWmin = 31    CWmax = 1023
802.11a/g  CWmin = 15    CWmax = 1023
```

CWmin 的大小是在两件事之间折中。

```text
CWmin 小 → 抢得快，但容易撞
CWmin 大 → 不容易撞，但空口经常白白空着
```

31 大概是"十来个站"这个量级下折中的结果。

站变多了怎么办？

靠 CW 自动翻倍来适应，不需要任何人改配置。

时隙这个小数字，其实也有物理含义。

它必须大于"一个站在最坏情况下检测到别人开始发送"所需的时间。

802.11b 的 20 μs，就是为了覆盖 BSS 半径（约 100 m）内的传播时延加检测时延。

所以时隙不是随便定的，它和覆盖半径绑在一起。

这和以太网的 2τ 是同一个道理，只是那边叫"争用期"，这边藏在一个"时隙"里。

算一下 802.11b 的退避上限：

```text
第一次尝试：从 [0, 31] 里取，平均等 15.5 个时隙
             15.5 × 20 μs = 310 μs

失败一次： CW = 63，平均等 31.5 个时隙 = 630 μs
失败两次： CW = 127，平均 63.5 个时隙 = 1.27 ms
失败三次： CW = 255，平均 127.5 个时隙 = 2.55 ms
失败四次： CW = 511，平均 255.5 个时隙 = 5.11 ms
失败五次： CW = 1023，平均 511.5 个时隙 = 10.2 ms
```

看出规律没有：**每失败一次，平均等待时间翻一倍。**

这和有线以太网的二进制指数退避是同一个思路，只是"撞"的判据从"听到冲突"换成了"没收到 ACK"。

有个细节容易错：

```text
有线：撞了 → 先发 jam → 再退避 → 重发
无线：没收到 ACK → 直接退避 → 重发
```

无线没有 jam。

因为发送方根本不知道撞了，也没有"立刻中止"的能力。

它只能把一整帧发完，然后等 ACK，等不到再重来。

所以一次无线冲突的代价，比有线大得多：

```text
有线冲突：发了几微秒就停，浪费很小
无线冲突：整帧发完（可能几百微秒到几毫秒），全白费
```

算个具体的对比。

```text
有线：1000 B 帧，10 Mbps，帧要发 800 μs
      但冲突最晚在 51.2 μs 内被发现
      浪费 ≤ 51.2 μs

无线：1000 B 帧，11 Mbps，帧要发 727 μs
      发送方全程不知道
      如果末尾才发现丢，浪费 727 μs
```

差了一个数量级。

这就是"无线对冲突更敏感"的量化原因。

## 7. 虚拟载波监听：NAV

为什么"听信道"这件事要做两遍？

因为物理监听只能覆盖到自己耳朵能到的地方，而无线里"听不见"是常态。

一遍管现在，一遍管接下来，两者取更忙的那个，才能把隐藏的邻居也算进来。

"听信道"这件事，无线做了两遍。

```text
物理载波监听（physical carrier sense）
  真的去测空中有没有 802.11 信号能量

虚拟载波监听（virtual carrier sense）
  听别人"说"信道要被占用多久，然后自己倒计时
```

虚拟监听靠的是帧里的 **Duration 字段**。

任何站收到一个帧，就把 Duration 的值读出来，塞进自己的 **NAV（network allocation vector，网络分配向量）** 计数器。

```text
NAV > 0  →  信道"逻辑上"忙，不许发（哪怕物理上听不到信号）
NAV = 0  →  才允许进入竞争
```

说白了，NAV 就是一串倒计时：读到多少微秒，就闭嘴多少微秒。

为什么需要这一层？

因为物理监听只能听到**自己能听到的**信号。

RTS（Request To Send，请求发送）和 CTS（Clear To Send，允许发送）是两个很短的控制帧：前者问"我能占多久"，后者答"你可以占"。

隐藏终端听不到，但可能听得到 CTS——而 CTS 里就带着 Duration。

```text
A 发 RTS（Duration = 整个交换要用的时间）
AP 回 CTS（Duration 同样）
C 听得到 AP 的 CTS，读 Duration，设 NAV
C 在 NAV 倒数完之前，不会发任何东西
```

这就是把"听不见的冲突"变成"看得见的预约"。

如果没有 NAV 会怎样：C 既听不到 A 的发送，也不会去读 AP 那个 CTS，于是它在 A 传到一半时插话。

AP 收到的整帧作废，A 白发了 727 μs 还得从头再来。

而且 A 只会以为"这次运气不好"，下一次照样被同一个 C 撞。

NAV 的全部价值，就是把"我有个听不见的邻居正在发"变成一行自己能读的倒计时。

一句话概括：

```text
物理监听管"现在有没有人在发"
虚拟监听管"接下来一段时间有没有人被允许发"
```

两者取"忙"的那个。

举个具体的数值例子。

```text
A 发 RTS，Duration = 1000 μs
B 收到 RTS，NAV = 1000，开始倒计时
AP 回 CTS，Duration = 1000 − SIFS − CTS 的发送时间
C 只听到 CTS，于是 C 的 NAV 比 B 短一点
```

为什么要减？

因为 CTS 发出去的时候，那段时间已经过去了。

**谁后听到，谁的 NAV 就短。**

这样才能保证所有站的 NAV 同时归零，而不是各算各的、越算越乱。

## 8. RTS/CTS 与隐藏终端

为什么还要专门加一套握手，而不是靠 NAV 自动生效？

因为 NAV 依赖"收到一个带 Duration 的帧"，而隐藏终端连数据帧都收不到。

必须有人替它把"这段时间被占了"这句话，用它能听见的音量再说一遍。

RTS/CTS 是 802.11 里唯一一个"显式握手"的机制。

```text
A ──── RTS ────► AP        "我想发 1000 字节，占多久"
A ◄─── CTS ──── AP         "可以，大家听着，这段时间归 A"
A ──── DATA ───► AP
A ◄─── ACK ──── AP
```

关键在于 CTS 是**广播**的，而且是从 AP 发出的。

AP 的覆盖范围比 A 大，所以：

```text
C 听不到 A 的 RTS，但听得到 AP 的 CTS
C 从 CTS 里读到 Duration，设 NAV，闭嘴
```

隐藏终端就这么被"通告"掉了。

时序上多花了多少？

```text
RTS + SIFS + CTS + SIFS
```

这四段时间是纯开销，数据一个字节都没传。

算一下 802.11b、11 Mbps 下的开销：

```text
RTS 20 B = 160 bit / 11 Mbps = 14.5 μs
SIFS                          = 10 μs
CTS 14 B = 112 bit / 11 Mbps = 10.2 μs
SIFS                          = 10 μs
合计                          = 44.7 μs
```

传一个 1000 字节的帧要 727 μs，44.7 μs 的开销约 6%，还能接受。

传一个 100 字节的帧只要 72.7 μs，44.7 μs 的开销超过 60%，就很亏。

所以 RTS/CTS 是**有条件启用**的：

```text
帧长超过 RTS 阈值（典型 2347 B，很多驱动默认 500 B 左右）才发 RTS
小于阈值直接发数据，赌一把
```

RTS/CTS 还有两个副作用，值得知道。

```text
1. 它不解决"暴露终端"：不在冲突范围的站也被 NAV 禁言了，浪费机会。
2. 它本身也可能撞：两个站同时发 RTS，CTS 就回不出来。
```

所以它是"降低概率"，不是"消灭冲突"。

无线里没有"消灭冲突"这回事。

还有另一面，叫**暴露终端（exposed terminal）**。

暴露终端（exposed terminal）：明明自己发了也不会撞，却因为听见别人在发而不敢发，白白错过机会。

```text
B 正在发给 A，C 听到了 B 的发送
但 C 其实可以同时发给 D（D 离 B 很远）
C 不敢发，白白浪费了机会
```

这是"过于保守"的代价。

RTS/CTS 把隐藏终端换成了暴露终端，不是免费的午餐。

## 9. 802.11 的帧格式与三种帧

为什么无线帧比以太网帧"胖"？

因为它要同时说清"这一跳是谁发给谁"和"最终要送到哪"，还要带上预约时长的字段。

多出来的字节，都是为跨无线和有线那一步付的钱。

先看数据帧的骨架。

```text
┌──────────┬──────────┬────────┬────────┬────────┬───────┬──────────┬──────┐
│ Frame    │ Duration │ Addr1  │ Addr2  │ Addr3  │ Seq   │ 数据      │ FCS  │
│ Control  │          │        │        │        │       │          │      │
│ 2 B      │ 2 B      │ 6 B    │ 6 B    │ 6 B    │ 2 B   │ 0–2312 B │ 4 B  │
└──────────┴──────────┴────────┴────────┴────────┴───────┴──────────┴──────┘
                                                    Addr4 6 B（可选，出现在 WDS 模式）
```

和以太网比，最刺眼的是**三个地址**。

以太网两个地址（目的、源）就够了。

802.11 要三个，因为帧可能要从无线跨到有线：

```text
Addr1  接收方（下一跳）
Addr2  发送方
Addr3  最终目的（可能是 DS 另一侧的主机）
```

这三个地址的含义随 Frame Control 里的 `To DS` / `From DS` 两位变化。

408 不考那么细，知道"因为要跨无线和有线，所以地址变多"就够了。

顺带算一下头部开销。

```text
固定部分 = 2 + 2 + 6 + 6 + 6 + 2 = 24 B
加 FCS 4 B = 28 B
以太网固定部分只有 14 B（不含 FCS）
```

每帧多背 14 字节。

帧越小，这 14 字节越心疼。

帧分三类：

```text
管理帧（management）  beacon、probe request/response、auth、assoc
                      → 发现网络、加入网络
控制帧（control）     RTS、CTS、ACK、PS-Poll
                      → 帮数据帧抢信道、确认
数据帧（data）        真正承载上层数据
```

你在 Wireshark 里看到的 802.11 流量，绝大多数是管理帧。

因为 beacon 每 100 ms 一次，一堆 AP 一起发，非常吵。

管理帧串起来的，就是"连上一个 WiFi"的全过程。

```text
1. 扫描   被动：听 beacon；主动：发 probe request，等 probe response
2. 认证   authentication（开放系统或共享密钥）
3. 关联   association request / response，拿到 AID
4. 加密   四次握手（WPA2）、或 SAE（WPA3）
5. 配地址 DHCP 拿 IP
```

注意第 3 步之后才能传数据。

只"连上"不"关联"是没用的，很多"连上了但上不了网"就是卡在第 4、5 步。

这套流程里有三处用了本篇的机制。

```text
probe request 是广播（目的 ff:ff:ff:ff:ff:ff），要走 DIFS + 退避
association response 要 ACK
beacon 不需要 ACK，它是单向广播
```

数据帧的长度也有讲究。

```text
MSDU 最大 2304 B（加密后 2312 B）
```

比以太网的 1500 B 大，因为无线可以把多个以太网帧聚合进一个 MSDU（A-MSDU）。

反过来也有**分片（fragmentation）**：帧太长就切成小片，每片单独 ACK。

分片（fragmentation）：把一个装不下或者容易出错的帧切成几个小帧，各带序号、各自等 ACK，坏哪片重传哪片。

```text
1000 B 的帧错一个比特 → 整帧重传 → 白费 727 μs
250 B 的分片错一个比特 → 只重传这 250 B → 白费 182 μs
```

分片是用"更多开销"换"更小的重传代价"。

信号差的时候开分片有收益，信号好的时候纯属浪费。

## 10. 无线与有线的 MAC 对比

为什么要并排比？

因为这两套机制最容易被背成两串互不相干的规则。

并排放之后你会发现，区别只有一句"先发还是先等"，其余每一条都是这句话的推论。

把两套机制并排放，差别一目了然。

| 方面 | 有线以太网 CSMA/CD | 无线 802.11 CSMA/CA |
|---|---|---|
| 发送前 | 听，空闲就发 | 听，空闲后还要等 DIFS + 随机退避 |
| 发送中 | 一直听，检测冲突 | 不听，物理上做不到 |
| 冲突的判据 | 收到叠加信号 | 超时没收到 ACK |
| 冲突后的动作 | 立即停，发 jam | 整帧发完，白费 |
| 确认机制 | 没有 | 每帧都要 ACK |
| 隐藏终端 | 不存在 | 存在，靠 RTS/CTS + NAV |
| 信道预约 | 没有 | Duration 字段 + NAV |
| 退避触发时机 | 冲突之后 | 发送之前就退避 |

最后一行是最本质的区别。

```text
有线：先发，撞了再退（Detection）
无线：先退，尽量别撞（Avoidance）
```

一个字之差，整套时序完全不同。

表里最容易被忽略的是"确认机制"那一行。

以太网没有确认，因为它假设"冲突能检测、比特基本不会错"。

无线有确认，因为它这两个假设都不成立。

所以 802.11 的 MAC 本质上比以太网"更厚"：多了 ACK、多了退避、多了预约。

## 11. 标称 1200 Mbps，为什么实测只有 400

为什么标称和实测差这么多，而且差得这么有规律？

因为无线是按"一次协调、发一帧"来算账的：协调的时间是固定的，帧再短也不会缩短它。

先把账算清楚，再看怎么把帧粘起来。

这是最常被问的一个"为什么"。

答案不在信号，在**开销**。

先算一个理想的单帧往返，用 802.11ac 一类的参数：

```text
PHY 速率       1200 Mbps
数据帧         1500 B
前导码 + PLCP  约 40 μs
DIFS           34 μs
平均退避       约 7.5 个时隙 × 9 μs = 67.5 μs
SIFS           16 μs
ACK（基本速率 6 Mbps）112 bit / 6 Mbps = 18.7 μs
```

数据本身只要多久？

```text
12000 bit / 1200 Mbps = 10 μs
```

于是一帧的总占用是：

```text
10 + 40 + 34 + 67.5 + 16 + 18.7 ≈ 186 μs
效率 = 10 / 186 ≈ 5.4%
```

1200 Mbps 的物理层，单帧效率只有 5%。

真正发数据的时间占不到二十分之一。

三个罪魁祸首：

```text
1. 前导码按固定时长发，不随速率缩短 → 速率越高，它占比越大
2. ACK/RTS/CTS 走"基本速率集"（通常 6 Mbps），不是 1200 Mbps
3. DIFS + 退避 是纯等待，一个字节都不传
```

基本速率集（basic rate set）：一个 BSS 里所有站都必须支持的最低速率，用最慢但最稳的调制方式发，保证控制帧人人都听得懂。

破解办法只有一个：**把多个帧粘在一起发**。

这就是 802.11n/ac 的帧聚合（A-MPDU）。

```text
64 个 1500 B 帧聚成一个聚合帧：
  数据  = 64 × 10 = 640 μs
  开销  = 40 + 34 + 67.5 + 16 + BlockAck ≈ 180 μs
  效率  = 640 / 820 ≈ 78%
```

效率从 5% 跳到 78%，这才是 11ac 能跑到几百兆的原因。

所以"标称速率"这个词有欺骗性：

```text
标称 1200 Mbps  = 物理层在理想条件下的瞬时比特率
实测 400–600    = 扣掉前导码、IFS、ACK、退避、重传、邻居竞争之后
```

还有两个减法不能忘。

```text
半双工：同一时刻不能收发，上下行共享这段空口时间
共享：  同一个信道上的所有 STA 和 AP 一起竞争，人越多每人越少
```

一句话：**无线的瓶颈从来不是调制，是协调。**

## 12. 容易混淆的点

为什么无线这一篇的"混淆点"特别多？

因为它的机制是从"做不到"推出来的，而不是从"规定"抄下来的。

**第一，CSMA/CA 不是"不检测冲突"。**

是"检测不了"，所以改成"避免"。

如果哪天硬件能边发边听，无线也会用 CD。

**第二，DIFS 比 SIFS 长。**

数字上 50 > 10。

含义上"等得久的优先级低"，别记反。

**第三，ACK 用 SIFS，所以不会被打断。**

别人还在等 DIFS，ACK 已经发完了。

这不是"ACK 优先"，是"ACK 等得少"。

**第四，退避发生在发送之前。**

这是 CSMA/CA 和 CSMA/CD 最容易搞混的地方。

有线的退避是"撞了以后等多久再重试"。

无线的退避是"想发的时候先随机等一会儿，把撞的概率摊开"。

两者都会在失败后加倍窗口，但触发点不一样。

**第五，CW 指数增长但有上限。**

CWmax = 1023，不会无限翻。

**第六，802.11 的"冲突"在发送方是不可见的。**

发送方永远不知道"撞了"，它只知道"没收到 ACK"。

所以丢帧和撞帧在发送方看来完全一样。

**第七，RTS/CTS 不是必需的。**

它是可选优化，大帧才用。

小帧开 RTS 反而拖慢网络，这是很多人调 WiFi 参数调错的地方。

**第八，AP 不是交换机。**

AP 是"无线的桥"：把 802.11 帧转成 802.3 帧，反之亦然。

虽然家用"路由器"把 AP、交换机、NAT、DHCP 全塞在一个盒子里。

**第九，beacon 不用 ACK，也不算冲突。**

它是 AP 单向广播，没有接收方确认。

所以 beacon 丢了就丢了，下一个 100 ms 还有。

**第十，隐藏终端不等于"信号弱"。**

隐藏终端是"听不见"，不是"听不清"。

信号弱是"听得见，但解码老出错"，两者的现象都是慢，处理办法完全不同。

两个站在互相的覆盖盲区里，但都能正常和 AP 通信。

所以"信号满格却特别慢"有时候就是隐藏终端在作怪。

**第十一，CA 不是"避免冲突发生"，是"降低冲突概率"。**

冲突仍然会发生，只是变少了。

真正兜底的是 ACK 加退避重传。

## 13. 408 怎么考

为什么这一块的计算题不难却容易错？

因为公式只有"字节乘 8 除以速率再累加间隔"一条，难点全在"哪几段 SIFS 要算、哪一段不算"。

题型和易错点一起看，才不会在细节上翻船。

无线这一块的题型：

```text
1. 判断 CSMA/CA 与 CSMA/CD 的差别（选择题常客）
2. RTS/CTS 解决什么问题
3. DIFS / SIFS 谁先发
4. 算一段 802.11 交换的总时间
```

### 例题（自拟）

某 802.11b 网络，速率 11 Mbps，时隙 20 μs，SIFS 10 μs，DIFS 50 μs。

RTS 20 B，CTS 14 B，ACK 14 B，数据帧 1000 B。忽略前导码。

三问：

```text
(1) 某站退避计数值为 5，信道在 t=0 变为空闲，它最早何时能开始发送？
(2) 从 RTS 开始到 ACK 结束，一次完整交换需要多久？
(3) RTS/CTS 这套握手本身占了多少时间？占 (2) 的比例是多少？
```

**第 (1) 问**

要先等 DIFS，再走 5 个时隙。

```text
t = DIFS + 5 × 时隙
  = 50 μs + 5 × 20 μs
  = 50 + 100
  = 150 μs
```

答：t = 150 μs。

注意不是 100 μs。

DIFS 是必须先等的，退避计数在 DIFS 之后才开始减。

**第 (2) 问**

按顺序累加，每一段都换成时间。

```text
RTS   20 B = 160 bit  / 11 Mbps = 14.5 μs
SIFS                            = 10   μs
CTS   14 B = 112 bit  / 11 Mbps = 10.2 μs
SIFS                            = 10   μs
DATA  1000 B = 8000 bit / 11 Mbps = 727.3 μs
SIFS                            = 10   μs
ACK   14 B = 112 bit  / 11 Mbps = 10.2 μs
```

求和：

```text
14.5 + 10 + 10.2 + 10 + 727.3 + 10 + 10.2 = 792.2 μs
```

答：约 792 μs。

**第 (3) 问**

RTS/CTS 的净开销 = RTS + SIFS + CTS + SIFS。

```text
14.5 + 10 + 10.2 + 10 = 44.7 μs
```

占比：

```text
44.7 / 792.2 ≈ 5.6%
```

答：44.7 μs，约占 5.6%。

如果数据帧只有 100 字节：

```text
DATA = 800 bit / 11 Mbps = 72.7 μs
总时间 = 14.5 + 10 + 10.2 + 10 + 72.7 + 10 + 10.2 = 137.6 μs
开销占比 = 44.7 / 137.6 ≈ 32%
```

开销从 5.6% 涨到 32%，这就是"小帧不值得开 RTS"的算术依据。

### 一道选择题

关于 CSMA/CA，下列说法正确的是？

```text
A. 无线网卡可以边发送边检测冲突，只是灵敏度较低
B. 802.11 的 ACK 使用 DIFS，因此优先级低于数据帧
C. RTS/CTS 的作用之一是让隐藏终端从 CTS 的 Duration 设置 NAV
D. CSMA/CA 不需要退避，因为冲突已经被"避免"了
```

答案：C。

逐个排除：

```text
A 错：物理上做不到，不是灵敏度问题（半双工 + 自干扰）
B 错：ACK 用 SIFS，比 DIFS 短，优先级更高
D 错：CA 的核心恰恰是"发送前就随机退避"
```

### 套路总结

```text
判差别题：抓三句——能不能边听边发、冲突靠什么发现、有没有 ACK。
RTS/CTS：答"隐藏终端 + 让第三方从 CTS 里读到 Duration 设 NAV"。
先后题：  SIFS < PIFS < DIFS，等得少的先发。
算时间题：一律"字节 → 比特 → 除以速率 → 加 IFS"，注意 SIFS 出现几次。
```

## 14. 真实网络里长什么样

为什么无线尤其需要看命令行？

因为"信号满格但很慢"这类现象，凭感觉永远分不清是信号弱、邻居多、还是自己在重传。

三个计数器摆在一起看，答案就出来了。

先看无线接口的状态。

```text
$ iw dev
phy#0
        Interface wlan0
                ifindex 3
                type managed
                channel 36 (5180 MHz), width: 80 MHz
```

`type managed` 表示这是"客户端模式"。

要做 802.11 抓包，得切到 `monitor` 模式。

```text
$ sudo ip link set wlan0 down
$ sudo iw dev wlan0 set type monitor
$ sudo ip link set wlan0 up
$ sudo iw dev wlan0 info
        type monitor
```

然后 Wireshark 里就能看到真正的 802.11 帧了。

```text
No.  Time      Source            Destination       Protocol  Info
1    0.000000  11:22:33:44:55:66 ff:ff:ff:ff:ff:ff 802.11     Beacon, SSID=MyWiFi
2    0.001204  11:22:33:44:55:66 66:77:88:99:aa:bb 802.11     Probe Response
3    0.104311  aa:bb:cc:dd:ee:ff 11:22:33:44:55:66 802.11     RTS
4    0.104425  11:22:33:44:55:66 aa:bb:cc:dd:ee:ff 802.11     CTS
5    0.104560  aa:bb:cc:dd:ee:ff 11:22:33:44:55:66 802.11     QoS Data
6    0.104890  11:22:33:44:55:66 aa:bb:cc:dd:ee:ff 802.11     Ack
```

（以上为简化示意，时间戳和地址都是编的。）

注意第 3、4 行就有 RTS/CTS，第 6 行紧跟一个 Ack。

在 Wireshark 里点开一帧，能看到 `Duration` 字段，那个值就是 NAV 的来源。

再看一个反常识的现象。

**普通模式下你抓不到 802.11 头。**

```text
$ sudo tcpdump -i wlan0 -e -c 2
14:30:02.113 3c:7c:3f:12:34:56 > 00:1a:2b:3c:4d:5e, ethertype IPv4 (0x0800)
```

这里显示的 `ethertype IPv4` 和两个 MAC，是**以太网格式**。

因为驱动做了 802.11 → 802.3 的转换，把三个地址压成两个，把 Frame Control 和 Duration 全扔了。

所以你看到的"无线抓包"其实是"伪装成以太网的无线帧"。

想看到 RTS/CTS 和 NAV，只有 monitor 模式一条路。

看关联的 AP 和信号质量：

```text
$ iw dev wlan0 link
Connected to 11:22:33:44:55:66 (on wlan0)
        SSID: MyWiFi
        freq: 5180
        signal: -52 dBm
        tx bitrate: 433.3 MBit/s
```

`-52 dBm` 是不错的信号（越接近 0 越好，-70 以下就开始不稳）。

扫一遍周围的 AP：

```text
$ sudo iw dev wlan0 scan | grep -E "SSID|signal|DS Parameter|RSN"
        signal: -52.00 dBm
        SSID: MyWiFi
        DS Parameter set: channel 36
        RSN:     * Version: 1
```

`DS Parameter set` 是信道号，`RSN` 说明这个 AP 支持 WPA2/WPA3。

同一个信道上有几个 AP，就有几个站在抢空口时间。

这就是"楼上楼下都用 6 信道"会互相拖慢的机制层面原因。

还有一个数字很能说明问题：

```text
$ iw dev wlan0 survey dump
        frequency:              5180 MHz
        noise:                  -95 dBm
        channel active time:    88213 ms
        channel busy time:      31204 ms
        channel busy time:      35%
```

`channel busy time` 占 35%，说明空口有三成时间被别人占着。

这个数超过 60%，再好的信号也会卡。

最后看一个最能体现"重传"的计数器：

```text
$ iw dev wlan0 station dump
Station aa:bb:cc:dd:ee:ff (on wlan0)
        signal:       -52 dBm
        tx retries:   1204
        tx failed:    37
        tx bitrate:   433.3 MBit/s
```

`tx retries` 就是"没收到 ACK 又重发"的次数。

它才是无线里"冲突"的真实体温计。

有线看 `collsns`，无线看 `tx retries`。

一个容易搞错的判读：`tx retries` 高不一定是信号差。

```text
信号弱       → 重传
邻居多       → 撞了重传
开了 RTS     → 握手本身失败也会重传
```

要定位物理层问题，得同时看 `signal` 和 `channel busy time`。

只看一个数会得出相反的结论。

## 15. 小结

压成几行。

```text
无线不能边发边听 → 不能做冲突检测 → 改成冲突避免
隐藏终端：A、C 都听得到 B，互相听不到
冲突的证据不是"听到撞了"，是"没收到 ACK"
CSMA/CA：听 → DIFS → 随机退避 → 发 → SIFS 后等 ACK
优先级靠 IFS：SIFS < PIFS < DIFS，等得少的先发
DIFS = SIFS + 2 × 时隙
退避：CW 指数增长到 1023 封顶，成功就重置
NAV：读 Duration，虚拟地"占住"信道
RTS/CTS：让隐藏终端从 CTS 里听到预约
```

一句话记住这个转折：

```text
有线是"撞了再退"，
无线是"先退再发"。
```

这一篇的三个关键词：听不见、约时间、靠 ACK 兜底。

听不见，所以不能检测。

约时间，所以有 DIFS、退避、NAV、RTS/CTS。

靠 ACK 兜底，所以丢帧和撞帧在发送方看来是同一件事。
