先算一个数。

一条 1 Mbps 的链路，帧长 1000 字节。

发送一帧要多久？

```text
8000 bit / 10^6 b/s = 8 ms
```

而这条链路的往返时延 RTT 是 20 ms。

现在按最朴素的方式发：发一帧，等确认，再发下一帧。

一帧从开始发送到收到确认，需要 8 + 20 = 28 ms。

其中只有 8 ms 在干活。

**链路有 71% 的时间是闲着的。**

这一篇讲的就是怎么把这个 71% 抢回来。

## 1. 流量控制与可靠传输的关系

两个词，经常被当成一回事。

其实它们管的是不同的事。

```text
流量控制：发送方发得太快，接收方的缓冲区会溢出。
         所以要有一个机制，让发送方知道"你慢一点"。

可靠传输：帧丢了、帧坏了、帧重复了、帧乱序了，
         要能发现，并且补回来。
```

一句话区分：

```text
流量控制管"速度"。
可靠传输管"内容"。
```

它们经常被同一套机制实现，但那是因为巧合，不是因为它们本质相同。

巧合在哪？

在"编号 + 确认"这四个字上。

```text
编号：让接收方能说"我要第 5 号"
确认：让发送方能知道"前 4 号都到了"
```

有了这两样，流量控制就能实现——接收方通过"我能收到第几号"来暗示缓冲区还剩多少。

可靠传输也能实现——发送方通过"第几号还没被确认"来判断该重传什么。

**所以滑动窗口一箭双雕。**

它是这一篇的主线，也是第 19 篇 TCP 流量控制的基础。

先分清两件事，再看它们怎么合流。

## 2. 停等协议：窗口为 1

最简单的可靠传输。

```text
发一帧 → 等确认 → 收到确认 → 发下一帧
```

```text
发送方                          接收方
   │                              │
   │  帧 0  ────────────────────►  │
   │  ◄──────────────────── ACK 0  │
   │                              │
   │  帧 1  ────────────────────►  │
   │  ◄──────────────────── ACK 1  │
   │                              │
```

停等协议（stop-and-wait）的名字就是这么来的：停下来，等。

它要处理四种情况，每一种都有考点。

**情况一：一切正常。**

发 0，收 ACK0；发 1，收 ACK1。序号在 0 和 1 之间交替。

**情况二：帧丢失。**

发送方发了帧 0，路上被噪声毁了，接收方根本没收到。

发送方等不到 ACK0，超时，重发帧 0。

接收方收到，回 ACK0。继续。

**情况三：确认丢失。**

帧 0 到了，接收方回了 ACK0，但 ACK0 在路上丢了。

发送方超时，重发帧 0。

接收方又收到一个帧 0。

**这时候如果没有序号，接收方会把它当成新数据，交给上层——重复了。**

有了 1 位序号，接收方一看：我刚收过 0，怎么又来个 0？

丢弃，但**必须再回一次 ACK0**。

为什么必须再回？

因为发送方还在等。它不知道是"帧没到"还是"ACK 没回来"。

如果接收方默默丢弃不回话，发送方会一直重发，死循环。

**情况四：确认迟到。**

ACK0 在路上堵了很久，发送方超时重发了帧 0。

接收方收到重传的 0，回 ACK0。

然后那个迟到的 ACK0 也到了。

发送方看到两个 ACK0，第二个是多余的，忽略即可。

**这就是 1 位序号够用的原因。**

因为停等协议规定"每发一帧必须等确认"，所以任何时刻最多只有一帧在"已发未确认"状态。

序号只需要区分"这一帧"和"上一帧"，两个值就够。

```text
n = 1 bit → 序号空间 2 → 窗口 1
```

这个关系后面会推广：

```text
窗口大小 ≤ 2^n
```

停等协议的窗口是 1，1 ≤ 2^1，成立。

还差一件事没交代：超时时间怎么定。

这是个没有标准答案的活。

```text
定得太短：ACK 还在路上，发送方就以为丢了，重传 → 伪重传
定得太长：真丢帧时要干等很久，利用率更惨
```

工程上的做法是先估计 RTT，再留余量。

```text
超时时间 ≈ 平滑 RTT + 4 × RTT 的偏差
```

为什么是 4 倍？

因为在一个正态分布里，均值加四倍标准差之外的概率不到万分之一。

留这么宽的余量，伪重传的概率就低到可以忽略。

TCP 的 RTO（重传超时）就是这么算的，第 19 篇会给出完整公式。

链路层的停等协议通常更粗暴：直接取一个固定的、远大于 RTT 的值。

因为链路层的 RTT 是稳定的，没什么可估计的。

## 3. 停等的利用率：算一遍，再看提速的代价

利用率（utilization）的定义：

```text
U = 有效工作时间 / 总时间
```

停等协议的一个周期是这样的：

```text
├── Td ──┤├────── RTT ──────┤├─ Ta ─┤
发送数据帧          等确认            收 ACK
```

- Td：数据帧的发送时延
- RTT：往返传播时延
- Ta：确认帧的发送时延

所以：

```text
U = Td / (Td + RTT + Ta)
```

代入题目给的数。

```text
帧长 L = 1000 B = 8000 bit
速率 C = 1 Mbps = 10^6 b/s
RTT = 20 ms
ACK 长度 = 20 B = 160 bit
```

算三个时延：

```text
Td = 8000 / 10^6   = 8 ms
Ta = 160  / 10^6   = 0.16 ms
RTT                = 20 ms
```

代入公式：

```text
U = 8 / (8 + 20 + 0.16)
  = 8 / 28.16
  = 0.2841
  ≈ 28.4%
```

如果题目说"确认帧忽略不计"，就是：

```text
U = 8 / 28 = 0.2857 ≈ 28.6%
```

两种答案差 0.2 个百分点，考试时按题目给的假设走。

这个 28% 意味着什么？

意味着这条 1 Mbps 的链路，实际吞吐量只有：

```text
10^6 × 0.284 = 284 kbps
```

**花了 100% 的钱，用了 28% 的带宽。**

想提高，只有三条路。

```text
① 加大帧长 → Td 变大，占比提高
② 减小 RTT  → 分母变小
③ 不等确认就继续发 → 换协议
```

第一条有上限：帧长受 MTU 和误码率限制，不能无限加。

第二条是物理限制：光速摆在那里，RTT 减不下去。

第三条才是出路。

但先看一个更隐蔽的副作用。

把链路速率从 1 Mbps 提到 1 Gbps，其他不变。

```text
Td = 8000 / 10^9 = 8 μs = 0.008 ms
U  = 0.008 / (0.008 + 20 + 0.0016)
   = 0.008 / 20.0096
   = 0.04%
```

**利用率从 28.4% 掉到了 0.04%。**

再算 100 Mbps：

```text
Td = 8000 / 10^8 = 80 μs = 0.08 ms
U  = 0.08 / 20.08 = 0.4%
```

规律很清楚：

```text
停等协议的利用率 ≈ Td / RTT = L / (C · RTT)
```

速率 C 在分母上。

**速率越高，停等协议的利用率越低。**

这不是反直觉，这是必然。

因为瓶颈从来不是"推比特进线路"的速度，而是"等一个来回"的时间。

链路越快，你越是在用一台更快的机器做更短的活，然后等更长的确认。

这就是为什么高速链路必须用滑动窗口：

**让多个帧同时在路上，用"在途帧数"去填满"时延带宽积"。**

## 4. 滑动窗口：把连发变成编号

滑动窗口（sliding window）的核心思想只有一句：

```text
允许发送方连续发多个帧，不必每帧都等确认。
```

代价是：必须给每个帧编号，而且编号范围不能无限大。

```text
序号位数 n → 序号空间 2^n → 编号 0, 1, 2, ..., 2^n - 1
发完 2^n - 1 之后，从 0 重新开始
```

发送方维护一个窗口，窗口里的帧是"已发但未确认"的。

```text
序号：  0  1  2  3  4  5  6  7  0  1  2  ...
        └──┬──┘
        已确认

           ┌───────────────┐
        │ 1  2  3  4  5 │ 6  7  ...
           └───────────────┘
           发送窗口 W = 5
           ├─ 已发未确认 ─┤├ 还能发 ┤
```

收到 ACK 后，窗口右移。

```text
收到 ACK2（表示 2 及之前的都收到了）

序号：  0  1  2  3  4  5  6  7  ...
        └────┬────┘
          已确认
                 ┌───────────────┐
              │ 3  4  5  6  7 │ ...
                 └───────────────┘
                 窗口右移了 2 格
```

移多少格，由确认覆盖了多少帧决定。

这就是"滑动"两个字的来历。

窗口怎么滑，有三条规则。

```text
发送窗口左边界：收到确认，前移到"被确认的最后帧 + 1"
发送窗口右边界：左边界 + W
接收窗口：      收到帧（或在 GBN 里只有按序到达）才前移
```

左右边界一起走，宽度不变。

所以窗口大小是一个"管道粗细"，不是"一共能发多少帧"。

还有一个绕不开的细节：序号会回绕。

```text
n = 3 时，序号是 0..7，第 9 帧的序号又是 0
```

所以严格说，序号是"模 2^n 的循环编号"。

接收方判断"新帧还是旧帧"，靠的不是序号本身，而是"序号在不在我的接收窗口里"。

这句话是理解第 7 节和第 9 节两处窗口上限的全部钥匙。

再补一句缓存的角色。

```text
发送缓存：窗口内的帧必须留着，重传时要原件
接收缓存：SR 里乱序到达的帧先存着，等缺口补上
```

停等协议的发送缓存只有 1 帧，所以实现最简单——一个变量就够。

窗口越大，缓存越大，内存开销越大。

**窗口的代价有两笔：一笔是序号空间，一笔是内存。**

窗口大小 W 有两个含义，别混。

```text
发送窗口 W：最多允许多少个"已发未确认"的帧
接收窗口 Wr：最多允许接收多少个"乱序到达"的帧
```

停等协议：W = 1，Wr = 1。

GBN：W 可以很大，Wr = 1。

SR：W 和 Wr 都大于 1。

## 5. 窗口要多大，才能填满链路

回到那个 71% 被浪费的问题。

一帧从发出到被确认，需要 Td + RTT。

这段时间里，链路上"能装下"多少帧？

```text
W ≥ (Td + RTT) / Td = 1 + RTT / Td
```

这个式子的意思是：**第一个 ACK 回来之前，你得有足够的帧在路上，才不会让链路空转。**

代入前面的数：

```text
Td = 8 ms, RTT = 20 ms

W ≥ (8 + 20) / 8 = 3.5
```

所以窗口至少 4。

换个角度理解这个数：它其实就是"时延带宽积除以帧长"。

```text
时延带宽积 = RTT × C = 20 ms × 1 Mbps = 20000 bit
换算成帧数 = 20000 / 8000 = 2.5 帧
```

链路上"在途"的容量是 2.5 帧。

你要让链路不空，就得让至少 2.5 帧同时在路上——取整就是 3 帧在途，加上正在发的那一帧，窗口 4。

```text
W = 1 + 时延带宽积 / 帧长
```

这个式子和前面那个是同一个东西，只是换了个说法。

第 00 篇算过时延带宽积，这里它第一次派上实际用场。

```text
W = 4 时：4 × 8 = 32 ms 的发送时间 > 28 ms 的周期
        链路不会空，U = 100%
```

通用的利用率公式：

```text
U = min(1, W · Td / (Td + RTT + Ta))
```

那个 min 很关键。

窗口再大，U 也超不过 1。

这就是"窗口不是越大越好"的第一层含义：

**超过填满链路所需的量，再多也是浪费内存。**

第二层含义在 GBN 和 SR 的窗口上限里，那个更狠。

## 6. GBN：累积确认与回退

后退 N 帧（Go-Back-N）是最容易实现的滑动窗口协议。

三条规则。

```text
① 接收窗口 = 1：接收方只按序接收，乱序到达的一律丢弃
② 累积确认：ACK n 表示"n 及之前的全部收到，我在等 n+1"
③ 超时重传：从出错的那一帧开始，全部重发
```

第二条和第三条是配套的。

因为接收方只按序收，所以它一旦发现"3 号没来，4 号来了"，就只能把 4 号丢掉。

丢掉之后，发送方重传时也只能从 3 号开始，把 3、4、5、6 全发一遍。

**这就是"后退 N 帧"这个名字：退回到出错的那一帧，重来。**

画个时序就清楚了。

```text
发送方                                接收方
   │                                    │
   │  帧0 ──────────────────────────►   │ 收 0，交付
   │  ◄────────────────────────── ACK1  │
   │  帧1 ────────X（丢失）             │
   │  帧2 ──────────────────────────►   │ 乱序，丢弃
   │  ◄────────────────────────── ACK1  │
   │  帧3 ──────────────────────────►   │ 乱序，丢弃
   │  ◄────────────────────────── ACK1  │
   │                                    │
   │  （帧1 超时）                       │
   │  帧1 ──────────────────────────►   │ 收 1，交付
   │  帧2 ──────────────────────────►   │ 收 2，交付
   │  帧3 ──────────────────────────►   │ 收 3，交付
   │  ◄────────────────────────── ACK4  │
   │                                    │
```

注意接收方那三个 ACK1。

它们不是"确认帧 1"，而是"我还在等 1"。

这种重复的 ACK 叫**重复确认（duplicate ACK）**。

TCP 的快重传就是靠它触发的（第 19 篇），但那是传输层的事。

GBN 的发送方看到重复 ACK 什么都不做，只等超时。

**GBN 的代价很直白：一帧出错，后面已经正确到达的那些帧也要重传。**

丢一帧，重传 W 帧。

窗口越大，浪费越大。

所以 GBN 适合"误码率低、窗口小"的场合。

它的好处是实现简单：接收方只要一个变量（期待的下一个序号），发送方只要一个计时器（最早未确认的那一帧）。

还有一个省帧的小技巧，叫捎带确认（piggybacking）。

如果链路是双向的，A 给 B 发数据的同时 B 也要给 A 发数据，那 B 就不用单独发一个 ACK。

```text
A → B：数据帧（seq=2），顺带 ACK 掉 B 之前发的帧
B → A：数据帧（seq=5，ack=3）
```

确认搭在数据帧的首部里，一个帧干两件事。

代价是延迟：如果 B 手上暂时没有数据要发，它就得等——等到有数据，或者等到一个"延迟确认"的计时器超时。

这个技巧在 TCP 里也用，叫延迟确认，通常最多等 200 ms。

**链路层和传输层在这里又一次撞了思路，这不是巧合。**

因为"双向链路"这个前提，在两层都成立。

## 7. GBN 的窗口为什么是 2^n − 1

这是这一篇最需要想清楚的地方。

先给结论。

```text
GBN：发送窗口 W ≤ 2^n - 1
```

n = 3 时，W ≤ 7。

为什么不等于 8？

用反证法走一遍。

假设 n = 3，W = 8。

发送方一口气发出 0 到 7。

接收方全部正确收到，交付给上层，回 ACK0 到 ACK7。

**八个 ACK 全部丢失。**

接收方的接收窗口向前滑到 0（期待下一帧是 0）。

发送方超时，重发帧 0。

接收方收到帧 0，一看：这正是我在等的序号，收下，交付。

**上层收到了一份重复的数据。**

问题出在哪？

出在"新旧帧撞号"上。

```text
发送方：帧 0 是"旧帧的重传"
接收方：帧 0 是"新的一轮的第一个帧"
两边对同一个编号的理解不一样。
```

窗口 7 就没这个问题。

```text
发 0 到 6，全部收到，ACK 全丢。
接收方期待 7。
发送方重发 0。
接收方一看：我在等 7，你给 0？这不是我要的，丢弃，回 ACK7（还在等 7）。
发送方收到 ACK7，知道 0 到 6 都到了，继续发 7。
```

序号 7 是"安全"的那一个——它永远处在"接收方还在等"的位置，不会被误认为新帧。

所以：

```text
2^n 个序号里，必须留一个当"分界",
能用的只有 2^n - 1 个。
```

> **反直觉的点在这里。**
>
> 窗口不是越大越好——序号位数固定时，窗口一旦超过一半，新帧和重传的旧帧就会撞号。
>
> 撞号之后，接收方无法区分"这是新数据"还是"这是重传"，重复就发生了。

而"重复"比"丢失"更难查，因为它不会报错，只会让上层收到两份一样的东西。

## 8. SR：缓存乱序，只重传出错帧

GBN 的浪费太明显。

有没有办法只重传那一帧？

有，选择重传（Selective Repeat）。

三条规则，正好和 GBN 对着。

```text
① 接收窗口 > 1：乱序到达的帧先缓存起来，等缺口补上再一起交付
② 逐帧确认：每个帧单独回一个 ACK，不用累积
③ 只重传出错的那一帧：超时计时器每帧一个
```

时序对比一下就很清楚。

```text
GBN（丢帧 1）                      SR（丢帧 1）
  发 0,1,2,3                        发 0,1,2,3
  1 丢失                            1 丢失
  收 2,3 → 丢弃，回 ACK1            收 2,3 → 缓存，回 ACK2、ACK3
  1 超时 → 重传 1,2,3               1 超时 → 只重传 1
  共发 7 帧                          共发 5 帧
```

丢一帧，GBN 多发 3 帧，SR 多发 1 帧。

**SR 省带宽，代价是复杂。**

发送方要为每个未确认帧维护一个计时器。

接收方要有缓存，还要能处理"缺口补上之后一次性交付"。

排序和去重逻辑也比 GBN 复杂。

还有一个新问题：接收窗口不能太大，否则也会撞号。

## 9. SR 的窗口为什么是 2^(n−1)

先给结论。

```text
SR：发送窗口 + 接收窗口 ≤ 2^n
通常取两者相等 → W ≤ 2^(n-1)
```

n = 3 时，W ≤ 4。

为什么比 GBN 还小一半？

因为 SR 的接收窗口大于 1，占用了序号空间。

用 n = 3、W = 5 反证一遍。

```text
序号空间：0..7，共 8 个

发送窗口 5：发送方可以发 0,1,2,3,4
接收窗口 5：接收方可以收 0,1,2,3,4
```

发 0 到 4，全部到达，接收方全部收下并交付。

接收窗口前移到 5,6,7,0,1。

现在帧 0 的 ACK 丢了（其他 ACK 都到了）。

发送方超时，重传帧 0。

接收方一看：0 在我的接收窗口里（因为窗口已经绕回来了），收下，交付。

**上层又收到一份重复的 0。**

问题还是撞号，但这次是因为接收窗口也参与了滑动，绕一圈之后把旧序号重新纳入。

W = 4 就没这个问题。

```text
发送窗口 4：0,1,2,3
接收窗口 4：0,1,2,3

收全 0..3，接收窗口前移到 4,5,6,7。
帧 0 的 ACK 丢了，发送方重传 0。
接收方一看：我的窗口是 4..7，0 不在里面，丢弃。
```

**接收窗口和发送窗口加起来不能超过序号空间，这是 SR 的硬约束。**

```text
W + Wr ≤ 2^n
W = Wr → W ≤ 2^(n-1)
```

两个窗口大小的对比，是这一篇最容易被考倒的地方。

```text
GBN：W ≤ 2^n - 1，Wr = 1
SR ：W ≤ 2^(n-1)，Wr = W
```

一个反直觉的推论：

**SR 比 GBN 更"高级"，但它的窗口反而更小。**

高级不等于窗口大。

窗口大小是被"序号空间够不够区分新旧帧"这条硬约束卡死的，和协议聪不聪明无关。

## 10. 一次含丢帧的完整时序

把两种协议放在同一张图上，看清楚它们的分歧点。

场景：一帧长 1000 字节，Td = 8 ms，RTT = 20 ms，窗口 4，帧 1 丢失。

超时时间这里取 40 ms（略大于"发完 + 往返"的 28 ms；取太短会伪重传，取太长会白等）。

```text
时间(ms)  发送方 GBN              接收方 GBN
   0      发 0  ──────────────►   收 0，交付，回 ACK1
   8      发 1  ──────X
  16      发 2  ──────────────►   非 1，丢弃，回 ACK1
  24      发 3  ──────────────►   非 1，丢弃，回 ACK1
  32      （窗口满，停）
  40      （帧 1 超时）
  40      发 1  ──────────────►   收 1，交付，回 ACK2
  48      发 2  ──────────────►   收 2，交付，回 ACK3
  56      发 3  ──────────────►   收 3，交付，回 ACK4

          总计发送 7 帧，白发了 3 帧
```

```text
时间(ms)  发送方 SR               接收方 SR
   0      发 0  ──────────────►   收 0，交付，回 ACK1
   8      发 1  ──────X
  16      发 2  ──────────────►   收 2，缓存，回 ACK3
  24      发 3  ──────────────►   收 3，缓存，回 ACK4
  32      （窗口满，停）
  40      （帧 1 超时）
  40      发 1  ──────────────►   收 1，交付 1,2,3 一起，回 ACK2
  48      发 4  ──────────────►   收 4，交付，回 ACK5

          总计发送 5 帧，白发了 1 帧
```

两条时间线，同一时刻的差别是：

```text
32 ms 时，GBN 的接收方手里什么都没有；
        SR 的接收方手里握着 2 和 3，就等 1。
```

这个"缓存"就是 SR 的全部价值，也是它全部复杂度的来源。

注意 SR 的 ACK2 在 40 ms 才回。

因为接收方是"缺口补上才交付"，交付动作发生在 1 到达之后。

但确认可以更早：2 和 3 一到就回 ACK3、ACK4，发送方据此知道 2、3 已到手，不必重传。

**确认可以提前，交付必须按序。** 这两件事在 SR 里是分开的。

## 11. 三种协议摆在一起

| 协议 | 发送窗口 | 接收窗口 | 确认方式 | 重传范围 | 计时器 | 序号位数下界 |
|---|---|---|---|---|---|---|
| 停等 | 1 | 1 | 逐帧 | 当前帧 | 1 个 | n ≥ 1 |
| GBN | ≤ 2^n − 1 | 1 | 累积 | 出错帧及其后所有已发帧 | 1 个（最早未确认） | 2^n ≥ W+1 |
| SR | ≤ 2^(n−1) | 与发送窗口相同 | 逐帧 | 只重传出错帧 | 每帧一个 | 2^n ≥ 2W |

利用率都可以用同一个式子估：

```text
U = min(1, W · Td / (Td + RTT + Ta))
```

三种协议的 W 不同，U 也就不同。

同一个 n = 3 的序号空间：

```text
停等：W = 1 → 8 / 28.16 = 28.4%
GBN ：W = 7 → min(1, 7×8/28.16) = 100%
SR  ：W = 4 → min(1, 4×8/28.16) = 100%
```

这一组数说明一件事：**在低误码率下，GBN 和 SR 的利用率都能打满，差别只在出错时的浪费。**

误码率高的时候，SR 的优势才显现出来。

## 12. 容易混淆的点

**第一，发送窗口和接收窗口不是一回事。**

发送窗口管"能发多少"，接收窗口管"能收多少"。

GBN 的接收窗口恒为 1，这是它"乱序即丢"的根源。

**第二，累积确认的 ACK n 到底确认了什么。**

不是"确认第 n 帧"，而是"n 及之前的全部收到，我在等 n+1"。

这个理解错了，判断重传范围就会全错。

**第三，序号位数和窗口大小的关系方向。**

是"窗口决定需要几位序号"，不是"序号位数决定窗口"。

答题时先写约束（2^n ≥ W+1 或 2^n ≥ 2W），再解出 n。

**第四，计时器的个数。**

```text
停等：1 个
GBN ：1 个（只为最早未确认的帧计时）
SR  ：每帧一个
```

GBN 只用一个计时器，是因为它的重传本来就是批量的——最早那帧超时，后面全要重发。

**第五，流量控制和拥塞控制。**

流量控制是"接收方说别发了"，拥塞控制是"网络说别发了"。

前者看接收缓冲区，后者看丢包和时延。

链路层只有前者，传输层两者都有。

**第六，"后退 N 帧"退的是什么。**

退的是"发送窗口的左边界"，不是"退回到第 0 帧"。

出错帧是 1，就退到 1，不是退到 0。

**第七，超时时间不是"越大越安全"。**

太大，真丢帧时要白等一整个周期，利用率掉下去。

太小，ACK 还在路上就重传，伪重传会让接收方收到重复帧，链路更乱。

它本质上是一个"宁可错杀"还是"宁可放过"的取舍，不是一个能算到最优的参数。

考试里如果给了"超时时间"，就按给的算；没给，就认为重传发生在"该收到确认之后"。

## 13. 408 怎么考

三种题型，都有固定套路。

```text
一、算窗口上限：给序号位数 n，问 GBN/SR 的最大窗口
二、算利用率：给帧长、速率、RTT、窗口，套公式
三、判断重传：给丢帧场景，问接收方回什么 ACK、发送方重传哪些帧
```

下面是自拟题，三问串起来。

**题目。**

一条链路：速率 1 Mbps，单向传播时延 10 ms，帧长 1000 字节，确认帧长 20 字节，序号用 3 位。

（1）用停等协议，信道利用率是多少？

（2）若要把利用率做到 100%，发送窗口至少多大？

（3）用 GBN，窗口取到上限 7，当前发送窗口覆盖 0 到 6 号，且 0 到 5 号已经全部发出。若帧 2 丢失，帧 3、4、5 正确到达接收方。接收方会回什么 ACK？帧 2 超时后发送方重传哪些帧？

**解答（1）。**

RTT = 2 × 10 ms = 20 ms。

```text
Td = 8000 / 10^6 = 8 ms
Ta = 160  / 10^6 = 0.16 ms

U = 8 / (8 + 20 + 0.16) = 8 / 28.16 = 28.4%
```

**解答（2）。**

```text
W ≥ (Td + RTT) / Td = 28 / 8 = 3.5
```

窗口取整，W ≥ 4。

用 4 验算一下：

```text
U = min(1, 4 × 8 / 28.16) = min(1, 1.136) = 100%
```

**解答（3）。**

接收方只按序收。

```text
帧 2 丢失 → 接收方还在等 2
帧 3 到达 → 乱序，丢弃，回 ACK2（我还在等 2）
帧 4 到达 → 乱序，丢弃，回 ACK2
帧 5 到达 → 乱序，丢弃，回 ACK2
```

所以接收方连回三个 **ACK2**。

帧 2 超时后，发送方重传**帧 2、3、4、5**。

为什么连 3、4、5 也重传？

因为接收方把它们丢了，它们从未被确认。

这一问的关键在于：**ACK2 的含义是"我在等 2"，不是"2 号到了"。**

答"重传 2"或"重传 2、3"都错。

**再补一道窗口题。**

序号 3 位，SR 协议的发送窗口最大是多少？若发送窗口取 4，接收窗口最多取多少？

```text
SR：W + Wr ≤ 2^n = 8
W = 4 → Wr ≤ 4
```

答案：发送窗口最大 4；W 取 4 时 Wr 最多 4。

如果题目问"序号 3 位的 GBN 窗口上限"，答案是 7，不是 8。

**这两个数（4 和 7）必须能不看书写出来。**

## 14. 真实网络里长什么样

链路层的这些协议，在今天的以太网里已经看不到了。

以太网不做确认，不做重传，丢帧就丢帧。

但同一套机制在别处活着，而且活得很好。

**802.11 的 Block Ack 就是 SR 的工程实现。**

无线帧的确认开销太大——每帧一个 ACK，空口就废了。

所以 802.11n 之后引入了块确认：发一组帧，接收方用一个 Block Ack 告诉发送方"这组里哪些收到了"。

那个位图就是 SR 的接收窗口状态。

```text
Block Ack 的位图（简化示意）：
序号：  1  2  3  4  5  6  7  8
状态：  ✓  ✗  ✓  ✓  ✗  ✓  ✗  ✓
        收  丢  收  收  丢  收  丢  收
```

发送方只看位图，只重传丢的那几个。

**这就是 SR，只是换了名字。**

**TCP 的窗口是同一套东西，只是换了一层。**

```console
$ ss -tin state established
State  Recv-Q  Send-Q  Local Address:Port  Peer Address:Port
ESTAB  0       0       10.0.0.2:22         10.0.0.9:51234
     cubic wscale:7,7 rto:204 rtt:0.85/0.4
     cwnd:10 ssthresh:7 bytes_acked:1234
```

`cwnd` 是拥塞窗口，`rto` 是重传超时，`rtt` 是往返时延。

TCP 的发送窗口 = min(cwnd, rwnd)，和这一篇的 W 是同一个位置。

区别只在：链路层的窗口防的是"接收方缓冲区溢出"，TCP 的窗口还要防"网络拥塞"。

TCP 处理丢包的两种方式，也正好对应这一篇的两种思路。

```text
超时重传：等 RTO 到了还没确认 → 重传最早的未确认段
         （GBN 的思路，但 TCP 只用"回退到最早那个"，不是整窗重发）

快重传：  收到 3 个重复 ACK → 立刻重传，不等超时
         （比 SR 更狠：连超时都不等）
```

三个重复 ACK 这个技巧，其实是把 GBN 里那串"我还在等 1"的重复确认，当成了"帧丢了"的明确信号。

**GBN 里那三个 ACK1 是噪音，TCP 里它是信号。**

同一个现象，两种用法，区别只在"谁有权决定重传"。

**网卡的环形缓冲区也是这个模型。**

```console
$ ethtool -g eth0
Ring parameters for eth0:
Pre-set maximums:
RX:  4096
TX:  4096
Current hardware settings:
RX:  256
TX:  256
```

256 个描述符就是 256 个"窗口"。

网卡填满了就丢，丢了多少记在 `tx_dropped` 里。

这一段是简化示意。

真实的网卡队列、NAPI、中断合并比这复杂得多，但"窗口 + 溢出丢弃"的结构是一样的。

**所以别把这一篇当成一个过时的协议族。**

它是所有"批量发送 + 按需重传"系统的原型。

## 15. 小结

三种协议，一条主线：

```text
停等 → 窗口 1，等确认，慢
GBN  → 窗口大，累积确认，出错全重传
SR   → 窗口一半，逐帧确认，只重传出错帧
```

两个必须背下来的约束：

```text
GBN：W ≤ 2^n - 1
SR ：W ≤ 2^(n-1)
```

一个必须记住的公式：

```text
U = min(1, W · Td / (Td + RTT + Ta))
```

一个必须记住的反直觉点：

```text
窗口不是越大越好。
序号空间是有限的，窗口一旦越过一半，
新帧和重传的旧帧就会撞号，
接收方分不清"新数据"和"重发的旧数据"。
```

还有个更隐蔽的反直觉现象，值得单独留一句：

```text
在停等协议下，链路速率越高，利用率越低。
因为瓶颈是 RTT，不是发送速率。
```

下一篇离开"一条链路"，进入"一根线被多台设备共享"的世界。

```text
计算机网络系统讲解 08：介质访问控制：信道划分与随机访问
```

那一篇会回答：

```text
ALOHA 的效率为什么卡在 18.4%？
1-坚持、非坚持、p-坚持，到底差在哪？
CDMA 的码片为什么要正交？
```

从下一篇开始，"谁先发"这件事，会变成一个可以算的概率。
