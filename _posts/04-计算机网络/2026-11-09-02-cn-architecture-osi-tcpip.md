> **读这篇之前，你只需要知道**：协议是两台机器事先约定好的"说话规矩"；分组是一段数据被切小之后、带着"从哪来到哪去"的那一小块。
> **这篇讲什么**：为什么要把网络通信切成几层、每层管什么、层与层之间靠什么交接，以及 OSI 的七层和 TCP/IP 的四层是怎么对上的。
> **一个类比**：寄一份跨国快递。你只管写清"寄给谁、寄什么"（应用层），快递公司负责"到哪个城市"（网络层），货车司机只管"这一段路怎么开"（链路层），而每一层都在包裹外面再加一张自己的单子。


先看一段真实的抓包输出。

```text
$ tcpdump -i eth0 -e -nn -c 1
12:04:31.882910 3c:52:82:1a:4b:7e > 00:1a:2b:3c:4d:5e,
ethertype IPv4 (0x0800), length 1514:
  192.168.1.20.51234 > 93.184.216.34.80:
  Flags [P.], seq 1:1461, ack 1, win 501,
  length 1460: HTTP: GET /index.html HTTP/1.1
```

一行里挤着四层的信息。

```text
3c:52:82:1a:4b:7e > 00:1a:2b:3c:4d:5e   MAC 地址，链路层
ethertype IPv4 (0x0800)                  类型字段，告诉上层"里面是 IP"
192.168.1.20 > 93.184.216.34             IP 地址，网络层
51234 > 80                               端口，传输层
GET /index.html HTTP/1.1                 应用层
```

同一串字节，四层各自读出自己关心的那几位。

这就是"体系结构"存在的理由。

先解释这串输出里出现的三个词。
MAC 地址：网卡出厂时就烧死的 48 位物理地址，同一段线上的设备靠它互相认人。
端口：一台机器上不同程序的门牌号，80 通常给网页服务，51234 是浏览器临时占用的。
以太网类型字段：链路层里的一个小标记，作用是告诉接收方"信封里装的是 IP，还是别的东西"。

这一篇要回答三个问题：

```text
为什么非要分层，不分行不行？
分了层之后，层与层之间靠什么约定的东西打交道？
这么多协议，各自应该塞进哪一层？
```

## 1. 这个问题解决什么

假设不分层。

一台机器要和另一台机器说话，从"应用要发什么"到"电信号怎么变"，全部写在一个程序里。

会出什么问题？

```text
换一块网卡，整个程序要重写
把以太网换成 Wi-Fi，上层全部改
从 IPv4 迁到 IPv6，连 HTTP 服务器都要动
```

每换一个底层技术，整套软件都要陪葬。

先说什么叫分层。
分层（layering）：把一次通信要干的活切成几段，每段只回答一个问题，相邻两段之间用固定的接口交接。
切完之后，某一段内部怎么改，只要接口不变，别的段就不用动。

分层的本质是**把变化隔离开**。

```text
物理层换光纤 → 上层不知道
链路层换 Wi-Fi → 网络层不知道
网络层换 IPv6 → 传输层不知道
```

代价是每一层都要加自己的首部，都有开销。

但换来的是：1969 年写的应用层协议，2026 年还能跑在 400G 光模块上。

**这一笔交易极其划算。**

所以分层不是学术洁癖，是工程上唯一能活下来的做法。

## 2. 最小模型：分层、封装、协议

先问为什么这三个词要放在一起学。
因为分层、封装、协议分别回答三件事："切成几段"、"每段外面加什么"、"同一段的两头怎么对话"。
缺一个，另外两个都说不完整。

三个词，三张图。

### 2.1 分层

```text
        主机 A                        主机 B
   ┌──────────────┐              ┌──────────────┐
   │   应用层      │              │   应用层      │
   ├──────────────┤              ├──────────────┤
   │   传输层      │              │   传输层      │
   ├──────────────┤              ├──────────────┤
   │   网络层      │              │   网络层      │
   ├──────────────┤              ├──────────────┤
   │  数据链路层   │              │  数据链路层   │
   ├──────────────┤              ├──────────────┤
   │   物理层      │              │   物理层      │
   └──────────────┘              └──────────────┘
        │                              │
        └──────── 传输介质 ────────────┘
```

实线是真实的数据通路，方向是上下。

但逻辑上，第 N 层的两个实体是在"对话"。

### 2.2 封装

封装（encapsulation）：每一层把自己这层的控制信息贴在数据前面（链路层还在末尾贴一个），像一层层套信封，里面的信纸一个字都不用改。

```text
应用层：            [ 数据 ]
                        ↓ + 应用层首部（有时没有）
传输层：        [TH][ 数据 ]
                        ↓ + 传输层首部
网络层：    [NH][TH][ 数据 ]
                        ↓ + 网络层首部
链路层：[FH][NH][TH][ 数据 ][FT]
                        ↓
物理层：  1010110100101110……
```

每层只在自己的位置上加东西，不看里面的内容。

链路层加了帧头帧尾，因为要在链路上标出"从哪开始、到哪结束"。

**帧尾是链路层独有的**，因为只有它需要在比特流里找边界。

### 2.3 协议

**协议（protocol）**：为进行网络中的数据交换而建立的规则、标准或约定。

三要素，缺一不可：

```text
语法：数据与控制信息的结构或格式（长什么样）
语义：发出什么控制信息，完成什么动作，做出什么响应（什么意思）
同步：事件实现顺序的详细说明（什么时候做）
```

举个具体的：

```text
语法：TCP 首部第一个字段是 16 位源端口
语义：SYN=1 表示请求建立连接
同步：先 SYN，再 SYN+ACK，再 ACK
```

三个都对上，才叫"实现了同一个协议"。

## 3. 一次完整走查：一封邮件穿过四层

为什么跟一封邮件走一遍？
因为"分层"和"封装"这两个词，只看定义记不住；跟着一层层加首部走一次，每一层加了几个字节、加来干什么，就再也忘不掉。

场景：你在笔记本上写一封 500 字节的邮件，点发送。

```text
应用层：SMTP 生成 "MAIL FROM / RCPT TO / DATA / 正文"
        交给传输层，500 字节
```

```text
传输层：加 TCP 首部 20 字节
        报文段 = 520 字节
        首部里写明：源端口 51234，目的端口 25
        还带上序号，因为要保证可靠
```

```text
网络层：加 IP 首部 20 字节
        数据报 = 540 字节
        首部里写明：源 IP 192.168.1.20，目的 IP 203.0.113.9
        还带 TTL=64，用来防止环路
```

```text
链路层：加以太网首部 14 字节 + 帧尾 4 字节
        帧 = 558 字节
        首部里写明：源 MAC、目的 MAC（下一跳路由器的）
        帧尾是 FCS，用来检错
```

```text
物理层：把 558 字节变成 4464 个比特
        按编码规则变成电信号/光信号发出去
```

这段走查里有三个字段名，后面还会反复出现，先解释掉。
TTL（time to live，生存时间）：IP 首部里的一个计数器，每经过一台路由器减 1，减到 0 就丢弃，用来防止分组在环路里永远打转。
FCS（frame check sequence，帧检验序列）：帧尾 4 个字节的校验值，接收方重算一遍，对不上就把整帧丢掉。
MTU（maximum transmission unit，最大传输单元）：链路层一次最多能接多大的 IP 数据报，以太网是 1500 字节。

注意两个细节。

第一，**每一层的地址不一样**。

```text
应用层：知道对方是 user@example.com
传输层：知道对方是 25 端口
网络层：知道对方是 203.0.113.9
链路层：知道下一跳的 MAC 是 xx:xx:xx:xx:xx:xx
```

从"人认识的地址"一路翻译到"网卡认识的地址"。

第二，**链路层的地址是"下一跳"的，不是"最终目的"的**。

```text
IP 首部的目的地址：最终目的（全程不变）
帧首部的目的 MAC：下一跳（每跳都变）
```

这个区别在第 14 篇讲 ARP 时会展开，现在先记住。

**封装是逐层加头，转发是逐跳换头。**

## 4. 拆开看：协议、服务、接口

先问为什么非要把这三个词分开。
因为它们回答的是三个不同方向的问题："谁和谁说话"（协议）、"谁帮谁干活"（服务）、"在哪儿交接"（接口）。
混着说，就会写出"TCP 为 HTTP 提供服务"和"TCP 和 HTTP 通信"这种自相矛盾的句子。

这三个词经常被混着说，408 又特别爱考它们的区别。

先给定义。

```text
协议（protocol）：对等层之间的通信规则，水平的
服务（service）：下层向上层提供的功能，垂直的
接口（SAP）：上下层之间的交接点，也叫服务访问点
```

一张图说清：

```text
      ┌─────────┐  ← 第 N+1 层
      │  实体    │
      └────┬────┘
           │  ← SAP / 接口（同一个节点内，垂直）
      ┌────┴────┐
      │ 第 N 层  │◄──── 协议 ────►  对端第 N 层（水平）
      └─────────┘
```

### 4.1 服务是垂直的

服务只发生在**同一台机器的相邻两层**之间。

```text
第 N 层向第 N+1 层提供服务
第 N+1 层是"用户"，第 N 层是"提供者"
```

服务是"我下面帮你干了什么"，不是"我跟对面怎么聊"。

### 4.2 协议是水平的

协议只发生在**两台机器的同一层**之间。

```text
A 的传输层 ◄──── TCP 协议 ────► B 的传输层
```

协议是"我们俩怎么说话"，不关上下层的事。

### 4.3 三个关键结论

这三条是选择题的直接考点。

```text
一、第 N 层协议对第 N+1 层是透明的
   上层不需要知道下层用什么协议、怎么实现。
   TCP 不知道下面是 IPv4 还是 IPv6。

二、上层通过 SAP 使用下层服务
   一个 SAP 就是一个地址，下层靠它区分不同的上层用户。
   传输层的 SAP 就是端口号。

三、服务原语有四种
   请求（request）、指示（indication）、响应（response）、证实（confirm）
```

服务原语这四项是按时间顺序发生的：上层发出"请求"，下层收到"指示"，下层回"响应"，上层收到"证实"。
它是同一台机器内部两个相邻层的交接动作，不是网上跑的报文。

说到 SAP，还有一个躲不开的问题：如果没有它，会怎样？
一台机器上同时开着浏览器、邮件客户端和游戏，回来的数据都从同一块网卡进来。
没有端口号区分，内核只能把每一份数据都复制给三个程序，让它们各自去猜哪份是自己的。
有了端口号，内核看一眼目的端口就分发：80 给网页服务，25 给邮件服务，对不上的直接拒掉。
这就是接口在工程上的作用：不是礼貌，是分工。

**最容易错的一条：**

**协议是"水平"的，服务是"垂直"的，接口在"垂直方向的边界"上。**

把它们画成三条线，考试时按"水平/垂直"判断，几乎不会错。

### 4.4 服务和协议不是一回事

下面这句话要读两遍：

```text
第 N 层提供的服务，由第 N 层的协议和它下面各层的服务共同实现。
```

但**服务**本身只描述"能看到什么"，不描述"怎么做到"。

举个例子：

```text
传输层向应用层提供"可靠、有序的字节流"这个服务。
怎么实现？用 TCP。
TCP 怎么保证可靠？用序号、确认、重传。
这全是协议内部的事，应用层看不见。
```

所以你可以把 TCP 换成 QUIC，只要还给应用层"可靠有序字节流"这个服务，应用层就不用改。

**这就是分层的价值：服务接口不变，实现随便换。**

## 5. 拆开看：OSI 七层的职责与数据单位

先说清这个模型是干什么用的。
通信这件事，从"用户想发什么"到"线上电压怎么变"，中间要做的判断太多，一次想不完。
所以先把它切成七段，每段只回答一个问题；切完之后，每一段都能单独设计、单独排错、单独换人做。

OSI（open systems interconnection，开放系统互连）参考模型：国际标准化组织给出的这张"切成七块"的图纸，只规定每块该干什么，不规定必须用什么协议。

OSI 参考模型把通信功能切成七块。

从下往上数。

### 5.1 物理层（Physical Layer）

```text
职责：在传输介质上传送原始比特流
单位：比特（bit）
关心：电压高低、光的波长、接口引脚、传输速率、比特同步
```

它不管比特是什么意思，只管把 0 和 1 送过去。

典型设备：中继器、集线器。

### 5.2 数据链路层（Data Link Layer）

```text
职责：把比特流组成帧，在一段链路上可靠传输
单位：帧（frame）
关心：成帧、差错控制、流量控制、介质访问控制
```

"一段链路"是关键词。

它只保证"我这一跳送到了"，不保证"全程送到了"。

典型设备：网桥、交换机。

### 5.3 网络层（Network Layer）

```text
职责：把分组从源主机送到目的主机，可能跨很多网络
单位：分组（packet），也叫数据报（datagram）
关心：路由选择、分组转发、拥塞控制、异构网络互联
```

"主机到主机"是关键词。

它要处理"下一跳走哪、路由表怎么来、网络之间怎么连"。

典型设备：路由器。

### 5.4 传输层（Transport Layer）

```text
职责：为两台主机的进程提供端到端的通信
单位：报文段（segment，TCP）或用户数据报（UDP）
关心：复用与分用、可靠传输、流量控制、拥塞控制
```

"进程到进程"是关键词。

它要处理"给哪个程序、要不要重传、发多快"。

### 5.5 会话层（Session Layer）

```text
职责：建立、管理、终止会话
单位：报文（message）
关心：会话同步、对话控制、断点续传的检查点
```

听起来很有用，实际上**没有独立协议**。

下一节专门说这件事。

### 5.6 表示层（Presentation Layer）

```text
职责：数据的表示、加密、压缩、格式转换
单位：报文（message）
关心：字符编码（ASCII/UTF-8）、序列化、加解密、压缩
```

同样没有独立协议。

### 5.7 应用层（Application Layer）

```text
职责：为用户的应用程序提供网络服务
单位：报文（message）
关心：HTTP、DNS、SMTP、FTP 这些具体协议
```

它是唯一"人能用"的一层。

### 5.8 数据单位对照

```text
应用层 ──── 报文 message
表示层 ──── 报文 message
会话层 ──── 报文 message
传输层 ──── 报文段 segment / 用户数据报
网络层 ──── 分组 packet / 数据报 datagram
链路层 ──── 帧 frame
物理层 ──── 比特 bit
```

上面三层都是"报文"，408 不区分。

顺便解释一下这些单位名为什么一层一个样。
报文（message）：应用层那一坨数据，还没有被任何一层包装过。
报文段（segment）：TCP 加上自己的首部之后的那一段。
分组（packet）：IP 加上首部之后的那一块，也叫数据报（datagram）。
帧（frame）：链路层加上首部和帧尾之后、真正要发到线上的那一串。
名字跟着层走，是因为每一层眼里"一块数据"的边界不一样；混着叫，算长度时就会多算或少算一个首部。

### 5.9 反直觉的地方

看一张 OSI 七层的协议清单，你会发现一个尴尬的事实。

```text
应用层：HTTP、DNS、SMTP、FTP、SSH、TLS……几百个
传输层：TCP、UDP、SCTP
网络层：IP、ICMP、IGMP、ARP
链路层：以太网、PPP、HDLC、802.11
物理层：一堆电气规范
会话层：？？？
表示层：？？？
```

会话层和表示层，找不到能拿出来的协议。

> **反直觉点：OSI 七层里，会话层和表示层没有真实的独立协议。**
>
> 它们描述的功能是真实存在的——字符编码转换、压缩、加密、会话恢复——但这些功能在实现中全部被应用层（或者应用层的库）吸收了。
> TLS 干的是"表示层"的活，却工作在应用层和传输层之间；gzip 是应用层的；检查点续传是 HTTP 的 Range 头。

原因在下一节讲 OSI 与 TCP/IP 的差异时会说清。

现在先接受这个结论：

```text
OSI 是"教学用的模型"，不是"实现的图纸"。
它的价值在于把问题拆开，不在于每层都真有一个协议。
```

408 出题人也知道这一点，所以它只考"哪层负责什么"，从不考"会话层用什么协议"。

## 6. 408 怎么考

这一章的题型很少，但每年都在。

```text
选择题：某个协议属于哪一层
      某台设备工作在哪一层
      服务/协议/接口的关系判断
      各层的数据单位
综合题：封装开销计算（常和第 12 篇的 IP 分片连考）
```

归层的判断口诀，比死记清单可靠：

```text
看这个协议"在跟谁说话"。
跟最终用户的程序说话 → 应用层
跟对面的进程说话 → 传输层
跟对面的主机说话 → 网络层
跟对面同一根线上的设备说话 → 链路层
只管电信号 → 物理层
```

### 例题（自拟，按 408 风格）

主机 A 要发送 1000 字节的应用层数据给主机 B，两者在同一以太网内。

```text
TCP 首部 20 字节
IP 首部 20 字节
以太网首部 14 字节，帧尾 FCS 4 字节
前导码 8 字节（物理层加）
MTU = 1500 字节
链路速率 100 Mbit/s
```

求：

```text
(1) 报文段、IP 数据报、帧的长度各是多少
(2) 是否需要分片
(3) 传输效率（应用层数据 / 帧长）
(4) 发完这一帧需要多少时间（含前导码）
(5) 若应用层要发 4000 字节，分几片，每片多长
```

### 解

```text
(1) 报文段 = 1000 + 20 = 1020 字节
    IP 数据报 = 1020 + 20 = 1040 字节
    帧 = 1040 + 14 + 4 = 1058 字节
```

```text
(2) 不分片。
    判断依据是 IP 数据报长度 1040 ≤ MTU 1500。
    注意：MTU 限制的是 IP 数据报，不是帧，也不是应用数据。
```

```text
(3) 传输效率 = 1000 / 1058 ≈ 94.52%
```

```text
(4) 含前导码的线上长度 = 8 + 1058 = 1066 字节 = 8528 bit
    时间 = 8528 / 10^8 = 8.528×10^-5 s = 85.28 μs
    不含前导码 = 1058 × 8 / 10^8 = 84.64 μs
```

```text
(5) 4000 字节应用数据：
    IP 数据报总长 = 4000 + 20(TCP) + 20(IP) = 4040 字节
    IP 载荷 = 4040 - 20 = 4020 字节
    每片最大载荷 = MTU - 20 = 1500 - 20 = 1480 字节
    4020 / 1480 = 2.716 → 向上取整 = 3 片
    分片载荷：1480 + 1480 + 1060 = 4020 ✓
    每片总长：1500 + 1500 + 1080 字节
```

验算一下第三片：

```text
1060 + 20 = 1080 字节 ≤ 1500 ✓
总字节 = 1500 + 1500 + 1080 = 4080
原始数据报 4040 + 两片各多一个 20 字节 IP 首部 = 4040 + 40 = 4080 ✓
```

对上了。

**这道题的关键只有两句：**

```text
封装是逐层加头，加一层就多一层开销。
MTU 卡的是 IP 数据报，不是应用数据。
```

### 附一道概念题

```text
下列设备中，工作在数据链路层的是：
A. 中继器   B. 集线器   C. 交换机   D. 路由器
```

答 C。

```text
中继器：物理层，只放大整形信号
集线器：物理层，多端口中继器
交换机：链路层，看 MAC 地址转发
路由器：网络层，看 IP 地址转发
```

## 7. 真实网络里长什么样

OSI 是模型，Linux 里能看到的是一层层的实际结构。

看网卡和它上面的地址：

```text
$ ip link show eth0
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
    link/ether 3c:52:82:1a:4b:7e brd ff:ff:ff:ff:ff:ff
```

这里的 `link/ether` 就是链路层的 48 位 MAC 地址。

`mtu 1500` 是链路层对网络层的承诺：一次最多给我 1500 字节。

看这一层的 IP 地址：

```text
$ ip addr show eth0
    inet 192.168.1.20/24 brd 192.168.1.255 scope global eth0
```

这是网络层的地址。

同一块网卡上，链路层地址和网络层地址各有一个，各管各的。

看传输层的连接：

```text
$ ss -tnp
State   Recv-Q  Send-Q  Local Address:Port    Peer Address:Port
ESTAB   0       0       192.168.1.20:51234    93.184.216.34:80
```

`ESTAB` 是传输层的状态。

一条连接由四元组唯一确定：源 IP、源端口、目的 IP、目的端口。

再看抓包里的分层：

```text
$ tcpdump -i eth0 -e -nn -vv -c 1
  ethertype IPv4 (0x0800), length 1514
  ...
  IP (tos 0x0, ttl 64, id 54321, offset 0, flags [DF], proto TCP (6), length 1500)
  ...
  TCP (6), length 1460
```

`ethertype 0x0800` 是链路层的"类型"字段。

它的作用就是告诉接收方：**把载荷交给网络层的哪个协议**。

这个字段就是分层的"接口"在报文里的具体体现。

同一种机制在每一层都有：

```text
链路层：ethertype（0x0800 = IPv4，0x0806 = ARP，0x86DD = IPv6）
网络层：protocol（6 = TCP，17 = UDP，1 = ICMP）
传输层：端口号（80 = HTTP，443 = HTTPS，53 = DNS）
```

**这就是"多路复用/分用"的实现方式：每层用自己的标识字段，把载荷交给正确的上层。**

还有一件事值得注意。

抓包时你永远看不到 OSI 的"会话层"和"表示层"。

没有 `ethertype` 指向它们，没有 `protocol` 字段标识它们。

因为它们在报文里根本不存在。

这就是第 5.9 节那个结论的实证：**模型有七层，报文里只有五层。**

## 8. TCP/IP 四层与五层教学模型

OSI 是 ISO 定的，TCP/IP 是实际跑起来的。

TCP/IP 分四层：

```text
┌────────────────────────────┐
│ 应用层                      │  HTTP DNS SMTP FTP
├────────────────────────────┤
│ 传输层                      │  TCP UDP
├────────────────────────────┤
│ 网际层（internet layer）     │  IP ICMP ARP
├────────────────────────────┤
│ 网络接口层（network access） │  以太网 PPP 802.11
└────────────────────────────┘
```

注意最下面那一层。

TCP/IP 的"网络接口层"把 OSI 的物理层和链路层合并了。

因为 TCP/IP 的初衷是"能跑在任何底层网络上"，它不想规定物理层。

教学上，为了讲清楚，又拆成五层：

```text
应用层
传输层
网络层
数据链路层
物理层
```

**408 用的就是五层模型。**

三种模型的对应关系：

```text
OSI 七层              TCP/IP 四层        五层教学模型
─────────────────────────────────────────────────
应用层 ┐
表示层 ├──────────── 应用层 ────────── 应用层
会话层 ┘
传输层 ───────────── 传输层 ────────── 传输层
网络层 ───────────── 网际层 ────────── 网络层
链路层 ┐
       ├──────────── 网络接口层 ─────── 数据链路层
物理层 ┘                              物理层
```

这张表要能默画。

408 的题目里说"网络层"就是五层模型的第三层，说"网际层"就是 TCP/IP 的第二层，指的是同一个东西。

### 8.1 沙漏模型：为什么 IP 在最细处

把 TCP/IP 的画法转 90 度，会看到另一件事。

```text
        HTTP  DNS  SMTP  FTP  SSH  QUIC
         ╲    ╲    │    │    │    ╱
          ╲    ╲   │    │   ╱    ╱
           ╲    ╲  │    │  ╱    ╱
            ╲    ╲ │    │ ╱    ╱
             ╲    ╲│    │╱    ╱
              ╲    │ IP  │    ╱        ← 细腰
             ╱    ╱│    │╲    ╲
            ╱    ╱ │    │ ╲    ╲
           ╱    ╱  │    │  ╲    ╲
          ╱    ╱   │    │   ╲    ╲
         ╱    ╱    │    │    ╲    ╲
      以太网  PPP  802.11  光纤  5G
```

这张图的形状叫**沙漏模型（hourglass model）**。

上面的口很宽：几百个应用层协议。

中间很细：只有 IP 一个。

下面的口很宽：什么链路层、什么物理介质都能跑。

```text
上层多样，下层多样，中间统一。
```

这个设计带来一个巨大的好处：

```text
新应用不需要改网络（上面加）。
新介质不需要改应用（下面加）。
只要它能跑 IP。
```

**这就是 IP 赢了的原因，不是因为它技术最先进，而是因为它站在了最窄的那一格。**

OSI 的网络层没做到这一点，它试图把上下都规定清楚。

## 9. 每层典型协议归属

这一节是纯记忆，但有规律。

### 9.1 应用层

```text
HTTP / HTTPS   网页
DNS            域名 → IP
FTP            文件传输
SMTP / POP3 / IMAP   邮件
SSH / Telnet   远程登录
DHCP           自动分配 IP（注意：它跑在 UDP 上）
SNMP           网络管理
```

DHCP 归应用层，虽然它干的是"配地址"这种网络层的活。

判断依据是"它用 UDP 传，是应用层协议"。

### 9.2 传输层

```text
TCP    可靠、面向连接、字节流
UDP    不可靠、无连接、报文
```

只有这两个是 408 的主角。

### 9.3 网络层

```text
IP     核心协议
ICMP   差错报告与探测（ping、traceroute 用它）
ARP    IP → MAC（408 归网络层）
IGMP   组播管理
```

ARP 归哪一层有争议，408 的答案在网络层。

理由：它处理的是 IP 地址到 MAC 地址的映射，属于网络层的地址解析。

但它的报文是直接封在以太网帧里的，不经过 IP。

这一点做选择题时要注意。

### 9.4 数据链路层

```text
以太网（Ethernet）   局域网主流
PPP                  点对点，拨号上网
HDLC                 早期广域网
802.11               无线局域网
```

### 9.5 物理层

```text
双绞线、同轴电缆、光纤、无线电
RJ-45 接口、SFP 光模块
RS-232、V.35 这些电气规范
```

物理层"协议"其实是一堆电气和机械标准，不是报文格式。

### 9.6 一张速查图

```text
HTTP  DNS  SMTP  FTP        ← 应用层
        │
TCP   UDP                   ← 传输层
        │
IP  ICMP  ARP  IGMP         ← 网络层
        │
以太网  PPP  HDLC  802.11    ← 链路层
        │
双绞线 光纤 无线电            ← 物理层
```

记住"每个协议只跟同一层的协议对话"，这张图就不会串。

## 10. 端到端 vs 点到点

先问这两个词为什么容易含糊。
因为两个词都在谈"送到"，但一个说的是"一段线送到就算完"，另一个说的是"从头到尾送到才算完"。
范围不同，能保证的事就完全不同。

这组词 408 反复考，而且很多教材讲得含糊。

定义很干脆：

```text
端到端（end-to-end）：传输层，两个进程之间
点到点（point-to-point）：链路层，两个相邻节点之间
```

区别在于"一段"还是"全程"。

```text
源主机 ── R1 ── R2 ── 目的主机
   │      │      │        │
   └──────┴──────┴────────┘
      链路层：一段一段，每段独立
   └──────────────────────┘
      传输层：从头到尾，一条
```

具体差别：

```text
链路层：每一跳都重新封装，差错控制只管这一段
        收到坏帧就丢，不会去问源头重传
传输层：全程负责，中间路由器不参与
        一个报文段丢了，由源主机的 TCP 重传
```

这就是为什么 TCP 能保证端到端可靠，而以太网不能。

因为以太网根本不知道"端"在哪。

**一句话：链路层的可靠是"这一跳送到了"，传输层的可靠是"对面收到了"。**

中间隔着路由器，路由器不帮忙，也不捣乱。

### 10.1 算一笔账：为什么链路层要逐跳检错

有一种说法是"反正 TCP 会重传，链路层不用管差错"。

算一遍就知道这个说法有多贵。

设一段链路的误码率是 10^-4，帧长 1000 比特。

一个帧完全正确的概率：

```text
(1 - 10^-4)^1000 = 0.9999^1000 ≈ e^(-0.1) ≈ 0.9048
```

所以一个帧出错的概率：

```text
1 - 0.9048 = 0.0952 ≈ 9.5%
```

如果一次传输要经过 10 跳，每一跳都不做差错检测：

```text
全程一次成功的概率 = 0.9048^10 ≈ e^(-1.0) ≈ 0.368
```

也就是说，**63% 的帧要重传**。

而这 63% 里，绝大多数只在某一跳坏了一个比特，前面九跳的传输全部白费。

如果每一跳都做 CRC 校验、坏了就丢：

```text
每一跳承担 9.5% 的损失，不会把错误传到下一跳
坏帧在第一跳就被拦下，后面九跳不用白跑
```

**链路层检错的价值不在于"能恢复"，而在于"及时止损"。**

以太网确实不重传，它只丢。

但丢得早，比传到终点再丢，便宜得多。

## 11. 面向连接 vs 无连接

先问为什么要把这两个词单独拎出来对比。
因为绝大多数人会把"面向连接"和"可靠"当成同一件事，一做题就翻车。
它们其实是两个独立的维度：连接说的是"有没有事先打招呼、双方记不记状态"，可靠说的是"丢了会不会重传、顺序会不会乱"。

这是另一组高频混淆。

```text
面向连接（connection-oriented）：
  通信前先建立连接，通信后释放，中间的分组走同一条路
无连接（connectionless）：
  每个分组独立选路，不保证顺序，不保证到达
```

注意：**"连接"是逻辑上的，不是物理上的**。

TCP 的连接只是双方各维护一份状态（序号、窗口、缓冲区），中间没有任何东西被"占住"。

四种组合，都真实存在：

```text
TCP：面向连接、可靠
UDP：无连接、不可靠
IP：无连接、不可靠
X.25 / ATM：面向连接（网络层也能面向连接）
```

最后一行是陷阱。

很多人以为"网络层一定是无连接的"，不对。

IP 是无连接的，但 X.25、帧中继、ATM 都是面向连接的网络层技术。

再补三个容易混的概念：

```text
连接（connection）：双方维护状态，有握手有释放
可靠（reliable）：有确认、有重传、有序
有连接 ≠ 可靠（TCP 可靠，但 ATM 的连接不保证不丢）
无连接 ≠ 不可靠（可以在无连接之上做可靠，比如 QUIC）
```

**"面向连接"和"可靠"是两个独立的维度，不要绑在一起。**

## 12. OSI 与 TCP/IP 的对应与差异

两者不是"同一套东西的两张画法"。

它们的出身完全不同。

```text
OSI：先有模型，后有实现。
      ISO 花了很多年讨论"应该怎么分层"，标准出来时，
      市场上已经有别的协议了。OSI 自己的协议栈几乎没人用。

TCP/IP：先有实现，后有模型。
      先有 ARPANET 上的代码和能跑的网络，
      再回头总结"我们其实分了四层"。
```

这个顺序差异，解释了一切。

### 12.1 差异一：层数不同

```text
OSI 七层，TCP/IP 四层。
差别在两头：OSI 拆了会话层和表示层，TCP/IP 合并了物理层和链路层。
```

### 12.2 差异二：设计出发点不同

```text
OSI 追求"理论完备"：每一层都有明确的职责定义，边界清晰。
TCP/IP 追求"能跑"：能互通就行，边界模糊一点无所谓。
```

### 12.3 差异三：网络层的地盘不同

```text
OSI 的网络层假设底层是统一的（它自己定义了完整的下层）
TCP/IP 的网际层假设"下面什么都有"，只负责把异构网络缝起来
```

这就是为什么 TCP/IP 能赢：

**它不要求你先换掉现有的网络。**

### 12.4 差异四：会话层和表示层为什么消失

回到第 5.9 节那个问题。

OSI 认为"会话管理"和"数据表示"是独立问题，值得单独两层。

现实是：

```text
字符编码转换 → 由应用自己处理（HTTP 的 Content-Type + charset）
压缩         → 由应用自己处理（gzip / brotli，HTTP 头里协商）
加密         → 由 TLS 处理，TLS 跑在应用层和传输层之间
会话恢复     → 由应用自己处理（HTTP Cookie、Session ID）
```

这些功能全都真实存在，但没有一个"通用到值得单独占一层"。

因为它们和具体应用强绑定。

```text
网页的"会话"和 FTP 的"会话"完全不是一回事。
HTTP 的压缩协商和 SMTP 的编码转换也没有共同点。
```

**能被独立成层的前提是"上层对它有一致的需求"。**

会话和表示不满足这个前提，所以被吸收了。

### 12.5 那 OSI 还有什么用

它的价值不在实现，在**教学和排错**。

```text
排错时从下往上：先看物理层通不通，再看链路层有没有错，再看 IP 通不通
设计时按层分工：写网卡驱动的不用管 HTTP
描述问题时用层的语言："这是三层问题"比"网络坏了"精确得多
```

**所以正确的态度是：**

```text
用 OSI 的框架思考，用 TCP/IP 的协议干活。
```

## 13. 容易混淆的点

集中收一遍。

先把这一节绕不开的两个词说清楚。
冲突域（collision domain）：一批共享同一段介质、同时发送就会互相撞包的设备范围。
广播域（broadcast domain）：一个广播帧能送到的全部设备范围。
两者都只跟"谁和谁共享一段线"有关，跟 IP 地址划分无关。

```text
1. 服务 vs 协议
   服务垂直（上下层），协议水平（对等层）。
   题目问"谁为谁提供什么"，答服务；问"谁和谁怎么通信"，答协议。

2. 接口 vs 协议
   接口（SAP）是上下层的交接点，协议是对等层的规则。
   端口号就是传输层的 SAP。

3. 网络层 vs 传输层的"可靠"
   链路层的差错控制只管一段。
   传输层的可靠管全程。
   中间的路由器既不帮链路层重传，也不帮传输层重传。

4. 端到端 vs 点到点
   传输层 = 端到端 = 进程到进程。
   链路层 = 点到点 = 相邻节点。

5. ARP 归哪层
   408 的答案：网络层。
   但它的帧不经过 IP，直接封在以太网里。

6. DHCP 归哪层
   应用层（基于 UDP）。
   它配的是网络层的地址，但它是应用层协议。

7. 面向连接 ≠ 可靠
   TCP 既面向连接又可靠。
   ATM 面向连接但不保证不丢。
   QUIC 无连接（UDP 之上）但可靠。

8. 会话层和表示层
   模型里有，报文里没有。
   考"职责"要答得出来，考"协议"一定没有。

9. 交换机 vs 路由器
   交换机看 MAC，工作在链路层，分割冲突域。
   路由器看 IP，工作在网络层，分割广播域。
```

再加两条更细的：

```text
10. 帧尾只有链路层有
    因为只有它需要在比特流里标记边界。
    其他层只加首部。

11. 前导码不算帧的一部分
    它是物理层加的，用于时钟同步。
    算帧长时不含，算线上传输时间时含。
```

### 自检三问

1. 如果去掉分层、把所有事写进一个程序，换一块网卡或把以太网换成 Wi-Fi 时，要改哪些地方？
2. 为什么说协议是"水平"的、服务是"垂直"的？如果反过来理解，会在哪道题上答错？
3. 给你 1000 字节应用数据、TCP 首部 20 字节、IP 首部 20 字节、以太网首尾 18 字节、MTU 1500 字节，你能算出帧长、判断是否分片、算出传输效率吗？

## 14. 小结

压成几句话。

```text
分层是为了隔离变化：换底层不影响上层。
封装是逐层加首部，链路层还多一个帧尾。
协议水平，服务垂直，接口在垂直边界上。
```

OSI 七层与数据单位：

```text
应用层  报文
表示层  报文
会话层  报文
传输层  报文段
网络层  分组
链路层  帧
物理层  比特
```

协议归属一句话：

```text
HTTP/DNS 在上，TCP/UDP 在中间，
IP/ICMP/ARP 在下，以太网/PPP/无线再往下，
双绞线/光纤/电波在最底下。
```

三个最容易记错的：

```text
服务是垂直的，协议是水平的。
端到端是传输层，点到点是链路层。
面向连接不等于可靠。
```

一句话记住这篇的核心：

```text
OSI 是思考的框架，TCP/IP 是干活的工具，
报文里只有五层，模型里画了七层。
```

一根铜线、一束光，最多能塞进去多少比特？
这个上限是设备决定的，还是物理定律决定的？
```

```
