运营商打来电话，说宽带免费从 100 M 升到 500 M。

你测了一下速，测速网站显示 480 Mbit/s。

然后你去下载一个放在美国的文件，速度还是 2 MB/s。

钱没多花，体验也没变。

问题不在于运营商骗人，而在于**"带宽"这个词被用来回答一个它答不了的问题**。

带宽只回答一件事：

```text
数据从网卡推上链路，需要多久。
```

它不回答"数据在路上要跑多久"，也不回答"中间有没有人排队"。

这篇要做的，就是把这几个数分开。

```text
带宽（bandwidth）
吞吐量（throughput）
时延（delay / latency），拆成四段
往返时间（RTT）
利用率（utilization）
```

分开之后你会发现，"带宽翻倍"和"下载快一倍"之间隔着好几个变量。

## 1. 这个问题解决什么

先给一个能站得住的定义。

**计算机网络**：把地理位置不同、具有独立功能的多台计算机，用通信设备和线路连起来，由软件实现资源共享的系统。

这句话里有三个词不能省。

```text
独立功能：每台机器自己能干活，不是终端附庸
连接：有形的线或者无形的信道
共享：共享的是资源，不是机箱
```

少一个，就变成别的东西。

一堆只能听主机话的哑终端接在一台大型机上，那叫多用户系统，不叫网络。

一台机器插四块网卡，那不叫网络，叫一台机器。

所以"网络"的最小门槛是：**至少两台能自己算的机器，加上一条能互相说话的通道**。

那这一篇解决什么问题？

它解决三个具体困惑。

```text
一、买宽带时销售说的 M，和你下载时看到的 MB/s，差在哪。
二、两个都叫"快"的网络，为什么一个下大文件快，一个打游戏不卡。
三、为什么"利用率 100%"不是目标，而是灾难的开始。
```

这三个困惑对应三个概念：带宽、时延、利用率。

后面每一节都在拆这三个词。

## 2. 最小模型：网络由什么组成

任何一张网络，从功能上都能切成两块。

```text
┌─────────────────────────────────────────────┐
│  资源子网（resource subnet）                 │
│  主机、终端、数据库、打印机、服务器            │
│  负责：产生数据、处理数据、提供资源            │
├─────────────────────────────────────────────┤
│  通信子网（communication subnet）            │
│  路由器、交换机、链路、调制解调器              │
│  负责：搬运数据                               │
└─────────────────────────────────────────────┘
```

这个切法很好用。

因为它对应一个非常实际的判断：

```text
资源子网慢 → 换 CPU、换硬盘、加内存
通信子网慢 → 换线路、换设备、改拓扑
```

你下载慢，先要判断是哪一半慢。

判断方法也很土：在同一台机器上，从局域网内另一台机器拷同一个文件。

如果局域网内飞快，出门就慢，问题在通信子网。

如果局域网内也慢，问题在资源子网，网卡、磁盘、CPU 都要查。

从"我"到"网"的边界，往往比想象中更靠里。

一台千兆网卡的主机，往本地 SSD 写数据时如果磁盘只有 80 MB/s，那这条链路能跑满 940 Mbit/s 也没用。

**网络的性能上限，永远由最慢的那一段决定。**

这句话在后面的每一层都成立。

功能上，网络被总结成四条。

```text
数据通信：最基本的功能，把数据从 A 送到 B
资源共享：硬件、软件、数据都能共享
分布式处理：一个大任务拆给多台机器算
提高可靠性：一条路断了还有另一条
```

408 选择题偶尔会直接问"网络的最基本功能是什么"。

答案是数据通信。

资源共享是目的，数据通信是手段，别答反。

## 3. 一次完整走查：下载 1 MB 文件的 8 秒

现在把时间拆开。

场景设定（全部数字都是自拟，方便验算）：

```text
文件大小：1 MB = 1,000,000 字节 = 8,000,000 比特
链路速率：100 Mbit/s
距离：1000 km 光纤
光在光纤里的速度：约 2×10^8 m/s
```

按定义算三段。

```text
发送时延 = 数据长度 / 链路速率
        = 8,000,000 bit / 100,000,000 b/s
        = 0.08 s
        = 80 ms

传播时延 = 距离 / 传播速度
        = 1,000,000 m / 2×10^8 m/s
        = 0.005 s
        = 5 ms

单程总时延 ≈ 80 + 5 = 85 ms
```

85 毫秒。

可你实际等了 8 秒。

差了 94 倍。

这 94 倍里，没有一秒是"带宽不够"造成的。

拆开看，多出来的时间花在这些地方：

```text
DNS 查询：几十毫秒，取决于递归路径
TCP 三次握手：1 个 RTT = 10 ms
TCP 慢开始：窗口从 10 个 MSS 开始翻倍，要涨到能装下 1 MB
服务端出口带宽：可能只有 10 Mbit/s，那你只能拿到 1.25 MB/s
服务端磁盘：机械盘随机读，几十毫秒一次
浏览器并发连接数与渲染
```

第二项和第三项已经能解释大部分。

把服务端出口当成 10 Mbit/s 再看一遍：

```text
发送时延 = 8,000,000 bit / 10,000,000 b/s = 0.8 s
```

0.8 秒，是本地链路的 10 倍。

再加上慢开始、握手、TLS 协商，8 秒一点都不奇怪。

**这就是第一个必须建立的习惯：**

**看到"慢"，先把总时延拆成四段加一个 RTT，再判断是谁慢。**

不拆，你只会一直骂运营商。

## 4. 拆开看：分类的三种切法

网络有好几种分类法，408 会考，但考得不深。

按覆盖范围切：

```text
PAN  个人区域网   几米      蓝牙、USB
LAN  局域网       几十米~几公里   以太网、Wi-Fi
MAN  城域网       几公里~几十公里  有线电视网
WAN  广域网       几十公里以上    互联网的骨干
```

边界是模糊的，"几公里"不是硬标准。

按拓扑切：

```text
总线型（bus）      一根线全挂上，两端要终结电阻
星型（star）       所有设备连到一个中心，中心是交换机
环型（ring）       首尾相连，令牌环网
树型（tree）       星型的级联
网状（mesh）       两两互联，骨干网用
```

现在的局域网基本都是星型，因为交换机便宜。

按交换方式切，这个最重要，下一节单独讲。

## 5. 拆开看：三种交换方式的时延

"交换方式"回答的是：数据从源到目的，中间那些节点怎么把它转出去。

三种做法，性格完全不同。

### 5.1 电路交换（circuit switching）

先建一条端到端的物理通路，再传数据，传完拆掉。

打电话就是这样。

```text
主叫 ──┐                    ┌── 被叫
       ├── 中间节点逐段接通 ──┤
       │   建链 → 传数据 → 拆链
```

关键性质：

```text
建链要时间（几百毫秒）
建链后独占带宽，别人抢不走
传输时延 = 传播时延，中间节点不存储转发
适合：长时间、连续、恒定速率的数据
```

缺点是"占着茅坑"。

你不说话的时候，那条通路也不能给别人用。

### 5.2 报文交换（message switching）

不建链，整个报文发给下一个节点，节点收全了再往下发。

```text
源 ──[整个报文]──> 节点A ──[整个报文]──> 节点B ──> 目的
     收全再发          收全再发
```

关键性质：

```text
不用建链
节点要有足够大的缓存装下整个报文
时延 = 逐跳"存储-转发"时间之和
报文越长，中间节点占线越久
```

一个 10 MB 的报文，每个中间节点都要先收 10 MB 再发。

这一跳就是几秒钟。

### 5.3 分组交换（packet switching）

把报文切成一个个小分组，每个分组独立转发。

```text
报文：┌──────────────────────────┐
       └──────────────────────────┘
切成：┌────┐┌────┐┌────┐┌────┐┌────┐
       └────┘└────┘└────┘└────┘└────┘
每个分组各自带首部，各自找路
```

关键性质：

```text
不用建链
节点缓存小（一个分组大小）
流水线：第 1 个分组还在路上，第 2 个已经在发
可能乱序、可能丢失，要靠上层补
```

### 5.4 算一遍：三种方式谁快

取一组能整除的数：

```text
报文长度 L = 10,000 bit
分成 n = 10 个分组，每组 p = 1,000 bit
经过 k = 3 段链路（源 → R1 → R2 → 目的）
每段速率 C = 1 Mbit/s
忽略传播时延、处理时延、排队时延
```

电路交换：

```text
建链时间 s = 0.2 s
传输时间 = L / C = 10,000 / 1,000,000 = 0.01 s
总时延 = 0.2 + 0.01 = 0.21 s = 210 ms
```

报文交换（存储转发，逐跳收全再发）：

```text
每跳 = L / C = 0.01 s
总时延 = k × L / C = 3 × 0.01 = 0.03 s = 30 ms
```

分组交换（流水线）：

```text
第 1 个分组到达目的：k × p / C = 3 × 0.001 = 0.003 s
之后每 p / C 到一个：第 n 个到达时间 = (k + n - 1) × p / C
= (3 + 10 - 1) × 0.001 = 12 × 0.001 = 0.012 s = 12 ms
```

三者摆一起：

| 方式 | 总时延 | 是否建链 | 节点缓存 | 适合 |
|---|---|---|---|---|
| 电路交换 | 210 ms（含 200 ms 建链） | 是 | 无 | 长时间、恒定速率 |
| 报文交换 | 30 ms | 否 | 整个报文 | 电报类，已淘汰 |
| 分组交换 | 12 ms | 否 | 一个分组 | 突发数据，互联网 |

**别急着记住"分组交换最快"。**

这张表里的 210 ms 主要是建链时间。

如果这个连接要传 1 小时的数据，建链那 200 ms 摊薄之后可以忽略，电路交换反而更稳、更省中间节点的开销。

分组交换真正赢的地方是**突发流量**：

```text
你发一条微信，可能只有 200 字节。
用电路交换：建链 200 ms 就为发 200 字节。
用分组交换：直接塞进去，几十毫秒完事。
```

互联网选分组交换，不是因为它在任何情况下都快，而是因为绝大多数流量是突发的。

### 5.5 分组交换的代价

代价写清楚，408 也爱考。

```text
每个分组都要带首部，有效载荷比例下降
可能乱序，接收端要重排
可能丢失，要重传
节点排队，时延抖动
```

首部开销是可以算的。

一个 1000 字节的分组，如果 IP 首部 20 字节、TCP 首部 20 字节、以太网首部加尾部 18 字节：

```text
总长 = 1000 + 20 + 20 + 18 = 1058 字节
应用数据占比 = 1000 / 1058 ≈ 94.5%
```

剩下 5.5% 是"路费"。

这个比例在第 02 篇还会再算一次。

## 6. 408 怎么考

这一节的题型固定，几乎每年都有。

```text
选择题：带宽与吞吐量的区别、时延的四个组成部分、利用率计算
计算题：给长度/速率/距离，求总时延
      给停等协议，求信道利用率
      给窗口大小，求利用率或最小窗口
综合题：三种交换方式时延比较（常和"分组流水线"一起考）
```

套路只有三条。

```text
一、发和传分开。"发"是推上链路，"传"是在路上跑。
二、只有发送时延和链路速率有关，传播时延只和距离、介质有关。
三、利用率公式的分母是"一个周期"，不是"一次发送"。
```

### 例题（自拟，按 408 风格）

一条链路长 2000 km，信号传播速度 2×10^8 m/s，链路速率 100 Mbit/s，帧长 1000 字节，确认帧长度忽略不计，处理时延和排队时延忽略。

求：

```text
(1) 发送时延
(2) 传播时延与 RTT
(3) 停等协议下的信道利用率
(4) 链路速率升到 1 Gbit/s 后的信道利用率
(5) 要让信道利用率达到 100%，窗口至少要多少个帧
```

### 解

先统一单位：1000 字节 = 8000 比特，100 Mbit/s = 10^8 b/s。

```text
(1) 发送时延 Td = 8000 / 10^8 = 8×10^-5 s = 80 μs
```

```text
(2) 传播时延 Tp = 2,000,000 m / (2×10^8 m/s) = 0.01 s = 10 ms
    RTT = 2 × Tp = 20 ms
```

```text
(3) 停等：U = Td / (Td + RTT)
       = 80 μs / (80 μs + 20,000 μs)
       = 80 / 20,080
       ≈ 0.003984
       ≈ 0.40%
```

只有 0.4%。

这条链路 99.6% 的时间在等确认。

```text
(4) 1 Gbit/s 时 Td = 8000 / 10^9 = 8 μs
    U = 8 / (8 + 20,000) = 8 / 20,008 ≈ 0.0004 = 0.04%
```

带宽涨了 10 倍，利用率掉了 10 倍。

因为瓶颈从头到尾都是 RTT，不是带宽。

```text
(5) 窗口为 W 时：U = W×Td / (Td + RTT)
    令 U = 1：
    W×80 = 80 + 20,000
    W = 20,080 / 80 = 251
```

**答：至少 251 个帧。**

验算一下这个 251 有没有物理意义。

```text
时延带宽积 = 带宽 × RTT = 10^8 b/s × 0.02 s = 2×10^6 bit
换算成 1000 字节的帧：2×10^6 / 8000 = 250 个帧
```

250 个帧正好"填满管道"，再多 1 个帧才能让发送方不停手，所以是 251。

两个算法对上了，说明公式没记错。

**这道题的考点就一句话：**

**带宽决定"多快能把数据推出去"，RTT 决定"推出去之后要等多久"。**

两者相乘才是管道容量。

## 7. 真实网络里长什么样

在 Linux 上看一条链路，用 `ip -s link`：

```text
$ ip -s link show eth0
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP
    link/ether 3c:52:82:1a:4b:7e brd ff:ff:ff:ff:ff:ff
    RX:  bytes packets errors dropped  missed   mcast
     918273645  712344       0       12       0   90211
    TX:  bytes packets errors dropped carrier collsns
     312004928  403211       0        0       0       0
```

三件事值得看。

```text
mtu 1500        一个帧能装的最大载荷，1500 字节
errors          物理层/链路层出错，非 0 说明线或光模块有问题
dropped         队列满了丢包，非 0 说明这里在拥塞
```

`dropped` 是最能说明"利用率"的字段。

队列满就丢，丢就重传，重传又占带宽，恶性循环。

要看链路协商出来的速率和双工，用 `ethtool`：

```text
$ ethtool eth0
Settings for eth0:
        Supported link modes:   1000baseT/Full
        Speed: 1000Mb/s
        Duplex: Full
        Link detected: yes
```

`Duplex: Half` 是个危险信号。

半双工加冲突检测，实际吞吐会掉到标称值的一半以下。

测真实吞吐用 `iperf3`，别用浏览器下载。

因为浏览器下载还受服务端、磁盘、TLS、拥塞控制影响。

千兆网卡上 `iperf3` 通常跑到 930–950 Mbit/s，而不是 1000。

这不是网卡虚标，是每帧都在交"路费"。

粗算一遍（简化示意，忽略 VLAN 标签等）：

```text
一个满载以太网帧，线上实际要发的字节：
前导码 8 + 目的 MAC 6 + 源 MAC 6 + 类型 2
+ 载荷 1500 + FCS 4 + 帧间隙 12
= 1538 字节

若 TCP 载荷是 1460 字节（1500 - 20 IP - 20 TCP）：
有效比例 = 1460 / 1538 ≈ 94.9%

1000 Mbit/s × 94.9% ≈ 949 Mbit/s
```

949 和实测的 930–950 对得上。

**这就是"标称带宽"和"有效带宽"的差距**，而且它和线路质量无关，是协议开销决定的。

## 8. 带宽：b/s 不是 B/s

这是最常见的一个错，必须一次性说死。

```text
带宽的单位是 bit/s（比特每秒），写作 b/s、bps、bit/s
文件大小的单位是 Byte（字节），1 Byte = 8 bit
```

所以：

```text
100 Mbit/s = 100,000,000 bit/s = 12,500,000 B/s = 12.5 MB/s
```

不是 100 MB/s。

差了 8 倍整。

运营商说的"100 M 宽带"，说的是 100 Mbit/s。

你下载时看到的 12 MB/s，说的是 12 MByte/s。

两个数是同一个东西，只是单位不同。

把这张对照记熟，能省掉很多次"被骗了"的错觉：

```text
100 Mbit/s  →  理论峰值 12.5 MB/s
200 Mbit/s  →  理论峰值 25 MB/s
500 Mbit/s  →  理论峰值 62.5 MB/s
1000 Mbit/s →  理论峰值 125 MB/s
```

注意"理论峰值"四个字。

实际值一定更低，因为还有上面算的 5% 协议开销。

还有一个更隐蔽的坑：**存储厂商用十进制，操作系统用二进制**。

```text
硬盘厂说 1 TB = 1,000,000,000,000 字节
Windows 显示 931 GB，因为它按 1024 进制算
```

这不是缺斤少两，是两套单位。

408 的规矩是：**1 KB = 1024 B，链路速率按十进制 b/s**。

做题时严格按这个来，别混。

带宽还有一个容易忽略的性质：

```text
带宽是链路的物理属性，由介质和收发设备决定
它说的是"最高能推多快"，不是"现在推多快"
```

所以"带宽"和"实际速率"是上限与实测的关系。

## 9. 吞吐量：链路速率不等于你拿到的速率

**吞吐量（throughput）**：单位时间内实际通过某个网络（或信道、接口）的数据量。

关键词是"实际"。

```text
带宽：这条链路最多能跑多少
吞吐量：这条链路现在跑了多少
```

一条 100 Mbit/s 的链路，吞吐量可能是 90 Mbit/s，也可能是 2 Mbit/s。

看几个典型的瓶颈位置：

```text
源主机磁盘慢        → 吞吐被磁盘卡住
中间某段链路只有 10 M → 吞吐被这段卡住（瓶颈链路）
接收方窗口小        → 吞吐被 rwnd 卡住
网络拥塞            → 吞吐被丢包和拥塞控制卡住
```

所以吞吐量的定义里有一句很重要的话：

**吞吐量由瓶颈链路决定，不由最快的那段决定。**

一条路径上 源—A—B—目的，带宽依次是 1 Gbit/s、100 Mbit/s、1 Gbit/s。

端到端吞吐量的上限是 100 Mbit/s。

这不是"平均"，是"最小值"。

再往下一层，吞吐量还分"线路吞吐"和"有效吞吐"。

```text
线路吞吐：链路上跑的比特数 / 时间
有效吞吐：应用层拿到的字节数 / 时间
```

两者差的就是首部开销和重传。

用第 7 节算过的比例：

```text
线路 949 Mbit/s 的 TCP 有效吞吐 ≈ 1460/1538 × 1000 ≈ 949 Mbit/s
再扣掉 TCP 重传和 ACK，实测 930 左右
```

**有效带宽（effective bandwidth）** 说的就是这个数：

```text
有效带宽 = 吞吐量 × 有效载荷比例
```

它才是用户真正感知到的速度。

讲"带宽"的时候如果不讲有效带宽，就是耍流氓。

## 10. 时延的四个部分

这是 408 最爱考的计算点。

总时延 = 四段之和。

```text
总时延 = 发送时延 + 传播时延 + 处理时延 + 排队时延
```

逐个说。

### 10.1 发送时延（transmission delay）

也叫传输时延。

```text
发送时延 = 数据长度（bit） / 链路速率（bit/s）
```

注意分子是比特，不是字节。

注意分母是链路速率，不是传播速度。

这一项和距离**完全无关**。

### 10.2 传播时延（propagation delay）

```text
传播时延 = 链路长度（m） / 传播速度（m/s）
```

传播速度取决于介质：

```text
真空 / 空气：约 3×10^8 m/s
光纤：约 2×10^8 m/s（折射率约 1.5）
铜缆：约 2.3×10^8 m/s（约为光速的 0.77）
```

这一项和链路速率**完全无关**。

一个很好的类比是车队过收费站：

```text
发送时延 = 所有车依次通过收费站的时间（收费口越多越快）
传播时延 = 最后一辆车从收费站开到目的地的时间（路越长越久）
```

收费站再加 10 个口，车在路上跑的时间一点不变。

**这就是本篇的反直觉点。**

> **带宽只影响"把数据推上链路"的时间，不改变"数据在路上跑"的时间。**
>
> 一条 10 Gbit/s 的跨洋链路，传播时延仍然是 60 ms 左右，一分不少。
> 带宽可以从 1 G 涨到 100 G，这 60 ms 是物理定律决定的。

### 10.3 处理时延（processing delay）

节点收到分组后要做的事：

```text
检查首部
查转发表
差错检测
必要时分片
```

通常是微秒级，做题时经常忽略。

但在高速链路上它占比不小：10 Gbit/s 的链路上，一个 1500 字节的帧发送时延只有 1.2 μs。

处理时延如果要做 2 μs，那就比发送时延还长。

### 10.4 排队时延（queueing delay）

分组在节点输出队列里等的时间。

```text
队列空 → 0
队列满 → 丢包
```

这一项是唯一"不确定"的时延。

它取决于流量强度，也因此决定了"利用率不能到 100%"。

### 10.5 四段的比例会随场景翻转

同一条链路，换一个数据长度，结论就变了。

```text
1000 字节，100 Mbit/s，1000 km：
发送 80 μs，传播 5000 μs
→ 传播占 98%

1,000,000 字节，100 Mbit/s，1000 km：
发送 80 ms，传播 5 ms
→ 发送占 94%
```

所以"哪个时延占主导"没有标准答案。

必须代入具体数字算。

这也是 408 出题的空间所在。

## 11. RTT 与利用率

### 11.1 RTT

**RTT（round-trip time，往返时间）**：从发送方发出数据开始，到收到接收方确认，总共花的时间。

```text
RTT ≈ 2 × 传播时延 + 处理时延 + 排队时延 + 确认帧的发送时延
```

做题时最常用的简化：

```text
RTT ≈ 2 × 传播时延
```

RTT 是"交互感"的来源。

```text
打游戏卡不卡，看 RTT
视频会议能不能对话，看 RTT
网页打开快不快，看 RTT（因为要建连、要握手）
```

ITU 的建议是语音通话单向时延控制在 150 ms 以内，超过 400 ms 基本没法对话。

换算成 RTT 就是 300 ms 以内。

这也是为什么卫星电话听起来像在自言自语。

同步卫星高度约 35,786 km，单程传播时延：

```text
35,786,000 m / 3×10^8 m/s ≈ 0.119 s ≈ 119 ms
```

一来一回 238 ms，已经接近对话容忍的极限。

**注意：卫星链路的带宽可以很大，但 RTT 被物理距离锁死。**

### 11.2 信道利用率

```text
信道利用率 U = 有数据通过的时间 / 总时间
```

对停等协议：

```text
U = Td / (Td + RTT)
```

对窗口为 W 的连续发送：

```text
U = W × Td / (Td + RTT)     （当 W×Td < Td + RTT）
U = 1                        （当 W×Td ≥ Td + RTT）
```

第二个式子的意思是：窗口大到能填满管道，链路就一直忙。

填满管道需要的窗口就是时延带宽积。

### 11.3 网络利用率与时延的关系

整个网络的利用率上来之后，排队时延会非线性上升。

经验公式：

```text
D = D0 / (1 - U)
```

其中 D 是当前时延，D0 是网络空闲时的时延，U 是网络利用率。

代几个数看看：

```text
U = 0.5  → D = 2 D0      时延翻倍
U = 0.8  → D = 5 D0      时延 5 倍
U = 0.9  → D = 10 D0     时延 10 倍
U = 0.99 → D = 100 D0    时延 100 倍
```

**这就是"利用率不能到 100%"的数学原因。**

不是设备不行，是排队论的必然结果。

U 越接近 1，分母越接近 0，时延趋向无穷。

实际工程里，骨干网利用率控制在 50% 左右，接入网峰值控制在 70%–80%。

超过这个数，一次突发流量就能让时延炸掉。

所以设计网络时，"留余量"不是浪费，是买稳定。

## 12. 带宽翻倍为什么不等于快一倍

现在可以定量回答了。

先把总时间写成一个式子。

传 N 比特的数据，经过一条链路：

```text
T = N / C + Tp
```

其中 C 是带宽，Tp 是单程传播时延（含处理和排队，先忽略）。

```text
带宽翻倍时，第一项减半，第二项不变。
```

所以：

```text
加速比 = (N/C + Tp) / (N/2C + Tp)
```

这个比值永远小于 2，除非 Tp = 0。

代入一组数看看能差多少。

```text
文件 N = 8×10^6 bit（1 MB）
距离 20,000 km，单程传播时延 Tp = 100 ms
```

```text
C = 80 Mbit/s：
T = 8×10^6 / 8×10^7 + 0.1 = 0.1 + 0.1 = 0.2 s

C = 160 Mbit/s：
T = 8×10^6 / 1.6×10^8 + 0.1 = 0.05 + 0.1 = 0.15 s

加速比 = 0.2 / 0.15 ≈ 1.33
```

带宽翻了一倍，只快了 33%。

再翻一次：

```text
C = 320 Mbit/s：T = 0.025 + 0.1 = 0.125 s
加速比 = 0.15 / 0.125 = 1.2
```

越翻越不划算。

把 C 推到无穷，T 趋近 0.1 s。

**也就是说，这条链路上，无论带宽多大，1 MB 文件的传输时间都不可能低于 100 ms。**

这就是"带宽墙"。

### 12.1 更极端的情况：高带宽 + 高时延

再看一个更反直觉的例子。

```text
链路带宽：1 Gbit/s
RTT：200 ms（单程 100 ms）
协议：停等，每帧 1000 字节
```

算吞吐量：

```text
一帧的发送时延 Td = 8000 bit / 10^9 b/s = 8 μs
一个周期的长度 = Td + RTT = 8 μs + 200,000 μs = 200,008 μs
吞吐量 = 8000 bit / 0.200008 s ≈ 39,984 b/s ≈ 40 kbit/s
```

**1 Gbit/s 的链路，跑出了 40 kbit/s 的吞吐量。**

只用到带宽的 0.004%。

> **反直觉点：带宽和吞吐量可以差四个数量级。**
>
> 高带宽 + 高时延的链路，如果协议不会"连续发"，吞吐量仍然可以低得可怜。
> 决定吞吐量的是"时延带宽积能被填满多少"，不是标称带宽。

这个例子解释了为什么 TCP 要做窗口、要有慢开始、要有时延带宽积这个概念。

也解释了为什么早期的卫星上网那么难受。

修复办法只有两个：

```text
一、把窗口开大，让管道被填满（TCP 窗口缩放选项）
二、减少往返次数（协议层合并请求）
```

第一条是 TCP 窗口缩放（window scaling）要解决的问题。

第二条是 HTTP/2 多路复用、QUIC 0-RTT 要解决的问题。

**所有"加速"技术的本质，都是在跟 RTT 较劲，而不是跟带宽较劲。**

### 12.2 什么时候带宽翻倍真的快一倍

条件很明确：

```text
发送时延远大于传播时延
即 N/C >> Tp
```

换成工程语言：

```text
传大文件，且链路不太长 → 带宽是瓶颈，翻倍就快一倍
传小文件，或者链路很长 → RTT 是瓶颈，翻倍几乎没用
```

这就是为什么：

```text
下 4K 电影，宽带升级感受明显
刷网页、打游戏，宽带升级感受不明显
```

因为前者是"发送时延主导"，后者是"RTT 主导"。

一个实用的判断：

```text
算一下 N/C 和 Tp 的比值。
比值大于 10，带宽是瓶颈。
比值小于 1，RTT 是瓶颈，加带宽没用。
```

## 13. 容易混淆的点

集中收一遍，这些是选择题的常客。

```text
1. 带宽 vs 吞吐量
   带宽是上限，吞吐量是实测。带宽 100 M，吞吐量可能只有 2 M。

2. 发送时延 vs 传播时延
   发送时延和"数据多长、链路多快"有关。
   传播时延和"路多远、信号多快"有关。
   两者没有关系，不要互相代入。

3. 速率 vs 传播速度
   速率是 bit/s，传播速度是 m/s。
   单位都不一样，别混。

4. RTT vs 单程时延
   RTT ≈ 2 × 单程传播时延。
   算利用率时用 RTT，算"数据到对面要多久"时用单程。

5. 1 KB = 1024 B，但链路速率按十进制
   408 明确这么规定。写答案时把单位带上，能自证。

6. 利用率 100% 不是好事
   排队时延 D = D0/(1-U)，U 趋近 1 时时延爆炸。
   工程上留 20%–50% 余量。

7. 电路交换不一定比分组交换慢
   短报文时电路交换被建链时间拖死。
   长连接时电路交换稳定且开销小。
```

还有两个更细的：

```text
8. 时延带宽积的单位是比特，不是字节
   它表示"管道里能装多少比特"，等价于"窗口至少要多大"。

9. 有效带宽 ≠ 带宽
   有效带宽要扣掉首部、重传、ACK。
   千兆网卡的有效带宽约 940 Mbit/s，不是 1000。
```

记这九个，比背定义有用。

## 14. 小结

把这一篇压成几句话。

```text
网络 = 资源子网 + 通信子网
功能 = 数据通信（最基本）+ 资源共享 + 分布式处理 + 可靠性
分类 = 按范围、按拓扑、按交换方式
```

三种交换方式：

```text
电路交换：先建链，独占，适合长时间恒定速率
报文交换：整包存储转发，节点缓存要大
分组交换：切小、流水线、适合突发，但有首部开销
```

五个性能指标：

```text
带宽      = 链路最高速率，单位 b/s，注意不是 B/s
吞吐量    = 实际通过的量，由瓶颈链路决定
时延      = 发送 + 传播 + 处理 + 排队
RTT       = 往返时间 ≈ 2 × 传播时延
利用率    = 忙的时间 / 总时间，越高排队时延越大
```

三个公式：

```text
发送时延 = L / C
传播时延 = d / v
时延带宽积 = C × RTT
```

一句话记住这篇的核心：

```text
带宽管"推出去多快"，
RTT 管"推出去之后等多久"，
两者相乘才是这条管道真正的容量。
```
