早上打开邮箱，点开一封带附件的邮件。

附件是一张图，图里还有一个外链。

在你看到这张图之前，这台机器做了三件事：

```text
用 IMAP 把邮件正文和附件从服务器拉下来
用 DNS 查出图片所在主机的 IP
用 SMTP 把你昨天写的回信推出去
```

三件事，三个协议，全在应用层。

前四层忙了半天，只保证一件事：字节从一台机器到了另一台机器。

字节到底是什么意思，是应用层说了算。

这一篇讲三个老协议。

DNS 是"名字换地址"，FTP 是"两条连接传文件"，电子邮件是"三个协议接力送一封信"。

三个都不难，但都有 408 爱考的那一个点。

先看第一个，也是最常被误解的一个。

## 1. 这个问题解决什么

应用层解决的是"语义"。

传输层把字节送到正确的进程，但它不知道这些字节是域名查询、是一个文件块、还是一封邮件的正文。

应用层协议就是给这些字节定规矩。

规矩有三部分：

```text
语法：报文长什么样（字段顺序、编码）
语义：每个字段是什么意思（这是查询还是应答）
时序：谁先发、谁后发、什么时候算结束
```

这套三件套，任何应用层协议都套得上。

DNS 的语法是"查询名 + 查询类型 + 查询类"，语义是"给我这个类型的记录"，时序是"一问一答，可以重传"。

FTP 的语法是"四字符命令 + 参数 + CRLF"，语义是"登录、切目录、取文件"，时序是"控制连接先建立，数据连接按需建立"。

SMTP 的语法是"命令 + 参数"，语义是"我要发信给这些人"，时序是"打招呼、报发件人、报收件人、给数据、说再见"。

应用层还有一个绕不开的东西：端口。

一个主机上同时跑着浏览器、邮件客户端、SSH，IP 只能定位到主机，端口才能定位到进程。

端口是 16 位，0–65535。

```text
0–1023      熟知端口，需要权限才能监听
1024–49151  登记端口
49152–65535 临时端口，客户端随机选
```

应用层协议的价值不在"协议本身多精妙"，在于**它让两台互不认识的机器，对同一串字节有同一个理解**。

## 2. 最小模型：C/S 与 P2P

应用层的所有协议，按"谁主动、谁常驻"只有两种形状。

客户/服务器（Client/Server，C/S）：

```text
服务器：地址固定、端口固定、一直在线、被动等
客户端：地址临时、端口随机、主动发起、用完就走
```

对等网络（Peer-to-Peer，P2P）：

```text
每个节点既是客户端，也是服务器
没有永远在线的中心
谁来提供数据，是临时协商出来的
```

两种形状的差别，全在"扩展性"三个字上。

C/S 的问题是服务器是瓶颈。

一万个客户端来下载，服务器上行带宽就是上限，加机器要花钱，还要做负载均衡。

P2P 把这个问题反过来：来的人越多，能提供数据的人也越多，总带宽反而变大。

代价是管理。

谁负责鉴权、计费、内容审核？

节点随时上下线，一个块可能只有一个人有，那个人走了怎么办？

所以工程上常见的是混合结构：

```text
BitTorrent：tracker 只做"谁有哪个块"的索引，数据直接在 peer 之间传
早期 Skype：登录靠中心服务器，语音通话尽量直连
 Napster：集中索引 + 直连下载
```

408 在这一块只考概念：C/S 与 P2P 的区别、P2P 里"每个节点既是客户端又是服务器"。

真正容易出错的是一个细节：**DNS 是 C/S 结构，但本地域名服务器自己也是服务器、也是客户端**。

它对客户端是服务器，对根和权威是客户端。

FTP 是 C/S，而且是有状态的 C/S。

SMTP 是 C/S，但邮件系统里还有 MTA 中继，一封信可能经三四个服务器，每个服务器都同时扮演客户端和服务器。

## 3. 一次完整走查：从敲域名到拿到 IP

先定场景。

```text
主机 H：192.168.1.10，本地域名服务器：202.96.128.86
H 要访问：www.example.com
本地域名服务器的缓存是空的
```

一次完整的解析，八个报文。

```text
主机 H              本地 DNS            根             .com 顶级        example.com 权威
  │                    │                │               │                  │
  │ ①查询 www.example.com ►│             │               │                  │
  │  （递归：你负责查到底）│                │               │                  │
  │                    │ ②查询 ─────────►│               │                  │
  │                    │◄─ ③转介：去问 .com 的服务器 ────│                  │
  │                    │ ④查询 ─────────────────────────►│                  │
  │                    │◄─ ⑤转介：去问 example.com 的权威 ─│                  │
  │                    │ ⑥查询 ───────────────────────────────────────────►│
  │                    │◄─ ⑦应答：93.184.216.34 ───────────────────────────│
  │◄─ ⑧应答：93.184.216.34│               │               │                  │
```

数一下：四个查询，四个应答，共八个报文。

这八个报文全部是 UDP，目的端口 53。

注意 ③ 和 ⑤ 不是答案，是"转介"（referral）。

根服务器不回 "93.184.216.34"，它回的是"`.com` 这一片不归我管，你去问这几个服务器"。

顶级服务器也不回答案，它回的是"`example.com` 这一片归 `ns.example.com` 管"。

只有权威服务器才给最终答案。

这就是层次结构的全部意义：**每一层只知道自己下一层在哪，不需要知道全世界**。

如果本地 DNS 有缓存，就只剩两个报文：

```text
①查询 ►  ②应答（TTL 还没到期，直接给答案）
```

如果主机自己有缓存（浏览器或操作系统），连这两个报文都没有。

Linux 上 `systemd-resolved`、macOS 上的 `mDNSResponder`、Windows 的 DNS Client，都在本地留一层。

## 4. DNS 的层次结构：四类服务器各管一段

域名系统（Domain Name System）是一棵倒着长的树。

```text
                    .（根）
        ┌───────────┼───────────┐
       com         org          cn
        │           │           │
    example      wikipedia    edu.cn
        │
   www.example.com
```

从右往左读，越往右越高。

`www.example.com` 里，`.` 是根，`com` 是顶级域，`example.com` 是一个区，`www` 是区里的一台主机。

名字有几个硬限制，选择题偶尔会碰：整串域名不超过 255 字节，每一段标签不超过 63 字节。

标签里的字母不区分大小写，`WWW.example.com` 和 `www.example.com` 是同一个名字。

四类服务器：

```text
根域名服务器：知道所有顶级域的服务器在哪（a.root-servers.net … m.root-servers.net）
顶级域名服务器：知道 .com / .cn 下面每个授权区的权威服务器在哪
权威域名服务器：真的存着某个区的记录，给出的答案有权威性
本地域名服务器：不存权威记录，只负责替客户端跑腿，并把结果缓存
```

根服务器全球 13 组名字（a 到 m），但物理实例远不止 13 台。

靠的是任播（anycast）：同一个 IP 在世界各地都有实例，路由把查询带到最近的那台。

所以"13 台根服务器"是个过时的说法，准确说法是 13 个根服务器标识。

四类里有一个例外：本地域名服务器不属于这棵树的任何一层。

它是网络管理员或者运营商给你的一个"代理"。

DHCP 下发地址时，会顺手把本地 DNS 的地址一起给你，就是图省事。

这也是 408 的一个常见判断：**本地域名服务器不属于域名服务器的层次结构**。

还有一个容易混的词：区（zone）和域（domain）。

域是名字空间的一段。

区是"授权"的单位：一个区就是一个（或一组）权威服务器真正负责的范围。

`example.com` 可以把 `shop.example.com` 这个子域授权出去，交给另一组服务器管。

授权之后，`example.com` 的权威服务器只留一条 NS 记录指向子域的服务器，剩下的就不管了。

## 5. 递归与迭代：谁替谁跑腿

这一节是这一篇最值钱的地方。

先把两个定义摆平，别看名字，看动作。

递归查询（recursive query）：

```text
你问 A：www.example.com 是多少？
A 说：你等着，我去问。
（A 去问 B，B 去问 C……最后由 A 把最终答案交给你）
```

迭代查询（iterative query）：

```text
你问 A：www.example.com 是多少？
A 说：我不知道，但你可以去问 B。
（你自己去问 B，B 再让你去问 C，你一路自己跑）
```

所以"递归"和"迭代"的区别，**不是查询报文走几次，而是谁负责跑完整个流程**。

放到真实配置里：

```text
主机 H  →  本地 DNS      递归（H 只问一次，本地 DNS 负责给最终答案）
本地 DNS →  根           迭代（根只回"去问 .com"）
本地 DNS →  .com 顶级    迭代（顶级只回"去问 ns.example.com"）
本地 DNS →  权威         迭代（权威给最终答案）
```

> **反直觉的点**：DNS 的"递归"和"迭代"说的是本地域名服务器**替不替客户端跑腿**，不是查询报文走几次。迭代查询里，客户端只问一次，剩下的都是本地 DNS 在跑。

这句话反过来读，能拆掉两个常见的错误理解。

错误一："迭代查询报文少。"

不对。

上一节数过，本地 DNS 先问根、再问顶级、再问权威，还是四个查询、四个应答。

递归和迭代的报文数一样多，区别只在"谁发出去的"。

错误二："递归查询是客户端一层层问上去。"

也不对。

递归查询里客户端问完第一次就可以去睡觉了，剩下的活儿全在本地 DNS 手上。

那为什么这么设计？

因为根服务器扛不住。

全球的根服务器每秒要处理海量查询，如果每个客户端都要求根"你帮我查到底"，根就得替全世界做递归，还要维护海量的会话状态。

迭代查询让根只干一件事：告诉你去问谁。

这一句话的答案可以被缓存很久，也可以被无数人共用。

客户端那一侧相反，它越笨越好。

所以家用路由器从 DHCP 拿到本地 DNS 地址，客户端只需要会一件事：把问题丢给本地 DNS，然后等答案。

这是"把复杂性推到网络边缘"的典型做法。

顺便记一个数：如果主机、本地 DNS 全无缓存，采用"主机→本地递归、本地→其余迭代"，总报文数是 8。

如果主机→本地也改成迭代（少见的配置），报文数会变，但 408 默认考 8 这个数。

## 6. 408 怎么考

应用层的题，几乎全是"记结论 + 辨归属"。

先列应用层四类题的落点：

```text
DNS   查询方式（递归/迭代）、记录类型、缓存、端口 53、UDP
FTP   控制连接 21、数据连接 20、主动/被动、为什么两条连接
邮件  SMTP 25 推、POP3 110 拉并删除、IMAP 143 拉并保留、MIME
HTTP  方法、状态码、连接方式、Cookie（第 22 篇）
```

DNS 的考法有三种。

一种是报文数。

一种是"某某服务器返回的是答案还是转介"。

一种是记录类型和 TTL。

FTP 的考法基本固定：端口号、哪条连接先建立、数据连接由谁发起。

邮件的考法更固定：谁推谁拉、端口、POP3 与 IMAP 的差别、MIME 解决什么问题。

**归属判断**是选择题的常客：

```text
DNS、FTP、SMTP、POP3、IMAP、HTTP、HTTPS、DHCP、SNMP、Telnet 都属于应用层
TCP、UDP 属于传输层
IP、ICMP、ARP、OSPF、BGP 属于网络层
```

这里埋了一个坑：**ARP 属于网络层，不是链路层**；**ICMP 属于网络层，不是传输层**。

还有一个小坑：DHCP 用 UDP，但它是应用层协议；DNS 主要用 UDP，也是应用层协议。

上一节那 8 个报文，是这一篇最该背下来的一道题。

三道能算的例题，自己先算再对答案。

**例题一（自拟）**

主机 H 的本地域名服务器缓存为空，H 访问 `www.example.com`，采用"主机→本地递归、本地→根/顶级/权威迭代"。

问：整个解析过程共交换多少个 DNS 报文？分别是什么？

答：

```text
8 个。
① H 查询本地 DNS      ② 本地 DNS 应答 H
③ 本地 DNS 查询根     ④ 根转介 .com
⑤ 本地 DNS 查 .com    ⑥ 顶级转介 example.com 的权威
⑦ 本地 DNS 查权威     ⑧ 权威应答 A 记录
```

四个查询、四个应答，全部是 UDP，目的端口 53。

**例题二（自拟）**

某邮件系统，一封邮件的正文 900 字节，附件 300 KB（二进制）。

附件用 MIME base64 编码，编码后体积约为多少？

答：

```text
base64 把每 3 个字节编成 4 个字符，膨胀 4/3 ≈ 1.333。
300 KB × 4/3 = 400 KB
```

多出来的约 100 KB，就是 SMTP 只认 7 位 ASCII 的代价。

**例题三（自拟）**

判断正误：客户端用浏览器登录 Web 邮箱，写信并点击发送，从浏览器到邮件服务器的这一段使用 SMTP 协议。

答：

```text
错。
浏览器到 Web 邮箱服务器用的是 HTTP（或 HTTPS）。
服务器内部再用 SMTP 把信推给收件方的 MTA。
SMTP 是"服务器与服务器之间"或者"邮件客户端与服务器之间"的协议，
不是"浏览器与服务器之间"的协议。
```

这一题就是 408 爱设的"协议归属"陷阱。

## 7. 真实网络里长什么样

先看 `dig`。

`dig` 是 DNS 的"显微镜"，它把应答里的每一段都摊开给你看。

```text
$ dig www.example.com

;; QUESTION SECTION:
;www.example.com.               IN      A

;; ANSWER SECTION:
www.example.com.        3600    IN      CNAME   example.com.
example.com.            3600    IN      A       93.184.216.34

;; Query time: 3 msec
;; SERVER: 202.96.128.86#53(202.96.128.86)
```

（简化示意，实际输出还包含 OPT、EDNS、SERVER 段的更多字段。）

三行里全是考点。

`3600` 是 TTL，单位秒。

`CNAME` 说明 `www` 只是个别名，真正的名字是 `example.com`。

解析一条 CNAME，客户端要再查一次目标名字，所以是两条记录。

想知道"到底是谁在跑腿"，加 `+trace`。

```text
$ dig +trace www.example.com

.                       518400  IN  NS  a.root-servers.net.
com.                    172800  IN  NS  a.gtld-servers.net.
example.com.            172800  IN  NS  a.iana-servers.net.
www.example.com.        3600    IN  A   93.184.216.34
```

（简化示意。）

四行就是四次迭代：根 → com → example.com → 答案。

`dig` 自己扮演了"本地 DNS"的角色，一路问过去，正好把第 5 节说的迭代过程打印出来了。

查邮件记录用 `dig MX`。

```text
$ dig MX qq.com

;; ANSWER SECTION:
qq.com.                 600     IN      MX      10 mx3.qq.com.
qq.com.                 600     IN      MX      20 mx2.qq.com.
```

（简化示意。）

数字 10、20 是优先级，越小越先试。

这就是"一封信怎么找到收件服务器"的答案：先查 MX，按优先级从低到高试。

Windows 上用 `nslookup`，会看到一句"非权威应答"。

```text
> www.example.com
服务器:  UnKnown
Address:  202.96.128.86

非权威应答:
名称:    www.example.com
Address:  93.184.216.34
```

（简化示意。）

"非权威"的意思是：这个答案是从缓存里拿的，不是权威服务器现给的。

一个词就把"缓存"这件事暴露了。

FTP 可以用命令行看。

```text
$ ftp ftp.example.com
220 Welcome to example FTP service.
Name: anonymous
331 Please specify the password.
Password:
230 Login successful.
ftp> passive
Passive mode on.
ftp> ls
227 Entering Passive Mode (93,184,216,34,200,10).
150 Here comes the directory listing.
226 Directory send OK.
ftp> quit
221 Goodbye.
```

（简化示意。）

这几行把"两条连接"演示完了。

`230` 之后控制连接就一直开着。

`ls` 的时候才临时开一条数据连接：`227` 里那六个数就是 IP 加端口，`200×256+10 = 51210`。

列完目录，`226` 表示数据连接关了，控制连接还在。

想验证"主动模式会卡"，在 NAT 后面的机器上强制用 PORT 就行。

```text
ftp> active
Active mode on.
ftp> ls
500 Illegal PORT command.
```

（简化示意，失败原因取决于防火墙策略，可能是超时而不是报错。）

防火墙看到服务器要从 20 端口连进来的那一刻，就把包扔了。

邮件的三个协议也可以用命令行看。

```text
$ openssl s_client -connect imap.example.com:143 -starttls imap
...
a1 LOGIN user password
a1 OK LOGIN completed
a2 SELECT INBOX
* 12 EXISTS
a2 OK [READ-WRITE] SELECT completed
```

（简化示意。）

`143` 是 IMAP 的明文端口，`-starttls imap` 把它升级成加密。

POP3 的对话更像"取完就走"。

```text
$ openssl s_client -connect pop.example.com:110 -starttls pop3
+OK POP3 ready
USER user
+OK
PASS password
+OK Logged in.
LIST
+OK 3 messages:
1 1200
2 3400
3 900
RETR 1
+OK 1200 octets
```

（简化示意。）

`RETR` 之后如果你没配"在服务器保留副本"，客户端退出时服务器就把这封信删了。

这就是 POP3 与 IMAP 最本质的差别：状态在谁那边。

## 8. FTP：为什么用两条连接

文件传输协议（File Transfer Protocol，FTP）是 1971 年的东西，比 TCP/IP 还老。

它的设计里有一条今天看来很怪：**传一个文件要用两条 TCP 连接**。

```text
控制连接：服务器 21 端口，客户端随机端口
数据连接：每次传文件时临时建立，传完就关
```

控制连接负责说话：

```text
USER / PASS      登录
CWD / PWD        切目录、看当前目录
TYPE A / TYPE I  文本模式 / 二进制模式
PASV / PORT      选数据连接的方向
RETR / STOR      下载 / 上传
LIST / NLST      列目录
REST n           从第 n 字节接着传
ABOR             中止正在进行的传输
QUIT             退出
```

数据连接负责搬字节：文件内容、目录列表，都走它。

数据连接内部还有三种传输模式，408 不考，但看 RFC 会遇到：

```text
MODE S  流模式，把数据当连续字节流，TCP 正好干这个，默认
MODE B  块模式，每个块带一个 3 字节的块头（块大小 + 描述符）
MODE C  压缩模式，用行程编码压一下（早就不用了）
```

流模式是事实标准，因为 TCP 已经是字节流了，再切块属于重复劳动。

控制连接在整个会话期间一直开着。

数据连接是一次性的：传一个文件开一条，传完关掉，再传再开。

为什么要这么分？

第一，命令和数据要能同时流动。

传一个 4 GB 的镜像，中途你想按 Ctrl+C 中止，这个"中止"必须能立刻送到服务器。

如果命令和数据挤在一条连接上，数据把带宽占满，你的 ABOR 就排在那 4 GB 后面，等你传完它才生效。

这在 408 里有个正式说法：**带外控制（out-of-band control）**。

第二，两种连接的寿命本来就不一样。

控制连接要活整个会话，数据连接是"用完即弃"。

硬塞进一条连接，就得在字节流里分隔"这是命令"和"这是文件内容"，协议会变复杂，还容易出错。

第三，数据连接可以换参数。

传文本用 ASCII 模式，传可执行文件用二进制模式，换一次类型只要在控制连接上发一句 `TYPE I`，不用重连。

第四，就是断点续传。

```text
REST 1048576     从第 1 MB 处接着传
RETR big.iso     开始下载
```

这两条命令都在控制连接上，数据连接才负责从那 1 MB 的位置往后搬。

断点续传的前提是"能定位"，而定位信息必须走在一条不会被数据淹没的连接上。

代价也很实在：两条连接意味着两组端口、两次握手、两套防火墙规则。

NAT 出现之后，这个代价变成了真问题，于是就有了主动和被动两种模式。

FTP 还是**有状态**的协议。

服务器要记住：你登录成谁了、当前在哪个目录、传输类型是什么、上一次 REST 到哪了。

这和 HTTP 的无状态正好相反，第 22 篇会拿它做对照。

## 9. 主动 PORT 与被动 PASV

两条连接里，控制连接的方向是固定的：客户端主动连服务器的 21 端口。

不定的是数据连接：谁连谁。

主动模式（PORT，也叫 Standard 模式）：

```text
客户端：我在 50000 端口等着，你来连我
        PORT 192,168,1,10,195,80
        （195×256 + 80 = 50000）

服务器：好，我从我的 20 端口连你
        源端口 20，目的端口 50000
```

（简化示意。）

服务器用 20 端口作为数据连接的源端口，"FTP 数据端口是 20"这个结论只在主动模式成立。

被动模式（PASV）：

```text
客户端：你在哪个端口等我？
        PASV

服务器：227 Entering Passive Mode (10,0,0,5,200,10)
        （200×256 + 10 = 51210）

客户端：主动连服务器的 51210 端口
```

（简化示意。）

两种模式的区别，一句话：

```text
主动模式：服务器发起数据连接（源端口 20）
被动模式：客户端发起数据连接（服务器端口随机）
```

为什么要有被动模式？

因为 NAT。

家里那台路由器给电脑分配的是 `192.168.1.10`，这个地址在公网上不存在。

主动模式下，客户端告诉服务器"你来连 192.168.1.10:50000"，服务器照做，包到了路由器上，路由器不知道该转给谁，直接扔掉。

客户端就只能干等，最后超时。

被动模式把方向反过来了：客户端主动往外连，NAT 表里本来就有这条出去的记录，回包能顺利进来。

所以今天几乎所有 FTP 客户端默认都用 PASV。

被动模式也有代价：服务器要开一大段高端口给客户端连，防火墙得放行，安全性差一些。

还有一个坑：**PASV 返回的是服务器的 IP，如果服务器自己也在 NAT 后面，返回的可能是个内网地址**，客户端连不上。

这时候要用 ` PASV` 的扩展，让服务器返回公网地址。

顺便区分三个名字：

```text
FTP    明文，21 控制 + 20 数据
FTPS   FTP over TLS，还是 FTP 的命令，只是套了 TLS
SFTP   SSH File Transfer Protocol，走 22 端口，跟 FTP 没有关系
```

408 只考第一条，但选择题里偶尔拿 SFTP 来混淆"FTP 的加密版本"这个说法。

严格说，SFTP 不是 FTP 的加密版，是另一套协议。

## 10. 电子邮件：三个协议与一条投递路径

一封邮件的生命周期，要经过三个角色、三个协议。

角色：

```text
MUA（Mail User Agent）    你用的邮件客户端，写信、读信
MTA（Mail Transfer Agent） 邮局，负责在服务器之间转信
MDA（Mail Delivery Agent） 投递员，负责把信塞进某个用户的邮箱
```

协议：

```text
SMTP   25    发信，推（push）
POP3   110   收信，拉（pull），默认下载后删除
IMAP   143   收信，拉（pull），服务器保留
```

投递路径：

```text
① 写信             MUA
② 提交             MUA ──SMTP──► 发送方 MTA
③ 找收件服务器      发送方 MTA 查 DNS 的 MX 记录
④ 转信             发送方 MTA ──SMTP──► 收件方 MTA（可能经多跳中继）
⑤ 投递             收件方 MTA ──► MDA ──► 用户邮箱
⑥ 取信             收件人 MUA ──POP3 或 IMAP──► 邮箱
```

（简化示意。）

关键在 ③：**信不是靠"收件人地址"直接送到对方主机的，而是靠 DNS 的 MX 记录找到对方的邮件服务器**。

`user@example.com` 里的 `example.com` 只是域名，SMTP 先查它的 MX，按优先级从低到高试。

这就是为什么把 MX 记录配错，邮件会全丢。

SMTP 有个硬伤：它只认 7 位 ASCII。

1980 年代大家都用英文，够用。

后来要传中文、传图片、传压缩包，就不够了。

MIME（Multipurpose Internet Mail Extensions）解决这个问题。

MIME 不是传输协议，是对 SMTP 的扩展，加了三样东西：

```text
Content-Type              这段数据是什么（text/plain; charset=utf-8，image/png）
Content-Transfer-Encoding 这段数据怎么编成 ASCII（base64、quoted-printable）
Content-Disposition       这段数据是显示在正文里，还是当附件下载
```

所以"一封带图片的邮件"在 SMTP 眼里，就是一封纯 ASCII 的信，里面有一大段 base64。

第 6 节那道 300 KB 变 400 KB 的题，算的就是这个膨胀。

POP3 和 IMAP 的差别，是 408 最爱考的一处。

```text
POP3：把信下载到本地，默认从服务器删除
      邮件状态在客户端，换个设备看不到
      文件夹在本地
      协议简单，省服务器空间

IMAP：邮件留在服务器，客户端只是"看"
      邮件状态在服务器，手机、电脑看到的是同一份
      文件夹在服务器，支持"只取正文不取附件"
      协议复杂，吃服务器存储
```

一句话记法：**POP3 是"取走"，IMAP 是"遥控"**。

端口一起背：110 是 POP3，143 是 IMAP，25 是 SMTP。

加密版本分别是 995、993、465/587，408 一般不深究，但知道有这回事不吃亏。

## 11. 容易混淆的点

第一组：递归与迭代。

看的是"谁负责跑完全程"，不是报文数。

主机问本地 DNS 是递归，本地 DNS 问根是迭代。

第二组：权威服务器与本地服务器。

权威服务器存着真的记录，答案带权威性。

本地服务器不存权威记录，只做代理和缓存，`nslookup` 里那句"非权威应答"说的就是它。

第三组：FTP 的两个端口。

21 是控制连接，全程都在。

20 是主动模式下的数据连接源端口；被动模式下数据连接用的是服务器随机端口。

第四组：主动模式谁发起。

主动：服务器发起（所以叫"服务器主动"）。

被动：客户端发起。

第五组：SMTP 与 POP3 的方向。

SMTP 只能推，不能拉。

POP3 和 IMAP 只能拉，不能推。

第六组：MIME 是什么。

它不是邮件传输协议，是 SMTP 的内容扩展。

"用 MIME 发邮件"这个说法是错的，MIME 只负责编码和标注类型。

第七组：DNS 用 UDP 还是 TCP。

正常查询用 UDP 53。

区域传送（主从服务器同步）用 TCP 53。

应答超过 512 字节时，要么截断后重试 TCP，要么用 EDNS0 扩展。

第八组：P2P 里没有服务器。

BitTorrent 有 tracker，但 tracker 只做索引，不传文件内容。

所以它是"混合结构"，不是纯 P2P。

## 12. 把四件事收成一张图

把这一篇的四个协议放在一张表里，考前扫一眼就够。

```text
你做的事     协议        端口        传输层   谁先发起        状态在哪
查域名       DNS         53          UDP      客户端          本地 DNS 缓存
传文件       FTP         21 控制     TCP      客户端          服务器
                         20 数据     TCP      看模式
发邮件       SMTP        25          TCP      客户端（推）    服务器队列
收邮件       POP3        110         TCP      客户端（拉）    客户端
             IMAP        143         TCP      客户端（拉）    服务器
看网页       HTTP        80          TCP      客户端          靠 Cookie
             HTTPS       443         TCP      客户端          靠 Cookie
```

（简化示意，端口是默认值，都可以改。）

再往上看一层，这三个协议有个共同的前提。

```text
DNS 给 FTP 提供"服务器主机名 → IP"
DNS 给邮件提供 MX 记录（找收件方的 MTA）
DNS 给 HTTP 提供"网站域名 → IP"
```

**DNS 是所有应用层协议的地基**。

它挂了，别的协议全都动不了，但 IP 直连还能通。

这也是排查故障时的第一分叉：域名不通但 IP 通，问题在 DNS。

四个协议还有第二个共同点：它们全是 C/S 结构。

P2P 只在文件共享这一块是例外，而 408 里 P2P 基本只考概念。

第三个共同点：它们的"可靠性"都建立在 TCP 上，只有 DNS 图快用了 UDP。

DNS 用 UDP 的理由很直接：一次查询就一问一答，两个报文，用 TCP 要先握三次手，开销比查一次还大。

代价是丢包要靠自己重传（客户端等超时再问一遍）。

## 13. 小结 + 下一篇

这一篇的五个结论：

```text
应用层定语义，端口定进程，C/S 与 P2P 是两种形状
DNS 四类服务器：根、顶级、权威、本地（本地不属于层次结构）
递归 vs 迭代 = 谁跑腿；一次无缓存解析 8 个 UDP 报文
FTP 两条连接：21 控制全程在，20 数据只在主动模式；命令与数据分离
邮件三协议：SMTP 25 推、POP3 110 取走、IMAP 143 遥控；MIME 只管编码
```

一个必须带走的反直觉点：

```text
"递归"和"迭代"说的是本地 DNS 替不替客户端跑腿，
不是查询报文走几次。
```
