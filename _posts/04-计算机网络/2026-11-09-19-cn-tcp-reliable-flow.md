一个常见的问题：

```text
"TCP 是可靠传输，那它保证不丢包吗？"
```

不保证。

TCP 跑在会丢包、会乱序、会重复的 IP 之上，它自己也在丢包。

它保证的是另外四件事：

```text
不丢（最终）：丢了的会被重传补上
不乱：接收方按序号重新排好，交给应用的是有序字节流
不重：重复的报文段会被识别并丢弃
不错：校验和不对的报文段直接丢掉，等重传
```

注意"最终"两个字。

过程中间，数据照样丢，照样乱，只是 TCP 会一直修，直到修好或者放弃。

这一篇拆的就是这个"修"的过程，以及发送方怎么知道自己能发多快。

## 1. "可靠"保证的是"最终按序交付"

把"可靠"这个词拆开，其实是三个独立的问题。

```text
问题一：怎么知道对方收到了？        → 确认（ACK）
问题二：多久没收到就该重发？        → 超时（RTO）
问题三：一次能发多少不被淹没？      → 窗口（rwnd）
```

三个问题对应三个机制，缺一不可。

只有确认没有超时：ACK 丢了，发送方永远等下去，连接卡死。

只有超时没有确认：每次都要等到超时才重发，吞吐量惨不忍睹。

只有重传没有窗口：接收方缓冲区爆掉，重传得越多丢得越多。

**这就是那个反直觉的点：**

> TCP 的"可靠"不是因为它不丢包，而是因为它有三件套：确认、超时、重传。它保证的是"最终按序交付"，中间过程照样丢。

换个说法：

```text
TCP 不是一条不漏水的管子。
TCP 是一个会一直补漏的水管工。
```

补漏有代价。

每一次重传都意味着：

```text
多占用一次带宽
多等一个 RTT（最坏情况）
多消耗一份发送方的缓冲区
```

所以可靠性和吞吐量之间永远在权衡。

这个权衡的参数就是 RTO 和窗口。

## 2. 序号与确认号：按字节编号，累积确认

上一篇讲过基本规则，这里只补可靠性需要的那部分。

TCP 把整个字节流从头到尾编号。

```text
应用写了 10000 字节
TCP 按 MSS 切成段（比如 MSS=1000）
第 1 段  seq=1,     长度 1000   → 占 1–1000
第 2 段  seq=1001,  长度 1000   → 占 1001–2000
第 3 段  seq=2001,  长度 1000   → 占 2001–3000
```

确认号是累积的。

```text
接收方回 ack=2001
含义：1 到 2000 全部收到，请从 2001 开始。
```

累积确认有一个巨大的好处和一个不小的坏处。

好处：ACK 可以合并。

```text
收到第 1 段，回 ack=1001
收到第 2 段，回 ack=2001
来不及回第 3 段，第 4 段又到了
→ 直接回 ack=4001，一个 ACK 覆盖两段
```

坏处：一个洞会挡住后面所有数据。

```text
收到 1–1000      → ack=1001
收到 2001–3000   → ack 还是 1001（因为 1001–2000 没到）
收到 3001–4000   → ack 还是 1001
```

发送方看到的是三个一模一样的 `ack=1001`。

这就是**重复 ACK（duplicate ACK）**，也是第 6 节快速重传的触发条件。

接收方这边，收到的乱序数据不会丢，先放进接收缓冲区，等洞补上再一起交给应用。

```text
接收缓冲区
+--------+--------+--------+--------+
| 1–1000 |  ??    | 2001–  | 3001–  |
|  已交   |  缺    | 待交付  | 待交付  |
+--------+--------+--------+--------+
                    ▲
              ack 只能指到这里：1001
```

接收方的缓冲区管理，比"收下就行"要复杂一点。

```text
接收缓冲区（按字节编号）
+----------+-----------+----------+----------+
| 1001–2000| 2001–3000 | 3001–4000| 4001–5000|
|  已到     |   缺      |  已到     |  已到     |
+----------+-----------+----------+----------+
                ▲
          ack 只能指到 2001
```

已到的乱序数据不丢，先进缓冲区。

应用读数据时只能读到连续的部分：读到 2000 就会阻塞，因为 2001 还没到。

这就带来一个实际问题：缓冲区会被乱序数据占满。

```text
缓冲 4 KB，乱序收到 3001–7000 共 4 KB，2001–3000 一直没到
→ 缓冲区满了，但应用一个字也读不到
→ 窗口被迫降到 0
→ 发送方以为接收方卡住了
```

SACK 能缓解这种情况：发送方知道缺的是哪一段，可以只重传那一段。

但缓冲区被占满这件事，还得靠接收方自己限制乱序队列的长度（Linux 有上限，超过就丢）。

## 3. 超时重传：RTO 怎么算

RTO（Retransmission Timeout）是发送方等 ACK 的耐心值。

设太小：ACK 还在路上就重传了，网络上全是重复报文。

设太大：真丢包时，发送方干等，吞吐量掉到底。

所以 RTO 必须**跟着网络的真实 RTT 走**。

最朴素的想法是"RTO = 平均 RTT 的 2 倍"，但不够。

因为网络 RTT 的波动本身也是信息：波动大的链路，RTO 要留更多余量。

Jacobson 的算法同时跟踪两个量。

```text
SRTT    平滑的 RTT 估计（加权平均）
RTTVAR  RTT 的偏差估计（平均绝对偏差）
```

公式，RFC 6298 用的版本：

```text
第一次测量 R 时：
    SRTT   = R
    RTTVAR = R / 2
    RTO    = SRTT + 4 × RTTVAR

之后每来一个样本 R'：
    RTTVAR = (1 - β) × RTTVAR + β × |SRTT - R'|      β = 1/4
    SRTT   = (1 - α) × SRTT   + α × R'               α = 1/8
    RTO    = SRTT + 4 × RTTVAR
```

为什么 α 和 β 这么小？

因为要"平滑"。

α = 1/8 意味着新样本只占 12.5% 的权重，一个突发的 RTT 抖动不会让 RTO 立刻跳起来。

β = 1/4 比 α 大，因为偏差要跟得更紧一些：网络一旦开始抖，RTO 得赶快放大。

系数 4 也有讲究。

在 RTT 近似正态分布的假设下，`SRTT + 4×RTTVAR` 大约覆盖 99% 的情况——重传得太早的概率足够低。

算一遍。

```text
初始测量 RTT = 100 ms
    SRTT   = 100
    RTTVAR = 50
    RTO    = 100 + 4×50 = 300 ms

第二个样本 RTT = 140 ms
    RTTVAR = 0.75×50 + 0.25×|100-140|
           = 37.5 + 0.25×40
           = 37.5 + 10
           = 47.5 ms
    SRTT   = 0.875×100 + 0.125×140
           = 87.5 + 17.5
           = 105 ms
    RTO    = 105 + 4×47.5
           = 105 + 190
           = 295 ms

第三个样本 RTT = 120 ms
    RTTVAR = 0.75×47.5 + 0.25×|105-120|
           = 35.625 + 3.75
           = 39.375 ms
    SRTT   = 0.875×105 + 0.125×120
           = 91.875 + 15
           = 106.875 ms
    RTO    = 106.875 + 4×39.375
           = 106.875 + 157.5
           = 264.375 ms  ≈ 264 ms
```

观察这三步：

```text
RTT 从 100 涨到 140，RTO 反而从 300 降到 295
原因：初始的 RTTVAR=50 是个保守的猜测，真实偏差只有 40，所以偏差估计下调
```

这就是"平滑"的实际效果：一开始宁可保守，样本多了就贴近真实。

还有两条实用规则。

```text
RTO 有下限：RFC 6298 建议 1 秒，Linux 实际用 200 ms（TCP_RTO_MIN）
超时后 RTO 加倍：1 → 2 → 4 → 8 …（指数退避），上限 60 秒
```

超时后加倍这件事很重要。

它意味着"连续丢包"时，TCP 会越来越耐心，而不是傻等一个固定值猛发。

## 4. Karn 算法：重传过的样本不能用

这里有一个隐蔽的坑。

```text
t=0     发送段 A，启动定时器
t=100   没收到 ACK，超时，重传 A
t=110   收到 ACK
```

这个 ACK 是对第一次发送的，还是对重传的？

分不清。

如果按第一次算，RTT = 110 ms。

如果按重传算，RTT = 10 ms。

两个数差了十倍，而发送方没有任何办法区分。

这就是**重传二义性（retransmission ambiguity）**。

Karn 算法的处理方式极其简单粗暴：

```text
只要这个段被重传过，它的 RTT 样本一律丢弃。
```

代价是：丢包多的链路上，RTT 样本变少，RTO 更新变慢。

补偿办法是第二条规则：

```text
发生一次超时，RTO 直接翻倍，不用等新样本。
```

这两条合起来，就是"Karn 算法"。

后来的实现用**时间戳选项（TCP Timestamps）**绕过了这个限制：

每个报文段带一个发送时间戳，ACK 里原样带回（echo），发送方一减就知道准确 RTT，不存在二义性。

所以现代 Linux 默认开着 `net.ipv4.tcp_timestamps = 1`，Karn 算法的"丢弃样本"规则实际上很少触发。

但 408 考的是经典版本，答案要写 Karn。

## 5. 快速重传与 SACK

超时重传的问题是：等太久。

一个 RTT 只有 10 ms 的连接，RTO 可能是 200 ms。

丢一个包，就要卡 200 ms。

有没有更快的信号？

有，就是重复 ACK。

```text
发送方发了 1、2、3、4、5 五段
段 2 丢了

接收方收到 1  → 回 ack=1001（期望 1001，即段 2）
接收方收到 3  → 回 ack=1001（dup 1）
接收方收到 4  → 回 ack=1001（dup 2）
接收方收到 5  → 回 ack=1001（dup 3）
```

发送方收到三个重复的 `ack=1001`，就能推断：段 2 大概率丢了，但后面的段都到了。

于是**不等超时，立刻重传段 2**。

这就是**快速重传（fast retransmit）**。

```text
触发条件：收到 3 个重复 ACK
动作：立刻重传那个 ACK 指向的段
```

为什么是 3 个而不是 1 个？

因为 1 到 2 个重复 ACK 有可能只是**乱序**。

```text
发送 1、2、3、4、5
网络把 2 和 3 的顺序颠倒了
接收方收到 1、3、2、4、5
→ 收到 3 时回了一个 ack=1001（dup 1）
→ 收到 2 后立刻回 ack=2001，然后 4、5 正常
```

只出现一个重复 ACK，不是丢包。

三个重复 ACK 意味着"连续三个段都到了，中间那个还没到"，丢包的概率就非常高了。

这是一个用很小的代价换取很小误判率的阈值。

快速重传解决了"等太久"，但还有一个问题：发送方不知道只丢了一个还是丢了几个。

```text
1、2、3、4、5、6、7 发出去
2 和 5 都丢了
接收方只会一直回 ack=1001
发送方重传 2，收到 ack=6001
然后才发现 5 也丢了，再重传 5
```

**SACK（Selective ACK，选择确认）**解决这个问题。

它在 TCP 选项里带上"我已经收到了哪些不连续的块"。

```text
没有 SACK：ack=1001
有 SACK：  ack=1001，SACK = [3001–4000], [6001–7000]
```

发送方一看就知道：1001–2000 和 5001–6000 缺，其余都收到了。

于是两个段可以一起重传，一个 RTT 解决。

SACK 在握手时用选项协商，协商成功才启用。

快速重传和拥塞控制是同一套机制的两个面。

```text
三个重复 ACK
  ├─ 可靠传输视角：立刻重传丢掉的那一段
  └─ 拥塞控制视角：网络还有余量，只减半
```

一个信号，两个用途。

这也是为什么"三个重复 ACK"既是可靠传输的考点，也是拥塞控制的考点。

阈值取 3，还有一个概率上的解释。

```text
1 个重复 ACK：乱序的概率不低
2 个重复 ACK：连续两次乱序，已经少见
3 个重复 ACK：连续三次乱序，概率极低
```

真丢包时，后面每到一个段就产生一个重复 ACK，很容易超过 3 个。

所以 3 是"误判率"和"反应速度"之间的折中。

如果链路本身乱序严重（比如多路径负载均衡），3 这个阈值就会误判。

表现是"明明没丢包，却频繁快重传"，白烧带宽。

这也是为什么 SACK 在有乱序的链路上特别有价值。

再补一句 SACK 的边界。

```text
SACK 块最多 4 个
每个块 8 字节（左边界 32 位 + 右边界 32 位）
选项总长不能超过 40 字节
```

所以它描述的是"最多 4 段不连续的已收数据"。

超过 4 段，就只能描述最重要的那几段。

## 6. 滑动窗口：单位是字节

前面讲的都是"怎么补"，现在讲"一次能发多少"。

如果 TCP 是停等协议（发一个等一个），吞吐量会被 RTT 锁死。

```text
一个段 1460 字节，RTT 50 ms
吞吐量 = 1460 × 8 / 0.05 = 233,600 bps ≈ 234 kbps
```

一条 1 Gbps 的链路，只能跑 234 kbps。

所以要连续发。

连续发就需要一个"允许发送的范围"，这就是**滑动窗口（sliding window）**。

窗口把发送缓冲区切成四段：

```text
发送缓冲区（按字节编号）
|<--------- 已发送并确认 -------->|<--- 已发未确认 --->|<--- 可发未发 --->|<-- 不可发 -->|
1                              3001                5001               7001
                                |<----------- 发送窗口 = 4000 字节 ----------->|
```

四个指针：

```text
左沿：最早一个没被确认的字节
右沿：左沿 + 窗口大小
窗口内：已发未确认 + 可发未发
```

收到确认，左沿右移，窗口整体右滑，新的字节进入"可发"区域。

```text
收到 ack=4001，窗口 4000
→ 左沿从 3001 移到 4001
→ 右沿从 7000 移到 8000
→ 序号 7001–8000 变成可发
```

**这里最容易错的一点：窗口的单位是字节，不是报文段。**

```text
窗口 = 4000 字节，MSS = 1000
→ 可以发 4 个满段
→ 也可以发 1 个 4000 字节的大段（如果 MSS 允许）
→ 还可以发 4000 个 1 字节的段（合法但愚蠢）
```

408 的题里，"窗口为 4"这种说法要看上下文：如果写"4 个报文段"就是段数，如果写"4000 字节"就是字节数。

真题一般给字节数。

## 7. 发送窗口 = min(rwnd, cwnd)

发送窗口由两个东西共同决定。

```text
rwnd（接收窗口）  接收方还有多少缓冲区空间 —— 怕淹死对方
cwnd（拥塞窗口）  网络还能承受多少 —— 怕压垮网络
```

实际能发多少，取两者较小值：

```text
发送窗口 = min(rwnd, cwnd)
```

两个约束的来源完全不同：

```text
rwnd 来自接收方的通告，是端到端的，跟路径无关
cwnd 来自发送方自己对网络的估计，跟丢包和 RTT 有关
```

举例：

```text
rwnd = 64 KB，cwnd = 10 × MSS = 14600 B
→ 发送窗口 = 14600 B，瓶颈在网络

rwnd = 8 KB，cwnd = 10 × MSS = 14600 B
→ 发送窗口 = 8192 B，瓶颈在接收方
```

这两个数在 `ss -ti` 里都能看到。

cwnd 是"网络让不让我发"，rwnd 是"对方收不收得下"。

**流量控制管的是后者，拥塞控制管的是前者。**

这句话是第 20 篇的入口，也是 408 最爱设的陷阱：题目说"接收方缓冲区满"，那是 rwnd 的问题；题目说"网络出现拥塞"，那是 cwnd 的问题。

### 7.1 窗口够不够大：从 BDP 看吞吐

窗口不只影响"发多快"，它直接决定"能吃多少带宽"。

```text
吞吐量 ≤ 窗口大小 / RTT
```

一条 RTT 100 ms、带宽 100 Mbit/s 的链路：

```text
要填满它，需要 100 Mbit/s × 0.1 s = 10 Mbit = 1.25 MB 的窗口
```

如果窗口只有 64 KB：

```text
64 KB / 0.1 s = 640 KB/s ≈ 5.1 Mbit/s
```

只用到 5%。

**这就是"长肥管道"问题：带宽 × 时延很大，窗口不够就吃不满。**

也是 TCP 窗口扩展选项（window scaling）存在的原因：

```text
首部里的窗口字段只有 16 位，最大 65535 B ≈ 64 KB。
窗口扩展用一个移位因子，把它放大到 2^30 量级。
```

408 的延伸考法：

```text
给带宽、RTT、窗口，问能不能打满；或者反求需要多大的窗口。
```

**记住这个换算：窗口（bit）≥ 带宽 × RTT。**

## 8. 流量控制：rwnd 的来回

接收方的缓冲区是有限的。

如果发送方发得比应用读得快，缓冲区就满了，新到的数据只能丢。

丢了的还得重传，越重传越堵。

流量控制就是让接收方主动告诉发送方："我还能收多少。"

机制简单到只有一句话：

```text
每个 ACK 报文里都带一个窗口字段 rwnd
rwnd = 接收缓冲区总大小 - 已收到但还没被应用读走的字节数
```

走一遍：

```text
接收缓冲区 4096 字节

t=0   应用还没读，缓冲区空
      B 通告 rwnd = 4096

t=1   A 发了 2000 字节，B 收到，应用还没读
      B 通告 rwnd = 4096 - 2000 = 2096

t=2   A 又发了 2096 字节，B 收到，应用还没读
      B 通告 rwnd = 0     ← 零窗口

t=3   应用读了 3000 字节
      B 通告 rwnd = 3000  ← 窗口更新
```

注意 t=3 这一行。

接收方不能只在 ACK 里捎带窗口更新，因为此时可能没有数据要确认。

所以 TCP 允许发一个**纯窗口更新报文**（不带数据、不带新确认，只改窗口字段）。

这个报文很容易被中间设备当成"重复 ACK"丢掉，所以实际实现要小心。

还有一条规则：**窗口只能变大，不能缩小（右沿不能左移）。**

```text
先通告 rwnd = 4000，后通告 rwnd = 2000
→ 发送方已经按 4000 发了，缩窗口会造成混乱
→ 实现上：右沿保持不变，左沿照常前进
```

这条规则在 408 里出过判断题。

窗口更新不是只有一种触发方式。

```text
1. 收到数据时，在 ACK 里捎带新窗口
2. 应用读走数据、缓冲区腾出空间时，主动发窗口更新
3. 窗口从 0 变成非 0 时，必须发（否则发送方永远不知道）
```

第三种最关键。

因为 rwnd = 0 之后发送方已经停了，不会再发数据来"触发" ACK。

接收方不主动通告，双方就死锁。

还有一个细节：窗口更新报文很容易丢。

```text
B 通告 rwnd = 4096
A 没收到，还以为是 0
→ A 继续等
→ B 以为 A 会发，继续等
```

纯窗口更新报文不带数据，也不带新确认，老式设备可能当成"重复 ACK"过滤掉。

所以协议要求两头都做：接收方发更新，发送方用坚持定时器兜底。

再说一个数值上的感觉。

```text
接收缓冲区 64 KB，RTT 50 ms
窗口打满时的吞吐 = 64 KB / 0.05 s = 1.28 MB/s ≈ 10 Mbps
```

想让这条连接跑满 100 Mbps，窗口至少要 640 KB。

而窗口字段只有 16 位，最大 65535 字节。

这就是窗口缩放选项存在的理由，也是"长肥管道"这个说法的来历。

## 9. 零窗口与坚持定时器

rwnd = 0 之后，发送方必须停。

但如果就此睡死，会有一个死锁风险：

```text
B 通告 rwnd = 0
A 停止发送，等 B 的窗口更新
B 的应用读了数据，缓冲区空了
B 发窗口更新报文 rwnd = 4096
这个报文丢了
→ A 还在等，B 以为 A 会发
→ 双方僵住
```

解决办法是**坚持定时器（persistence timer）**。

```text
收到零窗口通告后，启动坚持定时器
超时后发一个零窗口探测报文（通常只带 1 字节数据）
接收方必须回一个 ACK，里面带上当前窗口
→ 窗口开了就继续发，还是 0 就重新计时
```

探测的间隔是指数退避的：

```text
1s, 2s, 4s, 8s, 16s, 32s, 60s, 60s, 60s ...
```

上限 60 秒，之后一直每 60 秒探一次。

为什么要退避？

因为如果对端真的卡死了，每秒探一次纯属浪费。

60 秒的间隔也解释了另一个现象：一个被零窗口卡住的连接，可能要等一两分钟才恢复。

坚持定时器和重传定时器是两回事：

```text
重传定时器  管"发出去的数据没被确认"
坚持定时器  管"窗口是 0，我该不该问一句"
```

408 有一道经典题就是问：零窗口之后，发送方靠什么恢复？答案：坚持定时器。

## 10. 糊涂窗口综合症与 Nagle

窗口机制有一个副作用：小窗口。

```text
接收方缓冲区只剩 40 字节
它老老实实通告 rwnd = 40
发送方一看能发，赶紧发 40 字节
接收方应用读走 40 字节，通告 rwnd = 40
发送方再发 40 字节
……
每 40 字节一个报文，首部 40 字节，效率 50%
```

这就是**糊涂窗口综合症（Silly Window Syndrome，SWS）**。

两头各有一个解法。

接收方侧（Clark 算法）：

```text
不要通告小窗口。
窗口小于 min(MSS, 缓冲区一半) 时，直接通告 0。
等应用读够了、能腾出一个像样的窗口，再通告。
```

发送方侧（Nagle 算法）：

```text
只要还有"已发未确认"的小段，就不要发新的小段。
先把小数据攒起来，等 ACK 回来或者攒够一个 MSS 再发。
```

Nagle 的效果：把大量小包合并，减少首部开销。

Nagle 的代价：交互式应用会变慢。

```text
客户端发一个 10 字节的按键
Nagle 说：等 ACK 回来再发下一个
结果每个按键都要等一个 RTT
```

更糟的组合是 Nagle + 延迟 ACK。

```text
延迟 ACK：接收方等 40–200 ms 再回 ACK，期望能捎带数据
Nagle：没收到 ACK 就不发下一段
→ 双方各等各的，一次交互卡 40 ms
```

这就是很多游戏和远程终端要设 `TCP_NODELAY` 的原因：把 Nagle 关掉。

一句话总结这两个机制：

```text
SWS 治的是"窗口太小"，Nagle 治的是"报文太小"。
两个都在用延迟换效率。
```

Nagle 的规则可以写得很具体。

```text
if 还有已发未确认的数据 and 本次要发的数据 < MSS:
    攒着，等 ACK 回来再发
else:
    立刻发
```

两个后果。

```text
好处：小包被合并，首部开销大幅下降
坏处：最后一小段要等 ACK，多一个 RTT 的延迟
```

延迟 ACK 的规则同样具体。

```text
收到数据先不回，等 40–200 ms
这期间有数据要回，就捎带一起发
如果第二个满段到了，立刻回
```

两个机制撞在一起，就是经典的 40 ms 延迟。

```text
客户端：发一个小请求，要等 ACK 才能发下一个
服务器：收到请求，等 40 ms 看能不能捎带 ACK
结果：每个来回多 40 ms
```

关掉的办法：

```text
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &one, sizeof(one))
```

`TCP_NODELAY` 关的是 Nagle，不是延迟 ACK。

要关延迟 ACK 得用 `TCP_QUICKACK`，而且它只对下一次生效，得反复设。

两个选项经常被搞混。

实际项目里只设 `TCP_NODELAY` 就够了。

## 11. 容易混淆的点

**确认号是累积的，不是选择性的。**

`ack=2001` 不代表只收到 2000，而是 1–2000 全收到了。

**重复 ACK 不等于出错。**

1 到 2 个可能只是乱序，3 个才触发快速重传。

**重传定时器和坚持定时器不是一回事。**

前者等确认，后者等窗口。

**RTO 不是一个固定值。**

每个连接、每个时刻都在算。

**窗口单位是字节。**

但 408 题目有时候用"报文段个数"表示窗口，看清单位再动笔。

**接收窗口 rwnd 是接收方通告的，不是发送方算的。**

发送方算的那叫拥塞窗口 cwnd。

**超时后 RTO 会加倍，但 Karn 算法要求丢弃该段的 RTT 样本。**

两件事经常一起考。

## 12. 408 怎么考

这一节的题型：

```text
给序号、给窗口，问还能发多少字节
给 RTT 样本，问 RTO
问零窗口后怎么恢复
问快重传的触发条件
```

第一道，窗口计算，自拟。

```text
主机 A 向主机 B 发送数据，字节编号从 1 开始。
某时刻的状态：
  A 收到 B 的确认 ack = 3001，同时 B 通告 rwnd = 4000
  A 已经发出序号 3001–5000 共 2000 字节，尚未收到确认
  A 还有 5000 字节待发

问：
(1) A 当前的发送窗口范围是什么？大小多少？
(2) A 现在还能再发多少字节？序号范围？
(3) 随后 A 收到 ack = 4001，rwnd 仍为 4000，窗口变成什么？
(4) 若 B 通告 rwnd = 0，A 应该做什么？靠什么机制恢复？
(5) 若 A 待发的 5000 字节中只想发一个满段（MSS=1000），窗口允许吗？
```

解。

（1）窗口。

```text
左沿 = 3001
窗口大小 = 4000
右沿 = 3001 + 4000 - 1 = 7000

范围：3001 – 7000，共 4000 字节
```

（2）还能发多少。

```text
窗口内已发未确认：3001 – 5000，共 2000 字节
可发未发 = 4000 - 2000 = 2000 字节
序号范围：5001 – 7000
```

（3）收到 ack = 4001。

```text
左沿移到 4001
右沿 = 4001 + 4000 - 1 = 8000
窗口：4001 – 8000，共 4000 字节

已发未确认：4001 – 5000，共 1000 字节
还能发：4000 - 1000 = 3000 字节，序号 5001 – 8000
```

（4）零窗口。

```text
A 停止发送，启动坚持定时器
超时后发零窗口探测报文（1 字节）
B 回 ACK 并带上当前 rwnd
窗口开了就继续，仍是 0 就重新计时（1s,2s,4s,…上限 60s）
```

（5）发一个满段。

```text
MSS = 1000，可发窗口 2000 字节 ≥ 1000
→ 允许，发序号 5001–6000，发完后可发窗口剩 1000
```

第二道，RTO 计算，自拟。

```text
某连接第一次测得 RTT = 200 ms，之后第二次测得 RTT = 260 ms。

问：
(1) 第一次测量后的 SRTT、RTTVAR、RTO？
(2) 第二次测量后的 SRTT、RTTVAR、RTO？
(3) 若第二次测量后立刻发生超时，RTO 变成多少？
```

解。

（1）第一次。

```text
SRTT   = 200 ms
RTTVAR = 200 / 2 = 100 ms
RTO    = 200 + 4 × 100 = 600 ms
```

（2）第二次，R' = 260。

```text
RTTVAR = 0.75 × 100 + 0.25 × |200 - 260|
       = 75 + 0.25 × 60
       = 75 + 15
       = 90 ms

SRTT   = 0.875 × 200 + 0.125 × 260
       = 175 + 32.5
       = 207.5 ms

RTO    = 207.5 + 4 × 90
       = 207.5 + 360
       = 567.5 ms ≈ 568 ms
```

（3）超时后。

```text
RTO 指数退避：567.5 × 2 = 1135 ms
```

要提醒一句：如果这道题里那个段被重传过，按 Karn 算法这个 RTT 样本根本不进公式。

## 13. 真实网络里长什么样

先看单条连接的可靠传输状态。

```text
$ ss -tino state established '( dport = :443 )'
ESTAB 0 0 192.168.1.10:51234 93.184.216.34:443
     cubic wscale:7,7 rto:204 rtt:1.5/0.5 ato:40 mss:1448
     rcvmss:1448 advmss:1448 cwnd:10 bytes_sent:20480 bytes_acked:19032
     segs_out:120 segs_in:98 data_segs_out:40 retrans:0/3
```

（简化示意）

逐字段读：

```text
rto:204        当前 RTO 204 ms
rtt:1.5/0.5    SRTT 1.5 ms，RTTVAR 0.5 ms（注意：偏差是 RTTVAR 的一半表述）
retrans:0/3    当前重传 0 次，累计重传 3 次
bytes_sent     已发送字节
bytes_acked    已确认字节
```

`rtt:` 后面那两个数，是 SRTT 和 RTTVAR，单位都是毫秒。

但别指望拿这三个数手工对上。

`rto:204` 并不是简单的 `1.5 + 4×0.5 = 3.5`。

内核在算 RTO 时还夹着两个东西：

```text
下限：RTO 不小于 200 ms（TCP_RTO_MIN），所以 1.5 ms 的 RTT 也至少是 200 ms
粒度：定时器按 jiffies 走，结果会被向上取整
```

这正好解释了为什么低延迟链路上的 RTO 看起来"大得离谱"。

那不是算错了，是故意的：宁可晚一点重传，也不要天天误重传。

看全机的重传统计：

```text
$ netstat -s | grep -iE "retrans|timeout|dup"
    1203 segments retransmitted
    1203 retransmits
    8 fast retransmits
    2 timeouts
    512 duplicate ACKs received
    0 SACK retransmits
```

（简化示意）

三个数连起来看很有意思：

```text
fast retransmits 8  → 8 次靠重复 ACK 补的，代价约 1 个 RTT
timeouts 2          → 只有 2 次靠超时补的，代价是 RTO
两条加起来等于 retransmits，说明绝大多数丢包都被快重传接住了
```

如果 `timeouts` 明显偏大，说明丢包太严重，三个重复 ACK 都凑不齐——整窗丢了。

抓一次快速重传。

```text
$ tcpdump -i any -nn -S 'tcp port 443' -c 20
10:35:11.100001 IP 192.168.1.10.51234 > 93.184.216.34.443: Flags [.], seq 19033:20481, ack 1, length 1448
10:35:11.100002 IP 93.184.216.34.443 > 192.168.1.10.51234: Flags [.], ack 20481, win 501, length 0
10:35:11.100003 IP 93.184.216.34.443 > 192.168.1.10.51234: Flags [.], ack 20481, win 501, length 0
10:35:11.100004 IP 93.184.216.34.443 > 192.168.1.10.51234: Flags [.], ack 20481, win 501, length 0
10:35:11.100020 IP 192.168.1.10.51234 > 93.184.216.34.443: Flags [.], seq 20481:21929, length 1448
```

（简化示意）

后三行就是三个重复 ACK，ack 号一模一样。

Wireshark 会自动标出来：

```text
[tcp.analysis.duplicate_ack]  #1 / #2 / #3
[tcp.analysis.fast_retransmission]
[tcp.analysis.retransmission]
```

过滤表达式：

```text
tcp.analysis.retransmission
tcp.analysis.duplicate_ack
tcp.analysis.zero_window
```

（简化示意）

要看窗口的变化过程，用流图：

```text
Statistics → TCP Stream Graphs → Window Scaling
Statistics → TCP Stream Graphs → Time-Sequence (tcptrace)
```

前者画 rwnd，后者画"在途字节数"，能直接看到发送方有没有把链路填满。

再看内核参数。

```text
$ sysctl net.ipv4.tcp_sack net.ipv4.tcp_dsack net.ipv4.tcp_timestamps \
         net.ipv4.tcp_window_scaling net.ipv4.tcp_moderate_rcvbuf \
         net.ipv4.tcp_retries2
net.ipv4.tcp_sack = 1
net.ipv4.tcp_dsack = 1
net.ipv4.tcp_timestamps = 1
net.ipv4.tcp_window_scaling = 1
net.ipv4.tcp_moderate_rcvbuf = 1
net.ipv4.tcp_retries2 = 15
```

（简化示意）

逐个对应：

```text
tcp_sack              启用选择确认
tcp_timestamps        启用时间戳，绕开 Karn 的二义性
tcp_window_scaling    启用窗口缩放，突破 64 KB 上限
tcp_moderate_rcvbuf   接收缓冲区自动调节（按需长大，避免 SWS）
tcp_retries2          重传放弃次数上限，15 次对应约 924 秒
```

`tcp_retries2 = 15` 解释了一个现象：一条连接明明对端已经挂了，本端要等十几分钟才报错。

重传相关的参数还有几个，值得对着看。

```text
$ sysctl net.ipv4.tcp_retrans_collapse net.ipv4.tcp_early_retrans \
         net.ipv4.tcp_thin_linear_timeouts net.ipv4.tcp_recovery
net.ipv4.tcp_retrans_collapse = 1
net.ipv4.tcp_early_retrans = 3
net.ipv4.tcp_thin_linear_timeouts = 1
net.ipv4.tcp_recovery = 1
```

（简化示意）

```text
tcp_retrans_collapse        重传时把多个小段拼成大段，省首部开销
tcp_early_retrans           更早判定丢包（RACK 一类机制）
tcp_thin_linear_timeouts    稀疏连接的超时用线性退避，不用指数
```

排查重传，实用的顺序是这样。

```text
1. netstat -s 看 retrans 占比（正常应小于 1%）
2. ss -ti 看单条连接的 retrans 与 rto
3. tcpdump 抓包确认是"真丢"还是"乱序被误判"
4. 真丢 → 查链路；误判 → 查多路径负载均衡
```

（简化示意）

第三步最容易漏。

很多时候 `retrans` 计数在涨，链路却一点没丢包，只是乱序让发送方误判了。

这种"假重传"在有 ECMP 或链路聚合的网络里非常常见。

判据是翻抓包：同一个 seq 出现两次，但两次之间没有任何缺口。

那它就不是补漏，是补了一个"以为漏了"的洞。

## 14. 小结

可靠传输这一篇，压成四块：

```text
可靠 = 确认 + 超时 + 重传，保证最终按序交付，不保证不丢。
RTO = SRTT + 4×RTTVAR，α=1/8、β=1/4，超时后加倍。
重传过的段不取 RTT 样本（Karn）。
三个重复 ACK 立刻快传；SACK 告诉对方缺哪块。
```

流控这一篇，压成三块：

```text
窗口单位是字节，发送窗口 = min(rwnd, cwnd)。
rwnd 由接收方通告，零窗口靠坚持定时器恢复。
小窗口用 Clark 治，小报文用 Nagle 治。
```

下一篇只讲一个变量：cwnd。

```text
cwnd 从 1 个 MSS 开始，每个 RTT 翻倍 —— 这叫慢开始。
可它一点都不慢。
```
