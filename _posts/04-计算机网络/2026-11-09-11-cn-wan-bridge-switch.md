先想一个很怪的事实。

交换机有 24 个口，你随便插一个，立刻就能上网。

你没有配置过任何东西。

它怎么知道"发给 A 的帧该从哪个口出去"？

答案是：它一开始也不知道。

它边转发边学。

这一篇就从"它怎么学"讲起。

中间会经过三个地方：

```text
广域网：一条点对点的线，用 PPP
网桥：  把两个局域网连起来，靠自学习
交换机：网桥的多端口版，切开冲突域
```

三个地方的共同问题是同一个：

```text
一个帧进来，该往哪儿送？
```

## 1. 广域网和局域网，差在哪

先把两个词分清。

```text
LAN  局域网   一个单位自己建、自己管
              范围几百米到几公里
              带宽高、延迟低、便宜
              典型：以太网、WiFi

WAN  广域网   跨城市、跨国家
              链路是租运营商的
              带宽贵、延迟高、按距离和带宽计费
              典型：PPP、HDLC、帧中继、MPLS
```

最关键的一条差别不是技术，是**所有权**。

```text
LAN：线是你的，你想怎么拉就怎么拉
WAN：线是运营商的，你只能租，两端各接一个口
```

这决定了 WAN 协议的形态。

LAN 里有很多台设备抢一根线，所以需要 MAC、需要 CSMA/CD。

WAN 里只有两个端点，一根线连到底，什么都不用抢。

所以 WAN 的链路层协议长得很"轻"：

```text
不寻址（点对点，没有"发给谁"的问题）
不争用（没有第三方）
不保证可靠（错了交给上层）
只做三件事：成帧、检错、协商链路参数
```

408 里 WAN 的代表协议就两个：PPP 和 HDLC。

PPP 是重点。

顺带说一句，WAN 的链路层协议换过好几代。

```text
X.25     1970 年代   分组交换，逐跳确认，慢但可靠
帧中继    1980 年代   简化 X.25，去掉逐跳确认
ATM      1990 年代   53 字节信元，想统一话音和数据
MPLS     2000 年代   标签交换，运营商骨干
以太网    现在       城域以太网，WAN 和 LAN 的边界在消失
```

每换一代，都是"把可靠性推给两端，中间只做转发"。

今天你在家"拨号"用的是 PPPoE，在公司拉专线多半是以太网专线。

## 2. PPP 的帧格式

PPP（Point-to-Point Protocol，点对点协议）的帧长这样。

```text
┌──────┬──────┬──────┬────────┬───────────────┬──────┬──────┐
│ 标志  │ 地址  │ 控制  │ 协议    │ 信息           │ FCS  │ 标志  │
│ 0x7E │ 0xFF │ 0x03 │ 2 B    │ ≤ 1500 B      │ 2 B  │ 0x7E │
│ 1 B  │ 1 B  │ 1 B  │        │ （默认 MRU）   │      │ 1 B  │
└──────┴──────┴──────┴────────┴───────────────┴──────┴──────┘
```

逐字段看，有三个字段是"固定值"，很反常。

**标志 0x7E。**

二进制是 `01111110`，帧的起止定界符。

首尾各一个，中间的内容里绝不能出现这个字节，否则会被误认为帧边界。

所以要做填充，第 3 节讲。

**地址 0xFF。**

点对点链路只有两个端点，根本不需要地址。

这个字段存在纯粹是为了**兼容 HDLC 的帧格式**。

所以它永远填 0xFF，接收方也永远忽略它。

**控制 0x03。**

同样是为了兼容 HDLC，固定填"无编号帧"的编码。

这两个字段在现代 PPP 里可以被协商省略（地址控制压缩），省 2 字节。

**协议字段是真正有用的。**

它说明"信息字段里装的是什么"。

```text
0x0021  IPv4 数据报
0x0057  IPv6 数据报
0xC021  LCP（链路控制协议）
0x8021  IPCP（IP 控制协议）
0xC023  PAP（口令认证）
0xC223  CHAP（挑战握手认证）
```

看到没有：PPP 能同时承载 IPv4、IPv6、以及它自己的控制协议。

这就是"多协议"的意思。

**信息字段默认最大 1500 字节。**

这个数不是巧合，是为了跟以太网的 MTU 对齐。

**FCS 默认 2 字节**（可以协商成 4 字节）。

算一下总开销：

```text
1（标志）+ 1（地址）+ 1（控制）+ 2（协议）+ 2（FCS）+ 1（标志）= 8 B
```

8 字节。

记住这个 8，后面讲 PPPoE 的 MTU 1492 时会用到。

## 3. 字节填充与零比特填充

标志 0x7E 出现在数据里怎么办？

PPP 有两种解法，取决于链路是"异步"还是"同步"。

**异步链路（串口、拨号）用字节填充。**

规则三条：

```text
0x7E              →  0x7D 0x5E
0x7D              →  0x7D 0x5D
小于 0x20 的字符   →  0x7D, (原字节 XOR 0x20)
```

第二条是必须的：如果 0x7D 本身不转义，接收方看到 0x7D 就不知道该不该把下一个字节当转义结果。

第三条是为了把控制字符也挡掉，避免终端设备误判。

第三条的算法很漂亮：`c XOR 0x20` 相当于把第 6 位取反。

```text
0x7E XOR 0x20 = 0x5E
0x7D XOR 0x20 = 0x5D
0x03 XOR 0x20 = 0x23
0x1F XOR 0x20 = 0x3F
```

看，转义后的第二个字节都不可能是 0x7E 或 0x7D。

算一道题。

原始数据五个字节：

```text
7E  7D  03  20  1F
```

逐个处理：

```text
7E        → 7D 5E
7D        → 7D 5D
03 (<20)  → 7D 23
20 (=20)  → 20       ← 注意！0x20 不小于 0x20，不转义
1F (<20)  → 7D 3F
```

填充后：

```text
7D 5E  7D 5D  7D 23  20  7D 3F
```

5 个字节变成 8 个。

`0x20` 那一行是个高频陷阱：条件是"小于 0x20"，不是"小于等于"。

**同步链路（SONET/SDH）用零比特填充。**

同步链路是按比特流处理的，没有"字节"这个概念。

规则利用 0x7E 的形状：`01111110`，六个连续 1。

```text
发送端：信息字段里每出现 5 个连续的 1，就插入一个 0
接收端：每看到 5 个连续的 1，就删掉后面的那个 0
```

这样信息字段里永远不会出现 6 个连续 1，也就永远不会出现 0x7E。

```text
原始： 0111 1111 1100
        └5个1┘
插入： 0111 1101 1110 0
       ↑      ↑
       插0    插0
```

两种填充的差别一句话：

```text
异步：按字节转义，简单，开销不固定（1 变 2）
同步：按比特插入，透明，开销取决于数据内容
```

## 4. LCP 与 NCP

PPP 不只是"封装帧"，它还带一套**建链协议**。

三个层次：

```text
┌──────────────────────────────┐
│ 网络层协议  IP、IPv6 …        │
├──────────────────────────────┤
│ NCP  每个网络层协议一个        │  IPCP：协商 IP 地址、DNS
├──────────────────────────────┤
│ LCP  链路控制                  │  协商 MRU、认证方式、魔数
├──────────────────────────────┤
│ 封装  帧格式                   │  标志、地址、控制、协议、FCS
└──────────────────────────────┘
```

一次完整的 PPP 会话，顺序是固定的。

```text
1. 物理层连通（插上线、拨号成功）
2. LCP 协商：Configure-Request / Ack，谈 MRU、认证协议、压缩
3. 认证：PAP（两次握手，明文密码）或 CHAP（三次握手，不传密码）
4. NCP 协商：IPCP 分配 IP 地址、告诉对方 DNS
5. 传 IP 数据报
6. 挂断：NCP 关闭 → LCP 终止
```

两个认证协议的差别值得记一句。

```text
PAP：客户端直接发用户名密码   → 明文，链路上能被抓
CHAP：服务器发挑战，客户端用密码算哈希回传 → 密码不上线
```

所以今天的 PPP 基本都用 CHAP。

LCP 里还有个字段叫魔数（magic number），用来检测环路。

收到自己发出的魔数，就说明这条链路被绕回来了。

PPPoE 拨号上网就是这个流程的实例，第 14 节会看到它在主机上的样子。

## 5. PPP 为什么不用 CSMA/CD

这个问题 408 很爱问。

答案只有一句：**没有第三方，就没有争用。**

```text
CSMA/CD 要解决的问题：多个站抢一根共享线
PPP 的场景：          一根线只连两个端点
```

推下去，一条链上所有机制都失效了。

```text
不需要载波监听：没有别人在发，不用听
不需要冲突检测：撞不了
不需要 MAC 地址：地址字段固定 0xFF，没人看
不需要争用期：没有争用
不需要最小帧长 64 B：帧短也没关系，不会漏掉冲突
```

所以 PPP 可以有很短的帧，甚至可以传 1 个字节的信息。

对比一下两种链路的"帧长约束"来源：

```text
以太网：帧 ≥ 64 B，因为要撑够争用期才听得见冲突
PPP：   帧可以任意短，因为没有冲突要听
```

**同一条规则，换个介质就不成立了。**

这也说明为什么学网络不能只背参数：每个参数背后都有一个物理原因。

再补一句 HDLC。

408 只考它和 PPP 的关系，一句话就够：

```text
HDLC 是面向比特的同步链路层协议，PPP 的"前身"。
帧格式：标志 0x7E | 地址 | 控制 | 信息 | FCS | 标志
填充：  零比特填充（和 PPP 的同步链路一样）
三种帧：信息帧 I、监控帧 S、无编号帧 U
```

PPP 借了它的帧格式，扔掉了它的编号、确认和重传。

所以 PPP 是"HDLC 的简化版 + 多协议支持 + 一套建链协议"。

那个固定填 0xFF 的地址字段、固定填 0x03 的控制字段，就是从 HDLC 继承下来的"化石"。

## 6. 网桥：透明桥接

现在从"一条线"跳到"两个网"。

假设有两栋楼，各有一个以太网，要用一根线连起来。

最省事的办法是接一个**网桥（bridge）**。

网桥工作在链路层。

```text
它看的是帧，不是比特
它看 MAC 地址，不看 IP
它把帧"收下来、看一眼、再发出去"（存储转发）
```

它最重要的性质叫**透明（transparent）**。

```text
主机完全不知道桥的存在。
不用改 IP、不用改网关、不用装驱动。
插上线就通。
```

这叫透明桥接（transparent bridging），标准是 802.1D。

有两种桥接方式，408 只考第一种。

```text
透明桥接：  桥自己维护转发表，主机完全不知道
源路由桥接：源主机把整条路径写进帧里，桥照着转
```

源路由要求主机参与选路，早就淘汰了。

以太网用的是透明桥接，所以主机不用装任何东西。

它和集线器、中继器的区别，一句话：

```text
中继器/集线器：物理层，把信号放大整形，原样转发所有比特
网桥/交换机：  链路层，把帧收完整，查表决定从哪个口发
```

这个"收完整再发"带来三个直接好处。

```text
1. 能隔离冲突域：两边各自要跑 CSMA/CD，互不干扰
2. 能过滤：目的地在同一侧的帧，不过桥
3. 能连不同速率的链路：进来 10 Mbps，出去 100 Mbps
```

集线器一个都做不到。

网桥还有一个历史遗留的局限：它只隔冲突，不隔广播。

所以"用网桥把两个网连起来"从来不是"切广播域"的手段，只是"延长一段链路"。

要隔广播，必须上路由器。

## 7. 自学习：源地址学习、转发、过滤、泛洪

回到开篇那个问题：网桥怎么知道往哪儿发？

三个动作，全靠"看"。

**第一，源地址学习。**

```text
收到一个帧，看它的源 MAC，看它是从哪个口进来的。
把"这个 MAC 在这个口"记进转发表。
```

注意是**源**地址。

这一条最反直觉，也最容易考。

```text
为什么要学源地址？因为源地址一定是"在那个口的方向上"，这个信息是可靠的。
为什么不用目的地址学？因为目的地址可能在别处，你只知道"要发给他"，不知道"他在哪"。
```

**第二，目的地址决定转发还是过滤。**

```text
表里有这个目的 MAC，且出口 ≠ 入口  → 从那个口转发
表里有这个目的 MAC，但出口 = 入口  → 丢弃（过滤）
```

"出口等于入口"说明发送方和接收方在同一个网段，网桥不该插手。

**第三，查不到就泛洪。**

```text
表里没有这个目的 MAC  → 从除入口外的所有口发出去
```

**第四，表项会老化。**

```text
每个表项带一个计时器，默认约 300 秒。
超时没再听到这个源地址，就删掉。
```

老化是为了适应拓扑变化：一台机器换了口、或者搬走了，旧表项不能永远留着。

顺带算一下表的规模。

```text
48 口交换机，每口后面接 20 台设备 → 约 1000 条
典型 CAM 芯片能存 8K 到 32K 条 → 绰绰有余
```

但表可以被撑爆。

伪造大量源 MAC 去泛洪，表满了以后交换机无处可记，新帧只能全部泛洪。

这时候它退化成一个集线器。

这种攻击叫 MAC flooding，防范手段是限制每端口可学的 MAC 数量。

走一遍完整过程。

```text
初始：表为空

① A（口1）→ B
   学：A → 1
   查 B：未知 → 泛洪到 2、3、4

② B（口2）→ A
   学：B → 2
   查 A：在口 1 → 只从口 1 转发（不泛洪了）

③ C（口3）→ B
   学：C → 3
   查 B：在口 2 → 只从口 2 转发

此时表：A → 1   B → 2   C → 3
```

三个帧之后，表就建好了。

整个过程没有任何配置、没有任何协议报文。

**这就是"即插即用"的全部秘密。**

## 8. 生成树：为什么必须有

自学习有个致命弱点：**它假设网络是一棵树。**

如果拓扑里有环，会出两件大事。

```text
事件一：广播风暴
  广播帧从口 2 出去，绕一圈从口 3 回来，再泛洪出去，永远不停。
  几秒钟就能把带宽和 CPU 打满。

事件二：MAC 表震荡
  同一个源 MAC 从两个不同的口都能收到，
  表项被反复覆盖，转发方向来回跳。
```

一根网线插错，整个网络瘫痪，就是这个原因。

解法叫**生成树协议（STP，Spanning Tree Protocol，802.1D）**。

思路很朴素：

```text
既然环会死，那就把环剪断。
但物理上不剪（还要备份），逻辑上剪。
被剪掉的端口进入"阻塞"状态：不转发数据帧，只听 BPDU。
```

选举过程三步：

```text
1. 选根桥：BID 最小的当根（BID = 优先级 + MAC）
2. 每个非根桥选一个根端口：到根桥路径开销最小的口
3. 每条网段选一个指定端口：该网段上到根桥开销最小的口
4. 既不是根端口也不是指定端口的 → 阻塞
```

结果是：所有交换机在逻辑上构成一棵以根桥为根的树。

举个小例子：

```text
        S1（优先级 32768，MAC 最小）← 根桥
       /  \
     S2    S3
      \    /
       \  /   ← 这条链路有一端要被阻塞
        ──
```

三条连线，两个环。

STP 必须剪掉一条，网络才能收敛。

S2 和 S3 之间那条线，两端的路径开销一样，就比较 BID，小的那端当指定端口，另一端阻塞。

剪完之后，任意两台主机之间只有一条路径，环没了。

代价是收敛慢。

```text
BPDU 每 2 秒发一次
端口状态：阻塞 → 侦听（15 s）→ 学习（15 s）→ 转发
一次拓扑变化，可能断 30 秒以上
```

后来有了 RSTP（802.1w），把收敛压到秒级。

一句话记住 STP 的作用：

```text
用"逻辑上剪断"换"物理上有备份"。
```

## 9. 交换机：多端口网桥

交换机不是什么新东西。

```text
交换机 = 多端口网桥 + 专用硬件（ASIC）+ 每端口独立冲突域
```

它把网桥该做的事，用芯片做到了线速。

三个转发模式，区别只在"什么时候开始转发"。

```text
直通（cut-through）
  读到目的 MAC（前 6 字节）就转发。
  延迟最小（几 μs），但会把坏帧也转出去。

无碎片（fragment-free）
  收满 64 字节才转发。
  正好过滤掉冲突碎片，延迟居中。

存储转发（store-and-forward）
  收完整帧、查 FCS 通过才转发。
  延迟最大，但不转发任何坏帧。
```

现代交换机默认是存储转发，因为差错控制比那几微秒值钱。

还有一点必须说清：**交换机的"独享带宽"是有前提的**。

```text
全双工：每个端口可以同时收发，互不干扰 → 真正独享
半双工：还是要跑 CSMA/CD，还是要抢
```

对端如果是集线器，交换机端口也只能降到半双工。

所以"换交换机就快"这句话，隐含的条件是"对端也支持全双工"。

还有一个常被忽略的指标：背板带宽（交换容量）。

```text
24 口千兆交换机，全双工：
24 × 1 Gbps × 2（收、发各算一次）= 48 Gbps
```

标称的背板带宽低于这个数，就是"阻塞型"交换机。

端口很多、背板不够，同时通信时会互相排队。

## 10. 冲突域与广播域的划分规则

这一节是 408 的高频考点，规则必须记死。

先定义两个词。

```text
冲突域（collision domain）：会互相冲突的范围，一个时刻只能有一台在发
广播域（broadcast domain）：一个广播帧能到达的范围
```

四个设备，各切什么，一张表说清。

| 设备 | 工作层 | 分割冲突域 | 分割广播域 |
|---|---|---|---|
| 中继器 / 集线器 | 物理层 | 否 | 否 |
| 网桥 / 交换机 | 链路层 | 是 | 否 |
| 路由器 | 网络层 | 是 | 是 |
| 交换机上的 VLAN | 链路层（逻辑） | — | 是 |

记法只有一句：

```text
集线器什么都不切。
交换机切冲突域（一刀一刀切）。
路由器切广播域（一刀切干净）。
```

为什么交换机不切广播域？

因为**广播帧必须泛洪**。

```text
目的地址 FF:FF:FF:FF:FF:FF，交换机在表里查不到（也不该查）
规则说"查不到就泛洪" → 所有端口都发
于是广播穿过了整个交换机
```

所以一个交换机上的所有端口（同一 VLAN 内），在同一个广播域里。

> **反直觉的点**：交换机比集线器聪明得多，能查表、能过滤、能全双工。
> 但它对广播的态度和集线器一模一样：照单全收，全部转发。
> 一台 48 口交换机，仍然是 1 个广播域。
> "交换机分割广播域"这句话是错的，而且错得极其常见。

想切广播域，只有两条路：

```text
路由器：物理上分开，每个接口一个广播域
VLAN：  逻辑上分开，一台交换机内部切成多个广播域
```

现实中还有第三条：**三层交换机**。

它就是"交换机 + 路由模块"，在 VLAN 之间用硬件转发，速度接近二层。

所以机房里的"切广播域"，现在多半用三层交换机，而不是在一堆路由器上插线。

## 11. VLAN：切广播域的另一把刀

广播域太大有两个毛病。

```text
1. 广播流量占带宽（ARP、DHCP、NetBIOS 都是广播）
2. 一台机器中毒，广播风暴拖垮全网
```

VLAN（Virtual LAN，虚拟局域网）把一台物理交换机切成几台逻辑交换机。

```text
一台 24 口交换机
  端口 1-8   → VLAN 10（财务部）
  端口 9-16  → VLAN 20（研发部）
  端口 17-24 → VLAN 30（市场部）
```

效果：

```text
VLAN 10 的广播只在 1-8 口里传
VLAN 20 的广播只在 9-16 口里传
三个 VLAN 之间默认完全隔离，要通必须过路由器（或三层交换机）
```

标准是 **802.1Q**，做法是在帧里插一个 4 字节标签。

```text
┌──────────┬──────────┬──────────┬──────────────┬─────────┬──────┐
│ 目的 MAC │ 源 MAC   │ TPID     │ TCI          │ 类型    │ 数据 │
│ 6 B      │ 6 B      │ 0x8100   │ PCP 3 DEI 1 VID 12 │ 2 B  │      │
│          │          │ 2 B      │ 2 B          │         │      │
└──────────┴──────────┴──────────┴──────────────┴─────────┴──────┘
```

三个子字段：

```text
PCP  3 位  优先级，0–7，给 QoS 用
DEI  1 位  丢弃资格
VID  12 位 VLAN ID，0–4095，可用 1–4094
```

标签插在源 MAC 后面，所以帧长了 4 字节。

```text
最小帧：64 → 68 B
最大帧：1518 → 1522 B
```

端口有两种角色。

```text
Access 口：接主机，帧进出都不带标签（主机不知道 VLAN 存在）
Trunk 口： 接交换机，帧带着标签走，一条线承载所有 VLAN
```

"一台交换机当三台用"，说的就是这个。

## 12. 容易混淆的点

**第一，交换机分割冲突域，不分割广播域。**

这条被写进写作契约的"五个必须纠正的误解"里。

再念一遍：交换机切冲突域，路由器切广播域。

**第二，集线器两个都不切。**

它不仅不切广播域，连冲突域也不切。

10 台机器接一个集线器，就是 1 个冲突域、1 个广播域。

**第三，路由器的每个接口都是一个广播域。**

一台路由器有 4 个接口，就有 4 个广播域（如果不算 VLAN 的话）。

**第四，自学习学的是源地址。**

转发看目的，学习看源。

顺序别搞反：先学源，再查目的。

**第五，泛洪不等于广播。**

泛洪是一种**行为**（从所有口发出去）。

广播是一种**地址类型**（FF:FF:FF:FF:FF:FF）。

单播帧查不到表也会被泛洪。

**第六，PPP 不做可靠传输。**

它有 FCS 检错，错了就丢。

但没有序号、没有确认、没有重传。

"可靠"是 TCP 的事。

**第七，"透明"是对主机透明。**

主机不知道桥的存在。

但桥自己知道自己在干什么（它在维护转发表）。

**第八，VLAN 不是物理隔离。**

还是同一台交换机、同一块背板。

VLAN 是逻辑上的广播域隔离，不是带宽隔离。

**第九，集线器换成交换机，广播域不变。**

这是第 13 节第 (2) 问最常见的错答。

换交换机只增加了冲突域的数量，广播域一个都没多。

**第十，VID 只有 12 位，所以 VLAN 最多 4094 个。**

听起来够用，云环境里不够。

于是有了 VXLAN，24 位，一千六百万个。

## 13. 408 怎么考

这一块的题型：

```text
1. 数冲突域、数广播域
2. 给拓扑，判断交换机从哪个口转发
3. PPP 帧填充（字节填充 / 零比特填充）
4. 判断某设备工作在哪一层
```

### 例题（自拟）

拓扑如下：

```text
              ┌──────── 路由器 R ────────┐
              │ 接口1            接口2    │
              │                            │
            S1 ┘                            └ S2
         ┌────┼────┐                    ┌────┼────┐
        口1   口2   口3                口1   口2
         │     │     │                  │     │
        H1    PC4   PC5                PC6   PC7
         │
   ┌─────┼─────┐
  PC1   PC2   PC3
```

说明：S1、S2 是以太网交换机，H1 是集线器。

三问：

```text
(1) 冲突域有几个？广播域有几个？
(2) 若把 H1 换成交换机 S3（下挂 PC1、PC2、PC3），冲突域变成几个？
(3) 若在 S1 上把 PC4、PC5 划入 VLAN 10，其余端口留在 VLAN 1，广播域变成几个？
```

**第 (1) 问**

按"交换机每个端口一个冲突域"数。

```text
S1 口1 + H1 + PC1、PC2、PC3   → 1 个（H1 不分割）
S1 口2（PC4）                 → 1 个
S1 口3（PC5）                 → 1 个
S1 上行口 ↔ R 接口1            → 1 个
S2 口1（PC6）                 → 1 个
S2 口2（PC7）                 → 1 个
S2 上行口 ↔ R 接口2            → 1 个
```

合计 7 个冲突域。

广播域看路由器的两侧：

```text
R 左侧（S1 及所连所有设备）→ 1 个
R 右侧（S2 及所连所有设备）→ 1 个
```

合计 2 个广播域。

答：7 个冲突域，2 个广播域。

**第 (2) 问**

H1 原来是 1 个冲突域，换成交换机 S3 后：

```text
S3 口1（PC1）→ 1 个
S3 口2（PC2）→ 1 个
S3 口3（PC3）→ 1 个
S3 上行口 ↔ S1 口1 → 1 个
```

1 个变 4 个，净增 3。

```text
7 − 1 + 4 = 10
```

答：10 个冲突域。

注意广播域仍然是 2 个，交换机不切广播域。

**第 (3) 问**

S1 上原来是一个广播域，切成两个：

```text
VLAN 1 ：S1 口1（H1 侧）、上行口（R 侧）
VLAN 10：S1 口2（PC4）、口3（PC5）
```

加上 S2 那一侧：

```text
1（VLAN 1）+ 1（VLAN 10）+ 1（S2 侧）= 3
```

答：3 个广播域。

顺带说一句：PC4 想访问 PC6，现在必须先经过路由器（或三层交换）。

因为 VLAN 之间在二层是隔离的。

### 另一小题：交换机的转发判断

S1 的转发表如下：

```text
MAC                 端口
AA:AA:AA:AA:AA:AA     1
BB:BB:BB:BB:BB:BB     2
```

依次到达三个帧，问各自怎么处理。

```text
① 目的 AA:…  源 CC:…   从口 3 进入
② 目的 DD:…  源 AA:…   从口 1 进入
③ 目的 BB:…  源 EE:…   从口 2 进入
```

**第 ① 个**

目的 AA 在表里，出口是口 1，不是入口 3。

```text
→ 从口 1 转发（单播，不泛洪）
→ 同时学：CC → 3
```

**第 ② 个**

目的 DD 不在表里。

```text
→ 泛洪：从口 2、3、4 发出去（除入口 1）
→ 同时学：AA → 1（表里已有，刷新计时器）
```

**第 ③ 个**

目的 BB 在口 2，但入口也是口 2。

```text
→ 丢弃（过滤）：发送方和接收方在同一个网段，不需要交换机插手
→ 同时学：EE → 2
```

三个帧里，只有第一个是真正的"单播转发"。

第二个是泛洪，第三个是过滤。

408 最爱在这里设陷阱：看到"目的地址在表里"就以为一定会转发，忘了还有"入口等于出口"这种情况。

### 另一小题：PPP 填充

未填充的信息字段是：

```text
7E 03 7D 20
```

填充后是什么？

```text
7E → 7D 5E
03 → 7D 23   （0x03 < 0x20）
7D → 7D 5D
20 → 20      （0x20 不小于 0x20，不转义）
```

答：`7D 5E 7D 23 7D 5D 20`。

### 套路总结

```text
数域题：先数交换机的端口（每个端口一个冲突域），集线器整段算一个，
        再看路由器把广播域切成几块。
转发题：先看表里有没有目的 MAC，有就单播，没有就泛洪，同口就丢弃。
填充题：0x7E、0x7D、小于 0x20 的三类要转义，0x20 本身不转义。
VLAN 题：多切一个 VLAN 就多一个广播域，冲突域还是看端口数。
```

## 14. 真实网络里长什么样

先看 Linux 怎么当交换机用。

```text
$ sudo ip link add br0 type bridge
$ sudo ip link set eth1 master br0
$ sudo ip link set eth2 master br0
$ bridge link show
3: eth1: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding
4: eth2: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding
```

`master br0` 就是"这个口属于 br0 这个网桥"。

看自学习建出来的表：

```text
$ bridge fdb show br0
33:33:00:00:00:01 dev eth1 self permanent
3c:7c:3f:12:34:56 dev eth1 master br0
00:1a:2b:3c:4d:5e dev eth2 master br0
```

`master br0` 那两行就是学到的 MAC 表项。

不带 `master br0` 的是本地永久表项（组播地址之类）。

这张表就是交换机 ASIC 里那张表在软件里的样子。

看 VLAN：

```text
$ bridge vlan show
port    vlan-id
eth1    1 PVID Egress Untagged
eth2    10
eth2    20
```

`PVID` 是端口默认 VLAN，`Egress Untagged` 表示出去时剥掉标签（Access 口）。

`eth2` 同时属于 VLAN 10 和 20，说明它是 Trunk 口。

用 tcpdump 看 802.1Q 标签：

```text
$ sudo tcpdump -e -c 2 -i eth2 vlan
14:40:11.203 3c:7c:3f:12:34:56 > 00:1a:2b:3c:4d:5e,
    ethertype 802.1Q (0x8100), length 64: vlan 10, p 0, ethertype IPv4
```

`vlan 10, p 0` 就是 VID 和 PCP。

再看 PPP 在真实主机上的样子。

国内宽带拨号用的是 **PPPoE**（PPP over Ethernet）。

```text
$ ip link show ppp0
8: ppp0: <POINTOPOINT,MULTICAST,NOARP,UP,LOWER_UP> mtu 1492
    link/ppp
```

注意 `mtu 1492`。

以太网 MTU 是 1500，为什么 PPPoE 少 8？

```text
PPPoE 头 6 B + PPP 协议字段 2 B = 8 B
1500 − 8 = 1492
```

这就是那个 8 字节开销在真实世界里的痕迹。

也解释了为什么有些网站"能打开但图片加载不出来"：路径 MTU 发现没做好，1500 字节的包被丢了。

PPP 的地址和状态：

```text
$ ip addr show ppp0
8: ppp0: <POINTOPOINT,MULTICAST,NOARP,UP,LOWER_UP> mtu 1492
    link/ppp
    inet 100.64.13.7 peer 100.64.0.1/32 scope global ppp0
```

`peer` 后面那个地址就是链路另一端的地址。

点对点链路不需要掩码，只要知道"对面是谁"。

最后看网桥的端口状态，能直接看到 STP：

```text
$ bridge link show
3: eth1: ... master br0 state forwarding
4: eth2: ... master br0 state blocking
```

`state blocking` 就是被生成树剪掉的那个口。

它还在，只是不许转发。

## 15. 小结

三块内容，压成三段。

```text
广域网
  点对点，没有第三方 → 不需要 CSMA/CD，不需要 MAC
  PPP 帧：7E | FF | 03 | 协议 | 信息 | FCS | 7E，开销 8 B
  异步链路字节填充：7E→7D5E，7D→7D5D，<20→7D(c^20)
  同步链路零比特填充：5 个 1 后插 0
  LCP 建链、认证，NCP 配地址

网桥
  透明桥接：主机不知道桥的存在
  自学习：学源地址，查目的地址，查不到就泛洪，表项会老化
  环路会广播风暴 → STP 逻辑上剪成一棵树

交换机
  多端口网桥，每端口一个冲突域，全双工独享带宽
  切冲突域，不切广播域
  要切广播域：上路由器，或用 VLAN（802.1Q，帧加 4 B）
```

一句话记住那个最容易被考错的点：

```text
广播帧会被泛洪到所有端口，
所以交换机再贵，也切不开广播域。
```

这一篇里，MAC 地址只解决了"一跳之内送到谁"。

跨网段怎么办？

```text
计算机网络系统讲解 12：网络层：IPv4 分组与转发
```

那一篇会回答：

```text
IP 首部 20 个字节，每一位都在干什么？
1500 的 MTU 遇到 4000 字节的数据报，怎么分片？
分片为什么只在目的主机重组？
```
