> **读这篇之前，你只需要知道**：浏览器就是你用来打开网页的那个程序；URL 是地址栏里那一整串字符，说的是"你要的东西在哪"；RTT 是一次往返的时间，发出去再收到回应，一来一回。
> **这篇讲什么**：从浏览器拿到网址，到页面画出来之间发生的事——HTTP 报文长什么样、状态码是什么意思、为什么 HTTP 换了好几个版本、Cookie 怎么让"不记事"的协议变成登录状态、HTTPS 到底加了什么。
> **一个类比**：HTTP 像在餐厅点菜。你递一张纸条（请求报文）写明要哪道菜，服务员回一张纸条（响应报文）说明上没上成、为什么；纸条格式固定，所以后厨换人也能看懂。Cookie 像一张会员卡，你每次来都得出示一下，店里才认得出你是老顾客。


在地址栏敲一个 URL，回车。

半秒后页面出来。

这半秒里，DNS 查了名字，TCP 建了连接，TLS 换了密钥，HTTP 发了一问一答，浏览器把 HTML 变成像素。

第 21 篇讲完了 DNS。

这一篇从 DNS 之后开始，一直讲到像素。

先看一个数字。

一个 100 ms RTT 的链路，一个 5 个对象的页面，用 HTTP/1.0 打开要 1 秒，用 HTTP/1.1 打开只要 600 ms。

服务器一个字没改，只是把协议版本换了。

带宽没变，内容没变，省下来的全是"等待"。

这就是 HTTP 这一篇的主线：**HTTP 的每次进化，都在跟"等待"较劲**。

## 1. 这个问题解决什么

为什么"看网页"要拆成三样东西？

因为看到一个页面，其实是三件事各完成了一半：先要找到它（URL），再要取到它（HTTP），最后要能画出来（HTML）。

少任何一样，页面都不会出现。

万维网（World Wide Web）要解决一件事：让一台机器上的文档，能被另一台机器上的浏览器取到并显示。

它由三样东西组成，缺一不可。

```text
URL   怎么唯一地指一个资源
HTTP  怎么把资源取过来
HTML  取过来之后长什么样
```

三个都是应用层。

HTML 是内容格式，408 不管。

URL 和 HTTP 是这一篇的主角。

HTTP 的定位很特别：它本身不传送文件，它传送的是"消息"。

消息里可以装 HTML、装图片、装 JSON、装视频分片。

装什么由 `Content-Type` 说，HTTP 不关心。

正因为这样，HTTP 后来变成了通用传输层：REST API 走它、WebSocket 握手走它、gRPC 的 HTTP/2 走它。

一个 1991 年的协议活到今天，靠的就是这个"只传消息，不管内容"的克制。

端口两个：HTTP 80，HTTPS 443。

`https://example.com` 不写端口就是 443，`http://example.com` 不写就是 80。

这条"默认端口"是 408 的送分题，但每年都有人写错。

## 2. 最小模型：URL 与一次请求-响应

为什么先把一个网址拆开？

因为后面每一节都在用它的零件：host 决定问哪台服务器，port 决定敲哪个门，path 决定要哪份东西。

拆不清楚，后面的耗时、缓存、虚拟主机全都算不明白。

URL（Uniform Resource Locator）拆开是六个部分。

```text
  https://user:pass@www.example.com:443/shop/item?id=7#review
  └─┬──┘   └──┬───┘ └──────┬──────┘ └┬┘└────┬────┘ └──┬──┘
   scheme    userinfo      host      port  path      query  fragment
```

（简化示意。）

408 相关的只有三个：host、port、path。

`fragment`（`#` 后面那段）根本不发给服务器，是浏览器自己用的，用来滚到页面某个位置。

这一点很实用：如果你把带 `#` 的地址贴给别人，服务器永远看不到那段。

HTTP 的交互模型只有一个形状：请求-响应（request-response）。

```text
客户端 ──请求──► 服务器
客户端 ◄──响应── 服务器
```

永远是客户端先开口。

服务器不会主动给客户端发消息（服务端推送是 HTTP/2 的新东西，但它也是在一个已存在的请求上下文里推）。

一次交互的过程：

```text
① 客户端建立 TCP 连接（80 或 443）
② 客户端发一个请求报文
③ 服务器读请求，处理，发一个响应报文
④ 连接关不关，看协议版本和 Connection 首部
```

（简化示意。）

（这里先给"报文"一个定义：两台机器之间一问一答的那两段文本，就叫报文——客户端发的那段叫请求报文，服务器回的那段叫响应报文。它们的格式在下一节拆开看。）

整个过程是无状态的：服务器不记得你上次来过。

"无状态"这三个字，是这一篇后半段所有麻烦的来源。

## 3. 一次完整走查：从回车到首屏

为什么要把这半秒拆成九步？

因为"网页慢"这句话没法直接修。

拆开之后，你才能说清慢在哪一步，也才看得懂后面每一节到底在省哪一段。

把一次真实的页面访问拆成九步。

```text
① URL 解析        拆出 scheme/host/port/path
② 缓存检查        浏览器缓存、Service Worker、HSTS 表
③ DNS 解析        example.com → 93.184.216.34
④ TCP 三次握手    连 93.184.216.34:443
⑤ TLS 握手        协商密钥，验证证书
⑥ 发 HTTP 请求     GET / HTTP/2
⑦ 收响应          状态行 + 首部 + HTML 实体
⑧ 解析 HTML       构建 DOM，发现 css/js/img
⑨ 请求子资源      重复 ②–⑦，然后布局、绘制
```

（这三步里出现的词先解释一下：状态行是响应报文的第一行，写着版本号、状态码和一句短语；首部是紧跟着的一排"名字: 值"清单，说明内容的类型、长度、缓存规则；实体是首部之后真正的数据，比如那段 HTML。TLS 是 Transport Layer Security 的缩写，传输层安全协议，它在 TCP 之上再套一层加密，让中途的设备看不懂也改不了内容。）

每一步都要花时间，加起来就是"首屏时间"。

给一组典型数字（示例值，不是标准）：

```text
① URL 解析        0 ms（内存操作）
② 缓存检查        1 ms
③ DNS 解析        20 ms（有缓存时 0 ms）
④ TCP 握手        1 RTT = 30 ms
⑤ TLS 1.2 握手    2 RTT = 60 ms
⑥ HTTP 请求       1 RTT = 30 ms（首字节）
⑦ 响应传输        看大小
```

（简化示意。）

所以"首字节时间"（TTFB）大约是 140 ms。

真正拖慢首屏的往往不是服务器算得慢，是这四段往返：DNS 一次、TCP 一次、TLS 两次（TLS 1.3 只要一次）、请求一次。

这就解释了为什么工程上要做这几件事：

```text
DNS 预解析        <link rel="dns-prefetch">
连接预建          <link rel="preconnect">
TLS 1.3          省一个 RTT
HTTP/2 多路复用   省掉后续对象的握手
CDN               把 RTT 从 100 ms 压到 10 ms
```

每一招都在砍上表里的某一行。

注意 ⑧ 和 ⑨ 是循环：HTML 里发现 30 个资源，就要再走 30 次"缓存检查 → 取资源"。

这 30 次怎么取，就是第 8 节要讲的连接方式问题。

## 4. 请求报文：请求行、首部、空行、实体

为什么值得盯着一份报文的格式看？

因为 408 的题经常直接问"这个字段在哪一段""少了这一行会怎样"，答案全藏在四段结构里。

而工程上 90% 的"接口调不通"，也都是这几段里的某一段写错了。

HTTP 报文是纯文本（HTTP/2 之后是二进制帧，但语义一样）。

一个请求长这样：

```text
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (X11; Linux x86_64)
Accept: text/html,application/xhtml+xml
Accept-Encoding: gzip, br
Accept-Language: zh-CN,zh;q=0.9
Connection: keep-alive
Cookie: sid=abc123

（空行）
（这里是实体，GET 一般没有）
```

四段结构：

```text
请求行   方法 SP 请求目标 SP 版本 CRLF
首部行   Name: Value CRLF，可以有多行
空行     一个单独的 CRLF，标志首部结束
实体     可选，长度由 Content-Length 或 Transfer-Encoding 决定
```

（简化示意。）

空行是必须的，它就是"首部到此结束"的分隔符。

少了这一行，服务器会把实体当成首部继续读。

几个必背的首部：

```text
Host             目标主机名，HTTP/1.1 必需，一个 IP 上放多个网站靠它
User-Agent       客户端标识，服务器用来适配
Accept           能接受什么类型
Accept-Encoding  能接受什么压缩（gzip、br）
Content-Type     实体的类型（POST 时必有）
Content-Length   实体的字节数
Cookie           第 9 节的主角
Referer          从哪个页面跳过来的
If-None-Match    缓存验证，第 10 节讲
```

方法一共八个，408 主要考前五个。

```text
GET      取资源，参数在 URL 里，可缓存，安全且幂等
HEAD     只要首部，不要实体，用来探活和查修改时间
POST     提交数据，参数在实体里，不幂等，默认不缓存
PUT      上传/替换整个资源，幂等
DELETE   删除资源，幂等
OPTIONS  问服务器支持哪些方法，CORS 预检用
TRACE    回显请求，调试用，一般关掉
CONNECT  让代理建隧道，HTTPS 代理用
```

两个概念要分清，选择题常拿它们做文章。

**安全（safe）**：不改服务器状态。GET、HEAD、OPTIONS、TRACE 是安全的。

**幂等（idempotent）**：执行一次和执行多次，服务器状态一样。GET、HEAD、PUT、DELETE、OPTIONS、TRACE 是幂等的。

POST 既不安全也不幂等。

为什么关心幂等？

因为网络会重试。

浏览器刷新、代理重发、客户端超时重试，都可能把同一个请求发两次。

如果这个请求是 `PUT /user/7/name`，发两次结果一样，无所谓。

如果是 `POST /order`，发两次就下了两单。

所以工程上给 POST 加幂等键（idempotency key），本质上是在应用层把 POST 变成幂等。

## 5. 响应报文：状态行与五个族

为什么状态码要背到"给场景就能选码"？

因为它是整个协议里唯一一眼就能看出结果的信号：拿到码，立刻知道该重试、该改地址、还是该去登录。

状态码（status code）就是服务器回给浏览器的三位数字，第一位划大类，后两位说细节。

响应把请求行换成状态行。

```text
HTTP/1.1 200 OK
Date: Sun, 09 Nov 2026 02:45:00 GMT
Server: nginx
Content-Type: text/html; charset=utf-8
Content-Length: 1256
Cache-Control: max-age=3600
ETag: "5f8-abc"

（空行）
<!DOCTYPE html>
<html>...
```

状态码三位数，第一位定族。

```text
1xx  信息，请求已收到，继续
2xx  成功
3xx  重定向，还要再做一步
4xx  客户端错
5xx  服务器错
```

408 明确点名的十个，逐个说清"什么时候用"。

```text
200 OK               成功，实体里是资源
301 Moved Permanently 永久搬家，搜索引擎会改索引，浏览器会缓存这个跳转
302 Found            临时搬家，下次还来原地址（307 是它的"不改方法"版本）
304 Not Modified     资源没变，你别传实体了，用你本地的
400 Bad Request      请求报文本身有问题（语法错、参数缺）
403 Forbidden        服务器懂你的请求，但不给你（权限不足）
404 Not Found        资源不存在
500 Internal Server Error  服务器自己崩了
502 Bad Gateway      网关/代理从上游收到无效响应（上游挂了或不是 HTTP）
503 Service Unavailable    服务暂时不可用（过载、维护），可以带 Retry-After
```

（简化示意。）

几个容易混的对：

```text
301 vs 302   永久 vs 临时，区别在于"浏览器和搜索引擎要不要记住这个跳转"
302 vs 307   都临时，307 明确要求"重定向后还用原来的方法"
400 vs 404   请求本身错 vs 请求没错但资源没有
401 vs 403   没认证（要你登录）vs 认证了但没权限
500 vs 502   自己的代码崩了 vs 上游给的东西不对
502 vs 503   上游坏了 vs 自己忙不过来
```

304 是个特殊的成功码。

它属于 3xx，但不是"去别处拿"，而是"你手上的就是最新的"。

304 响应不带实体，所以特别省流量，第 10 节会算这笔账。

## 6. 408 怎么考

HTTP 的题分四类。

```text
状态码含义      给码问含义，给场景选码（最高频）
连接方式        1.0 与 1.1 的差别，RTT 计算
Cookie 作用     无状态怎么变有状态，Cookie 存在哪
端口与协议      HTTP 80 / HTTPS 443，HTTP 属于应用层
```

状态码题没有技巧，就是背。

但别死背数字，背"族 + 场景"：客户端错在 4xx，服务器错在 5xx，重定向在 3xx。

RTT 题有固定套路，见下面例题一。

Cookie 题常问三个点：Cookie 存在客户端、由 `Set-Cookie` 下发、每次请求自动带上。

偶尔会问"Cookie 和 Session 的区别"，答案一句话：Cookie 是客户端的一张纸条，Session 是服务器上的一份档案，纸条上写的是档案编号。

**例题一（自拟，RTT 计算）**

客户端访问一个页面，页面含 1 个 HTML 和 4 张小图。

RTT = 100 ms，忽略数据传输时间，DNS 已缓存。

求以下四种情况的耗时：HTTP/1.0 非持久、HTTP/1.1 持久非流水线、HTTP/1.1 持久加流水线、HTTP/2 多路复用。

答：

```text
HTTP/1.0 非持久：
每个对象 1 RTT 建 TCP + 1 RTT 请求响应 = 2 RTT
5 个对象 = 10 RTT = 1000 ms

HTTP/1.1 持久非流水线：
第一个对象 2 RTT，之后每个 1 RTT（连接复用）
2 + 4 = 6 RTT = 600 ms

HTTP/1.1 持久加流水线：
第一个 2 RTT，剩下的请求一次性发出，一个 RTT 全回来
2 + 1 = 3 RTT = 300 ms

HTTP/2 多路复用：
一次连接，一次往返把 5 个对象全要回来
2 RTT = 200 ms
```

四次计算的关键差别只有一句：**建立连接的那 1 RTT，以及能不能把多个请求塞进同一个往返**。

补一句易错点：真实浏览器在 1.0 时代会开 6 条并行连接，5 个对象并行取，总时间也是 2 RTT。

408 不考并行连接，默认串行。

**例题二（自拟，状态码选择）**

某网站把 `/old` 永久迁移到 `/new`，希望浏览器和搜索引擎都更新地址。

应该用哪个状态码？如果只是这周做 A/B 测试，又该用哪个？

答：

```text
永久迁移：301 Moved Permanently
临时测试：302 Found（要求保持方法用 307）
```

用 302 做永久迁移是常见错误：搜索引擎不会改索引，老地址会一直被抓。

**例题三（自拟，304 省多少）**

一个 1.2 MB 的页面，第二次访问时服务器返回 304，响应报文约 300 字节。

省下多少比例？

答：

```text
1.2 MB = 1.2 × 1024 × 1024 = 1,258,291 B
（按 1 MB = 1024 KB 算）
304 响应 300 B
1 - 300 / 1258291 ≈ 99.976%
```

省下 99.98% 的流量，只多花一个来回。

带 `If-None-Match` 的条件请求，是 Web 性能里性价比最高的一招。

这里有个单位坑：如果按 `1 MB = 10^6 B` 算，1.2 MB = 1,200,000 B，比例是 99.975%，结论一样。

408 里"1 KB = 1024 B"是默认约定，但链路速率一律按十进制 b/s，两套单位别混。

## 7. 真实网络里长什么样

`curl -v` 会把整个过程摊开。

```text
$ curl -v https://example.com/

*   Trying 93.184.216.34:443...
* Connected to example.com (93.184.216.34) port 443
* ALPN: offers h2,http/1.1
* TLSv1.3 (OUT), TLS handshake, Client hello (1)
* TLSv1.3 (IN), TLS handshake, Server hello (2)
* TLSv1.3 (IN), TLS handshake, Certificate (11)
* SSL connection using TLSv1.3 / TLS_AES_128_GCM_SHA256
* ALPN: server accepted h2
> GET / HTTP/2
> Host: example.com
> User-Agent: curl/8.4.0
> Accept: */*
>
< HTTP/2 200
< content-type: text/html; charset=UTF-8
< cache-control: max-age=86000
< etag: "5f8-abc"
< content-length: 1256
<
<!doctype html>
```

（简化示意，行号与顺序随版本略有差异。）

这一屏里有五个信息点。

`ALPN: offers h2,http/1.1` 说明客户端在 TLS 握手时就把"我支持 h2"告诉了服务器。

`server accepted h2` 说明协商成功，后面的请求直接用 HTTP/2。

`TLS_AES_128_GCM_SHA256` 是 TLS 1.3 的套件名，它把密钥交换、认证、加密、MAC 打包成一个名字。

`>` 开头的行是请求首部，`<` 开头的是响应首部，`空行` 分隔首部和实体。

想强制用 1.1 对比，加一个参数。

```text
$ curl --http1.1 -v https://example.com/
> GET / HTTP/1.1
< HTTP/1.1 200 OK
```

（简化示意。）

只想要首部，用 `-I`（就是发 HEAD）。

```text
$ curl -I https://example.com/
HTTP/2 200
content-type: text/html; charset=UTF-8
cache-control: max-age=86000
etag: "5f8-abc"
last-modified: Thu, 09 Nov 2026 01:00:00 GMT
```

缓存验证可以直接手搓。

```text
$ curl -I -H 'If-None-Match: "5f8-abc"' https://example.com/
HTTP/2 304
etag: "5f8-abc"
```

（简化示意。）

304，没有实体，一个来回解决。

看证书链用 `openssl`。

```text
$ openssl s_client -connect example.com:443 -servername example.com -showcerts

Certificate chain
 0 s:CN = example.com
   i:C = US, O = Let's Encrypt, CN = R3
 1 s:C = US, O = Let's Encrypt, CN = R3
   i:C = US, O = Internet Security Research Group, CN = ISRG Root X1
---
Protocol  : TLSv1.3
Cipher    : TLS_AES_128_GCM_SHA256
Verify return code: 0 (ok)
```

（简化示意。）

`0` 是服务器证书，`1` 是中间 CA，根 CA 一般不在链里发（浏览器本地有）。

`s:` 是 subject（这张证书是谁），`i:` 是 issuer（谁签的）。

顺着 `i:` 往上走，走到一个浏览器信任的根，链就闭合了。

`Verify return code: 0 (ok)` 就是"链验通了"。

浏览器里看的是同一套东西，只是图形化。

DevTools 的 Network 面板，每行一个请求，列有：

```text
Name     资源路径
Status   200 / 304 / 404
Protocol h2 / http/1.1
Size     实际传输字节（压缩后）
Time     总耗时
```

点开某一项看 Timing 页，会拆成：

```text
Queueing            排队（连接数满了要等）
Stalled             等 TCP 连接
DNS Lookup          查域名
Initial connection  建 TCP
SSL                 TLS 握手
Request sent        发请求
Waiting (TTFB)      等首字节
Content Download    下载实体
```

（简化示意，新版 Chrome 把部分项合并了。）

这张表就是第 3 节那个九步图的实测版。

看到一个页面慢，先看哪一段长：DNS 长 → 换 DNS 或加预解析；SSL 长 → 上 TLS 1.3 或换 CDN；TTFB 长 → 后端慢；Content Download 长 → 带宽或压缩问题；Queueing 长 → 连接数不够，考虑 HTTP/2。

## 8. HTTP/1.0、1.1、2：连接方式的进化

为什么同一个 HTTP，换个版本就能差十倍？

因为内容一个字没变，变的只是"一条连接怎么用"。

网页的耗时里，绝大部分不是"数据在线上跑"，而是"等一个来回"。

同样一份内容，协议版本不同，体验差十倍。

差别全在"一条连接怎么用"。

HTTP/1.0 的默认行为是：**一个对象一条连接**。

```text
① 建 TCP
② 请求 HTML
③ 收 HTML
④ 关 TCP

⑤ 建 TCP
⑥ 请求 logo.png
⑦ 收 logo.png
⑧ 关 TCP

（30 个资源就重复 30 次）
```

（简化示意。）

每个 TCP 都要付三次握手的钱。

更要命的是 TCP 的"慢开始"：新连接初始拥塞窗口很小，前几个 RTT 传得慢，刚好在传输结束前才热起来，连接就关了。

HTTP/1.1 把默认改成持久连接（persistent connection），也叫长连接。

```text
建一次 TCP，上面串行跑 N 个请求响应
靠 Connection: keep-alive 保持（1.1 里是默认，写 close 才关）
```

省掉了每个对象的一次握手。

HTTP/1.1 还加了三样东西，408 都爱考。

```text
Host 首部        一个 IP 上放多个网站（虚拟主机），必须有
分块传输         Transfer-Encoding: chunked，不知道总长度时也能边算边发
范围请求         Range: bytes=0-1023，断点续传和视频拖动靠它
```

Host 首部是 1.1 的强制项。

没有它，服务器收到 `GET /index.html` 根本不知道你要哪个站，因为一个 IP 上可能挂了五百个域名。

这也解释了一个现象：用 IP 直连一个虚拟主机，经常返回默认站点或 400。

流水线（pipelining）是 1.1 里一个"看起来很美"的特性。

```text
客户端一次发三个请求，不等响应：
GET /a.png
GET /b.png
GET /c.png

服务器按顺序回：
200 a.png
200 b.png
200 c.png
```

省了两个 RTT，但问题在"按顺序"。

`a.png` 卡住了，后面的 `b`、`c` 就算已经准备好也只能等着。

这就是队头阻塞（Head-of-Line blocking，HOL）。

浏览器最后干脆不用流水线，改用"开 6 条并行连接"绕过它。

HTTP/2 换了个思路：**把一条连接切成很多条并行的流**。

```text
HTTP/2 一条 TCP 连接
┌──────────────────────────────────────┐
│ 流 1  HEADERS + DATA                 │
│ 流 3  HEADERS + DATA                 │
│ 流 5  HEADERS + DATA                 │
│ ……                                    │
└──────────────────────────────────────┘
每帧带一个流 ID，接收方按流 ID 重组
```

（简化示意。）

三个关键改动：

```text
二进制分帧     报文切成帧（HEADERS/DATA/SETTINGS/RST_STREAM/WINDOW_UPDATE）
多路复用       一条连接上并发多个流，互不阻塞
头部压缩       HPACK，用静态表 + 动态表 + 哈夫曼编码压首部
```

头部压缩解决的是另一个浪费：每个请求都带一大坨几乎一样的首部（User-Agent、Accept、Cookie），1.1 里每个请求都重发一遍。

HPACK 把首部字段编号，第二次只发编号和差异。

HTTP/2 还加了服务端推送（server push）和流优先级，前者实际用得很少，后者争议很大。

HTTP/2 没有解决根本问题：它还是跑在 TCP 上。

一个 TCP 包丢了，整个连接上所有的流都得等它重传。

这叫 TCP 层的队头阻塞。

HTTP/3 把底层换成 QUIC（跑在 UDP 上），每条流独立重传，才真正解决这个问题。

408 不考 HTTP/3，但知道"HTTP/2 解决了应用层 HOL，没解决传输层 HOL"这句话，能解释很多现象。

| 版本 | 默认连接 | 并发方式 | 头部压缩 | 队头阻塞 |
|---|---|---|---|---|
| HTTP/1.0 | 非持久 | 多开 TCP | 无 | 无（但慢） |
| HTTP/1.1 | 持久 | 流水线（有 HOL）/ 多连接 | 无 | 应用层有 |
| HTTP/2 | 持久 | 单连接多路复用 | HPACK | TCP 层有 |
| HTTP/3 | 持久 | QUIC 多路复用 | QPACK | 基本没有 |

（简化示意。）

## 9. Cookie 与 Session

为什么"无状态"会变成麻烦？

因为登录这件事天生有状态：第一次请求你交了密码，第一百次请求服务器还得认得出是你。

协议自己不肯记，就只能让客户端每次把证据带在身上。

HTTP 是无状态的。

服务器处理完一个请求，就把你忘干净了。

但登录这件事必须有状态：第一次请求你交了密码，第一百次请求服务器得知道"还是你"。

解决方式是一个很朴素的交换：**服务器给你一张纸条，你每次来都带着它**。

```text
① 客户端  POST /login  （用户名、密码）
② 服务器  HTTP/1.1 200 OK
          Set-Cookie: sid=abc123; Path=/; HttpOnly; Secure; Max-Age=3600
③ 客户端  把 sid=abc123 存起来（按域名存）
④ 之后每次请求
          GET /profile
          Cookie: sid=abc123
⑤ 服务器  查 sid=abc123 对应的会话，认出是你
```

（简化示意。）

这张纸条就是 Cookie，一个"名字=值"的小字符串，存在浏览器里，按域名隔离。

服务器那边存的那份档案叫会话（Session）。

关键的一句：**Cookie 里放的只是一个编号（SessionID），真正的状态在服务器上**。

如果把用户名、权限直接写进 Cookie，客户端一改就越权了。

> **如果没有它会怎样**：假设浏览器既不保存 Cookie，也不在请求里带任何身份信息。
> 那么你每点一个链接、每刷新一次页面，服务器看到的都是一个从没见过的陌生人——刚登录完，下一页又让你重新登录。
> 购物车加了三件商品，跳到结算页就空了；你填了半小时的表单，提交时服务器不知道这半小时属于谁。
> 所以"HTTP 无状态"不是缺陷，它只是把"记住人"这件事推给了上层，Cookie 就是把这根线接回来的那一段。

七个属性，408 可能只问前两个，但工程上都要懂。

```text
Domain    哪个域名下自动携带（example.com 及其子域）
Path      哪个路径下自动携带
Expires / Max-Age  什么时候过期；不写就是"会话 Cookie"，关浏览器就没
Secure    只在 HTTPS 下发送
HttpOnly  禁止 JavaScript 读（document.cookie 读不到），防 XSS 偷 Cookie
SameSite  Lax / Strict / None，跨站请求要不要带，防 CSRF
```

`HttpOnly` 和 `Secure` 是最便宜的两个加固手段，代价是零。

Cookie 有三个绕不开的限制，也是工程上的三个坑：

```text
容量    每个域名约 4 KB，装不下大东西
数量    每个域名几十个，超了会被挤掉
流量    每个请求都自动带，Cookie 越大请求越重
```

第三条直接催生了"静态资源用另一个域名"这个做法：`cdn.example.com` 不带 `www.example.com` 的 Cookie，请求就轻了。

> **反直觉的点**：HTTP 是"无状态"协议，但 Web 应用几乎都是有状态的——状态不是 HTTP 记的，是你每次请求都带上了 Cookie。

这句话反过来读，能解释三件事。

第一，"HTTP 无状态所以快"是半对半错。

无状态让服务器不用为每个客户端留内存，确实省资源。

但带 Cookie 之后，每个请求都多背几百字节，而且服务器还是要查会话，状态一点没少，只是搬到了应用层。

第二，为什么关掉 Cookie 就登不上。

因为纸条没了，服务器每次看到的都是一个陌生人。

第三，为什么"多设备登录"在 Cookie 方案里天然支持、在"本地存 token"方案里也支持。

因为真正的状态在服务器，客户端只是持有凭证。

Session 方案的代价是服务器要存。

单机好办，多台服务器就得共享（Redis 之类），否则第二次请求打到另一台机器就"不认识你"。

这就是负载均衡要配"会话保持"的原因。

另一条路是把状态签进 token（JWT），服务器不存，靠签名验真伪。

代价是没法"立刻踢人下线"（token 没过期就一直有效），以及 token 变长。

两种方案没有对错，只是把"状态放哪"这个选择做在了不同地方。

## 10. 代理与缓存

为什么缓存值得单独一节？

因为它不改任何一行业务代码，却能把重复访问的流量砍掉九成以上。

Web 性能优化的第一招，从来都是"别发请求"。

缓存是 HTTP 里最省钱的一招。

一个页面 1.2 MB，用户第二次访问，如果资源没变，服务器只回 300 字节的 304，省 99.98%。

（第 6 节例题三算过这笔账。）

缓存分两种，判据不同。

**强缓存**：不问服务器，直接用本地副本。

```text
Cache-Control: max-age=3600      3600 秒内不再请求
Cache-Control: no-store          完全不缓存（银行页面）
Cache-Control: no-cache          可以存，但每次都要验证
Cache-Control: private           只给浏览器缓存，代理不许存
Cache-Control: public            谁都能存（CDN 喜欢）
Cache-Control: s-maxage=600      专门给共享缓存（代理）的 max-age
Expires: Sun, 09 Nov 2026 04:00:00 GMT   HTTP/1.0 的绝对时间，优先级低于 max-age
```

**协商缓存**：问一句"我这份还能用吗"，能用就回 304。

```text
Last-Modified       资源最后修改时间（秒级）
If-Modified-Since   客户端把上次的 Last-Modified 带回来
→ 没变就回 304

ETag                资源内容的指纹（可以是哈希）
If-None-Match       客户端把上次的 ETag 带回来
→ 没变就回 304
```

两套判据的区别，一句话：

```text
Last-Modified 精确到秒，一秒内改两次会漏
ETag 是内容指纹，更准，但要多算一次哈希
```

优先级：`ETag` > `Last-Modified`；`Cache-Control` > `Expires`。

一个请求进来，缓存怎么判：

```text
① 有 Cache-Control: no-store ？ → 不缓存，直接回源
② 有本地副本且 max-age 未过期 ？ → 直接用（不发请求，DevTools 显示 from disk cache）
③ 过期了，带 If-None-Match / If-Modified-Since 去问
④ 服务器回 304 → 用本地副本，刷新过期时间
⑤ 服务器回 200 → 用新副本，替换旧的
```

（简化示意。）

代理（proxy）在中间扮演两个角色。

正向代理：替客户端出面。

```text
客户端 ──► 正向代理 ──► 服务器
（服务器只知道代理的 IP，不知道你是谁）
```

反向代理：替服务器出面。

```text
客户端 ──► 反向代理（nginx）──► 一堆后端服务器
（客户端以为在跟一台服务器说话）
```

反向代理顺手就做了三件事：负载均衡、TLS 卸载（证书装在 nginx 上，后端跑明文）、缓存。

CDN（Content Delivery Network，内容分发网络）是"反向代理 + 就近部署"的极端版本。

它把内容推到离用户几十公里的节点，把 RTT 从 100 ms 压到 10 ms。

这也解释了 `Cache-Control: public` 与 `private` 的分界线：能被 CDN 缓存的必须是"所有人看到都一样"的东西。

带用户信息的响应，一旦被 CDN 缓存，就是事故。

## 11. HTTPS：TLS 握手四步与证书链

为什么 HTTPS 要单独占一节？

因为前面讲的每一件事，都是在明文里跑的：你请求了什么、服务器返回了什么，路上任何一台设备都能看、能改。

HTTPS 要同时做到三件事——看不见（加密）、改不了（完整性）、认得出（身份），其中第三件最难。

HTTPS 不是新协议，是"HTTP 跑在 TLS 上"。

```text
HTTP 报文 → TLS 记录（加密）→ TCP → IP
```

端口 443。

它要解决 HTTP 的三个明文问题：

```text
窃听    中间人能看到你请求了什么、返回了什么
篡改    中间人能改内容（插广告、改转账账号）
冒充    中间人假装是银行，你也没法分辨
```

前两个靠加密，第三个靠证书。

先说"握手"这个词：通信双方在正式传数据之前，先来回几段消息，把"我支持哪些算法、你是谁、我们最后用哪把钥匙"讲清楚——这段预备对话就叫握手（handshake）。

它本身不传业务数据，只负责"把钥匙和身份谈好"。

TLS 1.2 的握手，简化成四步：

```text
① ClientHello
   客户端 → 服务器：我支持的 TLS 版本、密码套件列表、一个随机数 Rand_C、SNI（我要访问哪个域名）

② ServerHello + Certificate
   服务器 → 客户端：选定的套件、一个随机数 Rand_S、服务器证书链
                    （ECDHE 时还带密钥交换参数）

③ 客户端验证 + 密钥交换
   客户端：用内置的根 CA 公钥，一层层验签，确认这张证书
           确实是 example.com 的、没过期、没被吊销
           然后生成预主密钥（RSA 套件）或用 ECDHE 算共享密钥

④ 双方切换加密
   ChangeCipherSpec + Finished
   之后所有数据用会话密钥对称加密（AES-GCM 之类）
```

（简化示意。真实握手还有扩展字段、会话恢复、证书状态查询。）

四步里最关键的是第 ③ 步。

客户端凭什么相信"这个公钥是 example.com 的"？

答案是证书链。

```text
叶子证书（example.com 的公钥 + 域名 + 有效期）
   ↑ 由中间 CA 的私钥签名
中间 CA 证书
   ↑ 由根 CA 的私钥签名
根 CA 证书（自签名，预装在操作系统/浏览器的信任库里）
```

（简化示意。）

验证过程是自下而上的：

```text
① 用中间 CA 的公钥，验证叶子证书的签名
② 用根 CA 的公钥，验证中间 CA 证书的签名
③ 根 CA 在不在本地信任库里？在，链就闭合
```

任何一环断了，浏览器就报"证书无效"。

为什么必须有 CA（Certificate Authority，证书颁发机构）？

因为公钥本身不携带身份。

服务器说"这是我的公钥"，你没法验证。

如果直接信它，中间人也可以给你一个他自己的公钥，你也照信，然后他解密、转发、再加密，你全程无感。

CA 的作用是提供一个"大家都信的第三方签名"。

CA 用私钥给你的公钥和域名签个字，浏览器用内置的 CA 公钥验这个字。

信任的根不在数学里，在"你的系统出厂时预装了这些根证书"这个事实上。

所以自签名证书一定报警：不是它算错了，是链的终点不在信任库里。

这也解释了为什么证书要和域名绑定：证书里有一项 SAN（Subject Alternative Name），列出了这张证书能代表哪些域名。

拿 `a.com` 的证书去服务 `b.com`，浏览器会拒。

TLS 1.3 把握手压到一个 RTT（会话恢复还能 0-RTT）。

做法是：客户端在 ClientHello 里就把密钥交换参数一起发过去，服务器一次就能算完。

代价是去掉了 RSA 密钥交换，只保留 ECDHE 这类"前向安全"的方案。

前向安全的意思是：就算服务器的长期私钥哪天泄露了，以前录下来的流量也解不开，因为每次会话的密钥是临时算的、用完就扔。

记住三个数字：HTTP 80、HTTPS 443、TLS 1.2 两 RTT、TLS 1.3 一 RTT。

## 12. 容易混淆的点

第一组：无状态与无连接。

HTTP 是无状态（不记你是谁），不是无连接（TCP 连接可以一直开着）。

"HTTP 是无连接协议"这个说法在 1.1 之后就不对了。

第二组：301 与 302。

永久与临时。区别在缓存和搜索引擎。

第三组：401 与 403。

401 是"你还没证明你是谁"（该弹登录框）。

403 是"我知道你是谁，但你不能看"。

第四组：502、503、504。

502 是上游给了坏响应。

503 是自己过载或维护。

504 是等上游超时（网关超时）。

第五组：GET 与 POST。

GET 参数在 URL、可缓存、可收藏、有长度限制、幂等。

POST 参数在实体、默认不缓存、不可收藏、不幂等。

第六组：Cookie 与 Session。

Cookie 在客户端，Session 在服务器，Cookie 里装的是 Session 的钥匙。

第七组：持久连接与长轮询。

持久连接是 TCP 不关（1.1 默认）。

长轮询是"请求挂起直到有数据"，是应用层的技巧，两回事。

第八组：HTTPS 与"加密的 HTTP 协议"。

HTTPS 不是一个独立协议，是 HTTP over TLS。

所以它的报文格式和 HTTP 完全一样，只是外面套了一层加密。

把这一篇收成一张时间轴。

```text
时间 ──────────────────────────────────────────────────────►

DNS       TCP        TLS          HTTP            渲染
查名字    三次握手    握手换密钥    请求/响应        解析+绘制
  │         │          │            │               │
  │  1 RTT  │  2 RTT   │   1 RTT    │   多次往返     │
  │         │          │            │               │
  └── 有缓存就 0 ──────┴── 1.3 省一个 ┴── 2 多路复用 ─┘
```

（简化示意。）

每一段能省的都省了，剩下的就是物理距离决定的下限。

再收一张"协议版本与等待"的图：

```text
1.0   每个对象 2 RTT（握手 + 请求）
1.1   首对象 2 RTT，之后每对象 1 RTT
1.1+流水线  首对象 2 RTT，其余 1 RTT 打包
2     整页 2 RTT（一条连接全取回）
3     整页 1~2 RTT，丢包也不互相拖累
```

（简化示意。）

这一篇所有内容的共同背景，是第 20 篇讲过的拥塞控制。

HTTP/2 在一条连接上并发几十个流，TCP 看到的是一个巨大的窗口需求，一旦丢包，所有流一起减速。

应用层的优化，最终还是要跟传输层讲和。

## 14. 小结 + 下一篇

六个结论：

```text
HTTP = 请求行/状态行 + 首部 + 空行 + 实体，方法分安全与幂等
状态码五个族：1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错、5xx 服务器错
1.0 非持久 → 1.1 持久 + Host + 分块 → 2 多路复用 + HPACK → 3 QUIC
Cookie 是客户端纸条，Session 是服务器档案，状态在服务器
强缓存看 max-age，协商缓存看 ETag / Last-Modified，命中回 304
HTTPS = HTTP over TLS，443 端口，证书链靠预装的根 CA 闭合
```

一个必须带走的反直觉点：

```text
HTTP 无状态，但 Web 有状态。
状态不是协议记的，是你每次请求都带着 Cookie。
```
