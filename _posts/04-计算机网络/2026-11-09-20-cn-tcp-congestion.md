一条 TCP 连接刚建好，发送方要发 1 GB 数据。

它面对一个它完全不知道的网络：

```text
这条路径的瓶颈带宽是多少？   不知道
中间有几条队列，排了多长？    不知道
现在有多少条别的连接在抢？    不知道
```

没有任何报文会告诉它这些。

它只能做一件事：**试探。**

先发一点点，没出事就多发一点，出事了就往回收。

这套试探的规则，就是拥塞控制。

四个算法，一个变量：

```text
慢开始、拥塞避免、快重传、快恢复
变量只有一个：cwnd（拥塞窗口）
```

## 1. 拥塞控制和流量控制不是一回事

上一篇的流量控制，管的是**接收方**。

```text
rwnd 小了 → 接收方缓冲区快满了 → 少发一点，别淹死对方
```

这一篇的拥塞控制，管的是**网络**。

```text
cwnd 小了 → 路径上的队列快满了 → 少发一点，别压垮网络
```

两者的判断依据相似（都是"发太多"），但对象完全不同。

```text
流量控制：怕接收方处理不过来      —— 端到端，一个接收方的事
拥塞控制：怕网络中间转发不过来    —— 全局，所有发送方的事
```

为什么"全局"这件事特别难？

因为网络里没有调度中心。

没有哪个设备会发一条"现在别发了"的广播。

每台主机只能凭自己的观察（丢包、时延变化）去猜整体状态。

```text
这是一个典型的分布式协同问题：
每个参与者只看到局部信息，
却要让整体不崩。
```

崩了会怎样？

```text
所有发送方都猛发
→ 队列溢出，大量丢包
→ 丢包触发重传，重传又是新流量
→ 有效吞吐量趋近于 0
```

这叫**拥塞崩溃（congestion collapse）**。

1986 年互联网真的发生过一次，吞吐量从 32 kbps 掉到 40 bps，跌了近千倍。

TCP 的拥塞控制就是在那之后加进去的。

## 2. cwnd：发送方对网络的猜测

拥塞窗口（congestion window，cwnd）是一个纯粹的本机变量。

**没有任何报文携带它。**

发送方自己在内存里维护一个数，单位是 MSS（最大报文段长度）。

```text
cwnd = 10  表示"我估计现在能连续发 10 个 MSS 而不出事"
```

它和 rwnd 的关系，上一篇已经说过：

```text
发送窗口 = min(rwnd, cwnd)
```

这一篇只关心 cwnd 怎么变。

先记住三个初始值（408 的约定）：

```text
cwnd 初始值 = 1 个 MSS
ssthresh（慢开始门限）初始值 = 一个很大的数，比如 16 或 65535
RTO 初始值 = 1 秒
```

现实和课本有差异，知道就行：

```text
RFC 5681 允许初始 cwnd 取 1–10 个 MSS
Linux 实际用 10 个 MSS（约 14600 字节）
```

所以抓包时会发现，Linux 一上来就发 10 个段，而不是 1 个。

408 按 1 算。

ssthresh 这个名字很直白：**slow start threshold，慢开始门限**。

它是 cwnd 的一个分界线：

```text
cwnd < ssthresh   用慢开始（指数增长）
cwnd ≥ ssthresh   用拥塞避免（线性增长）
```

这条规则是整个拥塞控制的主干。

两个算法就是在 ssthresh 的两侧切换。

## 3. 慢开始：从 1 个 MSS 起，每 RTT 翻倍

慢开始的规则只有一句：

```text
每收到一个 ACK，cwnd 加 1 个 MSS。
```

看起来是"每 ACK 加一"，效果却是"每 RTT 翻倍"。

推一遍就明白：

```text
第 1 轮：cwnd = 1，发 1 个段，收到 1 个 ACK → cwnd = 2
第 2 轮：cwnd = 2，发 2 个段，收到 2 个 ACK → cwnd = 4
第 3 轮：cwnd = 4，发 4 个段，收到 4 个 ACK → cwnd = 8
第 4 轮：cwnd = 8，发 8 个段，收到 8 个 ACK → cwnd = 16
```

一个 RTT 里，cwnd 里的每个段都回来一个 ACK，每个 ACK 让 cwnd 加一。

所以一个 RTT 下来，cwnd 正好加了自己那么多：翻倍。

```text
轮次   1    2    3    4    5     6
cwnd   1 →  2 →  4 →  8 → 16 →  32
```

指数增长。

10 轮之后就是 1024 个 MSS，约 1.5 MB。

**这里就是那个反直觉的点：**

> 慢开始一点都不慢。它指的是"从 1 个 MSS 这么小的窗口开始"，不是"增长速度慢"。论增长速度，它比拥塞避免快得多——一个是指数，一个是线性。

名字的来源是历史：在慢开始之前，TCP 一建连就把整个接收窗口灌出去，经常一上来就把网络打爆。

加了慢开始之后，起点被压到 1 个 MSS，所以叫"慢开始"。

```text
"慢"修饰的是起点，不是斜率。
```

它在什么时候停？

当 cwnd 涨到 ssthresh。

```text
cwnd = 16，ssthresh = 16
→ 下一轮改用拥塞避免
```

为什么必须在某个点停下来？

因为指数增长不可能持续。

```text
1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024 ...
```

涨到第 20 轮就是五十多万个 MSS，任何链路都撑不住。

ssthresh 就是"上次出事时的窗口的一半"，它大致标记了网络的容量上限。

在它下面可以猛涨（因为离危险还远），靠近它就得慢下来。

## 4. 拥塞避免：每个 RTT 加 1

进入拥塞避免之后，规则变了：

```text
每经过一个 RTT，cwnd 加 1 个 MSS。
```

从"翻倍"变成"加一"。

```text
轮次    5    6    7    8    9
cwnd   16 → 17 → 18 → 19 → 20
```

实际实现并不是"每个 RTT 加一"，而是"每个 ACK 加 MSS/cwnd"。

因为一个 RTT 里有 cwnd 个 ACK，累加起来正好是 1 个 MSS：

```text
每个 ACK：cwnd += MSS × MSS / cwnd
cwnd 个 ACK 之后：cwnd += MSS
```

这叫**加性增（additive increase）**。

一个完整的增长过程就是：

```text
指数增长（慢开始） → 到达 ssthresh → 线性增长（拥塞避免）
```

画出来是"先陡后缓"的形状。

线性增长有个重要含义：**它永远不会自己停下来。**

只要不丢包，cwnd 会一直加下去，直到：

```text
撞上 rwnd 的上限
或者把网络撑爆，出现丢包
```

所以 TCP 的稳态是一个不断试探、不断越界、不断被惩罚的循环。

```text
加性增，乘性减
Additive Increase, Multiplicative Decrease
```

这六个字（AIMD）是拥塞控制的核心。

它有一个很漂亮的性质：多条连接共享一条链路时，会收敛到大致公平。

```text
两条连接，一条 cwnd 大，一条小
→ 丢包时都减半，大的减得多，小的减得少
→ 反复几轮，两条趋于相等
```

## 5. 超时与三个重复 ACK：两种完全不同的反应

cwnd 增长到某一点，一定会出事。

出事有两种方式，TCP 对它们的反应完全不同。

| | 超时（RTO 到期） | 三个重复 ACK |
|---|---|---|
| 说明什么 | 严重：可能整窗都丢了，或者路径断了 | 轻微：只丢了个别段，后面的段还能到 |
| ssthresh | 当前 cwnd 的一半 | 当前 cwnd 的一半 |
| cwnd | 直接降到 1 个 MSS | 降到 ssthresh（减半后的值） |
| 之后进入 | 慢开始（重新指数增长） | 拥塞避免（直接线性增长） |
| 恢复速度 | 慢，要从 1 重新爬到峰值 | 快，峰值的一半起步 |

关键差别在最后两行。

**超时**是"我完全不知道网络现在什么状况"，所以保守到底：cwnd 归 1，从头再来。

```text
超时 → ssthresh = max(cwnd/2, 2)
      cwnd = 1
      → 慢开始
```

**三个重复 ACK**是"后面的包都到了，只丢了一个"，网络显然还在工作，还有吞吐能力，所以只减半。

```text
三个重复 ACK → ssthresh = max(cwnd/2, 2)
              cwnd = ssthresh
              → 拥塞避免
```

为什么减半，不是减到 1/4 或 3/4？

减半是一个经验上的平衡点：

```text
减太少：网络还没缓过来，继续丢
减太多：带宽浪费，恢复太慢
```

减半的好处是，cwnd 的峰值和谷值形成 2:1 的锯齿，链路利用率不会掉得太惨。

而"乘性减"（乘以 0.5）保证多条连接能收敛到公平，"加性增"保证利用率能慢慢爬回来。

这一对组合是经过几十年验证的。

## 6. 快重传与快恢复

上一节的"三个重复 ACK"这条路，展开就是两个算法。

**快重传（fast retransmit）**：

```text
收到 3 个重复 ACK，立刻重传缺失的那个段，不等 RTO 到期。
```

这一条上一篇讲过，属于可靠传输，但它同时也是拥塞控制的信号源。

**快恢复（fast recovery）**：

```text
快重传之后不要回到慢开始，直接把 cwnd 设成 ssthresh，进入拥塞避免。
```

为什么可以不回慢开始？

因为三个重复 ACK 已经证明了：**后面的数据能到达接收方。**

网络没有完全堵死，只是丢了个别包。

如果这时候把 cwnd 打回 1，等于把一个还能跑的网络当成死了，白白浪费十几个 RTT 去重新爬坡。

```text
超时：网络状况未知 → 从 1 重来
三重复 ACK：网络还在工作 → 减半继续
```

这就是"快恢复"这个名字的含义：**快速恢复到减半后的窗口，而不是快速恢复原窗口。**

课本上写的流程：

```text
收到 3 个重复 ACK：
    ssthresh = cwnd / 2
    cwnd = ssthresh
    执行快重传
    进入拥塞避免
```

一处教科书不写、但真实实现会做的细节：

Reno 实现会把 cwnd 先设成 `ssthresh + 3`，因为那三个重复 ACK 意味着有三个段已经离开了网络，可以多放三个段进来。

每多收到一个重复 ACK，cwnd 再临时加 1；收到新数据的 ACK 时，把 cwnd 压回 ssthresh。

408 按 `cwnd = ssthresh` 算就够了。

## 7. 一条完整时间轴：1 → 20 轮

设定：

```text
初始 cwnd = 1 个 MSS
初始 ssthresh = 16 个 MSS
假设每一轮都把窗口发满，都能收到 ACK（除了出事那两轮）
第 9 轮发生超时
第 17 轮收到 3 个重复 ACK
```

逐轮推：

```text
轮次   本轮 cwnd   发生了什么
 1        1       慢开始，起点
 2        2       翻倍
 3        4       翻倍
 4        8       翻倍
 5       16       到达 ssthresh = 16，下一轮起改用拥塞避免
 6       17       拥塞避免，每轮 +1
 7       18       +1
 8       19       +1
 9       20       +1；本轮发生超时
10        1       超时处理：ssthresh = 20/2 = 10，cwnd = 1，回到慢开始
11        2       翻倍
12        4       翻倍
13        8       再翻倍是 16，超过 ssthresh = 10，所以取 10
14       10       进入拥塞避免
15       11       +1
16       12       +1
17       13       +1；本轮收到 3 个重复 ACK
18        6       快恢复：ssthresh = 13/2 = 6（向下取整），cwnd = 6，直接拥塞避免
19        7       +1
20        8       +1
```

把每一次变化标出来：

```text
第 5 轮   cwnd 到达 ssthresh → 慢开始切换成拥塞避免
第 9 轮   超时 → ssthresh 从 16 改为 10，cwnd 从 20 掉到 1
第 13 轮  翻倍会越过 ssthresh（8×2=16 > 10）→ cwnd 直接取 10
第 14 轮  进入拥塞避免
第 17 轮  三个重复 ACK → ssthresh 从 10 改为 6，cwnd 从 13 掉到 6
第 18 轮  快恢复后不进慢开始，直接 +1
```

有三个地方容易算错，逐个说清。

**一、超时那一轮，ssthresh 用的是出事时的 cwnd。**

第 9 轮的 cwnd 是 20，所以 ssthresh = 20/2 = 10，不是 19 或 21。

ssthresh 只在出事那一刻更新，用的是那一刻的 cwnd。

**二、8 翻倍到 16 超过 ssthresh = 10 时，取 10 而不是 16。**

慢开始的停止条件是"cwnd 到达 ssthresh"，而不是"cwnd 不超过 ssthresh"。

所以这一步是"涨到门限就停"，直接落在 10。

**三、快恢复之后不经过慢开始。**

第 17 轮出事，第 18 轮 cwnd 就是 6，第 19 轮 7，第 20 轮 8。

如果这里错当成超时处理，第 18 轮会变成 1，后面全错。

顺手一问：这 20 轮一共发了多少个 MSS？

```text
第 1–5 轮：  1+2+4+8+16 = 31
第 6–9 轮：  17+18+19+20 = 74
第 10–13 轮：1+2+4+8 = 15
第 14–17 轮：10+11+12+13 = 46
第 18–20 轮：6+7+8 = 21

合计：31 + 74 + 15 + 46 + 21 = 187 个 MSS
```

## 8. cwnd 曲线长什么样

把上面那张表画成图。

每个 `#` 表示"该轮的 cwnd 达到了这个高度"，柱子顶端连起来就是 cwnd 曲线。

```text
cwnd
20 |........#...........   ← 第 9 轮，超时前的高点
19 |.......##...........
18 |......###...........
17 |.....####...........
16 |....#####...........   ← 第 5 轮到达 ssthresh = 16
15 |....#####...........
14 |....#####...........
13 |....#####.......#...   ← 第 17 轮，三个重复 ACK
12 |....#####......##...
11 |....#####.....###...
10 |....#####....####...   ← 第 14 轮，新的 ssthresh = 10
 9 |....#####....####...
 8 |...######...#####..#   ← 第 20 轮，cwnd = 8
 7 |...######...#####.##
 6 |...######...########   ← 第 18 轮，快恢复后的 cwnd = 6
 5 |...######...########
 4 |..#######..#########
 3 |..#######..#########
 2 |.########.##########
 1 |####################
   +--------------------
    12345678901234567890
    慢开始|拥塞避免|超时→慢开始|拥塞避免|快恢复
```

读这张图，三个特征最重要。

**锯齿。**

上升是慢的（线性），下降是陡的（直接砍半或砍到底）。

```text
           /|        /|
          / |       / |
         /  |      /  |
        /   |     /   |
       /    └────┘    └──
```

**下降的位置就是出事的位置。**

```text
掉到 1        → 超时
掉到一半      → 三个重复 ACK（快恢复）
```

**峰值由 ssthresh 决定。**

每次下降时，新的 ssthresh 就是"当前 cwnd 的一半"，也就是下一个锯齿的顶点大致位置。

```text
第 9 轮峰值 20 → ssthresh 10 → 下一个峰值大约在 10 附近开始线性上升
```

注意"大约"两个字。

拥塞避免是线性的，只要不丢包，它不会停在 ssthresh 上，会一直往上加。

ssthresh 只决定"从哪开始线性增长"，不决定"涨到哪停"。

真正让它停的是下一次丢包。

## 9. 发送窗口 = min(rwnd, cwnd)

这一篇的主角是 cwnd，但实际能发多少还要看 rwnd。

```text
发送窗口 = min(rwnd, cwnd)
```

四种组合：

```text
rwnd = 64 KB，cwnd = 10 MSS（14600 B）  → 窗口 10 MSS，瓶颈在网络
rwnd = 6 MSS，cwnd = 10 MSS             → 窗口 6 MSS，瓶颈在接收方
rwnd = 0                                → 停发，靠坚持定时器恢复
cwnd = 1（刚超时），rwnd = 64 KB         → 窗口 1 MSS，网络刚被打回原形
```

408 有一类题专门考这个：

```text
"某时刻 cwnd = 16，rwnd = 8，问发送窗口多大？"
→ 8。拥塞窗口再大也没用，接收方只收得下 8。
```

还有一类题更绕：

```text
"发送方收到了 3 个重复 ACK，此时 cwnd = 12，rwnd = 4，问接下来能发多少？"
→ rwnd 是 4，所以窗口是 4；但快恢复后 cwnd 变成 6，min(4,6) 还是 4。
```

这类题的套路：**先更新 cwnd，再取 min。**

## 10. Tahoe、Reno 与 BBR：三代想法

前面讲的流程，其实是两个版本的混合。

| | TCP Tahoe | TCP Reno |
|---|---|---|
| 三个重复 ACK | 快重传，然后 cwnd = 1 | 快重传 + 快恢复，cwnd = ssthresh |
| 超时 | cwnd = 1 | cwnd = 1 |
| 有无快恢复 | 没有 | 有 |
| 后果 | 每次丢包都从 1 重爬 | 单个丢包只减半 |

Tahoe 是 1988 年的版本，Reno 是 1990 年的。

两者差的就是"快恢复"这一步。

```text
Tahoe：丢一个包 = 从头再来
Reno：丢一个包 = 减半继续
```

408 现在默认考 Reno（有快恢复）。

再往后是 NewReno（处理一个窗口里丢多个包）、CUBIC（用三次函数代替线性增长，Linux 默认）、BBR。

BBR 值得单独说一句，因为它的思路完全不同。

```text
之前所有算法：把丢包当成拥塞信号
BBR：丢包不一定等于拥塞，队列排满才是
```

BBR 直接测量两个量：

```text
瓶颈带宽 BtlBw    一段时间内 ACK 回来的最大速率
最小 RTT minRTT   路径的物理传播时延
```

然后把 cwnd 设成它们的乘积（带宽时延积 BDP）：

```text
cwnd ≈ BtlBw × minRTT
```

它不靠丢包判断，所以能在有轻微丢包的链路上（比如跨洋链路）保持高吞吐。

代价是它对公平性不友好：BBR 连接和 CUBIC 连接抢带宽时，BBR 常常占便宜。

## 11. 容易混淆的点

**cwnd 不是 rwnd。**

cwnd 是发送方猜的网络容量，rwnd 是接收方通告的缓冲余量。

**慢开始不慢。**

指数增长，每 RTT 翻倍。名字说的是起点。

**ssthresh 是在出事时更新的，不是随时更新。**

只有超时和三个重复 ACK 这两个时刻才改它。

**超时和快恢复的处理不一样。**

前者 cwnd = 1 走慢开始，后者 cwnd = ssthresh 走拥塞避免。这是最高频的错点。

**快恢复不是"恢复到原来的窗口"。**

是恢复到减半后的值。

**cwnd 是每条连接独立的。**

一条连接丢包，不会影响另一条。这也是为什么"多条短连接"比"一条长连接"更容易抢占带宽。

**接收窗口为零不是网络拥塞。**

那是接收方的事，用坚持定时器解决，跟 cwnd 无关。

**拥塞避免阶段 cwnd 增长到 ssthresh 以上是正常的。**

ssthresh 只是切换点，不是天花板。

## 12. 408 怎么考

题型很固定：

```text
给初始 cwnd 和 ssthresh，画 cwnd 随 RTT 变化的曲线
问某一轮之后 cwnd 是多少
问超时和三个重复 ACK 分别怎么处理
问某时刻的发送窗口
```

下面这道是自拟的，和前面那条时间轴不重复。

```text
某 TCP 连接：
  ssthresh = 24 个 MSS
  cwnd = 24 个 MSS，当前处于拥塞避免阶段
  rwnd = 6 个 MSS

问：
(1) 此时收到 3 个重复 ACK，cwnd 和 ssthresh 变成多少？进入什么阶段？
(2) 之后又顺利过了 4 个 RTT，cwnd 是多少？
(3) 此时发生超时，cwnd 和 ssthresh 变成多少？
(4) 超时后再过 3 个 RTT，cwnd 是多少？处于什么阶段？
(5) 此时实际的发送窗口是多少？
```

解。

（1）三个重复 ACK。

```text
ssthresh = 24 / 2 = 12
cwnd     = ssthresh = 12
阶段     = 拥塞避免（快恢复，不经过慢开始）
```

（2）拥塞避免 4 个 RTT。

```text
12 → 13 → 14 → 15 → 16
cwnd = 16 个 MSS
```

（3）超时。

```text
ssthresh = 16 / 2 = 8
cwnd     = 1
阶段     = 慢开始
```

注意这里的 ssthresh 用的是超时那一刻的 cwnd = 16，不是 24。

（4）过了 3 个 RTT。

```text
第 1 轮：cwnd = 1，之后翻倍 → 2
第 2 轮：cwnd = 2，之后翻倍 → 4
第 3 轮：cwnd = 4，之后翻倍 → 8

3 个 RTT 之后 cwnd = 8，正好等于 ssthresh
第 4 轮开始进入拥塞避免
```

所以第 3 轮结束时 cwnd = 8，阶段是慢开始的末尾，下一轮切拥塞避免。

（5）实际发送窗口。

```text
cwnd = 8，rwnd = 6
发送窗口 = min(8, 6) = 6 个 MSS
```

再补一个常见的问法：

```text
"第 9 个 RTT 之后 cwnd 是多少？"
```

这类题一定要先弄清"第 n 个 RTT 之后"的计数方式。

判断标准是：慢开始阶段，第 n 轮开始时的 cwnd 是 `2^(n-1)`，一直涨到撞上 ssthresh。

所以初始 cwnd = 1、ssthresh = 16 时：

```text
第 1 轮开始 = 1
第 2 轮开始 = 2
第 5 轮开始 = 16   （到达门限，本轮起转拥塞避免）
第 6 轮开始 = 17
第 9 轮开始 = 20
```

这个"第 n 轮开始时"的口径，正好对应第 7 节那张表。

题目里给了表格就按表格填，别自己另立一套口径。

## 13. 真实网络里长什么样

先看一条连接当前的 cwnd 和 ssthresh。

```text
$ ss -tin dst 93.184.216.34
ESTAB 0 0 192.168.1.10:51234 93.184.216.34:443
     cubic wscale:7,7 rto:204 rtt:1.5/0.5 ato:40 mss:1448
     cwnd:10 ssthresh:7 bytes_sent:20480 bytes_acked:19032
     segs_out:120 data_segs_out:40 retrans:0/3
```

（简化示意）

```text
cwnd:10       拥塞窗口 10 个 MSS（刚建连，还在慢开始）
ssthresh:7    门限 7，说明之前出过事，cwnd 已经越过门限了？
```

这里有个容易看错的地方：`cwnd:10` 大于 `ssthresh:7`。

说明这条连接刚发生过一次丢包，ssthresh 被降到 7，但 cwnd 还在往下走的路上，或者快恢复的临时膨胀还没收回。

真实的 cwnd 轨迹要连续采样才看得出来。

```text
$ for i in $(seq 1 6); do ss -tin dst 93.184.216.34 | grep -o 'cwnd:[0-9]*'; sleep 1; done
cwnd:10
cwnd:20
cwnd:41
cwnd:83
cwnd:166
cwnd:332
```

（简化示意）

一秒一个点，看到的是翻倍——这就是慢开始。

如果看到的是

```text
cwnd:332
cwnd:333
cwnd:334
cwnd:335
```

那就是进了拥塞避免，每 RTT 加一。

再看全机的拥塞事件统计。

```text
$ netstat -s | grep -iE "retrans|timeout|fast|slow"
    1203 segments retransmitted
    8 fast retransmits
    2 timeouts
    47 slow start retransmits
```

（简化示意）

```text
fast retransmits      靠三个重复 ACK 补救的次数 → 只减半
timeouts              靠超时补救的次数 → 归 1，代价最大
slow start retransmits 慢开始期间的重传次数
```

如果 `timeouts` 占比很高，说明丢包是大面积的（整窗丢），网络真的堵了。

`nstat` 里还有更细的计数器：

```text
$ nstat -az TcpExtTCPTimeouts TcpExtTCPFastRetrans TcpExtTCPSlowStartRetrans TcpExtTCPLostRetransmit
TcpExtTCPTimeouts            2                  0.0
TcpExtTCPFastRetrans         8                  0.0
TcpExtTCPSlowStartRetrans    47                 0.0
TcpExtTCPLostRetransmit      0                  0.0
```

（简化示意）

看拥塞算法。

```text
$ sysctl net.ipv4.tcp_congestion_control net.ipv4.tcp_available_congestion_control
net.ipv4.tcp_congestion_control = cubic
net.ipv4.tcp_available_congestion_control = reno cubic bbr
```

（简化示意）

换算法：

```text
$ sysctl -w net.ipv4.tcp_congestion_control=bbr
```

只能改新建连接的默认算法，已建立的连接不受影响。

再看初始窗口。

```text
$ ip route show default
default via 192.168.1.1 dev eth0 proto dhcp src 192.168.1.10 metric 100
    cache
```

（简化示意）

`initcwnd` 和 `initrwnd` 可以挂在路由上：

```text
$ ip route change default via 192.168.1.1 dev eth0 initcwnd 10
```

这就是"为什么 Linux 一上来就发 10 个段"的来源。

Wireshark 里看 cwnd 的变化，用流图最直观：

```text
Statistics → TCP Stream Graphs → Time-Sequence (Stevens)
Statistics → TCP Stream Graphs → Window Scaling
```

（简化示意）

前者画的是"在途字节数（bytes in flight）"，形状应该和你手算的 cwnd 曲线一致：

```text
在途字节
   │        /|
   │       / |
   │      /  |
   │     /   |
   │    /    |
   │   /     |
   └──┴──────┴──── 时间
      上升段是加性增，竖直下落是乘性减
```

（简化示意）

如果图上的锯齿特别密、峰值特别低，基本可以判断这条路径在持续丢包。

如果锯齿很稀、峰值贴着带宽时延积，说明网络很健康。

## 14. 小结

拥塞控制这一篇，压成几块：

```text
控制对象：网络（cwnd），不是接收方（rwnd）。
发送窗口 = min(rwnd, cwnd)。
慢开始：从 1 个 MSS 起，每 RTT 翻倍，到 ssthresh 为止。
拥塞避免：每 RTT 加 1，线性。
超时：ssthresh = cwnd/2，cwnd = 1，慢开始。
三重复 ACK：ssthresh = cwnd/2，cwnd = ssthresh，拥塞避免。
```

一句话记住 AIMD：

```text
加性增，乘性减 —— 慢慢试探，出事就砍半。
```

再记一句最容易错的：

```text
超时归 1，快恢复减半。
这两个处理方式，是 408 拥塞控制题的全部区分点。
```
