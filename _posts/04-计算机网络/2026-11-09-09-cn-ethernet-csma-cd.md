一个 408 选择题的问法：

```text
以太网的最小帧长是多少？为什么是 64 字节？
```

很多人能背出 64。

再问一句"为什么"，就卡住了。

答案不是"太短的帧不好处理"。

答案是一句很物理的话：

```text
发送方必须在帧发完之前听到冲突。
帧一发完，就再也听不到了。
```

这一篇就从这句话开始，把 64 这个数字推出来。

## 1. 共享一根线，麻烦在哪

最早的以太网不是星形，是一根同轴电缆。

十几台机器挂在同一根线上。

```text
  主机A      主机B      主机C      主机D
    │          │          │          │
════╪══════════╪══════════╪══════════╪═════  同轴电缆
                    ↑
              收发器（tap）
```

这根线是**共享介质（shared medium）**。

同一时刻只能有一个站在发。

两个人同时说话，声音叠在一起，谁都听不清。

这就是**冲突（collision）**。

问题变成一句话：

```text
这根线现在能不能发？
```

谁来决定？

没有裁判。

只能每个站自己听、自己判断。

历史上这件事有三种解法，各有各的代价。

```text
令牌环：发一个令牌，拿到令牌才能发
        → 不会撞，但要维护令牌，一个站挂了全网停

主从轮询：主机挨个问"你要发吗"
        → 不会撞，但主机是单点，还慢

随机争用：谁想发就发，撞了再说
        → 不用裁判，代价是冲突
```

以太网选了第三种。

理由很工程：**没有中心、没有令牌、站点随时上下线。**

代价就是得自己解决冲突。

以太网给出的答案是 CSMA/CD。

## 2. 最小模型：CSMA/CD 的四个动作

名字就是四个动作。

```text
CS  Carrier Sense      载波监听    先听后发
MA  Multiple Access    多路访问    大家一起用这根线
CD  Collision Detection 冲突检测    边听边发
    Binary Exponential Backoff     冲突停发，随机重发
```

展开成四句话：

```text
先听后发：要发之前先听，线忙就等。
边听边发：发的过程中一直听，比较收到的和自己发的。
冲突停发：听出不对，立刻停，发一个冲突加强信号（jam）。
随机重发：等一个随机的时间再试，越撞等得越久。
```

四句话里，最容易被忽略的是第二句。

逐条拆开，每一句都对应一个具体的硬件动作。

```text
先听后发
  听的是"线路上有没有信号能量"，不是听里面装了什么数据。
  有能量 → 忙，继续等；没能量 → 空闲，可以发。
  陷阱：你听到的"空闲"，其实是 τ 之前的线路状态。

边听边发
  发的同时保持接收，把"我发出去的波形"和"我收到的波形"比。
  两者不一致 → 说明有第三方信号叠上来了 → 判定冲突。
  这个比较是模拟电路做的，不是软件做的。

冲突停发
  一旦判定冲突，立刻停止发送（不要把一个坏帧发完）。
  然后发一串冲突加强信号（jam），保证所有相关站都确知撞了。
  发 jam 而不是静默，是为了避免"有人以为没事"。

随机重发
  用二进制指数退避算一个等待时间，等完了重新走一遍流程。
```

"边听边发"是整个 CSMA/CD 的支点。

因为"听得出冲突"这个能力，是它区别于 CSMA/CA 的唯一硬件前提。

```text
能边发边听 → 撞了能立刻知道 → 停下来重发      （CSMA/CD）
不能边发边听 → 撞了也不知道 → 只能事先避免      （CSMA/CA）
```

有线能，无线不能。

第 10 篇专门讲无线为什么不能。

## 3. 争用期：2τ 到底是什么

先定义 τ。

```text
τ = 单程端到端传播时延
2τ = 往返传播时延 = 争用期（contention period）
```

为什么是"往返"，不是"单程"？

因为冲突最坏的情况，发生在对方**刚要发**的那一瞬间。

走一遍最坏情况。

```text
 A ●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━● B
   ├────────────── τ ───────────────┤

t = 0      A 开始发送帧
t = τ−ε    B 一直在听，但 A 的信号还没到，B 以为线空，开始发送
t = τ      A 的信号到达 B，B 立刻检测到冲突，停发
t = 2τ−ε   B 的信号才回到 A，A 这时才检测到冲突
```

关键在最后一行。

A 直到 `2τ−ε` 才知道撞了。

所以 A 必须保证：**到 2τ 这一刻，自己的帧还没发完。**

如果帧在 2τ 之前就发完了，A 会以为"发成功了"，收工走人。

那个撞坏的帧还在线上跑，没人重发。

这就是"帧太短"的真正问题。

反过来想一遍，如果帧只有 10 字节：

```text
10 B 在 10 Mbps 上只要 8 μs
8 μs < 51.2 μs 的争用期
帧早在听到冲突之前就发完了
```

发送方乐观地认为"发成功了"，实际上那个帧已经被撞成一堆噪声。

所以帧长不能"随便短"，它有硬下界，下界由时间决定。

写成不等式：

```text
发送时延 ≥ 2τ
```

`发送时延 = 帧长 / 数据率`，所以：

```text
帧长 ≥ 2τ × 数据率
```

**这就是最小帧长的全部来源。**

> **反直觉的点**：最小帧长不是为了"帧太短不好处理"，也不是为了凑一个好看的整数。
> 它是一条时间约束：发送方在帧发完之前，必须还听得见冲突。
> 帧一发送完，冲突就变成了"事后才知道"，以太网的重发机制就失效了。

## 4. 64 字节是怎么算出来的

10 Mbps 以太网，争用期取 51.2 μs。

代进不等式：

```text
2τ            = 51.2 μs
数据率         = 10 Mbps = 10 × 10^6 b/s

最小帧长 = 51.2 μs × 10 Mbps
         = 51.2 × 10^-6 s × 10 × 10^6 b/s
         = 512 bit
         = 64 B
```

512 bit，正好 64 字节。

这不是巧合，是标准**倒推**出来的。

先定"最小帧 64 B"这个好记的数，再反推 2τ：

```text
2τ = 512 bit / 10 Mbps = 51.2 μs
```

有了 51.2 μs，才去定"一个冲突域最大能有多大"。

传播速度按 2×10^8 m/s 估：

```text
最大跨度 = 51.2 μs × 2×10^8 m/s / 2
         = 5120 m  （单程上限）
```

实际标准给出的是 2500 m，留了大量余量给中继器和收发器电路。

```text
2500 m 往返 = 2 × 2500 / 2×10^8 = 25 μs
25 μs 只是电缆本身，
剩下 26.2 μs 全留给了 4 个中继器的处理时延和收发器时延。
```

所以这条链是绑死的：

```text
最小帧长 ← 争用期 ← 最大网段跨度
三个数只要定两个，第三个就定了。
```

换成 100 Mbps 呢？

如果跨度和 2τ 都不变：

```text
最小帧长 = 51.2 μs × 100 Mbps = 5120 bit = 640 B
```

640 字节的帧太重了。

标准的选择是**反过来缩跨度**：100BASE-T 仍然用 64 B 最小帧，把冲突域直径从 2500 m 压到约 200 m。

这就是快速以太网"网线最多 100 米"这条常识的由来之一。

同一套约束，三种取舍，摆在一起看：

```text
速率       争用期 2τ      最小帧长   冲突域直径
10 Mbps    51.2 μs        64 B       2500 m
100 Mbps   5.12 μs        64 B       约 200 m
1 Gbps     4.096 μs       64 B       约 200 m（半双工，靠载波延伸撑住）
```

注意 1 Gbps 那一行：争用期从"512 比特时间"变成了"4096 比特时间"。

按 1 Gbps 算，4096 bit = 4.096 μs，比 100 Mbps 的 5.12 μs 还短。

```text
64 B 的帧在 1 Gbps 上只要 0.512 μs，
远小于 4.096 μs 的争用期，
所以短帧必须用载波延伸补到 512 B 才敢上线路。
```

到千兆以太网，半双工下更极端：

```text
64 B 在 1 Gbps 上只要 0.512 μs
而 2τ 还是那个量级
```

标准干脆把争用期从"512 比特时间"改成"512 **字节**时间"（4096 比特时间 = 4.096 μs），短帧用**载波延伸（carrier extension）**补齐。

全双工则完全不玩这套，后面第 10 节讲。

## 5. 二进制指数退避：撞了以后等多久

冲突停了，不能马上重发。

两个站同时停、同时重发，必然再撞。

所以要等一个**随机**时间。

规则叫**二进制指数退避（binary exponential backoff）**。

```text
第 i 次冲突（i = 1, 2, 3, …）
k = min(i, 10)
从 { 0, 1, 2, …, 2^k − 1 } 里等概率取一个 r
等待时间 = r × 2τ
```

三个细节：

```text
1. r 的上限随冲突次数指数增长，但 k 封顶在 10。
2. 所以 r 最大 1023，等待上限 1023 × 2τ，不再继续翻倍。
3. i 到 16 还没发出去，放弃，向上层报错。
```

为什么封顶 10？

不封顶的话，撞了 20 次，r 的范围是 0 到 1048575，等到天荒地老。

封顶 10 保证了最坏等待有上界，同时 10 次冲突之后的"随机度"已经足够。

算几个数（10 Mbps，2τ = 51.2 μs）：

```text
i=1   k=1   r ∈ 0..1       最长等 1×51.2   = 51.2 μs
i=3   k=3   r ∈ 0..7       最长等 7×51.2   = 358.4 μs
i=4   k=4   r ∈ 0..15      最长等 15×51.2  = 768 μs
i=10  k=10  r ∈ 0..1023    最长等 1023×51.2 = 52377.6 μs ≈ 52.4 ms
i=12  k=10  r ∈ 0..1023    同上，不再增长
```

看出规律没有：**冲突次数越多，说明网上越挤，等待窗口就越大。**

这是一种"自适应"，不用任何人告诉它网络有多忙。

代价是：撞得越久，恢复越慢，而且所有站一起退避，容易出现"同步震荡"。

公平吗？

统计上公平，短期很不公平。

```text
所有站用同一套规则，长期机会均等。
但发送成功的站，冲突计数器被清零，退避窗口回到最小。
它下一次更容易抢到，连续成功的站越来越容易成功。
```

这叫**捕获效应（capture effect）**。

随机争用的固有毛病，不是实现 bug。

所以以太网适合"突发、轻载"的流量，不适合"持续满载"的流量。

真实以太网负载超过 30% 左右，冲突就会明显拖垮效率。

## 6. 以太网帧格式：两个数字的来历

先把帧画出来。

```text
┌──────────┬──────────┬──────────┬─────────┬───────────────┬────────┐
│ 前导码    │ 目的 MAC │ 源 MAC   │ 类型/长度│ 数据           │ FCS    │
│ 7 B      │ 6 B      │ 6 B      │ 2 B     │ 46 – 1500 B   │ 4 B    │
│ 10101010 │          │          │         │               │ CRC-32 │
│ ×7       │          │          │         │               │        │
└──────────┴──────────┴──────────┴─────────┴───────────────┴────────┘
   + SFD 1 B（10101011）紧跟在 7 B 前导码之后
```

物理层在真正发帧之前，先发 8 字节：

```text
7 B 前导码：10101010 重复 7 次，用来让接收方时钟同步
1 B SFD   ：10101011，最后一个字节的末尾两个 1 标记"帧开始了"
```

**这 8 字节不算进帧长。**

以太网的帧长从"目的 MAC"的第一个字节开始数，到 FCS 结束。

于是：

```text
最小帧长 = 6 + 6 + 2 + 46 + 4 = 64 B
最大帧长 = 6 + 6 + 2 + 1500 + 4 = 1518 B
```

数据字段的 46 和 1500 各有各的原因。

```text
46   = 64 − 6 − 6 − 2 − 4，纯粹为了凑够 64 B。
       上层数据不足 46 B 时，链路层自己填填充字节（padding）。
1500 = 早期以太网定的上限，后来成了全世界 MTU 的默认值。
```

类型/长度字段是二义的，靠数值区分：

```text
值 ≥ 0x0600 (1536)  →  类型（type），如 0x0800 = IPv4，0x0806 = ARP
值 ≤ 1500           →  长度（length），后面跟 LLC 头，这是 802.3 的写法
1500 到 1535 这一段是留给"区分"的缓冲区，两边都不填
```

FCS 用 CRC-32，生成多项式是 `0x04C11DB7`。

接收方算一遍，余数不对就整帧丢掉。

一个帧进到网卡，硬件按顺序做五件事。

```text
1. 认前导码，把接收时钟对上
2. 看目的 MAC：不是我的、也不是广播/组播 → 直接丢
3. 算 FCS：CRC 余数不对 → 直接丢
4. 看类型：0x0800 交给 IP，0x0806 交给 ARP
5. 数据字段往上递，填充字节在这里被扔掉
```

五步全在网卡上完成，CPU 完全不参与。

所以一块千兆网卡能线速丢掉每秒上百万个"不是给我的"帧。

以太网**只检错，不纠错，也不确认**。

丢了谁管？

上层管。

TCP 管重传，UDP 就真的丢了。

这也是"以太网是尽力而为"的第一层含义。

## 7. MAC 地址：48 位里的两个开关

MAC 地址（也叫物理地址、硬件地址）固定 48 位，6 字节。

```text
00 : 1A : 2B : 3C : 4D : 5E
└──── 前三字节 ────┘ └── 后三字节 ──┘
      OUI（厂商标识）      厂商自己分配
```

写在网卡的 ROM 里，理论上全球唯一。

一个自然的问题：既然有 IP 地址了，为什么还要 MAC？

```text
MAC 是扁平的，没有结构，交换机查表靠硬件，常数时间
IP 是分层的，前缀可聚合，路由表才不会爆炸
MAC 跟着网卡走，换一块卡就变
IP 跟着位置走，换个网络才变
```

两者各管一段路。

IP 管"从源主机到目的主机"，MAC 管"这一跳从这走到那"。

所以一个 IP 数据报穿过五个路由器，IP 地址一直不变，MAC 地址换了五次。

真正要记的是第一字节的两个位。

```text
第一字节  b0 = I/G 位
  0 → 单播（unicast），这块网卡自己收
  1 → 组播（multicast），一组网卡都收

第一字节  b1 = U/L 位
  0 → 全球管理（厂商烧进去的）
  1 → 本地管理（软件改的，虚拟机常见）
```

注意这两个位在**第一字节的最低位**，也就是在线上最先发出去的那一端。

所以按书写顺序看，第一个字节 `0x01` 的最低 bit 是 1，说明它是组播。

三种目的地址：

```text
单播：00:1A:2B:3C:4D:5E    发给一块网卡
广播：FF:FF:FF:FF:FF:FF    发给本广播域内所有网卡
组播：01:00:5E:xx:xx:xx    发给一组（IPv4 组播映射到 01:00:5E 开头）
```

交换机只看 MAC，不看 IP。

路由器换掉 MAC，保留 IP。

这条差别在第 11 篇会反复用到。

## 8. 10BASE-T 这个名字怎么读

名字是三个部分拼起来的。

```text
10      BASE            T
│       │               │
速率    传输方式         介质
10 Mbps 基带（baseband） 双绞线（twisted pair）
```

同类名字一起看就懂了：

| 名字 | 速率 | 介质 | 单段最大长度 |
|---|---|---|---|
| 10BASE5 | 10 Mbps | 粗同轴 | 500 m |
| 10BASE2 | 10 Mbps | 细同轴 | 185 m（约 200） |
| 10BASE-T | 10 Mbps | 双绞线 | 100 m |
| 10BASE-F | 10 Mbps | 光纤 | 更长 |
| 100BASE-TX | 100 Mbps | 双绞线（Cat5） | 100 m |
| 1000BASE-T | 1 Gbps | 双绞线（Cat5e/6） | 100 m |

BASE 后面跟数字表示"百米数"，跟字母表示介质类型。

`5` = 500 m，`2` = 约 200 m，`T` = twisted pair，`F` = fiber，`X` = 编码方式。

BASE 是 baseband（基带）的缩写。

基带的意思是：整根线只传一路数字信号，占满全部频带。

对应的词是 BROAD（broadband，宽带）：把频带切成几段，每段跑一路，有线电视就是这么干的。

802.3 里确实有过一个宽带版本，叫 10BROAD36（36 表示 3600 m），早就淘汰了。

所以今天说"以太网"，默认就是基带。

10BASE-T 带来的变化不止是换成网线。

它把"一根总线"变成了"以集线器为中心的星形"。

物理上是星形，逻辑上还是总线。

所有站共享同一个冲突域，还是得跑 CSMA/CD。

## 9. 集线器、交换机与冲突域

先看**集线器（hub）**。

它是物理层设备，本质是一个多端口中继器。

```text
端口 1 收到的比特，原样复制到端口 2、3、4……
不做任何判断，不看 MAC，不看 IP。
```

后果有三个：

```text
1. 所有端口在同一个冲突域里，一台发、全体听。
2. 同一时刻只能有一台在发，半双工。
3. 带宽是共享的：10 个口接 10 Mbps 集线器，平均每台 1 Mbps。
```

再看**交换机（switch）**。

它是链路层设备，每个端口是一个独立的冲突域。

```text
端口 1 收到帧，查 MAC 表，只从"该去的那一个口"发出去。
端口 2 和端口 3 之间可以同时通信，互不干扰。
```

查表这件事，一共只有四种结果。

```text
目的地址在表里，且不在来源端口   → 转发
目的地址在表里，恰好就是来源端口 → 丢弃（过滤）
目的地址不在表里                 → 泛洪（除来源端口外全发）
目的地址是广播                   → 泛洪
```

表一开始是空的。

所以交换机刚上电的那几十毫秒，它的行为跟集线器一模一样。

"泛洪"就是交换机看起来像集线器的那一刻，也是它**不分割广播域**的根本原因。

于是三件事同时变了：

```text
冲突域：从"一个"变成"每端口一个"
双工：  从半双工变成全双工（收发用不同的线对）
带宽：  从共享变成每端口独享
```

一个直观的对比：

```text
10 台主机，10 Mbps

接集线器：1 个冲突域，共享 10 Mbps，每台平均 1 Mbps，还要抢
接交换机：10 个冲突域，每台独占 10 Mbps，不用抢
```

注意最后一句"不用抢"的前提是全双工。

交换机端口如果跑半双工（比如对端是集线器），还是会有冲突，还是要 CSMA/CD。

## 10. CSMA/CD 为什么在交换式全双工下消失了

这是本篇最重要的一句结论。

```text
CSMA/CD 存在的前提是：多个站共享同一个介质，可能撞。
交换机全双工把这个前提拆掉了。
```

拆的方式很物理。

```text
传统共享介质：一根线，收发都在这根线上，两个方向会叠加 → 会撞
双绞线全双工：4 对线，1-2 对发，3-6 对收，两个方向物理隔离 → 不会撞
```

再加上交换机每个端口只连**一台**设备。

这条链路上只有两个端点。

点对点、方向分离，冲突在物理上不可能发生。

没有冲突，就不需要"听"。

不需要听，就不需要"争用期"。

不需要争用期，就不需要最小帧长。

不需要最小帧长，就不需要 46 字节填充的硬约束（虽然为了兼容还保留）。

所以全双工以太网的 MAC 层只剩两件事：

```text
组帧
差错检测（FCS）
```

发送方想发就发，不用等，不用退避。

这叫**全双工以太网不需要 CSMA/CD**，不是"关掉了"，是"用不上了"。

还有一层现实问题：双工方式怎么定？

靠**自协商（auto-negotiation）**：两边各自通告支持的速率和双工，取交集。

最坏的情况是人为关掉自协商，一边硬配全双工、另一边硬配半双工。

结果是半双工那侧一直检测到冲突、不停退避，全双工那侧不停丢帧。

链路能 ping 通，但吞吐只有几兆。

这种"双工不匹配（duplex mismatch）"是老网络里最经典的性能故障。

看一台现代主机：

```text
$ ethtool eth0 | grep -i duplex
        Duplex: Full
```

绝大多数情况下你看到的都是 Full。

所以你在一台普通 PC 上**永远抓不到一次真正的以太网冲突**。

冲突只活在三种地方：

```text
1. 还在用集线器的老网络
2. 强制半双工的链路（配置错误或对端不支持自协商）
3. 无线网络里的"类冲突"（其实是碰撞，用 CSMA/CA 处理）
```

## 11. 以太网的效率：为什么线上利用率上不去

共享式以太网有一个绕不过去的效率天花板。

轻载时几乎不撞，效率接近 1。

负载到三成左右，冲突开始明显，效率掉到七成上下。

负载再往上，吞吐量不升反降。

原因不神秘：**冲突消耗的是时间，而时间就是带宽。**

一次冲突总共浪费三段时间。

```text
第一段：A 已经发出的那部分帧，白发了
第二段：B 已经发出的那部分帧，也白发了
第三段：两边都退避 r×2τ，这段时间线上空着
```

还有一个隐藏成本：**冲突会连锁**。

A 和 B 撞完各自退避，如果 r 恰好又相同，就再撞一次。

退避窗口指数增长就是为了打破这种同步，但前几次冲突它几乎不起作用。

工程上用一个无量纲参数 `a` 来估算效率：

```text
a = 单程传播时延 τ / 发送时延 T0

T0 = 帧长 / 数据率
```

`a` 的含义很直白：它比较"信号跑一趟的时间"和"把整个帧推出去的时间"。

```text
帧很长、链路很短 → a 很小 → 帧发完了对方还没反应过来 → 冲突窗口占比小 → 效率高
帧很短、链路很长 → a 很大 → 还没发完就撞了 → 退避时间占比大 → 效率低
```

极限情况：

```text
a → 0    效率 → 1（几乎不浪费）
a = 0.5  效率大约 0.8 上下
a → 很大  效率趋近 1/(1+e) ≈ 0.37
```

所以"最小帧 64 B + 最大跨度 2500 m"这对数字真正保证的，不是某个格式，而是 `a ≤ 0.5` 这个工作区间。

换个说法：

```text
64 B 保证 T0 不能太短
2500 m 保证 τ 不能太长
两者一除，a 就被压在 0.5 以内
```

这也解释了为什么提高速率必须同时缩短网段：

速率提高 10 倍，`T0` 就缩到 1/10，`a` 涨 10 倍。

要么把 `τ` 也压到 1/10（跨度缩短），要么把帧加长（载波延伸），二选一。

交换式全双工把 `a` 这个概念整个消灭了：

```text
没有共享介质 → 没有冲突 → 没有争用期 → a 失去意义
```

所以从共享式换到交换式，是数量级的提升，不是百分之几十的提升。

## 12. 容易混淆的八个点

**第一，争用期不是 RTT。**

争用期 2τ 是"往返传播时延"，但它是一个**协议参数**，包含了中继器和收发器的处理时延，不等于物理上的光速往返。

10 Mbps 以太网取 51.2 μs，而 2500 m 电缆的光速往返只有 25 μs。

**第二，64 字节不含前导码。**

64 = 6 + 6 + 2 + 46 + 4。

前导码 7 B 加 SFD 1 B 是物理层加的，抓包软件也看不到它们。

**第三，46 字节是链路层填的。**

上层给了 20 字节数据，链路层补 26 字节填充，凑到 46。

接收方拆帧时再把填充扔掉。

上层完全不知道这件事发生过。

**第四，最大帧长有两个版本。**

不带 VLAN 标签是 1518 B。

带了 802.1Q 的 4 字节标签，就是 1522 B。

**第五，退避的"指数"有上限。**

k 封顶 10，所以等待上限是 1023 × 2τ。

不是"每次都翻倍"，是"翻到 10 次为止"。

**第六，冲突后发的是 jam，不是重传。**

先发一个冲突加强信号，让所有站都确知发生了冲突。

然后再退避、再重发。

**第七，集线器不分割任何域。**

它不分割冲突域，也不分割广播域。

它只是把信号放大复制。

**第八，交换机分割冲突域，不分割广播域。**

广播帧（目的 FF:FF:FF:FF:FF:FF）会被泛洪到所有端口。

这一条是 408 的高频陷阱，第 11 篇专门展开。

## 13. 408 怎么考

以太网这一块的题型很固定，四种：

```text
1. 算最小帧长 / 判断帧长范围
2. 算退避时间
3. 数冲突域、广播域
4. 帧格式字段判断（哪些字段在什么位置）
```

### 例题（自拟）

某以太网采用 CSMA/CD，数据率 10 Mbps，争用期 51.2 μs。

三问：

```text
(1) 最小帧长是多少字节？
(2) 若保持网段跨度不变，把数据率提高到 100 Mbps，最小帧长应为多少？
(3) 某站连续发生 4 次冲突，第 5 次发送前最多可能等待多久？
```

**第 (1) 问**

```text
最小帧长 = 2τ × 数据率
         = 51.2 μs × 10 Mbps
         = 512 bit
         = 64 B
```

答：64 字节。

**第 (2) 问**

跨度不变，意味着 2τ 还是 51.2 μs。

```text
最小帧长 = 51.2 μs × 100 Mbps
         = 5120 bit
         = 640 B
```

答：640 字节。

顺带说一句，真实标准没有选 640 B，而是把网段缩到约 200 m，保住了 64 B。

**第 (3) 问**

已经撞了 4 次，现在准备第 5 次发送。

退避用的 i 是"已经发生的冲突次数"，所以 i = 4。

```text
k = min(4, 10) = 4
r ∈ {0, 1, …, 2^4 − 1} = {0, …, 15}
最长等待 = 15 × 2τ = 15 × 51.2 μs = 768 μs
```

答：最多 768 μs。

如果问的是"撞了 12 次之后"：

```text
k = min(12, 10) = 10
r ∈ {0, …, 1023}
最长等待 = 1023 × 51.2 μs = 52377.6 μs ≈ 52.4 ms
```

注意 52.4 ms 而不是继续翻倍，这就是封顶的意义。

### 套路总结

三种常见变体，问法不同，答法不同。

```text
"最短帧为什么是 64 字节"   → 答时间约束（撑够 2τ），不是格式约束
"30 字节的帧存在吗"        → 不存在，链路层会填充到 64
"2τ 为什么取 51.2 μs"      → 由 64 B 和 10 Mbps 反推，再由 2500 m 验算
```

```text
最小帧长题：先找 2τ，再乘数据率，换成字节。
退避题：   先确认 i 是"已经冲突几次"，再 k = min(i,10)，上限 2^k − 1。
帧长范围题：记住 64 和 1518，注意题目问的是"含不含前导码"。
冲突域题：  集线器不算分割，交换机每个端口算一个。
```

## 14. 真实网络里长什么样

先看网卡自己报告什么。

```text
$ ip link show eth0
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP
    link/ether 3c:7c:3f:12:34:56 brd ff:ff:ff:ff:ff:ff
```

三行信息里有三个本篇的关键词。

```text
mtu 1500           →  最大帧 1518 的那个 1500
link/ether 3c:...  →  48 位 MAC 地址
brd ff:ff:ff:ff... →  广播地址，全 F
```

（以上输出为简化示意，实际字段顺序随内核版本略有差异。）

看双工和速率：

```text
$ ethtool eth0
        Speed: 1000Mb/s
        Duplex: Full
        Auto-negotiation: on
```

`Duplex: Full` 就是"没有 CSMA/CD"的直接证据。

用 tcpdump 看 MAC 头：

```text
$ tcpdump -e -c 3 -i eth0
14:22:01.113 IP 192.168.1.10.54321 > 93.184.216.34.443
    3c:7c:3f:12:34:56 > 00:1a:2b:3c:4d:5e, ethertype IPv4 (0x0800), length 74
```

`-e` 让 tcpdump 打出链路层头。

```text
3c:7c:3f:12:34:56  源 MAC
00:1a:2b:3c:4d:5e  目的 MAC（这里是网关）
ethertype 0x0800   IPv4
length 74          整帧 74 B（60 字节数据 + 14 字节帧头，没算 FCS）
```

注意 `length 74`：抓包工具看到的长度**不含 FCS**，因为 FCS 通常被网卡剥掉了。

这也是为什么你在 Wireshark 里看到的以太网帧最小是 60 B 而不是 64 B。

再抓一个广播帧看看：

```text
$ sudo tcpdump -e -c 1 -i eth0 arp
14:25:33.201 ARP, Request who-has 192.168.1.1 tell 192.168.1.10, length 42
    ff:ff:ff:ff:ff:ff > 3c:7c:3f:12:34:56, ethertype ARP (0x0806), length 42
```

目的地址是全 F。

这就是"广播"，交换机会把它从除来源端口外的所有端口发出去。

`length 42` 还能看出另一件事：42 小于 64。

说明链路层后来给它补了 18 字节填充，只是抓包点在这之前。

ARP 请求是"短帧必须填充"最日常的例子。

看 ARP 表（MAC 和 IP 的对应）：

```text
$ ip neigh
192.168.1.1 dev eth0 lladdr 00:1a:2b:3c:4d:5e REACHABLE
```

`lladdr` 后面那串就是本篇说的 48 位地址。

最后看统计：

```text
$ ip -s link show eth0
    RX: bytes  packets  errors  dropped  overrun  mcast
  918273645   1200345       0        3        0     211
    TX: bytes  packets  errors  dropped  carrier  collsns
  123456789    987654        0        0        0        0
```

`collsns`（collisions）这一列在现代全双工链路上永远是 0。

如果你看到它在涨，说明这条链路被配成了半双工，或者对端是个集线器。

想看更细的冲突分类，用 `ethtool -S`：

```text
$ ethtool -S eth0 | grep -i -E "collision|late"
     collisions: 0
     tx_late_collision: 0
```

`late_collision`（晚期冲突）是个特别有意思的计数器。

它的意思是"帧都快发完了才检测到冲突"。

正常网络里它应该恒为 0，因为 CSMA/CD 的设计就是保证冲突一定发生在争用期内。

它一旦非零，说明有人破坏了前提：

```text
网段超长（τ 变大，超出 2τ 预算）
中继器超过 4 个
有网卡不守规矩，发超长帧
```

这就是"最小帧长"这个约束在真实设备上留下的指纹。

## 15. 小结

把这一篇压成几行。

```text
共享介质 → 会撞 → 需要一套"谁先发"的规则
CSMA/CD = 先听后发 + 边听边发 + 冲突停发 + 随机重发
争用期 2τ = 最坏情况下听到冲突所需的时间
发送时延 ≥ 2τ → 帧长 ≥ 2τ × 数据率 → 512 bit = 64 B
退避：第 i 次冲突，k = min(i,10)，等 r×2τ，r ∈ 0..2^k−1，16 次放弃
帧：6+6+2+46..1500+4，最小 64 B，最大 1518 B
集线器：一个冲突域，半双工，共享带宽
交换机：每端口一个冲突域，全双工，独享带宽
```

一句话记住那个数字：

```text
64 字节不是"方便处理"，
是"发送方必须撑到听见冲突"。
```

天线只有一个，发的时候听不见别人，藏起来的站还互相看不见。

CSMA/CD 立刻失效。

