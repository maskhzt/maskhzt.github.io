先看一个每天都会发生的现象。

服务器上 `ss -tan` 输出几百行 `TIME-WAIT`。

有人搜到一句"把 `tcp_tw_recycle` 打开就好了"，在生产上敲下去，然后一批客户端连不上了。

还有人问：为什么握手是三次，四次不行吗？两次不行吗？

这两个问题的答案，其实在同一个地方：

```text
TCP 连接的每一步，
都在解决"双方各自要确认什么"这个问题。
```

这一篇把 TCP 的首部、握手、挥手、状态机拆开，每步都算具体数字。

## 1. 一条连接到底"连"住了什么

先纠正一个印象。

TCP 的"连接"不是一个物理的东西。

链路上没有一根线被你占住，中间的路由器也不知道你建了连接。

它只是两端内核里各存了一份状态：

```text
客户端内核                          服务器内核
  对方的 IP 和端口                    对方的 IP 和端口
  我的序号发到哪了                    我的序号发到哪了
  我期待对方的下一个字节              我期待对方的下一个字节
  接收窗口还剩多少                    接收窗口还剩多少
  哪些字节发了但还没被确认             哪些字节发了但还没被确认
  重传定时器                          重传定时器
```

这两份状态，加上同一条四元组，就是"连接"。

所以连接的本质是：

```text
两端对"我们聊到第几个字节了"达成一致，
并且都愿意为这个共识保留资源。
```

三次握手干的正是这件事：**建立这个共识。**

四次挥手干的是相反的事：**安全地撤销这个共识。**

## 2. TCP 首部：20 字节起，每个字段都在干活

```text
 0                    16                    31
+---------------------+---------------------+
|     源端口 (16)      |    目的端口 (16)      |
+---------------------+---------------------+
|                序号 seq (32)                |
+-------------------------------------------+
|               确认号 ack (32)               |
+-------+-------+---------------------------+
| 数据偏移| 保留  |    标志位（9 位）          |
|  (4)  |  (6)  |  CWR ECE URG ACK PSH RST  |
|       |       |  SYN FIN                   |
+---------------------+---------------------+
|     窗口 rwnd (16)   |    校验和 (16)       |
+---------------------+---------------------+
|    紧急指针 (16)      |    选项 + 填充       |
+---------------------+---------------------+
|                  数据                       |
+-------------------------------------------+
```

**首部最短 20 字节。**

"数据偏移"这个 4 位字段就是用来算首部长度的：

```text
数据偏移的单位是 4 字节（32 位字）
最小 5  →  5 × 4 = 20 字节
最大 15 → 15 × 4 = 60 字节
```

所以选项最多 40 字节。

必考的字段逐个说：

```text
序号 seq (32 位)     本报文段第一个数据字节的编号
确认号 ack (32 位)   期望收到的下一个字节编号
数据偏移 (4 位)      首部长度 / 4
窗口 rwnd (16 位)    接收方还能收多少字节（流量控制）
校验和 (16 位)       覆盖伪首部 + TCP 首部 + 数据
紧急指针 (16 位)     配合 URG 使用
```

标志位里最要紧的几个：

```text
SYN   同步序号，建连接用
ACK   确认号有效（连接建立后几乎恒为 1）
FIN   我要关闭这个方向
RST   重置连接，立即断开
PSH   尽快交给应用，别缓
URG   紧急指针有效
```

两个容易忽略的事实：

窗口字段只有 16 位，最大 65535 字节，对长肥管道完全不够。

所以 TCP 有一个**窗口缩放（window scaling）**选项，在握手时协商一个移位因子，最多移 14 位。

```text
65535 × 2^14 = 1,073,725,440 字节 ≈ 1 GB
```

这就是为什么握手报文里经常带一长串选项：MSS、SACK 允许、时间戳、窗口缩放，都在那一次里谈完。

握手之后就不能再变。

## 3. 序号与确认号：它们数的是字节

这是 TCP 和"编号报文"的协议（比如 GBN）最大的区别。

TCP 给**字节**编号，不给报文段编号。

```text
假设本次连接的初始序号是 1000
客户端要发 500 字节：

字节编号   1000 ... 1499
报文段 seq = 1000，长度 500 字节

所以发送方发完之后，下一个可用的序号是 1500。
```

确认号的含义是"我期待你下一个字节是几"。

```text
服务器回 ack = 1500
意思是：1000 到 1499 我都收到了，请从 1500 开始发。
```

注意这个表述。

`ack = 1500` **不代表收到了 1500**，它代表"1500 还没收到"。

这叫**累积确认（cumulative ACK）**：

```text
收到 1000–1099  →  ack = 1100
收到 1100–1299  →  ack = 1300
中间 1300–1399 丢了
收到 1400–1499  →  ack 仍然是 1300（不能说 1500，否则丢的那段就被掩盖了）
```

三个必须记住的规则：

```text
1. SYN 占 1 个序号。所以 SYN 的 seq=x，下一个数据从 x+1 开始。
2. FIN 占 1 个序号。所以 FIN 的 seq=y，对方要 ack=y+1。
3. 纯 ACK 不占序号。发一百个纯 ACK，序号不动。
```

规则 3 经常被忽略，题目里只要问"发了 n 个纯 ACK 之后 seq 变成多少"，答案是不变。

还有一点：初始序号（ISN）不是从 0 或 1 开始的。

RFC 793 要求 ISN 与一个 32 位时钟绑定，每 4 微秒加一。

目的是让每次连接的序号错开，避免旧连接的报文被新连接误收。

## 4. 三次握手：三个报文，四行时序

设客户端 A 的初始序号是 1000，服务器 B 的初始序号是 3000。

```text
客户端 A                                  服务器 B
   |                                          |
   |  ① SYN=1, seq=1000, 无数据                |
   | ───────────────────────────────────────► |
   |                                          |  状态：SYN_RCVD
   |  ② SYN=1, ACK=1, seq=3000, ack=1001      |
   | ◄─────────────────────────────────────── |
   |  状态：ESTABLISHED                        |  状态：ESTABLISHED
   |                                          |
   |  ③ ACK=1, seq=1001, ack=3001             |
   | ───────────────────────────────────────► |
   |                                          |
   |        双方都可以开始发数据了              |
```

把三个报文的每个数字列出来：

```text
报文  方向      标志        seq     ack     说明
①     A → B     SYN         1000    —       SYN 占 1 个序号
②     B → A     SYN + ACK   3000    1001    确认 A 的 SYN，同时发自己的 SYN
③     A → B     ACK         1001    3001    确认 B 的 SYN

连接建立后：
  A 的下一个发送序号 = 1001
  A 期待 B 的下一个序号 = 3001
```

第三条 ACK 有一个常被忽略的性质：**它已经可以携带数据了。**

如果 A 有数据要发，完全可以在第三个报文里捎上，不必等第四个报文。

这就是"三次握手最少三个报文"而不是"必须先空手 ACK 再发数据"的原因。

握手期间双方还交换了三个关键参数：

```text
MSS          每个报文段最多带多少数据（以太网一般 1460）
窗口缩放因子  窗口字段的移位量
SACK 允许    是否支持选择确认
```

以太网 MSS 1460 是这么来的：

```text
1500（MTU）- 20（IP 首部）- 20（TCP 首部）= 1460
```

## 5. 为什么是三次，不是两次

这是 408 最爱问的"为什么"。

先把两次握手的流程画出来：

```text
两次握手（错误示范）
客户端 A                                  服务器 B
   |  SYN=1, seq=1000  ────────────────────► |
   |                                        |  认为连接已建立
   |  ◄──────────────  SYN=1, ACK=1, ack=1001
   |  认为连接已建立                          |
```

问题出在服务器这边。

它收到 SYN，回了 SYN+ACK，然后就地认为"连接建好了"，开始分配资源、启动定时器。

但它手上只有两件事是确定的：

```text
确定：A 发过 SYN
不确定：A 收到了我的 SYN+ACK 吗？
不确定：A 现在还想连吗？（这个 SYN 可能是很久以前发出来的）
```

用一个具体场景说明第二点。

```text
t=0     A 发出 SYN(seq=100)，网络拥塞，这个报文卡在某个路由器里
t=0     A 等不到回应，重发 SYN(seq=200)，正常建连，传完数据，关闭
t=30s   那个卡住的 SYN(seq=100) 突然到了 B
```

如果只有两次握手：

```text
B 收到这个迟到的 SYN → 回 SYN+ACK(ack=101) → 认为连接建立
B 开始为这条连接分配内存、开定时器、准备收数据
A 根本没想连，收到 SYN+ACK 觉得莫名其妙，回一个 RST 或者直接丢弃
B 白等一场，资源空转到超时
```

这就是所谓的"历史重复连接"。

严重的时候，成千上万个伪造的旧 SYN 可以让服务器把内存耗光。

再加上第三个报文，服务器就有了一个"可以反悔"的机会窗口：

```text
B 发完 SYN+ACK 只进入 SYN_RCVD，不算建立。
只有收到 A 的 ACK，才真正 ESTABLISHED。
```

第三个报文的作用可以拆成两半：

```text
一半：确认 B 的 SYN（让 B 知道自己的初始序号被收到了）
另一半：让 B 确认"A 确实收到了我的 SYN+ACK"，并且"A 现在还想连"
```

**反直觉的点在这里：**

> 第三次 ACK 常常被理解成"多余的确认"，其实它是唯一一次让服务器**区分新连接和迟到旧 SYN** 的机会。

换个角度，从"要确认几件事"来数：

```text
A 要确认：B 收到了我的 SYN 且知道我的序号
B 要确认：A 收到了我的 SYN 且知道我的序号
A 要确认：B 现在愿意连
B 要确认：A 现在愿意连
```

四个确认，压缩进三个报文，已经是下限。

一个报文最多同时完成"我确认你"和"我提出我的序号"两件事，所以三次就是最小值。

## 6. 四次挥手：为什么要分四次

挥手比握手多一次，原因只有一个：**TCP 是全双工的。**

两个方向的数据流是独立的。

```text
A 说：我说完了（FIN）
B 说：知道了（ACK）
      —— 但 B 可能还有话要说 ——
B 说：我也说完了（FIN）
A 说：知道了（ACK）
```

这就是**半关闭（half-close）**。

收到 FIN 只代表"对方这个方向不再发数据"，不代表"我也不能再发"。

具体走一遍，接着上面的序号：

```text
客户端 A                                 服务器 B
   |                                         |
   |  ① FIN=1, seq=1501, ack=3301            |
   | ──────────────────────────────────────► |  CLOSE_WAIT
   |  FIN_WAIT_1                             |  （等应用调用 close）
   |                                         |
   |  ② ACK=1, seq=3301, ack=1502            |
   | ◄────────────────────────────────────── |
   |  FIN_WAIT_2                             |
   |                                         |
   |         B 把剩下的数据发完（这期间还能发）  |
   |                                         |
   |  ③ FIN=1, seq=3301, ack=1502            |
   | ◄────────────────────────────────────── |  LAST_ACK
   |  TIME_WAIT                              |
   |                                         |
   |  ④ ACK=1, seq=1502, ack=3302            |
   | ──────────────────────────────────────► |  CLOSED
   |  等 2MSL 后 CLOSED                       |
```

为什么 ② 和 ③ 不能合并？

因为 ② 是内核自动回的（收到 FIN，立刻 ACK），而 ③ 要等应用层决定"我没数据要发了"。

这两件事在时间上不重合。

如果 B 收到 FIN 时恰好也没有数据要发，内核可以把 ACK 和 FIN 合在一个报文里——这就是"四次挥手有时只看到三次"的原因。

所以"四次"是**上限**，不是恒定值。

还有一种更少见的情况：双方几乎同时发 FIN。

这时候不出现 CLOSE_WAIT，而是出现 `CLOSING` 状态，两边都等对方的 ACK。

## 7. TIME_WAIT：等 2MSL 到底在等什么

TIME_WAIT 是主动关闭方最后停的状态，时长 2MSL。

MSL 是"报文段最大生存时间"（Maximum Segment Lifetime），RFC 793 建议 2 分钟。

两个理由，408 都要写。

**理由一：保证最后一个 ACK 能到达对方。**

```text
④ 的 ACK 如果丢了：
B 停在 LAST_ACK，超时后重发 FIN(seq=3301)
A 如果已经 CLOSED，收到这个 FIN 只能回 RST
B 收到 RST，认为连接异常终止，报错
```

有了 TIME_WAIT，A 还在，能再补一个 ACK。

```text
A 在 TIME_WAIT 里收到重传的 FIN
→ 重置 2MSL 定时器
→ 再发一次 ACK
```

这个"重置定时器"的细节很重要：TIME_WAIT 不是固定等 2MSL，而是每收到一个重传的 FIN 就重新计时。

**理由二：让旧连接的报文在网络中消散。**

```text
t=0    连接 1（四元组 10000 → 443）关闭，双方进入 TIME_WAIT / CLOSED
t=1s   同一个四元组又被用来建连接 2（客户端端口复用了）
t=1.5s 连接 1 的某个迟到报文到了
       它带着连接 1 的序号，落在连接 2 的接收窗口里
       接收方无法分辨，把它当成连接 2 的数据 —— 数据就错了
```

等 2MSL，等于给"这条连接上所有可能迟到的报文"一个确定的死亡期限。

超过 2MSL，任何属于旧连接的报文都已经被网络丢弃，不可能再出现。

为什么是 2MSL 而不是 1MSL？

因为要覆盖"一个来回"：

```text
1 个 MSL：我的 ACK 走到对方
1 个 MSL：对方重传的 FIN 走回来
合起来 2MSL
```

现实中的数字和课本不完全一样。

Linux 的 TIME_WAIT 是**固定 60 秒**，写死在 `TCP_TIMEWAIT_LEN` 里，改不了。

`net.ipv4.tcp_fin_timeout` 管的不是 TIME_WAIT，是 FIN_WAIT_2 的存活时间。

这两个概念被混得很厉害，第 12 节会用命令演示。

TIME_WAIT 的两个副作用：

```text
占用端口：一条 TIME_WAIT 占一个四元组，高并发短连接会把临时端口吃光
占用内存：每条连接一小块内核结构，几万条就是几十 MB
```

缓解手段（知道名字就行）：

```text
net.ipv4.tcp_tw_reuse = 1     允许复用在 TIME_WAIT 的四元组（仅出向连接，且时间戳递增）
SO_REUSEADDR                 服务端重启时不被 TIME_WAIT 挡住绑定
用长连接                      最根本的办法，HTTP keep-alive 就是干这个的
```

`tcp_tw_recycle` 不要用。

它依赖对端时间戳单调递增，在 NAT 后面的大量客户端会被误判成"时间戳倒退"而丢包。

这个参数在 Linux 4.12 之后已经被移除。

## 8. 状态机：六个必须能背的状态

TCP 一共有 11 个状态，408 至少要能画出下面这些。

```text
建连接
  CLOSED ──发 SYN──► SYN_SENT ──收到 SYN+ACK──► ESTABLISHED

  服务端
  CLOSED ──监听──► LISTEN ──收到 SYN──► SYN_RCVD ──收到 ACK──► ESTABLISHED
```

```text
关连接（主动关闭方在左，被动关闭方在右）

  ESTABLISHED                    ESTABLISHED
      │ 发 FIN                        │ 收到 FIN
      ▼                              ▼
  FIN_WAIT_1 ──────── FIN ────────► CLOSE_WAIT
      │ 收到 ACK                      │ 应用 close，发 FIN
      ▼                              ▼
  FIN_WAIT_2                        LAST_ACK
      │ 收到 FIN                      │ 收到 ACK
      ▼                              ▼
  TIME_WAIT ──────── ACK ─────────► CLOSED
      │ 等 2MSL
      ▼
   CLOSED
```

六个状态的一句话定义：

```text
LISTEN       服务端在听，还没有连接
SYN_SENT     客户端发了 SYN，等对方回应
ESTABLISHED  可以双向传数据
FIN_WAIT_1   我发了 FIN，还没收到 ACK
TIME_WAIT    我发完了 ACK，等 2MSL
CLOSE_WAIT   对方要关，我还没 close（等应用层）
```

CLOSE_WAIT 是排障里最有信息量的一个状态。

它意味着**内核已经收到对方的 FIN，但本地应用没有调用 close**。

所以 CLOSE_WAIT 堆积，永远不是网络问题，一定是代码问题：

```text
忘了 close
连接池没有回收
异常分支里 return 之前没关
```

反过来，TIME_WAIT 堆积是"我方主动关闭太多"，属于正常的短连接现象。

一个常见的判断口诀：

```text
TIME_WAIT 多  →  我方主动关得多，调应用（用长连接）
CLOSE_WAIT 多 →  我方应用不关，改代码
```

## 9. SYN 洪泛、半连接队列与 RST

服务器收到 SYN 之后，会在 `SYN_RCVD` 状态挂一条记录，等第三个 ACK。

这些记录排的队叫**半连接队列（SYN queue）**。

第三个 ACK 到了、连接进入 ESTABLISHED，就转到**全连接队列（accept queue）**，等应用调用 `accept`。

```text
SYN ──► 半连接队列（SYN_RCVD）
          │ 收到 ACK
          ▼
        全连接队列（ESTABLISHED，等 accept）
          │ 应用 accept
          ▼
        交给进程
```

两个队列都有上限，满了就丢。

SYN 洪泛就是攻击者用大量伪造源地址的 SYN 塞满半连接队列，让真正的用户连不进来。

常见的缓解是 SYN cookie：不回状态，把连接信息编码进 seq 号，等 ACK 回来再还原。

一句话记住：

```text
SYN 洪泛打的是"服务器为一个还没确认的 SYN 保留资源"这件事。
```

RST 是另一条路：不走四次挥手，直接掀桌。

出现 RST 的典型场景：

```text
连一个没人监听的端口        → 内核回 RST，客户端报 Connection refused
收到不属于任何连接的报文     → 回 RST，告诉对方"这条连接不存在"
应用主动拒绝（SO_LINGER=0）  → close 时直接发 RST，跳过挥手
防火墙配了 REJECT           → 回 RST 而不是静默丢弃
```

RST 和 FIN 的区别，一句话：

```text
FIN 是"我这边说完了"，还要等对方也说完。
RST 是"这条连接立刻作废"，缓冲区里的数据全部丢弃。
```

所以看到 `Connection reset by peer`，说明对面（或中间设备）主动发了 RST。

而 `Connection timed out` 说明 SYN 发出去没有任何回应，被静默丢弃了。

后者通常是防火墙 DROP，而不是端口没开。

## 10. 容易混淆的点

**序号不是报文段编号。**

它数的是字节。一个 500 字节的报文段，seq 加 500。

**确认号不是"已收到的最后一个字节"。**

它是"期望收到的下一个字节"，比已收到的最后一个字节大 1。

**SYN 和 FIN 各占 1 个序号，纯 ACK 不占。**

算序号时漏掉这一点，整道题的数都会错位。

**第三次握手的 ACK 可以带数据。**

"三次握手期间不能传数据"是错的，只有前两次不能。

**TIME_WAIT 出现在主动关闭方。**

谁先发 FIN，谁最后进 TIME_WAIT。

所以高并发短连接的客户端更容易撞上端口耗尽。

**close 不等于连接立刻消失。**

调用 close 只是"我不再发了"，内核还要走完挥手流程。

**半关闭是合法的。**

一方发 FIN 之后，另一方仍可以继续发数据，这期间连接处于半关闭。

## 11. 408 怎么考

这一节的题型：

```text
填写握手/挥手报文里的 seq 与 ack
判断某个时刻连接处于什么状态
TIME_WAIT 的时长与理由
为什么是三次握手
```

下面这道是自拟的，把所有数字串成一条线。

```text
客户端 A 的初始序号 ISN = 1000
服务器 B 的初始序号 ISN = 3000
连接建立后：
  A 向 B 发送 500 字节数据
  B 向 A 发送 300 字节数据
然后 A 主动关闭连接。

问：
(1) 握手三个报文的 seq / ack 分别是什么？
(2) A 发完 500 字节后，B 回的确认号是多少？
(3) B 发 300 字节数据时 seq 是多少？A 回的 ack 是多少？
(4) 挥手四个报文的 seq / ack 分别是什么？
(5) 若 MSL = 2 分钟，TIME_WAIT 持续多久？为什么？
(6) A 在 TIME_WAIT 期间收到一个 seq=3301 的 FIN，会怎么做？
```

解。

（1）握手。

```text
① A → B   SYN=1        seq=1000  ack=—      （SYN 占 1 个序号）
② B → A   SYN=1,ACK=1  seq=3000  ack=1001
③ A → B   ACK=1        seq=1001  ack=3001
```

要点：② 的 ack = 1000 + 1 = 1001，因为 SYN 消耗了一个序号。

（2）A 从 1001 开始发 500 字节。

```text
占用序号 1001 – 1500
B 回的 ACK：ack = 1501
```

（3）B 的数据。

```text
B 从 3001 开始发 300 字节，占用 3001 – 3300
报文 seq = 3001
A 回的 ACK：ack = 3301
```

（4）挥手。此时 A 的下一个发送序号是 1501，B 的是 3301。

```text
① A → B   FIN=1        seq=1501  ack=3301
② B → A   ACK=1        seq=3301  ack=1502
③ B → A   FIN=1        seq=3301  ack=1502
④ A → B   ACK=1        seq=1502  ack=3302
```

注意 ③ 的 seq 还是 3301：B 在 ② 里发的纯 ACK 不占序号。

FIN 才占，所以 ④ 的 ack = 3301 + 1 = 3302。

（5）TIME_WAIT 时长。

```text
2 × MSL = 2 × 2 分钟 = 4 分钟 = 240 秒
```

两个理由：保证最后那个 ACK 能到达（丢了还有机会补），让旧连接的报文在网络中消散（避免污染同四元组的新连接）。

（6）收到重传的 FIN。

```text
A 重发一次 ACK(ack=3302)
并把 2MSL 定时器重置，重新开始计时
```

这就是"TIME_WAIT 期间收到 FIN 会重置定时器"那条规则。

再补一个常见的变形题：

```text
"若 A 在发 FIN 之前还有 100 字节数据没发完，能不能在 FIN 报文里带上？"
```

不能。

FIN 表示"这个方向的数据到此为止"，它自己占一个序号，但不携带数据（严格说 FIN 段可以带数据，但序号要先覆盖数据，序号关系会变得很绕，408 按"FIN 不带数据"处理）。

## 12. 真实网络里长什么样

先看状态分布。

```text
$ ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn
    412 ESTAB
     87 TIME-WAIT
      3 LISTEN
      1 CLOSE-WAIT
```

（简化示意）

一眼就能判断方向：

```text
TIME-WAIT 多  → 我方是主动关闭方，短连接偏多
CLOSE-WAIT 多 → 应用没 close，去看代码
```

看单个连接的细节：

```text
$ ss -tani dst 93.184.216.34
ESTAB 0 0 192.168.1.10:51234 93.184.216.34:443
     cubic wscale:7,7 rto:204 rtt:1.5/0.5 ato:40 mss:1460
     rcvmss:1460 advmss:1460 cwnd:10 bytes_sent:20480
```

（简化示意）

几个字段值得记：

```text
cwnd:10        拥塞窗口 10 个 MSS
rtt:1.5/0.5    平滑 RTT 1.5 ms，偏差 0.5 ms
rto:204        当前重传超时 204 ms
wscale:7,7     双方窗口缩放因子都是 7
```

抓握手。

```text
$ tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0 and host 93.184.216.34'
10:31:02.104512 IP 192.168.1.10.51234 > 93.184.216.34.443: Flags [S], seq 2745610289, win 64240, options [mss 1460,sackOK,TS val 1234 ecr 0,nop,wscale 7], length 0
10:31:02.135001 IP 93.184.216.34.443 > 192.168.1.10.51234: Flags [S.], seq 1083562789, ack 2745610290, win 65535, options [mss 1460,sackOK,TS val 98765 ecr 1234,nop,wscale 7], length 0
10:31:02.135120 IP 192.168.1.10.51234 > 93.184.216.34.443: Flags [.], ack 1, win 502, length 0
```

（简化示意）

三点观察：

```text
[S] 是 SYN，[S.] 是 SYN+ACK，[.] 是纯 ACK
ack 2745610290 = seq 2745610289 + 1，SYN 占一个序号
选项里 mss、sackOK、wscale 7 都在第一次握手谈定了
```

Wireshark 里更直观：`Statistics → Flow Graph`，能看到完整的一条竖线时序。

或者用显示过滤器：

```text
tcp.flags.syn == 1 or tcp.flags.fin == 1
```

（简化示意）

握手失败时看内核统计：

```text
$ netstat -s | grep -iE "listen|SYN"
    41234 SYNs to LISTEN sockets dropped
    87 times the listen queue of a socket overflowed
    23 SYNs to LISTEN sockets ignored
```

（简化示意）

```text
SYNs to LISTEN sockets dropped      半连接队列或全连接队列满了
listen queue of a socket overflowed 全连接队列溢出（应用 accept 太慢）
```

再看几个参数。

```text
$ sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog \
         net.ipv4.tcp_syn_retries net.ipv4.tcp_fin_timeout net.ipv4.tcp_tw_reuse
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 1024
net.ipv4.tcp_syn_retries = 6
net.ipv4.tcp_fin_timeout = 60
net.ipv4.tcp_tw_reuse = 2
```

（简化示意）

逐个对上：

```text
somaxconn            全连接队列上限，是 listen(fd, backlog) 的上界
tcp_max_syn_backlog  半连接队列上限
tcp_syn_retries      SYN 重传次数，6 次约 127 秒才放弃（1+2+4+8+16+32+64）
tcp_fin_timeout      FIN_WAIT_2 的存活时间，不是 TIME_WAIT
tcp_tw_reuse         允许复用 TIME_WAIT 的四元组
```

`tcp_syn_retries = 6` 这件事解释了一个常见体验：

连一个被防火墙 DROP 的地址，客户端要卡两分多钟才报 `Connection timed out`。

因为它在耐心地重发 SYN。

## 13. 小结

连接管理这一篇，压成四块：

```text
连接的本质：两端各存一份"聊到第几个字节"的共识。
首部 20 字节起，序号数字节，确认号指"下一个期望"。
三次握手：SYN、SYN+ACK、ACK，防旧 SYN，同步双方序号。
四次挥手：FIN、ACK、FIN、ACK，因为全双工，两个方向分别关。
TIME_WAIT 等 2MSL：保最后 ACK 到达，让旧报文消散。
```

再加一句最实用的：

```text
TIME_WAIT 是主动关闭方的正常状态，
CLOSE_WAIT 是被动关闭方没关，一定是应用的问题。
```
